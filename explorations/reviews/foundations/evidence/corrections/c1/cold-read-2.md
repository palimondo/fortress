## P-7: the goal, and what judges the designers' intent

- **Decided:** The revival finishes the design that Fortress's designers meant, and does not redesign the language. Success is measured by one program, microGPT, compiled to JVM bytecode and running fast. The specification in `Specification/` is the measure of what the designers meant. That specification is the team's Working Draft of February 2011, as the revival revises it, read together with the Types chapter of the team's 2012 restart (P-25). The revival changes the text only to remove contradictions. Where the team's later work, in the compiler or in the type papers, contradicts the original text, the text is changed to follow the later work (P-26). The specification stays a living document that states every change the revival makes to it (P-95 says how). A microGPT written in plain Java is the baseline for the measurement: it is the best possible result, and compiled microGPT aims at it.
- **Applies:** To the whole revival, as its overall goal and as the rule for reading intent. Limits: the specification is revised only to reconcile contradictions with the team's later work, never to add new design. "The language is not redesigned."
- **Requires:** A worker judges intent by the specification. Where a later team source contradicts it, the worker follows the later source and records the change in the specification as P-95 says. A worker must not redesign the language. Performance is measured against the pure-Java microGPT.
- **Unfinished:** The goal itself: microGPT compiled and running fast. The entry gives no number for "fast" beyond "aim at" the pure-Java result.
- **Could not resolve:**
  - "the Types chapter of the team's 2012 restart": I do not know what the 2012 restart was, or where that chapter is. P-25 is cited for it. This is a gap in context, not a language concept.
  - "cited beside it": unclear wording. It does not say whether that chapter has the same authority as the Working Draft, or is only a reference read next to it. P-26 ("later word wins") suggests it outranks the draft where they disagree, but the entry does not say so.
  - "the baseline ... the optimal result, the one to aim at": unclear wording. "Baseline" usually means the floor that a result is compared up from. Here it means the ceiling. The sense can be recovered, but the word pulls the other way.

## P-146: how the compiled checker types `self` in a self-typed trait

- **Decided:** A self-typed trait is `C[\X\]` whose parameter `X` extends `C[\X\]`, such as `Integral[\I extends Integral[\I\]\]`. Inside its method bodies, the compiled checker types `self` as `C[\X\] & X`: both the trait and the implementing type. Method signatures keep the plain trait type, because the POPL 2019 dispatch proofs assume that no declared type puts a type parameter inside an intersection. The one exception is the overloading check's exclusion test, which reads `self` in a signature as `C[\X\] & X` (P-157). The checker refuses an extender that instantiates the trait at some other type. An extender must be a subtype of the static argument it gives, so `object Bad extends Integral[\ZZ32\]` is refused, because `Bad` is not a `ZZ32` (Scala has the same rule). The library's source is not changed: no self-type annotation and no `comprises` clause are added. Walk is unchanged. With this rule, every self-typed method body in the library type-checks except `Integral`'s `numerator`, which each integer type declares itself instead. Reasons: the team's later texts point weakly toward the rule, and peer languages share it. The compiler's prelude writes the self type as a `comprises T` clause, but that form does not bind the library. Naden's Return Type Rule write-up is later than the team's last edits of that clause, and it puts the self type only in bounds (`X extends C[\X\]`), which is how the library writes it. F-225 states the rule as built, with the dates.
- **Applies:** On the compiled checker only, to traits of the self-typed shape above. Limits: method bodies only; signatures stay plain, except inside the exclusion test. Walk is not affected.
- **Requires:** Do not add a self type or a `comprises` clause to the library's text. Do not change walk for this. Do not write signatures with `C[\X\] & X`. An extender of a self-typed trait must instantiate it at itself. Do not expect a `numerator` body in `Integral` to check; each integer type declares its own.
- **Unfinished:** Nothing is stated as unfinished. F-225 calls the rule built. The entry does not say whether walk should ever refuse `Bad`.
- **Could not resolve:**
  - "The library's text gains no self type": a language concept I lack. The skill shows no Fortress syntax for declaring a self type apart from the `comprises T` form and the bound `X extends C[\X\]`. So I am not sure what form is being ruled out, beyond the `comprises` clause, which is named.
  - "except `Integral`'s `numerator`, which each integer type declares instead": two readings. Either the library already declares `numerator` in each integer type (a fact), or a worker must move it there (a requirement). The entry also leaves open whether `Integral` keeps an abstract `numerator`.
  - "an extender must be a subtype of the static argument that it gives": the limit is unclear. The example is a concrete object. The entry does not say what happens to a generic trait that passes its own self parameter on, as in `trait T[\Y extends T[\Y\]\] extends Integral[\Y\]`. `T[\Y\]` is not a subtype of `Y`, so read literally the rule refuses it. I cannot tell whether that is meant.
  - "the team's later texts point, if weakly, toward the rule": the texts are not named here. F-225 may hold them.

## P-153: integer power, split on the base

- **Decided:** Every integer type's `^` returns that same integer type at every exponent. At a negative exponent: base 1 gives 1, base -1 gives its exact power (±1), base 0 raises `DivisionByZero`, and any other base raises `IntegerOverflow`. To get a fraction, a program writes a float or rational base, as in `2.0^(-1)`. Reasons: the Working Draft's power, which gives a rational at a signed exponent, was never built on either path. The only integer-result power the team built is the compiler's prelude's, which gives `ZZ32`, `NN32` and `NN64` each a power of its own type. Overloads choose by type, and no type marks an exponent as negative (a signed integer or a numeral can be either), so the choice goes by the base's type. The exponent's sign is tested at run time, as the library tests signs everywhere (P-80).
- **Applies:** To `^` on every integer type, on both paths. Limits: the split is by the base's static type. An integer base never gives a fraction, whatever the exponent.
- **Requires:** Do not make an integer power return a rational or a float. Test the exponent's sign at run time, not through overloads or sign-refined types. Raise the named Fortress exceptions, never a raw Java exception. A test that wants a fraction uses a float or rational base.
- **Unfinished:** The compiled path. Its own powers give 0 at a negative exponent, give a raw Java exception at base 0, and overflow either silently or with a raw Java exception. Rows 441 and 523 hold this. The entry does not say whether walk's library already follows the rule.
- **Could not resolve:**
  - "Row 441: the same rule on the compiled path, whose own powers give 0 ...": unclear wording, because the sentence has no verb. I read it as "ledger row 441 is the open gap: the compiled path must get this same rule; today its powers give 0 ...". It could also be read as "row 441 records that the compiled path has this rule", which the rest of the sentence contradicts.
  - "and overflow silently or with a raw Java exception (row 523)": unclear wording. It is unclear whether overflow at a non-negative exponent belongs to row 441 with the rest, or to row 523 alone. Nor does it say which of the compiled powers overflow silently and which throw.
  - The exponent's type is not stated. Must it be the base's type, or can it be any integer (or numeral)? For `NN32` and `NN64` bases, the exponent cannot be negative if it has the base's type. The entry does not say whether those types take a signed exponent.
  - Whether `ZZ` (the unbounded integer) is among "each integer type" is not stated. I assume it is.

## P-154: a list is ordered only where its element type is totally ordered

- **Decided:** The library's `List` takes on its lexicographic order only where its element type extends `StandardTotalOrder`. It does so by conditional extension (a `where` form, P-151). Floats and `QQ` are only partially ordered, because NaN and `QQ`'s 0/0 compare with nothing. So on the compiled checker, a list of floats or of `QQ` has no `<`, `CMP` or other comparison, though `=` still works. A pair of floats stays ordered. The curator accepts that mismatch as a cost of the list rule. The rule for tuples is not decided here. No lexicographic trait over partially ordered elements is added now: the team never wrote one, and it touches neither the distance to the switch-over nor microGPT. Reasons: the two lexicographic traits in the team's unfinished draft (`Library/incomplete/advanced/Fortress.PartialTotalOrders.fss:117-140`) both bound the element by a total order, and conditional extension is a form the team wrote (P-151). The draft is not shown to be later than the specification's sentence that lets a list's order be partial where its elements' order is, so it does not count as the team's later word (P-26).
- **Applies:** To the library's `List`, on the compiled checker now. Limits: equality on lists is untouched. Tuples are outside the rule. Ordered lists over partial orders are not built now.
- **Requires:** Do not give a list of floats or of `QQ` comparisons. Do not add a partial-order lexicographic trait. Do not treat the incomplete draft as the team's later word.
- **Unfinished:** Walk's half: walk still gives every list an order (row 774). A partial lexicographic order is left for later, and so is the tuples' rule.
- **Could not resolve:**

  - "the specification's sentence that lets a list's order be partial where its elements' order is": unclear. ## P-12: after the switch-over, walk runs the compiled checker and uses its coercions

- **Decided:** After the switch-over, walk runs the compiled type checker on the programs it runs, which gives them static types. Walk then uses the static coercions that the checker inserts, in place of choosing a coercion from the run-time value (P-59). The curator wants the checker usable on walk's programs. Today `fortress typecheck` checks only against the compiler's prelude, so it does not check walk's programs (F-9). Walk is not changed for this before the switch-over. The step has three parts, and its size is unmeasured: (1) walk runs with the Scala checker on, where today it is off; (2) walk evaluates the `CoercionInvocation` nodes that the checker inserts, which it has no case for today (F-9); (3) the components that walk's programs import are cleared of the checker's errors (F-290 counts them).
- **Applies:** Only after the switch-over. Before it, walk stays as it is and keeps choosing coercions at run time.
- **Requires:** Before the switch-over, a worker must not change walk to run the checker or to use static coercions. After it, the three parts are to be built. Each imported component is cleared of checker errors either before this step or before the first program that needs that component.
- **Unfinished:** All three parts. The size of the work is unmeasured.
- **Could not resolve:**
  - "each before this step or before the first program that needs it": unclear wording. Read loosely, a component may be cleared either before the whole step or later, before the first program that imports it. That second option suggests the step can land with some components still failing. But "this step" could also mean part 3 itself. The phrase "needs it" probably means "imports that component", but it might mean "needs it cleared".
  - The entry does not say what walk does with a program that the checker refuses once the checker is on. A program that runs under walk today can be ill-typed (SKILL, "The phases"). Will walk then refuse it, or warn and run it?
  - "walk's programs": which set this is (every program walk runs, or the suites and the model program) is not stated. I take it to mean every program.

## P-17: unboxed doubles and arrays of unboxed doubles are required

- **Decided:** The compiled code must keep doubles unboxed, and arrays of doubles too. Without that, the revival misses its point. Reasons: a language meant for high performance cannot box its numbers. The specification states the same intent: its chapter on objects lets an implementation copy value objects, floats among them, freely, and its chapter on memory sequences makes a `LinearSequence` of a value type a sequence of unboxed values. Today the code generator boxes every number (an `RR64` is an `FRR64` object). In Java models of microGPT's three array kernels (dot product, matrix product, row lift), boxing is the main cost (F-11). How arrays store doubles, as `double[]`, is P-84's decision.
- **Applies:** To the compiled path's code generator and run time, for `RR64` values and arrays of them. Limits: the entry requires doubles only. It does not say whether other numbers (`RR32`, the integer types) must be unboxed too, though its reason ("cannot box its numbers") covers them all.
- **Requires:** A worker must treat unboxed doubles as a requirement, not an optional optimisation. Array storage follows P-84.
- **Unfinished:** All of it. The code generator boxes every number today.
- **Could not resolve:**
  - "row lift": a term I lack. It is a microGPT kernel, and the skill does not describe it. (It does not block the decision.)
  - "How arrays store doubles, as `double[]`, is P-84's decision": two readings. (a) P-84 decided that arrays store doubles as `double[]`. (b) P-84 decides the storage, and `double[]` is the form under question. I lean to (a).
  - Where "unboxed" must hold is not stated: in locals, fields, parameters, return values, and inside the specialised classes of generics (SKILL says a number stays boxed "also inside a specialised class"). I cannot tell whether the requirement covers all of these, or only arithmetic and array storage.
