## Where this belongs

The checker makes new analyzers constantly: `scala_src/typechecker/OverloadingChecker.scala:288`, `AbstractMethodChecker.scala:88` and `TypeWellFormedChecker.scala:57,66,76,85` each replace their analyzer with an extended one per generic declaration, and `STypeChecker.scala:189,202` extend per generic scope. So a memo on the analyzer would be dropped at every generic declaration; the table is the object whose lifetime is the whole check of one compilation unit, and it is what the two functions read. That is where the memo belongs, and where the prototype's author said it belongs (`explorations/perf-probes/nat/followup.md:96-98`).

The fix is not in a phase or in the library: the two functions answer the same question every time they are asked it, and nothing upstream can make them be asked less often without changing the checker's algorithms, which is not this rung's charter.

## Why the memo changes no answer

**What the two functions read.** `parents(t)` reads `typeCons(n)` for the trait's name, that index's `extendsTypes` and `staticParameters`, and `t`'s arguments, and returns their substitution (`TypeAnalyzer.scala:722-727`). `excludesClause(t)` reads the same index's `excludesTypes`, `extendsTypes` and `staticParameters`, substitutes, and recurses on each substituted supertrait (`:747-762`). `typeCons` is the table's `typeCons` (`TypeAnalyzer.scala:708-710`, `TraitTable.scala:33-74`), and `substitute` is a pure function of its three arguments (`ProjectFortress/src/com/sun/fortress/scala_src/types/TypeAnalyzerUtil.scala:35-60`: a map from parameter names to arguments and a tree walk). Neither function reads the analyzer's `env` or any of the analyzer's memos. So both are functions of the table and the type, which is the whole of the memo's key and owner.

**The table does not change.** `TraitTable` has no mutator: its two constructor parameters, `current` and `globalEnv`, are never reassigned (`TraitTable.scala:32`), and the memo is created with the table and dies with it. What the table reads beneath it does not change during the table's life either: a `CompilationUnitIndex` wraps its type constructors in `CollectUtil.immutable` (`ProjectFortress/src/com/sun/fortress/compiler/index/CompilationUnitIndex.java:41`); the only mutators of a trait's clauses, `ProperTraitIndex.addExcludesType` and `addComprisesType` (`ProjectFortress/src/com/sun/fortress/compiler/index/ProperTraitIndex.java:43-49`), are called from `IndexBuilder.checkTraitClauses` (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/IndexBuilder.scala:235,245,261`), which runs while the index is being built (`:175`), and from the unit-test helper `TypeParser` (`ProjectFortress/src/com/sun/fortress/scala_src/useful/TypeParser.scala:131-132`), which does so before it makes its table (`:173`); `extendsTypes` and `staticParameters` have no setter (`ProjectFortress/src/com/sun/fortress/compiler/index/TraitIndex.java:60,77`). Every place the checker, the desugarer or code generation "changes the trait table" in fact constructs a new one, with empty memos: the eight construction sites are `StaticChecker.java:213`, `Desugarer.java:121`, `CodeGenerationPhase.java:81,179`, `scala_src/typechecker/OverloadingChecker.scala:73`, `scala_src/overloading/OverloadingChecker.scala:52`, `AbstractMethodChecker.scala:58` and `TypeParser.scala:173`, and `TraitTable` has no subclass. A table can outlive a rebuilt index — `StaticChecker` rebuilds the component index after type checking (`StaticChecker.java:248`) and keeps using the analyzer over the old table for the second well-formedness check (`:268`) — but that is the tree's behaviour with or without the memo: the table reads the index it was built over either way, and the memo returns what that table would compute.

**What a hit can return that a recomputation would not.** Keys are compared by `equals`, and the AST's `equals` ignores source spans: `SpanInfo.equals` is true for any two (`ProjectFortress/src/com/sun/fortress/nodes/SpanInfo.java:46-55`), and `TypeInfo.equals` compares only static parameters and where clause (`ProjectFortress/src/com/sun/fortress/nodes/TypeInfo.java:58-73`). So a hit for a type equal to an earlier key returns the earlier call's result, whose substituted arguments carry the earlier call's spans and the earlier call's parenthesized flags: `TypeInfo.equals` and `TypeInfo.generateHashCode` (`ProjectFortress/src/com/sun/fortress/nodes/TypeInfo.java:58-72`, `:81-87`) leave out the `_parenthesized` field `TypeInfo` inherits from `ParenthesizedInfo` (`ProjectFortress/src/com/sun/fortress/nodes/ParenthesizedInfo.java:24`), just as they leave out the span (the second skeptic's correction). Nothing else can differ: `TraitType.equals` covers the name, the arguments and the trait's static parameters (`ProjectFortress/src/com/sun/fortress/nodes/TraitType.java:74-95`), which is all `typeCons` and `substitute` read. The tree's normalize memos already have this property (`TypeAnalyzer.scala:537-545` stores a normalized trait type under its name and arguments). I looked for both where they could show — located error messages, the serialized checked ASTs, which carry spans and the flag, and the class files — and neither shows: see the differentials below.

**Recursion.** `excludesClause` calls itself from inside its own computation, so the memo cannot use `ConcurrentHashMap.computeIfAbsent`, whose mapping function must not modify the map (the JDK documents this, and detects some cases with `IllegalStateException: Recursive update`); `memo` does `get`, computes outside the map, then `putIfAbsent` (`TraitTable.scala:89-96`), the same order as the tree's ten memos. A cyclic hierarchy recursed without end before the memo and still does; the memo stores nothing until a computation returns, and an exception (`typeCons`'s "Not in the trait table", a `ClassCastException` on a non-trait index) stores nothing either.

**Threads, the column the batch record names.** The checker runs on one thread: the JFR recording's 39,287 samples were "all on thread \"main\"" (`explorations/perf-probes/nat/followup/f3-jfr-top.txt:8`), and there is no thread, executor or fork-join use in `ProjectFortress/src/com/sun/fortress/compiler/`, `scala_src/` or `repository/` (the one `ForkJoin` hit, `compiler/codegen/CodeGen.java:651`, is a descriptor emitted into generated code). The four-thread gate runs execute compiled programs, and no file under `runtimeSystem/` names `TraitTable` or `TypeAnalyzer` (the 37 files that do are all compiler-side: under `compiler/`, `scala_src/` and `repository/ForeignJava.java`). So no two threads can reach one table in today's tree. The maps are `ConcurrentHashMap`s all the same: values are immutable Scala sets computed from immutable inputs, so two threads that race on one key compute equal values, one `putIfAbsent` wins, and `memo` returns the stored one (`TraitTable.scala:93-94`).
