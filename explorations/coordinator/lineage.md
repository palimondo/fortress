# Where this repository's history comes from

## The facts

- `palimondo/fortress` is a GitHub fork, created 2018-05-10, of `sirinath/fortress` (GitHub API: `fork: true`, `parent` and `source` both `sirinath/fortress`). That repository is a git conversion of the project's java.net Mercurial repository (it carries a `refs/import/*` namespace; the conversion mechanism is inferred, not verified). Its `master` is `a874948ac`; its relic branches and its `1.0` tag (`0e8ede7e7`) match this repository's `origin/*` refs exactly. Nobody in the tree or the transcripts had named sirinath before this note.
- The trunk: `git rev-list --count a874948ac` = 5,397; with the twelve relic branches 5,558. The true root is `72ae6881b` (jm143038, 2007-01-04); the trunk tip `a874948ac` (karl.naden, 2012-08-31). The conversion cut 146 parent links, so `a874948ac` has 147 parentless roots and a first-parent walk from the tip stops after six commits at `5a68404fd` (2012-07-19); `research/authorship.md:14-22`, corrected in `6beb45ec7`. Pavol has no commits between 2013 and 2026.
- The third-party port: `pluckyporcupine/fortress` is exactly one commit, `eab48aa6d` ("Initial commit.", author field "Matt Chelen", 2018-10-11), a squash based on a June 2012 tree, `build.xml` at Scala 2.10.7 and Java source level 1.9, README saying compiled programs do not run. It shares no git history with this repository.
- The graft: `8fe1daa8f` (2026-08-18, session 01LjDz79) copied 1,506 of that commit's files onto `a874948ac` (1,493 added, 13 modified); `c353a7676` regenerated the AST sources. One graft commit, not several. The instruction came from the HANDOVER.md of an earlier chat session (redacted in the archive; the compaction summary of 2026-08-19 01:58 records the prescription).
- What became of it: the old Scala jars removed in `439604f53`; the port's README replaced in `b7f53317d`; its scratch files and `NOTES.md` removed in `bbd34ca2a`; the vendored BCEL (388 files) removed in `f7c4bf0f2`. The spike `73f598202` (`spike/scala-upgrade`) showed the build revives on JDK 8 with five files and nothing from the port. Branch `clean-ladder` (14 commits, tip `8332bd34f`, revival commit `f39bee468`) was rebuilt directly on `a874948ac` with no graft.
- The rebuild never replaced `main`: `origin/main` still descends from `8fe1daa8f`; `git merge-base main origin/clean-ladder` is `a874948ac`. Pavol's plan to rename `clean-ladder` to `main` (transcript, 2026-08-23 19:13) is recorded nowhere as done. What the graft still leaves in `main`'s tree, by blob comparison: 6 of its 13 modified files byte-identical to the graft's version (`FTypeTuple`, `NodeFactory`, `InstrumentedParserGenerator`, `Util`, `ParserMaker`, `RatsUtil`) and 72 of its 1,493 added files (63 generated `nodes/` files, `Library/FortressAst.fsi`/`.fss`, two `contrib/Atom/language-fortress` files, the ant 1.9.10 jars, `default_repository/caches/global.map`); 406 added files are gone and 1,015 have changed since.

## Verification against Pavol's recollection (the same worker, re-briefed)

Pavol's recollection: main restarted from the sirinath copy and redid the modernization cleanly; nothing from the port should be on main. Checked:

- History: `8fe1daa8f` is an ancestor of `origin/main` (`git merge-base --is-ancestor`); `origin/clean-ladder` (`8332bd34f`) is not; their merge base is `a874948ac`. After his "I still will need to rename the main branch to that one" (transcript bdff267d part 000, 2026-08-23 19:13) and the coordinator's "tomorrow you run the tag script and rename the branch" (19:13), the same session went on committing on `claude/handover-reading-vn8zgr` and pushing it to `main` from 22:05 on, through the microGPT work. No transcript records a rename, merge or cherry-pick of `clean-ladder`; no `modernization/*` tag was ever pushed. One run did start from `clean-ladder`: `codex/astra-microgpt` (`explorations/astra/README.md:3`), whose documents alone came into main. So main continued the grafted line; the clean restart exists only as the unmerged branch.
- Working code: of the 78 byte-identical blobs, 4 are identical in `clean-ladder` too (the `import xtc.parser.Module` disambiguation in four parser files, made independently in `69b01f695`), nothing owed. 74 exist because of the graft: 63 generated `nodes/` files, `Operators.java`, `Library/FortressAst.fsi`/`.fss` (build output the 2012 trunk did not commit and `clean-ladder`'s `.gitignore:77-84` ignores; main tracks all 1,071 `nodes/` files); `FTypeArrayList.java` plus two lines in `FTypeTuple.java`, the port's fix for the JDK 8 `TreeSet` `ClassCastException`, whose `compareTo` always returns 0, harmless because both sets get one element, and **the only piece of the port main's code runs** (`clean-ladder` fixes the same bug with `listComparer`, `f39bee468`); cosmetic edits in `NodeFactory.java`; the unused ant 1.9.10 jars; the unused `contrib/Atom/language-fortress/`; the tracked whitespace-only `global.map`. Graft lines inside files edited later: `build.xml` (a dead `checkEnv` 1.9 condition, a dead `scala-lib` classpath entry), seven `@Deprecated` in `NamingCzar.java`, three `case e:Throwable` in `STypeChecker.scala` (same behaviour), one `.gitignore` comment.
- Everything else main differs from `clean-ladder` in (1,232 files) is the tracked `nodes/`, the revival's tests and library, compiler, runtime and checker edits after `sealed-tree`, the `experiment/` briefs, and the launcher scripts main's own rungs edited.

Verdict: on history the recollection is wrong, on working code largely right. Removable with no behaviour change, for the cleaner pass: the `FTypeArrayList` fix replaced by `clean-ladder`'s two lines, the dead jars, the Atom package, `global.map` (then ignored; one gated run to confirm the interpreter recreates it), the dead `build.xml` lines, the cosmetic edits; untracking the generated sources changes the workflow CLAUDE.md describes (stale-AST regeneration, committed determinism).
