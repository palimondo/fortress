# Is boxing the ceiling on the compiled path? A measurement

The record says the bytecode compiler lowers `RR64` to the runtime class
`FRR64` and emits no `DADD` (`explorations/repo-internals.md:129`), and that
compiled microGPT-shaped code runs 6.8-8.9x faster than the walk interpreter
(`explorations/compiled-path-gaps.md` §1b). From those two facts it is natural
to infer that *boxing is the ceiling* and that unboxed doubles and `double[]`
are the first thing performance needs. This probe turns the inference into a
measurement: the same loop in the interpreter, in compiled Fortress, and in
Java over boxed objects and over primitive `double`, all on one host with one
JDK, plus the generated bytecode that settles what "boxed" means here.

**Short answer: the inference is half right and the ordering is wrong.**
The compiled loop is 156x slower than the same loop over primitive `double` in
Java. Boxing — a fresh heap object per arithmetic result, allocation and
indirection included, measured with escape analysis defeated — accounts for
**2% of that gap**. The other 98% is three things the generated code does per
iteration that have nothing to do with the representation of a number: it
re-derives each float literal by formatting a `double` to a decimal string and
parsing it back, it guards every read and write of the loop's accumulator with
a transaction check whose debug message is built eagerly, and it runs the
"sequential" `for` loop as a recursive binary subdivision over boxed indices.

## 1. How it was run

Host: Linux 6.18.44-fc-v33 x86_64, 4 cores, 15 GB. JDK 25.0.3 (Ubuntu build)
for everything — `fortress`, `javac`, `java`, `javap` — via
`source /home/user/fortress/experiment/env.sh` (`FORTRESS_THREADS=1`,
`JAVA_FLAGS=-Xmx4g -Xss64m`); the Java forms were run with the same
`-Xmx4g -Xss64m`. Date 2026-09-15. Tree at HEAD; nothing outside
`explorations/perf-probes/` was modified.

The compiled path needed the full library-order rebuild from
`explorations/repo-internals.md` (the bytecode cache was empty). Caches were
wiped with `rm -rf default_repository/caches/*_cache
default_repository/caches/logs` (leaving the tracked `global.map`), then:

| step | wall, cold | wall, warm analysis cache |
|---|---|---|
| `fortress compile LibraryBuiltin/AnyType.fss` | 19.1 s | 2 s |
| `fortress compile LibraryBuiltin/CompilerBuiltin.fss` | 79.5 s | 81.3 s |
| `fortress compile ../Library/CompilerLibrary.fss` | 14.5 s | 13.7 s |
| `fortress compile ../Library/CompilerAlgebra.fss` | 1.9 s | 1.4 s |
| `fortress compile ../Library/CompilerSystem.fss` | 1.7 s | 1.5 s |
| **total** | **117 s** | **100 s** |

(`libcompile.out`, `libcompile2.out`.) Two passes were needed, and the reason
is worth recording: the first pass reported `exit=0` for every step and left
`default_repository/caches/bytecode_cache/` **empty** — no jars at all, though
the analysis caches were populated (hence the warm second column). Re-running
the identical commands one at a time produced the jars. Per-program compiles
are 0.7-2.2 s (`compile-benches.out`), matching the earlier characterization. A
component whose source is unchanged and whose jar exists is not recompiled, so
`touch` the source when the library underneath it has been rebuilt.

Timing: the loop only, with `nanoTime()` immediately around the `for` in the
Fortress sources (`bench1t.fss`, `bench2t.fss` — identical to `bench1.fss` and
`bench2.fss` character for character in their arithmetic) and `System.nanoTime`
around the loop in the Java sources. Three runs of each form, each in its own
fresh JVM, median reported. Every run's output is kept: `interp-runs.out`,
`timings.out`, `timings-ablation.out`; `medians.sh` derives `medians.tsv` from
those files rather than from anything typed by hand. The interpreter runs
(`interp-runs.out`) overlapped with a few short `javac` invocations; every
other run in `timings.out` and `timings-ablation.out` was made sequentially by
`run-all.sh` with the machine otherwise idle.

All forms of bench1 print `0.8646647302294265` and all forms of bench2 print
`1812692.3699162973` — interpreter, compiled Fortress and both Java forms agree
to the last digit.

## 2. bench1 — the scalar `RR64` loop

`for i <- seq(1#20000000) do acc := acc 0.9999999 + 0.0000001 end`
(juxtaposition is multiplication). 20 M iterations.

| form | loop, s (median of 3) | ns / iteration | x primitive Java |
|---|---|---|---|
| Fortress interpreter (walk) | 52.4383 | 2622 | 877x |
| **Fortress, bytecode compiler** | **9.3441** | **467** | **156x** |
| Java, full model of the generated loop | 8.0123 | 401 | 134x |
| Java, boxed + cell + transaction checks | 3.3815 | 169 | 56.5x |
| Java, boxed + literal decimal round-trip | 3.0976 | 155 | 51.8x |
| Java, boxed, escape analysis defeated | 0.2496 | 12.5 | 4.17x |
| Java, boxed `java.lang.Double` | 0.1504 | 7.5 | 2.52x |
| Java, boxed `FRR64`-shaped object | 0.1414 | 7.1 | 2.36x |
| **Java, primitive `double`** | **0.0598** | **3.0** | **1.00** |

Interpreter / compiled = **5.6x** (the note's 6.8x was startup-adjusted wall
clock on a contended machine; this is loop-only on an idle one).

The Java forms, in `java/`: `Bench1Prim` is the primitive loop. `Bench1Boxed`
allocates a fresh object per arithmetic result and per literal through a class
copied from `runtimeValues/FRR64.java` (final class, final `double` field,
private constructor, static `make`, no caching), with the arithmetic written in
the shape of the generated native wrapper — `getValue(); getValue(); <op>;
make(...)`. `Bench1BoxedDouble` is the same over `java.lang.Double` and agrees
within noise, so nothing here depends on the box's identity. `Bench1Cell` adds
the accumulator cell: the box is stored through a `volatile` field, as
`runtimeValues/MutableFValue.java` does, which also prevents the JIT from
scalar-replacing the boxes — it is the honest upper bracket on boxing, and it
is still only 4.2x primitive. `Bench1CellTx` adds the two
`BaseTask.inATransaction()` calls the generated body makes. `Bench1BoxedLit`
adds the `FFloatLiteral` decimal round-trip. `Bench1Full` models the whole
generated loop, recursive generator and boxed indices included, and lands
within 14% of the measured compiled time — which is the evidence that the named
costs are the actual ones.

### The same decomposition inside Fortress

Four compiled Fortress programs, identical but for the loop body
(`bench1a/b/c.fss`, same 20 M iterations, same host, same timing method):

| body | loop, s | delta | what the delta buys |
|---|---|---|---|
| `()` | 0.6272 | — | the generator: recursive subdivision, boxed index, closure call |
| `acc := acc` | 6.5532 | +5.9260 | the `MutableFValue` cell: volatile read + write, two transaction checks |
| `acc := acc + 0.0000001` | 7.8245 | +1.2713 | one float literal + one add |
| `acc := acc 0.9999999 + 0.0000001` | 9.3441 | +1.5196 | a second literal + a multiply |

and the Java ladder for the same steps: boxing with the cell costs
0.2496 − 0.0598 = **0.19 s**, the two transaction checks cost
3.3815 − 0.2496 = **3.13 s**, and the two literal round-trips cost
3.0976 − 0.1414 = **2.96 s**. The two ladders agree: what the Fortress ladder
charges to the cell (5.93 s), the Java ladder splits into 0.19 s of boxing and
3.13 s of transaction checks.

## 3. bench2 — user objects, two `opr` methods per iteration

`for i <- seq(1#2000000) do s := (s + V(1.0)) DOT V(0.9999999) end` with
`object V(data: RR64)`. bench2's shape does allow the three forms, plus a
fourth that is only possible here: `V` with a *primitive* `double` field, which
separates "a user object is allocated four times per iteration" (which Java
does too) from "the number inside it is boxed".

| form | loop, s (median of 3) | ns / iteration | x primitive Java |
|---|---|---|---|
| Fortress interpreter (walk) | 13.7497 | 6875 | 1974x |
| **Fortress, bytecode compiler** | **1.5924** | **796** | **229x** |
| Java, boxed `V` + literal round-trip | 0.3887 | 194 | 55.8x |
| Java, boxed: 4 `V` + 4 `FRR64` per iteration | 0.0454 | 22.7 | 6.52x |
| Java, 4 `V` per iteration, primitive field | 0.0273 | 13.7 | 3.92x |
| **Java, primitive `double`** | **0.0070** | **3.5** | **1.00** |

Interpreter / compiled = **8.6x**, matching the note's 8.9x.

Boxing the numbers inside the user objects costs 6.52 − 3.92 = 2.6x of a 229x
gap; allocating the four `V` objects costs 3.92x and is what the *program* asks
for, not what the compiler adds.

## 4. The bytecode: "boxed" shown, not inferred

`javap -c` on the generated classes, dumps kept in `javap/` (commands in
`javap/extract.sh`). bench1's loop body is compiled to a closure class
`bench1$\=fn@5\!7-28` implementing `Arrow<FZZ32,...>`; its `apply` **is** the
loop body. Quoting `javap/bench1.loopbody.javap.txt` in full for the arithmetic
(offsets 26-58):

```
        26: checkcast     #42     // class com/sun/fortress/compiler/runtimeValues/FRR64
        29: checkcast     #42     // class com/sun/fortress/compiler/runtimeValues/FRR64
        32: ldc2_w        #43     // double 0.9999999d
        35: invokestatic  #50     // Method …/runtimeValues/FFloatLiteral.make:(D)L…/FFloatLiteral;
        38: invokestatic  #56     // Method fortress/CompilerBuiltin.coerce_RR64:(L…$FloatLiteral;)L…/FRR64;
        41: invokestatic  #60     // Method fortress/CompilerBuiltin.juxtaposition:(L…/FRR64;L…/FRR64;)L…/FRR64;
        44: checkcast     #42     // class com/sun/fortress/compiler/runtimeValues/FRR64
        47: ldc2_w        #61     // double 1.0E-7d
        50: invokestatic  #50     // Method …/runtimeValues/FFloatLiteral.make:(D)L…/FFloatLiteral;
        53: invokestatic  #56     // Method fortress/CompilerBuiltin.coerce_RR64:(L…$FloatLiteral;)L…/FRR64;
        56: invokestatic  #65     // Method fortress/CompilerBuiltin."+":(L…/FRR64;L…/FRR64;)L…/FRR64;
```

No `dmul`, no `dadd`, no `dload`: every operand and every result is an `FRR64`
reference. The multiply forwards through two more frames before a primitive
ever appears — `fortress/CompilerBuiltin.juxtaposition` does an
`invokeinterface` on `RR64."juxtaposition?0"`
(`javap/CompilerBuiltin.juxtaposition_RR64.javap.txt`), whose default trait
method calls the native wrapper
(`javap/CompilerBuiltin.RR64.DefaultTraitMethods.javap.txt`), and only there
(`javap/simpleDoubleArith.wrapper.javap.txt`) does the arithmetic happen:

```
  public static …FRR64 doubleMul(…FRR64, …FRR64);
         1: invokevirtual #13   // Method …/FRR64.getValue:()D
         5: invokevirtual #13   // Method …/FRR64.getValue:()D
         8: invokestatic  #46   // Method …/nativeHelpers/simpleDoubleArith.doubleMul:(DD)D
        11: invokestatic  #35   // Method …/runtimeValues/FRR64.make:(D)L…/FRR64;
```

unbox, unbox, `dmul` (inside the helper), **allocate**: `FRR64.make` is
`return new FRR64(x)` and `FRR64.java` has no cache. So the record's claim is
exact. But the same excerpt shows the two costs that turn out to dominate:

1. **Each float literal is rebuilt on every iteration** (offsets 35/38 and
   50/53). `FFloatLiteral` stores the literal *as a `String`*: its constructor
   is `this(new Double(val).toString())` and `asRR64()` is
   `FRR64.make(Double.valueOf(val))`
   (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`).
   A constant in the source becomes a `double`→decimal format plus a
   decimal→`double` parse, 40 M times in this loop.
2. **The accumulator is a transacted heap cell.** Offsets 0-26 and 59-91 of the
   same method guard the read and the write with `BaseTask.inATransaction()`,
   and `BaseTask.java:246-254` builds its debug message at the call site —
   `debug("inATransaction: ftr = " + ftr + " task = " + ftr.getTask())` — with
   `debug` a non-final `private static Boolean` that is `false`. The message is
   constructed on every call. The cell itself (`MutableFValue.value`) is
   `volatile`.

A third cost is one level up, in the library rather than in codegen:
`bench1.javap.txt` shows the `for` lowered to `CompilerLibrary.seq(...)` then
`SeqGeneratorZZ32.loop(Arrow)`, and `Library/CompilerLibrary.fss:340-348`
implements the *sequential* loop as `countedseqloop`, a recursive binary
subdivision of the index range that allocates `FZZ32` boxes for `lo+hi`, the
midpoint and `mid+1`, calls a filter predicate closure per element, and reaches
the body through an interface call.

bench2 is the same story one level out: `javap/bench2.V.javap.txt` shows `V`'s
field declared `FRR64` and `+?0?`/`DOT?0?` forwarding to
`CompilerBuiltin."+"`/`juxtaposition` and allocating a fresh `V` per result,
and `javap/bench2.loopbody.javap.txt` shows the same per-iteration
`FFloatLiteral.make` / `coerce_RR64` pair for each of `1.0` and `0.9999999`.

## 5. What the numbers settle

The gap between compiled Fortress and primitive Java on bench1 is 9.284 s over
20 M iterations, a factor of 156. The Java boxed form brackets boxing from both
sides: 2.4x primitive when the JIT can see through the allocations, 4.2x when
the values are forced through a volatile cell so it cannot — that is 0.19 s, or
**2.0% of the gap**; even the widest bracket leaves 97% unexplained. Boxing is
therefore not the ceiling: the compiled path is roughly 40x away from the best
a boxed representation could already do. The rest of the gap is not "dispatch"
in the abstract either — it is three named, measured, separately fixable
things. About 30% (2.79 s Fortress-measured, 2.96 s in the Java model) is the
per-iteration decimal round-trip of the two float literals through
`FFloatLiteral`'s `String`, which constant-folding the literal coercion at
compile time removes outright. About 34% (3.13 s in the Java model, inside the
5.93 s the Fortress ladder charges to the accumulator) is the eagerly built
debug string inside `BaseTask.inATransaction()`, called twice per iteration — a
one-line fix: guard the message with the flag. About 7% (0.63 s) is the
generator, a recursive binary subdivision over boxed indices with a closure
call per element where a counted loop would do. What remains, roughly 2.8 s, is
the genuinely representational part: the volatile transacted cell, the four
allocations, the interface hop from `CompilerBuiltin.juxtaposition` to the
native wrapper, and the `checkcast`s — and *that* is what unboxed doubles and
`double[]` would attack. Two consequences for the worklist. First, the cheap
fixes come first: literal folding and the debug string are small local changes
worth an estimated 2.7x on this loop between them, against a much larger job
for unboxing. Second, unboxing remains the endgame — after the cheap fixes the
loop would sit near 3.4 s, still ~57x primitive Java — but it is entangled with
the same three items, since a compiler that keeps a `double` in a local has no
literal box to round-trip and no cell to transact. On bench2, where the program
itself asks for four object allocations per iteration, the same picture holds
with a larger representational share: boxing the `RR64` inside `V` costs 2.6x
of a 229x gap, and the user objects the program does ask for cost 3.9x.
