# The vocabulary of Run C4: habit or limit?

Pavol's question, in his words: the array vocabulary of Run C4 (`explorations/run-c4/src/FlatArrays.fsi`, `.fss`) "looks like code after type inference and specialization for our specific use case: specific type combinations, operator overloading, nothing of the Fortress-specific flavour where you declare mathematical properties in types and inherit implementation from traits. Is there a good reason, or did the workers go down the object-oriented and functional patterns they know from other languages without taking advantage of the Fortress specifics?"

This report answers it declaration by declaration, with a running probe behind every verdict. The probes are the `v*.fss` files in this directory, each with its `.out` (exit 0) or `.out.N` (a failed run, kept), run by `./run.sh Name [cold]` from this directory on the walk interpreter, JDK 25, `FORTRESS_THREADS=1`, the source path `.` then `run-c4/src` then the shipped libraries (`run.sh` sets it); `cold` wipes the probe's own cache entries first, because the Meet-Rule rejection fires only on a cold parsed cache (ledger row 98). `FlatArrays2.fsi`/`.fss` is the vocabulary with every habit removed; `Smoke1.fss`/`Smoke2.fss` are one program run against `FlatArrays` and against `FlatArrays2`, and `Time1`/`Time2` the same for cost. The ledger rows cited are `explorations/fortress-gap-ledger.md`.

The count: `FlatArrays.fsi` declares 38 names (`grep -cE '^(opr |object |[a-z][A-Za-z0-9]*(\[|\())'`); with the two postfix `^T` operators the model declares itself because an api cannot (row 133), the vocabulary is 40 declarations, which is the number in the question, and the table below has 40 rows.

## The short answer

Fortress's trait algebra gives implementation to a type that declares it extends the trait. The vocabulary operates on the library's own array objects (`__DefaultVector`, `__DefaultMatrix`, `__DefaultArray3`), which already extend what they extend and cannot be given more from a component; and what they extend is thin. So the "Fortress-specific flavour" is available in exactly one place, and the vocabulary has it: the arrays are the library's `Vector`/`Matrix`, which inherit `+`, `-`, unary `-` and `zero` from `AdditiveGroup` (v01a), and C4 never redeclares those. Everything else in the vocabulary is a declaration because the library has no trait that would supply it: `×` is excluded from arrays by design, scalar extension has no trait at all, rank 3 extends no algebraic trait, and reshape, plane, gather, outer product and ravel do not exist in the library. That said, the vocabulary does carry habits, in its shapes more than in its count: `RR64` hard-wired where `T extends Number` serves every element type (v04), `nat` parameters on signatures that do no dispatch, four aliases of one library call, two internal views exported for no caller, a `transpose` that the library's `.t()` already spells, and one operator (`diag(v) m`) that a Matrix view would make the library's product, at a measured price that justifies keeping it. Removing the habits takes the api from 38 declarations to 28 (40 to 30 with the model's `^T` pair) with the same numbers on a 24-line smoke; the count of 13 elementwise operators is irreducible on this library.

Habit against forced, over the 40: 10 are habits (four constructor aliases, the matrix `transpose`, `row` and `row3`, two of the four `rows` overloads, and the `Diag` product operator, that last one a habit only by count, since the native form costs 54× on its line); 30 are forced in count, of which 19 are habits in shape (the 13 operators specialised to `RR64`, six signatures carrying `nat`s that dispatch nothing) and 11 are as they must be.

## The five questions

**(1) Can the elementwise operators be inherited through the library's algebraic traits, and does `Array[\RR64,I\]` already carry `+`, `-`, `×` at any rank?** Rank 1 and 2 carry `+`, `-`, unary `-` and `zero`, from `AdditiveGroup` through `Vector` and `Matrix` (v01a lines 1-2), and C4 uses them without a declaration. Rank 3 carries nothing: `Array3` extends `Rank3` and `StandardMutableArrayType` and no algebraic trait (`FortressLibrary.fsi:1652-1655`), so `t + t` finds no declaration at all (v01b, the candidate list of every `+` in scope has no rank-3 member) and a runtime-built rank-3 array is neither an `AnyVector` nor an `AnyMatrix` (v01a line 8). `×` reaches no rank: `Vector` and `Matrix` are declared `excludes { AnyMultiplicativeRing }` (`FortressLibrary.fsi:1460-1462`, `:1578-1580`) because juxtaposition on them is the inner product, so `m × m` has no declaration (v01c); row 109 recorded the absence, this is why. Can a component supply it by extending the trait? Three ways, all tried, all fail: (a) a carrier extending both `Matrix` and `MultiplicativeRing` is accepted by the interpreter despite the exclusion and its `×` works, but its juxtaposition becomes the ring's elementwise product, so `h h` is no longer the matrix product (v02b line 1), and the inherited `+` dies with `** bug! MethodClosure +(self:AdditiveGroup[\T\],other:T):T ... has neither body nor def` because the carrier now has two `AdditiveGroup` instantiations (v02 line 3); (b) a carrier extending `Matrix` and a user trait `Elementwise`, overriding `replica` so that `map`, `ivmap`, `+` and scaling keep the carrier's type, sheds it at `.t()` and at the product, which allocate `matrix[\T,n,m\]()`, so `(h h) ⊙ h` fails (v03, lines 6-8); (c) the spec's bound `T extends AdditiveGroup[\T\]` is not met by `RR64`, which extends `AdditiveGroup[\Number\]` (v04b, no matching overload for an `RR64` array). Scalar extension (`a + s`) has no trait in the shipped library at all; the spec's algebraic-constraints library that would carry it does not ship (row 37). What does work, and is the native form C4 missed: one declaration per operator generic in the element type by its bound and in the index type, `opr +[\T extends Number, I\](a: Array[\T,I\], s: T)`, which serves `RR64` and `ZZ32` arrays at every rank and coexists with the library's own `opr +(Array[\ZZ32,ZZ32\], ZZ32)` (v04; Smoke2 line 24 gives integer keys `ks × ks`, which Smoke1 cannot). The count of 13 stays: no mechanism derives `s + a` from `a + s`, or `a > s` from anything.

**(2) One declaration generic in `I` for `exp`, `log`, `SQRT` and the scalar forms; why four `rows` and two `transpose`?** Yes for the elementwise functions, as row 161 established and Smoke2 lines 1-4 repeat at rank 1, 2 and 3; their bodies can even be `a.map[\RR64\](exp)`, the library's scalar function passed as a value (v09 lines 2-5), though the declaration stays so that the model reads `exp(z)` and not `z.map[\RR64\](exp)` with its mandatory static argument (row 21). The four `rows` are two arities times two ranks; the arity pair is forced (a monadic and a dyadic function type are different types), the rank pair is not: a generic index type gives no way to walk rows, but one `rows[\I\]` with a `typecase` on `AnyMatrix` merges the api surface to two declarations with the two bodies inside (v05; `FlatArrays2` does this, Smoke2 lines 16-19). This is a choice, not a limit: C4's four overloads are rank dispatch by the library's own `Rank1`/`Rank2` exclusions (row 214), which is the language's idiom, and the typecase is the same dispatch written by hand. The two `transpose`s: the Matrix one is a habit, because the library's `.t()` can follow a call where `^T` cannot, `onehot(ks, 5).t() dx` runs (v17); the rank-3 one is forced, `Array3` has no `t()` (v10 line 5; row 246).

**(3) Can the views be the library's own array-view machinery?** In part, at a cost. `view(p, off, nr, nc)`: a range subscript of a flat vector is a real zero-copy slice but rank 1, and the library has no reshape (`lib-grep.txt`; v14), so a matrix over a slice is a view object, which is the library's own idiom for a runtime shape (row 150). `row`: the library's `m[i,:]` is a writable zero-copy row and the row lift runs on it, `(out[i,:]).assign(f(m[i,:]))` (v06 lines 3-4), and it carries `SUM`, `|x|` and every index-generic operator; what it lacks is the vector algebra (row 54), which the model needs only for `x DOT x` in `rmsn` and `p DOT dy` in `sm_b`; one `opr DOT` over `Array[\RR64,ZZ32\]` beside the library's generic `Vector` `DOT` is accepted and serves the library row (v12, v12b). So `row`, `row3`, `RowView` and `Row3View` can go, and did in the first `FlatArrays2` (`FlatArrays2.libview.fss.txt`, `Smoke2.libview.out`: identical numbers). But the library's `m[i,:]` is built by `narrowToRange`, four `reflect`s and two objects per row (`FortressLibrary.fss:2363`, `:2330-2337`) and reads through two indirections: 162 ms against 32 ms for a six-line user view on the same lift, the user `DOT` being no part of it (v20). So `FlatArrays2` keeps one private `RowView` extending `Vector` (row 226's idiom) and exports no row: the habit was exporting an internal, not writing it. `row3` is then `row(plane(t, p), i)`. `plane`, `heads`, `unheads`: forced, the library's rank-3 subarray `t[(p,0,0)#(1,b,c)]` is rank 3 with a unit axis, not a Matrix, and there is no reshape (v10 lines 1-3; row 246). `Diag`: a `Diag` that is a `Matrix` view makes `diag(v) m` the library's product with no operator of its own (v07 lines 1-3, identical numbers), at 13× the row-scaling operator's cost at n = 16 and 54× at n = 64 (v07 line 4; Time1/Time2: 26 ms against 1499 ms), which is about 1.4 s of a 28 s batch-4 step; C4's operator is the right choice and the habit is only in the count.

**(4) Can the products be one generic declaration?** No, and they should not be: the matrix product is the library's, the row scaling is a different function, and the batched product is a third. What a probe adds: a user product generic in the index type, `opr juxtaposition[\I\](x: Array[\RR64,I\], y: Array[\RR64,I\])`, is accepted beside the library's `Matrix` product and dispatches by specificity, `m m` stays the library's product and `t t` takes the user's (v08), so the batched product needs none of its six `nat` parameters; `FlatArrays2` declares it over `Array[\RR64,(ZZ32,ZZ32,ZZ32)\]` (Smoke2 line 14). The one place the `Array3[\RR64,0,a,0,b,0,c\]` spelling is forced is the model's own `^T` pair: `Array[\RR64,(ZZ32,ZZ32,ZZ32)\]` beside `Matrix[\RR64,r,c\]` in one operator family is rejected, "at least one pair of parameters must have excluding types", because `Array[\E,I\]` carries no `Rank` (v18), while `Array3` is `Rank3`, which `Matrix`'s `Rank2` excludes, and that pair calls the nat-free `transpose` without trouble (v18b).

**(5) Which of the 40 are irreducible?** The 13 elementwise operators (in count; their `RR64` is a habit), `Diag` and `diag` (no diagonal in the library), the rank-3 `transpose`, `view`, `heads`, `unheads`, `plane`, the batched product, the plane-wise `+`, the two arities of `rows`, `gather` (no index-vector subscript, v11), `onehot` (no outer product, `lib-grep.txt`), `pick`, `flat` (no ravel or catenate; a paste of matrices fails, row 106; varargs is the form, row 130), and the model's two `^T`. Thirty of forty.

## B. FlatArrays2

`FlatArrays2.fsi` declares 28 names against `FlatArrays.fsi`'s 38 (30 against 40 with the model's `^T` pair, which does not change): the 13 elementwise operators generic in `T extends Number` and `I`; `Diag` as a `Matrix` view and `diag`; `view`, `heads`, `unheads`, `plane`, `transpose` with no `nat` on any signature; the batched product and the plane-wise `+`; two `rows`; `gather` generic in `T`, `onehot`, `pick`, `flat`. Gone: the four constructor aliases, the matrix `transpose`, `row`, `row3`, two `rows` overloads and the `Diag` product operator. The component (`FlatArrays2.fss`, 155 lines against 163 by a rough filter that drops blank and comment-only lines) has six private objects where C4 has seven: `PView`, `HeadsView`, `UnheadsView`, `PlaneView`, `Transposed3` as before but over `Array[\RR64,…\]` bases with their shapes from `reflect`, and one `RowView` in place of C4's `RowView` and `Row3View`.

The smoke: `Smoke1.fss` and `Smoke2.fss` are one 24-line program (`smoke_body.txt`) covering every declaration, the model's three vector functions with `x DOT x`, write-through of `view`, `heads` and `plane`, the batched product, the plane-wise sum, all four row lifts, the keys and `flat`, run against the two apis; `diff` of `Smoke1.out` and `Smoke2.out` is empty through line 23, and line 24 is `ks × ks` on integer keys, which `FlatArrays2` gives and `FlatArrays` cannot (`Smoke1.out.1`, its failure). Two earlier failed runs of each are my own smoke's fault, a key out of range (`Smoke1.out.0`, `Smoke2.out.0`).

The cost (`Time1.out`, `Time2.out`, batch-4 shapes, ms per operation): row lifts 62/55/305/195 against C4's 47/44/258/173, the difference being the `plane` and `typecase` per call; `diag(v) g` 1499 against 26, the price of the library product over a diagonal; the batched product 1148 against 1087 and the elementwise chain 42 against 40, the same. The variant whose row lift uses the library's own `m[i,:]` (`FlatArrays2.libview.fss.txt`, `Time2.libview.out`) runs the lifts at 180/227/744/868, which is why the private `RowView` stays. Taken into the model, `FlatArrays2` would cost about 5 % per batch-4 step for `diag` and about 2 % for the lifts; C4 should keep its `diag` operator and could take everything else.

## D. For Pavol, in one paragraph

Fortress gives implementation from traits to the types that declare them, and here the types are the library's own arrays, which cannot be given more from outside: what they inherit is `+`, `-`, unary `-` and `zero` at rank 1 and 2, and the vocabulary uses that without a declaration, so the trait flavour is there where it can be. It does not give `×` on arrays (excluded by design so that juxtaposition can be the inner product; the ring route breaks `+` and changes the meaning of the product), nor scalar extension (no trait for it ships), nor anything at rank 3 (no algebraic trait reaches it), nor reshape, planes, gather, outer product or ravel (none exist in the library), and the spec's algebraic-constraints library that would carry `Ring` and `Field` was never shipped. So thirty of the forty declarations are forced in count; the habits are in the shapes: `RR64` written where `T extends Number` is what the language would say, `nat` parameters on signatures that dispatch nothing (only the model's `^T` pair needs the `Array3` spelling), four aliases of one library call, two internal views exported, a `transpose` that `.t()` already is, and two rank overloads that one `typecase` merges. With those removed the api is 28 declarations against 38, the numbers are identical on the smoke, and the operators reach integer arrays too. The one operator that looks like a habit and is not is `diag(v) m`: as a `Matrix` view it needs no operator and costs 54× on its line. The reviewers' verdict of Phase 2 holds for this vocabulary as well: the "Fortress cannot" of leaving the traits alone was right, and the habits were the specialisations, which no probe had been asked to falsify.
