# Decision record: the paper's instance rule and the order of attempts (rung I, climb batch 8)

This is the decision record the S1 form asks for (`explorations/coordinator/POSITIONS.md`, "The S1 form"): each revised passage, what it said, what it says now, why, and the way back; and the decisions taken inside the rung, each with the alternatives considered and the evidence that settled it. Appendix I's entry "The inference of a call's static arguments" (`Specification/appendices/changes.tex`, `\seclabel{revival-inference}`) names this file. The base is `493b4076f`. The rung's report is `explorations/compile-ladder/rung-instance-bound/REPORT.md`.

The decisions this rung carries out, from POSITIONS.md:
- **A type parameter the arguments do not fix takes its bound, never `Bottom` (the paper's instance rule).** "such a parameter takes the intersection of its upper bounds, its declared bound (`Any` if none) under the constraint of the call's static return type; never `Bottom`, never the union of the arguments' types, never the value's type alone." Its batch 8 sentence: "one checker rung binds an inference variable with no lower bound to its bounds instead of `BOTTOM`, with row 447's and row 425's tests and the union candidate made `Any`."
- **The order of the checker's attempts at a call** (row 508): "the checker tries a call by subtyping without the expected type first and keeps that attempt when its result converts to the expected type, then tries coercion with the context, so a declaration that fits the arguments as they are is not passed over for one reached by coercion."
- **Conversions never change which declaration runs**, which the order serves, and answer 8's promotion, untouched: for number arguments it decides the instance before the paper's rule applies (`explorations/reviews/decisions-review/popl-recheck.md`, section 1.9).
- **The type group's late positions outweigh the early text**: the POPL 2019 paper (Park, Hong, Steele and Ryu) is the type group's last word, so its rule outweighs the chapter's earlier union and answers the Working Draft's open draft note. On the attempt order the paper is silent (it has no coercion; popl-recheck, section 1.13): the order rests on decision 1 alone and is not cited to the paper.
- **Every change to the specification is recorded with its reason** and **The S1 form**: the passage revised in place with a callout, the Appendix I entry updated, the team's draft note kept.

## 1. The passages revised

### 1.1 A new item of the rule (`Specification/basic/inference.tex`, section "The Static Arguments of a Call", the Instantiation list)

- Before: the rule had no item for a type parameter that neither an argument nor the expected type fixes; the chapter's list of what it does not yet describe named it and left open whether inference may give it `BottomType`.
- Now: an item after the lone-parameter item: such a type parameter, such as one that only the return type mentions as its whole type, "likewise takes the intersection of its upper bounds: its declared bound, `Any` if it has none, and what the expected type, where the call has one, requires of the declared return type"; "Inference never instantiates a static parameter at `BottomType`"; the example `stop[\T\](s: String): T`, at `ZZ32` under `x: ZZ32 = stop("no")` and at `Any` with no expected type; a callout recording the earlier text and the decision of 29 September 2026.
- Why: the decision above. The paper's solving step "never instantiates method type parameters with Bottom" (`research/extracts/ParkPOPL2019-extract.md`, section 4.2, p. 11:19) and takes "the intersection of the upper bounds"; the call's static return type is the expected type of the chapter. The lone-parameter item already gave the bound in these words since climb batch 7b; the new item extends the same words to a parameter no argument constrains at all.
- Way back: delete the item and its callout and restore the list item (1.2); the checker's `solveToBounds` (section 2, D1) is then the only place that implements it.

### 1.2 The list of what the chapter does not yet describe

- Before: "a static parameter that neither an argument nor the expected type fixes, such as a type parameter that only the return type mentions, as its whole type, or the element type of a reduction that only its generator clauses determine (`\secref{reduction-expr}`); whether inference may give such a parameter `BottomType`, which programmers must not write (`\secref{bottom-type}`), is left open".
- Now: two items: "a `nat` or `int` parameter that neither an argument nor the expected type fixes", and "the element type of a reduction that only its generator clauses determine (`\secref{reduction-expr}`): the rule above gives a static parameter of the big operator that nothing at the call fixes its bounds, not the type of the elements".
- Why: the type parameter is described now (1.1). A `nat` or `int` parameter is not covered by the rule, which is for type parameters, and stays undescribed. The reduction's element type stays undescribed because the bound is not the element type: the record's own measurement (REPORT.md, section 4, row 425) shows a generic big operator whose bound is `Number` gives `Number` for a clause form over `ZZ32` and the binding `s: ZZ32 = ...` is refused, while one whose bound is the element type compiles and runs (`compiler_tests/InferBigOperatorUnwritten`).

### 1.3 The callout after the list

- Before: the compiled type checker "binds the parameter to `BottomType`, except that it refuses a call that has no expected type when the parameter is declared `extends Any`"; the interpreter erases it of a function to `BottomType` and leaves a generic method's uninstantiated (rows 21, 424, 425 and 447); "Whether inference may do so is the team's question, kept in the draft note below."
- Now: the compiled type checker instantiates such a parameter at the intersection of its upper bounds as the rule says; on the compiled path a program's own unbounded type parameter is bounded by `Object` (row 412), so such a call whose expected type `Object` excludes, such as `()`, is a static error there; a reduction's big operator is an argument of the call the desugaring makes, so no expected type reaches it and a generic big operator whose static argument is not written is instantiated at its bound (row 425); the interpreter is as before (rows 21 and 424); the third item of the team's draft note is answered by the rule: inference may not give a static parameter `BottomType`. The sentences on `bool` parameters are unchanged.
- Why: the callout must say what the checker does once it is built (POSITIONS, "Every change to the specification is recorded with its reason"); walk is not this rung's (the batch record, rung I's section, "Walk is not this rung's"), so walk's behaviour stays described as it is (row 424, the walk rung after this batch).

## 2. Decisions taken inside the rung

**D1. Where the bound is computed: a call-only mode of the solver (`Formula.solveToBounds`), not a change of the shared `solve` or of `killIvars`.** Candidates: (a) change `slv` for every caller; (b) change `STypesUtil.killIvars` to bind `Any`; (c) post-process the solution in `inferStaticParamsHelper`; (d) a mode of `slv` that the call inference selects. (a) and (b) also reach `TypeSchemaAnalyzer.subUA` and `subEDsolution` (`scala_src/types/TypeSchemaAnalyzer.scala`, the two `inferStaticParamsHelper` calls), which ask whether *some* instance of a generic arrow makes one arrow a subtype of another: an existence question that the overloading checker asks (rung O's area), where `Bottom` is a legitimate witness and the paper's instance rule does not apply; (b) also changes the ancestor heuristic's trial maps (`Formula.scala`, the `proposedMap` line). (c) cannot see the meet with the expected type, which lives in the reduced formula's upper bounds. (d) changes only what a call instantiates. Taken: (d). `inferStaticParamsHelper` gains `toBounds` (default false); `inferStaticParams` (the subtyping attempt, and the coercion oracle's inference of a generic coercion's own parameters), `inferLiftedStaticParams` (a method's trait parameters, from its receiver) and the coercion attempt (`checkApplicableWithCoercion`) pass true; `TypeSchemaAnalyzer` and `addParamTypes` keep `solve`.

**D2. What `solveToBounds` does.** A type inference variable whose lower bounds are all `BottomType` or mention inference variables takes `ta.meet` of its upper bounds free of inference variables (its declared bound, instantiated, and what the expected type's constraint put there); if that meet is `BottomType` (the bound and the expected type exclude each other) the formula has no solution, never a `Bottom` binding; a variable the formula leaves unconstrained (the trivially true formula, a variable reduced away, a class of the unifier with no named member) takes `Any` (`STypesUtil.topIvars`), since only a top bound reduces away. A variable with a named lower bound is solved as before (the join, then the ancestor heuristic), which is the lone-parameter and argument-fixed case the chapter already describes. Alternatives refused: keeping `Bottom` as a lower bound that fixes the parameter at `Bottom` (an argument typed `Bottom`, a `throw`, says nothing about the instance; the decision says never `Bottom`); falling back to `Bottom` where the meet is empty (the batch record's stop: "A parameter nothing fixes bound to anything but its bounds under the expected type").

**D3. The promotion of a lone parameter's union offers "its upper bounds" (`None`) beside the named candidates, rather than adding the bound `Object` or `Any` to the named list.** `checkApplicableWithCoercion`'s `named` list excluded `Object` and `Any` as bounds; adding them would give `Object` where the expected type requires something narrower (`x: Number = pick0(w, r)` under `T` bounded by `Object` needs `Number`, the meet). The `None` choice leaves the parameter to the solver, which under D2 gives exactly the intersection of the upper bounds, context included. The narrowest of the candidates found still wins, so a written trait bound (`InferLoneBound`) and answer 8's number case are unchanged.

**D4. The order: subtyping without the context, then subtyping with it, then coercion with it, then coercion without it.** The decision's words are "subtyping without the expected type first and keeps that attempt when its result converts to the expected type, then tries coercion with the context". Candidates: (a) drop the attempt by subtyping with the context; (b) keep it second. Taken: (b). The attempt with coercion cannot check a lambda argument (`checkApplicableWithCoercion` returns not applicable when an argument is unchecked, `Functionals.scala:303`), so under (a) a call with a lambda argument whose instance only the expected type fixes would lose its only attempt that can accept it; and (b) does not pass over a fitting declaration for a coerced one, which is what the decision guards against, since its second attempt is still by subtyping. The fallback when no attempt is kept is unchanged in substance: the attempts with the context for a method invocation or operator, those without it for a call written `f(x)`.

**D5. Row 541's repair is in the constraint generation (`TypeAnalyzer.pSubInner`), not in the solver.** An argument of static type `L ∩ R` against a parameter type `$X` produced `pOr` of `L <: $X` and `R <: $X` (the intersection-on-the-left case comes before the inference-variable case), so the solver met a disjunction and took the branch that the set iteration put first: one conjunct, by declaration order, and on one program differently between two runs (row 541; the base run of this rung's tests shows the two messages, REPORT.md section 3). The solver cannot recover the intersection from the disjunction. One case placed before it makes an intersection a lower bound of an inference variable as a whole, the narrowest type the argument is substitutable for, which is the chapter's rule for one argument. It is the only edit of `TypeAnalyzer.scala`, outside `staticParam` (rung O's).

**D6. Row 535's pair becomes one compile test named `XXXInferLoneUnionClosedTrait.test`, and `InferLoneUnionClosedTraitLink.test` is removed.** The record says the link test is rewritten to `compile_err_contains` and the run test removed. The harness accepts a refusal only from an `XXX`-named `.test` file (`FileTests.java:932`, `shouldFail` from the file name; a plain file whose compile fails is a failure, `:384-404`), so the refusal is the `XXX` file, rewritten from `run` to `compile`, and the plain link file goes. The program writes `[\T extends Any\]`, so that the refusal names `BoxT[\Any\]`, the chapter's bound, and not the compile path's `Object` (row 412), as `InferLoneUnbounded` does.

**D7. The promoted pairs stay pairs.** Each run defect promoted (rows 447, 505, 508's three faces) keeps its plain link test and its run test, renamed without `XXX`, rather than one `.test` driving compile, link and run: one file fewer per pair would lower the compiler track's count (the gate's COUNT DOWN) for no gain. With the two new tests (`InferResultOnlyOverloaded`, `InferBigOperatorUnwritten`) and the split of `CoverageReturnInferred` (D8), the track's `.test` files go from 16 to 18 for these rows while one file is removed.

**D8. `CoverageReturnInferred` becomes a plain link test and an expected failure of its run.** With D5 the program compiles; its run dies before any output loading the instance at the intersection, "Unable to read serialized data for Intersection??" (`InstantiatingClassloader.xlationForFunctionOrGeneric`, `InstantiatingClassloader.java:2519`). The program is valid under every reading, so the run is home 2: `XXXCoverageReturnInferred.test` (`run_out_does_not_contain=REACHED`, `REACHED` printed first, `run_err_contains=Intersection`), shown red through the harness on a stand-in that runs. The run time is not this rung's file (`runtimeSystem/`, code generation); a new ledger row (559, provisional) names it.

**D9. The two attempt-order tests of climb batch N's rung T lose their rung letter on promotion** (`XXXExpectedTypeChoiceRungT` to `ExpectedTypeChoice`, `XXXExpectedTypeFnChoiceRungT` to `ExpectedTypeFnChoice`, with their link tests), since a test is named by its topic (the batch's register). The control `ExpectedTypeChoiceWrittenRungT`, which this rung does not change, keeps its name.

**D10. Row 425's test is a generic big operator of the test's own, over the compiler library's generators.** The compiler library's big operators are not generic (`Library/CompilerLibrary.fsi`, `BIG +` and `BIG MAX`), so the row's shape cannot be written with them. The test declares `opr BIG LAST[\T extends ZZ32\]()` and its own `__bigOperator` and `__generate` overloads, which overload the compiler library's (the desugaring's names, `DesugarerUtil.visitGenerators` and `PreTypeCheckDesugaringVisitor.visitAccumulator`); on the base it is refused with the row's own message, "BottomType->BottomType is not applicable to an argument of type ZZ32", and after the edit it runs and gives 9. Its bound is its element type. With the bound `Number`, the one library's `SUM` shape, the clause form under `s: ZZ32 = ...` is refused, "Right-hand side has type Number, but declared type is ZZ32" (REPORT.md section 4): no expected type reaches the big operator, an argument of `__bigOperator`, and the bound is not the element type. So the row's note: the bound is built; the element type needs the desugaring to fix the big operator's static argument from the clauses or the expected type, which is the row's second half, left open with the chapter's list item (1.2).
