## 1. A numeral's type: the compiler library's IntLiteral in the one library and in walk

The fork: how many interpreter outputs change when walk makes an integer numeral a value of the library's `IntLiteral`, a numeral's own type that each number type converts from (POSITIONS 2026-09-27, a numeral's type), and so where the rung goes.

The prototype, in `probes/numeral/`, three library variants over one Java shadow:
- `numeral-java.patch`, compiled into a classpath shadow: `FIntLiteral.make` returns an `IntLiteral` value for every integer numeral instead of an `Int`, `Long` or `BigNum` chosen by width (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/FIntLiteral.java:40-56`); its `getInt` and `getLong` answer the value when it fits; five conversion natives beside the team's `IntLiteral` natives (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/IntLiteral.java`).
- `numeral-lib-A0.patch`, the compiler library's model (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:390-429`): `object IntLiteral extends Number` beside the other number types instead of below `ZZ32`; the team's own arithmetic block enabled, which its comment holds back "until coercion is implemented" (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fss:492-534` at 2851e5086); getters `asZZ32`, `asZZ64`, `asNN32`, `asNN64`, `asZZ`; and a `coerce(x: IntLiteral)` on `ZZ32`, `ZZ64`, `NN32`, `NN64`, `ZZ`, `QQ` and `RR64`, with their api twins.
- `numeral-lib-A1.patch`: A0 with `ZZ32`'s `>`, `>=`, `<=` and `CMP` stated on `ZZ32` itself, as `ZZ64` states them under the team's comment "Argh! Due to method ambiguities with ZZ, these definitions must be given explicitly here" (`Library/FortressLibrary.fss:776-783`).
- `numeral-lib-B.patch`: A1 with `IntLiteral` also an `AnyIntegral`.

`variants.sh` applies each in turn and runs `NumMicro.fss` under walk; the four captures are `NumMicro.base.txt`, `.A0.txt`, `.A1.txt` and `.B.txt`.

What it measured:
- On the base, `NumMicro` prints its lines until `s: RR64 = 3000000000`, which walk refuses, "RHS expression type Long is not assignable to LHS type RR64" (`NumMicro.base.txt`): row 443 on today's tree.
- Under every variant the one library does not finish loading, so every interpreter test would fail; the count of changed outputs cannot be taken on this model. Each variant stops one step further in the library's own code:
  - A0: `0 <= r` in `offset` (`Library/FortressLibrary.fss:2146`, reached from `Library/String.fss:23`) is "Ambiguous coercion" among the `<=` of `RR64`, `QQ`, `ZZ64` and `ZZ`. `ZZ32`'s own `<=` comes from the generic trait `StandardTotalOrder[\T\]`, and walk's search for a coercion skips generic declarations (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/OverloadedFunction.java:821-852`, the `continue` on `GenericFunctionOrMethod`).
  - A1: `2:46` (`Library/String.fss:25`) finds no overload: the range operator is generic, `opr :[\I extends AnyIntegral\](lo:I, hi:I)` (`Library/FortressLibrary.fss:3913-3914`), an `IntLiteral` is not an `AnyIntegral`, and walk tries no coercion for a generic declaration.
  - B: `:` now applies, and its body's `0 asif ZZ32` (`Library/FortressLibrary.fss:3914`) fails, "Type of expression, IntLiteral, not a subtype of ZZ32", as the specification says it must: the subexpression of `asif` must be of a subtype of the given type (`Specification/basic/expressions/type-annotation.tex:40-52`). The library writes a numeral `asif` a number type at 38 sites (`grep -o "[0-9]\+ asif [A-Z][A-Z0-9]*"` over `Library/*.fss`).
- The compiled path has the same gap. `GenNumeral.fss` (in `probes/numeral/`, compiled in the compiler's world, `GenNumeral.comp.txt`) declares `g[\I extends ZZ32\](lo: I, hi: I)` and calls `g(2, 46)` and `g(2, n)` with `n: ZZ32`: the checker refuses both, "not applicable to an argument of type (IntLiteral, IntLiteral)" and "(IntLiteral, ZZ32)", and a `ZZ64` twin the same. The compiled checker does not infer a static parameter through a numeral's coercion either. Compiled programs have not met it because the compiler library's ranges are declared on `ZZ32` alone (`Library/CompilerLibrary.fsi:173-174`); the one library's are generic over `I extends AnyIntegral` (`Library/FortressLibrary.fsi:2197-2222`), so the compiled path meets it at the switch-over whether or not walk changes.
- By reading, two more of the library's reliances on a numeral being a `ZZ32` come after these: a numeral returned at a declared number type, such as `getter zero(): ZZ32 = 0` (`Library/FortressLibrary.fss:691` at 2851e5086), which walk does not convert (row 387); and answer 7's identity functions, which pass a numeral through `cast[\T\]` (`Library/FortressLibrary.fss:3107-3131`), which a numeral of its own type does not match (section 2).

What it settles: the numeral change is not a routine conversion. Before walk can take the compiler library's `IntLiteral`, a numeral has to meet a generic's bound, which needs a rule for inferring a static parameter from a numeral that neither path has; answer 8 put that rule, the promotion rule for mixed widths, in phase 3 with row 388's fix. Then the library's own numeral sites need respelling. This is the batch record's question for Pavol (section 1, Q1).

## 2. Row 426: why the compiled `cast[\T\]` never matches

The fork: whether row 426 fits the batch, which depends on its cause, not traced when the row was opened.

`probes/cast/`:
- `cast-template-javap.txt`: the compiler library's `cast` template tests `instanceof T`, which the loader rewrites to the instance's class, and then reads the clause's binding `y` as `getstatic fortress/CompilerLibrary$y.ONLY`, a top-level object that does not exist. That is the `NoClassDefFoundError: fortress/CompilerLibrary$y` of the row's own capture.
- `CastBind.fss` and `CastBind.comp.txt`: a `typecase` on the function's own static parameter matches at a concrete type on the compiled path: `isT[\ZZ32\](z)`, `isT[\RR64\](r)` and `isT[\String\](s)` answer "is T" for values of those types, and `isT[\ZZ32\](7)` answers "is not T", because a numeral is an `IntLiteral` at run time on this path (row 79). A clause that binds the value, in either spelling (`y: T` as the compiler library writes it, `x': T` as the one library does, `Library/FortressLibrary.fss:33-37`), dies reading `CastBind$x'`.
- `CaseBindPlain.fss` and `CaseBindPlain.comp.txt`: the same death with no static parameter anywhere, `w: Wrap => ...` dying on `CaseBindPlain$w`.

What it settles: row 426 is two things. One is row 351's typecase site: `CodeGen.forTypecase` never reads a clause's name (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:2116-2147`), and row 351 already records the fix, a local for the clause body in the shape `CodeGen` uses at `:2853` and `:3945`, at this site and at `forTry`'s (`:2020-2061`). The other is that `cast[\ZZ32\](0)` passes a numeral, which is not a `ZZ32` on the compiled path, as the specification has it (`Specification/basic/expressions/literals.tex:127-141`; a clause matches when the value's type is a subtype of the clause's type, `Specification/basic/expressions/typecase.tex:94-95`). Answer 7's identity functions pass numerals through `cast[\T\]` (`additiveIdentity`, `multiplicativeIdentity`), so on the compiled path they need both row 351's fix and branch values that are of type `T` at run time. Both are small; the batch record puts them in rung G.

## 6. `RR32` a sibling of `RR64`

The fork: whether anything in the library or the corpus argues for keeping `RR32` below `RR64`, against the specification, the later Types chapter, the team's 2009 commit and the compiler library (`explorations/reviews/batch-6-conformance.md`, finding 3).

The prototype, `probes/rr32/rr32-sibling.patch`, library only: `value object RR32 extends { Number, StandardPartialOrder[\RR32\], StandardMinMax[\RR32\], AdditiveGroup[\RR32\], MultiplicativeRing[\RR32\] }`, the algebra `RR64` carries at its own type; every `b:RR64` parameter of `RR32`'s natives made `b:RR32` (row 435's second fix) and its `MIN`, `MAX` and `MINMAX` answering `RR32`; `RR64` excluding `RR32`, no longer comprising it, and declaring `coerce(x: RR32) = asFloat(x)`, as the compiler library's `RR64` does (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:433-435`); `Number` comprising `RR32`. Three library sites needed more on the way, each recorded in the patch:
- `RR32`'s `^(self, b:ZZ64):RR32`, beside `^(self, b:Number):RR64`, broke the return-type rule once `RR32` is no longer an `RR64`, and so did `MultiplicativeRing`'s `^(self, other:AnyIntegral): T` beside the `Number` form; the prototype gives `RR32` one `^(self, b:AnyIntegral):RR32` on its own native and drops the other two integer forms.
- `Number`'s `=` compares a float with any number after `asFloat`, but tests for a float by `typecase ... RR64` (`Library/FortressLibrary.fss:358-365`); the prototype adds the `RR32` case, since an `RR32` would otherwise fall to `exactValue` and compare as 0/0.

`RR32Micro.fss`: on the base (`RR32Micro.base.txt`) an `RR32` value is an `RR64` in a `typecase`, and `a + 2.5` ends the run with `InterpreterBug: getRR32 not implemented for FFloatLiteral` (row 435). On the prototype (`RR32Micro.sibling.txt`) the value is an `RR32` and not an `RR64`; `a + b` is an `RR32` 4.0; `a + 2.5` and `2.5 + a` are 4.0 and `a + 2` is 3.5, by `RR64`'s arithmetic after the coercion, which is the specification's worked example (`Specification/basic/conversions-coercions.tex:861-898`); and an `RR32` passed to an `RR64` parameter converts.

**What the first shape missed.** `RR32`'s api declares its getters, one `^` and `MINNUM`/`MAXNUM` only (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:47-74`); its other operators are declared in the component alone. An operator `RR32` shares with `RR64` through an algebra trait (`+`, `-`, `DOT`, `TIMES`, juxtaposition, `^`, `MIN`, `MAX`) reaches `RR32`'s own declaration through the trait's. The rest (`/`, `SQRT`, the `_UP`, `_DOWN` and `IEEE_` forms, `|self|`, `floor`, `ceiling`, `truncate` and the others) are visible to a program only as `RR64`'s functional methods, which `RR64`'s api declares (`Library/FortressLibrary.fsi:313-372`). On the base an `RR32` is an `RR64`, so `RR64`'s `/` dispatches on its receiver to `RR32`'s; with the first shape `a / b` converts both `RR32` operands to `RR64` and answers an `RR64` (`probes/rr32/RR32Div2.fss`, `RR32Div2.sibling.txt`: `/`, `SLASH_UP`, `PLUS_UP` and `SQRT` answer `RR64`, the other five `RR32`).

**The second shape**, `probes/rr32/rr32-sibling-api.patch`, is the first plus 46 lines in `RR32`'s api declaring the operators its component defines, in `RR64`'s form (it applies to 2851e5086). With it all nine operators of `RR32Div2` answer `RR32` (`RR32Div2.sibling-api.txt`), and `RR32Micro` answers as with the first shape except that `SQRT a` is now `RR32`'s own, `1.2247449`, where the first shape computed it as an `RR64` (`RR32Micro.sibling-api.txt`).

**The corpus passes.** Rung F's three passes (`count-run.sh`, one JVM per test and private caches; `compare-normalised.py`, batch 5's normalisation) over the 414 files of `ProjectFortress/tests/` at 2851e5086, their machine lines and times in `probes/rr32/passes-machine.txt`: base A (30 minutes), base B and the first shape's edit (34 minutes each, run side by side), then the second shape's edit after them.
- The first shape (`probes/rr32/compare-sibling.txt`): 386 the same, 7 equal once normalised (library lines the edit moved), 17 unstable (the two base passes differ: timings, random data, task traces), and 4 changed. `XXXRR32MixedRungF` passes (exit 1 to 0), row 435's expected failure, which the rung promotes. `testRR32`, a team test, fails at its line 30, `infinity: RR32 = narrow(1.0) / narrow(0.0)`, "RHS expression type Float is not assignable to LHS type RR32": the missing api declarations above. `XXXArrayLiteralArgRungC` keeps its verdict, and its message lists `RR32`'s own `-` among the candidates where it listed `RR64`'s. `XXXInheritedOverload` names its two declarations in the other order, which its row calls unstable (row 430).
- The second shape (`probes/rr32/compare-sibling-api.txt`; 10 minutes, the load 2.2 at its start against 10 to 13 for the others): 387 the same, 7 equal once normalised, the same 17 unstable, and 3 changed, each keeping the verdict the rung expects. `XXXRR32MixedRungF` passes (row 435's expected failure). `XXXArrayLiteralArgRungC` keeps its verdict, and its message lists `RR32`'s own `-` and `RR32`'s instance of `AdditiveGroup`'s `-` among the candidates, where it listed `RR64`'s `-` with `RR32` in its receiver's type. `XXXCoercionTupleOverloadRungC` keeps its verdict and prints its two `pair` declarations in the other order, a set's order and not a property of the program, as in row 430's message. `testRR32` passes, as on the base, and no other output changes.
