## Row 864

- **Defect:** Under walk, a `builtinPrimitive` binding of a `nativeHelpers` helper in a dotted method of a generic trait or object whose `self` type no Java type carries (for example a program's own generic `Box[\T\]`) is not refused at load, as it is everywhere else. Walk checks `self` only when it makes the method's closure, and an instance's dotted methods get their closures when the instance is made. So a program that never makes an instance loads and runs. One that makes an instance dies at that point with 'no Java type carries Box, the type of self.' as an `InterpreterBug`, not as a load refusal. A generic trait's functional method, and a method with its own static parameters, are refused at load as they should be. So the gap is only dotted methods of generic types.
- **Where:** Walk only. `interpreter/glue/StaticNativeApp.java:189-193` (the `self` check) and `interpreter/evaluator/values/MethodClosure.java:36` (closure made at instance creation), at c124c6b65. `interpreter.md`, "Natives", already describes this gap and cites row 864.
- **Reproduce:** Run `ProjectFortress/tests/NativeHelperUncarriedSelfGenericObjectWalk.fss` under walk. It makes no instance and prints 'loaded', so it asserts the half of the gap that loads. To see the failure, add `println("before"); println(Box[\ZZ32\](3).len())`: it prints 'before', then stops with the message above. The reproducer does not hold this half; it is only in the notes.
- **Status:** Build a fix: check a generic type's helper bindings where the type is declared, so the reproducer's program is refused at load. The reproducer then turns red. It is a plain-named test that asserts today's wrong behaviour, not an `XXX` test, so the fix must change or replace it.
- **Could not resolve:** (1) "siblings: 847": the skill never defines "siblings", and I cannot tell whether 847 is the same defect elsewhere, a related one or a dependency. Unclear wording. (2) That the reproducer asserts the defect's harmless half (the load) is stated, but whether a worker should flip it to an expected-refusal test (`load_exception_contains`) at fix time is not. Unclear wording, minor. (3) What `Box` and `len` are (which helper `len` binds) is only implied. The reader has to open the reproducer. Minor.

## Row 888

- **Defect:** On the compiled path, with a `try` nested inside another `try` in the same body, the outer `try`'s `catch` gets the first chance at an exception thrown in the inner body. An exception both catch clauses take goes to the outer one, which is wrong. One that only the inner clause takes is not caught at all, and the body throws. Walk is correct (inner first).
- **Where:** Compiled path, code generator: `CodeGen.forTry` (`compiler/codegen/CodeGen.java:2033`, at c124c6b65) emits its exception-table entry before it visits the body. So the inner entry follows the outer one over the same range, and the JVM uses the first entry that covers the throw.
- **Reproduce:** The run-time `XXX` pair `compiler_tests/NestedTryInnerCatchLink.test` and `compiler_tests/XXXNestedTryInnerCatch.test`, run in one `junit.sh` call, the Link file first. Compiled, it prints `outer`, then ends with 'FortressException: class NestedTryProbe$Boom'. Walk's guard `tests/NestedTryInnerCatchWalk.fss` prints `inner` twice.
- **Status:** Build a fix in the code generator: the inner `try`'s entries must come before the outer one's (emit after the body, or order the table). Promote the `XXX` pair. Until then the workaround is to put the inner `try` in a function of its own.
- **Could not resolve:** (1) "the test's two functions": I take them as one per case (both clauses take it; only the inner one takes it), but the row does not say which output line belongs to which case, so it is unclear why only one `outer` is printed before the uncaught exception. Minor unclear wording. (2) "in one body": I read it as the same function or method body, not across calls. The workaround supports that. Otherwise clear.
