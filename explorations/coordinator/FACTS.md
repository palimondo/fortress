# Facts on record

## Execution model

- F-7 **Walk and the compiled path share the parser and the phases, and only the compiled path runs the static type checker.** Walk switches the checker off, and no switch turns it on. So walk checks no static types of expressions: an ill-typed expression shows only when it runs, as a failed dispatch or as another run-time error, such as F-239's refusal of an `if` on a value that is not a `Boolean`. At load, walk refuses some ill-formed declarations: the `fortress-repo` skill's `interpreter.md`, "What walk checks", lists them, with their evidence in F-29 (`comprises` clauses), F-142 (the Meet Rule for Functional Methods) and F-145 (uncovered abstract methods and `override`). The phases and where the two paths part: the skill's "How a program runs". Detail: `explorations/repo-internals.md`, "The two worlds".
- F-9 **`fortress typecheck` checks a program against the compiler's library, `Library/CompilerLibrary.fsi`, so it is no oracle for walk programs.** `Shell.java` calls `useCompilerLibraries()` for the command (row 69). The checker reaches walk's programs after the switch-over (P-12).
- F-11 **The code generator boxes every number, and boxing is the main representational cost of microGPT-shaped array code.** So a compiled `RR64` loop holds no `dadd` or `dmul` (the `fortress-repo` skill, "The compiled run time"). In Java models of microGPT's three kernels, boxed elements cost 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]`. No such kernel compiles yet: the compiler prelude has no array type (row 305), and the arrays reach the compiled path with the one library (P-37). Detail: `perf-probes/kernels/REPORT.md` sections 2 and 4.
- F-12 **On the compiled path, the scalar `RR64` loop `bench1t` ran in 0.74 s in one session's measurement; the loop still pays for its generator, for boxing and for a transaction check at each use of its accumulator.** `bench1t` is `for i <- seq(1#20000000) do acc := acc 0.9999999 + 0.0000001 end` on a `var acc: RR64`, with both literals written in the loop. The time is the median of three loop-only runs at one thread (`compile-ladder/rung0/REPORT.md`, "The four timings"). Times taken in different sessions differ on this machine, so compare only times from one session. What the loop does, read in its bytecode (`perf-probes/boxing/REPORT.md` sections 4 and 5): the `seq` loop becomes the compiler prelude's `countedseqloop`, which runs the iterations in order by a recursive split over boxed indices, with a closure call per element; each value is boxed (F-11); and the accumulator is a volatile cell whose read and write each first call `BaseTask.inATransaction`, as for every mutable local (F-40, what a size costs at run time, whose sized loop pays the same check). Within the boxing and the cell, the report counts four allocations per iteration, an interface call to the native wrapper and the casts, the part that unboxed doubles and `double[]` would attack. No share of the 0.74 s is measured.
- F-17 **The bytecode cache can come up empty after a library order that reports exit 0.** Running the same commands again, one at a time, made the jars. The cause is not known. Check the five jars before a compiled run (the `fortress-repo` skill's `build-and-caches.md`, "The library order"). Detail: `perf-probes/boxing/REPORT.md` section 1.
- F-18 **On the compiled path, the class loader makes the class of a generic instantiation at its first use, by rewriting the template's bytecode with ASM.** The class is `InstantiatingClassloader`; the `fortress-repo` skill's "The compiled run time" gives the mechanism. A size is part of the made class's name, as in `pNatMeth$Box⟦3⟧`, the object `Box` at size 3 in the probe component `pNatMeth`. Inside the class, the size's descriptor is `RTTIsize.of("<n>")` (F-129). Walk instantiates generics in its own evaluator, not by classes. Detail: `perf-probes/nat/java.md` section 1.
- F-19 **Implicit parallelism: a `for` loop is parallel unless every generator is `seq`, and a tuple's elements and an operator's operands are evaluated in parallel.** `FORTRESS_THREADS` sizes the work-stealing pool (the `fortress-repo` skill, "Parallelism and mutable state"). No program under `explorations/` writes `spawn` or `also`. Source: `Specification/basic/expressions/tuple-expr.tex:23-24`, `operator-app.tex:59`.
- F-20 **Sizes, the `nat` and `int` static parameters, are values at run time; they check shapes, and no optimization uses them (F-40, what a size costs at run time).** The compiled checker checks them (F-67), and a sized program loads and runs compiled (F-129). Under walk, `Vector` and `Matrix` take their sizes from an array built at run time: `f[\nat s\](v: Vector[\RR64,s\])` takes `s` from `array[\RR64\](3)`, and overloads on `Vector` and `Matrix` dispatch by rank (row 214). The array-type syntax `T[n]` with a `nat` parameter does not unify with such an array, "Cannot unify … with ArrayType", where `T[3]` with a literal size does (row 23). Walk matches sizes at dispatch. A mismatch, such as a `DOT`, the library's inner product, of a 2×3 matrix by a 2×3 matrix, whose inner sizes differ, is a `ProgramError`, "Failed to find any matching overload", that no `catch` takes (row 254). Source: `Specification/basic/trait-parameters.tex:97`.
- F-21 **The February 2011 Working Draft's bare `Nothing`, one object for every `T`, is accepted on neither path: the grammar refuses its `excludes` clause, and without that clause `T` is undefined.** The declaration is `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:40`). Both paths stop at a syntax error at `excludes`, since an object has no `excludes` clause (measured: `reviews/spec-refused-examples.md`, E4). Without that clause, both report `T is undefined` at the `T` of the `extends` clause: a `where` clause on an object binds no type variable of its `extends` clause, as row 17 holds for a trait. Today's specification refuses the form in any case, by instantiation exclusion, and marks it "Not allowed" beside the parametric `Nothing[\T\]` that the interpreter's library writes (F-167). P-90 still calls the bare `Nothing` future work that waits for such `where` clauses, not tried before then. Detail: `compile-ladder/rung-maybe/REPORT.md` section 5.
- F-22 **When a component's name differs from the api that it exports, neither path finds the component, for an exported function or variable alike.** The specification resolves an imported api to any component that exports it (`Specification/basic/components/overview.tex`). The tree looks only under the api's name, unless a user maps the api to its component by hand with `LinkShell`'s `alink` or `clink`. The linker's component repository looks this way (`Linker.whoIsImplementingMyAPI`), so `fortress link` and walk print "Could not find an implementation for API … on path" before any code is generated. The code generator names a reference to an exported declaration after the api, and the declaring class after the component. The link step rewrites such a reference to the component only when the repository names it, so files compiled one by one, without `fortress link`, die with `NoClassDefFoundError`. The missing step is the repository's: finding the component that exports the api. The report names two repairs, neither built: the repository could search the source path for that component, or the code generator could emit api-named forwarders, for which three comments in `CodeGen.java` leave a place. Walk and `fortress link` need the first. Workaround: name the api after its component. Gated by the expected failure `compiler_tests/XXXExportVarRungXLinked.test` (row 320). Detail: `compile-ladder/rung-export-var/REPORT.md`, "The measurement that separates them".
- F-23 **A comment placed after a declaration that ends in an expression or a type becomes part of that declaration's source span and of the unambiguous name the parser derives from it.** The parser's `createSpan` trims back over spaces only, and a declaration that ends in `end` is unaffected (row 359). So a comment-only library edit can change the syntax tree, and a before-and-after comparison of parse trees or diagnostics maps positions back first. Detail: `compile-ladder/rung-library-comments/REPORT.md` section 6, D1.
- F-24 **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees.** It throws a `FortressError` that holds the exception's object, as `Int.overflow()` does for `IntegerOverflow` (F-132; row 347, fixed). Any other Java exception of a native becomes a `ProgramError`, which no `catch` takes, so a division by zero ends the run (row 336). Gated by the `overflows(...)` assertions of `tests/IntSemanticsRungI.fss`. Detail: `compile-ladder/rung-int-semantics-walk/REPORT.md` section 4.1.
- F-25 **On the compiled path, the class loader loads each class under the JDK's class-loading lock, so the first load of an instantiation's class is safe on four threads at once.** `InstantiatingClassloader.loadClass` holds `getClassLoadingLock(name)` for the whole load, as the JDK's own `ClassLoader.loadClass` does. Without the lock, two threads that first loaded such classes at the same time could race, and the run died with a `NullPointerException` (row 417, fixed). The test `compiler_tests/FirstLoadThreadsRungG` calls the generic overload `f[\T\](v: Vt[\T\])` at eight instantiations, `Vt[\A1\]` to `Vt[\A8\]`, from a parallel `for` loop of 800 iterations. Observed: at four threads it failed 5 runs of 5 before the lock, and passed 5 of 5 after. It is one of the gate's atomic runs, which run each program at four threads (`gate.md`). Detail: `compile-ladder/rung-generic-runtime/REPORT.md` sections 1 (the runs) and 12 (why this lock).
- F-26 **Under walk, when one of two applicable declarations has static parameters of its own, the call chooses on their declared domains where exactly one lies inside the other, not by the order in which they are written.** It builds P-45, the choice among overloads by declared parameter types, under walk. A declaration has static parameters of its own if it is a generic function or constructor, or a functional method with static parameters in a trait or object without any. Its declared domain, walk's symbolic instance, is its parameter types with each type parameter standing for itself under its bounds. Where neither declared domain lies inside the other, where each lies inside the other, or where neither declaration has static parameters of its own, walk compares the domains of the instances that the call makes. So a functional method of a generic trait or object is compared on its instance, and a generic dotted method is chosen by F-253 (a generic method at a dotted call, also chosen on declared domains). If the chosen declaration is generic and its instance takes an argument only by a conversion, walk converts the argument and dispatches the converted arguments again, so the most specific declaration for the converted values runs. In two cases walk keeps the chosen instance, with no second dispatch: an overloaded dotted method, and a position whose conversion `Coercions.coercionFor` does not find, such as a tuple converted element by element. Two generic overloads whose static parameters agree in name, kind and bounds share one symbolic instance, even if their `where` clauses differ; no test or library declaration has such a pair (row 478). Gated by `tests/DispatchDeclaredDomain.fss` and `DispatchConvertedAgain.fss`. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.1, 5.2 (the second dispatch) and 5.5 (the symbolic instance).
- F-27 **Walk's load check reads again two kinds of overload pair that its parameter-by-parameter check refuses, and accepts those that pass: a generic declaration beside a plain one, read on their declared domains, and two plain top-level functions, not methods, whose overlap other declarations cover through `comprises` clauses.** To test a cover, the check cuts the overlap of the two domains, position by position, into parts by the `comprises` clauses. Each combination of parts must lie inside the domain of one declaration without static parameters that lies below both. So several such declarations may together cover the overlap. A search that does not settle refuses. A generic declaration beside a plain one passes where one declared domain lies strictly inside the other and the inner one's return type lies below the outer one's. Where neither lies inside the other, the pair needs the same cover, or declared domains that exclude each other read whole (F-258, exclusion over the whole parameter type). Equal declared domains are refused. It builds under walk P-46, by which a conversion never changes which declaration runs when one already fits, and P-60, by which several declarations below both may cover a meet. Two generic declarations are read on their declared domains too (F-252: the No Duplicates, Return Type and Meet Rules, each over its own instances). Walk still refuses the valid example of the POPL 2019 paper on symmetric multiple dispatch (`research/extracts/ParkPOPL2019-extract.md`, p. 11:13), a set of three generic declarations (row 539). Gated by `tests/ComprisesMeetWalk.fss` and `GenericBesidePlain*.fss`, among others. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.3 (generic beside plain) and 5.4 (the cover).
- F-28 **Walk instantiates a generic declaration declared to return `Any`.** `MakeInferenceSpecific` treats `Any` as it treats a trait type (row 157, fixed). Its visitor has no case for 11 of the syntax tree's 18 concrete type classes, and of those only the dimension forms can be written as a return type. Gated by `tests/GenericReturningAny.fss`. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` section 3.
- F-29 **Under walk, the load check refuses a trait or object that extends a closed trait of the program's main component where the trait's `comprises` clause does not allow it.** A closed trait is one with a `comprises` clause. The check reads every trait and object of every component of the program, the library's included, as a possible extender. An extender is allowed in three cases: it lies below a listed type; it is a trait whose own `comprises` clause lists only types that are allowed in turn; or it is a generic trait that some trait or object extends, and each of those extenders lies below a listed type (`Specification/basic/traits.tex`, "Trait Declarations"). The check does not yet read a clause declared outside the main component, the library's among them (row 551), or an object expression's `extends` clause (row 597). Nor does it check that each listed type extends the trait at every instantiation (row 598). A check that read the library's clauses would refuse at load every program that imports the library's `Reflect` (row 595), and four team tests and two demos whose objects extend `Number` or `Exception` directly (row 596). Their repairs come before that check and are the curator's. Gated by `tests/ComprisesUnlistedExtender` and `ComprisesGenericChildUnlistedExtender`, refused at load, and by the `XXX` tests of rows 487 (a type of another component below a generic subtrait of a closed trait), 551, 597 and 598, which stay green while walk still loads their programs. Detail: `compile-ladder/rung-walk-load-check/REPORT.md` section 5.
- F-269 **Under walk, a program's declarations of a library operator name are checked against the library's only when the program declares two or more of that name, and only on a cold cache.** One such declaration is not checked. Two or more are checked with the library's declarations, and the check can refuse them beside the library's generic declarations, even where they are more specific than the library's. It refused C4's former pair of `MAX` between an `RR64` and an `Array[\RR64,I\]`, in both orders, which C4 dropped when F-119's scalar extension took its place (row 341). It refuses the `Matrix`-specialised elementwise `×` of `apl/mg/elemwise_nat_probe.fss` (F-155). Walk writes a component to its cache before it runs this check, and skips the check on a component that it reads back. So a refusal appears once, on a cold cache, and never again (row 342). The check runs only when walk analyses the library itself again: deleting the program's own cache entries does not bring it back (row 342). So a test that depends on this check must run from an empty cache. Detail: rows 341 and 342; `compile-ladder/rung-library-comments/REPORT.md` section 4, a gated run that met a warm cache.

- F-40 **Measured on 2026-09-24 for two size designs that were not built, a size cost a few kilobytes at load and nothing in a hot loop, and only the overload dispatcher read a size off a value.** The two designs were design A, descriptor classes stamped for each size of each generic, and design B, a class for each number, passed to the generic's descriptor factory; both ran on the size probes' private build (`perf-probes/nat/size-cost.md` section 1). - F-42 **The compiled checker skips a compilation unit's (an api's or a component's) overloading and return-type checks when an earlier stage of that unit has reported an error.** `StaticChecker` returns before `OverloadingChecker` if the earlier stages found errors (`StaticChecker.java:268-279`). - F-43 **The overloading checker's memo hides some errors, and which ones changes from one build of the checker to another, so the gate's checker count and distance run with the memo off.** The memo keeps a "valid" verdict per pair of declarations. A pair that several traits inherit is checked once per trait, at that trait's instantiation, in hash-set order, so a pair valid for one trait is taken as valid for the next (`perf-probes/nat/triage.md` section 1). The memo is on by default (`OverloadingChecker.scala:79`), so an ordinary `fortress compile` can miss these errors. The JVM property `-Dfortress.analyzer.overload.cache=false` turns it off; the gate's checker count and distance stages set it.
- F-44 **The compiled checker enforces the multiple instantiation exclusion rule and relies on it, and the one library meets the rule.** The rule: no type extends two different instantiations of one generic trait. The checker's Return Type Rule relies on it: with the rule relaxed alone, a program passes the checker and dies with `IncompatibleClassChangeError` (`OverloadingOracle.scala:81-105`; the probe `ProbeMIEPick`). F-48 gives the kinds of static argument that the rule compares. Walk applies no instantiation exclusion: it accepts a type that extends two instantiations, and its overloading check does not count them as excluding (row 416; the review's section 3). P-43 keeps the rule. Besides the flat number tower of P-43, the library meets it by three changes of `952892a00`: `TotalComparison` extends `Comparison` and `StandardMinMax[\TotalComparison\]`, no longer `StandardTotalOrder[\TotalComparison\]`; `AnyMaybe` extends `AnyUniqueItem` alone, no longer `Equality[\AnyMaybe\]` beside it; and `andCondCombine` chooses `andRelCond` by a `typecase`, in place of a second `ANDCOND`. So under walk, a program's `p1 ANDCOND p2` of two relational predicates, conditions built from a relation over a generator, which `filter` fuses, is no longer itself a relational predicate (row 458). The distance holds no exclusion error (F-53).
