## Revival change

**The change.** The team's disambiguator, which walk and the compiler share, read a `typecase` arm `Id =>` whose name names no type as a binder over every value, the clause `Id: Any =>`, and let every other undefined name inside an arm's type pass without a message (`ProjectFortress/src/com/sun/fortress/compiler/disambiguator/TypeDisambiguator.java:240-250` and `:392-395` at 1609258002, the team's code of 2012); the team's test `compiler_tests/Compiled7.PatternMatching.b.fss:30` wrote `x => println x`. The tree now refuses such an arm on both paths with the message every undefined type name gets, 'Id is undefined.', and so a name in an arm's arrow type or static argument; an arm at a type parameter in scope tests against its static argument; a binder over every value is written `x: Any =>`; an element of a tuple of names, as `(x, y) =>`, still binds. Tests: `tests/TypecaseUndefinedArmWalk.fss`, `compiler_tests/XXXTypecaseUndefinedArmCompiled.test`, `tests/TypecaseUndefinedNameInArmTypeWalk.fss`, `compiler_tests/XXXTypecaseUndefinedNameInArmTypeCompiled.test`, `tests/TypecaseTypeParamArmWalk.fss`, `compiler_tests/TypecaseTypeParamArmCompiled.test`, `tests/TypecaseTupleArmUndefinedNameBindsWalk.fss`. The reason: "it is a static error for a reference to a name to occur where it is not in scope in the appropriate namespace" (`Specification/basic/declarations.tex:571-572`), and the chapter's grammar makes an arm a type, `TypecaseTypes ::= ( TypeList ) | Type` (`Specification/basic/expressions/typecase.tex:69-71`); measured, an arm at `Int`, which names no type, took `2.5` on both paths and printed 'an Int'. The skill's sentence that such an arm "takes every value, without a message" no longer holds.
