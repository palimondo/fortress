## Q1. Does an array of `RR64` (or `RR32`) compile to a flat primitive array, or to boxed objects?

**The record answers it, and the code still agrees.** P-17 and P-84 decide that arrays will be unboxed (`RR64` in `double[]`, each number type in its primitive array); P-85 leaves the "how" (decision A) until after the switch-over. F-18: the class loader only renames, so no instance gets a `double[]` field. F-333 describes the store. Observed: boxing costs 6.3×, 6.5× and 2.6× in Java models (row 306); a compiled `Array1` loop against the one library, in a scratch tree, ran about 100 times the Java time, 6 to 7 of it boxing (F-358).

**Answer: the elements are boxed on every path.** (read)
- **prelude:** no array type: `array[\RR64\](4)` gives 'Function array is not defined.', and only `ZZ32Vector` (an `int[]`) and `StringVector` exist (row 305); `RR32` arithmetic answers `RR64` (row 529).
- **one:** `array[\RR64\](n)` → `array1`'s `typecase` → `vector[\RR64,s0\]` → `__DefaultVector` (`Library/FortressLibrary.fss:2845-2856`), whose `mem` is a `PrimitiveArray[\T,s0\]` (`:2807-2808`) → `mem: JavaArrayStore = makeJavaArrayStore(s0)`, read back through `cast[\T\]` (`ProjectFortress/LibraryBuiltin/NativeArray.fss:15-25`) → `nativeHelpers/arrayOps.make` → `FortressArrayStore`, an `Object[]` of one boxed value object per element (`compiler/runtimeValues/FortressArrayStore.java:21-28`). `RR32` takes the same chain. No `float[]` store exists. `FortressRR64ArrayStore` is a `double[]` and has no `put`. Only `PrimImmutableRR64Array` holds it (`NativeArray.fss:37-45`), and no factory chooses that type: `FortressLibrary.fss` never names it.
- **walk:** an `AtomicArray`, with one `ReferenceCell` for each element, each holding a boxed float (`interpreter/evaluator/transactions/AtomicArray.java:23-37`).
- **Arithmetic is boxed too:** no primitive `double` arithmetic is emitted (F-11); in a hot scalar loop escape analysis removes the temporaries but one box per mutable assignment per iteration stays (F-301, observed once), and a stored element's box escapes (row 306).

So the handover's fallback condition ("if arrays box") holds today, but the curator's route is P-84, an unboxed store inside the library's own arrays that the model's vocabulary keeps using (P-87), not a separate Java tensor type. Open (P-85): A, the store; B, where unboxed arithmetic happens; D, the sizes in the model's types.

## Q2. Does mutable access outside `atomic` go through the STM (strong atomicity), or only access inside `atomic`?

**The record answers it, and the code still agrees.** Row 641 (observed): compiled code checks every mutable access, also outside `atomic`, about 1 to 2 ns a check: 64 % of an array loop with 7 checks an element, 9 to 15 % of a scalar loop. Row 948 (observed): a compiled block that reads `x` twice while another task assigns it plainly saw two values in 2,405 to 2,994 of 3,000 blocks; walk, 0 of 300. F-12; `explorations/reviews/parallelism-foundations-2026-11-08.md` §1.2, §1.4; `reviews/transaction-checks-ways-2026-11-17.md` §2. Strong atomicity on the compiled path is D2 (review-queue item 510), not yet asked.

**Answer, by path:**
- **walk: yes, and strongly.** (read) Every mutable variable, field and array element is a `ReferenceCell`. Each access is `synchronized` and finds the current transaction. A plain write aborts every reader and writer of the cell, and a plain read aborts its active writer (`interpreter/env/ReferenceCell.java:123-175`).
- **prelude and one: not through the STM, but through a check at every access.** (read; costs observed) Generated code calls `BaseTask.inATransaction()` before every read and write of a mutable local, a captured local, a top-level `var` and a `var` field (`compiler/codegen/VarCodeGen.java:334, 365, 490, 528, 660, 705`; F-374). The check reads the thread, its volatile task and the task's transaction (`runtimeSystem/BaseTask.java:255-263`). Outside a transaction the access is a plain volatile access of the `MutableFValue` cell (`compiler/runtimeValues/MutableFValue.java:18-33`), which neither takes nor checks the STM's global lock: weak atomicity (row 948). Immutable bindings and fields without `var` have no check.
- **one only: array elements pay a check too.** `FortressArrayStore.get` and `put` ask for the transaction at every access, then use `getVolatile` or `setVolatile` (`FortressArrayStore.java:35-57`). The prelude's `ZZ32Vector` has no check at all, and its elements stay outside the transaction even inside `atomic` (row 953).
- **The specification asks for strong atomicity.** `atomic` is atomic against "any action performed by any thread which is dynamically outside" (`Specification/basic/expressions/atomic.tex:36-41`), plain reads and writes included (`:104-106`).

So the handover's caveat holds for the compiled path only in part: the cost does follow `var` (and the one library's array elements), and removing `atomic` blocks removes none of it, but the cause is the per-access check, not strong atomicity, which the compiled path lacks.

## Q3. Which library paths use `atomic` or transactional cells internally?

**The record.** The parallelism review answers this (§1.8 and §6): microGPT never opens a transaction, and the library's own authors chose a sequential loop over atomic increments.

**I grepped the library now.** (read)
- **The core writes no `atomic` block.** None is in `FortressLibrary.fss`, `RangeInternals.fss`, `GeneratorLibrary.fss` or `NativeArray.fss`, nor in the prelude (`CompilerLibrary.fss`, `CompilerBuiltin.fss`). The only matches are two exception objects (`FortressLibrary.fss:2126-2132`) and two comments.
- **The two comments record a choice that matters for speed:** `Matrix.mul` runs its contraction axis in sequence, "If this were atomic, we could parallelize j-partition" (`FortressLibrary.fss:3135`), and dropped a cache-oblivious product "due to lack of support for atomic increment of matrix elements" (`:3264-3266`).
- **`atomic` blocks elsewhere:** `FileSupport.fss:152`, `:218` (`consume()`, reached by microGPT's loaders through `File` at load time: `explorations/run-c4/src/FlatData.fss:11`, `:69-75`); `List` through `OneShot` (`List.fss:13`, `:253-254`; `OneShotFlag.fss:18`); `Lazy.fss:60-63`; `SkipList.fss:641-692`; `ChunkedSparseArray.fss:94`, `:106`; `QuickCheck.fss:1035-1089`. None is on the step's path (inferred from the model's imports).
- **Cells that are transactional with no `atomic` written:** under walk, every array element and every `var`. Under one, every array element through `FortressArrayStore` (P-169 keys it by array and index), and every `var` local in a library body, such as the sequential leaf of every range reduction and loop (`result : T := red.empty()`, `i : ZZ32 := l`, `Library/RangeInternals.fss:1365-1385`), which pays row 641's check each iteration.
- **The generators and reductions themselves keep no shared state.** A range reduction joins the results of its two halves (`red.join(loop'(lo,mid-1),loop'(mid,hi))`, `RangeInternals.fss:1326`).

## Q4. Does the big-operator machinery treat `+` on floats as associative, and how are `Associative` and `Commutative` consulted?

**The record, which the code still agrees with:** the parallelism review §1.8 (algebra by reduction objects, associativity assumed and checked nowhere, deterministic join trees); row 37 (the specification's algebraic-constraints library does not ship); P-78 (`SUM`, `PROD` generic over `AdditiveGroup`, `MultiplicativeRing`); P-175 (a grain size). No ledger row holds `Associative` or `Commutative`.

**Answer:**
- **walk and one: yes, by declaration.** (read) `SUM[\T extends AdditiveGroup[\T\]\]` uses `SumReduction[\T\]`. That object extends `CommutativeMonoidReduction[\T\]` for every additive group (`FortressLibrary.fss:3700-3714`). `RR64` and `RR32` are additive groups (`Library/FortressLibrary.fsi:292-293`; `LibraryBuiltin/FortressBuiltin.fsi:41-42`). The contract is only a comment: "join must be associative with identity empty" (`FortressLibrary.fsi:2028-2030`).
- **No trait named `Associative` or `Commutative` is declared** in `Library/` or `LibraryBuiltin/`. The specification's `Commutative`, `Associative` and `ApproximatelyAssociative` (`Specification/advanced-lib/algebraic-constraints.tex:656-711`) are unbuilt (row 37). That text calls a float's `+` `ApproximatelyAssociative`, not `Associative` (`:586-590`).
- **Only the reduction object is consulted.** `SomeCommutativeReduction` is a mark whose one effect is that a commutative reduction is its own `reverse`, so a reversed generator does not swap operands (`FortressLibrary.fss:3487-3498`, `:3595-3609`, `:4186-4187`); `distribute` pairs are declared (`:3683-3708`). Nothing in `compiler/`, `scala_src/` or `runtimeSystem/` reasons about associativity (grep: one parsing comment, `scala_src/typechecker/impls/Operators.scala:400`).
- **The generator fixes the order.** (read) A `ZZ32` range splits at power-of-two boundaries and folds at most 16 elements left to right (`RangeInternals.fss:20`, `:1313-1333`, `:1365-1375`). The tree depends only on `(lo, hi)`, so a sum does not change with the thread count (inferred). On the prelude, reductions exist only over `ZZ32` and `String`, and run in sequence (row 982).
- **The specification already permits regrouping:** "A generator is permitted to group reduction operations in any way it likes consistent with its natural order" (`advanced/parallelism-locality/defining-generators.tex:61-66`); for a commutative operator "the order of terms is also arbitrary" (`basic/evaluation/reduction.tex:43-46`, on the unbuilt reduction variables). So SIMD lanes or several accumulators in a reduction's leaf need no new trait.
- **The matrix product is not a reduction.** Its leaf is a sequential read-modify-write, `res.put((a,c), res.get(a,c) + pr)` (`FortressLibrary.fss:3136`, `:3160`, `:3171-3172`). Its order is fixed by the library's code, not permitted by any rule.
- **Wider accumulation exists in the language.** (inferred) `SUM[\RR64\]` over `RR32` bodies converts each element by `RR64`'s `coerce(x: RR32)` (`FortressLibrary.fsi:295`; the `fortress-repo` skill, `revival-changes.md`, "Reductions").

## Q5. Does a disjoint-write parallel `for` over array indices run without any transactional overhead?

**The record:** row 641; row 155 (observed under walk: disjoint writes through views in a parallel `for`); F-350 (forked arms are joined); the parallelism review §5 (disjoint element writes are race-free by JLS 17.6 and `join`; volatile is stronger than the language needs); D1 (item 509), not yet asked.

**Answer: no path does STM work, since no transaction is opened, but every path pays something at each access.**
- **walk:** each element write is a `synchronized` `ReferenceCell.assignValue` that allocates a node (`ReferenceCell.java:123-160`); P-29 makes it irrelevant.
- **prelude:** there are no `RR64` arrays (row 305). A `ZZ32Vector` write has no check (row 953). `parloop` has no `var` (`Library/CompilerLibrary.fss:357-379`).
- **one:** each `a[i] := v` passes `PrimitiveArray.put` and reaches `FortressArrayStore.put` (`FortressArrayStore.java:35-57`). There it pays a check (an `instanceof` test and two volatile loads), a volatile store (`setVolatile`, a full fence on x86: inferred) and a boxed value (read). The counter of the leaf loop is a `var` (`RangeInternals.fss:1376-1385`), so each iteration pays about 3 to 4 checks (my count, inferred). Only the share of the locals is measured, and that against the prelude's `ZZ32Vector` (row 641). The store's check and the cost of volatile mode are unmeasured.

The transaction-checks review recommends its "Way 2" (a lexical rule in the code generator), which clears the counter's checks, and leaves the store's to D1. Neither is decided.

## Q6. How are native Java types exposed to Fortress, and can a thin wrapper over `float[]` be added that way?

**The record:** P-58 (every native binding is `builtinPrimitive("…")` naming a static helper in `nativeHelpers/`); P-169 (the arrays' store is a `FortressLibrary` trait over a compiled class, and walk's loader answers the same names with its own operations); F-333; F-301 (a generated wrapper unboxes each argument and boxes the result; C2 inlines it).

**Answer: yes, and the tree already holds the pattern to copy.** (read)
- **The pattern, for `RR64`:** the trait `JavaRR64ArrayStore`, whose `get(i: ZZ32): RR64 = builtinPrimitive("com.sun.fortress.nativeHelpers.arrayOps.getRR64")` (`FortressLibrary.fss:2533-2542`); static helpers in `nativeHelpers/arrayOps.java` over `FortressRR64ArrayStore`; the one library's table in `compiler/NamingCzar.java:490-491`, which pairs the Java class with the trait (it reads `float` as `RR32`, `:445-446`, `:481-482`); and walk's answers, `interpreter/glue/prim/ArrayOps.java:56-72`, over `JavaRR64ArrayStoreObject` (`LibraryBuiltin/FortressBuiltin.fss:53-59`).
- **A `float[]` store takes the same steps** (inferred): a class `FortressRR32ArrayStore` holding a `float[]`; helpers `makeRR32`, `getRR32`, `putRR32`, `initRR32` over `float`; a trait `JavaRR32ArrayStore`; one line in NamingCzar's table; walk's `ArrayOps` classes; a test on both paths. P-84 already decides that `RR32` arrays go in `float[]`. What remains open is how the factory chooses the store (decision A) and whether the store joins transactions (D1). A store with a `put` outside the transaction would repeat row 953.
- **A helper called per element still boxes at the boundary.** The wrapper makes a new box for each result (F-301). Only a kernel-sized helper avoids this, such as a whole matrix product over two stores (inferred). By P-27, it goes inside the library's own `Matrix.mul`, which the model already calls. A model-level tensor type would change model lines (P-87).
- **`import java` in a `.fss` file is the other route.** The compiled path binds static methods that way. Under walk it is unfinished, and no test uses it. P-58 settles the form of a binding.

## Q7. Does microGPT as ported train on one document per step, and where would batching go?

**The record:** F-355 (observed: the Java baseline's step takes about 101 µs at batch 1 and 407 µs at batch 4); `explorations/run-c4/design.md:47` (C4's 40 checks, batch 4 among them, pass under walk); `explorations/c4-parallelism.md` §2 (the contraction over positions is written as products; the sum lives inside `mul`).

**Answer:** (read)
- **The gradients are whole arrays, with a hand-written backward pass.** Each forward line has its backward line under it (`explorations/run-c4/src/MicroGptFlat.fss:57-65`). There is no graph of scalars. The scalar-graph port is the earlier `explorations/microgpt.fss`, which trains on one document per step (`:228-229`).
- **One document per step, set by the driver:** `bsz = 1` (`:82`), used in `keys(bsz, fn (i: ZZ32): ZZ32 => (s bsz + i) MOD corpus.size())` (`:88`); the banner literal prints "batch 1, 5 steps" (`:81`).
- **The step itself is already batched.** `step(p, b)` takes a vector of document keys (`:46`), and each (document, position) pair is one row of each matrix (`:51`). The corpus gives tokens, positions and the validity mask over |b|·blk rows (`FlatData.fss:110-117`). Attention stays inside each document through the planes of `heads` (`:49`; `FlatArrays.fss:82-96`). The loss is the token-weighted mean, `nv = ∑ vm`, `/ nv`, `diag(vm / nv)` (`:47`, `:56`, `:58`). `MicroGptFlatCheck.fss:61-73` checks batch 4 against goldens, and that its loss is the token-weighted mean of the single-document losses.
- **So a batched step changes one model line, `:82`, and the banner at `:81`.** The batch's gradient sum is then the contraction over B·16 rows inside each weight product (`:58-65`), which `mul` runs in sequence per output element (`FortressLibrary.fss:3171-3172`). The added parallelism is on the row axis: `rows` (`FlatArrays.fss:142-165`), the planes (`:131`), the maps, and `DOT` or `SUM` over B·16 > 16 elements (F-350).
- **The handover's design changes more lines** (inferred). Mapping the step over documents and summing the gradients changes the driver at `:88`. Each step also divides by its own `nv`, so per-document weights of nv_d/nv are needed to match the checked mean.
- **The curator's rules apply.** P-87: a change to any model line is shown to the curator as a diff before it is built. P-29: until microGPT runs compiled, C4 is not edited for speed. A batch size raised for speed falls under both.

## Q8. Does HotSpot auto-vectorise the i-k-j GEMM inner loop as the Fortress compiler emits it, or is an explicit Vector API kernel needed?

**The record** (observed in plain Java: F-355, `explorations/java-baseline/REPORT.md` §5; JDK 25, x86-64 with AVX-512, packed instructions counted): the i-k-j loop with two offsets, `out[ro+j] += s * w[rw+j]`, is not vectorised, since C2 does not prove the rows disjoint; one index on two arrays is, but pays only on long loops; a sum of products is half-vectorised and slower than with superword off; Adam's elementwise loop is vectorised 8 wide. The Vector API in the four products makes them 1.8 to 3 times faster and the step 101 → 75 µs, checks passing. No compiled matrix product has run (F-358).

**Answer: the compiler emits no such loop.** (read, plus inferred for C2)
- **prelude:** no matrix compiles (row 305). A matrix return type crashes the checker (row 1087).
- **one:** `Matrix.mul` is a recursive split (`FortressLibrary.fss:3129-3183`) that forks the halves of the rows and of the columns and runs the halves of the contraction in sequence, down to single elements. Each leaf is one boxed multiply-add through `res.get` and `res.put` and the store of Q1 (volatile mode, a check, a cast). There is no counted loop over a primitive array, which C2's superword pass needs.
- **An explicit kernel is needed (inferred).** Plain Java on JDK 25 did not vectorise this shape either (observed). The kernel would be a Java helper in `nativeHelpers/` (compiled at level 25, so it can use `jdk.incubator.vector`, with `--add-modules` at compile and run), called by the library's `mul` over the unboxed store. The record has no NEON measurement: all its timings are x86-64 with zmm.

## The handover's other statements, checked

**STM background.**
- **"Each shared variable has a version … at commit it locks the written variables":** neither path. Walk descends from DSTM: a node chain per cell, visible readers, eager conflict detection, a commit as one compare-and-set on the status, a manager that always aborts the other (parallelism review §1.2). The compiled STM has NOrec's shape: one global sequence lock, writes buffered in a `Hashtable`, validation by value, the first committer wins, unbounded retries, backoff off (`runtimeSystem/Transaction.java`; F-351; review §1.4).
- **"Instrumenting … costs 2–10×":** observed here: an uncontended compiled `atomic` increment 208 ns against 15 ns plain; a contended counter slower at four threads than at one; private work 2.0 to 2.7 times faster on four workers (review §3.3); the checks outside `atomic`, 9 to 15 % and 64 % (row 641).
- **Weak against strong atomicity:** walk strong, compiled weak (row 948), specification strong (Q2).

**Fortress specifics.**
- **"The original interpreter implemented `atomic` on a … library derived from DSTM2, with threads on Doug Lea's fork/join pool":** right for walk, qualified: DSTM2 was imported on 2007-06-13 (`9aed945d8`) and rewritten, and `dstm2/` is gone at `a874948ac`; the compiled path has a second, unrelated STM of 2012 (review §2); the pool is now `java.util.concurrent.ForkJoinPool`, once jsr166y.
- **"No published result shows a multicore gain":** not checked. The team never measured the compiled path (each check built a debug string until the revival fixed it, row 302); the revival found that the compiled STM does not scale (review §3.3).
- **"The bet was on hardware TM in Sun's Rock processor":** not checked. Nothing in `Specification/` or `Papers/` mentions Rock or hardware TM (grep). The specification says its read atomicity needs "hugely expensive mechanisms" (`basic/memory-model.tex:240-246`), and its cheaper local objects were never built (`advanced/parallelism-locality/shared-local.tex:40`).
- **"Object fields are immutable unless declared `var` or `settable`": partly wrong.** `var` makes a field mutable. `settable` gives it an implicit setter (`basic/traits.tex:745-759`), and implies `var` on an abstract field (`:757`). A value object's fields stay immutable: there a `settable` field is shorthand for building a new object and assigning it to the receiving variable (`basic/objects.tex:376-387`; walk runs it, row 116). The desugarer makes the setter (`compiler/desugarer/DesugaringVisitor.java:304`).
- **"`value object` gives immutable value types":** right by the specification, though nothing refuses a `var` field in one (row 112); compiled, `value` only adds a mark interface and inlines nothing (`fortress-repo` skill, `compiler.md`).
- **"Arrays are mutable":** yes (`put`, `a[i] := v`: `NativeArray.fss:18-20`), but each element is initialized at most once (`advanced/parallelism-locality/arrays-distributed.tex:71`; a second initialization is silently ignored, row 466), and immutable arrays exist (`PrimImmutableArray`, `freeze()`). microGPT writes almost only by initialization (`map`, `ivmap`, `tabulate`, `fill`); it assigns with `:=` only in `flat` (`FlatArrays.fss:185`) and in the loader.
- **The `atomic sum +=` and `SUM[i <- 1:n] a[i]` examples:** right in form. `SUM` writes its static argument where nothing fixes the element type (P-78); under walk and one a range reduction splits down to a grain of 16 (P-175); on the prelude, reductions run in sequence (row 982).
- **Right as stated:** `x = e` immutable and `var`/`:=` mutable (`basic/variables.tex`); `seq` makes a loop sequential (F-19), though compiled its `var` accumulator still pays the check (F-12); disjoint array writes need no `atomic` (`basic/memory-model.tex:69-75`; row 155); the specification's strong atomicity (`atomic.tex:36-41`, `:104-106`; for "if this one does", Q2).
- **"Where Valhalla would matter: only a value object inside an array":** too narrow here (inferred). Every number is a boxed value-object class (F-11), and P-17 requires unboxing. The specification makes access to a mutable location indivisible, "a large value object" included (`basic/memory-model.tex:252-256`), which limits flattening one of several fields. The emitted classes stay at bytecode version 1.6 because the loader's rewriting keeps no stack-map frames (`runtimeSystem/InstantiatingClassloader.java:78`); a value-class backend changes that first.
- **"Tiny matrices lose to scheduling":** agrees with F-356 (observed in a Java model): at the library's grains a step takes 19 to 32 times the plain step on one thread and 80 times on four, mostly from the product's missing grain.
- **"Prefer `float`":** see gap 1 below. On the prelude, `RR32` arithmetic answers `RR64` (row 529). The goldens and the tolerances of the model's checks (1e-12) are for `double`.
