Fortress revival · debugging report · JDK 11 rung

The Probe and the Pin

How 458 test failures under JDK 11 were traced to a single missing target= attribute in a 2012 build.xml — a narrated walkthrough of every grep, the construction of the ASM probe, and the reasoning that connected them. Everything below is reconstructed from the verbatim session transcript, not from memory.

Chain of evidence

  1. Gate summary: 458 junit failures, all in the compiler-path suites; the interpreter suite stayed green.
  2. First stack trace: ArrayIndexOutOfBoundsException inside ASM 3.1's ClassReader, reached from ForeignJava.findClass.
  3. Source read: that call parses a classfile for every import java ... in Fortress code.
  4. API survey: upgrading ASM would be a multi-file migration — wrong fix for this rung.
  5. Controlled probe: JDK 11's own classes parse fine; our freshly built class fails. Hypothesis overturned.
  6. javap: our class is major version 55 with invokedynamic string concat — javac was never told target=.
  7. The pin: target="${javaSourceVersion}" on all 8 javac tasks. Rebuild → v52 → probe passes → 458 failures become 3.

Step 1 / Read the failure at the summary level firstSizing the damage before touching any stack trace

The background gate had finished with testSystem=BUILD SUCCESSFUL, testFast=BUILD FAILED. Before looking at any individual failure, the first command extracted only the shape of the damage:

Ran — check JDK 11 gate final results

grep -E 'Tests run.*(Failures: [1-9]|Errors: [1-9])' $SP/jdk11-testFast.log | head
grep -c 'UNEXPECTED' $SP/jdk11-testFast.log

The first pattern is worth unpacking. JUnit prints one summary line per suite — Tests run: N, Failures: N, Errors: N, ... — and most of them say Failures: 0. The character class [1-9] deliberately excludes zero, so the grep returns only the suites that actually failed, skipping hundreds of healthy summary lines. The alternation catches suites that failed via errors rather than assertions. The second command counts occurrences of the harness's UNEXPECTED exception marker — not to read them, just to get a magnitude.

Got

Tests run: 642, Failures: 186, ...   ← CompilerJUTest
Tests run: 55,  Failures: 42,  ...   ← LibraryJUTest
Tests run: 263, Failures: 230, ...   ← OtherCompilerJUTest
235                                   ← count of UNEXPECTED markers

458 failures, 235 unexpected exceptions. Two structural facts fell out immediately, before reading a single trace: the failures were massive and uniform (230 of 263 in one suite — not a scattering of flaky tests, but something systemic), and testSystem — the 382-test interpreter suite — had passed untouched. Whatever broke, it broke only the path that compiles Fortress to JVM bytecode. That asymmetry became the first constraint on any hypothesis.

Step 2 / Get one representative trace, cheaplyAn awk idiom for "the first match, plus context, with line numbers"

Ran — extract first failure details from testFast log

grep -n 'UNEXPECTED' $SP/jdk11-testFast.log | head -3
awk '/UNEXPECTED/{print NR": "$0; c=NR} c && NR>c && NR<c+30' $SP/jdk11-testFast.log | head -45

With 235 identical-looking markers, reading them all would be waste; reading one, fully, is the move. The awk program is a hand-rolled grep -A30 with line numbers: on each match it prints the numbered line and records the position in c; the second clause then prints every subsequent line within 30 of the most recent match. Piped through head -45, it yields the first marker plus its complete stack trace and nothing else. (The preceding grep -n | head -3 confirmed matches began at line 134 — i.e. the failures started essentially at the top of the run, another hint of something systemic rather than test-specific.)

Got

java.lang.ArrayIndexOutOfBoundsException: Index 3145 out of bounds for length 79
  at org.objectweb.asm.ClassReader.readClass(ClassReader.java:1976)
  at org.objectweb.asm.ClassReader.accept(ClassReader.java:464)
  at com.sun.fortress.repository.ForeignJava.findClass(ForeignJava.java:135)
  at com.sun.fortress.repository.ForeignJava.processJavaImport(ForeignJava.java:291)
  at com.sun.fortress.repository.GraphRepository.collectExplicitImports(...)

This trace is unusually eloquent. An ArrayIndexOutOfBoundsException with a huge index (3145) against a tiny array (79) inside a classfile parser is the signature of a format-version mismatch: the reader has walked off the rails mid-file because the bytes don't mean what it thinks they mean. ASM 3.1 is from 2007. The frame below it says the crash happens during processJavaImport — so every Fortress program containing import java ... dies at compile time. That explains both the scale (458) and the asymmetry (the interpreter never parses classfiles).

Step 3 / Read the crash site and its callerTwo windows into ForeignJava.java

Two targeted Reads — not the whole 900-line file — at the line numbers the trace supplied: offset 100 for findClass, offset 255 for the calling context in processJavaImport. The first window found the exact call:

static ClassNode findClass(String s) throws IOException {
    ClassReader cr = new ClassReader(s);
    ClassNode cn = new ClassNode();
    cr.accept(cn, ClassReader.SKIP_DEBUG | ClassReader.SKIP_FRAMES | ClassReader.SKIP_CODE);
    return cn;
}

Two things mattered here. First, new ClassReader(String) loads the class by name through the classloader — so what gets parsed is whatever is on the runtime classpath, JDK classes and Fortress's own build output alike. Second, the exact flag set (SKIP_DEBUG | SKIP_FRAMES | SKIP_CODE) was recorded, because any faithful reproduction must use the same flags — ASM's parse path differs depending on what it skips. The second window showed the dot-to-dollar "hunting" loop that tries a.b.C.d, a.b.C$d… — which meant findClass gets called speculatively many times per import, so a single unparseable class poisons every import that touches it.

Step 4 / Survey before choosing the fixHow entangled is Fortress with ASM's API?

At this point the obvious fix candidate was "upgrade ASM." Before committing to that, one command measured its cost:

Ran — survey ASM API usage across Fortress source

grep -rEl 'implements (ClassVisitor|MethodVisitor|FieldVisitor|AnnotationVisitor)|extends (ClassAdapter|MethodAdapter|ClassNode|MethodNode)' . | head
echo ===
grep -rc 'org.objectweb.asm' --include=*.java . | grep -v ':0' | sort -t: -k2 -rn | head -12

The two greps answer two different questions. The first (-l, files-only) looks for classes that implement or extend ASM's visitor types — the load-bearing pattern, because ASM 4 turned the visitor interfaces into abstract classes and deleted ClassAdapter/MethodAdapter outright; every hit is a file an upgrade would break. The second (-c, count per file, grep -v ':0' to drop non-users, sort -t: -k2 -rn to rank by the count field) produces a league table of ASM dependence.

Got

9 files implement/extend ASM visitor types
  (Instantiater, MethodInstantiater, FortressForeignAdapter,
   FortressMethodAdapter, ByteCodeVisitor, ... ManglingMethodVisitor)
===
ForeignJava.java:33   NamingCzar.java:19   CodeGen.java:14   ...

Verdict: an ASM upgrade was a genuine migration project across the code generator, the runtime classloader, and a bytecode optimizer — far too much for a rung whose one variable was "JDK 8 → 11." So the fix had to go the other way: make the classfiles parseable by ASM 3.1. (The upgrade was deferred and later became its own gated rung — ASM 9.10.1 — where that 9-file survey served as the work list.)

Step 5 / The probeA 20-line controlled experiment

The standing hypothesis was "ASM 3.1 can't read JDK 11 classfiles." Plausible — v55 classfiles didn't exist in 2007. But it was still a guess, and the next step was built to split the hypothesis space in a single run:

Ran — probe which classes ASM 3.1 fails to parse on JDK 11

cat > $SP/asmprobe/Probe.java <<'EOF'
import org.objectweb.asm.ClassReader;
import org.objectweb.asm.tree.ClassNode;

public class Probe {
    public static void main(String[] args) {
        for (String s : args) {
            try {
                ClassReader cr = new ClassReader(s);
                ClassNode cn = new ClassNode();
                cr.accept(cn, ClassReader.SKIP_DEBUG | ClassReader.SKIP_FRAMES | ClassReader.SKIP_CODE);
                System.out.println("OK   " + s + " (methods=" + cn.methods.size() + ")");
            } catch (Throwable t) {
                System.out.println("FAIL " + s + " : " + t);
            }
        }
    }
}
EOF
javac -cp $TP/asm/asm-all-3.1.jar Probe.java
java -cp .:$TP/asm/asm-all-3.1.jar:/home/user/fortress/ProjectFortress/build Probe \
  java.lang.String java.lang.Object java.lang.Integer \
  com.sun.fortress.nativeHelpers.simplePrintln com.sun.fortress.nativeHelpers.systemOps

Every detail of the probe's construction is deliberate:

It replicates the crash site exactly. Same ClassReader(String) constructor, same ClassNode sink, same three SKIP flags copied from ForeignJava.findClass. A probe that "roughly does the same thing" proves nothing; this one is line-for-line the failing call with a try/catch around it.

It compiles against the identical jar. -cp third_party/asm/asm-all-3.1.jar — the vendored 2007 artifact itself, not a modern ASM from anywhere else.

Its classpath mirrors production. The probe's runtime classpath includes ProjectFortress/build, exactly what the Fortress compiler sees, so class names resolve to the same bytes.

Its argument list is the experiment. Three JDK platform classes (String, Object, Integer) test the hypothesis "JDK 11's own classfiles break ASM 3.1." Two classes from Fortress's own freshly compiled build output (simplePrintln, systemOps — natives the compiler imports constantly) test the alternative. One invocation, both hypotheses.

Got

OK   java.lang.String (methods=109)
OK   java.lang.Object (methods=14)
OK   java.lang.Integer (methods=60)
FAIL com.sun.fortress.nativeHelpers.simplePrintln :
     java.lang.ArrayIndexOutOfBoundsException: Index 3145 out of bounds for length 79
OK   com.sun.fortress.nativeHelpers.systemOps (methods=3)
The hypothesis flipped. JDK 11's platform classes — the "obvious" suspects — parse fine under those SKIP flags. The class that fails is our own, compiled minutes earlier by our own build. And it fails with the byte-identical exception from the test log (Index 3145, length 79), confirming the probe reproduces the real defect, not a lookalike. The bug wasn't in what JDK 11 ships; it was in what our build produces under JDK 11. (Also informative: systemOps passed while simplePrintln failed — same package, same build, so the trigger was some feature only one of them used.)

Step 6 / Interrogate the artifactjavap with a checklist of post-2007 constant-pool types

Ran — inspect constant pool of failing classfile

javap -v -p -cp ProjectFortress/build com.sun.fortress.nativeHelpers.simplePrintln 2>&1 \
  | grep -E 'major|minor|#[0-9]+ = (Dynamic|InvokeDynamic|MethodHandle|MethodType|Module|Package)|BootstrapMethods|NestHost|NestMembers|Attribute' | head

The grep pattern here is a checklist, not a search: it enumerates every constant-pool tag and attribute introduced after ASM 3.1's era — InvokeDynamic and MethodHandle/MethodType (Java 7), Dynamic (condy, Java 11), Module/Package (Java 9), NestHost/NestMembers (Java 11) — plus the version header. Whatever matches is, by construction, something a 2007 parser has never heard of. The #[0-9]+ = prefix anchors matches to actual constant-pool entries rather than incidental prose in method bodies.

Got

minor version: 0
major version: 55                        ← Java 11 format
#8  = InvokeDynamic  #0:#47  // makeConcatWithConstants(...)
#44 = Utf8           BootstrapMethods
#45 = MethodHandle   6:#64   // REF_invokeStatic
     java/lang/invoke/StringConcatFactory.makeConcatWithConstants...

Complete explanation in two lines. Major version 55: the class was compiled as Java 11 bytecode. And the payload that actually derails a 2007 parser: on JDK 9+, javac compiles ordinary string concatenation ("a" + b) to invokedynamic against StringConcatFactory — so even trivial 2008-era source code, recompiled, now contains constant-pool tags ASM 3.1 misparses, walking it into the weeds and off the end of a 79-slot array. That's also why systemOps survived: no string concatenation, no indy.

But why v55? The build had faithfully set Java 8 compatibility for years. That question pointed straight at the build file.

Step 7 / Find the hole in the buildOne grep over build.xml, then sed windows instead of scrolling

Ran — find javac source/target settings in build.xml

grep -n 'javaSourceVersion\|<javac\|source=\|target=\|release=' build.xml | head -40

One pass, four facts, because the pattern bundles the property definition and every mechanism that could pin a bytecode level (source=, target=, release=) together with every <javac opening tag. The -n matters — the line numbers are the input to the next command. The output showed: javaSourceVersion=1.8 defined at line 134; eight <javac tasks; source= present on five of them; target= present on zero; release= nowhere.

That's the whole bug, visible in a grep listing. Ant's <javac> with source="1.8" but no target= lets -target default to the running JDK — harmless for years because the running JDK was 8, silently catastrophic the day it became 11. Three tasks set neither attribute, drifting entirely with the JDK.

Ran — show all javac task definitions

for l in 426 512 541 561 663 690 711 1393; do
  echo "=== line $l ==="; sed -n "${l},$((l+7))p" build.xml
done

Rather than opening the 1,400-line file, the grep's line numbers were fed into a loop of sed -n "$l,$((l+7))p" — eight 8-line windows, one per javac task, printed side by side. The purpose was classification before editing: which tasks have source= only, which have neither, and whether the attribute blocks are textually uniform enough for pattern-anchored edits. They fell into exactly three shapes: five tasks with source= then debug="true"; two "bare" tasks (srcdir/destdir/debug, no version at all); and one single-line javac for the numerics package.

Step 8 / The pinThree edits that cover eight sites, then count-verify

The three shapes admitted three surgical edits — two of them replace_all edits anchored on multi-line context strings, so each fires on every instance of its shape and can't touch anything else:

EditAnchorCovers
1 · replace_allsource="${javaSourceVersion}" ⏎ debug="true" → insert target= between5 tasks
2 · replace_allsrcdir="${src}" ⏎ destdir="${build}" ⏎ debug="true" → insert source= + target=2 bare tasks
3 · singlethe one-line numerics <javac>, edited in place1 task

Both values pin to the same existing property, ${javaSourceVersion} — no new knob, and future version bumps stay a one-line change. Then the closing bracket of the whole investigation, verification by arithmetic:

Ran — verify all javac tasks now pin target

grep -c 'target="${javaSourceVersion}"' build.xml   # → 8  (= number of javac tasks)
git diff --stat                                      # → build.xml | 11 +, 1 −

Eight pins for eight tasks, and a diff-stat small enough to read as a sanity check that the replace_alls hadn't rippled anywhere unexpected.

Step 9 / Cheap proof before expensive proofSeconds of verification before 17 minutes of gate

Before spending a full test-gate cycle, the fix was proven at the artifact level: ant clean compileAll, then javap | grep major on the previously failing class — major version: 52 — then the same Probe binary re-run against the rebuilt tree — OK simplePrintln (methods=13). Only then was the fix committed (flagged to Pavol as an original-tree edit, build.xml only) and the full gate re-run in the background.

Gate rerun

testSystem: Tests run: 382, Failures: 0, Errors: 0        (unchanged, as predicted)
testFast:   458 failures → 3

The strategies, generalized

Read failures top-down: shape before content.

Suite-level counts (Failures: [1-9] to mute the zeros, grep -c for magnitude) revealed "systemic, compiler-path-only" before any stack trace was opened — which immediately constrained the hypothesis space to classfile handling.

One failure, read completely, beats 235 read partially.

The awk match-plus-context idiom pulled a single full stack trace out of a megabyte of log. Uniform mass failures almost always share one root cause; pick the first specimen and dissect it.

Reproduce the exact call, not a paraphrase.

The probe copied the crash site's constructor, flags, jar, and classpath verbatim. The reward: its failure was byte-identical to the log's (Index 3145 / length 79), which is what licenses trusting everything else the probe says.

Design inputs to split hypotheses, not confirm them.

Platform classes and own-build classes in one argument list meant a single run could overturn the leading hypothesis — and did. The most valuable probe output is the one that surprises you.

Greps can be checklists.

The javap filter enumerated every post-2007 constant-pool tag by name. When you know the taxonomy of possible culprits, encode the whole taxonomy in the pattern and let the output name the culprit.

Survey the blast radius before choosing the fix.

Two greps (visitor-subclass hits, per-file reference ranking) priced "upgrade ASM" at nine breaking files — the evidence for fixing the build instead, keeping the rung to one variable. The survey later became the work list for the real ASM rung.

Edit by shape, verify by count.

Classify the sites (sed windows from grep -n line numbers), anchor replace_all edits on multi-line context so they cover a shape exactly, then verify with arithmetic: grep -c = 8 = number of javac tasks.

Ladder of proof: cheap rungs first.

javap (seconds) → probe (seconds) → compile (80 s) → full gate (17 min). Each rung could have falsified the fix before the next was paid for.

Epilogue — the three survivors. The screenshot's window ends at the count-verify step; the story continued. The three remaining failures were genuinely different JDK 11 issues in Fortress's custom runtime classloader: Integer3/Integer4 died with IllegalAccessError when reflection-generated accessor classes were routed through InstantiatingClassloader (surfacing via the vendored jsr166y fork), and CompileMath hit a ClassFormatError because the native/java/lang/Math wrapper class carried a stale NestMembers view of the JDK 11 original. Their investigation proceeded by the same playbook — trace, source window, targeted grep for mustUseSystemLoader — and the deeper causes were retired for good by two later rungs of the modernization ladder: the jsr166y → java.util.concurrent migration and the ASM 3.1 → 9.10.1 upgrade.
