# Facts on record: history

## Execution model

<!-- moved 2026-09-19 from FACTS.md § Execution model -->
- **Boxing is not the ceiling on the scalar loop** (measured 2026-09-15, `perf-probes/boxing/REPORT.md`; an edge case, see the entry above): on the 20 M-iteration scalar loop, compiled Fortress is 156× primitive Java, and a Java loop boxed the way the runtime boxes is 2.4-4.2× primitive, so boxing explains about 2% of the gap. The gap is three named, separately fixable costs: each float literal is rebuilt per iteration through `FFloatLiteral`, which stores the literal as a `String` and parses it back (about 30%); the accumulator's read and write go through `BaseTask.inATransaction()`, which builds a debug message eagerly on every call (about 34%, a one-line fix); the sequential `for` is `countedseqloop`, a recursive subdivision with boxed indices and a closure call per element (`CompilerLibrary.fss:340-348`, about 7%); the representational rest (volatile cell, allocations, interface hops, checkcasts) is about 30%. Interpreter/compiled 5.6× on this loop, 8.6× on the allocation loop. Ledger row 302; row 303 (kernels) corrects the general claim: on array code boxing is 6.3-6.5× in the Java models, so this bullet holds for the scalar loop only.

<!-- moved 2026-09-20 from FACTS.md § Execution model -->
- The compiled path measured 6.8× on a scalar `RR64` loop, 8.9× on object-allocating code, 8× on startup, numerics identical (`compiled-path-gaps.md:45, 100-101`); what blocks it is its 592-line prelude (no `List`, no generic `array`, no `exp`/`log`, no `SUM`, an empty `Matrix`), not code generation (rows 71-82).

- **A top-level mutable variable compiled by rung 3 is outside the transaction.** `VarCodeGen.MutableStaticBinding` reads and writes it with a bare `GETSTATIC`/`PUTSTATIC` on a non-final, non-volatile static field, while the team's own `LocalMutableVar` and `MutableTaskVarCodeGen` in the same file call `BaseTask.inATransaction()` and route through `TXRead`/`TXWrite` over a `volatile` cell, and the interpreter stores the same construct in a transactional `ReferenceCell` (`BaseEnv.java:599-601`). `atomic do ... end` does compile on this path with a real retry loop (`CodeGen.forAtomicBlock`), so such a variable is not in the write set, is not rolled back on abort and is written again by the retry, against `Specification/basic/expressions/atomic.tex:37-42` and `:65-67`. - **The team already folds `IntLiteral` arithmetic at compile time and warned against doing it at run time.** `IntegerLiteralFoldingVisitor.java` folds the operators in `BigInteger` and `phases/PhaseOrder.java:57,142` wires `INTEGERLITERALFOLDING` before `TYPECHECK`; three lines below the comparison block rung 6 cited by line number, `FortressBuiltin.fss` carries the team's comment, verbatim: "Do not enable these until coercion is implemented; doing so will cause all our arithmetic to occur on IntLiterals". - **Checked integer arithmetic keeps integer loops scalar on the JVM** (2026-09-17, from the rung 6 skeptic's overflow finding; recorded at length in `performance-roadmap.md` under "Corrections recorded on the way"): `+` on `ZZ32` binds to `jIntOverflowingAdd` (`LibraryBuiltin/CompilerBuiltin.fss:625`), whose helper (`nativeHelpers/simpleIntArith.java`) tests the sign bits and throws `IntegerOverflow`, which the spec mandates (`Specification/basic-lib/basic-integers.tex:114-117`; `⊞`/BOXPLUS is the wrapping operator, `CompilerBuiltin.fss:626`); HotSpot's SuperWord vectorizes only counted loops with no control flow in the body, so a branch per operation, however cheap scalar, forecloses SIMD. The consequence for the roadmap: step A5's "SIMD comes free from HotSpot" holds for floating-point loops, which is where microGPT's hot arithmetic is (`RR64`, no trapping), and not for the integer indices, counters and reductions around them, nor for A2's address arithmetic. Four remedies exist, cheapest first, and the roadmap lists them; none is worth doing before the loops are measured.
