## 1. What changed

`walk` applies the declared type's lifted `coerce_<T>`, found at the top level of the type's environment, in three kinds of place:
- a single function's, constructor's, method's, native's and varargs parameter (`NonPrimitive.typecheckParams` and `buildEnvFromParams`);
- an overloaded call where no overload applies without coercion: `OverloadedFunction.bestMatchWithCoercion`, called at the team's TODO, takes the most specific applicable coercion by `conversions-coercions.tex:469-484` and refuses an ambiguous call; the result is a `Coercions.CoercedCall`, kept in the per-argument-type cache, which converts the arguments and dispatches the converted arguments as an ordinary call through the owning `OverloadedFunction` (`Coercions.java:228-230`); an overloaded method converts and calls `applyMethod` again (`OverloadedMethod.java:56-63`);
- a typed local, top-level or field declaration, and an assignment to a typed variable or field (`LHSEvaluator`, `BaseEnv.assignValue`, `BuildEnvironments`, and `LazilyEvaluatedCell`, which carries the declared type and converts when first computed).

A declaration, parameter or assignment of tuple type converts element by element, an element already of its type kept (`Coercions.coerce` and `coerceTuple`, `Coercions.java:88-116`); a size mismatch, a varargs element or an element with no coercion stays the loud error it was.

## 4. The specification

The places: `Specification/basic/conversions-coercions.tex:98-110` lists where coercion occurs, variable and field declarations (`:100-101`), arguments (`:102-103`), declared return types (`:104-105`), tests and properties (`:106`), contracts (`:107`) and constrained subexpressions (`:108-109`); the draft note at `:113-124` lists "assignment expressions with type on the left-hand sides" among the contexts to settle; assigning a field calls its setter, a functional call (`Specification/basic/expressions/bindings.tex:60-61`).

The resolution: applicable without coercion first, otherwise the coercion yielding the most specific type (`:455-460`); the specificity relation (`:469-484`, elementwise over tuples at `:493-496`, "more specific" at `:498-499`); the rewriting (`:516-536`). The last sentence of that passage, `:532-536`, in full: "The call $\f(\As)$ or $\As_0.\f(\As)$ is rewritten to \EXP{f(\mathrm{coercion}\llbracket{T}\rrbracket(\TYP{A}))} or \EXP{A_{0}.f(\mathrm{coerce}\llbracket{T}\rrbracket(A))} and the declaration with parameter type $T$ is applied to the call."

**Which declaration runs, a decision of the judge.** Read alone, "and the declaration with parameter type $T$ is applied to the call" says what the first pass did: apply exactly the declaration chosen before the conversion. The judge ruled the other reading, and the repair round built it: the clause names the static call's declaration, as for any call, and run-time dispatch refines it among itself and the declarations more specific than it. The grounds: the passage describes a static call, rewritten "for pedagogical purposes; implementation techniques may vary" (`:512-514`); the rewriting inserts explicit `coerce` calls into the expression, making an ordinary call (`:253-265`); what is fixed statically is the coercion, "the statically chosen coercion is applied at run time" (`:567-570`), not the declaration that runs; for every call the run-time dispatch "need only consider dispatching among that declaration plus declarations that are more specific than that declaration" (`Specification/advanced/overloading.tex:73-78`), "the most specific declaration that is applicable to a dynamic call is more specific than the most specific declaration that is applicable to the corresponding static call" (`:466-468`), and a call dispatches among the declarations applicable to it at run time (`Specification/basic/overloading.tex:263-276`). The specification's own example (`conversions-coercions.tex:572-604`) cannot tell the two readings apart, because there `B` excludes `A`, so a coerced `A` can only reach `f(A)`. The compiled path takes the same reading (`probes/skeptic/diff-1.txt:21`, `:28`). **The rejected alternative**, applying exactly the pre-conversion declaration, gave `g(NarrowOf(2))` = `g(Wide)` with `g(Wide)`/`g(WideOf)` declared, where the compiled run gives `g(WideOf)` and `walk` itself gives `g(WideOf)` once the same value is bound first (`probes/skeptic/diff-1.txt:5-6`, `:12-13`); it was the first skeptic's ground of refusal. `ProjectFortress/tests/CoercionRedispatchRungC.fss:36` cites `:532-536` together with `:253-265` and the two overloading passages for this reading.

## 5. Decisions

- **At a single value's check**, replace the value where `typeMatch` fails with the result of the declared type's coercion. Rejected: widening `FType.typeMatch` to substitutability, which would coerce when a declaration applies without it (against `:455-458`); relabelling with `FAsIf`, which changes the type seen and not the value; catching the refusal and retrying (the `Fcn.applyToArgs` shape), because the refusal is thrown after the value is lost and an exception per check costs more; rewriting the syntax tree with `coerce_` calls, which needs static types.
- **Overloaded call**: a second pass at the team's TODO that returns a `CoercedCall`, kept in the existing per-argument-type cache, valid because which overloads apply, with or without coercion, depends only on the argument types, which are the cache key (`OverloadedFunction.java:81-82`, `FValue.asTypesList`). Rejected: a second plan cache beside the first; coercion inside `bestMatchInternal`'s single pass (the specification tries every declaration without coercion first, `:522-525`).
- **The re-dispatch** (the judge's ruling): the converted arguments are dispatched as an ordinary call through the owning `OverloadedFunction`, and a method call re-enters `applyMethod`. Rejected: applying the overload chosen before conversion, the first pass (section 4). Rejected: caching the choice refined by the converted type, because the type of a `coerce` result may depend on the value (`CoercionRedispatchRungC`: `g(NarrowOf(3))` = `g(Wide)` after `g(NarrowOf(2))` = `g(WideOf)`).
- **Immutable top-level and field declarations**: the lazily evaluated cell carries the declared type and converts its value the first time it is computed (`LazilyEvaluatedCell.java:66-68`), the type evaluated in the cell's own environment. Anything that fails before a coercion is found leaves the value for the declaration's own check to report. Rejected: converting at the later check and replacing the cell's value, because a reader that forced the cell earlier would keep the unconverted value.
- **Finding `coerce_<T>`** at the top level of the declared type's environment, the functional-method precedent. Rejected: the type's own environment, the first pass's, which misses an object's coercions.
- **An ambiguous coercion** is an error at the call (`OverloadedFunction.java:845-851`; `probes/probes-after.txt:141-142`). The specification refuses such declarations statically, and `walk` has no checker. Rejected: the first candidate in the interpreter's sorted order, which would depend on declaration order.
- **A coercion whose result is not of its type** is an error that names the coercion (`Coercions.java:76-82`; `probes/probes-after.txt:157-161`). Rejected: falling back to the site's original refusal, which names the argument and not the coercion.
- **Assignment to a typed variable or field converts.** The list at `:98-110` reaches it through its last item; a field assignment is a setter call; the compiled checker coerces an assignment's right-hand side (`Operators.scala:449-450`, `:466-467`). Rejected: converting at declarations only.
- **Generic overloads are skipped by the coercion pass** (`OverloadedFunction.java:826`), and inference over a coercible argument is left for row 388. Rejected: inferring with the coercible positions set aside, a larger change to `EvaluatorBase` than the decision covers.

- **Tuple-typed targets** (the judge's scope decision): repaired element by element in `Coercions.coerce`, `coercionFor` unchanged. Rejected: an `XXX` test and a provisional row. Stated limits: varargs, keyword and arrow targets are not converted and not measured.

## 10. The cost

- **The caching holds for overloaded functions only.** `OverloadedFunction` keeps the coercions per argument types in its cache (`OverloadedFunction.java:760-776`) and re-dispatches every converted call. An overloaded method caches nothing, before the rung or after: `OverloadedMethod.mcache` is declared at `OverloadedMethod.java:28`, read at `:48` and `:56`, and written nowhere, so a converting overloaded method call runs `bestMatch` and the coercion pass on every call. The first pass's sentence "An overloaded call pays the cost once per argument types" held for overloaded functions only. The batch record's premise that overloaded methods share the per-argument-type cache through `OverloadedMethod.java:50` (`explorations/coordinator/CLIMB-BATCH-4.md:65`, repeated at `:79`) is wrong for the same reason.
- **A single function's parameter is not cached**: each converting call looks up `coerce_<T>` and dispatches among its declarations; `bestMatchWithoutCoercion` does not use that function's cache, which could hold a `CoercedCall` and would then chain.
- **Pavol's question (5) of 2026-09-24** (`explorations/coordinator/POSITIONS.md:82`): nothing happens in a class loader. The `coerce_` lookup runs only where a check fails, which today happens only on the way to an error; an overloaded function pays it once per argument types. One cost runs whether or not anything converts: every typed immutable top-level variable and every typed immutable field of every object instance evaluates its declared type when first forced (`BuildEnvironments.java:680-683`, `LazilyEvaluatedCell.java:66-68`, `Coercions.coerceToDeclared`, `Coercions.java:124-135`). Measured by the first skeptic, no difference above noise: base 2506, 2809 and 2733 ms against 2908, 2932 and 2572 ms, 400,000 instantiations with three typed fields at one thread (`probes/skeptic/fieldcost.txt`), on nproc 4, Intel(R) Xeon(R) Processor @ 2.80GHz, 2800.212 MHz, JDK 25, `FORTRESS_THREADS=1`, load 0.62 at the start (`probes/skeptic/fieldcost.txt:1`). Nothing was measured on the JIT, and `walk`'s speed is not the measuring stick.
