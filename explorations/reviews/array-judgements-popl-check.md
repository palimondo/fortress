## 0. The paper, in the words needed

- **FGFV**, "Featherweight Generic Fortress with Variance": traits like Java interfaces, objects like final classes, trait type parameters with variance marks and upper bounds, method type parameters with lower and upper bounds, calls that write no static arguments (p. 11:8; extract lines 46-56).
- **Trait parameters' bounds** are checked under an environment binding the parameters themselves ([D-Trait], p. 11:10), so an F-bounded trait parameter is admitted by the rule's form (extract lines 283-285).
- **Method parameters' bounds** may not name a method type parameter: "no reference to a method type parameter appears in any of the upper bounds" (p. 11:11; recheck line 20, quoting). The scope of a method type parameter extends to its right, and the run-time solve works right to left on that account (p. 11:11, p. 11:19; extract lines 196-207). The paper says restriction (1), the scoping, "makes dynamic dispatch more efficient" and restriction (2), the bounds, "makes it consistent" (recheck line 20, quoting).
- **[D-Method]** checks that a covariant or contravariant trait parameter appears only in positions of its variance; "type parameters of objects and invariant type parameters of traits are invariant" (pp. 11:11-12; extract lines 106-110).
- **[Anc-Same-Trait]**: a class extending two instances of one trait extends an instance below both; blanket for an invariant parameter (p. 11:11; extract lines 68-79).
- **The static rules**: a generic declaration is "a single declaration whose domain type is existentially quantified over its type parameters" (p. 11:3); No Duplicates, Meet and Return Type over domains, specificity by subtyping of domains, "sound but not complete", narrowed by existential reduction, which collects the constraints that keep an intersected domain off `Bottom` (pp. 11:12-14; extract lines 136-160). Theorem 4.1: a unique most specific declaration for every call; "No Duplicates makes specificity antisymmetric" (p. 11:15; extract lines 161-164).
- **The run time**: ilks; every call carries its static return type (pp. 11:16-17); [Dispatch] matches the ilks against the domain, matches the static return type against the declared one, and solves by "taking the intersection of the upper bounds", declared and computed, never `Bottom` (pp. 11:17-19; extract lines 186-207). Completeness of matching "assumes that a matched type holds no `Bottom` and no type parameter inside a union or intersection", which every declared type meets (pp. 11:21-22; extract lines 256-260).
- **Left out**: functional methods, closed types, nominal exclusion, modularity, top-level functions (pp. 11:3, 11:25); self types, a numeric tower, coercion, `nat` parameters (extract lines 277-285; recheck line 21).

### 7.1 The rules at the source, claim by claim

- **Figure 5, the No Duplicates Rule (p. 11:13).** Three rules, any one sufficient: [No-Dup-Triv] for different names, [No-Dup-Not-Less], `¬(Δ ⊢ dom(d) ⊑ dom(d'))`, and [No-Dup-Not-Gtr], `¬(Δ ⊢ dom(d') ⊑ dom(d))`. The prose: "if the domain type of one declaration is not a subtype of the domain type of the other, they satisfy the rule ([No-Dup-Not-Less] and [No-Dup-Not-Gtr])" (p. 11:12, lines 609-611). So two declarations are duplicates exactly when their domains are each below the other. *Confirms* § 4's caveat, and *overturns* the extract's compression, "neither domain is below the other" (`ParkPOPL2019-extract.md:150`), which should read "not each below the other"; the extract is not among this check's files, so that is reported, not repaired.
- **Theorem 4.1 (p. 11:15).** "We first show that the more specific relation of method declarations is a partial order. It is clearly reflexive and transitive since the existential subtype relation is reflexive and transitive. ### 7.2 Row 682 settled

**The pair.** `f(x: NatParamT)` beside `f[\nat n\](x: Nt[\n\])`, with `trait NatParamT comprises { Nt[\n\] } where [\nat n\]` and `value object Nt[\nat n\] extends NatParamT` (`ProjectFortress/compiler_tests/XXXNatOpenOverloadChecker.fss`). The domains are `∃∅. NatParamT` and `∃n. Nt[\n\]`.

**In the paper's own calculus the pair is valid, and the generic declaration is strictly more specific.** `∃n. Nt[\n\] ⊑ ∃∅. NatParamT`: open `n` as a constant; `Nt[\n\] <: NatParamT` by its `extends`. `∃∅. NatParamT ⊑ ∃n. Nt[\n\]`: [E-Sub] asks for one `γ` with `NatParamT <: Nt[\γ\]`; no ground size serves, since a trait is below no object instance. So [No-Dup-Not-Less] holds for the plain declaration, [Meet-Less] holds for the generic one, and [Return-Test] holds (`String` on both sides; `Nt[\n\] ⊓ NatParamT` is `Nt[\n\]`). The informal rule says the same: the paper's applicable sets are sets of types, "a generic method declaration d is applicable to a type α if there exists an instance D of d that is applicable to α, that is, the domain type of D is a supertype of α" (p. 11:5, lines 246-248), and the type `NatParamT` is in the plain declaration's set and in no instance of the generic one. That is walk's result and the row's first reading ("none of its instances takes a `NatParamT`, so the generic one is more specific"). So two sentences above are overturned as attribution: § 4's "the paper's No Duplicates rule refuses the pair (Theorem 4.1, p. 11:15)" and "the checker's refusal is the paper's verdict", with "In short" point 4, § 5's "Row 682: changes (§ 4)", § 6's item 3 and the fourth bullet "For Pavol". The paper, having no `comprises`, no `where` clause and no sizes, cannot see that every `NatParamT` is an `Nt[\n\]`, and accepts the pair.

**What makes them duplicates is the revival's opening rule, in the paper's form of the test.** The specification: an argument whose type is a trait whose `comprises` clause lists a type at a `nat` `where`-clause variable, "passed where that listed type is expected with a nat or int parameter in the variable's place, instantiates that parameter, for that call, with the size of the value itself" (`Specification/basic/trait-parameters.tex:106-116`, the revival's `\revision{revival-comprises}`). The checker: a trait that opens sizes is below `t` when its listed type, its sizes fresh names, is (`ProjectFortress/src/com/sun/fortress/scala_src/types/TypeAnalyzer.scala:273-286`), one subtype relation for applicability and for the overloading check alike. That rule reads `NatParamT` as `∃n. Nt[\n\]`. Fed to [E-Sub] it gives `∃∅. NatParamT ⊑ ∃n. Nt[\n\]` with `σ = [n#7/n]`, to the letter; the domains are then each below the other, and the pair is refused by the No Duplicates Rule in the paper's form (Figure 5), in the 2011 paper's ("if d1 ≤ d2 and d2 ≤ d1 then d1 = d2", `Papers/Types/rules.tick:158-161`; "equally specific (i.e., each more specific than the other)", `:184-185`) and in the specification's ("d1 and d2 are not each more specific than the other", `Specification/advanced/overloading.tex:548-549`). The applicable sets agree once the rule is granted: of calls, the specification's measure ("applicable to every call to which d1 is applicable", `overloading.tex:539-541`), each declaration applies to every call the other does; of values, every value of the trait is an `Nt[\k\]`. The 2011 paper adds no second route: its `comprises` clause enters exclusion only (`Papers/Types/exc-spec.tick:96`, `fig-exclusion.tick:117-122`), never subtyping, so its calculus too accepts the pair without the opening.

**How far the analogy carries.** Exactly as far as the opening rule. The paper fixes the form of the test and calls it "a sound approximation of the subset relation of applicable sets" (p. 11:13, lines 673-675); it leaves one question it cannot answer, whether a closed trait at a `where`-bound size is the existential of its listed type in the overloading check's subtyping. The revival has answered that question: the opening is on record and built (POSITIONS, "Arithmetic in a size ...", fork 3 at way 4a; FACTS, "The compiled checker accepts arithmetic in a size and opens a value of a trait whose comprises clause lists a type at a where-clause size"), and one subtype relation serving applicability and specificity is the consistent reading: a rule under which the generic declaration applies to every `NatParamT` argument makes the two declarations applicable to the same calls, which is what the No Duplicates Rule forbids, and at a static call on a `NatParamT` neither would be the unique most specific declaration, Theorem 4.1's failure. Walk's acceptance is its load check, which tests the nominal direction only (`Nt[\n\] <: NatParamT`; walk "checks part of this at load"), and its run is unambiguous because an ilk `Nt[\3\]` is strictly below `NatParamT`, so the generic declaration's instance is strictly more specific at every call. One caveat, by reading and not probed: by types, the plain declaration keeps a call of its own if the checker ever gives an argument the union of two listed instances, `Nt[\1\] ∪ Nt[\2\]`, which no single instance of the generic declaration takes and the opening does not open (a union is not a trait); the paper's types include such unions (Figure 8), and whether the checker's join of two listed instances is that union or `NatParamT` decides whether the plain declaration has any call at all.

**The verdict.** Settled for the checker: its refusal follows from the revival's own rules under a test whose form the 2019 paper, the 2011 paper and the specification share; the paper supplies the form and not the verdict. The test `XXXNatOpenOverloadChecker` stays as the refusal it pins (a refusal at compile time is written as an `XXX` compile test, `tests-writing.md`). The row keeps its number and gets a pointer to this section, its notes cell being at the template's limit. What remains is the curator's: the status word (`RETIRED`, the checker's refusal being no gap, or a re-class to walk's load check), and whether walk's load check should refuse the pair too, which is a walk row if he wants it.

**Found on the way: a wording defect of the specification.** `overloading.tex:539-541` defines "more specific" strictly ("and not the other way round"); under that definition "d1 and d2 are not each more specific than the other" (`:548-549`) refuses nothing, and an equivalent pair falls instead to the chapter's Meet Rule (`:551-553`: not excluding, neither strictly more specific, no third strictly more specific than both), which is why the row's note names the Meet Rule where the papers name No Duplicates. The 2011 paper's relation is non-strict (`rules.tick:184-185`). The chapter's No Duplicates sentence needs the non-strict relation, or the definition needs "as specific as" beside it.
