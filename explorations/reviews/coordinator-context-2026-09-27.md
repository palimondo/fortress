## Method

- **Segment boundary.** Compaction boundaries are system records with `subtype: "compact_boundary"`, immediately followed by a `user` record with `isCompactSummary: true` (text beginning "This session is being continued from a previous conversation"); `compactMetadata` on the boundary record gives `trigger`, `preTokens`, `postTokens`, `cumulativeDroppedTokens` and `durationMs` directly — no estimation needed for those figures. `find_compactions.py` finds all such records (and, as false positives, every `/context` command's own output, which contains the substring "Autocompact"). The segment analysed is transcript lines 32220-34387, from the compaction before the latest to the latest.
- **Context size.** For each `assistant` record, context = `usage.input_tokens + usage.cache_read_input_tokens + usage.cache_creation_input_tokens` — the exact size of what the API call received, cache-hit or not. `analyze_usage.py` walks every assistant record in the segment (709 of them) and reports the sequence, its peak, and the largest consecutive differences.
- **Category attribution is by character count ÷ 4, stated as an estimate, not exact.** `segment_extract.py` re-parses the segment once, pairing each `tool_result` to the `tool_use` that produced it (by `tool_use_id`) so results can be named by tool and, for `Read`/`Bash`, by file path or the harness's own `description` field. `categorize.py` sums those, plus assistant `text`/`thinking` blocks, plus `user`-role text split by `isMeta` (harness-injected) vs. real chat vs. `isCompactSummary` (the boundary artifact, excluded from both). `attach_breakdown.py` and `top_items.py` separately parse the transcript's `attachment`-type records (a distinct top-level record type, not nested in `user`/`assistant` messages) — these turned out to carry real wire-level context deltas (file attachments, added/removed tool and MCP-instruction blocks, the skill listing, per-turn bookkeeping), not mere UI rendering, so they are counted as their own categories rather than folded in or dropped.
- **The categorized total undercounts the measured growth**, and this is stated rather than papered over: summing every category above gives ≈499,000 tokens, against a measured organic growth (from the segment's first call to the pre-drop peak at 08:37) of roughly 685,000-742,000 tokens depending on which start point is used. The gap is consistent with chars÷4 underestimating dense technical/tabular text, and with a few harness-bookkeeping attachment types (`prompt_snapshot`, `deferred_tools_record`) being measured here by their JSON debug serialization, which may not equal their true wire size. The restart's 753,017-token cache rewrite is a re-transmission of content already counted once as it was first added, so it is reported only in the context-size section, not added again into the category totals.
- **What was not, and could not be, checked**: the `subagents/` folder under this transcript's directory holds many agent transcripts, but none of the tool calls in this segment's window (`Agent`, `TaskCreate`, `TaskUpdate`) reference a subagent whose own transcript would add anything beyond what its result already shows in the coordinator's own transcript; they were not opened. `/home/user/fortress-overflow` and `/home/user/fortress-triage` (the two worktrees named in the restart notice) were not touched, per instruction; the one out-of-repo `Read` found (a `fortress-positions` worktree copy of `POSITIONS.md`) was only counted, not opened further.
