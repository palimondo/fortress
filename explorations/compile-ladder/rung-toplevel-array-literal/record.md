# Rung B, rung-toplevel-array-literal: record lines

## Finding

Under walk a top-level variable declared with an array type and bound to an array literal is the array that the same declaration gives in a block. It holds for an immutable and a `var` variable whose declared type is the library's array trait of the literal's rank (`T[n]`, `T[n,m]`, `T[n,m,k]`, `Array1` to `Array3`, `Vector[\T,n\]`, `Matrix[\T,n,m\]`), for elements that are numerals, top-level names, expressions, strings and pasted arrays; a numeral element converts to the element type (`RR64[3] = [1 2 0.5]`, `NN32[2] = [1 2]`). An initializer above the variable reads the array. A field of a singleton or of a constructed object, declared so, is the array too (`ProjectFortress/tests/ObjectFieldArrayLiteral.fss`). A literal whose size is not the declared type's is refused at load, 'Type mismatch binding __DefaultVector[\ZZ32,3\] ... to shp (type Array1[\ZZ32,0,4\])', and an element that the array refuses is reported, 'Unification error: ... got arg "a" of type String'.

## FACTS entry

**Under walk a top-level array literal with a declared type is built into the library array of that type, in the variable's cell.** `LazilyEvaluatedCell.getValueNull` builds an immutable variable's literal when the cell is first forced, so a reader above the declaration, an importer and `forVarDecl4`'s type check all see the array; `BuildEnvironments.forVarDecl4` builds a `var` variable's. Both call `LHSEvaluator.topLevelArray`, which runs the block's code, `libraryArray`. The declared size is checked only at the top level, by `forVarDecl4`; a block binds a literal of another size (row NEW-B-1). A field declaration of an object takes the same code. An untyped top-level literal stays a paste (row 49). Tests: `ProjectFortress/tests/ObjectFieldArrayLiteral.fss`, `ProjectFortress/tests/TopLevelArrayLiteral.fss`, `TopLevelArrayLiteralSize.fss`, `TopLevelArrayLiteralElement.fss`. Detail: `explorations/compile-ladder/rung-toplevel-array-literal/REPORT.md`, "What changed and why".

## Revival change

**The change.** The team's walk bound a top-level variable declared with an array type to the literal's paste, a tuple, and stopped: `shp: ZZ32[3] = [27 16 27]` gave 'Type mismatch binding (27,16,27): (ZZ32,ZZ32,ZZ32) (type (ZZ32,ZZ32,ZZ32)) to shp (type Array1[\ZZ32,0,3\])'; only a declaration in a block built the array (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/LHSEvaluator.java:170-207`, the block's binding; `ProjectFortress/src/com/sun/fortress/interpreter/evaluator/BuildEnvironments.java:788-803`, the top-level check, which built nothing). The tree now builds a top-level literal with a declared array type into the library array of that type, for an immutable and a `var` variable, with numerals, names, expressions, strings or pasted arrays as elements, and a field of an object declared so (`ProjectFortress/tests/ObjectFieldArrayLiteral.fss`); a reader above the declaration sees the array; a literal of another size than its declared type, or with an element that is not of the element type, is refused at load. Test: `ProjectFortress/tests/TopLevelArrayLiteral.fss`, with `TopLevelArrayLiteralSize` and `TopLevelArrayLiteralElement` for the refusals. The reason: the specification gives an array expression one type wherever it stands, `Arrayk[\T, 0, n0, ...\]` (`Specification/basic/expressions/aggregate.tex`, "Array Expressions"), and a top-level declaration `id : Type = expr` the same meaning as a local one (`Specification/basic/variables.tex`, "Top-Level Variable Declarations"). Still so: a top-level literal without a declared type is bound as its paste and fails at its first use; write the type. A literal in a block of another size than its declared type is not refused; a `var` bound to a literal in a block is immutable; a literal assigned to a variable is not built.
