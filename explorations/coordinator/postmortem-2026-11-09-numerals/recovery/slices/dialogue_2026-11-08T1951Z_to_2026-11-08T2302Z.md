### L4309 · 2026-11-08T20:03:22Z · coordinator
``````
Your idea is the compiler prelude's design under other names, and the names turn out to carry the one thing that matters.

**What `IntLiteral` and `FloatLiteral` are.** An `IntLiteral` is an exact integer and a `FloatLiteral` is an exact rational: the same values as `ZZ` and `QQ`. The team gave them separate types for one reason: a numeral may convert narrower, and a `ZZ` or `QQ` value may not. Your rule of September, P-74: a conversion that keeps the value is implicit; one that can lose it is written out. So `z: ZZ32 = x` for a `ZZ` variable `x` needs `x.asZZ32`, and `r: RR64 = q` for a `QQ` needs `asFloat(q)`. But `z: ZZ32 = 3` and `r: RR64 = 0.1` must just work, with one rounding, because the programmer wrote the digits. The type `IntLiteral` says "this exact integer came from the source, so narrowing it is the programmer's intent". That is all it adds to `ZZ`.

**What happens if numerals are plain `ZZ` and `QQ`, as the restart says:**
- Either `ZZ` and `QQ` get implicit narrowing conversions into `ZZ32`, `ZZ64`, `RR64` and `RR32`, for every value, not only literals. Then `r: RR64 = q` silently rounds any rational, and `z: ZZ32 = x` silently raises on a big `ZZ`. That breaks P-74 everywhere.
- Or they don't, and `z: ZZ32 = 3` is refused until you write `3.asZZ32`.
- Or the checker remembers that a `ZZ` value came from a numeral and allows narrowing for those only. That is a literal type again, under no name.
- Run time is reading A's: `x = 3; x + 1` is arbitrary-precision arithmetic, `<|1, 2, 3|>` is a list of `ZZ`, and `3 SEQV z` is false, since `ZZ` and `ZZ32` are two types. And a rational leaks into computation: microGPT's `beta1 = 0.9` then `beta1^t` is exact rational arithmetic with a denominator that grows with `t`, where under A the tie rule makes it an `RR64`.

**So the fork is still A or B.** Your picture, full precision from the source and conversion at the place of use, is reading A: the numeral keeps its exact value until a type is fixed, and the literal type is what licenses the narrowing. The fold at typed places gives A the speed of constants where the type is known. Reading B keeps the same exactness at every typed place, and gives up only the untyped places: `x = 3` becomes a `ZZ32`, `y = 0.1` a `double`, and in exchange `3 SEQV z` is true, no literal value exists at run time, and the 24 glue bindings go.

If exactness until the place of use is the thing you want most, that argues for A. If you want the peers' behaviour and the simpler run time, B. The prototype tells us B's price in the checker; A's price is known.
``````

``````
**Reading a numeral in a base.** Each digit position is a power of the base. Before the point the powers go up from the base to the power 0; after the point they go down: 1 over the base, 1 over the base squared, and so on. The base is 10 unless `_r` says otherwise.
``````

``````
Here it is, step by step, with the terms first.

**Terms**
- **Numeral**: the digits written in the program, such as `3.14159` or `C.8_16`.
- **Compile time**: when the compiler reads the program and writes the class files.
- **Load time**: when the JVM loads a class file, once, before the program's code in it runs.
- **Run time**: when the JVM executes the program's code, each time the code is reached.
- **Coercion**: a conversion that the compiler inserts where a value of one type is used where another type is declared. Its body is library or program code.
- **Constant folding**: the compiler computes an expression at compile time and writes the result into the class file in place of the expression.

**What constant folding needs**
1. Every operand of the expression is a constant.
2. The compiler has the rule of the operation inside itself. It does not need to run any code of the program to get the result.
3. The result is a value that a class file can hold as a constant. A JVM class file holds five kinds: `int`, `long`, `float`, `double` and `String`.

**Cases that meet all three**
- `3 + 4`: the operands are numerals, the compiler knows `+` on integers, the result 7 is an `int`.
- `r: RR64 = 3.14159`: the operand is a numeral, the compiler knows how to round a rational to the nearest double, the result is a `double`.
- `q: QQ = 1/2`: the compiler knows rational arithmetic; the result is two integers, 1 and 2, which the class file holds.
- The prototype did these. This is the constant folding the Draft describes for "static expressions".

**The case that does not meet them**: `iv: Interval = 3.14159`, where `Interval` is a type that the program declares with its own `coerce`.
1. The operand is a constant. Met.
2. The operation is the body of the program's `coerce`. The compiler has no rule for it. The body is Fortress code: it can call functions, make objects, loop. To fold it, the compiler would have to execute Fortress code while compiling. No Fortress compiler can do that, the team's or ours. The only program that executes Fortress is walk. Not met.
3. The result is an `Interval` object. A class file cannot hold an object as a constant. Not met.

**What the Draft says.** It promises compile-time computation for static expressions: the quotient of two integer numerals, and a numeral with an exponent, converted to a float with one rounding (`literals.tex:166-173`).
``````
