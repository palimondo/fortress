## 2. Finding 1: rows 356 and 369, home 2 owed and not given

### What the specification settles, and how

**Row 356.** `Specification/basic/traits.tex:525-531`, read at `:512-545`: an overriding declaration "overrides any inherited declaration with the same name and the self parameter (if any) at the same position, whose parameter type ... is a strict subtype of the overriding declaration's parameter type. The measured consequence is the skeptic's `ProgramError` on the typed binding (`explorations/compile-ladder/rung-library-defects/probes/skeptic/SkepticLsplit-walk-post.txt:4-5`). The specification settles it against the library, as the row says.

**Row 369.** `Specification/basic-lib/objects.tex:161-188`, read at `:150-195`: a tuple's `toString` concatenates `(`, each element's `toString`, and after every element but the last `", "`, then `)`. Walk prints `(1,a)` (`explorations/compile-ladder/rung-default-rendering/probes/skeptic/skeptic2-differentials.txt:54-56`), because `FTupleLike.getString` appends `','` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/FTupleLike.java:52-64`, the `','` at `:60`), reached from `println(a:Any) = println("" a)` (`Library/FortressLibrary.fss:4145`, whose comment says the concatenation form "also works for tuples"). ## 3. Finding 2: L's `Condition.map` edit, ungated after P's stop

### What the specification settles, and how

`Library/FortressLibrary.fsi:761-763`: `trait SequentialGenerator[\E\] extends { Generator[\E\] }` declares `map[\G\](f: E->G): SequentialGenerator[\G\]`. `:771`: `trait Condition[\E\] extends SequentialGenerator[\E\]`. So `Condition.map` at `:790` overrides `SequentialGenerator.map`, and by `traits.tex:525-531` (section 2) its return type must be a subtype of `SequentialGenerator[\G\]`. The base line, `Generator[\G\]`, is the supertype of `SequentialGenerator[\G\]` (`:761`), so the base api was a static error under the specification; the landed line, `Condition[\G\]`, is a subtype (`:771`). The component already says `Condition[\G\]` (`Library/FortressLibrary.fss:1228`), and so does the compiler prelude (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:663`, `abstract map[\G12 extends Any\](f: E18->G12): Condition[\G12\]`). The edit is right on its own grounds, with or without rung P. The batch's stop for "a change to a declared type the prelude already has" is not triggered: the edit brings the api to the type the prelude already has.

### Why no gate on this tree can hold it

The checker reports the base line's error only when `checkP` is relaxed: the two `For map` errors at `FortressLibrary.fsi:762` and `:789` (base numbering) appear in `base-P` and are 0 in `mine-P`, (`explorations/compile-ladder/rung-library-defects/probes/differentials.txt:197-200`), and the batch record says the same of the unrelaxed checker: "absent from the 93 and present in every relaxation capture" (`CLIMB-BATCH-3.md:96`), so the count stage, L's own gate, reads 103 with or without the edit. Walk checks no api return type against its component (rule 4 of the shared prefix; L's thirteen controls unchanged, `record.md`, "What the rung did"). `compiler_tests/` cannot reach `Library/`, which the compiled path does not load. So on the merged tree there is no assertion, no `XXX` file and no stage line that changes with this edit. That is the same situation the batch record foresaw when it declared the rule-2 exception (`CLIMB-BATCH-3.md:156`: "L's fifth fix ... is only observable after P's relaxation, so its pre-edit evidence is the trace's captures and its verification is the merged tree"), with the verification deferred by P's stop rather than lost: whatever relaxation lands from P's fork, the count stage becomes this edit's gate on that tree, because reverting the edit there brings the two `For map` errors back (`differentials.txt:197-200`).

### The ruling

**Keep the edit; record it as ungated, with the reason and the gate to come.** The alternative, holding it back with P, was considered and rejected: it would re-introduce into the api a return type the specification calls a static error and the component contradicts, for procedural symmetry only; no test on this tree would read differently either way; and the edit is the fourth of L's five declared fixes (`CLIMB-BATCH-3.md:96`), whose evidence was committed and reproduced (`differentials.txt`, "mine-P against rec-P" and the `For map` block). What the record must now say, and does not: L's FACTS line accounts for 29 removed errors and never mentions the fifth fix; L's `record.md` presents it beside the four gated ones; `RECORD.md`'s L section does not name the exception as unmet. The repair adds that sentence in each place, and the coordinator puts it to Pavol beside P's fork, since the fork's outcome is what gates it.

This is a decision under the batch's rules, not under a silent specification: the specification speaks (section 3.1); what it does not speak to is the batch's gating discipline, and that is decided here and reported.
