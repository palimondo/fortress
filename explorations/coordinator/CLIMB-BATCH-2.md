# Climb batch 2

## The batch in one page

**What it is for.** Three small additions to the compiler's library, run through the batch machinery that ran batch 1, while the array design is written beside it as its own job. The array design is the real path to microGPT; this batch is what can be done without waiting for it, and it must not get in its way.

**The three rungs, one sentence each.**

- **X, `rung-export-var`.** A variable declared at the top level of a component and exported through an api compiles but crashes at run time (`NoClassDefFoundError`, ledger row 320; the failing program is the three-file probe `compile-ladder/repair-r1-atomic-static/probes/P8Api.fsi` + `P8Lib.fss` + `P8Main.fss`). Both microGPT programs export `corpus` exactly this way (`apl/mg/MicroGptApl.fsi:18`, `run-c4/src/MicroGptFlat.fsi:16`), so they will hit it the day arrays exist. This is the batch's one Java rung.
- **W, `rung-int-conversions`.** The four conversions between the fixed-size integer types, `widen`, `narrow`, `unsigned`, `signed`, do not exist in the compiler world; `ProjectFortress/tests/fib13.fss:30` stops on `unsigned(20)`. Library only.
- **B, `rung-tryatomic`.** The exception `TryAtomicFailure` is written in the compiler library and commented out; `tests/tryatomicTest.fss`, `nestedTransactions3.fss` and `abortTest.fss` stop on the name and nothing else. One uncomment and one api line.

**What it does not do.** microGPT does not move one phase: all eighteen of its components stop at disambiguate on `Array`, `Char`, `Vector` or `ImmutableArray` (`compile-ladder/baseline-2026-09-19/microgpt-phase.md`), and nothing in this batch declares an array; the wall is arrays. The ladder's pass count is expected to stay at 85: X moves no ladder file (no file in `ProjectFortress/tests/` has an api), W moves one file up one phase, B moves three files up one or two phases, and none of the four reaches `pass`. What the batch buys is X on the path and two library gaps closed at the lowest cost on record. If that is too little to spend a gate on, the alternative is to skip the batch and wait for the array sketch; that is Pavol's call, not the coordinator's.

**What the coordinator decided by default (`batch-2-open-decisions.md` A1-A7, each at its default), and Pavol may overrule at landing.**

What it changes: which defect gets repaired in Java this batch. Why: microGPT exports a variable; no program on the path writes `|0|`.
2. **A2, row 333** waits for a later batch's Java slot. What it changes: nothing on the path; the row stays open one batch longer. Why: it is a `.java` fix in six native methods, and folding Fortress guards into W would mix a repair into a feature rung on the same trait bodies.
3. **A3, the other two slots** go to the four integer conversions (W) and `TryAtomicFailure` (B); `printThreadInfo` stays out. What it changes: the batch's content. Why: W is the largest fork-free name set left, B is the cheapest rung on record, and `printThreadInfo` is Java and diagnostics only.
4. **A4, `Char`** stays out. What it changes: nothing now. Why: the five microGPT files that stop on `Char` contain no `Char` of their own; the name arrives through an imported interpreter api, so renaming `Character` moves no component (FACTS, ladder section).
5. **A5, the forks:** nothing behind them is touched, no array type, no `ImmutableArray`, no `Range` parameter, no shadowing rule. What it changes: the array sketch and the `nat`-checking prototype run beside the batch as their own worker sessions. Why: the path runs through the forks, not through this batch.
6. **A6, size:** three rungs, not four. What it changes: the one gate is amortised over three rungs; the run is about one worker-plus-skeptic pair shorter. Why: no fourth fork-free rung exists that does not edit a trait W edits.
7. **A7, the open questions** ride inside the rungs and Pavol sees each answer at landing. X: where the fix lives, and that it has two parts (the class name and the field descriptor). W: what `narrow` does when the value does not fit; this record recommends throwing `IntegerOverflow`, as the compiler world's own `asZZ32` does. B: none.

## The three rungs

### X. A top-level variable exported through an api links (ledger row 320)

**The program.** `probes/P8Api.fsi` declares `var shared: ZZ32`, `P8Lib.fss` exports it with `var shared: ZZ32 = 7`, `P8Main.fss` imports the api and prints it; `fortress compile` accepts all three and the run dies with `NoClassDefFoundError: P8Api$shared` from `Resource not found : P8Api$shared.class` (`compile-ladder/repair-r1-atomic-static/REPORT.md:159`, capture in `probes/probe-runs-preedit.txt`); `P9*` is the immutable control and fails the same way. When the api and the declaring component share a name, as every prelude pair does, the class exists and the run dies one step later on the field: `NoSuchFieldError: Class fortress.CompilerLibrary$__globalTimeInformation does not have member field 'FRR64 ONLY'` (`compile-ladder/rung-timing/probes/export-variable-3.txt`, from `ReadStoredTime.fss`). The two microGPT apis export `corpus: Corpus` (`explorations/apl/mg/MicroGptApl.fsi:18`, `explorations/run-c4/src/MicroGptFlat.fsi:16`).

**The specification.** `Specification/basic/components/source-code.tex:332-343`: "A top-level variable declaration declaring a single variable is satisfied by any top-level variable declaration that declares the name with the same type ... In either case, the modifiers including the mutability of a variable must be the same in the exported and satisfying declarations." `basic/components/initialization.tex:26-30`: "If a simple component has imports, take the transitive closure of all imported apis. Collect all declarations in this transitive closure, in any order, and prepend them to the component definition." So an exported variable is one declaration, the api's, satisfied by the component's; the specification has no view on class names. There is no deviation to argue: the compiled path fails to do what both passages take for granted. The mutability clause is already enforced: the checker refuses `x: T := e` against `var x: T` "due to different mutabilities" (`rung-timing/probes/export-variable.txt`, `-2.txt`), and `var x: T` in the api with `var x: T = e` in the component is the one spelling both sides accept.

**The mechanism, read in the tree (row 320's notes, re-read 2026-09-19).** Reading side: `CodeGen.forVarRef`'s fresh-import path, `ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:5953-5971`, builds the class name with `NamingCzar.jvmClassForToplevelDecl(id, packageAndClassName)` at `:5967`; that helper (`compiler/NamingCzar.java:1653-1656`) first replaces its api argument by `repairedApiName` (`:1673-1679`), which substitutes the package-and-class of the api the identifier carries, so the class asked for is the api's, `P8Api$shared`. Writing side: `forVarDeclPrePass:5924` emits the singleton class under the declaring component's name, `P8Lib$shared`. Nobody emits the api-named class, and when the names coincide the class exists but its field has the wrong descriptor, because `generateVarDeclInnerClass:5872-5881` gives a mutable variable's field R1's `MutableFValue` cell and the fresh-import path always builds a plain `VarCodeGen.StaticBinding` with the declared type's descriptor (`:5966-5970`), unlike `addTopLevelVarBinding:5934-5951`, whose `:5945-5950` branch checks mutability. A fix of the class name alone moves the failure from `NoClassDefFoundError` to `NoSuchFieldError`.

**The precedent.** The interpreter is no precedent for a class name: it binds imported declarations by environment (`BuildApiEnvironment.java`, map row `map/spec-to-implementation.md:153`), and its own library exports no top-level variable (`Library/FortressLibrary.fsi` declares none; its two mutable top-level variables at `.fss:4111` and `:4355` are private). The precedent is the compiled path's own handling of exported *functions*, which do link across differing names: `CodeGen.java:409-445` collects every exported function name "so that unambiguous names from APIs can also be emitted" and says of itself "it looks like this information is currently unused"; `:6577-6582` is a `????` comment where a forwarding wrapper was meant to go; `forFnRef:3556` is where an imported function reference gets its class; and `ProjectFortress/src/com/sun/fortress/linker/Linker.java:56-79`, `whoIsImplementingMyAPI(component, api)`, is the team's own answer to "which component implements this api for this component", falling back to the api's own name at `:72-76`, which is exactly why the prelude pairs work. The rung's precedent search is to find how a function reference crosses the api-to-component gap and whether a variable can cross the same way; the three callers of `jvmClassForToplevelDecl` (`CodeGen.java:5924`, `:5942`, `:5967`) are the whole site count.

**The test, first.** `ProjectFortress/compiler_tests/ExportVarRungXApi.fsi` (`var shared: ZZ32` and an immutable `fixed: ZZ32`), `ExportVarRungXLib.fss` (exports the api, defines both), `ExportVarRungX.fss` (imports the api, reads both, assigns `shared`, reads it back, prints PASS) and `ExportVarRungX.test` in the form of `compiler_tests/AtomicTopLevelVar.test`: `tests=ExportVarRungX`, `link`, `run`, `run_out_contains=PASS`, `run_out_does_not_contain=FAIL`. The harness finds an imported api and its component beside the test by name, as `RecursiveApiTest3.test` (`tests= RecursiveApiTest3c`) relies on with `RecursiveApiTest3a.fsi`/`.fss` and `3b` beside it. The failure to capture before the edit is the `NoClassDefFoundError`.

**The decision the rung carries.** None against the specification. The engineering decision is where the fix lives: the reader (name the class after the implementing component, which the linker can answer), the writer (emit the singleton under every exported api's name as well), or the link step; whichever it is, both parts must land, the class name and the descriptor by mutability, or the failure only changes its exception. The rung argues the choice from the function precedent and records it. It must not change any prelude declaration, must not touch the `atomic` rows 319, 322 and 324, and must not make `CompilerLibrary` export `__globalTimeInformation`.

**What it clears on the ladder.** Nothing: `ProjectFortress/tests/` holds no `.fsi` at all and the four `.fsi` of `not_working_library_tests/` declare no variable (2026-09-19), so `expectedMoves` is empty and the ladder subset step is replaced by the P8/P9 pair before and after. `writesState` is true: the mutable case reads and writes R1's transactional cell from a second component, so every differential runs at one thread and at four.

### W. `widen`, `narrow`, `unsigned`, `signed` on `ZZ32`, `ZZ64`, `NN32`, `NN64`

**The program.** `tests/fib13.fss:30-33` (`fib13[\NN32\](unsigned(20))`), `longPrim.fss:23-30` (`widen(124867)`), `UnsignedTest.fss:17-23` (`unsigned(0)` ... ), `NumberPrintTest.fss:52-58` (`widen`, `unsigned`, `narrow`). The compiler prelude has none of the four names (grep of `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi`, 2026-09-19) but has every ingredient: `ZZ64.asZZ32` (`.fsi:150`, body `.fss:575` `jLongOverflowingToInt(self)`), `ZZ64.coerce(x: ZZ32)` (`.fsi:148`, `.fss:574` `jIntToLong(x)`), `NN64.coerce(x: NN32)` (`.fsi:326`, `.fss:809`), and the bit reinterpretations `ZZ64.bitsAsNN64` (`.fsi:152`, `.fss:577`), `ZZ32.bitsAsNN32` (`.fsi:212`, `.fss:660`), `NN32.bitsAsZZ32` (`.fsi:273`, `.fss:748`), `NN64.bitsAsZZ64` (`.fsi:331`, `.fss:812`); `jLongOverflowingToUnsignedInt` is bound at `.fss:85`. So each of the four is one declaration and one one-line body per trait, library only.

**The specification.** Silent on the four names: a grep of every prose chapter for `widen`, `narrow`, `unsigned`, `signed` finds only the `widens` coercion keyword (`basic/conversions-coercions.tex:762-835`, the automatic widening of numeric literals, a different mechanism), the fixed-size types named in prose (`basic/types-vals-vars.tex:512-513`) and "unsigned binary form" in the description of `integerLength` (`basic-lib/basic-integers.tex:802`). What it does say about a result that does not fit: `basic/operators/opr-overview.tex:172-176`, the wrapping and saturating forms "do not overflow", which implies the ordinary forms may; `basic-integers.tex:368-370`, on ZZ the wrapping and saturating forms "do exactly the same thing, because operations on type ZZ never need to wrap or saturate". Row 333's note reads the same passages the same way: the plain form throws `IntegerOverflow` when the true result is unrepresentable, and wrapping is a separately spelled operation.

**The precedent.** Declarations: `Library/FortressLibrary.fsi:490-492` (`ZZ32`: `widen(self):ZZ64`, `unsigned(self):NN32`), `:431` (`unsigned(self):NN64` in `trait Integral[\I\]`, the api's spelling of what `ZZ64`'s body binds at `.fss:764`), `:529` (`ZZ64`: `narrow(self):ZZ32`), `:457-458` (`NN64`: `narrow(self):NN32`, `signed(self):NN64`, a return type the interpreter never checks), `ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:105-107` (`NN32`: `widen(self):NN64`, `signed(self):ZZ32`). Bodies: `FortressLibrary.fss:692-697`, `:762-765`, `:816-819`, `FortressBuiltin.fss:442-447`, each a `builtinPrimitive` glue class. The glue is where the answer to the open question lives: `Int.java:221-223` `ToLong` is `(long) x`; `NN32.java:237-240` `ToUnsignedLong` is `Unsigned.toLong(x)` (zero-extension); `ZZ32.java:213-216`, `NN32.java:231-234`, `Long.java:231-234`, `UnsignedLong.java:224-227` return the bits unchanged (`unsigned`, `signed`); `Long.java:237-240` `FromLong` is `Int.rc(x)`, and `Int.rc` (`:239-245`) raises `error("Overflow of ZZ32 " + i)` when the value does not fit; `UnsignedLong.java:230-233` `FromLong` is `(int) x`, a silent truncation. So the interpreter checks `narrow` on the signed side and truncates on the unsigned side, two answers in one library, and neither is a catchable Fortress exception.

**The decision the rung carries.** What `narrow` does out of range. This record's recommendation, for the rung to argue and Pavol to overrule: throw `IntegerOverflow` (`CompilerBuiltin.fsi:741`) on both sides, which is what the compiler world's `asZZ32` already does through `simpleIntArith.longOverflowingToInt:94-98`, what the interpreter's `Int.rc` does on the signed side, and the specification's pattern for an unrepresentable result; the unsigned side then deviates from the interpreter's `(int) x`, and the deviation is recorded. The out-of-range cases go in the test both ways, in the `shouldOverflow` shape of `library_tests/Integer3.fss:17,93`. `widen` is sign-extension from `ZZ32` and zero-extension from `NN32`; `unsigned` and `signed` reinterpret the bits, so `unsigned(-1)` is 4294967295 and `signed` of it is -1 again.

**The test, first.** `ProjectFortress/library_tests/IntConversionsRungW.fss` + `.test` (`tests=IntConversionsRungW`, `link`, `run`, `run_out_contains=PASS`, the form of `IntegralOpsRungN.test`): every direction on every type, `widen` of a negative `ZZ32` and of a large `NN32`, `narrow` in range both ways and out of range both ways, `unsigned`/`signed` round trips at -1 and at the type minimum, and the two identities of `NumberPrintTest.fss:54-55`, `unsigned(widen(43))` and `widen(unsigned(43))`, printed. Out of scope, by name: `partitionL` (`FortressLibrary.fsi:491`), `partition` (`:1382`), `big`, `RR64.narrow(): RR32` (`.fsi:362`), and anything in `trait RR64`, `IntLiteral` or the tower.

**What it clears on the ladder.** `tests/fib13.fss` alone (`baseline-2026-09-19/ladder.tsv:251`, missing name `unsigned`), to typecheck or better. Corrected from `candidates.md:137,141`, which were written before rung N landed: `longPrim` loses `widen` and stays on an operator the ladder prints as `?` (`ladder.tsv:288`); `UnsignedTest` loses four names and stays on `partitionL` (`:133`); `NumberPrintTest` stays on `big` (`:83`); `intPrim` and `simpleSum` name none of the four (`:283`, `:366`); `naiveSeq` stops on `partition`, a different function (`:296`). `writesState` false.

### B. `TryAtomicFailure` in the compiler library

**The program.** `tests/abortTest.fss:26`, `nestedTransactions3.fss:27` and `tryatomicTest.fss:23` each catch `TryAtomicFailure` around a `tryatomic` block and stop at disambiguate on that name alone (`ladder.tsv:193`, `:307`, `:392`).

**The specification.** `Specification/basic/expressions/atomic.tex:45-48`: "A tryatomic expression consists of tryatomic followed by an expression. It acts exactly like atomic except that in certain circumstances (see transactions) it throws TryAtomicFailure and discards the effects of its body." `advanced/parallelism-locality/transactions.tex:34-38`: "if it aborts due to a call to abort or due to conflict ..., the checked exception TryAtomicFailure is thrown." `basic/exceptions.tex:67-80`: `Exception comprises { CheckedException, UncheckedException }`, and a functional that may throw a checked exception lists it in its header. So the object is a checked exception with no fields.

**The precedent.** The interpreter: `Library/FortressLibrary.fsi:1047` `object TryAtomicFailure extends CheckedException`, body `.fss:1566-1568` with `getter asString(): String = "Try/atomic failure"`. The compiler world: the identical three lines at `Library/CompilerLibrary.fss:283-285`, inside the block comment `:253-291` that holds nine checked-exception objects (`map/dormant-code.md:32` lists them at the stale lines 220-258; re-anchor by symbol); `trait CheckedException extends Exception excludes UncheckedException` is live at `CompilerBuiltin.fsi:745` and `IOException extends CheckedException` at `:748` is a checked exception already in use. The api `Library/CompilerLibrary.fsi:66-103` lists the unchecked exception objects and no checked one.

**The edit and the test, first.** Move the three lines out of the comment (close it before them and reopen after, or move them below `:291`); do not uncomment the other eight, and in particular not `MatchFailure extends CheckedException` at `:258`, which would collide with the unchecked `MatchFailure` at `:243`. Add `object TryAtomicFailure extends CheckedException end` to `CompilerLibrary.fsi` after `CastException` at `:103`. Test: `ProjectFortress/library_tests/TryAtomicRungB.fss` + `.test` (`tests=TryAtomicRungB`, `link`, `run`, `run_out_contains=PASS`): a function that throws `TryAtomicFailure`, a `try ... catch e TryAtomicFailure => ...` that catches it (the shape of `library_tests/Integer3.fss:17` and `FailInference1.fss:21`), its `asString` compared to "Try/atomic failure", and PASS. Do not write a `tryatomic` expression in the gated test: it would stop at codegen.

**What it clears on the ladder.** The three files leave disambiguate and will not pass: `tryatomic` parses to `TryAtomicExpr` (`ProjectFortress/astgen/Fortress.ast:678`), the checker types it (`scala_src/typechecker/impls/Misc.scala:455-457`), and `CodeGen.java` has no visitor for it (grep, 2026-09-19), so `tryatomicTest` and `nestedTransactions3` are expected at codegen; `abortTest` also calls `abort()` and `printThreadInfo`, which the compiler world lacks, so typecheck. `expectedMoves` declares typecheck or better for all three, the floor the gate checks. Implementing `tryatomic`, `abort` or `printThreadInfo` is out of scope (Java, and X holds the slot). `writesState` false; the rung has no decision to carry.

## How it is run
