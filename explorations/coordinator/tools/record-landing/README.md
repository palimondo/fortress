# The record-landing workflow

`record-landing.js` does the record's work after a landing, which the coordinator did by hand through a record writer and a routing worker until climb batch 24. It is the smallest first version of the design `explorations/coordinator/process-engineering/record-landing-workflow.md` (`5384a4f35`), which the curator approved with its eight defaults on 2026-11-02. It runs in six stages for the record, in the pattern of the orientation workflow (`../orientation/orientation.js`), five more for the skill after the orientation update ("The skill update"), and one for the revival page ("The revival page"):

1. **Sort** (Opus, `sort.md`): `prepare.sh` makes the worktree and its branch and writes the evidence into the run's folder (`evidence.py`'s header lists its six files; `plan.md` ends with the PLAN lines that look stale, from `plan-moves.py --stale-at`, cut at 40,000 characters, past which the whole list is in `plan-stale.txt`, which the cut line names); the sorter reads it, the review's routing part and the batch record's items, and writes `owed.md`, one line per change with its number, its home, its kind, its weight, its ground and its writer, and marks each kind and each "Needed by" that no source states as set by the workflow.
2. **Write**: a Sonnet driver runs `drive.sh 1` in the background and waits for it in steps of 240 s, under the five minutes that its prompt cache lives. `drive.sh` starts two headless Opus writer streams side by side through the worktree's copy of `../record-clarity/writer-stream.sh`: the entries writer (`entries.md`: FACTS, POSITIONS, an entry's history, ledger rows, as `record.apply` and `rows.rewrite`) and the routing writer (`routing.md`: PLAN, PLAN-history, the queue, INDEX, other notes, edited in the worktree). Then `checks.sh 1` writes `mech-1.md`.
3. **Check**: the checker (`check.md`: coverage, fidelity, form and routing) and the clarity cold reader (`../record-clarity/coldread.md`, unchanged, told to write its report in parts of five entries) on `clean.txt`, side by side.
4. **Fix**: `drive.sh 2` resumes both streams once with the three reports, then `checks.sh 2` writes `mech-2.md`.
5. **Judge** (Opus, `judge.md`): apply or hold each change once, `final.apply` and `final.rewrite`, `diff.md` (within 10,000 characters), and `final.sh`, which runs every check again and makes two commits on the branch. The judge writes nothing after the commits.
6. **Land** (Sonnet, in the script): only when the judge's checks pass (the branch holds its commits past AT, `mech-final.md` says every check passes, the worktree is clean), the lander puts the two commits on `main`, runs the checks on `main`, pushes, and removes the worktree and the branch; then the script runs the orientation workflow in update mode as a child workflow (`../orientation/orientation.js`, one level deep), on the entries in the orientation call of `diff.md`'s "Next". "Landing its result" gives each step.
7. **Skills** (a Sonnet driver; the skill writer, a headless Opus session): `skills.sh N 1` writes the writer's task from `skill-task.md` and the landed files, and starts a fresh writer on it through `../skill-writer.sh new`; the writer installs what the orientation judge accepts and brings the `fortress-repo` skill in line with the landing, and commits on `main`.
8. **Cold read** (Opus): the changed parts, by `../../skill-cold-read-brief.md`, as a worker new to the repository.
9. **Fixes**: `skills.sh N 2` resumes the same writer on the cold read's flags (`skill-fixes.md`).
10. **Page** (Opus, `page.md`): the page of `fortress-repo`'s landed changes, by the source and the URL that the boot note names, published by that URL.
11. **Push** (Sonnet, in the script): `folders.sh N` commits the run's folders, then the pushes as the Land stage's; the result's `line` is the one line for the coordinator's chat message.
12. **Revival page** (Sonnet, in the script; then a Sonnet publisher, `revival-publish.md`): `../revival-page/update.py --landing N --run-start base` in the main tree, the files that it names committed by named paths and pushed as the Push stage's; then the page published by its URL with the Artifact tool. The result's `line` gains the page's commit and version.

The mechanical checks (`checks.sh`): the six record files reset to the worktree's base, the cut-only POSITIONS lines checked with `../record-clarity/words-subset.py --root`, the writers' files applied with `record.py apply`, `../ledger-clarity/apply.py` and `ledger.py add` (the new rows of `rows.add`, or at the final round the judge's `final.add` where it wrote one), each history block "by climb batch N landing workflow (Opus)"; then `record.py check --base`, `ledger.py check`, `ledger.py landing-check`, `check-index.sh`, `plan-moves.py`, `queue-check.py` and `lengths.py`.

- `plan-moves.py` fails a line out of PLAN that is not word for word in PLAN-history. Its `LOOK` lines, which never fail, name each PLAN line that still looks stale: a line whose own review-queue item is in (a) and that carries no cleanup's mark ("closed at the cleanup of DATE"), a list of items that names a settled one or differs from the queue's list that it names, and a review finding that a commit outside the record names. The checker takes each as a coverage failure, unless `owed.md` or the routing report says why the line stays.
- `queue-check.py` fails a gap in the new numbers, a new open item without "Needed by", a count that its items do not make, and an item new in "Answered by a decision of his" that cites no word of his on that same item, or that names a default taken without him ("at its default", "by the coordinator"). Such an item stays open, landed and then reviewed. The rule leans to keeping an item open: a true answer of his worded with those phrases fails too, and is reworded.
- `lengths.py` informs: each changed entry's length, and each entry already over 600 that grew, which the judge holds unless the owed clause alone explains the growth.

`drive.sh --dry-run` prints the commands of a round and starts nothing. The streams' headless sessions run `facts-extract.sh` and the `git` reads that `writer-stream.sh` allows, and not `record.py`, `ledger.py` or the checks, which need an approval that a headless session cannot get. So `checks.sh` is the first to apply and check the writers' files, after each round, and the fix round reads its output in `mech-1.md`.

Every brief reads the record only through `facts-extract.sh`, `record.py` and `ledger.py` in the worktree, and entries are written only through `record.py`. The run takes three arguments and no text, so a run gives the workflow data, never rules of its own. The briefs change only at the curator's yes.

## Running it

After the post-batch review is committed:

    Workflow({ scriptPath: '/home/user/fortress/explorations/coordinator/tools/record-landing/record-landing.js',
               args: { batch: 'N', base: 'BASE', landing: 'LANDING' } })

It makes `/home/user/fortress-landing-N` on the branch `record/landing-N` at `main`'s head. A replay adds `at`, the commit to make the worktree at, and its worktree and branch end in `-replay`; it stops after the judge, and lands nothing and runs neither the orientation update, the skill update nor the revival page. The replay of climb batch 24's landing, before the first live run at climb batch 25's:

    Workflow({ scriptPath: '/home/user/fortress/explorations/coordinator/tools/record-landing/record-landing.js',
               args: { batch: '24', base: 'b0f6cd6b7', landing: '25238e60c', at: '43cd61b62' } })

That one runs in `/home/user/fortress-landing-24-replay` on `record/landing-24-replay`. A killed run resumes with the same script path, `resumeFromRunId` and the same args, byte for byte; each script skips a step whose output exists. During a run the coordinator writes none of the files that the workflow writes; a decision that the curator gives meanwhile is recorded after the landing. The design's estimate for a landing like climb batch 24's was 0.9M to 1.7M tokens written and 1 to 1.5 hours; the replay wrote 2.06M in 65 minutes (`process-engineering/record-landing-replay-24.md`, section 6). With the driver's waits under five minutes and the cold read in parts, a like landing writes about 1.8M, an estimate. The skill update adds about 0.4M to 0.7M, an estimate: at climb batch 25's landing the coordinator's two writer tasks wrote 107K to the cache, the rest is the cold read, the page and the drivers.

## What it writes

Until the landing, everything goes in the worktree, and the main tree is not touched. The run's folder, `explorations/compile-ladder/climb-batch-N/record-landing/` in the worktree, holds `run.env`, the evidence, `owed.md`, the writers' files, briefs and reports (the entries writer's new ledger rows in `rows.add`: each row line, `| ? | ...`, under a line `## TITLE` that names its section, a title of `ledger.py sections`, as in `## 10. Strings, maps and printing`; `checks.sh` adds each with `ledger.py add` after the other applies, so the first commit carries it, and names in its summary a row line with no such line above it, which it does not add), `check.md`, `cold-read.md`, `mech-1.md`, `mech-2.md`, `mech-final.md`, `final.apply`, `final.rewrite`, the commit messages and `diff.md`, and the logs of the rounds, which git ignores. The markers of finished rounds are in the worktree's `tmp/record-landing/`, which git ignores too, so the worktree is clean after the commits. The branch holds two commits: FACTS, POSITIONS, their histories and the ledger; then PLAN, PLAN-history, the queue, INDEX, the other notes and the run's folder. Each message ends "By the climb batch N landing workflow (Opus).", then the committing part's footer. The landing puts the two commits on `main`, and the run's folder with them, at `explorations/compile-ladder/climb-batch-N/record-landing/` in the main tree; the logs go with the worktree. The workflow's result names the worktree, the branch and `diff.md`, holds the judge's final message with the two hashes, and adds `land` (how the commits landed, their hashes on `main`, the refs pushed, what was removed, the entries given to the orientation update) and `orientation`, the child workflow's result; then `skills`, `coldRead`, `fixes`, `page` and `push`, the skill update's stages, and `line`, the one line for the coordinator's chat message; then `revival` and `revivalPublish`, the revival page's two agents; on a stop, `stopped` says where and why. The skill update writes in the main tree, in `explorations/compile-ladder/climb-batch-N/skills/`: `base.txt`, `task-1.md`, `writer-1.md`, `cold-read.md`, `task-2.md`, `writer-2.md`, and the logs, which git ignores; its markers and its writer's session are under the main tree's `tmp/record-landing-N/`. The writer's commits are on `main`; `folders.sh` commits the `skills/` folder and the orientation update's `orientation/` folder in one more commit. The revival page's stage writes, through `update.py`, the files that the script's README names (the page's two files, `landings.csv` and its row for the batch, the chart and `measure.py`'s five data files, the GitHub Pages copy under `docs/`), and commits them in one more commit, "Revival page: where it stands at the landing of climb batch N, the record chart regenerated"; its log and marker are `revival.log` and `revival.done` under the main tree's `tmp/record-landing-N/`, and its commit message `tmp/revival-msg-N.txt`.

## Landing its result

The workflow lands its own result, by the curator's rule of 2026-11-03 (`../../HELD.md`, "Held in chat (2026-11-03)", 06:2x); the design's decision 6, the coordinator's cherry-pick, is reversed. After the judge, the lander, in the main tree:

1. Checks the judge's checks: the branch holds its commits past AT, `mech-final.md` says "Every check passes.", the worktree is clean. If one fails, it lands nothing, and the result's `stopped` says so; the worktree and the branch stay.
2. Puts the commits on `main`: `git merge --ff-only` of the branch when `main` is still at AT, which keeps the judge's hashes; otherwise `git cherry-pick AT..BRANCH`, since `main` moved during the run. A refusal or a conflict is aborted, `main` stays where it was, and the run stops as in step 1.
3. Runs on `main` `record.py check --base <main before the landing>`, `ledger.py landing-check <the batch's base>` and `check-index.sh`. If one fails, `git reset --keep` takes the run's commits off the local `main`, which is not pushed, and the run stops as in step 1.
4. Pushes, in the order of the `fortress-repo` skill's committing part: `git log origin/main..main` lists only the run's commits, then `main`, `main:claude/worker-brief-fable-vnnuv8` and `main:blinded-fable`. A refused push, or another agent's commit in that list, stops the run, landed but not all pushed, before the orientation update.
5. `git worktree remove` the worktree, without `--force`, and `git branch -D` the branch.
6. Reads the facts list of the orientation call in the landed `diff.md`'s "Next" (the entries that the landing and the run added or changed); the script then runs `orientation.js` with `mode: 'update'`, `out` the batch's `climb-batch-N/orientation/` and `stream` `orientation-bN`. Nothing waits on the coordinator between the record's commits and the update. With no entry there, the update is skipped, and the skill update still runs. If the update fails to start, the run stops, landed and pushed, before the skill update. The skill update below installs its result.

The coordinator then reviews the commits on `main`: `git show --stat` of each commit the result's `land` names, and the landed `diff.md`, not the record. It asks whether it would have done anything differently, and names each POSITIONS change to the curator, from `diff.md`, as the `coordinator` skill's "Quiet times" says. Each held change: run it again, file it in the queue, or leave it. Each "Needed by" and each kind that the workflow set, and each move to (a)'s "Answered by a decision of his", are in `diff.md`'s "For the curator", and wait for the coordinator to confirm. Once the reviews show the workflow sound, this review stops, and the behaviour the workflow encodes is relied on. On a stop, the result's `stopped` names what to do: a stop at steps 1 to 3 leaves `main` as it was, and the worktree and the branch for a resume; a stop at step 4 leaves the commits on the local `main`, for the coordinator to push or take off. The replay lands nothing on `main`: an Opus worker compares its two commits with the hand-made ones (`be3b07aac`, `08cc69e2d`, `b49631cb4`, `85b2998e9`), change by change.

## The skill update

After the orientation update, the workflow brings the `fortress-repo` skill in line with the landing, by the `coordinator` skill's `references/batch.md`, "The landing", step 4, and `references/skill-rewrite.md`, "The method", step 7. No step of the coordinator's comes between. Each driver waits in steps of 230 s, under the five minutes that its prompt cache lives.

1. **The task.** `skills.sh N 1` writes `task-1.md`: the standing rules of `skill-task.md`, then the landing's data from the main tree. The data is the landing's own list of the skill sentences that it made false: the landed `diff.md`'s section "For the skill writer", if the judge wrote one, and else the bullets of its "For the coordinator" that name the skill, which the judge copies from the sort's `owed.md`; the same bullets of `owed.md`, which give each sentence's ground; and the "For the skill writer" sections of `entries-report.md` and `routing-report.md`. Then `diff.md`'s "POSITIONS", and the orientation update's verdicts: its `judgement.md` if its judge ran, or that its admission admitted nothing. If no line names the skill and the judge did not run, no writer starts, and no page or cold read follows. Climb batch 25's landing gives the instance (`skills.sh 25 1 --dry-run` prints its task): its data names the seven sentences that the coordinator's own task to the writer brought in line at that landing; the task's two other changes, a wait cap and a reading rule, came from the review's findings on the process, which stay the coordinator's.
2. **The writer.** `skills.sh` starts a fresh skill writer on the task (`../skill-writer.sh new`), with the standing brief `../../skill-writer-brief.md`. It installs each section that the orientation judge judged "install", word for word, and the lines of `sources-mapping.md`; brings each listed sentence in line, after it reads the entry or row that grounds it; checks each sentence that rests on a changed decision; edits only `fortress-repo`; and commits on `main` by named paths, without pushing. Its session is kept under `tmp/record-landing-N/skill-writer/` (`SKILL_WRITER_STATE`), so the coordinator's own writer session stays as it was. `skills.sh` prints the writer's report, the base, the commits since the base that touch `.claude/skills/`, and the parts that they changed, `sources.md` left out.
3. **The cold read.** An Opus agent reads the changed parts by `../../skill-cold-read-brief.md`, with the base and the parts, and writes `cold-read.md` in parts. If only provenance lines changed, there is no cold read and no page item.
4. **The fixes.** `skills.sh N 2` writes `task-2.md` from `skill-fixes.md` and resumes the same writer on the cold read's flags. The writer rules on each flag itself: it fixes it, deletes a passage that names a rule's source, or leaves it with its reason; a change of meaning stays a decision not taken.
5. **The page.** An Opus agent (`page.md`) takes the page's URL and source from the boot note's "Pages". The page holds only the changes that the curator has not read. The same line of the boot note gives the item that he read up to, and the time of his word. The agent drops that item and every older one. It adds one item per change after the page's last item, and numbers the new items on from it, so the items stand oldest first. An item holds the new text whole, the old words struck through and the changed words marked, and the reason in plain words with no flag code or item number. An approved draft whose words did not change at the landing gets no item. The agent publishes the source by the page's URL with the Artifact tool, after reading the URL. If it cannot publish, it writes the source, and the result's `line` names it for the coordinator to publish by its URL.
6. **The push.** `folders.sh N` commits the `skills/` and `orientation/` folders by named paths with the committing part's footer. A Sonnet agent then pushes as the Land stage does: `git log origin/main..main` must list only the run's commits, those whose paths are all under `.claude/skills/` or the two folders; another agent's commit that stays a minute stops the push, and the result's `stopped` says so.

The result's `line` gives the commits and the page's link, for the coordinator's one line to the curator (`coordinator` skill, "The curator's role and decisions"). The orientation update's held sections, in its `queue.md`, are not filed in the review queue by the workflow: that stays the coordinator's. During the run the coordinator starts no skill-writer task of its own on `fortress-repo`.

## The revival page

Last, only when the Push stage pushed everything, the workflow keeps the revival page current (`../revival-page/README.md`), as the coordinator did by hand after climb batch 26's landing (`0868faa51`). No step of the coordinator's comes between.

1. **The script.** A Sonnet agent runs, in the main tree, `python3 explorations/coordinator/tools/revival-page/update.py --landing N --run-start base` in the background and waits in steps of 230 s. The run start is the script's documented proxy, the time of the base commit that the gather record names, and the new `landings.csv` row's note says so: the run start that the other rows hold, the first line of the batch run's first agent, is only in its transcripts, and the tree holds no other time of the launch (the gate summary's `# machine --- gate batch N` time is the gate's start). For the eight batches from climb batch 20 to 26 whose gather record names its base, the base commit's time is the row's run start, or up to three minutes before it. If the script stops (exit 2: a source's form changed), the run stops there, landed and pushed, and `stopped` gives the script's message; nothing of the page is committed.
2. **The commit and the push.** The same agent commits the paths that the script prints in its first step, and the five data files that its note names, by named paths, with the message that it prints, "By the climb batch N landing workflow." and the committing part's footer, as `folders.sh` commits; then it pushes as the Push stage does, when `git log origin/main..main` lists only that commit.
3. **The republish.** A Sonnet agent (`revival-publish.md`) reads the page's URL, `PAGE_URL` in `update.py`, and the artifact's published `record-growth.png`, and publishes `revival-story.html` with `record-growth.png` as its supporting file by that URL. If it cannot publish, the result's `line` names the two files and the URL, for the coordinator to publish by it.

A resume skips the script and the commit once the page's commit is on `main`. A replay never reaches this stage. The result's `line` ends with the page's commit and the version that the publish gave.
