# Walk's two load readings, checked against the specification and the team's library

## 1. What was checked, and against what

Climb batch 12's rung W made walk refuse at load an object that inherits an abstract method and gives it no body (row 649), and an `override` that overrides nothing (row 653's walk half). Two readings landed with it, each below the traits chapter's letter, each listed for the curator (`explorations/coordinator/PLAN.md:669-670`; `explorations/reviews/batch-12-review.md:173-174`, `:325-327`):

- **Q1.** A declaration with a body whose parameter types are each at or below the abstract method's counts as defining it (the worker's decision 2, `explorations/compile-ladder/rung-walk-load-checks/REPORT.md:195-199`; row 666).
- **Q2.** "Overrides" includes an inherited declaration with equal parameter types (decision 4, `REPORT.md:205`), against the chapter's "strict subtype".

The standards, in the record's order: the specification, with the Types chapter beside it where it speaks (POSITIONS, "The specification stays the standard, the Types chapter beside it."); the type group's late positions, which outweigh earlier text where they differ (`.claude/skills/fortress-repo/references/specification.md`, "Weighing the sources"); and the library's own practice (POSITIONS, "The library's own practice is the standard."). For each reading: what landed, exactly; what each source says; the verdict; what a replacement would change in the library, the tests and the demos; and the default.

## 2. Q1: a body at narrower parameter types defines an inherited abstract method

### 2.1 What landed

`Constructor.checkForDef` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/Constructor.java:423-453`) refuses an object, or an object expression, without static parameters that inherits a declaration without a body, unless `definedBelow` (`:466-484`) finds, among what the object's traits provide, one declaration with a body of the same name and self position whose parameter types are each a subtype, equality included, of the abstract declaration's. One such body is enough: nothing asks that the bodies together cover the abstract declaration's parameter types. A body whose parameter types walk cannot read counts too (`:480-482`). The residue is gated by `ProjectFortress/tests/XXXAbstractMethodPartlyDefinedWalk.fss` (row 666: `tag(self, x: ZZ32) = 1` under the abstract `tag(self, x: Number)` loads). The record states it so (FACTS, "Walk refuses at load an object that leaves an inherited abstract method without a body, ..."; PLAN, "Pavol's answers", item 51, and `PLAN.md:116`).

### 2.2 The chapter's letter

- A trait inherits the method declarations its immediate supertraits provide, "except those method declarations that are overridden ... or whose parameter type (not including the type of the self parameter) is equal to the parameter type of a method declaration that occurs in the trait declaration" (`Specification/basic/traits.tex:521-527`).
- "An abstract method declaration declares an abstract method; any object inheriting an abstract method must define a body expression for the method" (`:570-572`; the Working Draft of February 2011 has the same words, `Specification-1.0-frozen/basic/traits.tex:511`, and so does the 1.0 release).

Read literally, as the worker read it (`REPORT.md:121-128`, section 5): an object whose own declarations are at narrower types has none with the abstract declaration's parameter type, so it inherits the abstract declaration and must define it; a narrower body, alone or with others, does not. That refuses the landed allowance and the coverage shape alike.

The chapter is not of one mind, though. Its own sentence on functional methods says "An abstract function declaration ... can be provided also for overloaded functional method declarations" (`:558-560`), and the rule for abstract function declarations, as the revival revised it under the type group's reading of a `comprises` clause, asks for coverage: "the argument types of the concrete declarations for f must together cover T", "a definition for every type listed in the comprises clause of Molecule, or definitions that together cover those types, or it is a static error" (`Specification/basic/functions.tex:386-395`, `:431-434`, the callouts `revival-covering` at `:396-400` and `:435-444`). The Meet Rule has its covering case in the same words (`Specification/advanced/overloading.tex:312-336`). Only the sentence at `traits.tex:570-572` is older than that reading.

### 2.3 The team's later word

- **The compiled checker, Guy Steele, May 2012.** `AbstractMethodChecker.checkObjectDeclaration` (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/AbstractMethodChecker.scala:81-122`, the comment "GLS 5/30/12" at `:112`): "For each abstract method, check to see whether it is covered by one or more concrete definitions" (`:96`). It takes the concrete declarations of the name and self position whose domains are below the abstract one's, joins their domains into a union, and refuses the object unless the abstract domain is a subtype of that union. A lone narrower body fails it; narrower bodies that together cover pass it.
- **His next commit, 59fdeff62, 2012-06-06**: `TypeAnalyzer` reads a `comprises` clause when it asks whether a closed trait is below a union, "This should improve the behavior of 'covers' checks in AbstractMethodChecker" (`ProjectFortress/src/com/sun/fortress/scala_src/types/TypeAnalyzer.scala:154-158`). So the checker's coverage reads `comprises` clauses, on purpose, since June 2012. The worker measured it: `CoverAbstractProbe`, the shape of `trait D comprises { P, Q }` with abstract `f(self, other: D)` and `P` declaring `f` over `P` and over `Q`, type checks (exit 0), and `PartAbstractProbe`, row 666's program, is refused, "Domain Number is not a subtype of ZZ32" (`REPORT.md:147-148`).
- **Welterweight Fortress, 2012.** The Covered judgement: "The notion of 'covering' is a generalization of the notion of 'overriding,' because an abstract function with an argument that is a trait type with a comprises clause is considered to be covered if it is implemented for all the types comprised"; "the domain type of an abstract function ... must be a subtype of the union of the domains of the concrete definitions"; and "the same rules are used to check methods as well as functions, and for methods, the type of the trait or object within which the method is declared is not considered" (`Papers/Welterweight/static.tick:27-47`; the rule, `Papers/Welterweight/fig-covered.tick:9-13`).
- **The internal FAQ**: "An abstract method can be implemented by concrete methods whose return types are subtypes of the abstract method" (`Specification/appendices/FAQ.tex:159-162`), several concrete methods for one abstract one.
- **The later restart** says nothing: its Types, traits, declarations, objects and overloading chapters hold neither "abstract" nor "override" (`Documentation/Specification/Prose/Language/*.tick`).
- **The team's walk** never made the check: its `checkForDef` returned for every `FnDecl`, body or not (`Constructor.java:399-404` at `a874948ac`), which is row 649.

By the record's weighing, the checker's rule and Welterweight's are the type group's late position, written by the team member who wrote the chapter; they outweigh the sentence at `traits.tex:570-572`.

### 2.5 Verdict

The landed reading is a stopgap, not a reading of any team source. It is wider than the checker's rule, since a lone narrower body satisfies it, and outside the chapter's letter, which admits no narrower body. The rule that should hold is the one the team wrote last, the Covered rule: an object defines an inherited abstract method when its declarations with bodies of that name and self position, at parameter types below the abstract one's, together cover the abstract one's parameter types, `comprises` clauses read as the checker reads them since 59fdeff62. A lone body at the abstract declaration's own parameter types is the trivial cover, so the chapter's plain case is inside it. That is way (a) of Q1's entry, sharpened: the test is coverage, whether or not a `comprises` clause supplies it. It is the type group's word of 2012, it is what the chapter already says of abstract functions and of overloaded functional methods, and it is what the team's library (`Pairs`) and the team's test (`FileConversion`) do. Way (b), the letter, is ruled out: it refuses both, and the checker.

Building it: in walk, `definedBelow` gathers every body below the abstract declaration and tests coverage with `OverloadedFunction.overlapPieces` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/OverloadedFunction.java:1023`), walk's reader of `comprises` clauses for the Meet Rule, rather than returning at the first body; in the specification, `traits.tex:570-572` through the revision form, in the words `functions.tex:431-434` already uses. The same entry should correct a sentence the revival wrote that this check shows false: "The compiled type checker checks, at each object declaration, that the object's concrete methods cover the abstract methods it inherits, reading no comprises clause" (`functions.tex:441-443`; `Specification/appendices/changes.tex:2604-2606`). It reads one, by 59fdeff62 (`TypeAnalyzer.scala:154-158`) and by the worker's `CoverAbstractProbe`; the comprises judgement had already noted Steele's rule (`explorations/reviews/comprises-type-level-judgement.md:21`).

### 2.6 What replacing it would change

With the Covered rule in place of the allowance, on the merged tree:

- Accepted as today: `Pairs` (`RunRanges` is covered by `SingleRange` and `RangeSet` through its clause), `FileConversion.fss`, and the 20 demos that import `Pairs` (`BirdCount1q` to `BirdCount2d`).
- Refused at load, newly: `MersenneTwisterInit` (`Library/Random.fss:323`, row 668), and with it the `Random` component and the two that import it, `QuickCheck` (`Library/QuickCheck.fss:13`) and `ReflectiveQuickCheck` (`Library/ReflectiveQuickCheck.fss:11`); the 14 `Gen` objects without static parameters in those two components (`QuickCheck.fss:258-365` among them; row 669). The tests that import them: `LibraryMeetDeclarations`, `QuickCheckTest` (the team's), `RandomTest`, `ReflectiveNumberTypes`, `ReflectiveQuickCheckTest`, `UniformDistributionStridedRange` and `XXXUniformDistributionRangeType` in `ProjectFortress/tests/`. No demo imports them.
- Promoted: `XXXAbstractMethodPartlyDefinedWalk`, row 666 closed.

Under the letter instead, `Pairs`, `FileConversion.fss` and the 20 `BirdCount` demos are refused as well. So the coverage rule can land only after rows 668 and 669 are repaired in the library, the order PLAN gives ("before row 666 is tightened"); by reading, 669's repair is of rung G's kind for row 628, the `Any` device replaced by the implementer's shape, and 668's is a body at `Generator[\ZZ32\]`. Both are a library rung's to design from the library's own way.

### 2.7 Default

As landed: walk's allowance, row 666 open, until rows 668 and 669 are repaired; then the Covered rule, with the chapter's sentence revised. Q1's entry says so already. It stands, and the answer to its question is (a) in the form above.

## 3. Q2: an `override` with equal parameter types overrides

### 3.1 What landed

`Constructor.checkOverrides` (`Constructor.java:555-576`) refuses an own declaration with the modifier `override` of an object, or of a trait without static parameters, that `overriddenBy` (`:615-634`) relates to none of the declarations its immediate supertraits provide; a generic or unreadable inherited declaration of the name counts as overridden. `overriddenBy` asks that each parameter type of the inherited declaration be a subtype of the override's, equality included. So `object B extends A` with `override f(x: ZZ32)` over `A`'s `f(x: ZZ32)` loads. The same non-strict relation drops inherited declarations in `providedByTrait` (`:528-530`), and `FunctionalMethodMeets.inherited` folds the equal clause and the override clause into one test (`OverloadedFunction.java:1211-1233`). No ledger row gates the equal-typed case (no row's text holds it), and no test writes it; PLAN's Q2 entry is its only record.

### 3.2 The chapter's letter

"A method declaration may have the modifier override. Such a declaration overrides any inherited declaration with the same name and the self parameter (if any) at the same position, whose parameter type, not counting the type of the self parameter, is a strict subtype of the overriding declaration's parameter type. ... A declaration with the modifier override must override some inherited declaration. It is a static error if a declaration with the modifier override does not override any inherited declaration" (`traits.tex:585-595`; the frozen copy, `:529`, `:535`, the same). The inheritance rule's second clause (`:525-527`) is the complement: a declaration with equal parameter types hides the inherited one without overriding it. So an equal-typed `override` hides by `:525-527`, overrides nothing by `:589`, and is a static error by `:594-595`. The letter is unambiguous.

Its history makes it deliberate. The 1.0 release of March 2008 (`Specification-1.0-frozen/fortress.1.0.pdf`, its text extracted) holds `override` only in the grammar and in the calculus's judgement on method overriding, which is redefinition at equal types with no modifier; it has no paragraph on the modifier. The team's internal list asks, under "overriding (03/10/08)", after an example in which `B`'s `override m(x: Object)` widens `A`'s `m(x: ZZ)`: "Do we want to allow to have override when the parameter types of the two declarations are the same?" (`Specification/appendices/future.tex:156-184`). The paragraph was written after that question, with "strict", and the question was never marked answered. The chapter's note says the modifier itself was "not yet supported" (`traits.tex:15-16`).

### 3.3 The team's later word

None. The later restart holds no text on the modifier (the keyword list and the BNF only). Welterweight has no modifier and calls covering "a generalization of the notion of 'overriding'" (`Papers/Welterweight/static.tick:28`). The Dispatch paper: "in Fortress overriding is merely a special case of overloading because the type of the receiver object is taken into account" (`Papers/Dispatch/body.tex:789-792`). Nothing outweighs the chapter here.

### 3.4 The implementations

- The team's checker never read the modifier (no `isOverride` in `scala_src` at `a874948ac`); the team's walk read it by name, dropping an object's inherited declarations of that name (`Constructor.java:442-474` at `a874948ac`, `newOverrides`).
- The revival's checker reads inheritance by the chapter: `providedAndOverridden` (`ProjectFortress/src/com/sun/fortress/scala_src/useful/STypesUtil.scala:1651-1700`) tests equality first, `equivalentED`, and marks the pair `equal` without consulting the modifier; only then, `isOverride && subtypeED`, an override (`excludes`, `:1663-1671`). Its return-type check treats an `equal` pair as an overloaded pair, both ways (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/OverloadingChecker.scala:662-691`). So the checker does not read an equal-typed `override` as overriding; it reads it as the equal clause. It has no check of the modifier at all, which is row 653's checker half, waiting on row 650. PLAN's Q2 entry, "Both paths read it as overriding", is exact for walk and not for the checker.
- Walk: as landed, non-strict in both the drop and the check.

### 3.5 The library and the tests

The library writes no `override`: none in `Library/*.fss`, `Library/*.fsi`, `ProjectFortress/LibraryBuiltin/` or `ProjectFortress/CompilerLibrary/` (the word occurs only in prose comments, `Library/Random.fss:22`, `:43`, `Library/ReflectiveQuickCheck.fss:107`, `Library/FortressLibrary.fss:4164`). Redefinition at equal parameter types is everywhere in it without the modifier, `getter asString()` in every object for one. The team's tests write it to widen: `disp0.fss` (`Number` over `ZZ32`), `disp1.fss` (`Number` over `ZZ32`, `Any` over `T`). The revival's tests write it to widen (`OverrideInTraitWalk`, `FunctionalMethodMeetProvided`, `AbstractOverrideUndefinedWalk`, `FunctionalMethodOverrideOtherPathWalk`, `OverrideFunctionalMethodWiden`, `OverrideAbstractMethodWiden`, `XXXOverrideInheritedThroughOtherSupertype`, `XXXOverrideModifierCodeGeneration`, `XXXOverrideReturnTypeNotSubtype`, `XXXOverrideGenericReturnTypeNotSubtype`) or over an unrelated type to be refused (`OverrideNothingWalk`, `OverrideNothingInTraitWalk`, the generic expected failures). No program in the tree writes an equal-typed `override`; no program's verdict hangs on Q2, and none needs the lenience.

### 3.6 Verdict

The landed reading does not stand as a reading of the chapter. It is a lenience: a modifier the chapter refuses is accepted. It changes no program's run (the inherited declaration is hidden either way, by the equal clause), only which programs load. Nothing later than the chapter speaks, nothing in the library or the tests needs it, and the team wrote the sentence with the question in view. Row 614's decision 3, which the worker followed, says "the chapter's second clause already makes an equal parameter type not inherited, so the rung follows `FunctionalMethodMeets.inherited`, which is not strict" (`explorations/compile-ladder/rung-walk-open-param/REPORT.md:193`). That is right about inheritance and silent about the check: that inheritance treats an equal-typed declaration and an overriding one alike does not make the first an override.

What should replace it: in `checkOverrides` alone, the strict relation, each parameter type of the inherited declaration a subtype of the override's and not all equal; `providedByTrait` and `FunctionalMethodMeets.inherited` unchanged, since there the equal clause and the override clause rightly act together. A test `ProjectFortress/tests/OverrideEqualTypesWalk.fss` keyed `load_exception_contains=does not override any inherited declaration` (an object with `override f(x: ZZ32)` over a trait's `f(x: ZZ32)`), written as the expected failure `XXXOverrideEqualTypesWalk` first, with a row for the lenience, until the next walk rung makes the check strict. Row 653's checker half, when row 650 lets it be built, keyed the same way; `providedAndOverridden`'s `equal` flag already separates the two cases (`STypesUtil.scala:1655-1657`). What it changes: nothing in the library, the tests or the demos.

The other way is to answer the team's question of 2008 with yes: `traits.tex:589`, "a strict subtype", becomes "a subtype", through the revision form (the Appendix I entry, the `\revision` callout, the front matter and a decision record), and both paths stay as they are. That touches the specification and both implementations' reading, so it is the curator's (POSITIONS, "Which decisions taken inside the work reach Pavol, and how."). The first way needs no decision: it is the standard as written.

### 3.7 Default

The record's default, (a) as landed, holds only if the text is revised. By the standard the default is (b), the chapter's strict reading; what is built today stays until the next walk rung, gated by a row and an expected failure.

## 4. Three gaps in the record

1. The equal-typed `override` under walk has no ledger row and no expected failure, though walk accepts what `traits.tex:589-595` refuses; a departure from the text needs one (`specification.md`, "When the text and an implementation disagree"). The row and `XXXOverrideEqualTypesWalk` above close the gap under either answer.
2. The `revival-covering` callout's sentence that the compiled checker covers abstract methods "reading no comprises clause" (`functions.tex:441-443`; `changes.tex:2604-2606`) is false by 59fdeff62 (`TypeAnalyzer.scala:154-158`) and by the worker's `CoverAbstractProbe` (`REPORT.md:147`). It should be corrected in the entry that revises `traits.tex:570-572`.
3. PLAN's Q2 entry says both paths read an equal-typed `override` as overriding; the checker reads it as the equal clause and has no check of the modifier (section 3.4). A wording fix.
