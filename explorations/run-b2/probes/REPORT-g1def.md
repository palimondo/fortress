**D. Pasting — NEGATIVE-VERIFIED for the asked goal; POSITIVE-VERIFIED for square blocks.**
Works: `m: Matrix[\RR64,4,4\] = [ a b ; c d ]` over 2×2 blocks pastes correctly (`g1d_paste4`, block a top-left … d bottom-right). Two independent implementation bugs block the 3×16 goal.
(1) A **one-row** (rank-1) paste of array elements always fails, square or not: `g1d_paste1` (`[ h1 h2 h3 h4 ]`, declared LHS `Matrix[\RR64,3,16\]`) and `g1d_paste5` (`[ a b ]`, 2×2 blocks) both give
`Element at [0] has extent 4 along axis 1 but an earlier element has length 0` (2 for paste5). Cause: `IUOTuple.finish()` allocates `extentSums = new int[result_rank]` (zeros) while `pushLengths` only initialises a slot when `current < 0` — `IUOTuple.java:107,199-212`.
(2) **Non-square** blocks fail even at rank 2: `g1d_paste3` (`[ h1 h2 ; h3 h4 ]`, 3×4 blocks) dies with `java.lang.ArrayIndexOutOfBoundsException: Index 12 out of bounds for length 12` at `AtomicArray.get` ← `IndexedArrayWrapper.get:86` ← `IUOTuple.arrayCopyto:309`. Extents are taken as `Indexed1`=rows, `Indexed2`=cols, but `IndexedArrayWrapper.get/put` swap indices 0 and 1, so the source is read transposed; only r=c survives. Since blocks must be square and extents must agree across block rows/columns, a 3×16 from 3×4 blocks is unreachable by pasting at any spelling.
Spellings tried: literal with declared LHS type; nested `[ [ h1 h2 h3 h4 ] ]` (`g1d_paste2`, same extent error); two-row `[ h1 h2 ; h3 h4 ]`; static args `[\RR64,3,16\ h1 h2 h3 h4 ]` (`g1d_paste6`: `Unmatched delimiters "[\" and "]".` — ledger row 12).

**E. Map union — POSITIVE-VERIFIED** (`g1e_union.fss`, `g1e_gen.fss`, `g1e_bigmerge.fss`, `g1e_bigunion{1,2,3}.fss`).
`e1.union(plusM, e2)` gives `dom {W,b,c}`, `u[W] = W1+W2` elementwise, `b`/`c` passed through; `e1 UNION e2` keeps the left value. Three spelling constraints found:
- The map literal **needs its static args**: `{[\String, Array[\RR64,(ZZ32,ZZ32)\]\] "W" |-> W1, … }`. Without them, `array[\RR64\](2,3)` is dynamically `__DefaultMatrix[\RR64,2,3\]` and Map's invariance rejects the value: `RHS expression type NodeMap[\FlatString,__DefaultMatrix[\RR64,2,3\]\] is not assignable to LHS type Map[\String,Array[\RR64,(ZZ32,ZZ32)\]\]`.

- A component-level `type Mat = …` parses but is not implemented: `** bug! Not yet implemented: TypeAlias` (`g1e_alias.out`), so every type must be spelled out.
Generator questions: `for (k,v) <- seq(e1) do … end` works; list comprehension `<|[\String\] k | (k,v) <- e1 |>` works; map comprehension `{[\String,RR64\] k |-> v[0,0] | (k,v) <- e1 }` works.
`BIG UNION` **requires explicit static args**: `BIG UNION[ m <- seq(ss) ] m` fails with `Failed to find any matching overload, args = (EmptyMap[\BOTTOM,BOTTOM\],NodeMap[\String,ZZ32\])` at `Map.fss:198:46` (the `embiggen` identity is uninstantiated); `BIG UNION[\String,ZZ32\][ m <- seq(ss) ] m` and `BIG UNION[\String,ZZ32\](seq(ss))` both work, as does the matrix-valued form.
Because `UNION` keeps the leftmost value, summing many environments needs either the fold `for m <- seq(es) do acc := acc.union(plusM, m) end` or a **user big operator**, which works: `g1e_bigmerge.fss` declares `opr BIG MERGE()` via `embiggen[\…\](fn (a,b) => a.union(plusM, b), {[\…\] })` and `opr BIG MERGE(g)` via `__bigOperatorSugar`, then `BIG MERGE[ m <- seq(es) ] m` yields W=11100, b=20200, c=3000. (An `embiggen` argument must be an untyped lambda; passing a typed named function gives `Unification error: … embiggen param 1 (j:(Any,Any)->…)`.)
