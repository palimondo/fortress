# Record lines, rung W (`rung-int-conversions`)

## FACTS.md

Four lines, for the compiler-prelude section and the test-harness section.

**The four integer conversions, 2026-09-20.** `widen`, `narrow`, `unsigned` and `signed` are declared on the compiler prelude's four fixed-size integer traits: `widen` and `unsigned` on `trait ZZ32`, `narrow` and `unsigned` on `trait ZZ64`, `widen` and `signed` on `trait NN32`, `narrow` and `signed` on `trait NN64` (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:206-207`, `:269-270`, `:328-329`, `:386-387`, bodies at `.fss:654-655`, `:745-746`, `:810-811`, `:874-875`). `widen` sign-extends from `ZZ32` and zero-extends from `NN32`; `unsigned` and `signed` reinterpret the bits, so `unsigned(-1)` is 4294967295 and `signed` of it is -1; `narrow` throws `IntegerOverflow` when the value does not fit, on both the signed and the unsigned side. `NN64.signed` is declared returning `ZZ64`, not the `NN64` the interpreter's api writes. Gated by `ProjectFortress/library_tests/IntConversionsRungW.fss` (47 assertions) and `.test`. Not added, by name: `partitionL`, `partition`, `big`, `RR64.narrow(): RR32`, and `narrow`/`widen` on `trait ZZ`, which the interpreter declares at `Library/FortressLibrary.fsi:539-540`.

**The compiler prelude's naming convention for overflow, counted 2026-09-20.** In `CompilerBuiltin.fss` the plainly-spelled member of a numeric trait takes the *Overflowing* native and the wrapping and saturating behaviours have their own spellings, which take the Wrapping and Saturating ones: `opr +` at `:763` against `opr BOXPLUS` at `:764` and `opr DOTPLUS` at `:765` is the pattern, and it holds at thirteen plainly-named members of `trait NN32` and `trait NN64` and nineteen of `trait ZZ32` and `trait ZZ64`. This is the in-file evidence that decided what `narrow` does out of range, against the interpreter's truncating unsigned narrow.

**`NN64.coerce(x: NN32)` sign-extended until 2026-09-20.** The body, now at `CompilerBuiltin.fss:816`, was `jMakeNN64FromZZ64(jIntToLong(jMakeZZ32FromNN32(x)))` and `simpleLongArith.intToLong` is `(long) i` (`ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleLongArith.java:302-304`), so an `NN32` of 4294967295 coerced to `NN64` became 18446744073709551615 (measured, `explorations/compile-ladder/rung-int-conversions/probes/probe-coerce-nn-preedit.txt`). It was the only site in the file that widened `NN32` bits to a long. Repaired by rung W with a new native binding, `simpleUnsignedIntArith.toLong`, and gated by three assertions in `IntConversionsRungW.fss`. `library_tests/AverageTest.fss:138` exercises the coercion a thousand times per run and `:110` twice per loop iteration, both with values below 2^31 where the two extensions agree, so the repair is value-neutral there and `library_tests/Integer.test` still gives `OK (27 tests)`.

**An interpreter-only defect has no gated expected-failure home, 2026-09-20.** `shouldFail` is taken from the file name only in the `.test`-driven suites — `FileTests.java:932`, `boolean shouldFail = s.startsWith("XXX")` in `suiteFromListOfFiles` — and `ProjectFortress/tests/` holds 383 `.fss` and no `.test` file at all, so `FileTests.interpreterSuite("tests", true, false)` (`:768`) runs every one of them directly and hands each `InterpreterTest` its own suite-level `expect_failure`, which is `false` (`:825-829`). An `XXX` name in `ProjectFortress/tests/` is honoured only in the exception path at `:346`, which tolerates a failure; nothing there turns red when such a file starts passing. So a defect that shows only under `walk` takes a ledger row, not an `XXX` test, and rule 4's fourth case is the instrument for it.
