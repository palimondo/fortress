# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- **On microGPT-shaped code, boxing is the dominant representational cost, and nothing microGPT-shaped runs on the compiled path today** (measured 2026-09-15, `perf-probes/kernels/REPORT.md`, which corrects the boxing probe's scalar-loop conclusion below as Pavol suspected): the three kernels the program is made of (a 4192-element dot product, a 16×16 matrix product, the row lift with `rmsn`) all fail to compile with `Array is undefined`, `Vector is undefined`, `Array3 is undefined` in `FlatArrays.fsi` (77 errors): the compiler prelude lacks the array TYPES, not only the constructor (wider than ledger row 72; ledger row 305). In Java models of those kernels, boxing as the runtime boxes costs 6.3× (dot), 6.5× (matrix), 2.6× (row lift) over `double[]`, because array element results escape and cannot be scalar-replaced; the generic array object adds only 1.6-9% on top. On the interpreter, the only path that runs them, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch, 0% number representation (JFR on `krows`). A fairly written scalar loop (literals hoisted, no `:=`) compiles to 9.7× primitive Java; JFR on the real compiled run puts 88.9% of the mutable-variable loop under `BaseTask.inATransaction()`'s eagerly built debug string (`BaseTask.java:248`, `Thread.toString()` through `StringBuilder`). Order that follows: (1) an `RR64` array type in the compiler library (G2) so the kernels exist on that path; (2) the two one-line defects, the debug string and `FFloatLiteral`'s String round-trip; (3) unboxing and `double[]`, where the remaining ~6× on array code lives, designed into (1) rather than retrofitted. Also: a local function does not compile (`Can't compile LetFn`, `CodeGen.java:1552`, ledger row 304); a failed compile leaves a 0-byte jar in the bytecode cache.
- Rung 0's two fixes took the eager debug string (row 302) and `FFloatLiteral`'s String round trip (row 303) out of the scalar loop, so the boxing probe's own reading of the unrepaired tree — 156× primitive Java, of which boxing was about 2 %, with `countedseqloop`'s boxed indices and closure call (about 7 %) and the representational rest (about 30 %) still unaddressed — is history (`FACTS-history.md` § Execution model; `perf-probes/boxing/REPORT.md`).
- **The two one-line runtime defects are fixed** (2026-09-17, rung 0 of the plan, `compile-ladder/rung0/REPORT.md`, `before.out`/`after.out`): guarding `BaseTask.inATransaction()`'s debug message with the `debug` flag it already had (`BaseTask.java:248`, ledger row 302) takes the compiled `bench1h`, the loop whose literals are hoisted so the transaction check is the only defect left in it, from **8.8159 s to 0.7287 s** (loop-only medians of 3, JDK 25, 20 M iterations, same freshly rebuilt library jars on both sides).
- **Caching the `double` in `FFloatLiteral`** instead of keeping the literal as a `String` and re-parsing it in `asRR64()` (ledger row 303) takes the compiled `bench1t`, which builds both float literals inside the loop, from **13.0566 s to 0.7384 s**; the literals' own share, the `bench1t` minus `bench1h` difference, falls from 4.2407 s to 0.0097 s, so the per-iteration decimal round trip is gone (2026-09-17, `compile-ladder/rung0/`). The gate after both edits: `ant testFast` 1,377 tests, `ant testSystem` 382 tests, zero failures and zero errors.
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine; the 2026-09-17 before-run of the same unmodified tree measured 13.0566 s and 8.8159 s, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes (observed 2026-09-17).
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); whether `nat` parameters are baked into stamped classes is unprobed.
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see the prelude section). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half).

The interpreter's glue classes take the evaluator's boxed values and cannot be reused by the compiled path; the compiler's natives are static Java methods, and `nativeHelpers/` already ships 355 of them, covering about 79 of the 108 by another name.

## The territory map (2026-09-16, `explorations/coordinator/map/`)

- Tasks and transactions are implemented twice, `interpreter/evaluator/` and `runtimeSystem/`, independently (B.11). Row 302's fix is in the compiled world's copy only.
- `import java` also works on the interpreter path through `ForeignComponentWrapper` + `ClosureMaker`; no test uses it (B.12). Corrected 2026-09-20 (`perf-probes/prelude/import-java-interpreter.md`): wired and unfinished, it does not work; four gaps, all on the interpreter's side: `NamingCzar.fortLib` is fixed to the builtin api, which declares none of `ZZ32`/`RR64`/`JavaString` in that world (`NamingCzar.java:294-295`); a second `import java` from one package falls through `Driver.ensureApiImplemented` to a `ClassCastException` (`Driver.java:464-466`, "temp hack till we knit in natives properly"); the foreign name is never rewritten (`ForeignComponentWrapper.java:31,38`) and `BaseEnv.java:531-533` bugs on the qualified reference; and `ClosureMaker` emits a call into the compiler's `nativewrapper_cache`, which the interpreter neither writes nor loads. So one binding file cannot serve both worlds; the one-library variant is one shared text with one small builtin component per world behind a single api, which makes the api-to-differently-named-component link (ledger row 320's class-name half, `Linker.whoIsImplementingMyAPI`) live work.
- Codegen refuses any declaration carrying a where clause or a contract (`CodeGen.java:2937, :2941, :4076, :4078, :4983, :4985`); not in the ledger (flagged, Pavol's call). `atomic <expr>` has no visitor, `atomic do … end` compiles; `spawn`, `label`/`exit`, object expressions, array literals and comprehensions, local function declarations have no visitor (`spec-to-implementation.md` §3).
- The checker (`IndexBuilder.scala:187-189`) refuses `type` aliases, `test` and `property` on both paths. Coercion is the one mechanism the compiler path has and the interpreter does not (no `Coercion`/`coerce` under `interpreter/`; row 19).
- **A generic object referenced without its static arguments is a static error on the compiled path, and the checker never consults the expected type for it** (2026-09-19, `explorations/compiler-probes/maybe-inference/inference.md`): `b: Box[\ZZ32\] = Box` fails with `Ill-formed type: Box`; a bare `Empty` as a call argument or a field default fails with `T is not in the kind env`, an internal `bug()` from `TypeAnalyzer.scala:766` reported at the declaration's span; the same forms with the static argument written compile and run on both paths. The decision is in the checker's `SVarRef` case, `typechecker/impls/Misc.scala:624-641`, whose `:639-640` keeps the uninstantiated type under the team's own `TODO: handle missing static args`; static-argument inference exists only for arrows (`STypesUtil.scala:912-930`, called from application and coercion), and a parametric empty case reached by `coerce` still fails bare. Under `walk` the same forms are `InterpreterBug: Couldn't figure out Empty[\T\](uninstantiated) <: Opt[\ZZ32\]`. Consequence for row 331: a parametric `Nothing[\T\]` would serve the corpus's `Nothing[\ZZ32\]` and never the specification's bare `= Nothing`; the non-parametric object plus `coerce` that the prelude uses is the only shape that compiles, so `Maybe` stays as landed. Incidental: `typecase` over a user-declared generic object crashes code generation (`Error trying to close method scope`, `CodeGen.java:2802`), row 340. Corrected the same day by the minimal reproducer (`compiler-probes/maybe-inference/probes/TcPlain.fss`): neither the generic object nor `typecase` alone is the trigger; a `typecase` used directly as a function or method body whose value needs an implicit coercion (`IntLiteral` to a declared `ZZ32`) makes ASM's stack-map frame computation fail (`ArrayIndexOutOfBoundsException` under `MethodWriter.visitMaxs`, relabelled by the `catch (Throwable)` at `CodeGen.java:2801-2802`); wrapped in `do … end` the same body compiles, and every gated use of the shape returns `()` so never reaches the coercion.
- The gate: two corpora, hand-ported, sharing no file name; only `parser_tests/` is read by both; no test compares the paths on one program; interpreter tests pass on "no exception and no `fail` in output" (`FileTests.java:367-371`), compiler run tests on exit code plus `PASS`. `fortress.unittests.noopt=true` (`default_repository/configuration:51`) hides 226 tests and leaves the 43-file bytecode optimizer with zero. Every `testSystem` shard runs `FORTRESS_THREADS=1` (`build.xml:1184`), so no gated test sees concurrency; `TransactionJUTest`'s multi-threaded half is commented out (`TestTask.java:43-44`). No `nat`-parameterised program is compiled or run; the cache round trip is not asserted (`ASTJUTest.java:654`). 121 `.fss` inside green directories are dark; `linker_tests`, `compiler_regressions`, `BirdyLib`, the `not_working_*` directories are orphaned (`map/test-coverage.md`).

## The compile-path ladder baseline (2026-09-17, `explorations/compile-ladder/REPORT.md`)

- The compiled world's mutable-variable cell holds `fortress.AnyType.Any`, the language's top type, not `runtimeValues.FValue`: `FValue` is an abstract class (`runtimeValues/FValue.java:13`) and a compiled closure is not one of its subclasses, so a mutable variable of arrow type failed the verifier. The defect was already in the tree for *local* mutable variables, which have always been stored in such a cell (`compile-ladder/repair-r1-atomic-static/probes/P15LocalArrow.fss`, `P16LocalArrowTask.fss`: `VerifyError` on `49ee5e91`, `f(1) = 3` after R1), and R1 fixed both kinds by widening the payload (`runtimeValues/MutableFValue.java:18-32`, `runtimeSystem/Transaction.java:20,27-28,144,152,226`).
- **A numeral's value reaches the compiled world intact as of the repair batch of 2026-09-18.** `CodeGen.forIntLiteralExpr` chose the numeral's representation by `BigInteger.bitLength()` against `<= 32` and `<= 64`; `bitLength()` counts no sign bit, so a non-negative numeral of bit length exactly 32 or exactly 64 was truncated into a signed slot and arrived wrapped negative — `4294967295` and `18446744073709551615` both became `-1`, against `Specification/basic/expressions/literals.tex:83-86` (a numeral of digits has the value of its digits in radix ten, with nothing bounding it) and `basic-lib/basic-integers.tex:368-370,398-401` (wrapping and saturating have their own operator spellings and "operations on type $\mathbb{Z}$ never need to wrap or saturate"). The bounds are now `<= 31` and `<= 63`, exact for both signs, and `FIntLiteral.asNN64` reads the decimal string a numeral of bit length 64 now keeps. Where the compiled run contradicted `walk` in silence it now agrees with it: `4294967295` at `ZZ` prints `4294967295` on both paths, and `a = 4294967295; b = 1; println (a + b)` prints `4294967296` on both (ledger row 317, `compile-ladder/repair-r2-literal-wrap/REPORT.md`).
- **The repair turns one loud failure into a quiet value, and the value it prints is wrong even though the value it holds is right.** `FIntLiteral.asNN64` threw for every string-carried numeral before this rung, and `simpleIntLiteralArith.fromBigInteger` sends every `IntLiteral` arithmetic result of bit length 64 or more to the string branch (`nativeHelpers/simpleIntLiteralArith.java:31-32`), a path R2 does not touch — so the transition needs no numeral of bit length 64 in the source at all. `x = 9223372036854775807` then `n: NN64 = x + x + 1` raised `Error: Not in range for NN64: 18446744073709551615` before R2 and now computes $2^{64}-1$, which `literals.tex:83-86` makes the correct value, and prints it as `-1` because `FNN64.toString` is signed (`compiler/runtimeValues/FNN64.java:20`, ledger row 326). The probe is `compile-ladder/repair-r2-literal-wrap/probes/skeptic/s3.fss` with `s3.compiled` and `s3.walk`; `walk` refuses the coercion instead ("RHS expression type Long is not assignable to LHS type NN64"). The error that named the true value is gone while the rendering is wrong, so row 326 and this fact are one situation and should be read together.
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification/basic-lib/convenience.tex:49`) gives the identical single error from `fortress compile` and from `fortress walk`, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`). ## The library's arrays and algebra

- `Vector[\T extends Number, nat s0\]` and `Matrix[\T extends Number, nat s0, nat s1\]` are the only sized array traits; `Array3[\T, nat b0, nat s0, …\]` carries no algebraic trait (row 292; `FortressLibrary.fsi:1460, 1578, 1652`).
- `Vector` and `Matrix` inherit `+`, `-`, unary `-` and `zero` from `AdditiveGroup`, nothing else; `×` reaches no array by design because juxtaposition is the inner product and the array traits exclude `AnyMultiplicativeRing` (rows 64, 109, 293); a carrier that extends the ring is accepted unchecked, changes juxtaposition to elementwise and breaks `+` (vocabulary review v02, v02b).
- The library's products are declared with shared `nat`s (`Matrix[\T,n,m\]` × `Matrix[\T,m,p\]`, `FortressLibrary.fsi:1508-1516`); C4's own products were not, which is habit; the focused base's `FlatArrays2` states them (twelve declarations including the per-rank elementwise `×` and `/`, 25 of 29 nats agreeing; 39 declarations), and a wrong-shape call is refused at dispatch, uncatchable for an overloaded name (row 83), as a unification error naming the nat for an unoverloaded one (`apl/mg/checks/mismatch_probe.out`).
- Two declarations of one name differing only in the element type, or a rank-specialised declaration beside an index-generic one, are refused at load ("at least one pair of parameters must have excluding types"; `apl/mg/checks/model_run.out.0`, `elemwise_nat_probe.out.0`); two apis' overloads of one name are checked as one family, so two vocabularies cannot stand in one component (`diag_fwd_two_vocabularies_rejected.out.0`).
- The shipped `RR64` does not satisfy the specification's algebraic bound `T extends AdditiveGroup[\T\]` (vocabulary review, probe `v04b_groupbound.out.0`); `T extends Number` is the bound that works for every element type and rank (row 295).
- No trait for scalar extension ships; no reshape, plane, gather, outer product or ravel exists in the library (vocabulary review, section A).
- An array is a trait with `get`/`put`; a view is an object implementing it over other storage, the language's own idiom; the library's row slice `m[i,:]` costs 5× a six-line user view; a diagonal as a `Matrix` view costs 13-54× the operator (vocabulary review v20, v07).
- The element type is `Number` only for `Vector`/`Matrix` (row 24); irrelevant to numeric microGPT, decisive for Run B's autodiff value and for APL characters.
