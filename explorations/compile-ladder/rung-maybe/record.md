## FACTS.md

Four lines. The first is the rung; the other three are facts it established on the way. The
first belongs in the compile-path ladder section, the other three wherever the prelude and
the map are discussed.

> **The compiler prelude has `Maybe` since 2026-09-19, and its empty case follows the specification rather than the interpreter.** `value trait Maybe[\T extends Any\] extends { Condition[\T\] } comprises { Just[\T\], NothingObject[\T\] }` with `coerce(_: Nothing)`, plus `value object Just[\T\](x: T)`, `value object NothingObject[\T\]` and a non-parametric `value object Nothing end` (`Library/CompilerLibrary.fsi:217-234`, bodies `.fss:522-580`), in place of the team's draft that had been commented out at those same lines. The bodies are the shipped `Option`/`Some`/`NoneObject`/`None` (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:649-661`, `.fss:1308-1367`) copied member for member with the names changed and `getter isNothing(): Boolean = NOT self.holds` added; `Maybe` is a second copy of the `Condition` protocol beside `Option`, not built over it, because `Option`'s `comprises` clause is closed and widening it would be a change to a declared type the prelude already has. Gated by `ProjectFortress/library_tests/MaybeRungM.test`. **The empty case is the fork this rung decided**: the specification declares `Nothing` as one non-parametric object (`Specification/basic-lib/convenience.tex:49`, a prose chapter) and uses it as a value at a `Maybe[\String\]` (`basic/exceptions.tex:122,124`, `= Nothing`), which works here only because the compile path has coercion and the interpreter does not; the interpreter's parametric `value object Nothing[\T\]` (`Library/FortressLibrary.fss:1342`) is a workaround its own source calls one ("Obviously ought to be a non-parametric singleton when we get where clauses working", `:1340-1341`), and all 22 corpus files and the interpreter-world collections in `Library/` write that parametric form. Consequence: `Nothing[\ZZ32\]` is now "Unexpected type for a singleton object reference" on the compile path, so the two ladder files this rung was assigned, `tests/ExceptionScoping.fss` and `tests/oddJuxt.fss`, do not pass — that cost is the new ledger row. What the rung does deliver is the cascade it was chosen for: over the six ladder files whose recorded first error named one of the three names, 58 errors become 22, and `HeapTest.fss` and `IntMapTest.fss` move off `Maybe is undefined` in `Library/Heap.fsi:54` and `IntMap.fsi:33` to their next wall.

> **One Fortress scope cannot hold both spellings of an optional type's empty case, and the non-parametric declaration wins the name silently.** Declaring `value object NothingD[\T extends Any\] extends MaybeD[\T\]` and then `value object NothingD end` in one component does not raise a duplicate-name error: the name resolves with zero static parameters, and it is the *parametric* declaration's own header and the `comprises` clause naming it that become errors — "Incorrect number of static arguments for type 'NothingD': provided 1, expected 0" (`explorations/compile-ladder/rung-maybe/probes/DualNothing.fss`, `.txt`). So an optional type's empty case is a binary choice, with no overload that serves both spellings, and a tree that mixes them fails at the parametric uses rather than at the declarations.

> **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification/basic-lib/convenience.tex:49`) gives the identical single error from `fortress compile` and from `fortress walk`, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause in either implementation. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at codegen — `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4088`) — but nothing reaches it. This is the mechanism behind `FortressLibrary.fss:1340-1341`'s "when we get where clauses working", and it is why both worlds must spell the empty case some other way.

> **`Maybe`, `Just` and `Nothing` are named from Java after all, in `syntax_abstractions/`, which is outside the `compiler/` + `runtimeSystem/` scope the climb has been grepping.** `syntax_abstractions/phases/TemplateVarRewriter.java:114-117` builds an **unqualified** `Maybe[\X\]` trait type for a grammar template variable of option depth (`NodeFactory.makeId(span, "Maybe")`), and `syntax_abstractions/util/FortressTypeToJavaType.java:50-58` maps the name texts `Maybe`, `Just` and `Nothing`, each with exactly one type argument, to the Java `Option<arg>`; `FortressTypeToJavaTypeJUTest.java:60-94` is that mapping's unit test, and the interpreter's `Evaluator.java:595` compares a typecase clause's type name against `"Just"`. Being unqualified, they resolve against whatever `WellKnownNames.useCompilerLibraries()` points the prelude at (`WellKnownNames.java:113-115`), so before this rung an option-depth gap referred to an undeclared `Maybe` on the compile path and now it resolves — the direction the design intends, since the name was chosen for the interpreter prelude's `Maybe`. It cannot break: that code reads only the name text and the argument count, and `Maybe[\T extends Any\]` takes the one argument it expects. It also cannot reach the gate, though not for the reason a grep of the compile-path corpora gives: `grep -rln 'grammar '` over `compiler_tests/`, `other_compiler_tests/` and `library_tests/` finds no file, but those three are not the only gated corpus — `syntax_abstraction_tests/` is driven by `SyntaxAbstractionJUTest`, which `testFast` does run (`build.xml:974` includes `**/*JUTest.class` in the `misc` track and `:987` excludes only `SyntaxAbstractionJUTestAll`). The reason is the phase order: that suite runs `ForUse.fss` and its siblings through `StaticTestSuite.StaticTestCase` (`SyntaxAbstractionJUTest.java:31,41`), whose `compile()` sets `Shell.setPhaseOrder(PhaseOrder.interpreterPhaseOrder)` (`ProjectFortress/src/com/sun/fortress/compiler/StaticTestSuite.java:334`), so it never loads `CompilerLibrary` and never sees this rung's declarations. **The general lesson for later rungs**: "nothing in Java or Scala names this" must be grepped over `src/com/sun/fortress/` and not over `compiler/` and `runtimeSystem/` alone.
