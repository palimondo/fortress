## Reading contract

The writer puts these lines at the head of the orientation, in this order, in about 900 characters:

1. **What it is.** The current departures of revived Fortress from the team's Fortress and from what a model expects from Java, Scala, Haskell or Julia. The team left three forms that disagree: the specification, walk with the interpreter's library, and the compiled path with the compiler's library. The rules below say how this tree resolves them.
2. **Who reads it, and when.** Every worker reads it whole, after `SKILL.md`, before work. It assumes the core's definitions. It assumes nothing of the batch history, the coordinator's record or `sources.md`.
3. **What a rule is.** Each rule states the tree as it stands. A rule that names a POSITIONS entry (P-N) is a decision of the curator. A rule without one states what the tree does: build on it, and do not cite it as a decision. Question a rule only on new evidence (`SKILL.md`, "When to explore"). (The lint refuses the phrases "the curator's decision" and "his decision" in this skill: use these words.)
4. **Where the rules come from.** Most follow the type group's later texts over the specification's early text (P-26; `exploring.md`, "Weighing the sources"). Where a rule changed the specification, Appendix I keeps the original text (`specification.md`). The Working Draft, `Specification-1.0-frozen/`, is unrevised.
5. **What is not here.** A departure of walk or the compiled checker from a rule is named by its gap-ledger row. Specialist detail is in the area parts, which each rule names. A change that is not here can be in the record: search FACTS and POSITIONS (`records.md`, "Reading the record") before you call a disagreement a conflict (`exploring.md`).
6. **Why it matters.** An old note, a team test and your training can be right about the team's walk and wrong here: the number types do not nest, fixed-width arithmetic does not wrap, and walk converts arguments.

### 1. Dispatch and overloading (5 rules)

- **D1. Overloads may differ in their static parameters, and are judged on declared domains.** A declaration's declared domain is the set of argument types that its declared parameter types accept, at every instance within its bounds (define here). Both paths judge an overload set by the No Duplicates, Return Type and Meet Rules (core states them, unnamed) on declared domains; the Return Type Rule holds at every instance, not at one. **Corrects:** the Working Draft's ban on overloads whose static parameters differ, and a check of a generic declaration at one instance, as Java's erasure suggests. **Prevents:** refusing or rewriting valid library pairs (the ban would refuse about 180 api pairs); trusting a pair that passes at one instance (it compiled and failed the JVM's verification, row 536). **Old:** 1, 2, 5 (its resolution's first sentences). **Record:** P-45, F-174, F-50, F-75, F-252, F-275; quiz B.3 grades "overload sets are checked pair by pair" outdated.
- **D2. Where a declaration has static parameters, exclusion is read over the whole tuple of parameter types.** By the exclusion rule, a value of both domains has one instance of each generic type at each position, so those instances' static arguments are equal; the domains exclude where these equalities cannot hold together, or where some position excludes at the instance that they force. So `o[\T\](x: P[\T\], b: Box[\T\])` beside `o[\T\](x: Q[\T\], b: Box[\T\])`, with `P[\T\] excludes { Q[\T\] }`, is valid on both paths. A pair where the equalities fix one declaration's static parameter and leave one of the other's free overlaps, and both paths refuse it. **Corrects:** exclusion read position by position, as the team's walk did ("at least one pair of parameters must have excluding types") and as a Java or Scala reader would. **Prevents:** splitting or renaming a valid generic pair; relying on a pair with a free parameter. **Old:** 6 (its limits go to the area parts). **Record:** P-152, F-258.
- **D3. Walk chooses at a call by declared parameter types, never by the order of the declarations, and infers a generic method's static arguments.** It infers a dotted generic method's own static arguments from the arguments' run-time types, as for a generic function, also among the receiver's overloads; it compares a functional method of a generic trait on the instance that the call makes. A call with an argument outside a bound still fails, "Cannot unify". **Corrects:** the team's walk, which chose by the order of writing and failed a dotted generic call with "Unification error". **Prevents:** reordering declarations to steer dispatch; writing static arguments or wrappers around a generic method. **Old:** 4, 22. **Record:** F-26, F-253; `Library/Generator2.fss`, the team's note on `distribute`.
- **D4. Walk's load check is not the specification's verdict.** It refuses some valid pairs and loads some invalid ones, and the compiled checker differs from it on others. Each case has a ledger row: 539, 416, 786, 412 and 759, 779, 780, 788, 787. At load, walk does not check two functional methods of a generic trait or object on their declared domains; it compares them at each call, so a call can fail "Cannot find definition for method" (row 780). Before you take a load refusal or acceptance as a rule of the language, or change code to satisfy it, find its row; `interpreter.md`, "What walk checks", lists the cases. **Corrects:** walk and the checker accept the same pairs, and both follow the specification. **Prevents:** reshaping valid code to pass walk (the library's bounds check is three functions named by rank because walk refuses the overload, row 416's note); taking a pair as valid because walk loads it; reporting a known gap again. **Old:** 5 (the refusal messages, the team-rule cases, the eight departures), 6 (the limits). **Record:** F-27, F-252, F-257, F-274, F-275, F-238; quiz trap 13 ("the interpreter is more permissive") holds only in part.
- **D5. Functional methods with equivalent parameter types are duplicates wherever `self` stands, and abstract declarations count.** The checker reads every functional method that a type provides, abstract ones included, in its overloading checks: an abstract and a concrete declaration with the same parameter types in one trait are refused. An object that inherits an abstract functional method from one trait and a body for it from a sibling trait is refused unless it declares the method itself (P-149; Scala accepts it). **Corrects:** `self`'s position tells two methods apart; an abstract declaration does not overload (Java, Scala). **Prevents:** declaring `f(self, y: S)` beside `f(x: S, self)` (the code generator stopped, "apparently malformed overload set not rejected"); relying on a sibling trait's body. **Old:** 3, 13. **Record:** F-223, F-80, F-142, P-149.

### 2. Traits and objects (6 rules)

- **T1. The exclusion rule (core) is the compiled checker's, and walk does not apply it.** The checker refuses a type that extends two instantiations of one generic trait and relies on the rule: relaxed alone, a program passes and dies with `IncompatibleClassChangeError`. Walk accepts such a type and does not count two instantiations as excluding (row 416), so a program that breaks the rule runs under walk and is refused compiled. The specification now states the rule; the Working Draft's examples that break it stay, marked "Not allowed". **Corrects:** the Working Draft and the team's nested number types, which break the rule; a walk run as proof that a hierarchy is legal. **Prevents:** copying a "Not allowed" example; a library or test hierarchy that only walk accepts. **Old:** 8. **Record:** F-44, P-43, P-97; quiz B.11 lists the rule as missing.
- **T2. A `comprises` clause is read at the level of values.** Every value of the closed trait is a value of a listed type. So a generic trait may extend the closed trait without being listed if every type below it is below a listed type, as `Integral[\I\]` extends `AnyIntegral`; and several declarations below two overloads may together cover their meet (cover: core). Walk checks only the main component's clauses at load (`interpreter.md`). **Corrects:** Scala's `sealed`, where each direct subtype is listed, and four passages of the Working Draft that read the clause by types. **Prevents:** listing a generic subtrait, or refusing one; adding a meet declaration that a cover makes needless. **Old:** 9. **Record:** P-60, P-44, F-175, F-76.
- **T3. `override` widens; to replace an inherited declaration at its own parameter types, declare it again without `override`.** An `override` overrides an inherited declaration only where the inherited parameter types are strictly narrower. A type provides what it declares and inherits, less what its own declarations override or repeat; both paths read it so, and the checker checks that an overriding return type is a subtype. Walk refuses at load an `override` that overrides nothing, also one at equal parameter types, except at an instance of a generic trait above a declared object, where equal types count as overridden; the compiled checker accepts it (row 653), and the code generator refuses the `override` modifier (row 650). A trait's `override` holds for every type below it. **Corrects:** Java's and Scala's `override` at the same signature. **Prevents:** a Java-style `override` in the library, which makes walk refuse every program at load (`interpreter.md`, "What walk checks"). **Old:** 12, 10 (the trait's `override`), 11 (the `override` half). **Record:** F-147, F-88, F-145; the team's `ProjectFortress/tests/disp0.fss`, valid by the rule.
- **T4. An object defines an inherited abstract method by bodies that together cover its parameter types.** One body at its parameter types, or bodies at narrower ones that cover them with `comprises` clauses read (P-147). Walk refuses at load an object or object expression without static parameters that leaves one uncovered, or whose cover search does not settle (the limits are in `interpreter.md`), and a valid object whose one body has a static parameter of its own (row 728); it checks no generic object (row 665). The checker has the same limits, and refuses a cover that needs a split where the abstract or a covering method has static parameters (row 725). **Corrects:** Java's rule that one exact signature implements; the team's walk, which loaded such an object and stopped at the call ("has neither body nor def"). **Prevents:** leaving an abstract method uncovered in the library, which stops every program at load; treating narrower bodies as leaving the object abstract. **Old:** 11 (the abstract half). **Record:** F-145, P-147; the team's `Random` and `QuickCheck` left three methods uncovered.
- **T5. In a self-typed trait the checker types `self` as the trait met with the implementing type.** For `trait T[\X extends T[\X\]\]`, or a trait bounded by a self-typed trait that it extends at `X`, with no `comprises` clause or one that lists only `...`: in `T`'s bodies, `self` is `T[\X\] & X`; signatures keep `T[\X\]`; a trait, object or object expression that extends `T[\A\]` and is not an `A` is refused. Walk is unchanged. A compiled body that returns `self` still fails the JVM's verification when its class loads at an object type. **Corrects:** Java's F-bounded `this`, which is only `T` and needs a cast; Scala's explicit self-type. **Prevents:** casting `self` or rewriting the library's default bodies (`floor(self): I = self`); an extender at another type. **Old:** 17. **Record:** P-146, F-225.
- **T6. An order needs bounded elements.** A pair or a triple compares by `<`, `<=`, `>`, `>=` and `CMP` only where each element type extends `StandardPartialOrder`; walk refuses at the call a tuple with an element of another type, also where earlier elements decide, as `(1,()) < (2,())`, and numbers of two run-time types at one position, as `(1,2) < (1,2.5)` (row 511). Unordered deciding elements give `false`, or `Unordered` for `CMP`. A `List[\E\]` is ordered only where `E extends StandardTotalOrder[\E\]` (conditional extension, S3); its `=` stays element-wise. **Corrects:** Python's and Scala's lexicographic order over any tuple, decided by the first unequal element; an order at every element type. **Prevents:** comparing nested or mixed-number tuples in a test; sorting a list of `RR64` or `QQ` in code that must compile. **Old:** 33, 28 (the list's order). **Record:** F-92, P-154, F-255.

### 3. Static parameters, `where` clauses and sizes (4 rules)

Keep the heading's first words "Static parameters": `SKILL.md:132` points to it.

- **S1. A type parameter that a call does not fix takes its bound (core), with these exceptions.** The compiled checker takes the intersection of its upper bounds, narrowed by the expected type. Under walk, an F-bounded parameter stays open (core); walk prints it `OPEN`, as `BoxU[\OPEN\]`, and a generic type that holds it admits no more than at `Bottom`. Walk still gives `Bottom` to a parameter declared with two bounds neither below the other (row 591), to one that an argument bounds only from above with a bound that names another static parameter (row 612), and to one that only the result of a function expression without a return type fixes (row 587). **Corrects:** Scala's inference of `Nothing`, and the team's `Bottom` or unsolved parameter. **Prevents:** expecting `Bottom` or `Nothing` for an unconstrained parameter; misreading `OPEN` in a message. **Old:** 21, 24 (the open parameter). **Record:** P-48, F-78, F-141, F-143; quiz B.11 lists the rule as missing.
- **S2. Only the compiled checker gives a call written as an argument the enclosing call's context.** Where the enclosing call is not accepted as written, the checker types each argument that is a call with inferred static arguments again, with each enclosing declaration's parameter type as its expected type, and never passes over a declaration that accepts the call as written. So `takesBox64(mk())` compiles for `mk[\T\](): BoxT[\T\]`. Walk gives an argument no expected type (row 705): there `mk()` takes its bound. **Corrects:** Java's and Scala's inference of a nested generic call from its target. **Prevents:** a walk test that relies on an inner call's result-only parameter. **Old:** 23. **Record:** P-51, F-221; `ProjectFortress/tests/XXXInferCallArgumentWalk.fss`.
- **S3. Only the `where` forms that the team wrote are built, and only the compiled checker reads them all.** The forms (P-151): conditional extension, an `extends` entry under a `where` clause that binds no variable and states only constraints `T extends SomeTrait`, so the type extends the parent exactly where they hold (define here); a function's or a method's condition on its own static parameters, or a method's on its trait's, checked at a call, a dotted call by the receiver's static argument; and a type `where`-clause variable in a `comprises` clause, `AnyList comprises List[\E\] where [\E\]`, which the checker opens at each call as a fresh type equal only to itself, and walk binds at load as a type that stands for every type. Walk and the compiled run time read a conditional extension at every instance (row 774); walk runs a dotted call that breaks a method's condition (row 777); the code generator compiles a conditional `extends` and refuses a declaration with a `where` clause of its own (row 701). The checker's unchecked cases and the variable's departures are in `compiler.md`. **Corrects:** Haskell's and Scala's constraints, enforced wherever they stand; any `where` form working. **Prevents:** relying on walk to enforce a condition; writing a form the team did not write; expecting a declaration with its own `where` clause to compile. **Old:** 28, 27, 32. **Record:** P-151, F-250, F-255, F-256, F-251.
- **S4. Sizes are checked and computed by their written form.** The compiled checker checks sizes, and the run time carries each as a descriptor (core). Two sizes are the same when they are written alike once each operation on numerals is computed: `2 3` is `6`, and `s0 s1` is not `s1 s0`. A static parameter is not known to differ from a numeral, so in `typecase N[\b0\] of N[\0\] => ...` the arm is reachable. The checker computes a power of 0, 1 or -1 at any exponent and of another base up to the exponent 4096, and refuses a larger one; neither path computes a negative exponent, and walk refuses it. The class loader computes a size when it names a class, `Box[\2 + 1\]` is `Box[\3\]`, and checks no kind (row 675). A size known only at run time comes from `NatReflect`'s `reflect`: its `NatParam` value, passed where `N[\n\]` is expected, binds `n` at the call, under walk at dispatch, in the checker as a fresh size equal only to itself; its compiled run waits for the switch-over. **Corrects:** dependent-type normalisation, where `s0 s1` equals `s1 s0` and `n + 1` differs from `0`. **Prevents:** expecting two sizes written in different orders to match; overloads at `T[\n+1\]` beside `T[\0\]`, which the team's own answers refuse. **Old:** 30, 29, 31. **Record:** P-40, P-41, P-55, F-176, F-222, F-129, F-270; `ProjectFortress/compiler_tests/XXXNatOpenRun.fss`.

### 4. Numbers (4 rules)

- **N1. The flat number types are route A.** The siblings of the core's bullet keep the exclusion rule: route A (P-43). Route C, the alternative not taken, keeps a nested tower under the forest rule of the team's 2012 patent applications, which lets a type extend several instantiations of a self-typed generic trait along a chain (F-46). The record and the team's notes still call the number and order traits "the tower"; "the flat tower" means the siblings. **Corrects:** a nested tower, as Haskell's classes and Java's widening suggest, and as the team's walk had. **Prevents:** reading "the tower" in an entry as nesting; meeting "route C" in an Appendix I entry without its meaning. **Old:** 34. **Record:** P-43, F-131, F-45, F-46; cold readers lacked both names (concepts lists p3, p8, f3, f4).
- **N2. Under walk a numeral is a value of a run-time class, and generics instantiate at it.** The compiled checker types every integer numeral as `IntLiteral`, a sibling under `Number` from which each number type converts. Walk gives a numeral the type `ZZ32`, `ZZ64` or `ZZ` by its value, as the value objects `Int`, `Long` or `BigNum`, and instantiates a generic at that class: `Box[\Int\]` is not `Box[\ZZ32\]` and dispatches past it (row 364); `IntLiteral`'s arithmetic answers a `ZZ32` (row 578). `array1` and `array2` give a `Vector` or a `Matrix` only at the eight number types, and a plain array at any other element type, a user subtype of `Number` included, whose `+` and unary `-` fail dispatch under walk; under walk an inferred element type is a run-time class, so it gives a plain array (row 721): write the static argument. This holds until walk runs the checker (P-12, P-76). **Corrects:** a numeral that is a `ZZ32` everywhere, as Java's `int`; the specification's vector at every element type below `Number`. **Prevents:** a walk test that expects `Box[\ZZ32\]` from a numeral; calling `+` on an `array1` result with an inferred element type. **Old:** 45, 38 (`IntLiteral`'s power). **Record:** F-74, F-79, F-229, F-262, P-76; quiz B.6 and trap 11.
- **N3. Arguments convert by declared coercions, and a generic call promotes.** Walk converts by coercion at a call, a typed binding and an assignment, and chooses the coercion by the run-time value; the checker chooses it statically (P-59). A generic declaration that applies is instantiated by promotion, at the narrowest type into which its arguments coerce, on both paths: a `ZZ32` with a `ZZ64` gives `ZZ64`, and with an `NN32` too (define promotion here). Walk does not convert or promote through the elements of a tuple or a varargs argument: it takes their join (rows 395, 511). Where several declarations apply only by coercion and none is more specific, both paths stop, "Ambiguous coercion"; the checker reads a tie that only a numeral makes as `ZZ32`, else `ZZ64` or `ZZ`. **Corrects:** Java's widening, Haskell's absence of conversions, the team's walk that converted nothing, and element-wise promotion of a tuple. **Prevents:** expecting `f(ZZ32, ZZ64)` on a generic `f[\T\](a: T, b: T)` to fail or to run at `Number`; expecting a mixed tuple to convert. **Old:** 35, 36. **Record:** F-128, F-55, F-73, P-46, P-74, P-59; quiz B.6 grades the interpreter's coercion outdated.
- **N4. An integer power answers its base's own type.** In the interpreter's library each integer `^` answers its base's type at an exponent of any integer type. At a negative exponent, the bases 1 and -1 give their exact power, 0 raises `DivisionByZero`, and any other base raises `IntegerOverflow`. For a fraction, write a float or rational base: `2.0^(-1)` is 0.5, `(2/3)^(-1)` is `3/2`. `QQ`'s power takes an exponent of any integer type. Until the switch-over the compiler's prelude differs: its `ZZ32` power gives 0 at a negative exponent and a raw Java exception at a base of 0 (rows 441, 523). **Corrects:** `2^(-1)` as 0.5 (the team's walk, Python) or as the rational `1/2` (the Working Draft). **Prevents:** writing `10^(-k)` for a fraction, as the team's own tests and demos did. **Old:** 38, 39. **Record:** P-153, F-263, F-262.

### 5. Reductions and comprehensions (2 rules)

- **R1. A reduction's static argument, by path.** The compiled checker takes the element type neither from the clauses nor from a declared type that receives the value: a big operator whose bound names its parameter (`SUM`, `PROD`, `BIG MAX`, `BIG MIN`) needs its static argument written in every clause form, as `SUM[\ZZ32\][j <- 0#n] f(j)` (row 731); a plain-bounded one takes its bound, or the reduction's expected type where the bound does not fit. Walk (core gives the order) instantiates it at the value's declared type: a local variable's, or a top-level or local function's return type, also where the clause form ends a block; a method's return type, a field, a top-level variable, a parameter and an assignment do not direct it. Else at the join of the elements' run-time types, which it collects first; where the join is outside the bound, the parameter stays open and each `+` runs at its operands' types. An element that converts to the instance is converted; any other stops in `__bigOperator`, "body param 1". With no declared type, an empty `SUM` gives the integer 0 and an empty `PROD` the integer 1 (row 716); a nested clause form is built at its elements' run-time types (rows 20, 717); a written static argument that is not a number type ends an empty or filtered `SUM` in `CastError` (row 436). `SUM e` over a collection needs no static argument. **Corrects:** inference from the body's type, as in Scala or Haskell; an empty `RR64` sum as 0.0. **Prevents:** an unwritten `SUM` in code that must compile (the model's flat program writes `SUM[\ZZ32\]`); relying on a method's return type to type walk's reduction. **Old:** 25, 44, 24 (the reduction's part). **Record:** F-59, F-228, F-221, P-78; quiz B.7 grades `SUM` outdated.
- **R2. A reduction without an identity lifts to `Maybe[\R\]`.** `BIG MIN`, `BIG MAX` and `BIG //` extend `AssociativeReduction[\R\]`: its `simpleJoin` takes and answers `R`, and every `lift` takes `R`. Walk refuses at load a reduction that declares `simpleJoin` at `Any` or with untyped parameters, and one with static parameters stops at its first join. A static argument that names the lifted type is `Maybe[\R\]`. **Corrects:** the team's `AnyMaybe` and its `Any`-typed `simpleJoin`, which the team's tests copy. **Prevents:** declaring a new reduction on the model of a team test. **Old:** 48. **Record:** F-144; `ProjectFortress/tests/HeapTest.fss`.

### 6. Implementation limits (2 rules)

- **L1. Walk runs programs that the checker refuses, because it has no static types until it runs the checker after the switch-over (P-12).** So walk chooses coercions by value (N3), gives numerals and inferred parameters run-time classes (N2), gives an argument no expected type (S2), runs a dotted call that breaks a method's condition (S3), and takes a `Maybe` as an `if` condition: a `Boolean` by its value, an object named `Just` as true and one named `Nothing` as false, any other value refused, "If clause did not return boolean". The specification and the checker take only a `Boolean`. The compiled path's own limits until the switch-over (the bound `Object`, the compiler's prelude, the code generator's walls) are in `compiler.md`. **Corrects:** an interpreter run as proof that a program is well typed; Python's or JavaScript's truthiness; the team's walk, which took every object but `Just` as false. **Prevents:** writing walk-only code where the compiled path must run it. **Old:** 50, 20 (its compiled half, as a pointer). **Record:** P-12, P-59, F-239; `SKILL.md`, "The phases"; quiz trap 13.
- **L2. Write every parameter type; a return type may be left out only where the api gives it.** The compiled path refuses every parameter written without a type, of a top-level function, a method or a local function: "Missing parameter type for" and its name. Walk runs such declarations, except a method that implements an abstract declaration, which stops at its first call (row 405). A component's function that leaves out its return type takes it from the exported api's declaration at the function's own parameter types, and from none where several fit. **Corrects:** the components chapter, which promises inference of every left-out type, and Scala's local inference. **Prevents:** untyped parameters in code that must compile. **Old:** 54, 53. **Record:** F-266, F-254; `Specification/appendices/changes.tex`, "The type of a parameter that a declaration leaves out".

## Candidates outside the old part

Not in the old part, so not in the 23. The judge decides by the admission test; each needs its evidence of a mistake before it takes space.

- **C1.** The integer and rounding rules of POSITIONS P-66 to P-75: `round` on an exact half goes to the even integer (P-67); the float types' `floor` and `ceiling` keep their float type (P-68); `LSHIFT` and `RSHIFT` (P-69); `narrow` keeps the low 32 bits (P-72); `NN32` coerces into `RR64` implicitly (P-75). Java's defaults differ on each. `library.md` holds only the wrapping operators and the `RR64` conversions.
- **C2.** Neither the compiled checker nor walk's load check checks the overloads of operators named by symbols, nor `SUM` and `PROD` (row 584; F-80, F-81, F-142); P-155 orders it built before the switch-over. A worker who adds an `opr +` overload expects a check.
- **C3.** Walk's numeral gaps that P-76 lists: a numeral that walk matches as a `ZZ32` in a `typecase` or an overload (row 79), a numeral at an `NN32` or `NN64` binding (row 454), a numeral beyond `ZZ32`'s range at an `RR64` binding (row 443). Each fits N2 as a clause.
