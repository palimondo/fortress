## 3. What the specification settles, and how

It settles the item twice over, and in the direction of the trial patch.

1. **`shift` is a functional method of ℤ.** `Specification/basic-lib/basic-integers.tex:695-702`: `shift(self, k: IndexInt): ZZ`, "The result of `shift(x,k)` is ⌊x·2^k⌋ … positive values of k shifts the bits to the left, and negative values of k shifts the bits to the right." The explicit `self` makes it a functional method, called `shift(x, k)`, not `x.shift(k)`; the team's own dormant draft has it in exactly this form beside `even` and `odd` (`Library/incomplete/basic/Fortress.Number.fsi:162`, `:172-173`). Option 2 of `REPORT.md` section 5 (a dotted method) and option 3 (another spelling) are therefore against the specification's form, and option 4 (leave it undeclared) is against Pavol's decision. The option set had one member consistent with both, and it is the trial.

2. **A parameter named `shift` in the library is then a static error, so the parameters must be renamed.** `Specification/basic/declarations.tex:426-431`: "It is also a static error for multiple declarations with overlapping reaches to declare the same name in the same namespace unless the declarations are overloaded or one declaration shadows the other." `:435-436`: "The reach of a functional method declaration is the component containing that declaration", which for `shift` on `ZZ` is `FortressLibrary`, the component that also holds `trait Range`'s `shiftLeft(shift: I)` (`Library/FortressLibrary.fss:3668-3671`). `:459-461` gives a parameter its own reach inside that component, so the reaches overlap. The list of permitted shadowing at `:476-529` admits a keyword parameter (`:508-511`), `self` and `result`, and fields or dotted methods; a positional parameter is not on it, and `:533` closes the list: "No other shadowing is permitted in a Fortress program." A variable and a function are not overloaded. So within `FortressLibrary` alone the collision is a static error under the specification, independent of the implementation. For the importing components (`RangeInternals`, `List`, and every program) `:454-456` gives an imported declaration the reach of the importing component, which is the reading the shared implementation enforces (`ProjectFortress/src/com/sun/fortress/scala_src/disambiguator/ExprDisambiguator.scala:745-763`, `checkForShadowingVar`, which rejects a variable whose name is any variable or function in scope). ## 1. Finding 1, the refusal ground: upheld

**What is true.** `BigNum.shiftLeft` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/BigNum.java:237-250`) bounds the count at `:243` (`if (v > Integer.MAX_VALUE) throw Int.overflow();`) and then calls `u.shiftLeft((int) v)` inside a `try` at `:244-249`, translating the `ArithmeticException`. The JVM's `BigInteger.shiftLeft` allocates the shifted magnitude before its range check throws, so for `3 << 2147483647` about 268 MB is asked for first. The interpreter's launcher gives the JVM `-Xmx256m` unless `JAVA_FLAGS` is set (`bin/fortress:28-29`), and the harness gives it 768 MB (root `build.xml:131`, `junitMem`, used by the `junit` task's `maxmemory` at `:1181`; `probes/harness-one.sh` copies that as `-Xmx768m`). Measured by the skeptic on the landed tree: under `bin/fortress` with `JAVA_FLAGS` unset the gated test dies at `IntSemanticsRungI.fss:93` with `java.lang.OutOfMemoryError: Java heap space` (`probes/skeptic/test-default-heap.txt:1-3`), and prints `PASS` without that line (`probes/skeptic/test-default-heap-no93.txt`); the same shift is `THROWS IntegerOverflow` at 768m and 4g (`probes/skeptic/SkBigAlloc.txt:6-10`) and an `OutOfMemoryError` at 256m (`:1-4`).

**Why it is refusal-grade.** Three reasons, any one enough. `record.md` FACTS line 2 (`record.md:10`) and `REPORT.md` section 4.4 (`REPORT.md:71-73`) claim an unrepresentable left shift raises "a catchable `IntegerOverflow`", unconditionally; it does so only above the launcher's heap, and a claim that holds only under the shared prefix's `JAVA_FLAGS="-Xmx4g ..."` is not a fact about the tree. An `OutOfMemoryError` is a `java.lang.Error` that no Fortress `catch` and no harness expected-failure sees, so the gated assertion `:93` is a red at the tree's own default that the gate cannot show. And a runtime that allocates 268 MB to learn that a shift does not fit, when the answer is one `bitLength()`, is the wrong shape for a language whose specification says overflow "throws an `IntegerOverflow`" (`Specification/basic/operators/opr-overview.tex:154-155`, read with `:140-170`).

**The repair, and why it is exact.** The skeptic's one line after `:243`, `if (u.abs().bitLength() + v > Integer.MAX_VALUE) throw Int.overflow();`, trialled in a scratch overlay (`probes/skeptic/fix-trial-patch.txt`), makes the unmodified test print `PASS` at `-Xmx256m` (`probes/skeptic/fix-trial-default-heap.txt`).
