# Extending Fortress's syntax: lessons from the APL ladder

Between 2026-09-11 and 2026-09-15 an APL was written as a sub-language of Fortress: a feasibility study (`apl-probes/REPORT.md`), six rungs of Stefan Kruger's "Learning APL" climbed chapter by chapter inside `apl⦇ … ⦈` (`apl/rung-1` … `apl/rung-6`), a port of a 25-line flat-style microGPT (`apl/microgpt/`), and a rewrite of the calling convention for that program (`apl/mg/`). The purpose was never APL: it was to find where the specification's syntax-extension mechanism and the library give out, and what exactly gives. What follows is what a later DSL writer meets, in the order they meet it; the evidence is ledger rows 179-287 and the probes named beside each claim.

The mechanism runs and it carried a real language. The tooling around it is the worst in the tree, so plan the work as a sequence of small bisecting probes, not as one grammar debugged at the end.

## Declaring a grammar and importing it

The form that is implemented is FOOL'09's `grammar … end` inside an api. The specification's own normative form, `syntax OpenExpander Id CloseExpander = Expr`, is not implemented and `syntax` is not a declaration keyword (row 267, `apl-probes/b12_spec_syntax_form.fss`); chapter 27 is a one-sentence stub pointing at the paper, so the only description of the live spelling is `Syntax.rats`, 434 lines. Read it first: the shipped `transformer/` examples are written in a dead pre-`=>` spelling that fails to parse, and the build never runs them — `SyntaxAbstractionJUTestAll.java:36` and `:39` glob the top directory only, and `build.xml:1260` hangs off `testNightly`, so the green suite says nothing about syntax abstraction either way (row 268).

A grammar may live only in an api (row 269), so a sub-language is always three files: the grammar api, a stub component exporting it, and the using component (`apl-probes/e30_aplg.fsi` + `e30_aplg.fss` + `e30_apl.fss`; at scale, `apl/base/AplSyntax.fsi` + `AplCore.fss`). They need not share a directory, but `FORTRESS_SOURCE_PATH` replaces the shipped four-entry default rather than extending it (row 190).

Three spellings cost a run each. An api that gives one of its own nonterminals an AST type must `import FortressAst.{...}`, or every annotation in it is undefined, with no diagnostic naming the import and nothing in the specification mentioning it (row 271, `gap-ledger-probes/apl-merge/f01_noast*`). A nonterminal may not be named with a word of two or more uppercase letters, because such a word is an operator: `WE` is a bare `Syntax Error` at the name (row 193, `NodeUtil.java:1460-1477`). And the brackets are not privileged — `⦇` U+2987 and `⦈` U+2988 were chosen because they appear nowhere in the parser, operator table, library or specification (row 277); any glyph run free of the macro language's special characters works.

The tax is the edit-run loop. Two Rats! parser generations happen at run time, about forty seconds cold, so `javac` on the classpath is a hard requirement for any program that uses a grammar (row 266). `fortress parse` checks a grammar api in about 0.6 s and is the only fast check there is, but it always fails on a component that *uses* an expander, with an empty message, because it does not run the syntax-abstraction phase (row 191).

## What a gap can and cannot be

A gap is a pattern variable typed `Id`, `Expr`, or one of your own nonterminals, and it is the only way use-site text reaches the expansion. `Expr` gaps work, subject to the greed below. The `Id` gap is where the design gives out.

An `Id` gap works in exactly one position: spliced into a lambda parameter, where it binds an ordinary Fortress variable that later statements of the sub-language read under their own spelling, and that host code in the same block reads as itself (row 201, `apl/v1-probes/q01_bind.fss`, `q06_block.fss`). It cannot be read as a variable reference anywhere: bare it dies in the template parser, and off an expression's first token it dies in the disambiguator, because `Transform.forVarRef` looks a `VarRef`'s id up in the hygiene environment instead of recurring into it (rows 182, 202). It cannot stand left of `=` or `:=`, where the template parser's `AssignLeft` production receives a null text (rows 186, 196) — four spellings across two rungs before the design moved. And it refuses `_` (row 242).

Repetition has exactly one legal use. A `*`- or `+`-bound gap splices with `**` into a list literal that carries an explicit static type; drop the `[\ZZ32\]` and the element type is computed from the runtime class and unification fails (row 272, row 20's mechanism through an expansion). Without the splice the same gap crashes the generated parser with a raw Java cast error and no Fortress diagnostic (row 273, `ComposingSyntaxDefTranslator.java:489-490`, conversion commented out beneath). A bound `?` gap is `not supported now`, with twenty lines of implementation commented out under the throw (row 274, `:508-509`) — which is why an elided axis `m[1;]` needs a production of its own (row 197) and why a reduce slash cannot be made optional inside one production (row 180).

The deepest constraint: a transformer is a template, not a computation. `case … of` dispatches only on `Cons(h,t)` and `Empty` over a repetition-bound list, never on an AST constructor; asking what an `Expr` gap *is* gives `Unrecognized constructor name: IntLiteralExpr` (row 275, `TemplateVarRewriter.java:122-147`, `Transform.java:752-762`). The grammar can count what a repetition matched and nothing else, so every decision that depends on a value belongs in the expansion — the feasibility grammar carried each glyph out as a `String` and dispatched in the using component (row 282), and the later bases expanded straight to typed calls.

## Hygiene, and the two ways a name can meet its binder

Hygiene is implemented, and it forbids the obvious trick: a binder written as a literal identifier of a template is gensymmed, the free name of another rule's template is not, so the two never meet, and an expander-written preamble leaves every reference template unbound (row 204, `apl/v1-probes/q08_cell.fss`: `Variable m is not defined.`). A name and its binder can meet in only two ways — both through a gap (row 201), or both from the use site's own declarations (row 206).

The second is what everything here is built on: free identifiers inside `<[ … ]>` resolve at the use site, not in the grammar's api (row 270, `apl-probes/b05_hygiene.fss`). The grammar may name `aplDy`, `rows`, `gather`, `pow`, and the using component supplies them, so a grammar api never exports an operator across an api boundary — the standing workaround for row 30. The host may also declare the sub-language's variables outright, and then both sides see every update across use sites (row 206).

The cost is the error story. An unbound free name in a template is a static failure before anything runs, reported against the grammar api at line 1 column 2 (row 243); so is a type error inside an expansion (row 213); so is a missing overload reached through one, which arrives as a host unification error at the same span (row 230). A use that matches no production is not reported as a syntax error at all — the keyword is read as an identifier, `Variable apl is not defined` (row 229) — and a reported column is a furthest-failure position, not the offending token (rows 242, 261). The paper requires errors at use sites to name the use site; this implementation does the opposite, so a sub-language of any size is debugged by bisection.

Two positives close the section: a typed lambda written whole inside one template works and dispatches, hygiene renaming binder and references together, and it selects an arrow-typed overload as a hand-written lambda does (row 285, `apl/probes-4b/y02_lambda.fss`; the negative control, binder in one template and reference in another, is `y04_split.fss`); and a template can assign, if the left of `:=` is a literal name of the template rather than a gap (row 205).

## The closed name sets, and why

Since a name cannot be read through a gap, a sub-language that wants `v` to mean the user's `v` must spell the name: a character class of letters concatenated right-recursively into a `String`, as the shipped `Xml.fsi` builds attribute names, and the class must be letter-then-letter-or-digit or the `9` of `9 2 6` is read as a name (row 194).

A terminal that is a valid identifier becomes a keyword of the *whole language*: it is made a `KeywordSymbol`, every user-grammar keyword joins `FORTRESS_KEYWORDS`, and `Id` then excludes it, so writing `v` as a terminal makes `v` unreadable as a name everywhere, templates included; the character class `[v]` reserves nothing (row 203, bisected by `q04`/`q05`). The same fact prices the entry form: a bare `apl` keyword would reserve that word program-wide, while `apl⦇` is not a valid identifier.

So each name is one grammar alternative. The microGPT rung alone added ninety-six name lines — sixty-five array names, twenty-six strand names, five function names — and 124 of the focused base's 197 alternatives are name lines. Three costs come with it: a name outside the set is a `Syntax Error` at the use site rather than a run-time value error; a strand rule over every name merges two names on consecutive lines into one strand, so rung 5 needed a third, disjoint set for strand elements (row 253); and a name may carry a digit after a capital and an underscore, but the underscore's class must be written `` [`_] `` — a bare `[_]` is a Syntax Error at the character — and a name with an underscore must stand above its prefix (row 257).

Names must also survive the host: its keywords are unusable (`value`, `at`, `type`, `label`, `wrapped`; eighty-six in all, rows 8, 262), so is every name the using component imports (`Variable rows is already declared`, row 262), and there is no shadowing anywhere, across five kinds of name (rows 92, 147, 167, 168). On the lambda route a name binds once per block, a second `←` being a nested parameter of the same name (row 207); the way out is to bind a mutable *value* instead, which the library's arrays are — `v[3] ← ¯1` became an in-place put and assignment stopped being rebinding (row 224).

## PEG greed, and where rule order decides

The generated parser is a Rats! PEG: ordered choice, no re-entry for a shorter match. Everything below follows from that.

An undelimited `Expr` gap swallows any host-known operator that follows it — `⍎v ≡ 1 4⍴⍎v` parsed as one `EQV` application inside the first gap (row 183) — and delimiters do not help, because the closing delimiter is not a barrier the gap can see: a rule `( a:AplE , b:AplE ) ⍴ r` never matches once a catenate rule exists, and only atom-typed gaps make it match (row 235). Hence the rule for separators, learned twice: a host `Expr` gap may be followed only by a terminal outside the host's operator table, or by one of your own nonterminals. A rule `y⦇ a:Expr ⋄ b:Expr ⦈` never matches, `⋄` being the host's DIAMOND, and `∘` behaves the same, while `⍤`, in no host table, separates cleanly (row 284, `apl/probes-4b/y01_named.fss`).

Inside an ordinary nonterminal, order decides: the first alternative that succeeds wins, so a specialised rule must stand above the rule it refines. A parenthesised-left rule must stand above the plain rule for the same glyph or the atom rule's own `( … )` eats the parenthesis first — and the failure is not a syntax error but a *wrong parse* that reaches the library and surfaces as a missing overload against the grammar api (row 236); the folded `+/l×r` must likewise stand above the plain `+/v` (row 287).

Between alternatives of one macro *bracket*, order does not decide at all: the closing bracket makes the parser backtrack, so a shorter alternative above a longer one still lets the longer match (row 287's positive half). Two bracket facts cost a worker four false diagnoses: a use of the expander cannot be an operand of a juxtaposition — `("" apl⦇ 5 ⦈)` is `Variable apl is not defined`, while the same use as an argument or a binding's right-hand side parses (row 239) — and nine uses in one expression do not parse where eight do (row 261).

What the PEG gives free is worth as much: APL's strand notation needs ordered choice and nothing else, `AplStrand` being right-recursive over the host's `LiteralExpr` and backtracking at the first glyph; and right-to-left evaluation falls out of the *shape* of the productions — a dyadic rule takes a strand on the left and the whole rest of the expression on the right — so the host's precedence does not apply inside the brackets at all (row 282, `apl-probes/REPORT.md` §E).

## Separators, line breaks and the host's operator table

Whitespace in a production is optional at the use site: a literal space and an explicit `SPACE` both become the host's optional-whitespace nonterminal `w` (row 179), which is what lets a book's examples be copied in verbatim. Nothing can *require* a space, and `#` after a symbol deletes that optional `w` rather than demanding one (row 212); its real uses are gluing a name's characters and gluing a high minus to its digits.

Because `w` crosses line breaks, a line break does not separate two statements whenever the next line can extend the phrase above. The ladder widened this four times: by a numeral (row 228), by any dyadic glyph (row 238), by the operand of a function (row 241), and by two ordinary names (row 253). Three remedies were used: an explicit separator terminal (`⋄`); a comment tail bounded by the end of line, which needs `#` on *every* symbol or the optional whitespace looks past the newline and the comment swallows the statements below (row 227); and a non-consuming `AND NEWLINE` lookahead for a form that ends at the line (row 209). A form with no terminator at all parses and then silently runs on (row 210). A line break *inside* a production is the opposite of optional: it is a required line break at the use site, so a long rule must be written on one long line (row 244). Statements themselves are free — `⋄` as an ordinary terminal, or a line break in the production, which becomes the host's own `br`, so `;` works in its place (row 208).

The host's operator table is the other half of the design. APL's functional-symbol block U+2336-U+237A is not an operator character set, by specification as well as implementation — the operator characters are enumerated in `appendices/operators.tex` and the only U+23xx there are `⌈ ⌉ ⌊ ⌋`, so adding one means regenerating `Operators.java` from `operators.txt`, that is, changing the language (row 278). Inside a sub-grammar those glyphs are ordinary terminals, as is any character class over them, because a generated Rats! parser matches raw characters and never goes through the Fortress lexer (row 276). But the *shared* glyphs are usable at the ordinary level and should be: `× ÷ - + * ⊖ ⊂ ⊃ ≡ ≢ ∘` each take a prefix and an infix declaration, so APL's monadic/dyadic split is ordinary overloading (rows 216, 279); `≠ < > ≥ ∧ ∨` take infix declarations returning an array rather than a `Boolean` (rows 218, 233); `⌈ ⌊` are enclosers, declarable only as bracketing operators with unparenthesised parameters (rows 216, 280); `,` takes neither fixity. A glyph is therefore reachable two ways, and the ladder used both.

The macro language's own special characters — `space : ? # + * [ ] | _ { }` and the backtick — need a backtick escape in a *terminal*, though not inside a template (row 222), and `\` and `.` refuse the escape entirely, being plain items (row 250). That escape is the nastiest trap here: the preparser reads a backtick as an opening quote and rejects the api, unless an APL glyph stands above it — whereupon the preparser cannot tokenise the glyph, its token loop stops, and the delimiter check is silently skipped from there on (row 181). The portable form of the same trick is a `**` above the escape, which is why the shipped `Regex.fsi`, which backtick-escapes ten characters, is accepted at all: it disables the checker on its own line 93 (row 211).

## What a template can and cannot expand to

It can expand to a host operator application, prefix or infix, characters unescaped (row 222); to a call; to a typed lambda written whole (row 285); to an assignment to a literally named `var` (row 205); to a statically typed list literal with a `**` splice (row 272); and to a block of statements. It cannot expand to a binding or an assignment whose left side is a gap (rows 186, 196), nor mention a name the use site does not have (rows 204, 243).

One silent failure is worth the rest of this section. A template that writes the host's caret drops its right operand without a word: `<[ (1.0 (l)) ^ (r) ]>` expands to `1.0 (l)`, so `apl⦇ 10*10 ⦈` evaluated to `10.0`, the causal mask came out `-10` instead of `-1E10`, and every loss of the model moved from the seventh digit — three runs before the cause was found (row 286, `apl/mg/checks/model_run.out.1`). Through a one-line glue function `pow(b: RR64, e: ZZ32): RR64 = b^e` the same rule is exact. Nothing in six rungs had put a host infix operator other than `+ - × ÷` in a template, which is why nothing caught it. The rule: no host caret in a template, and treat any other host operator there as unproven until a probe prints its value.

## Function values, the frame stack, and why it was replaced

APL's direct functions take implicit arguments `⍺` and `⍵` and recur through `∇`. None can be a template-written binder, because hygiene renames a template's own binder and a reference written by another rule never meets it (row 204), and the host refuses a nested lambda re-declaring an enclosing name (row 207). The universal base answered with a frame stack: every APL function value, glyphs included, is a zero-parameter lambda over one mutable stack; `aplCall(f, ⍺, ⍵)` pushes, calls, pops; `⍺ ⍵ ∇` are frame reads; and APL's rule that `⍺ ⍵` are never inherited comes free (row 245). It is the only shape that survives nesting, and it carried two chapters of the book, glyphs as first-class values included (row 234).

It cost three things. Everything on that route is untyped — `() -> Any` in, `Object` out — because an overloaded family whose declared *result* is `Any` does not dispatch at all, however exactly the parameters match (row 240), leaving `Object` the only declarable result and one contested row about whether the interpreter should accept a tuple declared that way (row 258). It is slow where the call is per element: 3.5× a direct `+` on scalars, unmeasurable on 100-element vectors (row 245), but 3.8× on a 16×16 product, which pays 8192 frame pushes (row 256). And it is unsafe under the language's implicit parallelism: tuple elements are evaluated in parallel in separate implicit threads, so `¨` over a strand of three arrays pushed three frames onto one stack and the model died at pool size 4 (row 265); the base sequences the two sites it controls and the limit stands everywhere else.

The focused base dropped the mechanism for the one program that mattered. Its single principle: no function value crosses a rule boundary untyped — a function appears in APL text only as a *name*, resolved at the use site to a typed host declaration (rows 270, 285) and picking its overload by arrow type (row 171), or as a derived function one rule expands whole. That removed the `Any`, the `Object`, the frame pushes and the race together. What it gave up is real: dfn bodies, `⍺ ⍵ ∇`, guards, dops, glyphs as values — two of the six rungs' subject. The generalisation: if your sub-language needs user-written functions with implicit arguments, the frame stack is the shape that works, and it is untyped, about 3.5× per call, and needs every parallel-evaluated group sequenced by hand; if the programs are known in advance, spend the rules on them and keep everything typed.

## Rank in the type

The first APL library carried rank as run-time data — one `value object AplArr(shape, data)`, every primitive dispatching on a string. It worked and was retired after two rungs, because it was an interpreter nested inside the interpreter and taught nothing about Fortress (`apl/README.md`; its probes survive as `apl/v1-probes/`, cited by the mechanism rows).

The replacement put rank in the type: a scalar is an `RR64`, a vector a `Vector[\RR64,s\]`, a matrix a `Matrix[\RR64,r,c\]`, a rank-3 array an `Array3` (row 246). That buys a great deal from the host. Rank overloading works with the `nat` inferred from a runtime-built array (row 214); overloading on the *index's* rank works too, so "a scalar index lowers the rank, a vector index keeps it" is dispatch and never a shape test (row 225); a six-line view object over a runtime-sized matrix is a real `Vector` where the library's own slice is not (rows 226, 55); `requires` contracts fire through a macro expansion as catchable violations, so APL's LENGTH, INDEX and DOMAIN ERROR are contracts on the declarations (rows 220, 231); a library array is already a full generator with no mix-in (row 221); and the shipped `opr DOT` is already APL's inner product in all four rank pairs (row 254).

It costs one declaration per rank combination — thirty-six for one chapter's bracket algebra (row 225) — and has two hard edges. The one primitive whose result rank is a run-time value, dyadic `⍴` with a computed left argument, cannot be fixed in the grammar; reinstating it means a sum type over the ranks plus a `typecase` at the head of every primitive, that is, re-entering the whole design through one glyph (row 223). And an element type outside the numeric tower cannot join the family: a `Char` array beside an `RR64` one is rejected, `Vector` demanding `T extends Number` and both being `Rank1` with nothing excluding between them (row 219). Stated once: rank in the type buys the host's dispatch, contracts, generators and parallelism; rank as data buys a computed rank and nested values. These programs wanted the first, and it is also the fast one.

## The cost facts

A direct rule reaching a typed library entry costs 3.8× less than the same function through the general call — 12.97 s against 49.32 s for 200 products of 16×16 matrices (row 256). That number is the argument for the direct rules of rungs 1, 3, 5 and 6, and for the focused base entire. One frame push is 3.5× a direct `+` on scalars and unmeasurable on 100-element vectors (row 245): the cost appears exactly where the call is per element. A rule should delegate rather than loop — the shipped `DOT` is itself 1.46× a hand-written triple loop in the same library (row 256). Parser generation is the fixed tax: two Rats! generations per run, about forty seconds cold (row 266), with no fast check for a component that uses an expander (row 191).

The end-to-end number settles the approach. The focused base writes 19 of the program's 25 Dyalog lines as APL text over an existing Fortress vocabulary; its forward pass agrees with the hand-written program intermediate by intermediate to 0.0, its 40 checks pass at both pool sizes with identical values, and its cost is the hand-written program's — 439 s against 528 s and 444 s at pool size 1, 254 s against 263 s at pool size 4 (`apl/mg/REPORT.md`). The universal base's 1.12× and 1.49× on the same checks were the frame stack and its sequential general route. A sub-language's expansion cannot be better than the vocabulary it expands to, and it need not be worse.

## The walls

**Nested arrays.** The flat carrier's wall is the element type: no element can be an array, and a boxed element is a new *representation*, not a new function — one trait and two variants replace one carrier, and all sixty-five top-level functions are typed in the old one (row 199, where the skeleton runs, so the price is measured and not argued). The ladder avoided nesting instead: a strand of arrays became a Fortress tuple, which dispatches on arity, may be an overloaded family's result type, holds three different ranks, and binds through a lambda of that many parameters (row 252). That works where the nesting is one level and known, which is where it was; rung 8 was not built for this reason.

**Implicit arguments.** `⍺ ⍵ ∇` cannot be binders written by a template (rows 204, 207). Either a frame stack with everything it implies, or no user-written functions inside the sub-language. There is no third answer in this implementation.

**Characters.** A `Char` array cannot join the rank-overloaded family (row 219), so characters cost a parallel set of names for every primitive (`aplShowC`, `aplTallyC`); nine of one chapter's examples and all the character material stayed out of scope. A string literal has no `\u` escape either, so a glyph must stand in the source — which works, the tree being read as UTF-8 (row 200).

**And the diagnostics**, which no design choice avoids: every static error inside an expansion points at the grammar api's line 1 (rows 213, 230, 243), a use matching nothing is not a syntax error at all (row 229), and reported columns are furthest-failure positions (rows 242, 261).

## Where the record is thin, or disagrees with itself

The ledger and the ladder's reports agree about the mechanism, and where they differed the ledger's row carries the correction rather than the report: rung 2b concluded that a sub-language comment may only follow the *last* statement of a block, true only of a tail spelled `NOT ⦈ _` and corrected by row 227; and `apl/base/AplCore.fss`'s own header says a top-level `opr` declared in an api does not reach an importing component, which row 215 falsifies — row 30 is about library generic code, not a user call site. Four APL rows cited the feasibility study's table as though it were merged before it was; it is now rows 266-283. One count is off in the review that classified the rows: it prices the syntax-extension worklist item at twenty rows and its own list names twenty-one.

Two thin places. Nothing here was run on the bytecode-compiler path — every row is the walk interpreter — and the syntax-abstraction tests are not in the green suite at all (row 268), so the suite says nothing about this mechanism either way. And the one contested claim in this area is row 258's type half: a tuple returned as a declared `Object` result, which the specification does not admit and the walk interpreter accepts. The paper the rows argue with (`research/extracts/growing-a-syntax.md`) agrees on hygiene and the lambda binding, disagrees on substituting a pattern variable into any term position and on use-site errors, and is silent on the preparser, keywords, statements and whitespace — four of the six things that actually cost time.

## The shape that came out of it

The design the ladder ended with, stated so it can be copied: no function value crosses a rule boundary untyped; a function appears in the sub-language only as a name resolving at the use site to a typed host declaration, or as a lambda one rule writes whole; every rule expands to one typed entry of a vocabulary that already exists and is imported unchanged; rank stays in the type; the glue library holds only the patterns that vocabulary does not spell; the names are a closed set, one grammar line each; and the separators are the sub-language's own glyphs, chosen outside the host's operator table.

In numbers: 446 lines of grammar, 197 alternatives of which 124 are name lines and 73 are rules, beside 39 lines and eleven declarations of glue — against the universal base's 899-line grammar and 2,343-line library (`apl/mg/REPORT.md`). What it buys is that the expanded program *is* the target program, so its cost is the target's cost, its numbers are the target's numbers to the last bit, and polishing the vocabulary polishes the notation.

The shape is available to any sub-language whose programs are known in advance. A sub-language meant for programs not yet written pays the universal base's price instead, and the rows above say what that price is.
