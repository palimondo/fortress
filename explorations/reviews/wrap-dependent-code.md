# What the code that relies on wrapping should become

## 0. The question, and what this note read

Under `walk` (the interpreter), arithmetic on the fixed-width integers `ZZ32` and `ZZ64` *wraps*: when the true answer does not fit in 32 or 64 bits, the machine keeps its low 32 or 64 bits and throws the rest away, so `ZZ32` maximum plus one comes out as the `ZZ32` minimum. The specification says such an *overflow* (an answer outside the type's range) throws `IntegerOverflow` (`Specification/basic/operators/opr-overview.tex:154-155`, `:195-196`). Pavol decided that `walk` follows the specification (ledger row 379; `explorations/coordinator/POSITIONS.md:88`). Rung O built it in a shadow: the ten arithmetic *natives* (the Java methods the interpreter calls for `+`, `-`, multiplication, `DIV` and unary `-`) of `Int.java` and `Long.java` raise `IntegerOverflow`, and 11 interpreter tests then stop, because library code or the test itself relies on wrapping (`explorations/compile-ladder/rung-walk-overflow/REPORT.md` §§ 1, 4). This note asks what each of those pieces should become.

Read for this note: the specification's operator and integer chapters, its operator appendix and its binary-word chapter; `Library/` (the interpreter's library, including the team's drafts under `Library/incomplete/`); the compiler's prelude `ProjectFortress/LibraryBuiltin/CompilerBuiltin.*` and its natives; the interpreter's natives; `Papers/`; the git history; rung O's `REPORT.md` §§ 1-4 and `probes/`; protocol § 6; `FACTS.md`; `repo-internals.md`. Not read: rung O's `REPORT.md` § 8 and `JUDGE.md`. Seen by accident: ledger row 403, which sits two rows below row 348 in the ledger, ends with one sentence naming the judge's three candidate routes; it was read while reading row 348. The list in section 1 was built from the sources and is wider than those three.

## 1. Every way the language and the library offer

Three words first. *Wrapping* arithmetic keeps the low bits of the true answer, as described above. *Checked* arithmetic gives the true answer or throws `IntegerOverflow`. *Saturating* arithmetic clamps: an answer above the maximum becomes the maximum, one below the minimum becomes the minimum.

Code meets overflow with one of two needs. Some code *means to wrap*: it wants the answer modulo 2^32 or 2^64, as a hash function or a random-number generator does. Other code *must avoid overflow*: the answer it wants fits in the type, but a step on the way does not, or the code wants to know when an answer would not fit. Each way below says which need it serves and where it stands on each path.

### The library's own ways

1. **Compute where nothing can overflow, then reduce on purpose** (means to wrap). The Mersenne twister in the same file as the failing generator holds its 32-bit words in `ZZ64`, and its seeding generator multiplies there, where a 31-bit constant times a 32-bit word cannot leave 63 bits, and then keeps the low 32 bits with an explicit mask: `state := (1812433253 (state BITXOR (state RSHIFT 30)) + 1) BITAND 4294967295` (`Library/Random.fss:336`, again at `:344`; the twister itself masks its words at `:278`, `:286`). Its documentation comment names the reason, "Its seed vector is of `ZZ64` due to the overflow mechanism" (`Library/Random.fss:350-351`). This runs the same on both paths and never overflows. It needs a type twice as wide as the answer, so for 64-bit work it needs the unbounded `ZZ` (way 9).
2. **The named truncating conversion** (means to wrap). `narrow` keeps the low 32 bits of a `ZZ64` on both paths, decided by Pavol for row 346 (`POSITIONS.md:76`; `ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Long.java:248-252` is `(int) x`; the compiled body `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss:659`). So `narrow(widen(c1) widen(n) + widen(c2))` is an exact 32-bit wrap with no overflow anywhere. `ZZ`'s `narrow` and `widen` (to `ZZ32` and to `ZZ64`) also keep the low bits under `walk`, `BigInteger.intValue` and `longValue` (`Library/FortressLibrary.fss:891-895`; `ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/BigNum.java:286-296`); that truncation is not a decision on record, only the tree's behaviour.
3. **Reorder the computation so no step leaves the range** (must avoid overflow). `meetingPoint` in the range library "tries to avoid overflow" by stepping from one bound towards the other instead of multiplying strides (`Library/RangeInternals.fss:58-79`). In the compiler's prelude Steele wrote `floorAverage` and `ceilingAverage`, which compute the average of two integers from bit identities "without overflow" (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss:655-658`, `:746-749`; commit `4180a0dac`, 2012-05-18, "new methods floorAverage and ceilingAverage do not risk overflow").
4. **Bit operators in place of arithmetic** (either need). `BITAND`, `BITOR`, `BITXOR` and `BITNOT` never overflow, and shifts let the bits shifted out fall off silently on both paths, by Pavol's decision on row 335 (`POSITIONS.md:73`). So "the bits below position `b`" can be written `BITNOT (widen(-1) LSHIFT b)`, which touches no arithmetic operator, instead of `(widen(1) LSHIFT b) - 1`.
5. **Explicitly named wrapping and saturating operators beside checked defaults**, in the team's last library (means to wrap). The compiler's *prelude* (the library the compiled path reads today, which the one-library decision will delete at the switch-over, `POSITIONS.md:46`) gives every integer type three families: `+`, `-` and multiplication are *Overflowing* natives that throw, `BOXPLUS`, `BOXMINUS`, `BOXDOT` and `BOXCROSS` are *Wrapping* natives, and `DOTPLUS`, `DOTMINUS` and `DOTCROSS` are *Saturating* natives (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss:669-684` for `ZZ32`; the natives `ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleIntArith.java:62-82` checked, `:224-234` wrapping). Steele wrote all three families in one commit, `9ce7d8189` (2011-09-08). The spellings are the specification's reversed (row 348), and `BOXCROSS` and `DOTCROSS` are names the specification does not have. The team's own tests use the wrapping one for exactly the shapes that fail here: a multiplicative seed sequence, `intSeed := intSeed BOXCROSS intMult` (`ProjectFortress/library_tests/AverageTest.fss:123-140`, Steele, in the tree by 2012-05-22, `e177c3e2c`, a parentless snapshot), and `result := result BOXCROSS 2    (*) Overflow is ignored` (`ProjectFortress/library_tests/ShiftTest2.fss:27`, `:201`, Steele, `e6f04f2b1`, 2012-05-23). Under `walk` none of these names is declared.

### The specification's ways

6. **The wrapping operators ∔ (`DOTPLUS`), ∸ (`DOTMINUS`) and ⨰ (`DOTTIMES`)** (means to wrap). "Wraparound addition and subtraction on fixed-size integers are expressed by ∔ and ∸ … These operations do not overflow" (`Specification/basic/operators/opr-overview.tex:205-209`), and "Wraparound multiplication on fixed-size integers is expressed by ⨰" (`:172-176`). The integer chapter declares unary ∸ as well as binary (`Specification/basic-lib/basic-integers.tex:381-382`), and on the unbounded `ZZ` makes them the ordinary operators, "because operations on type ℤ never need to wrap or saturate" (`:369-370`, `:400-401`, `:416`). The parser maps the ASCII names to the characters (`ProjectFortress/src/com/sun/fortress/parser/Literal.rats:263`, `:270-271`). Not declared in the interpreter's library: under `walk` a use ends the run with "Operator ? is not defined." (row 348's probe, `explorations/compile-ladder/rung-int-conversions/probes/skeptic/skeptic-SK8Wrap.txt:3`, exit 255). On the compiled path `DOTPLUS` and `DOTMINUS` exist but saturate (way 5), and `DOTTIMES` does not exist.
7. **The saturating operators ⊞ (`BOXPLUS`), ⊟ (`BOXMINUS`), and ⊡ (`BOXDOT`) or ⊠ (`BOXTIMES`)** (must avoid overflow, by clamping) (`opr-overview.tex:174-175`, `:207-208`). On the compiled path the same names wrap (row 348); under `walk` they are not declared. No failing site needs a clamp.
8. **The checked default, and catching it** (must avoid overflow). `IntegerOverflow` is an unchecked exception (`Library/FortressLibrary.fss:1522-1523`), so code may `catch` it and take another path; a native's `IntegerOverflow` reaches a Fortress `catch` under `walk` since rung I (`FACTS.md:24`; helper `Int.overflow()`, `ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Int.java:256-259`), and the rung's test wraps the pattern in a helper, `overflows(f)` (`ProjectFortress/tests/IntSemanticsRungI.fss:4-9`). The library itself never catches it.
9. **The unbounded `ZZ`** (must avoid overflow). "Operations on type ℤ never need to wrap or saturate" (`basic-integers.tex:369-370`). `ZZ64`'s `big` converts to it (`Library/FortressLibrary.fss:770-771`), and the specification's `shift` is exact on it (row 335). Each operation then allocates a Java `BigInteger` (an arbitrary-size integer object).
10. **The binary-word layer's methods** (either need). The specification's lowest layer, `BinaryWord`, from which it says types such as `ZZ64` are to be "defined by libraries coded entirely in Fortress" (`Specification/advanced-lib/binary.tex:14-34`), spells every variant as a method: `wrappingAdd`, `wrappingSubtract`, `wrappingNegate`; `add(other, carryIn): (T, Bit)`, which returns the carry bit beside the sum; `signedAdd(other, overflowAction: () -> T)`, where the caller supplies what happens on overflow; `saturatingSignedAdd`; `multiplyLow`, `multiplyHigh` and `multiplyDouble`, the full double-width product; and `leftmostOneBit` (`binary.tex:1177-1235`, `:1510-1514`). Nothing in the tree implements it.

### Two further mechanisms

11. **Stating a property only where it is meant** (tests). The QuickCheck library has a conditional property, `cond ==> prop` (`Library/QuickCheck.fsi:408-417`), and generates `ZZ32` values by size level, levels 0-2 staying within 2^23 (`Library/QuickCheck.fss:55-61`).
12. **Precedence.** ∔ and ∸ may be mixed with each other and bind looser than ⨰, and nothing else is stated for them (`Specification/appendices/operators.tex:215-224`); when no relation is stated, "there is no precedence relationship between those two operators" (`:15-18`), so an unparenthesised mix of ∔ with `+`, `BITAND` or juxtaposition is refused, and every rewritten expression below is fully parenthesised. Every equivalence operator such as `=` binds looser than every arithmetic operator (`:390-392`).

### What is not a way

- **The unsigned types.** The specification's overflow rule covers every integer result (`opr-overview.tex:155`), so `NN32` and `NN64` do not wrap by design. Under `walk` they wrap today: their natives call `com.naturalbridge.misc.Unsigned.add`, which is a bare `iadd` (read with `javap` from `ProjectFortress/third_party/unsigned/unsigned.jar`; `ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/NN32.java:109-112`). Row 379 does not cover them (section 11).
- **The object hash.** The specification's `hash(maxval)` and `hashCode` (`Specification/basic-lib/objects.tex:60-72`) give each object a hash for hash tables; they are not a scrambling function over integers, and the interpreter's library declares neither.

## 2. The refresher: what the three kinds of arithmetic mean

- An integer in mathematics has no size. A 32-bit word has 2^32 bit patterns, and in *two's complement*, the layout every JVM uses, they stand for -2^31 through 2^31-1, the top bit counting as -2^31.
- **Wrapping** is arithmetic *modulo* 2^32 (or 2^64): two integers count as the same when they differ by a multiple of 2^32. That arithmetic is a *ring*: `+` and multiplication are associative and commutative, multiplication distributes over `+`, and every value has a negative. So every identity built only from `+`, `-` and multiplication holds exactly, for instance `(p ∔ q) ∔ r = p ∔ (q ∔ r)` for all `p`, `q`, `r`. Order does not survive: the maximum ∔ 1 is below the maximum. Wrapping is the right meaning when a program cares about the answer modulo 2^n, as hashes, random-number generators, checksums and bit masks do, and the wrong one when it cares about how big a number is.
- **Checked** arithmetic is a partial operation: every answer it gives is the true integer answer, so a program that finishes has computed exactly what the unbounded integers would. Laws such as associativity hold wherever both sides answer, but one side can throw where the other does not: `(MAX + 1) + (-1)` throws, `MAX + (1 + (-1))` is `MAX`.
- **Saturating** arithmetic never throws and never wraps, and it is not associative: `(MAX ⊞ 1) ⊞ (-1)` is `MAX - 1`, `MAX ⊞ (1 ⊞ (-1))` is `MAX`. It suits signals, pixel values and counters that should stick at their limit. In the specification the boxed operators mean "toward zero" on floats too, rounding toward zero (`opr-overview.tex:181`, `:214`), and a clamp is the representable value nearest the true answer on the side of zero, so the box family is one idea across both kinds of number.
- **The bit identities three of the library sites use.** For a power of two `p`, `p - 1` is the mask of the bits below `p`, and `-p` is the mask of the bits at and above it. For positive `p` both are ordinary integers that fit. When `p` is the sign bit alone, which as a number is the minimum, the true values of `p - 1` and `-p` do not fit, but their wrapped values, the maximum and the minimum, are exactly the masks wanted. Those sites are right *because* the machine wraps: they are modular arithmetic spelled with the ordinary operators.

## 3. What each path does today

- **`walk`, `ZZ32` and `ZZ64`.** The natives are one-line Java arithmetic that wraps (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Int.java:98-125` and `Long.java`'s twins; the wrapped values are measured in row 379). Since rung I, `GCD` and `LCM` check (`Int.java:137`, `:145`). `partitionL`, the largest power of two below its argument, is the native `Integer.highestOneBit(u - 1)` (`Int.java:212-216`), whose `u - 1` wraps inside Java whatever the Fortress operators do.
- **`walk`, `NN32` and `NN64`.** They wrap too (section 1, "What is not a way").
- **`walk` has none of ∔, ∸, ⨰, ⊞, ⊟, ⊡ or ⊠** (row 348's probe).
- **`walk` with rung O's shadow.** Eleven of 393 test files stop. A pass whose natives log each overflow and still wrap finds exactly the same eleven (`explorations/compile-ladder/rung-walk-overflow/probes/overflow-probe-summary.txt:6-16`): `HeapTest` (2 `Int$Add`, 20 `Int$Mul`), `IntMapTest` (4 `Int$Sub`, 27 `Long$Negate`), `QuickCheckTest` (8 `Int$Add`, 146K `Long$Mul`), `RandomTest` (926 `Long$Mul`), `RangePrototype` (40 `Int$Sub`), `ReflectiveQuickCheckTest` (12 `Int$Add`, 131K `Long$Mul`), `intPrim` and `longPrim` (1 `Int$Add` and 1 `Int$Sub` each), `setSum` (22 `Int$Sub`), `simpleSum` (1 `Int$Sub`), `zeno` (32 `Long$Sub`).
- **Row 146's shape.** A `ZZ64` variable set from a small numeral holds a `ZZ32` value under `walk`, so it wraps today, and overflows under rung O, at 32 bits (`explorations/compile-ladder/rung-walk-overflow/probes/Row146Width.txt:2-7`, `:11-16`). `longPrim` is that case (`REPORT.md` § 1).
- **The compiled path.** `+`, `-`, multiplication, `DIV`, unary `-` and `|x|` throw on all four fixed-width types (`FACTS.md:79`; `CompilerBuiltin.fss:669-684`); `BOX…` wraps and `DOT…` saturates (row 348, gated as the expected failure `ProjectFortress/compiler_tests/XXXBoxDotSpellingsRungW.test`); there is no `DOTTIMES` and no saturating `DOT`. The failing library bodies do not run compiled yet, because the compiled path reads its own prelude until the switch-over; after it, they throw there too (row 403).

## 4. What the specification says, under every spelling

- **The rule**, stated twice: "The handling of overflow depends on the type of the number produced. For integer results, overflow throws an `IntegerOverflow`. Rational computations do not overflow." (`Specification/basic/operators/opr-overview.tex:154-156` for multiplication and division, `:195-197` for addition and subtraction).
- **The spellings**: wraparound ∔, ∸ and ⨰, saturating ⊞, ⊟, ⊡ or ⊠, "These operations do not overflow" (`:172-176`, `:205-209`). Steele's 2012 rewrite of the prose keeps both paragraphs word for word (`Documentation/Specification/Prose/Language/Operators/operator-overview.tick:154-155`, `:172-176`, `:195-196`, `:205-209`, added in `91e71e62e`, 2012-05-28, "Spec has new directory Language/Operators").
- **The integer chapter.** `ZZ` extends `CommutativeRing[\ZZ,∔,∸,⨰\]` beside the rings of the plain and the boxed operators (`Specification/basic-lib/basic-integers.tex:196-203`); the identities of ∔ and ⨰ are 0 and 1 (`:337-341`); on `ZZ` they equal the plain operators "because operations on type ℤ never need to wrap or saturate" (`:359`, `:369-370`, `:385`, `:400-401`, `:416`). The chapter is about `ZZ`; it names no fixed-width type.
- **The same idea under another spelling**: the binary-word methods of way 10 (`Specification/advanced-lib/binary.tex:1172-1235`, `:1510-1514`), where wrapping, carry-out, a caller-supplied overflow action, saturation and the double-width product are method names on the layer the fixed widths are to be built from.
- **The precedence appendix** (way 12): ∔ and ∸ mix only with each other and bind looser than ⨰ (`Specification/appendices/operators.tex:215-224`).
- **What 1.0 said.** The published 1.0 specification (2008-03-31, `403afbe0b`; the same file is `Specification-1.0-frozen/fortress.1.0.pdf`), the version cut down to what the interpreter implemented, has no overflow rule and lists `DOTPLUS` and `BOXPLUS` only in its precedence appendix (text extracted with `pdftotext`; its one mention of `IntegerOverflow` is the object's declaration).
- **What it does not say.** Nothing in the specification tells a hash or a random-number generator which family to use; it supplies the spellings and the default.

## 5. Where it sits in the numeric tower

- The interpreter's library nests `ZZ32` inside `ZZ64` inside `ZZ` (`Library/FortressLibrary.fsi:465`, `:499`, `:537`) and `NN32` inside `NN64` inside `ZZ` (`:438`; `NN32` itself in `ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:82`). Generic code reaches integer operators only through `Integral[\I\]` (`Library/FortressLibrary.fsi:414-436`), and the range library is generic in `I extends Integral[\I\]` (`Library/RangeInternals.fss:1013`, `:1183`). So a wrapping operator the range split uses must be declared on `Integral[\I\]` and implemented by every integer type, `ZZ` included, where the specification makes it the plain operator.
- Route A (`POSITIONS.md:92`) flattens the tower into siblings, each with its own algebra, a wider type converting from a narrower one. Each fixed width is then its own ring under ∔, ∸ and ⨰: the integers modulo 2^32 and modulo 2^64 are different rings, and a `ZZ32` ∔ `ZZ64` converts to `ZZ64` first and wraps at 64 bits.
- The checked operators are ℤ's operators restricted to the range: every answer agrees with `ZZ`. The wrapping operators are a different ring, not a restriction of ℤ's, which is why they carry their own names. Saturation is not a ring at all.
- The bit arithmetic of the range split, the sparse array and the integer map lives in the modular ring by nature, since a mask is a pattern of bits, not a size.

## 6. What the library already does in the same family

- The interpreter's library, written against a wrapping interpreter, relies on the wrap only where its authors did not stop to think about it. Where they did, they wrote around overflow: the Mersenne twister's wide words (way 1), `meetingPoint` (way 3). No body of the library relies on wrapping and says so.
- The team's compiled library did it the specification's way: a checked default, a named wrapping family and a named saturating family on every integer type, overflow-free averages, and tests that spell the wrap explicitly wherever they want it (way 5). Only the letters of the names are swapped.
- Where the designers already departed from Java, on record: `+` checked where Java wraps (Steele's Overflowing natives, 2011; row 379 for `walk`); round half to even (row 329); nonnegative `GCD` (row 334); the smart shift (row 335). The one integer decision that followed Java is `narrow`, which truncates as a Java cast does (row 346), and that is a conversion with its own name, not an arithmetic operator.
- The compiled library's own parallel range split has the same problem in another form: `parloop` splits at the midpoint `z = lo+hi … (*) Danger of overflow here` (`Library/CompilerLibrary.fss:359-371`, five more at `:377-414`), written by Steele in `d535963cb` (2011-10-12), a month after he made `+` checked. His `floorAverage` of 2012-05-18 is the overflow-free midpoint (way 3), and it was never put into `parloop`.

## 7. What the peers do

Each quotation below was fetched on 2026-09-26 unless marked otherwise.

**JVM family**
- **Java.** `+` wraps silently: "If an integer addition overflows, then the result is the low-order bits of the mathematical sum as represented in some sufficiently large two's-complement format" (JLS § 15.18.2, <https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html>; not fetched, the chapter is too long for the fetch tool, quoted from the standard's text). Checking is a library method: `Math.addExact` "Returns the sum of its arguments, throwing an exception if the result overflows an `int`", since Java 8; the high half of a product is `Math.multiplyHigh`, since Java 9 (<https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Math.html>).
- **X10**, IBM's language from the same DARPA programme as Fortress, compiled to Java and C++: `Int`'s `+` and `*` say "Overflows result in truncating the high bits" and are the bare expressions `((#this) + (#x))` in both back ends (<https://raw.githubusercontent.com/x10-lang/x10/master/x10.runtime/src-x10/x10/lang/Int.x10>). There is no checked operator.

**Close to the metal**
- **Swift.** "By default Swift reports an error rather than allowing an invalid value to be created. However, when you specifically want an overflow condition to truncate the number of available bits, you can opt in to this behavior … Overflow addition (`&+`), Overflow subtraction (`&-`), Overflow multiplication (`&*`)" (The Swift Programming Language, Advanced Operators, <https://raw.githubusercontent.com/swiftlang/swift-book/main/TSPL.docc/LanguageGuide/AdvancedOperators.md>). The error stops the program; it cannot be caught.
- **Rust.** "If a program contains arithmetic overflow, the programmer has made an error. In the following discussion, we maintain a distinction between arithmetic overflow and wrapping arithmetic. The first is erroneous, while the second is intentional." Builds with debug assertions must panic; "Other kinds of builds may result in panics or silently wrapped values on overflow, at the implementation's discretion"; "`i32::wrapping_add` provides two's complement, wrapping addition", and "a `Wrapping<T>` newtype … ensures all standard arithmetic operations for `T` have wrapping semantics" (Rust Reference, <https://doc.rust-lang.org/reference/behavior-not-considered-unsafe.html>). The standard library adds `checked_add`, "returning `None` if overflow occurred", `saturating_add` and `overflowing_add` (<https://doc.rust-lang.org/std/primitive.i32.html>).
- **Zig.** "Operators such as `+` and `-` cause Illegal Behavior on integer overflow"; `+%` wraps, `+|` saturates, and `@addWithOverflow` reports the overflow beside the result (<https://ziglang.org/documentation/master/>).
- **C.** Signed overflow is undefined behaviour and unsigned arithmetic is reduced modulo 2^n (C11 § 6.5 ¶ 5, § 6.2.5 ¶ 9; not fetched).

**Scientific**
- **Julia.** "In Julia, exceeding the maximum representable value of a given type results in a wraparound behavior"; "The `Base.Checked` module provides a suite of arithmetic operations equipped with overflow checks"; where overflow cannot be tolerated, `BigInt` (manual, Integers and Floating-Point Numbers, <https://docs.julialang.org/en/v1/manual/integers-and-floating-point-numbers/>). The reason given: "If you can't count on the results of integer operations being integers, it's impossible to generate fast, simple code the way C and Fortran compilers do", and saturation was refused as the default because "Saturating integer arithmetic isn't associative" (FAQ, <https://docs.julialang.org/en/v1/manual/faq/>).
- **NumPy.** Fixed-size integers wrap: "`numpy.power` evaluates `100 ** 9` correctly for 64-bit integers, but gives -1486618624 (incorrect) for a 32-bit integer" (<https://numpy.org/doc/stable/user/basics.types.html>).

**Unbounded**
- **Python.** "Integers have unlimited precision." (<https://docs.python.org/3/library/stdtypes.html>). Fortress's `ZZ` is in this family.

**Reading.** The specification's design is Swift's (an error by default, wrapping only under its own operator), with the saturating family as operators, as Zig has them, and a catchable exception where Swift stops the program; the Fortress text predates Swift's 2014 release (section 8). Of the four peers Pavol named, Swift and Rust separate "meant to wrap" from "overflowed by mistake" in the spelling; Julia and X10 wrap everything, Julia for loop speed. Rust and Zig also offer "tell me it overflowed and let me decide" as a primitive; the specification has that only in its unimplemented binary-word layer (way 10).

## 9. The derivation from Pavol's principle, case by case

The principle (`POSITIONS.md:72`, 2026-09-22): use the JVM's defaults where they make sense; correct the JVM's mistakes through the lens of a high-performance, mathematically precise language; where hardware behaviour is expressible in bytecode it gets its own explicit spelling, in the family the specification already has for wrapping and saturating.

**In general.** The JVM's default `+` wraps (JLS § 15.18.2). The specification, and Pavol's decision on row 379, correct that: `+` is checked. The hardware behaviour, the wrap, is a single `iadd`, `isub`, `imul`, `ladd`, `lsub` or `lmul`, and the specification's spelling for it is ∔, ∸, ⨰. So code that means to wrap should say ∔, ∸ or ⨰. Code that must avoid overflow should be reordered so that the checked operators never trip, as the library already does (way 3), and not respelled with a wrap it does not mean.

**Costs on the JVM**, by reading; none of these was measured for this note.
- ∔, ∸, ⨰: the plain instruction, with no branch. They are what the compiled prelude's Wrapping natives already are (`simpleIntArith.java:224-234`).
- Checked `+`: a sign test and a branch that is never taken (`simpleIntArith.java:62-66`), or `Math.addExact`, which the JIT compiles to the processor's overflow flag. The performance roadmap notes that the branch may keep a loop from being vectorised (`explorations/performance-roadmap.md:90-100`, read from HotSpot's documented rules, unmeasured).
- A reordering: one comparison, or the same subtractions in another order; nothing measurable.
- `ZZ`: a `BigInteger` object for every operation, allocated and collected.
- A clamp: a comparison and a branch per operation.
- The interpreter's own speed does not enter any decision (`POSITIONS.md:38`).

**Case by case.** Each case says what the code means, what it becomes under the principle, and the alternative from section 1 with its cost.

- **(a) The range split's `split-1`**, six sites: `Library/RangeInternals.fss:1031`, `:1046`, `:1201`, `:1221`, `:1242`, `:1266`. Row 403 and rung O's report list five; `:1266`, the loop's negative-stride branch, has the same text (by reading). It means a bit mask (section 2). It becomes `hi BITAND (BITNOT (split DOTMINUS 1))`: the same value as today, and no cost. Alternative: say "split at zero" in words, `if lo < 0 AND 0 <= hi then 0 else hi BITAND (BITNOT (split - 1)) end` (written with the element type's own zero in the generic code), which costs a comparison per split and changes Maessen's text more. A third, the compiled library's midpoint split through `floorAverage` (section 6), never overflows but moves every split point off the power-of-two boundaries Maessen chose, so it is a redesign, not a repair.
- **(b) The range split's `(lo BITXOR hi)+1`**, the same six sites. It overflows only when `lo BITXOR hi` is the maximum, for instance on a range `0:2147483647` (by reading), and `partitionL` then subtracts the 1 again inside Java, so the pair computes the highest set bit of `lo BITXOR hi`. It becomes `(lo BITXOR hi) DOTPLUS 1`, exact at no cost. Alternative: a primitive that gives the highest set bit directly, the specification's `leftmostOneBit` (`binary.tex:1289`, `:1464`), which removes the `+1`; that is a new native no site needs.
- **(c) The strided distance `(…) - lo - 1`**, four sites: `:1201`, `:1221`, `:1242`, `:1266`. It means an ordinary distance, and that distance fits whenever `mid > lo`, which always holds, but its first step `mid - lo` overflows when `lo` is the minimum and `mid` is 0 (by reading, row 403). This is must-avoid, not means-to-wrap: reorder it as `(mid - 1) - lo`, with `mid` named first, and keep the checked operators.
- **(d) `LinearCongruential`**, `Library/Random.fss:235` (measured) and `:241` (by reading). It means arithmetic modulo 2^48, done through arithmetic modulo 2^64. It becomes `((mult DOTTIMES widen(state)) DOTPLUS add) MOD modulus`: the same values, no cost, `MOD` bringing a negative wrapped value back into range as it does today. This is right only because 2^48 divides 2^64. The object is generic in its modulus (`Random.fss:222`) and built once, with 2^48 (`:253`); for a modulus that is not a power of two, today's code and this one both give wrong numbers without a word (section 11). Alternatives: exact through `ZZ`, right for every modulus, at a `BigInteger` per random number (`QuickCheckTest` alone meets 146K overflowing products); or the Mersenne twister's habit (way 1), splitting the state into 24-bit halves so every product fits, about five lines and three multiplications.
- **(e) `ChunkedSparseArray.secondaryIndex`**, `Library/ChunkedSparseArray.fss:76` (measured). It means the bits below the mask. It becomes `popCount((mask DOTMINUS 1) BITAND fe)`. Alternatives: `if mask < 0 then BITNOT mask else mask - 1 end`, or, from the bit index `indexAndMask` already computes (`:75`), `BITNOT (widen(-1) LSHIFT b)` (way 4).
- **(f) `IntMap.keySplit`**, `Library/IntMap.fss:675-676`: the negation at `:676` measured (27 `Long$Negate`), `mn-1` at `:675` by reading when the smaller key is the minimum. Both are bit masks. They become `p = partitionL(((mn DOTMINUS 1) BITXOR mx) DOTPLUS 1)` and `(DOTMINUS p) BITAND mx`. Alternative: a sign case, since the negated `p` is the minimum exactly when the keys straddle zero, where the answer is 0.
- **(g) `HeapTest`'s `spread`**, `ProjectFortress/tests/HeapTest.fss:95-99`. It means a scramble modulo 2^32: with `c1` odd, `n ↦ c1 n + c2` maps `ZZ32` onto itself one to one, so the test's keys stay distinct. It becomes `((c1 DOTTIMES n) DOTPLUS c2, n)`. Alternative: `narrow(widen(c1) widen(n) + widen(c2))` (way 2), which never overflows and gives the same value.
- **(h) `intPrim.fss:21-22` and `longPrim.fss:21-22`.** They assert of `+` and `-` exactly what the specification refuses; their author's intent (section 8) was "the boundary behaves as it should". Under the specification the wrap identity belongs to the wrapping operators and the plain ones throw, so each file asserts both: `a.minimum DOTMINUS 1 = a.maximum` and `a.maximum DOTPLUS 1 = a.minimum`, and, with a copy of rung I's helper, `overflows(fn () => a.minimum - 1)` and `overflows(fn () => a.maximum + 1)`. `longPrim`'s `a: ZZ64 = 0` holds a `ZZ32` (row 146), so all four test 32 bits there until `a` is set with `widen(0)`; that is row 146's correction, not this one's.
- **(i) The associativity properties**, `QuickCheckTest.fss:89-90` and `ReflectiveQuickCheckTest.fss:16-17`: "associativity of `+` operator over `ZZ32` domain: should pass", set against `RR64`'s "may fail". Under checked `+` associativity is not a total property of `ZZ32` (section 2). The ring the specification declares for it is ∔, so the property becomes `(p DOTPLUS q) DOTPLUS r = p DOTPLUS (q DOTPLUS r)` and still should pass. Alternatives: keep `+` and state the property only where it answers, "`+` agrees with ℤ wherever it answers", with `==>` over the sums computed in `ZZ` or with the generator held to its levels 0-2 (way 11); or move the property to `ZZ`.

**One thing all cases share.** A `ZZ64` variable that holds a `ZZ32` value (row 146) wraps at 32 bits under ∔ exactly as it does under `+` today; the respelling keeps today's values, that quirk included. Fixing row 146 is its own row.

## 10. The options as they would be put to Pavol

**Option 1, the specification's own way.** Declare ∔, ∸ (unary and binary) and ⨰ in the interpreter's library, on `Integral[\I\]` and on `ZZ32`, `ZZ64`, `NN32`, `NN64` and `ZZ`; rewrite the sites of section 9 with them; reorder the strided distance; then land rung O.
- *What the work does.* Under `walk` the new operators are bound to wrapping natives: on `NN32` and `NN64` to the natives `+` uses today, unchanged; on `ZZ32` and `ZZ64` to new small wrapping classes, because rung O's patch turns today's classes into checked ones (four a width: add, subtract, multiply, negate); on `ZZ` to the exact ones, as the specification says.
- *What it produces.* Every site gives the value it gives today, because the wrapping operator is the arithmetic the site gets today. So rung O's count is expected to fall to zero. That has to be measured with the same runner, not assumed.
- *What it touches.* `Library/FortressLibrary.fsi` and `.fss` and `ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi` and `.fss` (for `NN32`), about 50 lines; `Int.java` and `Long.java`, eight small classes; `RangeInternals.fss` (about 16 lines at the six sites), `Random.fss` (2), `ChunkedSparseArray.fss` (1), `IntMap.fss` (2); five tests (about 12 lines). All are edits to the original tree and are flagged as such. It adds one gated test of ∔, ∸ and ⨰ at both widths' boundaries, and the rung declares its checker count, since `Integral` gains declarations.
- *What it commits him to.* Row 348 is decided for the specification's spelling in the one library. The compiled prelude's reversed operators leave with the prelude at the switch-over, and the compiled tests that use them are respelled then: 10 files, 138 matching lines (`Integer3`, `Integer4`, `NN32`, `NN64`, `ZZ`, `AverageTest` and `ShiftTest2` in `library_tests/`; `IntegerLiteralsFolding`, `IntSemanticsRungB` and `XXXBoxDotSpellingsRungW` in `compiler_tests/`), with `BOXCROSS` becoming ⨰. The saturating family stays undeclared in the one library until a step of its own. It shares `FortressLibrary.fsi`/`.fss` with the tower-flattening rung, so the manifest orders the two.
- *Variant 1b.* The three bit-mask cases (a), (e) and (f) written with explicit sign cases instead of ∸, and the wrapping operators kept for the generator, the hash and the tests. The commitments are the same; there is more text to review, and "split at zero" is said in words.

**Option 2, restructure everything and declare no operator.** Every site is rewritten in the library's avoid-overflow habits: the zero case in the split, a highest-set-bit primitive or a guard for the `+1`, masks by shift, a sign case in `IntMap`, the hash through `widen` and `narrow`, the generator exact through `ZZ` or by split multiplication, and the tests asserting the throw, with the properties restated on the range where `+` answers.
- *What it commits him to.* No new operator, and row 348 stays open. After the switch-over the one library has no spelling for a wrap at all, so the team's compiled tests that wrap with `BOXCROSS` and `BOXPLUS` lose their operator. Each site's reasoning changes, not just its spelling. The generator costs either a `BigInteger` per random number or a five-line split multiplication. The two QuickCheck tests test different properties from today's. Under his principle, the hardware behaviour is left without its explicit spelling.

**Option 3, the whole family now.** Option 1, plus the saturating operators ⊞, ⊟, ⊡ and ⊠ in the same rung (new clamping natives under `walk`, about eight small classes).
- *What it commits him to.* The same as option 1, plus declarations that no site uses yet, and a gated test for both families. The protocol's "one variable per step" argues for doing it later.

**Not an option.** Keeping `walk` wrapping would reverse row 379, and the compiled path throws on these same bodies at the switch-over anyway (row 403).

**Recommendation (my reading, not a decision):** option 1: declare ∔, ∸ and ⨰ in the one library, respell the wrap-reliant sites and tests with them, and reorder the strided distance, as the step before rung O; the saturating family gets a later step of its own.

## 11. Found on the way

- **A sixth split site.** `Library/RangeInternals.fss:1265-1266` has the same `split-1` and the same distance as the five that row 403 and rung O's report list (by reading).
- **The unsigned types wrap under `walk` and row 379 does not cover them.** `NN32` and `NN64` arithmetic goes through `com.naturalbridge.misc.Unsigned.add`, `subtract` and `multiplyTo…`, which are bare `iadd` and `lmul` (read with `javap`; `NN32.java:103-124`, `UnsignedLong.java:104-125`), while the compiled path's `NN32` `+` throws (`CompilerBuiltin.fss:768`). Steele's gated `ProjectFortress/tests/UnsignedTest.fss:195-211` (`dc41d5000`, 2008-07-21) uses unary `-` on an unsigned value as 2^w minus that value. It is the same question as this note's, larger, and it comes later, when the unsigned natives are checked.
- **`LinearCongruential` is wrong for most moduli.** The object is generic in its modulus, but wrapping modulo 2^64 and then taking `MOD modulus` is right only when the modulus is a power of two; the library builds it only with 2^48 (`Library/Random.fss:222`, `:253`).
- **A wrapping operator under `walk` needs natives of its own.** Rung O's patch changes today's ten natives in place (`REPORT.md` § 3), so after it no native wraps; a wrapping operator bound to the old names would start to throw.
- **The box family means "toward zero" on both kinds of number.** Saturation clamps toward zero, and the same boxed operators on floats round toward zero (`opr-overview.tex:181`, `:214`). That is a design reason behind the specification's pairing, relevant to row 348.
