## 2. Precedent search: has the team solved this here, and in how many ways

**And those two bodies do not agree with the api or with each other on the return type of the two truncating methods.** `trait Number`'s own body, in the same trait the api at (a) describes (`Library/FortressLibrary.fss:349-420`), declares `truncate(self):RR64` at `:418` and `round(self): ZZ` at `:419`, where the api declares `truncate(self):ZZ64` (`Library/FortressLibrary.fsi:332`) and `object Float`'s body declares both `ZZ64` (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fss:188-191`). ## 3. The specification, read

`Specification/basic-lib/numbers.tex` is chapter 33, "Numbers", and it has exactly one section, "Rational Numbers" (`:12-17`); the ℝ types appear in it only as names inside the subtype lists of the ℚ family (`:37-90`). The four rounding methods are declared at `:457-462` and defined in prose at `:464-477`: `floor` "returns the largest integer that is not greater", `ceiling` "the smallest integer that is not less", `round` "returns the integer that is closest … but if this rational number is exactly halfway between two consecutive integers, then `round` returns whichever of the two integers is **even**", `truncate` "returns the ceiling … if it is negative, and otherwise … the floor", that is toward zero. `:464` and `:467` both say "likewise the enclosing operator", so the specification makes the named method and the bracket the same operation with the same result type.

**A correction to the brief.** CLIMB-BATCH-1.md section F says "the 'Real' numbers section of that chapter is commented out (`numbers.tex:920`)". There is no such section and no such line: the file is 566 lines long and has no second section, commented out or otherwise, and no file under `Specification/basic-lib` or `Specification/advanced-lib` reaches line 920 except `advanced-lib/binary.tex`. The chapter's many `%` lines are the ASCII sources of the typeset displays, as `explorations/coordinator/map/design-intent-sources.md:104` already records for `algebraic-constraints.tex`; they are not disabled text. The conclusion the brief drew from the wrong citation is nevertheless right — the specification has no chapter for the real types — but it is right because the chapter was never written, not because it was switched off.

For `exp`, `log` and the trigonometric functions the prose is silent in the sense that matters (no definition and no declaration), but it is not silent about their existence, and two passages are worth having on the record because they are the closest the prose comes: `Specification/basic/expressions/constant.tex:123-133` lists "`+`, `-`, `×`, `·`, `/`, `!`, `MIN`, `MAX`, `√`, `floor`, `ceiling`, `hyperfloor`, `hyperceiling`, `gcd`, `lcm`, `sin`, `cos`, `tan`, `arcsin`, `arccos`, `arctan`" as the operations that may combine numeric **static** expressions — naming six of the transcendentals in mathematical spelling (`arcsin`, not `asin`), defining none, and not naming `exp`, `log` or `atan2` at all; and `Specification/basic/dimensions.tex:214-215` presumes them as library functions — "Other numerical functions, such as `sin` and `log`, require dimensionless arguments."

## 4. The four deviations, each a decision

**(i) `floor` and `ceiling` return `RR64`, where the specification says ℤ.** Alternatives: `RR64`, which is precedent (d) — the team's commented-out draft in this very file — and also precedent (a), the interpreter's method type; or `ZZ64`, which is the specification's ℤ and the interpreter's *bracket* type. `RR64` was chosen. The reason is not that the specification is silent; it is that the specification requires the method and its enclosing operator to be the same operation with the same result (`numbers.tex:464`, `:467`, "likewise the enclosing operator"), the compiler prelude's two brackets are already declared `RR64` (`CompilerBuiltin.fsi:437-438`), and changing a declared type the prelude already has is one of the two stops CLIMB-BATCH-1.md reserves. Declaring the methods `ZZ64` would have satisfied the specification's magnitude and broken its identity, leaving one trait in which `floor(x)` and `⌊x⌋` have different types. Declaring them `RR64` keeps the trait coherent and leaves a single pre-existing deviation, now written down as a ledger row rather than doubled.

**(ii) `round` and `truncate` return `ZZ64`.** No enclosing operator for either exists in the compiler prelude, so (i)'s constraint does not apply; `ZZ64` is both the precedent (`FortressBuiltin.fss:187-190`) and an integer type, which is what ℤ asks for. The alternative, `RR64` for symmetry with `floor` and `ceiling`, was rejected: it would deviate from the specification and from the precedent at once, for symmetry alone.

**(iii) `round` is built on `Math.rint`, not `Math.round`.** `Math.round` rounds an exact half toward positive infinity, which contradicts `numbers.tex:470-472`; `Math.rint` rounds an exact half to the even integer, which is that sentence. The interpreter's `Float$Round` is `Math.round(x)` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Float.java:382-385`), so this is a deliberate deviation from precedent (b) — taken because precedent (c), the team's own ℚ body at `Library/FortressLibrary.fss:589`, implements the specification's rule in Fortress, and because a gated interpreter test asserts it: `ProjectFortress/tests/RationalTest.fss:428` asserts `round(15/6) = 2`, that is `round(2.5) = 2`. The differential in section 6 shows `walk` answering `3` for the same value at `RR64`. Ledger row (provisional 329) carries the interpreter-side defect.

**(iv) `atan2` takes `x: RR64` where the interpreter takes `x: Number`.** The compiler world's `Number` is an empty marker (`CompilerBuiltin.fsi:96`, `spec-to-implementation.md:410`) and carries no arithmetic, and every binary declaration in the compiler world's `trait RR64` narrows the interpreter's `Number` parameter to `RR64` already (`CompilerBuiltin.fsi:419-435` against `Library/FortressLibrary.fsi:291-316`). So the type follows the file. The parameter **name** `x` is kept from the interpreter rather than renamed to the file's usual `other`, because for `atan2` the name carries meaning: `self` is the *y* coordinate and the argument is the *x* coordinate, which is what `Float.java:334-337` computes (`ATan2 extends RR2R`, `f(y, x) = Math.atan2(y, x)`, with `RR2R.applyMethod(FObject x, FValue y)` at `:86-92` putting `self` first).

**A fifth decision, about the natives' home.** The eleven new static methods went into `ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleDoubleArith.java`, the team's own file, rather than into a new file beside it as rung 7 did with `simpleIntLiteralArith.java`. The criterion is the one that made rung 7 split: its helper dealt in a Fortress type and needed a clause in `NamingCzar.fortressTypeForForeignJavaType` (`ProjectFortress/src/com/sun/fortress/compiler/NamingCzar.java:343-344`). These eleven deal in `double` and `long`, which the generic path maps without a clause (`NamingCzar.java:441-446`, `s(Type.LONG_TYPE, fortLib, "ZZ64")` and `s(Type.DOUBLE_TYPE, fortLib, "RR64")`), and they are the same kind of one-line wrapper over `java.lang.Math` as the file's existing `doublePow`, `doubleSQRT`, `doubleFloor`, `doubleCeiling` and `doubleAbs`. A new file would have split the double primitives across two files with no criterion. Worth noting for the next rung that touches this: `doubleTruncate` and `doubleRound` are the first natives in the tree that take a `double` and return a `long`.

**A sixth decision, about the test's assertions.** The comparing `assert` has no `RR64` form — rung 4 added `ZZ32`, `String` and `Character` only (`Library/CompilerLibrary.fsi:45-49`) — and this rung did not add one. The alternative, adding `assert(x: RR64, y: RR64)` and `assert(x: RR64, y: RR64, failMsg: String)` to `CompilerLibrary`, was rejected for two reasons: rung T of this batch is editing `CompilerLibrary` in the same wave, and batch rule 1 keeps the merge clean by keeping the rungs' declarations disjoint; and floating-point assertions want an epsilon rather than `=`, which a comparing `assert` cannot express. The test therefore uses the Boolean form over `opr =` for the exact cases and over a local `near` for the inexact ones, and `.asZZ32` into rung 4's `ZZ32` form for `round` and `truncate` — the same idiom as `ProjectFortress/library_tests/IntLiteralArithRung7.fss:58-70`.

| `ceiling(2.5)` | 3.0 | 3.0 | 3, in ℤ |
| `ceiling(-2.5)` | -2.0 | -2.0 | -2, in ℤ |

Two rows diverge, and the specification settles both against the interpreter: `Math.round` rounds an exact half toward positive infinity, so it is right at `3.5` and at `-2.5` by coincidence and wrong at `2.5` and `-3.5`. The interpreter is not merely wrong against the specification, it is inconsistent with itself: `Library/FortressLibrary.fss:589` gives ℚ a hand-written round-half-to-even body, and the gated interpreter test `ProjectFortress/tests/RationalTest.fss:428` asserts `round(15/6) = 2`, that is `round(2.5) = 2`, on ℚ. Provisional ledger row 329 records it; the repair is one token in `Float.java:384` and is outside this rung, which touches no interpreter-world file.

(The compiled probe's output carries one extra space per line. That is gap ledger row 76 — string juxtaposition inserts spaces on the compiled path because `trait String`'s `opr juxtaposition(self, b:Object): String = self ||| b` uses the smart concatenation (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss:400`, which is row 76's `:384` moved down by rungs 5 and 7) where `Library/FortressLibrary.fss:4050` uses `||` — and not an effect of this rung.)

**Differential 2, the four rounding methods against their enclosing operators.** Four assertions in the test compare `floor(x)` with `⌊x⌋` and `ceiling(x)` with `⌈x⌉` at `2.5` and `-2.5`; all four hold. This is the identity `numbers.tex:464` and `:467` require ("likewise the enclosing operator"), and it is the reason section 4 (i) gives for the `RR64` return type.

## 9. What was not done, and the decisions not taken

`coerce(x: IntLiteral)` on `trait RR64` was not added, though it is now the first blocker of three of the seven subset files and is one line. Reasons in section 7; it is the natural next rung on this trait and it wants its own before/after.

The ten IEEE directed-rounding operators (`PLUS_UP`, `MINUS_UP`, `DOT_UP`, `SLASH_UP`, `SQRT_UP` and their `_DOWN` partners, plus the seven `IEEE_*` forms the interpreter also has at `Library/FortressLibrary.fsi:299-316`) were not added: they are not among the thirteen, and they are half of `realArith.fss`'s remainder. They are cheaper than they look, though, and the next rung that wants them should know it. `java.lang.Math` has no directed-rounding arithmetic, but this repository already carries its own: `com.sun.fortress.numerics.DirectedRounding` (`ProjectFortress/src/com/sun/fortress/numerics/DirectedRounding.java`, pure Java, `addUp` at `:129`, `nextUp` at `:111`, the `*Down` forms written as `-op(-x, -y)` at `:126`), which the interpreter's glue calls directly (`Float.java:136-162`). So that rung is an `import java` block over that class plus the declarations, the same shape as this one — with one thing to check first: `DirectedRoundingTest` is one of the two test classes `explorations/coordinator/map/test-coverage.md:187` records as matching no green fileset, so the helper is unexercised by the gate.

`e` and `pi` were not added as top-level constants and are not needed: `realArith.fss:13` imports them (`import Constants.{...}`, declared `pi : FloatLiteral` and `e : FloatLiteral` at `Library/Constants.fsi:16-17`) and they resolve on the compile path — neither appears among that file's remaining errors. This rung's own test declares its own two at `RR64`, because a `FloatLiteral` constant would need coercing at every use.

`round`'s and `truncate`'s behaviour on NaN and on the infinities was not pinned by the test. `numbers.tex:479-481` says the four methods return the argument unchanged for `+∞`, `-∞` and `0/0` on ℚ* and ℚ#, which a `ZZ64`-returning method on a float type cannot do; `(long) Math.rint(NaN)` is `0` and `(long) Math.rint(+∞)` is `Long.MAX_VALUE`. That is the same question as row 330 and belongs with it rather than being settled unilaterally here.

No form of `assert` was added at `RR64`, for the reasons in section 4; and the test file carries the corpus's `Copyright 2011, Oracle` header, as all eight earlier rung tests in `library_tests/` do (`AssertRung4.fss:1-10` and the rest). That header is factually an attribution of a 2026 file to Oracle. Following it keeps the corpus uniform and diverging in one file would settle nothing, so it was followed — but it is a batch-wide question rather than this rung's, and it is raised here rather than decided.

The JUnit suite was not run. `LibraryJUTest` calls `Shell.resetRepository()` before it starts (`LibraryJUTest.java:32-34`), which would wipe `default_repository/caches` and cost the 165 s library rebuild, and the batch is gated once after the merge by the coordinator. The recorded pass is the same sequence the harness runs — `link`, `run`, stdout contains `PASS` — taken by hand and captured.
