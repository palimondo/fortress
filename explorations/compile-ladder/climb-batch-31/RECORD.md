### Rung M, `rung-method-forwarders`: the methods that a class inherits

**The change.** The team's code generator (`compiler/codegen/CodeGen.java`, `dumpMethodChaining`, with `STypesUtil.removeIdenticallyCoveredMethods`, `scala_src/useful/STypesUtil.scala:1574`) wrote a forwarder for each inherited declaration with a body that no declaration of a subtype covered, comparing the two domains as schemas over each trait's own static parameters; it skipped every declaration without a body, an imported api's among them. So a compiled generic trait that declared again a method which it inherited through a trait that was not its first could not load, and a compiled object could not call a method whose body an imported api's trait gave it, unless that trait was first in its extends clause. The tree now writes one method for each such group, which runs the declaration of the lowest type that declares it, as walk does, and forwards to the api trait's body: `compiler_tests/TraitOwnMethodBesideInheritedCompiled`, `compiler_tests/ApiTraitMethodNotFirstCompiled`. The reason: the traits chapter, section "Method Declarations" (`Specification/basic/traits.tex:584-590`), by which a trait does not inherit a declaration whose parameter types are those of one that it declares; the measured failures 'ClassFormatError: Duplicate method name "mx?0"' and 'AbstractMethodError ... does not define or inherit an implementation'; and the compiled checker's reading of an api's method without `abstract` as one with a body (`scala_src/typechecker/AbstractMethodChecker.scala:274`). A programmer no longer needs to put an api's trait first in an extends clause, or to keep a generic trait from declaring again what it inherits. Two limits stay: an object's own overloads of a functional method with self not first beside an inherited one still die at dispatch, and a body of a self-typed trait that returns `self` still fails verification at an object instance.

### Rung L, `rung-label-exit`: label and exit on the compiled path

#### The change

The team's code generator had no case for a label block or an exit: `CodeGen` declared no `forLabel` and no `forExit`, so the node reached `defaultCase`, which refused the declaration with 'Can't compile Label' (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:1859`, `defaultCase`). Walk runs both, and matches an exit to a label by the label's name (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/Evaluator.java:628-645`, `:500-519`); its `try` offers an exit that passes it to the `catch` clauses as the library's `LabelException` (`Evaluator.java:1453-1456`).

The tree now compiles both (`CodeGen.java:1776-1857`, `runtimeSystem/LabelExit.java`). A compiled exit leaves the evaluation of the label block in which it was made, also from the body of a `for`, from a function expression and from another task; a parallel loop first joins the iterations that it forked, which run to their end or to their own exit; the label's value is one of the exiting values. No compiled `catch` clause takes an exit. Test: `compiler_tests/LabelExitCompiled`. Where a label block is evaluated again inside itself, a compiled exit leaves the evaluation in which its function was made, and walk's leaves the innermost one: `descend` of `compiler_tests/LabelEvaluationIdentityCompiled` gives 102 compiled and 104 under walk.

A compiled program must still keep to four spellings: bind a number that a label block yields beside an exit's value to a typed variable first, as `none: ZZ32 = -1` (`compiler_tests/XXXLabelNumeralValueCompiled`); bind a label block's value in a statement of its own, not as a call's later argument (`compiler_tests/XXXAtomicBlockLaterArgument`); do not rely on a `finally` clause between an exit and its label (`compiler_tests/XXXFinallyOnEscape`); do not exit out of an `atomic` block and rely on its writes, on either path (`compiler_tests/XXXExitOutOfAtomicCompiled`, `tests/XXXExitOutOfAtomicWalk.fss`). A function, a variable and a label in scope may not share a name: the checker refuses 'Cannot use an existing identifier … for a 'label' expression'. An exit that runs after its label block has completed ends a compiled program (`compiler_tests/ExitAfterLabelCompletedCompiled`). The skill's list of constructs that the code generator has no case for names `label` and `exit`, which it now has.

The reason, as evidence: the specification's section "Label and Exit" (`Specification/basic/expressions/label.tex:52-66`); the one library's `Indexed.indexOf` (`Library/FortressLibrary.fss:2189-2195`), above every string and array, was refused; the failing run 'Can't compile Label at …LabelExitCompiled.fss:13.29'.

#### Provenance

Ledger row 81; the rehearsal's wall W9; fork L1 of the batch record (an exit leaves through the loop's body as an abrupt completion that names its label, each evaluation with its own identity; a parallel loop joins the arms that it forked first) under P-175; climb batch 31, rung L.

### Rung A, `rung-atomic-expr-field`: atomic as an expression, and a mutable field inside a transaction

#### The change

- **An atomic expression compiles.** The team's code generator compiled `atomic do ... end` and had no case for `atomic e` over any other body: its `defaultCase` refused the node, 'Can't compile AtomicExpr' (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:1776` and `forAtomicBlock` at `:1835`, at `c1ce2a35e1`). The tree now compiles `atomic e` as the atomic block that holds `e`, with the value of `e` (`compiler_tests/AtomicExprCompiled`). The reason: the specification gives the atomic expression its body's value and makes all its reads and writes one step (`Specification/basic/expressions/atomic.tex`, section "Atomic Expressions"), walk runs it, and the one library writes it (`Library/OneShotFlag.fss:18`). Where the body's value is a numeral at a place of declared type, write `atomic do ... end`: the checker refuses `atomic if c then 1 else 0 end` there, and `atomic 1` fails the JVM's verification (ledger row 1043).
- **A compiled object's `var` field is tracked by a transaction, at the cost of a check on every access.** The team's code generator read an object's field with a bare `GETFIELD` and wrote it with a bare `PUTFIELD`, a `var` field as any other (`ProjectFortress/src/com/sun/fortress/compiler/codegen/VarCodeGen.java:174-236` at `c1ce2a35e1`), so an `atomic` block did not track it: 40,000 `atomic do n := n + 1 end` on a field from a parallel loop gave 34,631 to 39,313 at four threads. The tree now keeps a `var` value parameter or `var` field in a cell that the object holds, read and written as a top-level `var` is; each access, outside `atomic` too, first asks whether a transaction is running (`compiler_tests/AtomicFieldCompiled`). A field without `var` is as it was. The reason: mutable fields of reference objects are mutable locations (`Specification/basic/evaluation/memory-ops.tex`, section "Memory and Memory Operations"), an atomic expression's reads and writes are all one step, and walk is exact on the same program.
- **A loop body or a function expression in an object's method works on the object's `var` field, not on a copy.** The team's code generator gave each task and closure a copy of a field's value, made when the task or closure was built, so a write from a loop body in the object's own method was lost, at one thread too, and a function expression read a stale value: `for i <- 1#k do atomic do n := n + 1 end end` in a method left `n` at 0. The tree now gives the task or closure the field's cell (`compiler_tests/VarFieldCapturedCompiled`). The reason: the measured failure, and walk's result on the same program.
- **Do not give a `value` object a `var` field in a compiled program.** The specification forbids it (`Specification/basic/objects.tex`, section "Value Objects") and nothing refuses it; with the field in a cell, two such objects built alike are no longer strictly equivalent, `V(1) === V(1)` is `false`.

- The field in a cell: ledger row 319; fork A1 of `explorations/coordinator/CLIMB-BATCH-31.md`, "Forks the batch takes", whose default it builds ("A `var` field is kept in a cell, as a top-level `var` is"); P-169, whose store and slots are untouched; climb batch 31, rung A.
- The captured cell: measured by rung A of climb batch 31 while building fork A1; no row; a consequence of A1's default.
- The value object: ledger row 112, with the note above.

### Rung V, `rung-walk-value-bound`: two repairs of walk before the merge

**The change.** The team's walk takes two overloaded parameter lists to exclude each other wherever every parameter at which they differ is an object type of one of them (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/OverloadedFunction.java:511` at c1ce2a35e1, the team's `distinct |= unequal && (allObjInstance1 || allObjInstance2)`), and so compares no return types for such a pair. The tree now reads a generic function beside a declaration without static parameters, whose parameter types some instance of the generic accepts, by the overloading rules on their declared domains: `pickFirst[\T extends Number\](a: T, b: T): T` beside `pickFirst(a: NN32, b: NN32): String` is refused at load, 'fails the Return Type Rule' (`ProjectFortress/tests/GenericBesidePlainObjectReturnRuleWalk.fss`), and beside `pickFirst(a: NN32, b: NN32): NN32` it loads and the plain declaration runs for two `NN32` values (`ProjectFortress/tests/GenericBesidePlainObjectValidWalk.fss`). The team's walk also refuses every type that is not a value type below a value type (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/types/FTraitOrObject.java:97-104` at c1ce2a35e1), the type parameter of a generic method included: `Holder[\RR32\]().held()`, for `held[\T extends S\]()` in `Holds[\S\]`, stopped with 'non-value subtype of value type RR32'. ### Rung X, `rung-return-rule-object`: the checker's Return Type Rule at an object type

**The change.** The team's compiled checker tested the Return Type Rule at one instance of the less specific declaration, the solution of the domains (`ProjectFortress/src/com/sun/fortress/scala_src/overloading/OverloadingOracle.scala:81-95` at a874948ac), and so accepted `ident[\T\](x: T): T` beside `ident(x: Circle): Circle`, `Circle` an object; the team's code generator returned an arm's result from the dispatcher without a cast (`ProjectFortress/src/com/sun/fortress/compiler/OverloadSet.java:1865-1866` at a874948ac), and the class of the generic declaration's instance at another object type failed the JVM's verification, `VerifyError: Bad return type`. The tree now compares every instance of the less specific declaration whose domain meets the more specific one's: where the more specific declaration's parameter type is an object type and the other's is a type parameter, only the instances at which the parameter holds the object. It accepts the pair, refuses `g[\T\](x: T): T` beside `g(x: Circle): String`, and the dispatcher casts an arm's result to its range where that range is a static parameter, so the pair runs and each call runs the most specific declaration that takes its argument. Tests: `ProjectFortress/compiler_tests/OverloadReturnObjectDomain` (accepts, runs) and `XXXOverloadReturnObjectDomainOtherType` (refuses). The reason: the Return Type Rule speaks of argument types other than `BottomType` (`Specification/advanced/overloading.tex:555-559`), an object trait type excludes any type that is not its supertype (`Specification/basic/types-vals-vars.tex:288`), and the type group's paper sets aside the instances of the special arrow whose domain is `Bottom` (`Papers/Types/overloading-check.tick:180`); the verifier's refusal is quoted in the report.

### Rung K, `rung-comprises-cast`: the cast where a trait's value stands for a listed type

**The change.** The team's code generator emitted no cast where the checker reads `self` as more than its trait: `evalArg`'s single-argument branch evaluated the argument and cast nothing, and a method's body was returned as it stood (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java`, `evalArg` and `generateActualMethodCode` at the team's last commit). The specification gives `self` the type of its trait met with the types its `comprises` clause lists, or with its self-type parameter (`Specification/basic/expressions/var-ref.tex:64-76`), and the compiled checker accepts `den(self)` for `den(r: R)` in `trait Q comprises { R }`, and `twin(self): S = self` in `trait Shape[\S extends Shape[\S\]\]`. The compiled program then failed the JVM's verification when the trait's class loaded: 'VerifyError: Bad type on operand stack ... Type Q is not assignable to R', 'VerifyError: Bad return type'. The tree now casts a value that has self's type to a declared type strictly below its trait, at a single argument of a function, a method or a constructor, at a typed binding, at an assignment and at a method's returned value, also where the value is a typecase whose arms are each `self`: `compiler_tests/ComprisesValueAtListedTypeCompiled` and `compiler_tests/SelfTypeReturnSelfRun` run. Two places still fail and are written around by binding `self` at the listed type first, `r: R = self`: a function expression or a local function that returns `self` so (`compiler_tests/XXXComprisesValueFromClosureRun`), and a conditional with `self` in one arm and a listed value in the other (`compiler_tests/XXXComprisesValueAtConditionalArmRun`). A trait that lists a type at a `where`-clause variable gets no cast, and a call that opens its value to the variable still fails (`compiler_tests/XXXNatOpenRun`). A variable declared at the trait, other than `self`, does not stand at a listed type: the checker refuses it. A `typecase` on `self` narrows only through a binder, `c: Disc => f(c)`.
