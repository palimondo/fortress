4. **`shiftLeft` computes as `BigNum$LShift` at every `int` count, and its negation does not compute as `BigNum$RShift` at `Integer.MIN_VALUE`.** On JDK 25, `BigInteger.shiftLeft(Integer.MIN_VALUE)` answers 0 for 5 and -1 for -5, and `shiftRight(Integer.MIN_VALUE)` throws 'BigInteger would overflow supported range' (a scratch Java program, its output: 'shiftLeft(5, MIN): 0', 'shiftLeft(-5, MIN): -1', 'shiftRight(5, MIN): ArithmeticException BigInteger would overflow supported range'). So `ZZ`'s `LSHIFT` and `shift` bind the existing helper, and `RSHIFT` a new one that answers 0 at a zero value and `IntegerOverflow` otherwise, as the glue's `shiftLeft(u, 2^31)` does. Test: the walk guard's 'ZZ -5 LSHIFT the ZZ32 minimum' and 'ZZ 5 RSHIFT the ZZ32 minimum throws IntegerOverflow', and the compiled test's `shlZ` and `shrZ` lines at `min32`.
5. **A clamp of a `ZZ` exponent beyond the `ZZ32` range cannot keep the glue's answers by sign and parity alone.** The glue raises `IntegerOverflow` for every base of magnitude 2 or more there; a clamp to the even 2^31-2 would make `bigPower(2, 2^31-2)` build a number of 2^31-1 bits, which `BigInteger` holds. So `ZZ`'s wide `^` passes the conversion whether its base is 0, 1 or -1 (`|self| <= 1`), and for any other base an exponent beyond the range becomes 2^31-1, which `bigPower` refuses before it builds the power where `(bitLength(|a|)-1)·b` reaches 2^31-1, the bound past which `BigInteger` overflows (`simpleArbitraryPrecisionArith.java:196-212`). Test: the walk guard's 'ZZ 2^(a ZZ 2^70) throws IntegerOverflow' and '... 2^70+1 ...', and 'ZZ (-1)^(a ZZ 2^70)' and '... 2^70+1'. The fixed-width bases need no such flag: `powExact`'s multiplications overflow within 64 steps at any exponent.

## Revival change

**The change.** The team's interpreter library declares each integer type's shifts and power once: the shifts over `AnyIntegral`, `ZZ32`'s at a `ZZ64` count, and the power over `AnyIntegral` (`git show a874948ac:Library/FortressLibrary.fss`, lines 684-691 and 752-759; `git show a874948ac:ProjectFortress/LibraryBuiltin/FortressBuiltin.fss`, lines 434-441), and the team's compiled prelude declares them only at narrow types, `ZZ32`'s and `ZZ64`'s shifts at their own width (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss:736-737`, `:647-648`) and the powers of `ZZ32`, `NN32` and `NN64` at an exponent of the base's own type (`:744`, `:809`, `:878`). The tree now declares both in the one library's api: the declaration over `AnyIntegral`, and beside it a public declaration at a `ZZ32` count on `ZZ32`, `NN32` and `ZZ`, a `ZZ64` count on `ZZ64` and `NN64`, and a `ZZ32` exponent on all five (`Library/FortressLibrary.fsi:525-530`, `:582-587`, `:644-649`, `:701-712`; `ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:164-169`). A call at the narrow type runs the native directly; any other integer count or exponent is converted in Fortress, with the answers of the earlier glue: `tests/NativeHelperShiftPowerWalk.fss` asserts them on both versions, and `compiler_tests/NativeHelperFamilyShiftPowerCompiled.fss` the helpers on the compiled path. The reason: no Java type carries `AnyIntegral` (walk refuses such a binding, `tests/NativeHelperUncarriedWalk.test`, 'no Java type carries the declared type of parameter a'), and the compiled path calls only a static helper of `nativeHelpers/`. At `NN32` and `NN64` the exponent's narrow type is `ZZ32`, not the prelude's own type, since a signed exponent must reach the helper for the run-time test of its sign.
