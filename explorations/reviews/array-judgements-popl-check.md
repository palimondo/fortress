## 0. The paper, in the words needed

- **FGFV**, "Featherweight Generic Fortress with Variance": traits like Java interfaces, objects like final classes, trait type parameters with variance marks and upper bounds, method type parameters with lower and upper bounds, calls that write no static arguments (p. 11:8; extract lines 46-56).
- **Trait parameters' bounds** are checked under an environment binding the parameters themselves ([D-Trait], p. 11:10), so an F-bounded trait parameter is admitted by the rule's form (extract lines 283-285).
- **Method parameters' bounds** may not name a method type parameter: "no reference to a method type parameter appears in any of the upper bounds" (p. 11:11; recheck line 20, quoting). The scope of a method type parameter extends to its right, and the run-time solve works right to left on that account (p. 11:11, p. 11:19; extract lines 196-207). The paper says restriction (1), the scoping, "makes dynamic dispatch more efficient" and restriction (2), the bounds, "makes it consistent" (recheck line 20, quoting).
- **[D-Method]** checks that a covariant or contravariant trait parameter appears only in positions of its variance; "type parameters of objects and invariant type parameters of traits are invariant" (pp. 11:11-12; extract lines 106-110).
- **[Anc-Same-Trait]**: a class extending two instances of one trait extends an instance below both; blanket for an invariant parameter (p. 11:11; extract lines 68-79).
- **The static rules**: a generic declaration is "a single declaration whose domain type is existentially quantified over its type parameters" (p. 11:3); No Duplicates, Meet and Return Type over domains, specificity by subtyping of domains, "sound but not complete", narrowed by existential reduction, which collects the constraints that keep an intersected domain off `Bottom` (pp. 11:12-14; extract lines 136-160). Theorem 4.1: a unique most specific declaration for every call; "No Duplicates makes specificity antisymmetric" (p. 11:15; extract lines 161-164).
- **The run time**: ilks; every call carries its static return type (pp. 11:16-17); [Dispatch] matches the ilks against the domain, matches the static return type against the declared one, and solves by "taking the intersection of the upper bounds", declared and computed, never `Bottom` (pp. 11:17-19; extract lines 186-207). Completeness of matching "assumes that a matched type holds no `Bottom` and no type parameter inside a union or intersection", which every declared type meets (pp. 11:21-22; extract lines 256-260).
- **Left out**: functional methods, closed types, nominal exclusion, modularity, top-level functions (pp. 11:3, 11:25); self types, a numeric tower, coercion, `nat` parameters (extract lines 277-285; recheck line 21).

## 1. Fork 2's bound is an F-bound

**The trait-level bound is in the paper's admitted form.** [D-Trait] checks a trait parameter's bounds under the parameters themselves (p. 11:10), so `T extends MultiplicativeRing[\T\]` on `Vector` is well formed by the rule's form, as the library's twelve F-bounded traits are (`Library/FortressLibrary.fsi:73`, `:175-229`, `:265`, `:277`, `:446`, `:1341`, `:1508`, `:1516` at `HEAD`). The `nat` parameter beside it is outside the paper altogether.

**The function-level bound is outside the paper's theorem.** Restriction (2) excludes a method type parameter from every upper bound (p. 11:11). Fortress's top-level functions and operators are the paper's receiver-free case (extract lines 405-408, by reading), so `pmul[\T extends { Number, MultiplicativeRing[\T\] }, nat k\]` and the block's `opr +[\T extends { Number, AdditiveGroup[\T\] }, I\]` are Naden's rewrite shape, `add⟦X <: Ring⟦X⟧⟧(X, X): X`, which the extract notes the paper excludes (extract lines 348-349, 377-378). The half adds 38. So the fork roughly doubles what stands outside Theorem 5.11, and adds no new kind of declaration. FACTS already says the theorem does not cover the library's F-bounded functions (FACTS, "The team's latest word on types ..."; recheck § 1.4).

**Same ground.** The restriction exists for the solve: a right-to-left pass that takes the intersection of ground upper bounds (p. 11:19), which an upper bound naming the parameter would not give. Where the ilk fixes the parameter at an invariant position, lower and upper bound coincide and the declared bound is a ground check after substitution, never a type to solve for; the recheck read this for `Generator[\T\]` (§ 1.4, "the bound is checked and never solved"). Every declaration of the family fixes `T` so: by a parameter `Vector[\T,k\]`, `Matrix[\T,n,m\]` or `Array[\T,I\]` (invariant), or, for the nullary factories `vector[\T,s0\]()` and `matrix[\T,s0,s1\]()`, by the result `Vector[\T,s0\]`, which the paper's second step reads off the call's static return type (p. 11:18) and the compiled path off the written static arguments. `additiveIdentity[\T extends AdditiveGroup[\T\]\](): T` (`.fss:3230`) is already that result-only shape. The judgement's own line holds: "the arrays' calls all fix `T`" (`array-fork2-judgement.md:173`).

**Dispatch and instantiation at run time.** The class loader stamps `Vector[\RR64,16\]` from the static arguments; the paper's run time has every type parameter "instantiated with ground types" (p. 11:17); the two agree. The dispatcher scans overloads most to least specific by the ilks, [R-Method]'s shape (p. 11:17; extract lines 180-185). Where the paper's instance and the value's differ, a parameter nothing fixes (recheck § 1.6), no array call arrives. The dispatcher does not yet carry the call's static return type (`OverloadSet.java:2048`), a phase 5 line already on PLAN; the arrays add nothing to it.

**[Anc-Same-Trait] and [D-Method].** The ancestor rule bears on the bound's satisfiers and the family's extenders, not on the bound: each number type extends `MultiplicativeRing` at itself once (`Integral[\I\] extends MultiplicativeRing[\I\]`, `.fsi:446`; `RR64` and `QQ` likewise), `TransposedMatrix[\T,s0,s1\]` extends `Matrix[\T,s0,s1\]` once, C4's `Diag` extends `Matrix[\RR64,s,s\]` once. [D-Method] constrains variant parameters' positions; Fortress's generics are invariant, so it is met trivially, and a bound is not a method position in the paper (it is checked by [D-Trait]). FACTS already draws the one consequence, that no self-typed algebra trait can be covariant (recheck § 1.1).

**Unsound, or outside?** Outside. The paper gives no counterexample for an F-bounded method parameter; it drops the shape so that its solve has ground bounds and its proof goes through (p. 11:11, p. 11:19; p. 11:25 on what it could not prove, which is the union-of-lower-bounds instance, not this). The library has stood on this ground since answer 7's `SUM` and `PROD` (`d846e3644`), on the 2011 rules as the checker implements them (recheck § 1.4).

**Verdict: stands, with a sentence.** The fork 2 judgement's § 2.4 and the record's sentence for fork 2 gain: the family's traits and objects carry the F-bound in the paper's admitted form; its 38 generic functions and operators join the library's F-bounded functions outside the 2019 theorem, each with `T` at an invariant position, where the bound is checked and never solved.

## 2. The block's per-operator bounds and "no blanket ring bound"

- The paper has no library, no numbers and no operators, so it says nothing on which capability a bound should name. The judgement's reading of POSITIONS, "The integration review's checks" (the letter bent on the two traits, the reason kept, the first half kept on the block; `array-fork2-judgement.md:100`, `:180`), is untouched.
- It sharpens one of the judgement's reasons for keeping `Number` (§ 2.5, "`Number`'s closure is doing work"). Each block operator is a pair of mirror declarations, `(Array[\T,I\], T)` and `(T, Array[\T,I\])` (`.fss:4756-4766` at `HEAD`). Neither is more specific, and no third covers their meet, so the Meet Rule holds only if the domains exclude ([Meet-Excl], p. 11:13). - The same reduction over the closed family of 17 types is where row 688's minutes went (`perf-probes/checker-speed/REPORT.md` § 2, § 3). The paper's calculus never meets a closed family, so its silence on static cost is not evidence either way.
- **Verdict: stands, with a sentence.** The block's pairs are valid overloads through `Number`'s closure, which is outside FGFV; `Number` in each bound is what the Meet Rule needs, and the per-operator capability beside it is the paper's concern in no way.

## 3. Fork 3's opening of a size

- **The run-time half, supported.** The paper's [Dispatch] matches the ilk `N[\3\]` against `N[\n\]`; the position is invariant, so `n` gets `3` as lower and upper bound, and the solve takes it (pp. 11:17-19).
