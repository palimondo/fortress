## Revival change

### The change

- The team's sources: the comment of `builtinPrimitive` (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:14-29` at the team's last commit `a874948ac`), which the specification prints in its `FortressBuiltin` api, says that the argument "names a Java Class which is a subclass of `com.sun.fortress.interpreter.glue.NativeApp`"; walk's `NativeApp.checkAndLoadNative` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/NativeApp.java:164-215` there) loads the string only with `Class.forName` and refuses anything else, 'Native class … not found.'; and every binding of the team's library names such a glue class, so walk's `ZZ32` `DIV` by zero ends the run in `Int$Div`'s `x / y` (`interpreter/glue/prim/Int.java:126`).
- What the tree now does: the string names either a glue class or a public static method of a class of `com.sun.fortress.nativeHelpers`, written `com.sun.fortress.nativeHelpers.Class.method`; walk takes the method whose Java types carry the declared types, `self` first, carries values at the declared types, raises a helper's compiled exception as the library's, and refuses a string under that package that names nothing or fits nothing (`ProjectFortress/tests/NativeHelperBindingWalk.fss`, `NativeHelperRaiseWalk.fss`, `NativeHelperMisspeltWalk.fss`, `NativeHelperMisfitWalk.fss`, `NativeHelperUncarriedWalk.fss`), though it reads a method's `self` only by its Java type, so a binding in a method of a program's own type loads (`XXXNativeHelperUncarriedSelfWalk.fss`). Trait `ZZ32`'s `=`, `<`, `-`, `DOTMINUS`, `+`, `DOTPLUS`, `DOT`, `TIMES`, juxtaposition, `DOTTIMES`, `DIV`, `BITAND`, `BITOR`, `BITXOR`, `BITNOT`, `widen` and `unsigned`, and `Int`'s `asString` and `asExprString`, name the helpers the compiler's own library binds (`NativeHelperFamilyZZ32Walk.fss`), and `ZZ32`'s `DIV` by zero raises `DivisionByZero` (`ZZ32DivisionByZeroWalk.fss`). A helper bound over `String` receives a non-flat string's type name, as a glue class does (`NativeHelperNonFlatStringWalk.fss`).
- The reason, as evidence: a glue class takes walk's boxed values, `protected final FValue applyToArgs(FValue x, FValue y)` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Util.java:253-254`), which compiled code does not have; the compiled path binds its natives to these same static methods over plain Java values, as `import java com.sun.fortress.nativeHelpers.{…}` in `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss`. A binding that names a helper is the one text both paths can call. The helper's raise names a class of the compiled library, `Utility.makeFortressException("fortress.CompilerBuiltin$DivisionByZero")` (`ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleIntArith.java:79`), which walk has not, hence the translation; and the specification asks the exception: "For integer results, division by zero throws a DivisionByZero." (`Specification/basic/operators/opr-overview.tex:164-165`).
