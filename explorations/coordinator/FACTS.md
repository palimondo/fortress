# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- On microGPT-shaped array code boxing is the dominant representational cost, 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` in Java models of the program's three kernels, and nothing microGPT-shaped compiles: the compiler prelude lacks the array types, with `Array`, `Vector` and `Array3` undefined in `FlatArrays.fsi` (row 305, wider than row 72). On the interpreter, the only path that runs the kernels, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch and 0% number representation (JFR on `krows`). The two one-line runtime defects the probe found are fixed (rows 302, 303; the next two entries), and no array type goes into the compiler prelude: the arrays reach the compiled path with the one library (POSITIONS, the library route). A failed compile leaves a 0-byte jar in the bytecode cache (`perf-probes/kernels/REPORT.md`).
- The boxing probe's scalar-loop reading, 156× primitive Java with boxing about 2% of it, is of the tree before rung 0's two fixes (rows 302, 303; `compile-ladder/rung0/REPORT.md`); of the costs it named, `countedseqloop`'s boxed indices and closure call (about 7%) and the representational rest (about 30%) are unaddressed (`perf-probes/boxing/REPORT.md`).
- The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `compile-ladder/rung0/REPORT.md`).
- `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `compile-ladder/rung0/REPORT.md`).
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine: the same unmodified tree measured 13.0566 s and 8.8159 s in another session, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes.
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`), and its descriptor in a stamped class is `RTTIsize.of("<n>")` ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see "The checker and the one library" below): this no longer holds. The checker checks `nat` and `int` static parameters ("The compiled type checker checks `nat` and `int` static parameters" below), and a sized program loads and runs compiled ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half).
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** The Working Draft's `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:49`, kept in `Specification/basic-lib/convenience.tex:61-65` marked "Not allowed") stops on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`; `reviews/spec-refused-examples/probes/SpecNothing.fss` and its captures). Without that clause, `fortress compile` and `fortress walk` give the identical single error, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`; `reviews/spec-refused-examples/probes/SpecNothingNoExcludes.fss`). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause in either implementation. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at codegen — `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4093`) — but nothing reaches it. This is the mechanism behind the library's comment on its parametric `Nothing[\T\]`, "Obviously ought to be a non-parametric singleton when we get where clauses working" (`Library/FortressLibrary.fss:1449-1450`), and it is why both worlds must spell the empty case some other way.
- **An exported function fails exactly as an exported variable does when a component's name differs from the api it exports, and the failure is the repository's, not codegen's** (`compile-ladder/rung-export-var/`). Both paths assume an api and its implementing component share a name: `fortress link` and `walk` print "Could not find an implementation for API … on path", and the compiled run dies with `NoClassDefFoundError`. The assumption is `Linker.whoIsImplementingMyAPI`'s fallback to the api's own name (`linker/Linker.java:72-76`); only `LinkShell`'s `alink`/`clink` register another. The specification resolves an imported api to a component that exports it (`Specification/basic/components/overview.tex:33-35`), and the team reserved the codegen half in `CodeGen.java:411-441`, `:1856`, `:6599-6606`. Gated as an expected failure by `compiler_tests/XXXExportVarRungXLinked.test`.
- **A comment placed after a declaration that ends in an expression or a type becomes part of that declaration's source span and of the unambiguous name the parser derives from it** (`compile-ladder/rung-library-comments/probes/SpanAbsorb.fss` and `SpanAbsorb.txt`; ledger row 359). `createSpan` (`parser/Fortress.rats:145-157`) trims back over space characters only; a declaration ending in `end` is unaffected. So a comment-only library edit is not neutral at the syntax-tree level, and a before-and-after comparison of parse trees or diagnostics maps positions back first (`compile-ladder/rung-library-comments/parse-compare.sh`, `remap-lines.py`).
- **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees** (`compile-ladder/rung-int-semantics-walk/REPORT.md`, section 4.1): `throw new FortressError((FObject) Driver.getFortressLibrary().getRootValue(name))` from a `builtinPrimitive` method reaches `Evaluator.forTry` unchanged; the helper is `Int.overflow()` (`interpreter/glue/prim/Int.java:258-261`). Every other Java exception is mapped as before (`FunctionClosure.java:188-196`), so row 336's division by zero still ends the run.
- **The compiled run's class loader takes its first load of a name under the JDK's class-loading lock, and a generic arm's first load is safe on four threads** (`compile-ladder/rung-generic-runtime/REPORT.md` sections 1, 11, 12; row 417). `InstantiatingClassloader.loadClass` runs under `getClassLoadingLock(name)`, as the JDK's `ClassLoader.loadClass` does; no loader in the tree registers as parallel-capable, so the lock is the loader's own monitor, and the explicit loads (`RTHelpers.loadClosureClass`, `RTHelpers.getRTTIclass`, the union instantiation) are under it too. ## The checker and the one library

- The one library binds its natives with `builtinPrimitive("…")`: 424 live bindings in nine files (445 written, 20 inside comments, one `RR32` binding fewer since `RR32` became a sibling of `RR64`), 125 of them in `FortressLibrary.fss`, and the rest of the library is plain Fortress. Beside them, walk loads the Java classes of 32 objects of `native component`s by name and binds `true`, `false` and `Any` at start-up. The interpreter's glue classes take the evaluator's boxed values and cannot be reused by the compiled path; the compiler's natives are static Java methods over plain Java values, called through `import java`: 369 public static helpers in 25 classes of `nativeHelpers/`, which the compiler prelude's 366 native bodies call. Matched by owner, name and signature, then by operation: 147 of the bindings are bound on the compiled path already, so only their binding text changes; 61 have a helper that nothing binds yet, 25 of them under a name the compiler prelude binds to another helper, the 12 wrapping operators among them (row 348); 139 need a new static helper, written from 132 glue classes of about 0.7K lines; and 78 need something else, 36 methods of native I/O objects (`Writer`, `BufferedWriter`, `FileReadStream`, `FileWriteStream`, `Reader`) and 42 with no compiled analogue (reflection, `Thread`, the native arrays, the task trace). The prelude and what it imports hold 369 of the bindings. Every program's output needs the I/O objects: `println` writes through `stdOut`, a native `Writer` (`Library/FortressLibrary.fss:4340-4343`, `Library/Writer.fss:20-24`), so the first compiled program on the one library needs `Writer`'s natives. Source: `perf-probes/prelude/natives-shape.md` § 2, its scripts and every binding's class under `perf-probes/prelude/natives-shape/count/` (`classified.tsv`).
