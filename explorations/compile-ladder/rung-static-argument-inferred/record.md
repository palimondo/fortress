## For FACTS

**The compiled checker instantiates a reduction that writes no static argument by its expected type, else by the type of its body, where the call as written is not accepted; a reduction that is accepted as written is unchanged.**

- The fact: for `__bigOperator(BIG OP(), clauses)` with no static argument written, `reductionApplication` (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Functionals.scala:634`) first checks the call as written, where the big operator has an instance alone; if that is not accepted or its type does not convert to the expected type, it writes the static argument as the expected type, then as the body's type, each only where the type meets the bounds of the big operator's one static parameter, and takes the first form that is accepted and converts. The elements are converted to the instance. A call's argument has no expected type where the call is accepted without one (P-51), so a reduction there runs at its body's type.

## Revival change

### The change

The team's sources and what they say or do:

- The specification directs a reduction's desugaring by the type of its expression, "a sum is desugared with the reduction for the type N of the expression" (`Specification/basic/expressions/reductions.tex:28`), and says of a reference to a polymorphic function that "the static arguments are statically inferred from the context of the function call" (`Specification/basic/expressions/var-ref.tex:38-39`). It gives no rule for either inference.
- The team's checker typed the big operator's call alone, as an argument of `__bigOperator`, and refused a reduction with generators whose big operator's bound names its own static parameter, as `SUM[j <- 0#i] f(j)`: "Could not check call to operator BIG + ... is not applicable to an argument of type ()." It gave a generic function passed as a value the function's own type with its static parameters, and stopped with an internal error, 'F is not in the kind env [][][]', where that type met a parameter type.

What the tree now does:

- A reduction with generators that writes no static argument is accepted by the compiled checker. Where the call is accepted with the big operator instantiated alone (a plain bound), nothing changes. Otherwise the big operator is instantiated by the reduction's expected type, where the type meets the big operator's bound, the reduction so instantiated is accepted and its type converts to the expected type; the elements are converted to it. Otherwise it is instantiated by the type of the reduction's body, a numeral at its default. So `x: RR64 = SUM[j <- 0#n] f(j)` with `f` answering `ZZ32` sums in `RR64`, and `t = SUM[j <- 0#n] f(j)` in `ZZ32`. A reduction written as a call's argument takes its body's type where the call is accepted so. Walk reads a declared type only at a local variable and a top-level or local function's return type, so at a method's return type, a field, a top-level variable or an assignment the two paths sum in different types: write the static argument there in a program for both paths. A big operator with two or more static parameters, as `BIG MIN_MAX`, still needs them written for the checker. Test: `compiler_tests/InferBigOperatorSelfBound`; walk's departure, `tests/XXXReductionDeclaredTypeMethodWalk`.
- A reference to a generic function with one declaration, where an arrow type is expected (a parameter of arrow type, a variable, field or return declared with one, an assignment), is instantiated by that arrow type: `useOne(count)` compiles for `count[\F extends Object\](b: Box[\F\]): ZZ32` and `useOne(g: Box[\ZZ32\] -> ZZ32)`, and a function generic in a `nat` passes at a sized arrow type. The checker refuses, with a message, a reference whose arrow type leaves a static parameter open (one that only the return type mentions among them) and the application of a variable bound without a type to such a reference; write the static arguments, or declare the variable's arrow type. A name with several declarations of which one is generic is not instantiated. Test: `compiler_tests/GenericFunctionAsValueCompiled`, `XXXGenericFunctionAsValueOpenCompiled`, `XXXGenericFunctionAsValueUntypedCompiled`.

The reason, as evidence: the checker's refusal of the model's line `matOffset(i: ZZ32): ZZ32 = SUM[j <- 0#i] matCount(j)` and of the library's three sites with their arguments removed, each 'is not applicable to an argument of type ()' on the earlier code and accepted now; the checker's internal error on `useOne(count)`; walk's instance of a reduction at a local variable's declared type, which the expected type first makes the compiled path share.
