## Revival change

**The change.** The team's walk registers the constructor of a native singleton with its values' class only when the object is made from its name: `makeNativeObject` does it (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/FlatString.java:32-35`, and the same in `Boolean.java`, `Char.java`, `NN32.java`, `RR32.java`), called when the singleton's lazily evaluated cell is first read (`BuildNativeEnvironment.java:144-162` at a874948ac, `forObjectDecl1`). So the team's library names the object `FlatString` as a value before its first native string: `FlatString; (* This initializes the constructor for FlatString before its type is used (in the next line). *)` (`Library/FlatString.fss:29-30` at a874948ac). The tree now registers each native singleton's constructor as walk binds the singleton in its component's environment (`BuildNativeEnvironment.java:161-163`), and the library names no native object as a value: `ProjectFortress/tests/NativeStringsReadyAtLoadWalk.fss` binds, prints and measures a string and `lineSeparator` under walk without the line. The reason, as evidence: with the team's mechanism and without the line, every walk program dies as the library loads, 'NullPointerException: Cannot read field "selfType" because the return value of "com.sun.fortress.interpreter.evaluator.values.FNativeObject.getConstructor()" is null' (`harness-one.sh` on the program above, the base's walk with the line taken out); and the compiled path refuses such a name as a value once the object is compiled over a payload class, 'Can't compile the number type FlatString as a value yet' (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:7019`).
