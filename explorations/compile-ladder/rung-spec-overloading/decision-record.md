## 2. The sentence and its history

- **The sentence.** "Although there may be multiple declarations with the same functional name, it is an error for their static parameters to differ (up to α-equivalence), or for one declaration to have static parameters and another to not have them. Hence, static parameters do not enter into the determination of which declarations are applicable, so we ignore them for most of this chapter" (`Specification-1.0-frozen/basic/overloading.tex:100-108`), with its echo "Overloaded declarations must have static parameters that are identical (up to α-equivalence) ... static parameters ... are ignored in the remainder of this chapter" (`Specification-1.0-frozen/advanced/overloading.tex:95-103`).
- **Its date and author.** It is in the earliest reachable git copy of the LaTeX, `0f49d8698` (2009-11-06, Sukyoung Ryu, "[spec] Added the entire spec files. The next task is to integrate the technical decisions since 1.0.", `git show 0f49d8698:Specification/basic/overloading.tex`, line 108); the conversion severed the links before it (`research/authorship.md`), so its authoring commit is not recoverable (`explorations/reviews/mie-probes/spec-sentences-dated.md`).
- **The 1.0 section it displaced.** The Fortress 1.0 release of 2008 has instead Section 15.6.1, "Type Relationships with Static Parameters": "For type parameters, we use their bounds as their supertypes. As with the rest of this chapter, the type relations described in this section may be replaced when the static type checker and the type inference engine are implemented." (`Specification-1.0-frozen/fortress.1.0.pdf`, Section 15.6.1; read with `pdftotext`, the text at lines 5232-5238 of its output.) The section expected its own replacement.
- **Walk since 2007.** `3e05c3424` (2007-05-21, David Chase): "Changed overloading to implement (roughly) the "nice" proposal where functions with different numbers of static parameters can all be overloaded together"; `b176e1440` (2007-06-27, Jan-Willem Maessen): "Removed a tonne of gratuitous type parameters now that we support non-homogenous parameterization of overloadings". Neither path has enforced the sentence since (FACTS, "The compiled checker does not enforce the specification's sentence that overloads may not differ in static parameters").
- **The paper.** Allen, Hilburn, Kilpatrick, Luchangco, Ryu, Chase and Steele, OOPSLA 2011 (`Papers/Types/`): a generic declaration is applicable when one of its instances is (`Papers/Types/setup.tick:393-397`); specificity by applicable sets, checked as subtyping of existential domains (`Papers/Types/rules.tick:84-116`); the three rules (`rules.tick:158-180`); existential reduction (`Papers/Types/exc-reduction.tick:1-60`): under the assumption that an intersection is not `Bottom`, the constraints are gathered and unified, and where the premises fail the existential is related to itself, not to `Bottom`. The compiled checker applies these rules (`ProjectFortress/src/com/sun/fortress/scala_src/overloading/OverloadingOracle.scala`).
- **The restart.** The team's 2012 restart of the chapter goes from the operator note straight on where the sentence stood (`Documentation/Specification/Prose/Language/overloading.tick:100-114`), and its Types chapter gives function types holding arrow and universal arrow types together (`types.tick:553-558`, `:794-801`) and drops from a quantified type a static parameter that appears in none of its types (`:764-767`).
- **The way back and its price.** Enforcing the sentence (the overloading judgement's option 3) refuses every set with differing lists on both paths, lifted methods included: 179 library api pairs under the narrow reading and 335 under the wide one, the tower's own method implementations among them (`explorations/reviews/mie-probes/scope-call-site-dispatch.md`; `explorations/reviews/overloading-judgement.md` section 3.2), and it would undo `b176e1440`'s removal of the padding. It is the route back if the model is ever abandoned; the Appendix I entry keeps the sentence's text.

## 3. The model the text states (answer 9, POSITIONS 2026-09-26)

- `Specification/basic/overloading.tex:100-110`: declarations of one name may differ in their static parameters; a declaration with static parameters is read over its instances. `:149-155`: the static arguments a call writes are substituted; those it does not write are inferred after the selection. `:194-199` and `:235-239`: applicability when some instance within the bounds is (named and dotted calls). `:365-375`: specificity by applicable sets, the paper's definition; "No static arguments are inferred for the comparison".
- `Specification/advanced/overloading.tex:108-122`: the echo replaced by a pointer. `:530-650` (the new section "Declarations with Static Parameters"): the three rules as the paper states them, the Return Type Rule over every instance; exclusion by existential reduction with instantiation exclusion, every static argument but an operator argument counting (POSITIONS 2026-09-26, the second batch-5 answer); the gather removed, on the skeptic's correction 2, the sentence that two parameter types are not taken to exclude only because the static arguments at which they could meet are ones a bound rules out, since the compiled checker takes that step for a named forced argument (`SkExclBound3`) and not through ancestors (`DifferMIE`), and no decision settles it: "Passages not yet revised" names the question; the example pair (the shape of the probe `GenPlainRTR`, `explorations/reviews/overload-static-params-ways/probes/GenPlainRTR.fss`, the paper's `baz` pair of `Papers/Types/examples.tick:146-175` over `Shape` and `Round`) as "Not allowed", with the paper's repair (the second declaration generic with the tighter bound).

## 5. The dispatch sentence (item 30 and the paper's instance rule)

- `Specification/basic/overloading.tex:312-332` in the dispatch paragraph, the callout `:333-349`, the examples `:377-405` after the definition of "more specific".
- **Which declaration runs** is decision 1 of 2026-09-28 (the most specific declaration applicable to the values, a generic one applicable when some instance within its bounds fits), confirmed by item 30's decision (POSITIONS 2026-09-29, PLAN item 30).
- **At which instance** is the paper's rule (POSITIONS 2026-09-29, a type parameter that a call's arguments do not fix): [Solve-Step] (p. 11:19) takes "the intersection of the upper bounds", declared and computed; [R-Method] (p. 11:17) carries the call's static type to run time and matches it against the declared return type; the team's assumed union of the lower bounds could not be proved (section 5.4, p. 11:25) (`research/extracts/ParkPOPL2019-extract.md` section 4.2; `explorations/reviews/decisions-review/popl-recheck.md` section 1.6). The text: the intersection of the declared bound (`Any` if none) and the bounds that the arguments' dynamic types and the call's static type place on the parameter; fixed by the value where the parameter is a static argument of a trait in a parameter type (instantiation exclusion, cross-referenced to `\secref{trait-types}`); never `BottomType`, never the union.
- **The difference named for Pavol's review.** The paper's dispatcher solves every call this way, the declaration the static call selected included. The text keeps, for a declaration the static call selected, the instance inferred at the call (as item 30's judgement words it, `explorations/reviews/plain-beside-generic-judgement.md` section 5). The two differ only for a type parameter that neither the call's static type nor an invariant position in a parameter type constrains, such as a parameter that is the whole type of a parameter and does not appear in the return type: the static inference takes the narrowest candidate of the arguments' static types (the inference chapter), the paper's dispatcher the declared bound. By reading, no program's value turns on it; which instance runs is observable only through a value of a generic type built from the parameter.
