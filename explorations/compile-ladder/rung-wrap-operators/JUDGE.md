## 3. The text is not a property of the program on the untouched tree

- On the base tree, with the JVM's default flags, the same file names `a(x:Sub1,y:Base)` first in 11 of 16 runs and `a(x:Base,y:Sub2)` first in 5 (`probes/order/order-repeat-base.txt`, runs 1-4 and 5-16, machine line at its head). - Neither the launcher nor the gate pins the JVM: `grep -n 'ActiveProcessorCount\|UseSerialGC\|TieredStop'` finds nothing in `bin/fortress`, `build.xml` or `ProjectFortress/build.xml`. Only the comparison runner pins it (`explorations/compile-ladder/rung-wrap-operators/count-run.sh:20`, copied from `explorations/compile-ladder/rung-walk-overflow/count-run.sh:18`). So the file counted as "stable" only because the comparison's three passes all ran pinned; under the flags every user and the gate run, it varies on the base already.
- In the gate it varies for one more reason: `testSystem` runs four shards in parallel, each a forked JVM with no pinning flag (`build.xml:1171-1197`, `:1206-1211`), and runs each interpreter test in-process in its shard's JVM (`ProjectFortress/src/com/sun/fortress/tests/unit_tests/FileTests.java:332`; `InterpreterTest`, `:708`, runs the file through `Shell` in the same JVM, `:722-729`), so the order also depends on every test that ran before it in its shard, and D's new file moves the shards' sorted order (`CLIMB-BATCH-5.md` section 4).
- The mechanism, by reading, as the worker gives it, each line opened: `FType`'s hash is a function of a global serial counter (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/types/FType.java:96-101`, returned by `hashCode` at `:88-90`); a method signature's hash is built from its domain types' hashes (`interpreter/evaluator/values/SingleFcn.java:87-95`); an object's methods are collected in a `GHashMap` keyed by that signature (`interpreter/evaluator/values/Constructor.java:181-182`) and iterated in hash order (`:325-326`); the overloading check walks the resulting list pairwise (`interpreter/evaluator/values/OverloadedFunction.java:229-251`) and prints the pair as "(first)" and "(second)" in list order (`:550-557`). How many `FType`s exist before `Base`, `Sub1` and `Sub2` are made therefore decides the order, and any change to the library, or to the threads that load it, can change that number.
