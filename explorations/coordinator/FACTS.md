# Facts on record

## Execution model

- F-7 **Walk and the compiled path share the parser and the phases, and only the compiled path runs the static type checker.** Walk switches the checker off, and no switch turns it on. So walk checks no static types of expressions: an ill-typed expression shows only when it runs, as a failed dispatch or as another run-time error, such as F-239's refusal of an `if` on a value that is not a `Boolean`. At load, walk refuses some ill-formed declarations: the `fortress-repo` skill's `interpreter.md`, "What walk checks", lists them, with their evidence in F-29 (`comprises` clauses), F-142 (the Meet Rule for Functional Methods) and F-145 (uncovered abstract methods and `override`). The phases and where the two paths part: the skill's "How a program runs". Detail: `explorations/repo-internals.md`, "The two worlds".
- F-9 **`fortress typecheck` checks a program against the compiler's library, `Library/CompilerLibrary.fsi`, so it is no oracle for walk programs.** `Shell.java` calls `useCompilerLibraries()` for the command (row 69). P-12 has walk run the checker on its own programs after the switch-over, and walk cannot do so as it stands: it runs with type checking and the Scala checker off, the Java checker is gone (`compiler/StaticChecker.java:228-229`), and it has no case for the `CoercionInvocation` nodes that the checker inserts, by reading (row 833).
- F-11 **The code generator boxes every number, and boxing is the main representational cost of microGPT-shaped array code.** So a compiled `RR64` loop holds no `dadd` or `dmul` (the `fortress-repo` skill, "The compiled runtime"). In Java models of microGPT's three kernels, boxed elements cost 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]`. No such kernel compiles yet: the compiler prelude has no array type (row 305), and the arrays reach the compiled path with the one library (P-37). In a hot compiled loop, escape analysis removes the temporary boxes, and one box per assignment to a mutable variable per iteration stays (F-301), as long as C2's inline depth reaches each box's constructor chain (F-302). Detail: `perf-probes/kernels/REPORT.md` sections 2 and 4; `perf-probes/helper-calls/REPORT.md` section 4.
- F-12 **On the compiled path, the scalar `RR64` loop `bench1t` ran in 0.74 s in one session's measurement; the loop still pays for its generator, for boxing and for a transaction check at each use of its accumulator.** `bench1t` is `for i <- seq(1#20000000) do acc := acc 0.9999999 + 0.0000001 end` on a `var acc: RR64`, with both literals written in the loop. The time is the median of three loop-only runs at one thread (`compile-ladder/rung0/REPORT.md`, "The four timings"). Times taken in different sessions differ on this machine, so compare only times from one session. What the loop does, read in its bytecode (`perf-probes/boxing/REPORT.md` sections 4 and 5): the `seq` loop becomes the compiler prelude's `countedseqloop`, which runs the iterations in order by a recursive split over boxed indices, with a closure call per element; each value is boxed (F-11); and the accumulator is a volatile cell whose read and write each first call `BaseTask.inATransaction`, as for every mutable local (F-40, what a size costs at run time, whose sized loop pays the same check). Within the boxing and the cell, the report counts four allocations per iteration, an interface call to the native wrapper and the casts, the part that unboxed doubles and `double[]` would attack. No share of the 0.74 s is measured.
- F-17 **The bytecode cache can come up empty after a library order that reports exit 0.** Running the same commands again, one at a time, made the jars. The cause is not known. Check the five jars before a compiled run (the `fortress-repo` skill's `build-and-caches.md`, "The library order"). Detail: `perf-probes/boxing/REPORT.md` section 1.
- F-18 **On the compiled path, the class loader makes the class of a generic instantiation at its first use, by rewriting the template's bytecode with ASM, and the rewriting only renames, so it gives no instance a `double[]` field.** The class is `InstantiatingClassloader`; the `fortress-repo` skill's "The compiled runtime" gives the mechanism. A size is part of the made class's name, as in `pNatMeth$Box⟦3⟧`, the object `Box` at size 3 in the probe component `pNatMeth`. Inside the class, the size's descriptor is `RTTIsize.of("<n>")` (F-129). A field of the template's type `T`, `LT;`, becomes `LFRR64;` in `Box⟦FRR64⟧`, and `[D` is no class name, so stamping alone keeps every number boxed (F-11). The team's direction for unboxing builds on this class per instantiation (the plan in `compiler/optimization/Unbox.java`; the loader's empty "expando" stub, `runtimeSystem/InstantiatingClassloader.java:168-172`), but a loader that stamps an `RR64` instance with a `double[]` field, way A4 of array decision A (P-85), does not exist and is unmeasured. Walk instantiates generics in its own evaluator, not by classes. Detail: `perf-probes/nat/java.md` section 1; `coordinator/array-design.md` section 2 (probe 1); `reviews/array-design-ways.md` section 3, way A4.
- F-19 **By the specification, the iterations of a `for` loop, the elements of a tuple, and the arguments of a call or an operator may run in parallel, and a program must assume that they do.** A `for` loop is sequential only if every generator is, as `seq(g)` or `sequential(g)` makes it. An implementation may also run them one after another (`evaluation/parallelism.tex:88-90`), so a program cannot count on parallel runs either. For the elements of a tuple and the operands of an operator, each path starts a task only where it judges it worth it: walk by `TupleTask.worthSpawning`, which also governs a call's arguments, and the code generator by `ParallelismAnalyzer`. Compiled, a function call's arguments run in order (`CodeGen.evalArg`). A `for` loop over a range without `seq` runs by splitting the range into `do … also do … end` blocks. Under walk, every such block is a task, and walk's library splits down to single elements (`Library/RangeInternals.fss`). Compiled, the first block runs in place, and each other block forks only where `BaseTask.forkIfProfitable` judges it worth it, as tuple elements do; the compiler prelude's `parloop` splits down to `FORTRESS_LOOP_CHUNK` elements, 1 by default. `FORTRESS_THREADS` sizes the pool of worker threads (the `fortress-repo` skill, "Parallelism and mutable state"). By grep, no program under `explorations/`, the model programs and the probes, writes `spawn`, which starts an explicit thread, or an `also do` block, so their parallelism comes only from loops, tuples and arguments. The revival's tests under `ProjectFortress/` write both. Source: `Specification/basic/expressions/for.tex:28-32`, `tuple-expr.tex:23-24`, `operator-app.tex:58-59`, `evaluation/parallelism.tex:50-80`.
- F-20 **Sizes, the `nat` and `int` static parameters, are values at run time; they check shapes, and no optimization uses them (F-40, what a size costs at run time).** The compiled checker checks them (F-67), and a sized program loads and runs compiled (F-129). Under walk, `Vector` and `Matrix` take their sizes from an array built at run time: `f[\nat s\](v: Vector[\RR64,s\])` takes `s` from `array[\RR64\](3)`, and overloads on `Vector` and `Matrix` dispatch by rank (row 214). The array-type syntax `T[n]` with a `nat` parameter does not unify with such an array, "Cannot unify … with ArrayType", where `T[3]` with a literal size does (row 23). Walk matches sizes at dispatch. A mismatch, such as a `DOT`, the library's inner product, of a 2×3 matrix by a 2×3 matrix, whose inner sizes differ, is a `ProgramError`, "Failed to find any matching overload", that no `catch` takes (row 254). Source: `Specification/basic/trait-parameters.tex:96`.
- F-21 **The February 2011 Working Draft's bare `Nothing`, one object for every `T`, is accepted on neither path: the grammar refuses its `excludes` clause, and without that clause `T` is undefined.** The declaration is `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:40`). Both paths stop at a syntax error at `excludes`, since an object has no `excludes` clause (measured: `reviews/spec-refused-examples.md`, E4). Without that clause, both report `T is undefined` at the `T` of the `extends` clause: a `where` clause on an object binds no type variable of its `extends` clause, as row 17 holds for a trait. Today's specification refuses the form in any case, by instantiation exclusion, and marks it "Not allowed" beside the parametric `Nothing[\T\]` that the interpreter's library writes (F-167). P-90 still calls the bare `Nothing` future work that waits for such `where` clauses, not tried before then. Detail: `compile-ladder/rung-maybe/REPORT.md` section 5.
- F-22 **When a component's name differs from the api that it exports, neither path finds the component, for an exported function or variable alike.** The specification resolves an imported api to any component that exports it (`Specification/basic/components/overview.tex`). The tree looks only under the api's name, unless a user maps the api to its component by hand with `LinkShell`'s `alink` or `clink`. The linker's component repository looks this way (`Linker.whoIsImplementingMyAPI`), so `fortress link` and walk print "Could not find an implementation for API … on path" before any code is generated. The code generator names a reference to an exported declaration after the api, and the declaring class after the component. The link step rewrites such a reference to the component only when the repository names it, so files compiled one by one, without `fortress link`, die with `NoClassDefFoundError`. The missing step is the repository's: finding the component that exports the api. The report names two repairs, neither built: the repository could search the source path for that component, or the code generator could emit api-named forwarders, for which three comments in `CodeGen.java` leave a place. Walk and `fortress link` need the first. Workaround: name the api after its component. Gated by the expected failure `compiler_tests/XXXExportVarRungXLinked.test` (row 320). Detail: `compile-ladder/rung-export-var/REPORT.md`, "The measurement that separates them".

So a comment-only library edit can change the syntax tree, and a before-and-after comparison of parse trees or diagnostics maps positions back first. Detail: `compile-ladder/rung-library-comments/REPORT.md` section 6, D1.

- F-26 **Under walk, when one of two applicable declarations has static parameters of its own, the call chooses on their declared domains where exactly one lies inside the other, not by the order in which they are written.** It builds P-45, the choice among overloads by declared parameter types, under walk. A declaration has static parameters of its own if it is a generic function or constructor, or a functional method with static parameters in a trait or object without any. Its declared domain, walk's symbolic instance, is its parameter types with each type parameter standing for itself under its bounds. Where neither declared domain lies inside the other, where each lies inside the other, or where neither declaration has static parameters of its own, walk compares the domains of the instances that the call makes. So a functional method of a generic trait or object is compared on its instance, and a generic dotted method is chosen by F-253 (a generic method at a dotted call, also chosen on declared domains). If the chosen declaration is generic and its instance takes an argument only by a conversion, walk converts the argument and dispatches the converted arguments again, so the most specific declaration for the converted values runs. In two cases walk keeps the chosen instance, with no second dispatch: an overloaded dotted method, and a position whose conversion `Coercions.coercionFor` does not find, such as a tuple converted element by element. Two generic overloads whose static parameters agree in name, kind and bounds share one symbolic instance, even if their `where` clauses differ; no test or library declaration has such a pair (row 478). Gated by `tests/DispatchDeclaredDomain.fss` and `DispatchConvertedAgain.fss`. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.1, 5.2 (the second dispatch) and 5.5 (the symbolic instance).
- F-27 **Walk's load check reads again two kinds of overload pair that its parameter-by-parameter check refuses, and accepts those that pass: a generic declaration beside a plain one, read on their declared domains, and two plain top-level functions, not methods, whose overlap other declarations cover through `comprises` clauses.** To test a cover, the check cuts the overlap of the two domains, position by position, into parts by the `comprises` clauses. Each combination of parts must lie inside the domain of one declaration without static parameters that lies below both. So several such declarations may together cover the overlap. A search that does not settle refuses. Where neither lies inside the other, the pair needs the same cover, or declared domains that exclude each other read whole (F-258, exclusion over the whole parameter type). Equal declared domains are refused. It builds under walk P-46, by which a conversion never changes which declaration runs when one already fits, and P-60, by which several declarations below both may cover a meet. Two generic declarations are read on their declared domains too (F-252: the No Duplicates, Return Type and Meet Rules, each over its own instances). Walk still refuses the valid example of the POPL 2019 paper on symmetric multiple dispatch (`research/extracts/ParkPOPL2019-extract.md`, p. 11:13), a set of three generic declarations (row 539). Gated by `tests/ComprisesMeetWalk.fss` and `GenericBesidePlain*.fss`, among others. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.3 (generic beside plain) and 5.4 (the cover).

- F-173 **The specification's type-inference chapter states the rule that the compiled checker builds: the declaration is chosen first, then its static arguments are inferred.** It states P-46, P-48 and P-49. One that is the whole declared type of one or more parameters, as `T` is of `x: T`, and that nothing else fixes, takes the narrowest type, within its bounds, that every one of those arguments has or converts into: `ZZ64` for a `ZZ32` and an `NN32`. Where there is none, and no numeral settles the tie, it takes its bound, narrowed by what the call's expected type requires of the return type (P-48). So does a type parameter that neither an argument nor the expected type fixes. Inference never gives a type parameter `BottomType`. The compiled path departs from the chapter in these ways, among others. Its prelude lacks the coercion of `NN32` into `ZZ64`, so a `ZZ32` and an `NN32` instantiate a type parameter at `ZZ`, not `ZZ64`; no callout names this (row 442, `compiler_tests/XXXInferPromoteNN32`). The callouts at `Specification/basic/inference.tex:234-296` and `:361-422` also give walk's departures, such as the return type `BottomType` that walk gives a function expression that declares none (row 587). Plain tests gate the rule for a type parameter that is a parameter's whole type, at its bound where no argument type is narrowest, on both paths: `compiler_tests/InferLone*` and `tests/InferLone*Walk.fss`. Detail: `compile-ladder/rung-instance-bound/REPORT.md` (the bound rule); `Specification/basic/inference.tex:45-122` (the chapter's rule).
- F-174 **The specification states the type group's 2011 overloading model: declarations of one name may differ in their static parameters, and a declaration with static parameters is read as one declaration over all its instances within its bounds.** It states P-45 and P-42. The section "Declarations with Static Parameters" states the OOPSLA 2011 paper's three rules: No Duplicates, Return Type and Meet. It gives one more restriction as the compiled path's, not the language's. Where one generic declaration is more specific than another with as many static parameters, the two must declare them of the same kinds, position by position. Also, the more specific one's return type must be a subtype of the other's when their static parameters are matched by position, so the checker refuses an override whose return type reorders its static parameters (row 398, fixed). The section "Principles of Overloading" forbids overloading a functional whose single parameter's type is a type parameter with the bound `Any` written, as `T extends Any`. A type parameter with no `extends` clause, whose bound is also `Any`, is exempt. Both paths refuse such an overload: the checker in `OverloadingChecker.checkBoundAny`, and walk since row 534's fix. Neither path runs every set that the rules allow. Appendix I's entry "Overloading with static parameters" names the sets that each path fails. In row 542, the checker refuses a generic declaration beside a plain one over an object type, as `ident[\T\](x: T): T` beside `ident(x: Circle): Circle`. In row 537, the code generator fails on two generic declarations whose bounds differ. In row 539, walk refuses at load the 2019 paper's valid set over an array list and a list. In rows 779 and 780, walk fails on two generic functional methods one of whose declared domains lies inside the other's: in a trait or object without static parameters it refuses them at load, and in a trait with static parameters it loads them, but a call to which both apply fails. - F-176 **The specification allows arithmetic in a size, and two size arguments are identical when they are written alike once each operation whose operands are numerals is replaced by its value.** It states P-55. By the grammar, a size is a numeral, a name, a sum, a difference, a product, a power to a numeral or a name, or a bracketed size. So `2 3` and `6` are identical, but `s0 s1` and `s1 s0` are not. Two types are identical when they have the same name and identical static arguments, sizes compared this way. Two sizes are known to differ when they are two different numerals. A static parameter, or a size in which one occurs, is not known to differ from a numeral, since an instance may make them equal. F-146 gives the compiled checker, and F-222 walk's arithmetic. When walk infers a size parameter from a call's argument type, it matches a numeral and binds a name, and solves no size written as an operation: read in `IntNat.unifyStaticArg` (`interpreter/evaluator/types/IntNat.java:126-147`), and observed in row 767. Source: `Specification/basic/types-vals-vars.tex:49-62`; `Specification/appendices/grammars/concrete-syntax.tex:533-547` (`IntExpr`).
