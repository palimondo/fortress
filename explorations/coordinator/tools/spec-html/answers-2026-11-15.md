# Answers to the notes of 2026-11-15

Every program below ran on 2026-11-15, at commit `d9918f9098`, from a scratch folder with a private caches folder.
The two ways to run a program have these names here:

- **walk**: the interpreter. `fortress P.fss` and `fortress walk P.fss` are the same command.
- **compiled path**: `fortress compile P.fss` writes JVM bytecode, and `fortress run P` runs it.

A **row** is a row of the gap ledger, `explorations/fortress-gap-ledger.md`.
**P-N** is a decision in `explorations/coordinator/POSITIONS.md`.
**F-N** is a fact in `explorations/coordinator/FACTS.md`.
The **Working Draft** is the team's unrevised text of February 2011, in `Specification-1.0-frozen/`.

## Note 3. About this working draft: "widening coercion"

https://palimondo.github.io/fortress/specification/preface.html#p-f85a28b6

Yes. Widening coercion is built on both paths today.

- Each wider number type declares a `coerce` from each narrower one. A value converts at a call, at a typed binding and at an assignment (P-74).
- The compiled path chooses the coercion by the static type. Walk has no static types, so it chooses by the value at run time (P-59).
- Two cases still fail under walk. A body with a declared return type is not converted (row 387). The elements of a tuple are not converted (row 395).

## Note 4. About this working draft: "some modifiers (override, io, atomic, value, ...)"

https://palimondo.github.io/fortress/specification/preface.html#p-0ee6a8b8

Yes for `atomic` and `value`, with limits on the compiled path. `io` runs and nothing checks it. `override` works under walk only.

- `atomic` as a block, `atomic do ... end`, runs on both paths. As a function's modifier it runs under walk: a program with `atomic bump(): () = n += 1` printed `100` after 100 calls. The code generator refuses that modifier: "Don't know how to compile this kind of FnDecl" (row 304 holds the local function; row 650 holds the same refusal for `override`). `atomic` as an expression, without `do`, does not compile either (`references/compiler.md`, "What the compiled path cannot compile yet").
- `value` works on both paths. Two value objects of one type are equivalent when their fields are (P-168; row 906, fixed). Walk still lets a value object declare a `var` field (row 112). On the compiled path the modifier does not unbox the fields.
- `io` is accepted on both paths. A program with `io say(s: String): () = println s` printed its line under walk and compiled. Neither path checks what the modifier promises.
- `override`: walk checks at load that the declaration overrides something. The compiled checker accepts an `override` that overrides nothing (row 653). The code generator refuses every `override` (row 650).

## Note 5. About this working draft: "Non-type static parameters"

https://palimondo.github.io/fortress/specification/preface.html#p-56c0c623

Yes, `nat` is one of them, and it is built. A static parameter that is not a type has one of six kinds: `nat`, `int`, `bool`, `dim`, `unit` and `opr`.

- `nat` and `int` (sizes): built on both paths. The checker computes arithmetic on numerals and compares other sizes by their written form (P-55). Two open defects: a size of 2^31 or more read as a value (row 962), and a compiled call whose `where` clause introduces a size (row 867).
- `bool`: not usable. The compiled checker refuses to infer one (row 307). Walk stops at load on a method whose parameter type has one (row 761).
- `opr`: runs under walk. On the compiled path, a generic object with an `opr` parameter dies at run time (row 366).
- `dim` and `unit`: not built on either path (row 26).

## Note 6. About this working draft: "where clauses and conditional extension"

https://palimondo.github.io/fortress/specification/preface.html#p-3e0c2dfb

Three forms of the `where` clause are built, and conditional extension is one of them (P-151). The other forms that the specification describes are not built.

The three forms:

- Conditional extension. An `extends` entry has a `where` clause, and the type extends the parent only where the condition holds. The library's `List[\E\]` extends `LexicographicOrder[\List[\E\],E\] where { E extends StandardTotalOrder[\E\] }`.
- A condition of a function or a method on its static parameters, checked at the call.
- A type variable of a `where` clause in a `comprises` clause: `AnyList comprises List[\E\] where [\E\]`.

What does not hold yet:

- Walk and the compiled run time apply a conditional extension at every instance, also where the condition fails (row 774).
- The compiled checker lets a member that it checked under the condition be called where the condition fails (row 773).
- Under walk, a dotted call runs although it breaks the method's condition (row 777).
- The code generator emits no code for a `where` clause, so compiled code does not check one (F-181).

### The whole list of the preface, today

One item for each feature of the preface's list, in its order.

- **Widening coercion.** Built on both paths (P-74, P-59). Note 3 has the limits.
- **Multifix operators.** Walk never looks for a declaration with three or more operands. It makes binary calls (row 29). The compiled checker can choose a multifix declaration for a chain `a OPLUS b OPLUS c` (F-221).
- **Type coverage check.** I read this as the check that an object's bodies cover each abstract method that it inherits. It is built on both paths (P-147, P-60). Walk skips it for a generic object (row 665).
- **Generic overloading check.** Built on both paths: overloads may differ in their static parameters, under three rules (P-45, P-152). Walk departs on two functional methods of one type (rows 779, 780).
- **Definite assignment check.** Built on neither path. A local variable declared without an initial value stops the code generator (row 1001, new today).
- **Keyword and varargs parameters.** Keyword parameters are built on neither path (row 652). A varargs parameter runs under walk in a function (row 130), not in an object's constructor (row 11). The compiled checker types one (F-86). The code generator refuses it (row 624).
- **Some modifiers.** Note 4.
- **Qualified names.** Not built. Under walk, `FortressLibrary.println("x")` stops: "Variable FortressLibrary is not defined."
- **Identifiers including connecting punctuation.** `my_count` is a name on both paths: a program that binds and prints it printed `3` under walk and compiled. `W_1` is not an identifier: `_1` reads as a radix (row 15).
- **ASCII conversion.** Only the conversion of names is built. The appendix's own draft note says so (`Specification/appendices/ascii-to-unicode.tex:15`). `∑` is not read as `SUM` (row 5).
- **Array comprehensions.** Not built on either path (row 50).
- **Reduction variables.** Not built. `acc += e` in a parallel loop loses updates. Write `atomic do ... end` around the update (row 59).
- **Distributions.** Not built. Neither library declares a `Distribution` trait.
- **Matrix unpasting.** Not built (row 108).
- **Non-type static parameters.** Note 5.
- **Dimensions and units.** Not built on either path (row 26).
- **Tests and properties.** A `test` function runs under `fortress test` (row 120). The form `test Id[gens] = Expr` and every `property` declaration stop their component on both paths (rows 121, 122; F-182).
- **Type aliases.** `type Idx = ZZ32` stops its component on both paths (row 18).
- **Where clauses and conditional extension.** Three forms are built (P-151). Note 6.
- **Abstract function declarations.** In a trait they work on both paths (P-147). At top level they run on neither path (`Specification/basic/functions.tex:444`). Walk stops: "Function definition should have a body expression." The code generator stops: "Abstract function declarations are only supported in traits."
- **Checked, deferred and chained exceptions.** Neither path checks a `throws` clause (row 352).
- **Contract checking.** Walk runs a function's `requires` and `ensures`. The code generator refuses a function with a contract (row 701). Both paths drop the contract of a trait or an object (row 781).
- **Static expressions.** An expression of numerals alone folds to one exact value on both paths, and two joined string literals fold to one (P-173, P-171). A size may hold arithmetic (P-55). Static range types are not built.
- **Some types.** `ZZ` and `QQ` are in walk's library (`Library/FortressLibrary.fsi:720`, `:395`). The compiler's library has `ZZ` and no `QQ`. No library declares `HeapSequence`, `LinearSequence` or an unbounded natural type.
- **Tail-call optimization.** Walk has none: a tail call 200,000 deep overflowed a 64 MB stack.
- **Import API names.** Not built. `import api List` stops under walk: "Not yet implemented: 'import api APIName'; try 'import APIName.{...}' instead."
- **Components linking.** `fortress link` joins a compiled component with the components that implement the apis that it imports. It finds a component only under its api's own name (F-22, row 320). Notes 11 and 13 say what else of linking was never built.
- **No entry.** The record holds nothing on these, and I ran no program for them: varargs expressions, Unicode canonicalization, object copy, unboxed types, mutual recursion in value objects, the thread fairness guarantee, some operators on aggregate expressions, some functions of the "other expressions" section, and the compound APIs check.

## Note 8. Chapter 1, section 1.1: "Although Fortress is statically and nominally typed, types are not specified for all fields, …"

https://palimondo.github.io/fortress/specification/intro.html#p-284c2aab

"Nominally typed" means that two types are the same type only if they have the same name. The inference of left-out parameter types was a wish: the team never wrote how it works, and only one case of it is built.

**Nominal typing.**
A trait type is known by its name and its declared `extends` clause. Two traits with the same methods are still two types. Swift's protocols and Scala's traits work the same way. The opposite is structural typing, where a type is known by its shape. Fortress has both: trait types are nominal, and tuple types and function types are structural (`Specification/basic/types-vals-vars.tex:21-26`). So `(ZZ32, String)` needs no declaration.

**What the specification says of left-out types.**

- The introduction's sentence is the team's. Versions 1.0 alpha, 1.0 beta and 1.0 print it too.
- The Working Draft's chapter on type inference was a heading and two draft notes. The first note reads: "This chapter will include the Fortress static type inference mechanism." (`Specification-1.0-frozen/basic/inference.tex`; F-169).
- The one rule that the team wrote is in the chapter on components. A declaration of a component takes the types that its api declares for it. After that, "type inference is performed over all program constructs that still include elided types" (`Specification/basic/components/type-inference.tex`). The team never described that second step.
- The revival wrote the inference chapter for a different thing: the static arguments of a call, as the `ZZ32` in `identity[\ZZ32\](3)`. Its first paragraph says that the inference of left-out types over a whole program is "not yet described" (`Specification/basic/inference.tex`).
- Appendix I records this, under "The type of a parameter that a declaration leaves out" (`Specification/appendices/changes.tex`).

**What each path does today.**

- A return type may be left out on both paths. The checker types the body.
- A parameter of a function expression may be left out on both paths, where the context expects a function type.
- A parameter of a function that the component's api declares may be left out on both paths (row 178). Note 9 has the program.
- Any other parameter without a type is refused on the compiled path: "Missing parameter type for x" (F-266, row 405).
- Walk has no static types. It runs an untyped parameter and takes any value for it (row 176).

This program leaves out a return type and a function expression's parameter type. It prints the same under walk and compiled:

```fortress
component LeftOut
export Executable

twice(x: ZZ32) = x + x
apply(f: ZZ32 -> ZZ32, x: ZZ32): ZZ32 = f(x)

run(): () = do
    println twice(21)
    println apply(fn n => n + 1, 41)
end

end
```

```
42
42
```

**Is it a good idea?**
For parameters, the evidence says no, and the project's rule agrees: "Write every parameter type" (`references/revival-changes.md`, "Implementation limits"). Three reasons:

- With overloading, a parameter's type is what chooses the declaration. An inferred type would let a change in a body change which overload a caller gets.
- The team's own draft note names a circle: to group `a b c` the checker must know which names are functions, and to infer that it must know how they are used (`Specification-1.0-frozen/basic/inference.tex`).
- The team's last text still has no rule for it.

The case that is built is the useful one. The api states the types once, and the component does not repeat them. That is like a C header: the signature is stated once.

## Note 9. Chapter 1, section 1.1: "These design decisions are motivated in part by our goal of making the scientist/programmer’s …"

https://palimondo.github.io/fortress/specification/intro.html#p-edfaffe1

At the level of a component, the types come from the api, not from the body. Nothing defaults to `Any` on the compiled path: a parameter that no api types is refused. Only walk behaves as you describe, because it has no static types at all.

**Case 1: the api declares the types, and the component leaves them out.** It runs on both paths.

The api, in `Area.fsi`:

```fortress
api Area
area(w: ZZ32, h: ZZ32): ZZ32
end
```

The component, in `Area.fss`:

```fortress
component Area
export Area
area(w, h) = w h
end
```

The program, in `UseArea.fss`:

```fortress
component UseArea
import Area.{ area }
export Executable
run(): () = println area(6, 7)
end
```

Under walk, and compiled (`fortress link UseArea.fss`, then `fortress run UseArea`):

```
42
```

The two paths differ on a wrong call, `area("six", "seven")`:

- Compiled, it is a static error: "(ZZ32, ZZ32)->ZZ32 is not applicable to an argument of type (String, String)." The checker also types the body with `w` and `h` as `ZZ32`: a body `w.length` is refused, "ZZ32 has no getter called length".
- Under walk it runs and prints `sixseven`. Walk never compares a component with its api (row 841), so `w h` joins the two strings.

**Case 2: a local function's parameter without a type.** It runs under walk only.

```fortress
component LocalUntyped
export Executable
run(): () = do
    twice(x) = x + x
    println twice(21)
    println twice(1.5)
    println twice("ab")
end
end
```

Under walk:

```
42
3.0
```

Then the third call stops the run: "Failed to find any matching overload, args = ("ab","ab")". This is your picture: `x` takes any value, and each `+` is looked up at run time from the values' types. It is not inference. It is the absence of a check.

Compiled, the same program is refused before it runs:

```
LocalUntypedC.fss:4:11:
    Missing parameter type for x
```

A top-level `twice(x) = x + x` gets the same two results: walk prints `42`, and the compile says "Missing parameter type for x".

**Case 3: refused on both paths.** A method that leaves out a type and implements an abstract method.

```fortress
component UntypedMethod
export Executable
trait Greeter
    greet(name: String): String
end
object Polite extends Greeter
    greet(name) = "Good day, " || name
end
run(): () = println Polite.greet("Pavol")
end
```

Walk refuses it at load: "Object Polite does not define an abstract method declared in type Greeter". The compiled path refuses the parameter (row 405). With `greet(name: String)` it runs.

## Note 10. Chapter 1, section 1.1: "In addition to objects and traits, Fortress allows the programmer to define top-level functions. …"

https://palimondo.github.io/fortress/specification/intro.html#p-a3cd883e

In Fortress, a call chooses among overloads when the program runs, by the run-time types of all its arguments. Java, Scala and Swift choose an overload when the program is compiled, by the static types.

**Step 1: one argument.** Both variables have the static type `Shape`.

```fortress
component Dispatch1
export Executable

trait Shape end
object Circle extends Shape end
object Square extends Shape end

describe(s: Shape): String = "some shape"
describe(c: Circle): String = "a circle"

run(): () = do
    s: Shape = Circle
    t: Shape = Square
    println describe(s)
    println describe(t)
end

end
```

```
a circle
some shape
```

Java and Swift print `some shape` twice. They pick `describe(Shape)` at compile time, from the variable's declared type.
Fortress looks at the value: `s` holds a `Circle`, so the most specific declaration that fits is `describe(c: Circle)`.

**Step 2: two arguments.** Every argument counts, not only the first.

```fortress
component Dispatch2
export Executable

trait Shape end
object Circle extends Shape end
object Square extends Shape end

hit(a: Shape, b: Shape): String = "shape, shape"
hit(a: Circle, b: Shape): String = "circle, shape"
hit(a: Circle, b: Square): String = "circle, square"

run(): () = do
    c: Shape = Circle
    q: Shape = Square
    println hit(c, q)
    println hit(c, c)
    println hit(q, c)
end

end
```

```
circle, square
circle, shape
shape, shape
```

Java and Swift print `shape, shape` three times.
Single dispatch, `c.hit(q)`, would choose by `c` alone. To choose by `q` too, Java needs the visitor pattern. Fortress needs nothing.

**Step 3: a tie, and the Meet Rule.** Take only these two declarations:

```fortress
hit(a: Circle, b: Shape): String = "circle, shape"
hit(a: Shape, b: Circle): String = "shape, circle"
```

The call `hit(Circle, Circle)` fits both, and neither is more specific than the other. Fortress forbids the pair before any call runs. Walk refuses the program at load:

```
Overloading of
    (first) hit(a:Shape,b:Circle) ... and
    (second) hit(a:Circle,b:Shape) ... fails because
    (first) b is more specific than (second) b but
    (first) a is less specific than (second) a
```

The **Meet Rule** states the cure. Where two overloads can both fit one call, a third declaration must cover exactly the arguments that fit both. Those arguments are the meet of the two: here `(Circle, Circle)`. The rule has two other ways out: one overload is more specific than the other, or the parameter types exclude each other.

The last program adds the third declaration. It also has a **functional method**: a method that lists `self` among its parameters. It is called as `touches(a, b)`, not `a.touches(b)`, and it dispatches on all its arguments, as a top-level function does.

```fortress
component Dispatch3
export Executable

trait Shape
    touches(self, other: Shape): String = "shape touches shape"
end
object Circle extends Shape
    touches(self, other: Circle): String = "circle touches circle"
end
object Square extends Shape end

hit(a: Circle, b: Shape): String = "circle, shape"
hit(a: Shape, b: Circle): String = "shape, circle"
hit(a: Circle, b: Circle): String = "circle, circle"

run(): () = do
    c: Shape = Circle
    q: Shape = Square
    println hit(c, c)
    println hit(c, q)
    println touches(c, c)
    println touches(c, q)
end

end
```

```
circle, circle
circle, shape
circle touches circle
shape touches shape
```

In Java, `c.touches(c)` picks the receiver's class at run time and the parameter's overload at compile time, so it prints `shape touches shape`. Fortress prints `circle touches circle`. Most Fortress operators are functional methods, as `opr +(self, other: T): T`.

## Note 11. Chapter 2, section 2.1: "After issuing this command, we can no longer refer to HelloWorld component when issuing …"

https://palimondo.github.io/fortress/specification/overview.html#p-136580aa

A fortress, in the specification, is a persistent store of compiled components and apis that also runs the commands on them. The team never built it. The tree has caches instead, and no `remove` command.

**What the specification means.**
"Every component is installed in a persistent database on the system. We think of this database, which we call a fortress, as the agent that actually performs operations such as compilation, linking, upgrading, and execution of components: a virtual machine, a compiler, and a library registry all rolled into one" (`Specification/basic/components/overview.tex:55-63`). A component in it is a compiled unit, not a parsed tree. "The resident fortress" is only the chapter's name for the one fortress that the example's commands talk to.

**What the tree has.**
A folder of caches, `default_repository/caches/`. Your reading fits half of it:

- `bytecode_cache/` holds one jar of JVM bytecode for each compiled component. This is the nearest thing to the specification's fortress.
- `interpreter_parsed_cache/` and `interpreter_cache/` hold walk's parsed trees. They only save walk from parsing again.

A cache is not a fortress. It gives no names to rebind, and it has no commands of its own.

**The chapter's commands, in the tree.**

- `fortress compile`: exists.
- `fortress run`: exists, with another meaning. Note 13 has it.
- `fortress link` and `fortress api`: exist.
- `fortress remove`, `fortress removeApi`, `fortress upgrade` and `fortress upgradeAll`: do not exist. `fortress remove Hello` prints the usage message.

The chapter says so itself, in a draft note at its head: sections 2.1 to 2.3 "are out of date".

## Note 12. Chapter 2, section 2.1: "The first line is an export statement; we ignore it for the moment. The …"

https://palimondo.github.io/fortress/specification/overview.html#p-18267c77

This is a fault of the Working Draft, not of the HTML page. The team took `args` out of `run` on 13 March 2009 and changed the example, but left the sentences around it.

**The editions.**

- Version 1.0 alpha (2006) and beta (2007) print `run(args) = print "Hello, world!"`, and the api as `run: String... -> ()`.
- Version 1.0 (March 2008) prints `run(args) = print "Hello, world!"`, and the api as `run(args: String...): ()`. In these three editions the sentence and the example agree.
- The Working Draft (2011) prints `run() = print "Hello, world!"` and `run(): ()`, with the old sentence: "defines a function run, which takes a parameter named args".

**The change.**
Commit `96f547cea4`, by Jan-Willem Maessen, 13 March 2009. Its message: "Changed Executable api to have no arguments; program arguments are now available from System.args. Another consequence is that the !SimpleExecutable is no longer necessary."

- It changed `Library/Executable.fsi` from `run(args: String...): ()` to `run(): ()`.
- It changed 887 files, among them the specification's example programs, which are real files that the team's tests run (`SpecData/examples/preliminaries/Overview.shell.a.fss`).
- It did not change the chapter's sentences. Those are prose in `overview.tex`.

**Where a program gets its arguments today.**
From the `System` api, as the immutable array `args` (P-170):

```fortress
component Args
import System.{ args }
export Executable
run(): () = do
    println |args|
    for i <- seq(0 # |args|) do println args[i] end
end
end
```

`fortress Args.fss one two`, under walk:

```
2
one
two
```

Until the compiled path moves onto walk's library, a compiled program imports `CompilerSystem`, whose `args` is a `StringVector` (`Library/CompilerSystem.fsi`).

**Your other question.**
Yes: a component that exports `Executable` must define `run` as the api declares it. The compiled path checks this. A component with `run(args: String...): ()` is refused: "Component OldRun exports API Executable but does not define all declarations in Executable. Missing declarations: {run():()". Walk does not check it (row 841): the same component runs.

## Note 13. Chapter 2, section 2.1: "It can be compiled. In this case, the Fortress program is compiled into a …"

https://palimondo.github.io/fortress/specification/overview.html#p-ade874e1

"Resident" carries no technical meaning. Your memory of the commands is right, and the chapter is wrong for today's tree: `fortress X.fss` without a sub-command is walk, and `fortress run` runs only what `fortress compile` wrote.

**The word.**
The sentence defines it: "we often refer to the fortress we are storing components in as the resident fortress". It is the fortress that lives on this machine and takes our commands. Nothing stays in memory between commands.

**What each command does today**, with `Hello.fss` holding `component Hello`:

- `fortress Hello.fss` runs the program under walk. It prints `Hello, world!`. It writes no bytecode.
- `fortress walk Hello.fss` is the same command.
- `fortress compile Hello.fss` checks the static types and writes `Hello.jar` into the bytecode cache. It prints nothing when it succeeds.
- `fortress run Hello` runs that jar on the JVM. It takes a component's name, not a file. It compiles nothing.
- `fortress link Hello.fss` compiles the component, and joins it with the compiled components that implement the apis that it imports.
- `fortress build Hello.fss` builds those components too, then links.

**Where the chapter differs.**

- The chapter says that `fortress run HelloWorld.fss` executes a source file directly. Today that fails: "Could not load Hello.fss".
- The chapter says that `fortress` alone is short for `fortress run`. Today it is short for `fortress walk`.
- Before any compile, `fortress run Hello` fails: "Could not load Hello", "Resource not found : Hello.class". So yes, you must compile before `run`.
- The chapter says that a compiled program is compiled again when its source is newer. `fortress run` does not do that. Walk does read a changed source again.
- So `fortress X.fss` is not `compile` and then `run`. The two paths share the parser and the early phases, and nothing after them.

The chapter describes one program that can be either executed or compiled, with one store behind both. The tree has two separate ways to run a program. The chapter's draft note says that this section is out of date.

## Note 15. Chapter 2, section 2.1: "fortress compile HelloWorld2.fss"

https://palimondo.github.io/fortress/specification/overview.html#p-ffe59943

In the tree, one file holds one component, and the file's name without `.fss` must be the component's name. `compile` takes a file because it reads source. `run` takes a component's name because it reads the cache.

- `fortress compile Hello` fails: "Cannot find file .../Hello". `fortress link Hello` works: `link` and `build` add `.fss` when it is missing. `fortress run Hello` takes the name only.
- A file whose component has another name is refused on both paths: "Component/API names must match their enclosing file names." (row 68).
- A file with no `component` line is a component with the file's name. `Bare.fss`, holding only `export Executable` and `run() = println "Hi, it's me again!"`, runs under walk and compiled, as the component `Bare`.
- A file with two components is refused: "Nested component definitions are not allowed."

So your second guess is the right one for the tree: the correspondence is one to one. The chapter's paragraph on several components in one compiled file describes the fortress design, which was not built. The chapter contradicts itself there: the sentence just before says that a source file "must contain exactly one component declaration".

One more rule of names holds in the tree. An api and the component that implements it must have the same name, or neither path finds the component (F-22, row 320). The specification lets any component export any api.
