# What the field did with the exclusion trade after 2012

## 1. The Fortress type group and Karl Naden after 2012

- **POPL 2019 kept the rule for invariant traits and moved the return-type check to run time.** Park, Hong, Steele, Ryu, *Polymorphic symmetric multiple dispatch with variance*, PACMPL 3 (POPL), art. 11, doi:10.1145/3290324 (text from the Wayback copy of the ACM PDF). The core calculus FGFV has multiple inheritance, variance and reified dispatch. Its [Anc-Same-Trait] rule: "if a class C extends two instances of a trait T, T⟦α⟧ and T⟦ρ⟧, then C also extends some T⟦γ⟧ … that extends both … because the rules guarantee that there always exists a single minimal ancestor when a class extends multiple instances of a trait, no ambiguous method calls are possible due to multiple instances of a trait" (p. 11:11). For an invariant T only γ = α = ρ satisfies this (derived here, not stated there), so the invariant case of the exclusion stands, and the covariant case is Naden's "minimal instantiation" refinement.
- Its dispatch uses the call's static return type: "[R-Method] seeks the most specific method declaration with a dispatchable instance that is applicable to the ilk of the arguments and whose return type is a subtype of the annotated static return type" (p. 11:17), because "Supporting variance in a type-sound manner requires keeping track of the static types of method invocations at run time" (p. 11:7). This is the option Naden's write-up describes as "The runtime could be enhanced to include return type constraints when considering applicability" and rejects because "programmers can no longer understand the execution of a program without static type information" (`justificationOfRTR.tex:247-253`, `:288-289`). The paper proves soundness with the ancestor rule in place (sufficiency). It contains no self types and no numeric tower (searched for "self", "comprises", "Integer", "tower"). It leaves out "modularity, nominal exclusion, and closed types", which "can be added in an obvious way" (p. 11:25).
- Its precursor is in the tree: `Papers/Welterweight/paper.tick:499-509` (Chase, Hilburn, Luchangco, Naden, Ryu, Steele, Tristan, "PAPER SUBMITTED TO 2012 ACM SPLASH---OOPSLA"). It states the same rule under the name Ancestors Meet Rule, with the reason: "if an object value belongs to one or more instances of some trait T, there is a *unique minimal instance* of T … being able to identify this minimal instance quickly is essential to the efficient dynamic dispatch algorithms we present later" (`static.tick:83-89`). A self-typed-generics step in its dispatch algorithm is commented out (`dispatch.tick:195-212`).
- **Four Oracle patents, filed 2012-08-31 (the day of Naden's write-up), name inventors from the type group, Naden among them.** US 8,843,887 B2, *Fast dispatch predicate for overloaded functions with generic type hierarchies that lack contravariance* (Chase, Steele, Naden, Hilburn, Luchangco; granted 2014-09-23; https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8843887), and US 8,898,632 B2, *Dispatch predicate … using type intervals* (…/downloadPdf/8898632). Both print the same list of "Restrictions on Fortress types" (8,843,887 col. 7 l. 40 to col. 8 l. 13; 8,898,632 col. 7 l. 52 to col. 8 l. 28). It includes "Minimal instance of generic ancestors: If S<:G[\T\], then there exists U such that for all T where S<:G[\T\]: if G's ith static parameter is invariant, then Ui=Ti", which is the exclusion. It also includes "Self-types meet: if T<:U=S[\U\] and T<:V=S[\V\] then T<:S[\meet(U, V)\] and meet(U, V) must be a declared (not intersection) type. In practice, this means that the instantiations of a particular self-typed generic must form a forest."
- The patents define the idiom: "the 'self-typed generic,' where a generic in T also comprises exactly T … Because the only subtype of Comparable[\T\] is T, the two types include exactly the same sets of values, and are in some sense the same type" (8,843,887 col. 6 l. 40-56). Their inference step lifts a lower bound "to a self-type that simultaneously satisfies the one or more self-typed constraints" (col. 2 l. 35-42; col. 12 l. 1-8). The list does not say how "Self-types meet" combines with the invariant clause. The library's `trait Equality[\T extends Equality[\T\]\]` has no `comprises T` (`Library/FortressLibrary.fsi:72-74`), so it is not a self-typed generic in the patents' sense. This is the only text found that admits the tower's shape, several self-typed instantiations along a chain, inside the rule; no paper published it. Companion patents US 8,893,082 (Naden, Chase, Hilburn: type inference with intervals and inference directions) and US 8,893,098 (deferred type inference) were identified by title only.
- **Naden's TLDI 2012 workshop paper** (*Towards Practical Runtime Type Instantiation*, dated 2011-11-10, https://www.cs.cmu.edu/~kbn/pubs/fortressInstantiation.pdf) gives the motivation for specialisation: "designers of the Fortress programming language found it useful while writing their standard library to define both monomorphic and polymorphic versions of functions". Its matching step assumes the exclusion: "we can determine what instantiation Ty′ of Baz is a supertype of Ty (as in [5] we require that this query return the unique minimal answer)", where [5] is Tate et al., PLDI 2011. Applicability there still includes the return bound "[TX/X]τr <: Tr", with Tr "the return type of the statically most specific applicable function signature". Footnote 1 relaxes the scoping rule "in the case of selftypes".
- Naden's later work is on permissions and concurrency: POPL 2012 *A Type System for Borrowing Permissions*, and TOPLAS 36(1) 2014 *Æminium* (Stork, Naden, et al.). Both are listed at https://www.cs.cmu.edu/~aldrich/papers/, which lists no Wyvern paper with him and nothing later. His homepage (© 2011, https://www.cs.cmu.edu/~kbn/) says "I am a third year PhD student in the Computer Science Department at Carnegie Mellon University" and "I spent the summer of 2011 as an intern at Oracle Labs East working on the Fortress programming language." Current affiliation: not established. A public org chart lists a "Karl Naden" as Principal Consultant at J2 Interactive (https://theorg.com/org/j2-interactive/org-chart/karl-naden), but no page found names both him and CMU or Fortress, and LinkedIn refused the fetch.
- Other type-group work: Kim and Ryu, CPP 2011 (a Coq model without generics, per POPL 2019 p. 11:4), and Kim, Ryu, Luchangco, Steele, APLAS 2013, doi:10.1007/978-3-319-03542-0_11 (abstract not reachable: the publisher elides it at Semantic Scholar and Springer redirects to login). The Semantic Scholar citation list of the OOPSLA 2011 paper (https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/2048066.2048140/citations) has 19 entries. Beyond these three it shows no later paper by Kilpatrick, Hilburn, Allen or Luchangco on the subject.
- **No published resolution of the tower conflict and no proof that the rule is necessary were found.** The published results prove soundness with the rule, and the only necessity argument remains Naden's `BadList` counterexample.

## 2. Julia

- Single abstract inheritance, concrete leaves. "concrete types may not subtype each other: all concrete types are final and may only have abstract types as their supertypes … It turns out that being able to inherit behavior is much more important than being able to inherit structure, and inheriting both causes significant difficulties in traditional object-oriented languages" (https://docs.julialang.org/en/v1/manual/types/, introduction). The tower is `abstract type Real <: Number`, `Integer <: Real`, `Signed <: Integer` and `primitive type Int32 <: Signed 32 end`, `Int64 <: Signed 64` (same page, "Abstract Types", "Primitive Types"). `Int32` is not below `Int64`. Parameters are invariant: "even though Float64 <: Real we DO NOT have Point{Float64} <: Point{Real}".
- The formal account calls it "nominal single subtyping" and says: "There is no notion of soundness in Julia, even for fully type-annotated programs. If a method call does not have a most specific method, a runtime error will be reported. Ambiguity in dispatch is always resolved dynamically." (Zappa Nardelli et al., *Julia subtyping: a rational reconstruction*, OOPSLA 2018, doi:10.1145/3276483, pp. 113:3-4, https://hal.science/hal-01882137/document). The manual's example `g(x::Float64, y)` beside `g(x, y::Float64)` gives "MethodError: g(::Float64, ::Float64) is ambiguous", with the advice "specifying an appropriate method for the intersection case" (https://docs.julialang.org/en/v1/manual/methods/, "Method Ambiguities").
- Follows from those two facts (not stated in a source): each type has one declared supertype and invariant parameters, so a value reaches each parametric ancestor through one chain, and `where T` binds from it. Naden's `BadList` cannot be declared, specialised methods beside generic ones are allowed, and no static return type is promised to break.
- Why no multiple inheritance. Bezanson's thesis (*Abstraction in Technical Computing*, MIT 2015, https://worrydream.com/refs/Bezanson_2015_-_Abstraction_in_Technical_Computing.pdf) lists "Intersections, multiple inheritance" among features that "would be difficult to add, or possibly break decidability of subtyping" (p. 63). Under "Simulating multiple inheritance" it presents Tim Holy's trait-by-dispatch pattern, noting "The original author of a type like Array does not need to know about this property, unlike the situation with multiple inheritance or explicit interfaces" (p. 74, citing github.com/JuliaLang/julia/issues/2345#issuecomment-54537633). The manual documents it as "Trait-based dispatch" ("Holy-trait" pattern, methods manual).
- Julia issue #5, "abstract multiple inheritance" (Karpinski, 2011-04-27, still open, https://github.com/JuliaLang/julia/issues/5), proposed allowing it under one restriction: "If two abstract types are are [sic] used for dispatch in the same 'slot' of the same generic function object then they cannot share a common, concrete descendant". That is an exclusion requirement in the spirit of Fortress's meet rule. It never shipped.
- Mixed arithmetic goes through promotion, not subtyping. `+(x::Number, y::Number) = +(promote(x,y)...)` and "the arguments of functions are never automatically converted"; also "although every Int32 value can also be represented as a Float64 value, Int32 is not a subtype of Float64" (https://docs.julialang.org/en/v1/manual/conversion-and-promotion/; thesis pp. 90-91). On Fortress specifically: its "coerce feature … a built-in notion of type widening … It is not possible to provide these features in Julia without doing violence to our 'everything is a method call' semantics" (thesis p. 94).

## 3. X10

- X10 follows Java's rule: "Limitation: A class or struct may not implement two different instantiations of a generic interface. In particular, a class or struct can implement only one function type." (*X10 Language Specification* v2.6.2, §4.6 Function types, p. 48, Wayback copy of x10.sourceforge.net/documentation/languagespec/x10-262.pdf; the same sentence is in v2.1 of 2011-02-23, p. 50, https://www.classes.cs.uchicago.edu/archive/2011/winter/32102-1/reading/x10-latest.pdf). No reason is given.
- Numbers are structs, which "do not have superclasses, and cannot extend anything" (§4.2.2, p. 33). Mixing goes through implicit widening: "Byte < Short < Int < Long < Float < Double" (§11.23.2, p. 178). Overloads are chosen statically: "Method resolution is the problem of determining, statically, which method … should be invoked" (§8.12, p. 133).
- Its generics are reified (*Fast method dispatch and effective use of primitives for reified generics in managed X10*, X10 Workshop 2012, doi:10.1145/2246056.2246060). The Java back end loses that for one self-typed interface: mapping "x10.lang.Comparable[T] … to java.lang.Comparable … results in the lost of runtime type information for Comparable[T]" (§18.2, p. 244).

## 4. The multiple-dispatch line

- None of the pre-Fortress systems had type parameters. The OOPSLA 2011 paper says of Dubious, MultiJava and F(EML): "None of the systems described above support polymorphic functions or types" (`Papers/Types/related-work.tick:36`). POPL 2019 repeats this (p. 11:25) and adds that ML≤ "lacks multiple inheritance" and that ParaSail "does not support covariant and contravariant type parameters".
- Cecil combined multimethods, multiple inheritance and F-bounded generics by erasing type arguments from dispatch: "Method lookup does not depend on the instantiating types … message sends foo[int]() and foo[string]() will always be dispatched to the same method implementation" (*The Cecil Language: Specification and Rationale*, §4.1.2, http://projectsweb.cs.washington.edu/research/projects/cecil/www/Vortex-Three-One/doc-cecil-lang/cecil-spec-82.html). Its tower puts the self-typed trait at the root only: `extend num isa ordered[num]`, then "num can have subtypes, such as int or float, which can be compared with each other … extend int isa num; extend float isa num; 3 != 3.14 -- legal" (§4.4, …/cecil-spec-86.html). Litvinov's 2003 thesis (ftp.cs.washington.edu) timed out.
- Tate, Leung, Lerner (*Taming Wildcards in Java's Type System*, PLDI 2011, https://www.cs.cornell.edu/~ross/publications/tamewild/tamewild-tate-pldi11.pdf), the source Naden cites for the unique minimal instantiation: "For Java this invocation is always unique, although this is not necessary for our algorithm" (§4.2, p. 5).
- Later work POPL 2019 cites: FHJ (Wang et al. 2018), whose dispatch "uses static types at run time", and Castagna et al. 2015, "a statically-typed calculus with dynamic (explicit) dispatch through pattern-matching" (p. 11:26). No other paper on soundness with multiple dispatch, reified generics and multiple inheritance together was found.

## 5. Other languages with generics and one generic interface twice

- **Java** forbids it: "different parameterizations of the same generic interface … This requirement was introduced in order to support translation by type erasure" (JLS SE 21 §8.1.5, https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html). The reason is erasure, not dispatch. The OOPSLA paper's "it is already required in Java" (`exclusion.tick:154-156`) borrows the rule without that reason.
- **C#** (reified) allows it except where two instantiations "may unify for some type parameter substitutions" (CS0695, https://learn.microsoft.com/en-us/dotnet/csharp/misc/cs0695). Overloads are resolved statically: "Overload resolution is a binding-time mechanism" (§12.6.4.1), and "Static binding takes place at compile-time", except for `dynamic` (§12.3.2) (https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions).
- **F#** 5 added it: "You can now implement the same interface at different generic instantiations" (RFC FS-1031, https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-50).
- **Swift** has no generic protocols, and the Generics Manifesto files them under "Unlikely": "Implicit in this feature is the ability for a given type to conform to the protocol in two different ways" (https://github.com/swiftlang/swift/blob/main/docs/GenericsManifesto.md, "Generic protocols").
- **Rust** allows `impl From<u8> for u64` beside `impl From<u16> for u64` (https://doc.rust-lang.org/std/primitive.u64.html) and forbids only overlap: "Two trait implementations overlap when … the implementations can be instantiated with the same type" (Reference, "Trait implementation coherence", https://doc.rust-lang.org/reference/items/implementations.html).
- **Kotlin** forbids it: the supertype closure must be "consistent, i.e., does not contain two parameterized types with different type arguments" (https://kotlinlang.org/spec/type-system.html, "Simple classifier types").
- **Scala** refuses it with "illegal inheritance; … inherits different type instances of trait" (compiler message, https://www.scala-lang.org/old/node/3423). No sentence found in SLS 2.13 ch. 5.
- **Haskell** allows one instance per class and type: "A type may not be declared as an instance of a particular class more than once in the program" (Haskell 2010 §4.3.2, https://www.haskell.org/onlinereport/haskell2010/haskellch4.html). Instances are resolved statically.
- **C++** templates instantiate distinct classes, and overload resolution selects from "a list of expressions that are to be the arguments of the call" (https://eel.is/c++draft/over.match.general). Nothing selects by instantiation at run time.
- **Ceylon** (reified, multiple interface inheritance, declaration-site variance; "Like C#, and unlike Java, Ceylon's type system is fully reified") keeps the exclusion for invariant parameters and relaxes the variant ones: "for every invariant type parameter T of Y, the type argument A … given in V and … B … given in W must be exactly the same type, and, furthermore, X is a subtype of an instantiation U of Y such that U is a subtype of V&W" (spec §3.7.2 "Principal instantiation inheritance", mirror http://lucaswerkmeister.github.io/ceylon-spec/html_single/). It has no overloading at all: "Overloading is illegal in Ceylon" (§3.2.1).

## 6. The self-typed algebra tower

- Greenman, Muehlboeck, Tate (*Getting F-Bounded Polymorphism into Shape*, PLDI 2014, doi:10.1145/2594291.2594308, https://users.cs.utah.edu/~blg/publications/fbound/effing-bound-polymorphism.pdf) identify the pattern. Self-typed traits are "shapes", and "The primary one is to encode a form of self types … useful for binary methods … as well as algebraic operations, such as addition" (p. 3). Their numeric example: with Integer only `Summable<Integer>` and Float only `Summable<Float>`, "the join of Integer and Float does not exist"; under Material-Shape Separation "Summable is only permitted in inheritance and type-variable constraints, not as the type of an expression" (p. 7). A survey of 13.5 million lines of Java found no overlap (abstract), and the Ceylon team found one counterexample and planned adoption (p. 5). The paper does not treat dispatch. It names "type families" (family polymorphism) as the second use of shapes, not the tower.
- The flat encodings in current use:
  - C#: `public interface INumber<TSelf> … where TSelf : INumber<TSelf>`, implemented separately by `Int32` and `Int64` (https://learn.microsoft.com/en-us/dotnet/api/system.numerics.inumber-1).
  - Swift: generic heterogeneous operators `static func < <Other : BinaryInteger>(lhs: Self, rhs: Other) -> Bool`. The proposal "DOES NOT solve the integer promotion problem" (SE-0104, https://github.com/swiftlang/swift-evolution/blob/main/proposals/0104-improved-integers.md).
  - Scala: type-class values `trait Numeric[T] extends Ordering[T]` and `implicit object IntIsIntegral` (https://raw.githubusercontent.com/scala/scala/2.13.x/src/library/scala/math/Numeric.scala, l. 221, l. 67).
  - Cecil: the algebra on the root `num` only (§4).
- Typed Racket nests the tower statically ("Integer is a subtype of Rational, which is a subtype of Real") with union types and "overloading with intersection types". It names the tower as the hard case for typed languages: "No existing typed language provides as rich a numeric hierarchy nor as many generic operations as those found in Smalltalk, Scheme, or Racket" (St-Amour et al., *Typing the Numeric Tower*, PADL 2012, pp. 1-2, 5, https://www2.ccs.neu.edu/racket/pubs/padl12-stff.pdf). It has no self-typed traits and no run-time dispatch on type arguments.
- Apart from Naden's write-up and the 2012 patents, no source was found that treats a nested tower carrying self-typed traits at each level together with run-time dispatch over reified generics.

## What the field settled and what it did not

- **Keep the rule and flatten the tower.**
  - Java, Kotlin, Scala and X10 keep the rule, with flat numeric types and widening. Java's stated reason is erasure.
  - The Fortress group kept the rule after 2012 (Welterweight 2012, POPL 2019), for "unique minimal instance" dispatch.
  - Cecil's root-only `ordered[num]` and C#'s `INumber<TSelf>` on sibling structs are two flat shapes in use.
- **Drop the rule and instantiate at the call site with no specialised overloads.**
  - C#, F#, Rust and Haskell allow multiple instantiation, and every one chooses instances and overloads statically. None has run-time dispatch over generic overloads, the one place Naden's hole opens.
  - Ceylon allows variant multiple instantiation and has no overloading.
- **Neither route.**
  - Julia avoids the trade by single inheritance and gives up static soundness ("no notion of soundness"). It keeps specialised methods and moves ambiguity to a run-time error.
  - POPL 2019 keeps both the rule and specialisation by checking the static return type at run time, the option Naden rejected.
  - The 2012 patents' "Self-types meet … must form a forest" admits the tower's chain of self-typed instantiations inside the rule, close to the review's route C. It was never published, and its test (`comprises T`) is absent from the library's `Equality`.
- **Not settled.** Nobody published a resolution of the tower conflict under run-time dispatch, or a proof that the rule is necessary; the published proofs show only that it suffices.
