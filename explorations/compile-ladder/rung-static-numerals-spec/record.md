## Revival change

**The change.**
- The team's source: the Working Draft gives a numeral six types, `NaturalNumeral[\n,10,v\]` (and `Literal[\v\]` without leading zeros), `NaturalNumeralWithExplicitRadix[\n,r,v\]`, `RadixPointNumeral[\n,m,10,v\]`, `RadixPointNumeralWithExplicitRadix[\n,m,r,v\]` and `Numeral[\n,m,r,v\]` above all (`Specification-1.0-frozen/basic/expressions/literals.tex:83-129`), says that "Numerals are not directly converted to any of the number types" (`:132-141`) and that libraries define coercions from numerals (`:146-148`), and says nothing of a numeral's value when a program runs or of when a coercion is applied. The team's compiled library types numerals by run-time values, `trait IntLiteral` and `trait FloatLiteral` with getters such as `asZZ32` and `asRR64` (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:390`, `:479`, at b5b0f82c13), whose coercions run on that value.
- What the text now says: a numeral's type exists only at compile time, `NaturalNumeral[\n, r, v\]` or `RadixPointNumeral[\n, m, r, v\]`, at the Draft's arities with the radix as `r`, below a `Numeral` without static parameters; the explicit-radix types and `Literal` are not built; no value of a numeral type exists when a program runs, so a numeral type has no method, no `asFloat` and no `=` with a number type; every number type, the library's and a program's, takes a numeral through `coerce[\nat n, nat r, nat v\](x: NaturalNumeral[\n, r, v\])` or its radix-point form, whose body reads the four numbers as `ZZ` values; the compiler folds it to a constant, or makes the value once per place; `-3` at a program's type is the type's own `-` on the coercion's result for `3`; a `where` clause over the four numbers refuses a numeral statically (`Specification/basic/expressions/literals.tex:98-285`; `Specification/appendices/changes.tex:5010-5486`). The tests that show the tree doing so land with the code: `ProjectFortress/tests/NumeralStaticDesignWalk.fss`, `ProjectFortress/tests/NumeralOwnTypeWalk.fss`, `ProjectFortress/tests/NumeralTypeNoValueWalk.fss`, `ProjectFortress/compiler_tests/NumeralStaticDesignCompiled.fss` and `ProjectFortress/compiler_tests/XXXNumeralWhereRefusedCompiled.test`.
- The reason, as evidence: the Draft's own ground, "This approach allows library designers to decide how numerals should interact with other types of objects by defining coercion operations" (`Specification-1.0-frozen/basic/expressions/literals.tex:142-145`), which a coercion that sees only a value cannot carry out: a 16-bit float type's coercion from the four numbers rounds `1.00390625000000000001` once, to `0x3F81`, where a coercion from an `RR64` gives `0x3F80` (`ProjectFortress/compiler_tests/NumeralStaticDesignCompiled.fss`, "BF16(1.00390625000000000001) rounds once, to 0x3F81"); a JVM class file holds no object constant, so a value at a place is a constant or a field filled once when the class loads; the team's own word on the run-time value, "IntLiterals should always be transient objects with minimal lifetime" (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FIntLiteral.java:21-23` at b5b0f82c13).
