## Findings

1. **A compiled method's JVM parameters follow its declaration.** One parameter of a declared tuple type is the tuple's elements, one JVM parameter each, and the body makes the tuple again (`CodeGen.addParams`); one parameter whose declared type names a type parameter is one JVM parameter at every instance, the boxed tuple where the instance makes it a tuple, as the generic trait's interface declares it (`CodeGen.paramTypeAtInstance`, `ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:901-924`); several parameters are one JVM parameter each. Conditions: the compiled path, at the commits named above. Evidence: `compiler_tests/TupleIndexMethodCompiled.test` passes (link, run, `PASS`) and failed on the base, 'java.lang.VerifyError … Type 'TupleIndexMethodCompiled$Arr2' (current frame, stack[0]) is not assignable to 'com/sun/fortress/compiler/runtimeValues/FZZ32''. What it means: a call through a generic trait's type at a tuple instance takes the tuple as one value, and a call on the object of the trait's body at the tuple type takes its elements; the code generator chooses by the declarations that the receiver's type holds (`callTakesTupleBoxed`, `CodeGen.java:7375-7407`).
2. **Two bridges join an instance's boxed tuple to a body's elements.** The code generator writes, in the class of a trait or object whose body at a tuple type shadows a generic trait's method over a type parameter, a method of the interface's boxed signature that unpacks the tuple, casts each element and calls the body virtually (`tupleElementsBridge`, `CodeGen.java:950-982`, written from `dumpOverloadedMethodChaining`, `:1537-1545`). The class loader writes, in an instantiated class, beside a method whose template's one parameter is a type parameter that the instance makes a tuple type, a method of the elements that packs them and calls it (`ProjectFortress/src/com/sun/fortress/runtimeSystem/Instantiater.java:119-165`), never in an interface (`:130`); it is made only where a tuple type, `LTuple⟦`, is substituted for a template parameter that was not one already (`:124-128`). ## FACTS.md

> **A compiled method's JVM parameters follow its declaration, and two bridges join an instance's boxed tuple to a body's elements.** One parameter of a declared tuple type is the tuple's elements, one JVM parameter each; one parameter whose declared type names a type parameter is one boxed JVM parameter at every instance, a tuple among them, as the generic trait's interface declares it. The code generator writes, where a body at the tuple type shadows such a method, a method of the boxed signature that calls the body with the elements (`CodeGen.tupleElementsBridge`), and a dotted call passes the tuple boxed where the receiver's type holds only such declarations (`CodeGen.callTakesTupleBoxed`); a generic dotted method of one parameter is called with the receiver and the argument as two values. The class loader writes, in an instantiated class and never in an interface, beside a method whose template's one parameter is a type parameter that the instance makes a tuple type, a method of the elements that calls it (`runtimeSystem/Instantiater.java:119-165`). Test: `compiler_tests/TupleIndexMethodCompiled.test`. Detail: `explorations/compile-ladder/rung-tuple-parameter/REPORT.md`, "The convention as built".
