## Revival change

**The change.** The team's walk wrote a `Char`'s `asExprString` through `FChar.toString`, `"'" + Unprinter.enQuote(...) + "'"` (`interpreter/glue/prim/Char.java:177-181`, `interpreter/evaluator/values/FChar.java:104-106`), as `'\'0e9''` for `é`, a text the parser refuses; the team's compiled helper wrote `'"'` and `'\'` for the quotation mark and the reverse solidus and the separator U+2028 as itself, which the parser also refuses (`nativeHelpers/simpleChar.java:21-44` at the base); the team's parser refused codes of six digits and lower-case five-digit codes whose first four are decimal (`parser/Literal.rats:460-464` at the base); the specification's list of character-literal forms did not name a character followed by its code (`Specification-1.0-frozen/basic/lexical-structure.tex:861-877`). Now both paths write the helper's text, `'\"'`, `'\\'`, the five escapes, the code alone for the other controls, U+201C, U+201D, U+2028, U+2029, the surrogates and past U+FFFF, and the character with its code elsewhere, as `'é 00e9'` (`tests/NativeHelperFamilyCharWalk`, `compiler_tests/NativeHelperFamilyCharCompiled`); the parser reads every such text back, codes of four to six digits in either case among them (`tests/CharExprStringReadBack`); the list names the form. A character past U+FFFF written as itself still does not parse (`tests/XXXCharLiteralSupplementary`). The reason: the library's contract for the getter, the team's comment that its text "will equal self" when read (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi:36`), held for walk's text at 100 of 1.11M code points and for the helper's at all but 6 of the BMP (a sweep with `compiler/Parser.parseString`); the helper's form and the parser rule that reads it are one 2011 commit of the team's (`c2c769094`).
