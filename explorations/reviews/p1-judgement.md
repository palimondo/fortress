# P1: an F-bounded type parameter that nothing at a call fixes, under walk: the judgement

## For Pavol

**Question.** Under walk, what does a type parameter get when no argument fixes it and its bound names the parameter itself, as `T` in `SUM`'s `T extends AdditiveGroup[\T\]`? Today it gets `Bottom`, so `SUM[i <- 1:n] i` dies at its first element. Twelve ways are on file, six measured. Which one?

**Refresher.**

- A type parameter is a hole in a declaration that a type fills: `T` in `opr SUM[\T\]()`. Its bound is the widest type allowed in the hole. `T extends Number` says: any number type.
- An F-bound is a bound that names the parameter itself: `T extends AdditiveGroup[\T\]`. It says: `T` must be a type whose `+` takes a `T` and gives a `T`. `ZZ32` fits, `RR64` fits, `Number` does not, since `Number` has no `+` of its own. The library's algebra is written this way (`AdditiveGroup[\T\]`, `MultiplicativeRing[\T\]`, `StandardMin[\T\]`, `Library/FortressLibrary.fsi:262`, `:274`, `:189`), because in Fortress an operation on a type is declared on that type, `ZZ32 + ZZ32`, not on a parent, `Number + Number`. The bound is what lets the checker accept `a + b` inside `SUM`'s own code.
- "Nothing at a call fixes it." A call usually fills the hole from its arguments: `SUM (1#100)` has a generator of `ZZ32`, so `T` is `ZZ32`. But the clause form `SUM[i <- 1#100] i` is rewritten by the parser into a call of `SUM()` with no argument, made before any element exists (`Library/FortressLibrary.fss:1302`, `__bigOperator` takes the reduction first). Nothing fills the hole.
- Your decision on record for that case: the parameter takes its bound. For an F-bound there is no bound to take: `AdditiveGroup[\T\]` is not a type until `T` is known. The paper the rule comes from leaves this case out: "no reference to a method type parameter appears in any of the upper bounds" (`research/extracts/ParkPOPL2019-extract.md:282-285`).
- One line: `total = SUM[i <- 1#100] i` (`explorations/claude_demo.fss:33`). Today: "Unification error: Closure/Constructor for join param 1 (a:BOTTOM) got arg 98: ZZ32". Written `SUM[\ZZ32\][i <- 1#100] i`, it runs.
- Who meets it. The specification's five red examples, each this shape: `opr (n: ZZ32)! = PROD[i <- 1:n] i` (`SpecData/examples/preliminaries/Overview.factorial.fss`, `advanced/OprDecl.Postfix.fss`), `factorial(n) = PROD[i <- 1:n] i` (`preliminaries/Overview.Expression.big.fss`), `SUM[i <- x.indices()] x[i] DOT y[i]` (`advanced/OprDecl.Bracketing.fss`), `SUM [x <- 1#100] 3 x + 2` (`advanced/Generators.ReductionClass.fss`). The walk smoke test. 18 of the team's 21 demos, which are not gated. The library itself: `String`'s `upto` and `beyond` call `BIG MIN` with nothing written (`FortressLibrary.fss:4237`, `:4243`), and run only because `MinReduction`'s join is typed `Any`, not `T` (row 424's last note; row 628). MicroGPT does not meet it: its walk checks write every argument (`explorations/run-c4/src/MicroGptFlatCheck.fss:27`, `:56`, `:72`), and `microgpt2.fss` hides the library's `SUM` with its own (`:257`).

**The nine steps, in short.**

1. The type theory. An F-bound `T <: F[T]` has many solutions (`ZZ32`, `RR64`, every type that extends `AdditiveGroup` of itself) and no largest one: generics are invariant, so the solutions are not ordered, and "the bound" as one type does not exist (by reading; the notion is Canning, Cook, Hill, Olthoff and Mitchell, "F-bounded polymorphism for object-oriented programming", FPCA 1989, cited by its record). `Bottom` is the one closed type that fits every F-bound, and it holds no value: a hole filled with nothing. The paper's rule, the intersection of the upper bounds, is stated only where no bound names the parameter (`ParkPOPL2019-extract.md:196-205`, `:282-285`). So the theory gives no instance here. It leaves three honest answers: refuse the call, keep the hole abstract, or read the type from somewhere else, the elements or a default.
2. What each path does today. Walk: `Bottom`. Rung W gives a parameter nothing fixes its bound, but `boundAtInstances` answers null for a bound that mentions the parameter, and a big operator's static parameters are kept at `Bottom` on purpose (`EvaluatorBase.java:140-144`, `:156-188` at `cec70988b`; rung W's decision D2). Walk then checks the first element against `join(a: T, b: T)` at `T = BOTTOM` and refuses it (`NonPrimitive.java:256-269`); an empty sum takes the identity witness's first branch and `cast[\BOTTOM\]` fails with `CastError` (`FortressLibrary.fss:3208-3215`, `:33-37`). The compiled checker: the bound, and it refuses the call, "an F-bounded parameter that nothing fixes has no instance at its bound" (rung I's report, section 5, `BIG MIN`'s no-argument form; row 425 for the clause form).
3. What the specification says. Normative: a reduction is rewritten by the type `N` of its expression, `SUM[\N\]` with `SumReduction[\N\]` (`defining-generators.tex:154-164`). So `SUM[i <- 1:n] i` means `SUM[\ZZ32\]`. The inference chapter: a parameter nothing fixes takes the intersection of its upper bounds, "never ... at `BottomType`" (`inference.tex:93-105`), and it lists "the element type of a reduction that only its generator clauses determine" as not yet described: the rule gives the big operator's parameter "its bounds, not the type of the elements" (`:240-249`). Its interpreter box records walk's `Bottom` as a departure (`:285-289`). The revival's note in the reductions chapter: until an implementation rewrites by type, write the argument (`reductions.tex:27-44`).
4. Where it sits in the type system. Three places. (a) The rewriting, which picks `SUM[\N\]` from the expression's static type: walk has no static types. Under walk the element type can only come from (c).

## The judgement

### 1. The way, stated

An F-bounded type parameter that nothing at a call fixes is not instantiated under walk. It is left open.

- "Open" is a type of walk's own (`BottomType.OPEN` in `plan-9/probes/P1-open.patch`). It is below every type, as `BottomType` is (`BottomType.java:20-22`, `subtypeOf` answers true), so it sits wherever `Bottom` sat: the identity witness's `typecase` over `() -> T` still takes its `ZZ32` branch, and `BigReduction[\OPEN,OPEN\]` matches `__bigOperator`'s parameter as `BigReduction[\BOTTOM,BOTTOM\]` did. Nothing but itself is below it (`FType.java:312-318`, the fallback `other instanceof BottomType`).
- Every value matches it where walk checks a value against a type: a closure's parameter (`NonPrimitive.java:256`, through `typeMatch`, `FType.java:108`, which `OPEN` overrides), a typed local (`LHSEvaluator.java:219`), `as` and `asif` (`Evaluator.java:104`, `:113`) and a `typecase` clause (`:1396`). So `join(a: OPEN, b: OPEN)` admits the elements, `result : T := red.empty()` admits the identity, and `cast[\OPEN\](v)` returns `v`.
- It applies at instantiation only (rung W's D1), to any generic function whose parameter's bound mentions the parameter and that nothing fixes, big operators included: the probe's block tests `bounded`, not `bounds`, so D2's exclusion of big operators does not reach it, and a big operator's plain-bounded parameters stay at `Bottom` (probe `List`, `ArrayList[\Int\]` in every column).
- What it is, by reading: the run-time counterpart of the specification's type-directed rewriting. The chapter picks `SUM[\N\]` from the expression's static type; walk, with no static types, leaves the hole open and lets each typed site take the element in hand. It is also the sum-replacement judgement's alternative 2, "a parameter whose type erased to Bottom accepting any argument", named there as walk's road if one is wanted (`reviews/sum-replacement-judgement.md:282-289`).
- What it is not: an instance. The chapter's "never `BottomType`" and the paper's "never instantiates method type parameters with Bottom" are about an instance that refuses every value. An open parameter refuses none. The specification's box says so in those words, not as "the parameter takes `OPEN`".
