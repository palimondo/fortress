# Concepts for every worker, chunk f5

The entries name these concepts without defining them, since other entries use them too. Each belongs in the `fortress-repo` skill, not in the revival part that is being rewritten.

| Term | Entries | Where to define it | What the definition needs |
|---|---|---|---|
| The distance stage and the count stage | F-65, F-66, F-75; also F-53 | `references/compiler.md` | Chunk f0's `concepts.md` defines the distance. The count stage stops at each component's first error; its table is `gate/checker-count.txt`, with a 900-second limit that stops the run (`checker-count/run.sh:69`). F-53 holds both current values. |
| A batch's gate | F-66 | `references/gate.md`, one sentence after its count of seven steps | A batch's gate is the worker's seven steps, then step 8, the count stage, and step 9, the distance stage (`coordinator/climb-batch-workflow.md:220`). |
| Batch names | F-65, F-74; also 6.5, 7b, 7R, 13b in other entries | The `fortress-repo` core's "batch" definition, in one clause | The core names climb batches by number. Some carry a letter or a suffix, such as 7C or N. |
| The trait table | F-65, F-72; also F-235 | `references/compiler.md` | The checker's index of the types that a compilation unit sees, its own and every api's, built anew by each phase that needs one (`TraitTable.scala`; `rung-analyzer-memo/REPORT.md`, "The table does not change"). |
| A compilation unit | F-72, and the record at large | The `fortress-repo` core, beside "component" | A component or an api. The core defines both, but not the word "unit" that the record uses for either. |
| A size, and the kinds of static parameter | F-67, F-69; also F-20, F-61, F-146, P-40 | `fortress-repo` core, "Static parameters" | A static parameter is a type, or a `nat`, `int`, `bool`, `dim` or `unit` value. A size is a `nat` or `int` parameter, as in an array's length. The compiled checker infers only types and sizes at a call; it does not infer the other three kinds. |
| An arm of an overload set | F-69; also F-68, P-40 | `fortress-repo` core, beside multiple dispatch | One declaration of an overloaded name, as the record calls it. |

| A result-only type parameter | the new entry; also F-84, F-78, P-48 | `fortress-repo` core, "Static parameters" | A type parameter that occurs only in the result type, so that no argument fixes it (P-48's words). The core's bullet already says what a parameter that a call does not fix takes. The core is the home, not `references/compiler.md`, since walk meets it too (P-48). Chunk f6's `concepts.md` defines it. |
| Walk's numeral, `IntLiteral` | F-73, F-74; also F-79, F-262, F-263, P-76 | `fortress-repo` core, "Numbers are siblings, not a tower" | `IntLiteral` is the numeral's own type in the interpreter's library (P-76, F-79). The definition should give both, so that a reader of walk's messages recognises `Int`. |
| Coercion | F-73; also P-74, F-51 | `fortress-repo` core, beside numbers | A conversion that a type declares with `coerce`, which the checker may insert at a call. A declaration applicable only with coercion ranks below one applicable without it. |
| A default waiting for review, the review queue | F-73, F-75 | The short orientation that replaces the revival part | Chunk f0's `concepts.md` defines PLAN items and the review queue. An entry that cites a review-queue item states a choice built at a default, not the curator's ruling. |
| Phase 3's road, parked rows | F-72 | The short orientation | `PLAN.md` lists the rows on phase 3's road with no batch named, which the phase still owes, and the rows "Off the path, parked", which no batch will take up unless the curator decides. |
| What a compiled `XXX` test pins (added by the judge) | F-64, F-67, F-69, F-75; also F-70 | `references/tests-writing.md`, "How `XXX` works" | In a compiled test folder an `XXX` compile test with `compile_err_contains` or `compile_err_equals` asserts that the checker refuses the program with that message. The tree spells two kinds so: a refusal that the specification makes, and a refusal that is a limit or a defect, whose program asserts the specification's answer (`compile-ladder/rung-nat-checker/REPORT.md` section 6, "Refused rightly, or refused as a limit"). Either kind turns red when the checker stops refusing. Which kind a test is, the entry's row or its program says. The second cold reader could not tell the two apart from the skill. |
| A rung's manifest, `expectedCheckerCrash` (added by the judge) | F-66; also P-39 | `references/gate.md`, beside the sentence on a batch's gate | The block of the batch script between its `MANIFEST` and `END MANIFEST` lines gives each rung's fields. One of them, `expectedCheckerCrash`, lists a checker crash that the rung expects, so that the count stage does not turn the gate red on it (`coordinator/climb-batch-workflow.md`, "The manifest and the scatter"; P-39). |
| `...` in a `comprises` clause; a closed trait; a generic subtrait (added by the judge) | F-64, F-72; also F-62, F-63, P-44 | The `fortress-repo` core, "Traits and objects" | A closed trait is one with a `comprises` clause. Only in an api may the clause include `...`, which leaves room for more subtypes that the api does not show (`Specification/basic/traits.tex:160-161`; the draft note at `:277-283`). A generic subtrait is a trait with static parameters that extends the closed trait without being listed, as `Integral[\I\]` extends `AnyIntegral` (P-44). |
