# Opus and Fable rungs, climb batches 29 to 33b: cheap measures, and the pairs for a blind grading

## The tiers, as found at the source

A rung is one task of a climb batch: a worker builds it on a branch, a skeptic checks it and may commit fixes, and the gather lands it on `main` as one commit. The tier is the model family that ran the run's agents.

- Opus, at effort `xhigh`: climb batches 29 (6 rungs, run `wf_110667e0-c4a`), 29b (2, `wf_ab289a6d-124`), 31b (3, `wf_8ca4b98b-7c0`), 33 (6, `wf_6339efde-563`) and 33b (4, `wf_1413c43f-684`). 21 rungs.
- Fable, at effort `medium`: climb batches 30 (3, `wf_94bad6da-b78`), 31 run 1 (6, `wf_dbc6b8c2-529`) and 32 (7, `wf_16f35394-635`). 16 rungs.
- Source: every agent's meta file names the tier (`"model": "opus"` or `"fable"`), every message of its transcript names the model and carries its `effort`. In each run every rung worker, skeptic, judge, gather, review, gate and commit agent has the same tier and effort, with two exceptions that touch no rung: each run's disk agent ran at `low`, and climb batch 31's judge of the red gate ran at `high`.
- So the brief's list holds. What it did not say: the Opus runs were at `xhigh`, so tier and effort change together. No measure here can tell the model from its effort.
- The skeptic of each rung had the worker's tier. So a measure of what the skeptic found measures the pair, worker and skeptic, not the worker alone.

## What was measured, per rung

Each item below is a column of the data file.

- **Area**: the part of the system that the rung's commit changed most, counted in code lines. The areas: the checker (`scala_src/`), the code generator with the class loader and the run time (`compiler/codegen/`, `runtimeSystem/`, `compiler/runtimeValues/` and the code generator's helpers `NamingCzar`, `OverloadSet`, `Types`), walk (`interpreter/`, `nativeHelpers/`), the parser, the shared front end (the phases that both paths run: `desugarer/`, `disambiguator/`, `phases/`, `nodes_util/`), the library (`Library/`, `LibraryBuiltin/`), the specification and the tools (the driver, build and scripts). One hand choice: `scala_src/useful/STypesUtil.scala` counts as the code generator for rungs 31 M and 33b R, whose edits there serve the code generator.
- **Kind**, read from the rung's mission in section 4 of its batch record: a defect fixed (the construct existed and did the wrong thing), a feature built (the path had no case for the construct), a design carried out (a decision of the curator that changes the language or the library), or text of the specification only.
- **Size of task**: the expected minutes of the batch record's manifest (the planner's estimate, which orders the scatter only), and the rows closed, counted as ledger rows whose notes say `fixed` with the rung's commit.
- **Landed lines**, from the rung's own commit on `main` (`git log --first-parent <base>..<landing>` names one commit per rung). Code lines added and removed, apart from tests, the specification and `explorations/`. Specification lines apart. The Rats! parser's two generated files (`parser/Fortress.java`, `templateparser/TemplateParser.java`) are left out: 879 lines in 32 P and 644 in 32 S. Test lines added and removed; test files added; test programs added and changed (a test program is a `.fss` file, or a JUnit test class, in a test folder). Code lines outside the rung's area.
- **Process**: the skeptic's fixes, from its returned result, where the skeptic itself labels each fix a "defect" (of the change) or a "correction" (a test, a citation, the report); a defect fix "in code" is one whose paths hold a source file. A contested fix and its judge's ruling. The merged-diff review's blocking and routed findings that name the rung, attributed by my reading. A repair commit after the gather that touched the rung's files. Rows the rung's worker and skeptic opened (from the gather's result; the gathers of 31b and 33 did not mark the skeptic's rows, so the two are one column).
- **Later rows**: ledger rows opened after the batch landed whose text names the rung (below, "Defects found later").
- **Tokens written** by the rung's worker and its skeptic, summed over their transcripts. A restart leaves two transcripts for one role; both count. That happened to 31's skeptics K and X, 32's workers P and N, and 33b's worker R and skeptic N.

## What can be compared, and what cannot

Comparable:

- Defects fixed: 10 Opus rungs (29 G, 31b T, 31b E, 33 D, V, Q, I, C, 33b W, R) and 10 Fable rungs (30 N, P, X, 31 M, V, X, K, 32 P, S, B), of the same expected size (median 190 and 200 minutes) and closing nearly the same number of rows (29 and 28).
- Within them, the code generator: 6 Opus rungs (31b T, 33 V, Q, I, 33b W, R) and 4 Fable rungs (30 P, X, 31 M, K).
- Defects and features together: 12 Opus rungs and 15 Fable rungs. This is the main comparison below.

Not comparable:

- Designs: 7 Opus rungs (29 N, C, F, S, 29b A, 31b O, 33b N) and 1 Fable rung (32 N). The Opus designs are the large ones of the period, the numerals and the number objects: 4.7K of Opus's 5.8K code lines added and 4.0K of its 4.2K removed.
- Text of the specification only: 2 Opus rungs (29 T, 29b T), no Fable rung.
- Areas with one tier only: the parser (Fable's 32 P and S), the shared front end (Opus's 29 F, 29 S and 33 D), the tools (Opus's 33 S). Walk has 5 Fable rungs and 3 Opus rungs, two of them designs. No rung's main area is the library: its lines ride with walk or the code generator.
- Time: the Opus rungs of 33 and 33b came after the Fable rungs of 31 and 32 and built on them (33 Q on 31 K's cast, 33b R on 31 M's forwarders). The skills and briefs changed from batch to batch. Fable's 31 and Opus's 31b ran on the same day from one record, the closest pair of runs in time.
- Effort, as said: `xhigh` against `medium`.
- Later rows: a rung landed 9 days ago had 9 days to be found wrong; one landed this morning had hours. The median rung of the main comparison landed 0.5 days ago for Opus and 2.2 days ago for Fable.
- Tokens: a Fable token and an Opus token take different shares of the session's limit (`analysis.md` of the coordinator skill), so the counts compare activity, not cost.

## Defects found later

How I searched: for each rung, the ledger rows numbered above the ledger's highest row at its batch's landing commit, each read as its current line and every earlier line in the history file. A row is a hit if it names the rung's landed commit, its worker's head or a skeptic's fix commit (the first 7 hex digits), names the rung as "climb batch B rung L" or a near form, or names a Java or Scala member (7 characters or more, found in at most 25 rows) on a changed line or hunk header of the rung's commit. The search gave 28 hits. I kept a hit only where `git log -S` shows the rung wrote the member and the row's mechanism is that member. It misses: a row that tells the defect by its behaviour alone; a member in the library's Fortress code; a defect not yet in the ledger; and every rung landed hours ago.

Kept, by rung (an "edge" is a form beside the one the rung built, that its change does not reach):

- Opus 29 F: row 971, a numeral coercion run in a class's initializer that spawns a task fails the class's load (fixed by Fable's 30 N).
- Opus 29 C: rows 1060 (fixed by 33 C) and 1074, the default of a numeral at an untyped binding misses a block after a local declaration and a `try` (`joinNumerals`).
- Opus 29b A: row 1075, `tupleJoin` has no case for a `case` or a `try`.
- Opus 33b R: row 1089, a regression: `("ab" asif String) < ("cd" asif String)` answered true on the base and false since R's `hasBodyInItsTrait`. Its own skeptic found it; the row was written after the landing. Row 1088, R's other regression, was recorded at the landing and does not count here.
- Fable 30 X: row 1039, an edge: an `exit` out of an `atomic` block loses the block's writes, where 31 L's `exit` meets X's handler (`leaveTransaction`).
- Fable 31 V: row 1058, its `returnRuleAtObjectArguments` refuses a valid pair whose result is a tuple.
- Fable 31 K: row 1070, an edge: `castToTypeBelow` does not cast a `typecase` arm. And row 1071: K's worker met the checker's refusal of `self.d` and recorded no row; 33 Q's skeptic recorded it.
- Fable 32 F: row 1036, an edge: walk does not instantiate a generic function at a declared arrow return type or a field's type.

Dropped: rows 980 (contested, a design question), 973 and 975 (the dispatch of a numeral under walk, settled by the curator's P-46), 987 (the team's parallelism analyzer), 1010 and 1063 (the checker's well-formedness pass), 1077 (walk's matrix type), and 1088 and 1089 as hits for 31 M (the change was 33b R's).

## The pairs, ranked

Each pair is one Fable rung and one Opus rung of the same area and kind, near in size, with few lines outside the area.

1. **31 K (Fable) and 33 Q (Opus).** Both are defects of the code generator: the cast where `self`, or a value of a trait with a `comprises` clause, stands at a type below its trait, which the JVM's verifier otherwise refuses. Q extends the member that K wrote (`castToTypeBelow`) to a conditional's arm and a closure's result, and makes pass two of the expected-failure tests that K added. Expected 150 and 200 minutes; 2 and 3 rows closed; 44 and 36 code lines added; 191 and 146 test lines added; no line outside the area.
2. **31 M (Fable) and 33b R (Opus).** Both are defects of the code generator in how a class finds the methods it inherits through an api's trait, in the same two files (`CodeGen.java`, `STypesUtil.scala`); R edits `hasBodyInItsTrait`, which M wrote. Expected 220 and 200 minutes; 3 rows each. Code lines added, 103 against 18, and R carries a known regression (row 1089), which makes the pair a check of whether the graders find it. Against it: the sizes differ fivefold, and R's worker restarted.
3. **30 X (Fable) and 31b T (Opus).** Defects of the code generator with the run time or the class loader, of near size: 210 and 220 minutes, 204 and 214 code lines, 7 and 5 rows. The subjects differ: the compiled transaction against a method whose one parameter is a tuple.
4. **31 X (Fable) and 31b E (Opus).** Defects of the checker, run on the same day: 160 and 180 minutes, 1 and 3 rows, 69 and 19 code lines. X has 28 lines in the code generator's `OverloadSet.java`, and its test was withdrawn after the gate (above). The subjects differ: the Return Type Rule against a numeral that ends a block.

Not chosen: 31 V or 32 B (Fable) against 29 G (Opus), the walk defects, because 29 G's task was a third of their size (60 minutes against 200 and 150) and ran eight days earlier on another state of the numerals.

## The recommended pilot: 31 K and 33 Q

The landed diff of each, code and tests only, is its commit on `main` restricted to `ProjectFortress/`. This leaves out its Appendix I lines in `Specification/appendices/changes.tex` and its record under `explorations/`.

- **31 K, Fable.** `git show --format= 6df780a7d0 -- ProjectFortress/`: `compiler/codegen/CodeGen.java` (+44) and 18 files under `compiler_tests/`. Its parent on `main` is `1ce04203c5` (31 X); the batch's base is `c1ce2a35e1f1efabb59e0aaed9375994381512b3`. Its task: `explorations/coordinator/CLIMB-BATCH-31.md:664`, section 4, "K. The cast where a value typed by a trait stands for the type that the trait's `comprises` clause lists: the checker accepts it, and the compiled code now casts (rows 991 and 695)". The landed diff holds its skeptic's code fix `f9bc4f2546` (14 lines added and 2 removed in `CodeGen.java`: the cast also where the value is a `typecase` whose arms are each `self`). The worker's own head is `f2d66de4e1` on `wip/rung-comprises-cast`, if the grading wants the worker alone.
- **33 Q, Opus.** `git show --format= 1f6c166b0d -- ProjectFortress/`: `CodeGen.java` (+8), `runtimeSystem/MethodInstantiater.java` (+28, -1) and 23 files under `compiler_tests/`. Its parent on `main` is `5073eb2aaf` (33 V); the batch's base is `1609258002b016489c96bd6e438389e89773b9eb`. Its task: `explorations/coordinator/CLIMB-BATCH-33.md:658`, section 4, "Q. `self` at a self type or a listed type on the compiled path: an arm of a conditional, a function expression's or a local function's result, and a default body that calls a method on a value of the self-type parameter (rows 1051, 1050 and 1052; review-queue item 572)". Its skeptic made no code fix; the worker's head is `0afb9ce991` on `wip/rung-self-arm-closure`.

Why this pair: the closest match of mechanism, area, kind and size; each diff is under 260 added lines, so several judge models can read both whole; each landed as one commit with nothing else in its code files. What a judge can still see: the diffs name no batch, rung or model, but the commit messages do, so a judge gets the diff without its message. Q's diff renames two of K's `XXX` tests and touches K's member, so a judge given both can tell which came first, though not which tier.

## Limits

- Lines are a cheap proxy. They do not say whether code is right, clear or in the right place. The blind grading is for that.
- The kind and the attribution of review findings and later rows are my reading, each listed in the data file so that it can be checked.
- Every Fable rung ran at `medium` and every Opus rung at `xhigh`; the skeptics shared the worker's tier.
- With 12 and 15 rungs, a difference of one or two rungs in a count is noise.
