**1.** Two places, with the repo as the one that actually counts. Anything about the project itself goes in a short notes file inside the repository, something like a NOTES.md at the root, committed and pushed every time it changes, because that is the only store that survives a lost container. It holds the current goal, what is done, what each worker is on, decisions with the reason behind them, and open questions, all with absolute dates, and it stays short enough to read in full. The memory directory under my Claude profile gets the things about you and how you want me to work, plus one pointer telling me to read the repo notes first. Its index is loaded into context automatically, so after a compaction I follow that pointer, read the notes file, and run a quick git log and status to see what changed since the notes were written. After a lost container I clone, do the same, and treat the pushed notes as the truth. I would update the notes as part of finishing any piece of work rather than at the end of the day, since the container can go at any moment.

**2.** I keep the whole report and I do not paste it into my notes. The raw text goes into the repo as its own file in a reports folder, named with the date and the worker, committed and pushed as is, so the detail is never lost and I can go back to it. Then I read it fully and pull three things into the notes file: decisions with the reason given, measurements that actually change what we do next, and open points turned into concrete questions or tasks. Every item I pull out gets the date, which worker produced it, and a pointer to the report file it came from, because weeks later a bare number with no owner is useless and because workers are sometimes wrong and I want to know whose numbers to recheck. Measurements go in a small table with the conditions they were taken under, not in prose. Any decision in the report that changes direction I do not adopt quietly, I flag it to you in the next message with my own view, and the rest I summarize to you in a few sentences with the file name in case you want the full thing.

**3.** First the compaction summary itself, since it carries what I was in the middle of, and then the memory index that is loaded for me, which should tell me to go to the repo notes. I read the notes file in full, every time, which is exactly why I keep it short, because a notes file I skim is a notes file I will misread. Then git status and the last handful of commits to catch anything that landed after the notes were last written, including worker pushes. That is the fixed part and it should be a few minutes of reading at most. Beyond that I read only what the task in flight points to, usually one worker report or one source file, and nothing else until I need it. I would not reread old reports to feel caught up, since the point of the notes is that I do not have to.

**4.** I split by what still affects decisions versus what is just history. The notes file I read every time stays a current-state file, so anything finished, superseded, or settled moves out into a dated history file that I do not read unless a question sends me there. A decision that is still in force stays as one line with its date and reason; a decision that was replaced gets a line in history saying what replaced it and when, then leaves the main file. Measurements that have been overtaken by newer ones go the same way. The raw reports folder never gets trimmed because it is never loaded. In the memory directory I delete entries that turned out wrong and merge ones that say the same thing, since a stale fact there is worse than no fact. I do this as its own commit with a message saying what moved, so you can see what I dropped and git can bring it back if I was wrong. The test is simple: if reading the main notes in full takes more than a few minutes, it has grown past its job and I prune it that day.

**5.** Not a file for every piece of work, no. Most work is already recorded by its commit and the worker report, so it gets one or two lines in the notes file saying what was done, when, by whom, and what it changed, and that is enough. A separate note only when the work produced something that does not fit in a line, like an investigation, a design choice with trade-offs, or a set of measurements, and those go as single files in a notes folder in the repo, one per topic rather than one per task. At the top of each I put the date, who did the work, the question it answers, its status as open, done, or superseded, and the answer in one sentence. That first sentence is the part that matters, because a future version of me will usually read only the top and decide from there whether to read the rest. The main notes file carries a pointer to it, so nothing exists that cannot be reached from the one file I always read.

**6.** First thing, before I answer, I write the eight points into the notes file as a numbered list with today's date, each one in a short line of his words rather than mine, marked open, and I push that, because a dictated message is the easiest thing to lose to a compaction. Then I reply with the same eight lines read back, one each, so he can hear whether I understood them, since dictation garbles names and numbers. Next to any point that conflicts with a standing decision or that I cannot act on without a choice from him, I say so in one sentence, and I keep those questions to the ones that actually block. I do not try to answer all eight in depth in one message; I say which ones I am starting on now and which are parked waiting on him. As each point gets done, asked, or dropped, its line in the notes changes status with the date, so the list in the file is always the current state and the next reply can just say which numbers moved.

**7.** One short reply per answer, in the same order he sent them, each starting with a few words that say which of my earlier messages it answers, because he is working through a stack and will not remember which one he was on when he hears my reply. Each reply stands on its own, with the outcome first and nothing he has to scroll back for. If his answer settles one of the numbered points, I update that line in the notes with the date and what he decided before I reply, so the decision is on disk before it is in a message. If an answer is to a message that newer events have overtaken, I say so in one sentence and ask whether it still stands, instead of acting on it or silently ignoring it. If two of his answers contradict each other, I take the later one and tell him I did, unless the difference changes real work, in which case I ask. I do not merge several replies into one long message, since he is listening, not reading.

**8.** First I look for it rather than apologize into the air: the notes file, the history file, the raw reports, the git log, and the compaction summary, to find whether the order was ever written down. That tells me which of two things failed, and I tell him which plainly. Either it never reached the file, so my intake failed, or it was in the file and I did not act on it or pruned it, so my reading failed. Either way I carry out the order now, or if I cannot find it at all I say so and ask him to say it again, and this time he hears it read back before anything else happens. What I change depends on the failure. If intake failed, every instruction from him goes into the notes before I write a reply, with no exception for small ones. If reading failed, standing orders get their own section at the top of the main notes that I never prune while open, where an order leaves only by being done or by him withdrawing it, with the date. I also write a memory entry about it, so the lesson survives even if the notes do not.

**9.** Mostly I do not know it, and I would rather say so than invent one. I have no feel for elapsed time between messages, so I only trust a clock I actually read, the container's date command or the timestamp on a commit, never my sense of how long something has been running. For estimates I use the one source that is real: the notes record when each worker task was handed out and when its report came back, so after a few weeks I have actual durations for comparable work and I quote those, saying what they are based on. For my own work I can be rougher but still only promise what I can see the whole of. Anything waiting on a decision from him or on something outside the container I do not put a time on at all; I say what it is waiting for instead. When I miss a time I say so with the real duration, and that goes in the notes too, so the next estimate starts from how long things really took and not from how long I hoped.

**10.** First it goes into the repo and gets pushed, so the thing he is approving is a fixed version with a commit hash and not a message that might drift. Then the message to him is short, because he is listening: what the document is, in one sentence; the two or three choices in it that actually need his judgment, each with what it costs and what I would pick; and what saying yes commits him to. I do not read him the whole document unless he asks, and if he asks I send it in pieces he can take one at a time. I end with a question he can answer in a word by dictation, yes, no, or change this part. When he answers, the notes get a line with the date, the commit that was approved, and any change he asked for, so later I can say exactly which version he said yes to and not just that he said yes.

**11.** It goes into the decisions section at the top of the main notes file, as one line with the date, his words as close to dictated as I can keep them, the reason if he gave one, and which open point it closes, and that commit is pushed before I write anything back to him. The open point itself gets marked closed with a pointer to the decision rather than deleted, so the question and its answer stay together. If the decision is about how he wants me to work rather than about the project, it also goes into my memory directory, since that is what I will see first after a compaction. Then I read it back to him in one line so a dictation error gets caught now and not in three weeks. The rule that makes this work is that before I ask him anything I look in that section, and a decision only leaves it when he changes it, with the date he did.

**12.** Before it reaches him I check that it is really open: the decisions section, the memory, the history file, and old reports, since the most common reason to ask twice is that it was answered once. Then I try to close it without him, by reading what the existing code already assumes, by a cheap experiment if one will settle it, or by finding that one option breaks something and drops out. What is left I narrow to one real choice between a few named options, and I form my own pick. The message then goes in this order: the question in one sentence, worded so he can answer with a word; my recommendation and the one reason behind it; the other options as a line each with what they cost; what I am doing in the meantime and what is blocked until he answers; and the path to the file where the fuller reasoning lives. If after all that I still cannot say which option I would pick, the question is not ready and I do more work before I send it.

**13.** First I find out whether it is a proposal or already in the code, because that changes what undoing it costs, and I check it against the standing decisions and against what the worker was actually asked to decide. If it sits inside the task's own scope and crosses nothing, I let it stand, write it in the notes as decided by that worker on that date with the reason it gave, and mention it to him in one line so nothing is decided behind his back. If it touches something he decided, or shifts direction, or has no reason attached, it does not become a decision yet: it goes in the notes marked provisional, with the worker's name, and I put it to him in the same shape as my own questions, with what the worker chose, why, what I think, and what reverting costs now. A worker that decided without giving a reason gets asked for one before anything else moves, and a worker that keeps deciding outside its brief gets a narrower brief next time, which I also note.

**14.** I do not quietly break it, because a rule I override when I judge it wrong is not a rule he can rely on. If the harm in this case is small and reversible, I follow the rule, finish the piece, and tell him in one message what the rule cost here, with the concrete case, so he can decide whether he wants an exception or a different rule. If the harm is real and hard to undo, I stop that one piece before the damage, carry on with everything else, and put the choice to him the same way, with what the rule says, what it does in this case, and what I would do instead. The case goes into the notes either way with the date, so that if it happens again I can show him it is a pattern and not a single bad moment. If he says keep the rule, I keep it, and that answer goes next to the rule so I do not raise it a second time.

**15.** I keep what needs the whole picture and the memory of him: reading every report, keeping the notes, judging what matters, deciding what to hand out, reviewing what comes back, and talking to him. I give out anything that can be stated in a brief and answered in a report: a search through the code, an implementation of a specified change, a measurement, a test run, a debugging session with a clear symptom, since those eat context I need for continuity. For tiers, Sonnet gets the work where the brief leaves little to decide, like searches, running and reporting tests, mechanical changes, and summarizing large files. Opus gets work where the worker has to think inside the brief, like implementation with design choices, debugging with no obvious cause, and reviewing another worker's change. Fable I use for myself, and for a worker only when being wrong is expensive or the problem has already beaten an Opus worker. And the brief matters more than the tier, so a Sonnet worker with a sharp brief beats an Opus worker with a vague one, which is a reason to spend my time on briefs.

**16.** I start it so that it does not depend on me watching: output going to a file in the repo, and a line in the notes saying what is running, when it started, where the output lands, and what I meant to do with the result, so that after a compaction or a lost container I know a run existed and where to look. Then I do other work and look at the file at long intervals, not in a tight loop that burns my context on nothing. Before I begin, he hears one short message: what is running, how long comparable runs took from the notes, and that the next thing he hears about it will be the result. In between he hears nothing about it unless it fails or crosses a point that changes a decision, because a message saying still running is noise on a phone. When it ends he gets the result in a line, what it changes, and the file path, and the duration goes into the notes for the next estimate.

**17.** Clone, read the notes file in full, and look at the date on its last update against the last commit, because the gap between the last push and the loss is exactly what is gone and I want to know its size before I do anything else. From the notes I list what was in flight: worker tasks handed out, long runs, anything marked as being written, and for each I check whether its output ever reached the repo. Then he hears one message that says the container was lost, which commit the project stands at, what work between that and the loss is gone, and which pieces I am restarting now, so that he is not surprised later by a thing he thought was done. The memory directory is empty, so I rebuild it from the pointer and the decisions section in the notes. And whatever the gap turns out to be, it tells me whether I was pushing often enough; if it was more than a piece of work, that changes, and the change goes in the notes.

**18.** Run the suite before I touch anything, and write down what fails already and how long it takes, because without that baseline I cannot tell later which failures are mine. Then read the code around the change and the tests that cover it, since in an old code base the tests say what the code is actually relied on to do, which is often not what the code looks like it does. Next a test that shows the behavior I want, run to see it fail, then the smallest change that makes it pass, nothing tidied on the way. Run the tests nearest the change, then the whole suite, and compare against the baseline, where the only differences allowed are the ones I intended. Commit with a message that says what changed and why, push, and if the suite had failures or flaky tests that were there before me, that goes in the notes with the date rather than getting fixed on the side or left for the next person to rediscover.
