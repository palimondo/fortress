## Revival change

**The change.** The team's code generator refuses a function, method, object or trait declaration whose own header carries a `where` clause: each of the guards of `forFnDecl`, `forObjectDeclPrePass` and `forTraitDecl` requires `header.getWhereClause().isNone()` (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:2936`, `:4075`, `:4982` at the team's last commit `a874948ac`), so `fortress compile` stops with 'Don't know how to compile this kind of FnDecl.' or 'Can't compile TraitDecl …'/'Can't compile ObjectDecl …'. What the tree now does: it compiles such a declaration, and emits nothing for the clause, whose constraints the checker has checked; a call of a function or method whose clause introduces a `where`-clause variable dies at run time (NEW-G-1); a function or method with a contract is still refused (`ProjectFortress/compiler_tests/WhereBoundFunctionCompiled.fss`, `WhereBoundMethodCompiled.fss`, `WhereBoundObjectCompiled.fss`, `WhereBoundTraitMethodCompiled.fss`, `ComprisesWhereFunctionalMethodCompiled.fss`; `XXXFunctionContractCodeGeneration.fss`). The reason, as evidence: the specification lets a declaration carry the clause, "Static parameters may have constraints placed on them in a \KWD{where} clause." and "Object or functional declarations may include \KWD{where} clauses" (`Specification/basic/trait-parameters.tex:332-333`, `:497`); the clause only constrains static parameters, which the checker checks and the run time does not see; and the library carries such clauses (`Library/FortressLibrary.fss:3449`, `:3451`, `:4114`; `Library/List.fss:87`; `ProjectFortress/LibraryBuiltin/NatReflect.fss:24`), which the code generator refused while the checker passed them, measured as 'Don't know how to compile this kind of FnDecl. node = g[\U\](u:U):String' on a program of that form.
