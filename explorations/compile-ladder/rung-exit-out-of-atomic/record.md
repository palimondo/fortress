# Climb batch 35, rung A: the record lines

## Findings

1. **An exit out of an `atomic` block to an enclosing `label` now keeps the block's writes, on both paths.** Conditions: any exit (`exit` with or without a target or a `with` clause) that leaves one or more atomic blocks, at one thread and at four; a nested block's commit hands its writes to the outer transaction, whose own commit, on the same exit, stores them. Evidence: compiled, `BaseTask.leaveTransaction` commits on a `LabelExit` (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:303-309`); walk, `FortressTaskRunner.doItOnce` commits on a `LabelException` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/tasks/FortressTaskRunner.java:133-141`); tests `ProjectFortress/tests/ExitOutOfAtomicWalk.fss` and `ProjectFortress/compiler_tests/ExitOutOfAtomicCompiled.test` (with `ExitOutOfAtomicCompiledLink.test`), which failed on the base ('FAIL: a ZZ32: 0 =/= a ZZ32: 7; writes within a block that an exit leaves are retained'; 'FAIL:  0 =/= 7; atomic.tex, section "Atomic Expressions": ...') and pass on `eb2f652487` ('OK (1 test)'; 'PASS', 'OK (3 tests)'), and at one thread by direct runs. What it means: a program may exit out of an atomic block; the workaround of a flag set in the block and an exit after it is no longer needed. Row 1039 closes.
2. **A commit that fails on an exit runs the block again, as at a normal end.** Compiled, the commit's `TransactionAbortException` takes `leaveTransaction`'s abort path (`BaseTask.java:317-322`): the block starts again where the abort names its transaction, else the abort goes on to the ancestor's block; walk, `AbortedException` reaches `doIt`'s retry. Evidence: 1000 parallel exits out of a block that increments one counter keep all 1000 writes at four threads (the tests' contended case); `FORTRESS_THREAD_STATISTICS=y FORTRESS_THREADS=4 bin/fortress run ExitOutOfAtomicCompiled` printed 'PASS Had to retry a transaction 93 times' to '291 times' over five runs. What it means: an exit out of a contended block loses no update.
3. **An exception other than an exit still discards the block's writes, on both paths.** Evidence: the gate's atomic runs, 72 of 72 `PASS` on `eb2f652487`, `AtomicThrowRevertsCompiled` among them; under walk a program with `a := 4` then `throw FailCalled("out")` in an atomic block caught outside, beside `b := 6` then an exit: 'a = 0', 'b = 6' (old code: 'a = 0', 'b = 0').
4. **An exit that runs after its label block has completed (row 1041), run inside an atomic block, now commits that block's writes too, on both paths.** Neither path can tell an exit to an enclosing label from one to a completed label block: the compiled commit is for every `LabelExit`, walk's for every `LabelException`. Evidence: under walk, `w := 5` then `kept()`, a function made in a completed `label gone` that runs `exit gone`, inside `atomic do ... end`, the whole in `try ... catch e LabelException => ...`: 'caught LabelException', 'w = 5' (old code: 'w = 0'). Compiled, by reading (`BaseTask.java:303`): the exit then ends the program, as row 1041 says; `compiler_tests/ExitAfterLabelCompletedCompiled.test` still passes on `eb2f652487` ('OK (2 tests)'). What it means: it belongs to row 1041's question (review-queue item 562).
5. **Under walk an exit out of a `tryatomic` block that no `atomic` block encloses, to an enclosing label, never reaches its label** (NEW-A-1). `Evaluator.forTryAtomicExpr` catches every `Exception` and throws `new RuntimeException(e)` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/Evaluator.java:229-231` at 13f4fdea75), the exit among them; the run dies: 'java.lang.RuntimeException: java.lang.RuntimeException: ...:10:7-15: exit from nonexistent label block done', on the base and after the fix. By `Specification/basic/expressions/atomic.tex:46-48` `tryatomic` acts exactly like `atomic`, so the exit reaches the label and the writes are kept. Test: `ProjectFortress/tests/XXXExitOutOfTryAtomicWalk.fss` (green as an expected failure; red with `atomic` in place of `tryatomic` for one run). Compiled, the program meets row 353's wall: 'Can't compile TryAtomicExpr'. Inside an `atomic` block `tryatomic` runs as plain code of the enclosing transaction (row 952), and the exit reaches its label with both blocks' writes kept (skeptic's program, walk, new code: 'o t = 1 3'; old code 'o t = 0 0'). What it means: write `atomic`, not `tryatomic`, around an exit.
6. **Walk's suite is unchanged by the fix:** `ant testSystem` on `eb2f652487`, 879 tests in four shards (214, 228, 216, 221), 0 failures, the count of the last landed gate (`explorations/compile-ladder/climb-batch-34b/gate/summary.txt`).
7. **Under walk an exception thrown out of a `tryatomic` block that no `atomic` block encloses never reaches a `catch` clause around it** (NEW-A-2; found by the rung's skeptic). `Evaluator.forTryAtomicExpr` wraps it in a `RuntimeException`, as it wraps an exit (NEW-A-1, the same cause, `ProjectFortress/src/com/sun/fortress/interpreter/evaluator/Evaluator.java:229-231` at 13f4fdea75); the run dies: 'java.lang.RuntimeException: java.lang.RuntimeException: FortressException: Boom', on the base and after the fix, at one thread and four, where the same program with `atomic` prints the `catch` clause's line. What it means: write `atomic`, not `tryatomic`, around a throw that a `catch` outside takes.

## Revival change

The change: the team's walk runs an atomic block in `FortressTaskRunner.doItOnce`, which commits the block's transaction only after the body ends normally and gives it up uncommitted in its `finally` when anything leaves the body (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/tasks/FortressTaskRunner.java:121-138` at 13f4fdea75), so an `exit` (a `LabelException`) out of the block lost the block's writes. The compiled path's handler, `BaseTask.leaveTransaction`, did the same: it ended the transaction without a commit for anything but an abort (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:293-314` at 13f4fdea75). The tree now commits the block's transaction when an exit leaves it, on both paths, and an exit that leaves a nested block and its outer one commits both; a commit that fails runs the block again; an exception other than an exit still discards the writes. Tests: `ProjectFortress/tests/ExitOutOfAtomicWalk.fss` and `ProjectFortress/compiler_tests/ExitOutOfAtomicCompiled.test`. The reason: the specification, "If it completes abruptly by exiting to an enclosing \KWD{label} expression, writes within the block are retained and become visible to other threads." (`Specification/basic/expressions/atomic.tex:60-63`), and the measured failure on the base: 'FAIL: a ZZ32: 0 =/= a ZZ32: 7; writes within a block that an exit leaves are retained' (walk), 'FAIL:  0 =/= 7; ...' (compiled). An exit that runs after its label block has completed commits the blocks it passes as well, since neither path tells it from an exit to an enclosing label. Under walk an exit out of a `tryatomic` block that no `atomic` block encloses still dies before its label.

Provenance: the question was review-queue item 561, who builds the exit out of an atomic block (row 1039); the answer followed is climb batch 35's fork A1, "An exit out of an atomic block commits the block's transaction, then leaves; a failed commit runs the block again, as at a normal end; an exception other than an exit discards the writes as today" (default); built by climb batch 35, rung A.
