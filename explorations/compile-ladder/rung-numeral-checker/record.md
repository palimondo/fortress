## For FACTS

**The compiled checker converts a numeral where nothing fixes a type into its default, refuses one out of range, and refuses a numeral type written other than as a parameter's type.** Where no place's type has a coercion from the numeral's type or is a numeral type, a numeral becomes a `ZZ32`, or a `ZZ64` or `ZZ` by its value, or an `RR64` with a radix point; a type parameter that numerals alone fix takes the narrowest default holding them all; the conversion into the default ranks as no coercion; a numeral outside a bounded number type's range, or rounding to an infinity, is a static error; `IntLiteral` and `FloatLiteral` are written in a program only as a parameter's type; a `nat` or `int` parameter read as a value is a `ZZ32`. It builds P-173's checker, P-174's written-only rule and P-40's size value. Tests: `compiler_tests/LiteralDefaultCompiled`, `XXXLiteralTypeUnwritable.test`, `XXXNumeralBeyondZZ32Range.test`, `NatValueZZ32Compiled`. Detail: `compile-ladder/rung-numeral-checker/REPORT.md` section 1. F-57's sentences on the checker's numeral type and on no static range refusal, F-73's "narrowest type" for a parameter numerals alone fix, and F-79's "the type that the compiled checker gives an integer numeral" are made false (REPORT.md, section 11).

## Revival change

**The change.**
- The team's checker gave every numeral the one type `IntLiteral` or `FloatLiteral` and kept it wherever nothing converted it (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Misc.scala:468-473`), and gave a `nat` or `int` parameter read as a value the type `IntLiteral` (`scala_src/typechecker/staticenv/KindEnv.scala:69-70` before the change); its tests wrote `IntLiteral` as a variable's and a return type (`ProjectFortress/compiler_tests/Compiled5.ah.fss:17`, `Compiled9.g.fss:18`), and a numeral outside a type's range compiled and failed when it ran.
- The tree now converts a numeral where nothing fixes a type into `ZZ32`, or `ZZ64` or `ZZ` by its value, or `RR64` with a radix point, a type parameter that numerals alone fix into the narrowest of these holding them all (`compiler_tests/LiteralDefaultCompiled`); refuses `IntLiteral` and `FloatLiteral` written in a program other than as a parameter's type (`XXXLiteralTypeUnwritable.test`); refuses a numeral outside a bounded number type's range, or rounding to an infinity, statically (`XXXNumeralBeyondZZ32Range.test`); and reads a size used as a value as a `ZZ32` (`NatValueZZ32Compiled`, `XXXNatValueNN32Refused.test`).
- The reason: under the one type, `bigN = 3000000000` read as a `ZZ32` at a tie and died when it ran ('java.lang.Error: Not in range for ZZ32: 3000000000'), `a: ZZ32 = 4294967295` compiled and raised at run time, and `7` at a parameter of type `Object` took no `ZZ32` clause where the interpreter took it; the Working Draft gives numerals types of their own so that a library decides by coercions how they meet other types (`Specification-1.0-frozen/basic/expressions/literals.tex:141-145`), which a place that declares no coercion does not use.

**Provenance.** P-173 (a numeral converts where it stands, else into its default; the narrowest default; out of range refused), P-174 (a numeral type written only as a parameter type; no coercion, no numeral), P-40 (a size used as a number is a `ZZ32`), P-49; climb batch 29's forks C1 to C8, with C4 as the batch review changed it; climb batch 29, rung C.
