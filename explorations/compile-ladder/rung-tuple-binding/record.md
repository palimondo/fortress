# Rung D, rung-tuple-binding: record lines

## Finding

A top-level binding of several names to one right side compiles and runs on the compiled path, at commit `47aad62914`. The checker types each name by its element, or by its declared type: a numeral element takes its default at an untyped name (`ZZ32`, `RR64`), and its declared type's conversion at a typed one. The code generator evaluates the right side once, into a hidden top-level variable `<Component>$tuple$<first name>`, at the first read of any of the names, and makes each name a top-level variable of its own class, immutable or mutable, exported and imported as any other. A wildcard binds nothing. It holds for a right side that is a tuple expression, a call or a variable of tuple type, for the forms `(a, b) = e`, `(a: T, b: U) = e`, `(a, b): (T, U) = e`, `(a, b): T... = e`, `var (a, b): (T, U) = e` and `(a, b): (T, U) := e`. Where only some of the names declare a type and the right side is no tuple expression of as many elements, as `(total: ZZ64, part) = two()`, the checker checks the right side again against each name's type, so the element converts or the binding is refused (commit `a29032ee89`, the skeptic's; `ProjectFortress/compiler_tests/TopLevelTupleBindingMixedTypes.test`, `XXXTopLevelTupleBindingMixedRefused.test`); at `47aad62914` such a binding compiled unchecked and failed the JVM's verification at class load. ## For FACTS

**A top-level tuple binding compiles: each name is a top-level variable of its element's type, and the right side is evaluated once, at the first read of any name.** The checker gives the tuple that it rebuilds from the checked elements their tuple type, from which each name's thunk reads its own (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Decls.scala:272-277`); the code generator keeps the right side's value in a hidden class `<Component>$tuple$<first name>` and gives each name its own class, whose initializer takes its element out by the tuple's typed getter (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:6528`). So a model line of this form compiles as written, and a name bound so is typed as a single binding's is. Under walk the same right side runs once for each name and once more (row NEW-D-1). Test: `ProjectFortress/compiler_tests/TopLevelTupleBindingCompiled.test`. Detail: `explorations/compile-ladder/rung-tuple-binding/REPORT.md`, "What changed and why" and "The binding as compiled".

## Revival change

**The change.** The team's code generator refuses a top-level declaration of several names: `forVarDeclPrePass` throws 'VarDecl … tupled lhs not handled.' where the left side has more than one name (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:6475-6477` at `db352c1776`), and the team's checker, in its case for a tuple expression of as many elements, rebuilds the right side without a type, so that each name has none (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Decls.scala:270-272` at `db352c1776`). The tree now compiles the form: each name is a top-level variable of its declared type or its element's type, a numeral element at its default, and the right side is evaluated once, when the first of its names is read (`ProjectFortress/compiler_tests/TopLevelTupleBindingCompiled.test`). A use of a name at another type is refused (`ProjectFortress/compiler_tests/XXXTopLevelTupleBindingType.test`, whose prefix is the harness's mark of a compile that must fail). A name's declared type is checked against its element also where other names of the binding declare none and the right side is a call (`ProjectFortress/compiler_tests/TopLevelTupleBindingMixedTypes.test`, `XXXTopLevelTupleBindingMixedRefused.test`): the team's checker leaves such a name unchecked, as it still does in a local tuple binding (`ProjectFortress/compiler_tests/XXXLocalTupleBindingMixedTypes.test`). The reason: the specification gives the form for every top-level declaration, "All forms can be used with tuple notation to declare multiple variables together" (`Specification/basic/variables.tex:99`), and a variable's value "is computed to be the value of the initializer expression" (`:63`); walk's own desugaring states the same design, "Introduce a temporary, then initialize elements piece-by-piece" (`ProjectFortress/src/com/sun/fortress/interpreter/rewrite/DesugarerVisitor.java:858-859`). Walk departs from it: its right side runs once for each name and once more (`ProjectFortress/tests/XXXTopLevelTupleBindingOnceWalk.fss`).
