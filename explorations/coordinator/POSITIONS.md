# Pavol's positions, decisions and known ground

## The goal

- P-7 **The goal is to finish what the designers intended, measured by one program, microGPT, compiled to bytecode and running fast.** The judge is `Specification/`, the Working Draft of February 2011 as the revival revises it, with the 2012 Types chapter cited beside it (P-25). The language is not redesigned. The specification is a living document that states the revival's changes (P-95). The floor to measure against is a pure-Java microGPT, not yet written (PLAN phase 6).
- P-8 **Where the designers left no word, he decides by the goal, a compiled microGPT running fast, not by type-theoretic purity, and stays true to the spirit of Fortress.** He accepts the language's unfinished corners rather than stall in theory. He has not read the specification, the type papers or the library, and takes the designers to have known more than he does.
- P-9 **The search is for microGPT's most readable expression.** In the flat program in Hsu's style, C4, polishing happens in the vocabulary, the operations the model is written in (P-87). C4 is the APL program's target form. Its hyperparameters are tuple bindings, the form an APL strand assignment expands to; the semicolon form of those lines is set aside.
- P-10 **The APL side quest is closed: its remaining ground, tacit functions, characters and nested arrays, is not pursued.** Its sub-language expands APL to Fortress code over native arrays, and its APL microGPT program stays in the walk check (P-30).
- P-11 **The 2D notation is a gimmick: no work on it unless he asks.** Fortify's mathematical rendering bakes one view of a computation into the syntax, though the same mathematics can be written many ways. APL's one glyph for each transformation does that better. It is presentation only, off the path, and no argument for Fortress.
- P-12 **After the switch-over, walk runs the compiled type checker on its programs, and then uses the static coercions that the checker inserts.** The curator wants the checker usable on the programs that walk runs. Today `fortress typecheck` checks a program only against the compiler's prelude, so it is no check of walk's programs (F-9 holds this fact). Walk is not changed for this before the switch-over. After it, walk runs the checker on its programs and so gains their static types. Walk then uses the static coercions that the checker inserts, in place of its choice on the run-time value (P-59, walk's choice of coercions until the switch-over). Still to build: both steps, after the switch-over (PLAN, phase 4, names the batch that gives walk the checker's static types).

## History he knows (do not re-explain)

- P-17 **Unboxed doubles and arrays of doubles are required: without them the revival misses its point.** The code generator boxes every number, and boxing is the main cost on microGPT's array kernels (F-11). The storage is P-84's decision; unboxed arithmetic is PLAN phase 6 (P-33).
- P-19 **The tree is not described as the third-party port's migration grafted on its history.** The files that still say so wait for the lineage cleanup (PLAN, "Off the path, parked"), which `coordinator/lineage.md`, "Files that still repeat it", lists.

## Decisions on record

### The standard and the sources

- P-25 **The specification stays the standard, the Types chapter beside it.** Where the Types chapter of the team's unfinished 2012 restart (F-166) covers a topic, it is cited beside `Specification/` as the designers' later word. On the rules that the revival revises, it is their latest intent, which the goal is to finish. It covers the exclusion rule, as instantiation exclusion in its two-part form, the `covariant` modifier, and `Bottom`, which no program can write.
- P-26 **The type group's late positions outweigh the specification's early text where they conflict.** The early text was a wish. The type group then made the language run, for performance and with specialization a must, and learned what is feasible. So their later word wins: the exclusion rule, specialization kept, the compiler prelude's tower flattened in 2009 and 2010 (P-43), Naden's 2012 write-up, the POPL 2019 paper. The implementers' later word also outweighs unfinished text. The revival does not second-guess them: it knows less than they did.
- P-27 **The library's own practice is the standard.** What microGPT invented goes into the standard library, in the library's own style. Whoever extends the library first studies how it does the same kind of thing, and follows that pattern; exclusion, for one, is all over it. He had to find the diagonal's override himself (P-88) because that study was skipped. No fix is designed from the specification alone or from a workaround on the user's side.
- P-28 **Fleshing out the standard library is a very important task.** Its next layer is the algebraic one: `Ring`, `Field` and what the matrices and tensors of machine learning need, so that the library's traits reach them; it is parked off microGPT's path (PLAN, "Off the path, parked"). It goes into the standard library itself (P-27), not into a tree of the revival's own.
- P-29 **Walk's speed is irrelevant to every judgement of Fortress's performance.** Walk is far slower than Python's interpreter (`explorations/microgpt-port.md`, "Step-0 results", a measurement of 2026-08-23). Fortress's performance is judged on the compiled path, once the compiler runs programs. So no performance decision rests on walk's timings. In particular, until microGPT runs compiled, C4, the flat microGPT program, is not edited for speed. The gate never runs microGPT's two programs, C4 and the APL-style program, because they run too long to be tests. Why: walk is the unoptimised path, as a debug build is in Swift, where performance is not judged either.
- P-30 **The microGPT walk check after a batch runs in under a minute.** It runs about two forward-and-backward passes against the reference values, which shows that the model's mathematics still works and that the library's changes did not break it. A slower check is to him a waste of time.
- P-32 **The territory map (`coordinator/map/`) maps the tree down to where the design intent is written, in the papers as well as the specification.** It and the record's other maps, FACTS and `INDEX.md`, are kept current and used, so that nothing on record is found again from scratch.
- P-33 **The plan (`coordinator/PLAN.md`) holds the phases in the order he approved.** Still to build: 3, the checker at a true zero; 4, the switch-over, natives then names; 5, microGPT compiles: its static types, the array design and the code generator's holes; 6, microGPT fast. Where the work stands: PLAN's "Where we stand". Re-approval row 41 (ledger row 320: a component named apart from its api does not link) joins the switch-over's design.

### The one library and the compiled checker

- P-37 **One library, the interpreter's, is the library the compiler checks.** The interpreter's `FortressLibrary` and `FortressBuiltin` become the compiled path's library. He sees the compiler's prelude (`CompilerLibrary`, `CompilerBuiltin`, `CompilerAlgebra`) as a bootstrap to remove, so no declaration goes into it, and its three files are deleted at the switch-over with their tests kept. Code-generator rungs go on. How the checker comes to accept the library is a plan shown to him step by step, not a question to ask again. Still to build: PLAN phase 4.
- P-38 **The compiler prelude's defects are not repaired: they go with it at the switch-over.** Its `Maybe` block and its `REM` guard `if other = -1 then 0` stay as landed until the prelude is deleted, and their tests stay. Then the compiled tests respell its reversed wrapping and saturating operators (row 348), `ZZ64`'s compiled shift closes (row 381), and the specification's `shift` reaches the compiled path (row 383). `XXXShiftDeclRungI` is then promoted, and the switch-over batch finds the compiler tests that bind `shift`, a reserved name from then on. Still to build: PLAN phase 4.
- P-39 **The checker count is measured in every gate, and its total never turns the gate red.** A rise of the count is reported and never fails a batch on its own; F-66 gives what turns its stage red. The distance to the switch-over (F-53), over all apis and components, is a report-only stage of the phase-3 gates, whose work drives it down.
- P-40 **Sizes are checked, and a size that inference leaves unknown is an error only where it is used.** A size is a `nat` or `int` static parameter, such as the length of an array in its type. The compiled checker checks sizes, and refuses a size beyond `NN32` or `ZZ32` (F-140, the bound on both paths). Wherever the array design creates a JVM array, it checks the length there, at run time, and refuses one over 2^31-1. A size that inference leaves unknown is an error only when it reaches a type, a name or a value. So a declaration may declare a size that none of its types uses, and pass. A call that cannot fix a size of the declaration that it would choose is refused, also inside an overload set, instead of passing over that declaration. In the rule that no type extends two different instantiations of one generic trait, two instantiations differ when any static argument but an operator differs, so `Vec[\3\]` and `Vec[\4\]` are two; boolean arguments count too once the checker has boolean parameters. A size used as a number, as in the range `0#n`, converts to `ZZ32` where one is needed, as a numeral does. The 17 vector and matrix operators of the `FortressLibrary` api lose their unused sizes by `explorations/perf-probes/array-sites/e3-rebased.patch`, which finishes the team's own fix of 2008: that fix removed them from the component only. Built, except three parts. The JVM length check waits for the array design (PLAN, phase 5); under walk such an array dies with a raw Java exception (gap-ledger row 527). The checker still passes over a declaration whose unfixed size occurs in its own parameter type (row 400). The checker compares no boolean arguments (row 406).
- P-41 **At run time a size travels as the descriptor that a type argument has (design B).** It fills the slot that the team's code generator reserved. Each number has one descriptor, from a table, with no holder class, as the team instantiates types. Operator static arguments stay compile-time names (F-39): he sees no need to unify them.
- P-42 **An unbounded type parameter's implicit bound is `Any`, not `Object`.** `Any` holds tuples, functions and `()`, which `Object` does not, and the library instantiates its generic containers at tuples, arrays indexed by pairs among them. The specification states the bound, with a callout that keeps the Working Draft's `Object`. The compile path's `Object` bound departs from it until the switch-over (row 412).
- P-43 **The exclusion rule stays, and the number tower is flat (route A).** The compiled checker keeps the multiple instantiation exclusion rule. So the library's numbers are flat, as the team (Chase, Ryu, Maessen and Allen) flattened the compiler prelude in 2009 and 2010. The fixed widths, `ZZ`, `QQ` and `RR64` are siblings under `Number`, each with its own algebra, and `Number` has no catch-all operators. Why: the flattened prelude is the team's last record of the Fortress way, and its route leads to the POPL 2019 paper, which keeps the rule. He cares that specialised code runs fast, not how a specialisation is chosen. F-46 prices a return to route C.
- P-44 **`AnyIntegral`'s closure stands, and the checker reads `comprises` the 2012 way.** The closure `AnyIntegral comprises { ... }` stands, with a `NOT YET` comment in the team's wording. A generic child of a closed trait may extend it when every type that the checker knows below it is listed. The clause's text and walk stay as they are. Row 487 records the hole that every reading but the 2008 one shares: a program's own `Integral` subtype in another component is not caught.
- P-45 **Overloaded declarations may differ in their static parameters.** The specification drops its sentence that forbids this, and keeps it as superseded text. It states instead the overloading model of the type group's 2011 paper (`Papers/Types/`), which the compiled checker already used. The checker keeps the paper's three rules: No Duplicates, Meet and Return Type. It checks the Return Type Rule over every instance of a generic declaration that the argument types allow, not over one guessed instance. One rule of the old sentence survives: if one generic declaration is more specific than another, their static parameters must line up position by position, as Java's rule for overriding a generic method requires. Walk chooses among overloads by the parameter types that each declaration declares, not by the order in which they are written. At load, walk judges each pair of two generic declarations by the checker's rules on their declared parameter types. It does not refuse a pair only because none of their parameter types exclude, as when one declaration is more specific than the other. Walk and the checker must accept the same pairs. The library repairs, by declarations of its own, the overload sets that the checker refused, and no line of microGPT's two programs changes. Still to build, where walk or the checker still judges a pair against these rules: walk compares two functional methods of a generic trait or object on the instance that a call makes (F-26); both paths refuse the paper's own valid example (gap-ledger row 539); walk refuses two nested generic functional methods of a plain trait, and fails at a call on them in a generic trait (rows 779 and 780); and walk and the checker disagree on four kinds of pair (rows 759 and 786 to 788). PLAN, phase 3, item 19, the next checker batch's candidates, lists all of these rows but 539.
- P-46 **A conversion makes a call possible, and never changes which declaration runs when one already fits.** Declarations are chosen on declared domains, by applicability and then specificity (P-45). The chosen one is instantiated by answer 8's promotion (P-74), its coercions inserted statically. So beside a plain arm over `Any`, a generic arm over `T extends Number` runs at `ZZ64` for a mixed-width call. Why: he wants fast generic code that a JVM can specialise. His own broader rule, to apply any conversion that reaches a specific declaration and to fall back to a plain one only when none does, is not taken. Both paths infer static arguments with coercion and the same promotion, and P-49 orders the checker's attempts. Still open: the dispatch between two generic declarations (row 537, PLAN phase 5).
- P-47 **Each integer type declares its own `MIN`, `MAX` and `MINMAX`.** It follows `QQ`, `RR64` and the compiler library, and the specification's `ZZ`, which declares its own `MIN` and `MAX`, so that under walk the family answers at the promoted type.
- P-48 **A type parameter that a call's arguments do not fix takes its bound, never `Bottom`.** Its instance is the intersection of its upper bounds, constrained by the call's static return type, never the arguments' union or the value's type alone. The rule is the team's later word (POPL 2019). He ranks the team's later work above his own reading. It sets the instance, not which declaration runs (P-46). MicroGPT's types are concrete, so it is untouched. The library keeps the team's unbounded declarations. Walk has no static types, so where dispatch reaches a declaration it still takes the value's type. Still to build: a compiled dispatcher that carries the static return type (row 538, PLAN phase 5).
- P-49 **The checker tries a call without the expected type first, and with coercion only after (row 508).** It keeps the first attempt, by subtyping, when its result converts to the expected type, and only then tries coercion with the context. So a declaration that fits the arguments as they are is not passed over for one reached by coercion.
- P-50 **The body of a `label` expression, and each value that an `exit` gives it, take the expected type of the whole `label`.** A `label` is a named block that code inside it can leave early with `exit`, giving a value with `with`. The specification types a `label` as the union of its body's last expression and the values that its `exit` expressions give. So when a `label` has an expected type, the compiled checker passes it into the body and into each of those values, as it does into each clause of a `typecase`. The specification's inference chapter lists the body and those values as contexts that carry an expected type. P-51 decides the same question for a call written as another call's argument. Built (F-87 lists the checker's contexts that carry an expected type).
- P-51 **The checker retries a call written as another call's argument against each declaration's parameter type.** Take an outer call `f(g(x))`, whose argument is an inner call `g(x)`. If none of the compiled checker's attempts at the call accepts `f(g(x))` (P-49 gives the order of those attempts), the checker checks `g(x)` again, once for each declaration of `f`, with that declaration's parameter type at `g(x)`'s position as its expected type. The retry covers every inner call with inferred static arguments, not only one whose type parameter occurs in its result type alone. Why: the curator wants the type inference rules unified across contexts, which covers cases that the team did not build. As built, a generic declaration of `f` is first instantiated from the other arguments. The declaration whose retry succeeds is kept, or the most specific of several; otherwise the call goes on as it would without the retry. The measurement behind the decision is in `explorations/reviews/argument-context-probe.md`. Built.
- P-52 **A range of rank 2 or 3 checks containment corner by corner (row 657).** The bounds check behind `narrowToRange` compares the other range's bounds by the ranges' point-by-point order, `PCMP`, not by the tuple order, which serves sorting. So `((0,0):(9,9)).narrowToRange((2,-1):(5,5))` raises `IndexOutOfBounds`.
- P-53 **`String`'s `left` and `right` answer `Just(c)` (row 606).** For a non-empty string they return `Just` of the first and of the last character, as their declared `Maybe[\Char\]` and the `left` and `right` of the library's ranges and lists do. So walk prints `Just` of the character, not the character.
- P-54 **`QQ`'s `ceiling` and `truncate` keep `ZZ` and raise at +∞, −∞ and 0/0 (row 635).** The declared integer result and the peer languages win over the specification's paragraph that returns the argument at an infinity, and that paragraph is revised. `floor`, `round` and the two brackets raise too. A rung after the switch-over makes `QQ` follow the float ruling (row 330): the methods keep the type, and the brackets, `round` and `truncate` give ℤ.
- P-55 **A size may hold arithmetic, compared by its written form once numerals are folded (array fork 1, 15a with (b)).** The checker accepts a sum, difference, product or power in a size. `2 3` folds to `6`, but `s0 s1` is not `s1 s0`. The class loader computes the value when it makes a class. A size name may equal a numeral, as the team's Q&A answers, so the `N[\0\]` arm of a `typecase N[\b0\]` is reachable. The library keeps the team's sizes written as products and sums.
- P-56 **The open range `(:)` keeps its wildcard type, and its five cutting methods fail (row 656).** `TrivialOpenRange` stays `OpenRange[\Any\]`. A range over `ZZ32` is not a range over `Any`, so no body can type its `truncL`, `truncR`, `every`, `imposeStride` and `atMost`. They are `fail` bodies with a message, the team's own device for such a body. Nothing in the tree calls them on `(:)` but the five tests that pin the `fail`. Way (c), `(:)` over `ZZ32`, is not taken: probe P3 found that it makes things worse, with more values lost than gained (`reviews/ranges-and-index-types.md`, section 5).
- P-57 **`LexicographicReduction.isLeftZero` takes `TotalComparison`, so the team's answers are reached (row 582).** The team's overload `isLeftZero(_:Comparison)` is declared over `TotalComparison`, so the inherited `ReductionWithZeroes.isLeftZero` no longer shadows it. `LessThan` and `GreaterThan` answer `true`, and `EqualTo` `false`. Why: it cleared the count stage's last api error (F-53).
- P-58 **Every native binding is a `builtinPrimitive` call naming a static helper.** Each binding stays the library's own form, a body that is exactly `builtinPrimitive("…")`, and its string names a static helper of `nativeHelpers/`, not an interpreter glue class. Walk loads the string through a loader beside its glue classes. The compiled path rewrites each body at the parse into a synthetic `import java` and a call before the checker, and refuses a string that names no helper. Each natives rung's bindings meet the checker as they land, not all at once at the switch-over. Way 2, `import java` blocks in the library, is not taken. Still to build: the natives rungs, PLAN phase 4.
- P-59 **Walk chooses coercions on the value until the switch-over.** Walk has no static types, so it chooses a coercion by the value, where the specification and the compiled path resolve it statically. This is accepted as the interpreter's limit, stated in one callout of the coercion chapter, with `XXXCoercionStaticRungC` and `XXXCoercionStaticNarrowRungC` as its record. After the switch-over walk takes the static coercions that the checker inserts. MicroGPT's static types are concrete, so both paths agree on it.
- P-60 **The specification reads a `comprises` clause at the level of values (row 491).** "Covers" is defined once, and the Meet Rule has a closed-trait case. A call whose argument sits between closed traits is typed by the intersection of its candidates' return types, with run-time uniqueness in place of static. Why: the proof addendum (`reviews/comprises-type-level-proof-addendum.md`) shows this sound for ground declarations, `G[\ZZ32\]` among them, at calls that need no coercion, with the coverage search local to overload checking. A generic declaration that needs a run-time instance is outside it. The specification states that boundary.
- P-62 **The `covariant` keyword is future work, off the path to microGPT.** Row 404 records the hole: the checker accepts variance, and neither path carries it to run time. Its expected-failure tests are owed in a batch rung. The future work is declaration-site variance, carried to run time on both paths. When it lands, a rung tries to bring back the specification's sign-refined number types as covariant static parameters.
- P-146 **In a self-typed trait, the compiled checker types `self` in the method bodies as also being the implementing type.** A self-typed trait is a trait `C[\X\]` whose parameter `X` extends `C[\X\]`, such as `Integral[\I extends Integral[\I\]\]`. In its method bodies, `self` has the type `C[\X\] & X`. The method signatures keep the plain trait type, because the proofs of the POPL 2019 paper on multiple dispatch (Park, Hong, Steele and Ryu) assume that no declared type holds a type parameter inside an intersection. The checker refuses a type that extends such a trait at another type, since an extender must be a subtype of the static argument that it gives: `object Bad extends Integral[\ZZ32\]` is refused, because `Bad` is not a `ZZ32`. Scala has the same rule for self types. The library's text gains no self type and no `comprises` clause, and walk is unchanged. The rule accepts every self-typed method body of the library except `Integral`'s `numerator`, which each integer type declares instead. Why: the checker reads the library as the team wrote it, as P-44 does for the closure of `AnyIntegral`, by one rule that peer languages share. Built (F-225 states the rule as built).
- P-147 **An object defines an inherited abstract method when its bodies of that name at narrower parameter types together cover the abstract method's parameter types.** It is the team's rule of 2012, in Steele's compiled checker and Welterweight's Covered rule, with `comprises` clauses read as the checker reads them; a body at the abstract method's own types is the plain case. So the team's `Pairs` and `FileConversion` stay valid, walk agrees with the checker, and the traits chapter's sentence is revised in the S1 form (P-96). Walk's allowance of any one narrower body goes.
- P-148 **The checker's speed comes right after its correctness.** A rung that adds to the checker first makes the change correct, then, in the same rung, makes the new code fast without changing which programs the checker accepts or refuses, so that no optimization is left for after the landing. The aim is a checker that stays usable as it grows: some slowdown is fine, but new checks have made it orders of magnitude slower, enough to hold a landing. The timing is a smoke test: one run, to catch a slowdown of several times; a small difference is noise. Built in the `fortress-repo` skill (`compiler.md`, "The checker's time").
- P-149 **An object that inherits an abstract functional method from one trait and its body from a sibling trait, and declares none of its own, is refused.** So `object O extends { A, B }`, with `pick(self)` abstract in `A` and given a body in `B`, must declare its own `pick`, as the specification's text and the type group's Welterweight calculus require and as walk already does; an abstract and a concrete declaration of one method in one trait are refused too. Why: the revival honors the designers' intent and does not change Fortress's nature for a convenience; other languages are consulted only to reconcile a conflict between earlier and later designers' choices, and here there is none.
- P-151 **Only the `where` forms the team wrote down are built.** A trait that extends another under a `where` condition is that type only where the condition holds, and its members are checked under the condition; a method's `where` condition bounds its static parameters; and the team's comment `AnyList comprises List[\E\] where [\E\]` becomes live. `SUM`'s fusion with `MAX` and `MIN` stays, the team's commented generic `distribute` measured for its two type errors; the rest of `AnyList` moves into `List`. Why: a feature with little support in the team's work bends the language beyond what he can review; one is built where the team left enough design intent for it, or where it is on the critical path to running fast compiled. Still to build: the rest of `AnyList` moved into `List`, which climb batch 17 built otherwise (review-queue item 188); the members scoped to the condition, since a member checked under it stays callable where it fails (row 773); walk's half (row 774); and the code generator's half (row 701), after the switch-over (PLAN, phase 3, the `where` clauses' line).
- P-152 **Exclusion between two generic declarations is read over the whole parameter type, on both paths (the specification's existential reduction).** Two declarations whose parameter types exclude each other only together, through a shared parameter that fixes one static argument, are read as the specification reads them: the pair is valid where the declared domains meet the overloading rules. Walk and the compiled checker both change to read the whole parameter type, so that rows 740 and 741 close, and walk loads the program that it refused after climb batch 16. Why: the type group's paper of 2011 decides exclusion between parameter types with static parameters by existential reduction (`Papers/Types/exc-reduction.tick`; the team's later word, P-26), as the revised specification states (`advanced/overloading.tex`, "Declarations with Static Parameters"). Still to build: walk's reading of such a pair where one declaration has a `where` clause (row 787), and of an object type over a static parameter (row 788).
- P-154 **A list compares only elements that are totally ordered, while a pair of floats is ordered.** So on the checker a list of floats or of `QQ` has no `<`. No lexicographic trait over partially ordered elements is added now: the team never wrote one, and the case touches neither the distance nor microGPT. Why: the team's later code bounds the element of both lexicographic traits by a total order (`Library/incomplete/advanced/Fortress.PartialTotalOrders.fss:117-140`; P-26), and conditional extension is a `where` form the team wrote (P-151). Still to build: walk's half (row 774; PLAN, phase 3, item 19), and a revision note at the specification's two sentences that order every list (`advanced-lib/algebraic-constraints.tex:519-522`, `basic/operators/opr-overview.tex:293-295`).
- P-155 **Symbolic operators are checked for overloading before the switch-over.** The compiled checker's overloading check reads `+`, `^`, `||`, the subscripts and every other symbolic operator by the rules it applies to any function, so that the switch-over's zero is a true zero. Why: the skip is a gap the team knew (its open-issues list calls the library's subscript pair "not really a valid overloading"), not a rule, and an unchecked zero hides known errors. Each design that the check needs, such as a bound on the subscripts' index type that keeps ranges out, or a vector plus a number beside a vector plus a vector, is brought to him with the probe's measurement before its rung (`perf-probes/symbolic-operators-2/REPORT.md`). Still to build: the check and its rungs (row 584; PLAN items 38 and 59).

### Numbers

- P-66 **The integer principle: Java's and the JVM's defaults stay where they make sense, and are corrected where they fail high performance or mathematical precision.** The team did so with rounding. A hardware behaviour that bytecode can express gets its own explicit spelling, as the specification's wrapping and saturating operators do. Where the JVM prevents a correct implementation, the project gives way for now. The peers to compare are Julia, X10, Swift and Rust.
- P-67 **`round` on an exact half goes to the even integer, on both paths.** Under walk and on the compiled path, `round(2.5)` gives 2: an `RR64` or `RR32` value rounds an exact half to the even integer, as a rational does. This is the specification's rule for rationals, the default rounding of IEEE 754, and the rule of the team's own `round` on rationals. Built.
- P-68 **`floor` and `ceiling` on the float types keep the float; ⌊x⌋, ⌈x⌉, `round` and `truncate` return the unbounded ℤ.** The library's own `truncate` and `round` are tidied to match. Still to build: a library rung after the switch-over, which first counts the interpreter tests whose output changes (row 330).
- P-69 **`LSHIFT`/`RSHIFT` are bit operators on the fixed widths; `shift` is exact on ℤ.** A count at or beyond the width gives 0 or the sign, and a negative count reverses. Shifted-out bits fall silently, as in every peer language. Compiled code shifts the machine word, never through ℤ. A count may have any integral width (row 380). Built on both paths, but for the compiled `NN32` and `NN64`, whose shifts are refused (row 442); the compiled path gets them, `shift` and the any-width count at the switch-over (P-38).
- P-70 **`GCD` and `LCM` give nonnegative results, and `LCM` raises an overflow error when the multiple does not fit, on both paths.** The specification says so. Built (row 334), but for the compiled `NN32` and `NN64`, which get both operators at the switch-over (row 442).
- P-71 **`|0|`, `-0` and `0 DIV -1` do not overflow: an overflow guard tests for the most negative value itself, not for `a = -a`.** The compiled natives and their siblings with that guard are fixed. Built (row 333).
- P-72 **`narrow` out of range truncates to the low 32 bits, signed and unsigned, on both paths.** The team's boundary test `tests/UnsignedTest.fss` asserts the unsigned case. Built (row 346).
- P-73 **Fixed-width overflow raises `IntegerOverflow` under `walk`, as the specification says and the compiled path does, `NN32` and `NN64` included.** Code that means to wrap uses the specification's operators ∔, ∸ and ⨰, fully parenthesised, since their precedence is stated only among themselves. The saturating operators wait for a step of their own. Built (row 379).
- P-74 **Mixed integer widths convert by declared coercions: each wider integer type declares a `coerce` from each narrower integer type, as the compiler prelude does.** A conversion that is exact is implicit, and a conversion that can lose precision is written out. So `ZZ32` values and integer numerals coerce into `RR64` implicitly, and a `ZZ64` value into `RR64` is written out (P-66, Java's defaults corrected where they lose precision). A call of a generic function with arguments of mixed widths infers, on both paths, the narrowest type into which its arguments coerce. A range is over `ZZ32` only (P-77, the rule on ranges). The specification's `widens` declaration, which would make a narrow computation stored into a wide variable run wide, is deferred. Built, except the implicit coercion of `NN32` into `RR64`, which is still to build (P-75 holds it, with its conflict with the overloads of `RR64` and `ZZ64`).
- P-75 **`NN32` coerces into `RR64`, since the conversion is exact (P-74).** Not built: with that coercion, a `ZZ32` with an `NN32` is ambiguous between `RR64`'s and `ZZ64`'s operators on both paths, where P-74 gives `ZZ64` (row 575). It waits as PLAN item 37, with its candidates.
- P-76 **The numeral switch, split by where the static types are: a numeral's type is `IntLiteral`, which each number type converts from, in the library now and under walk once walk has static types.** It is the compiler library's working design, taken over the specification's unfinished numeral types. The library half (Q-lib) is built, with the team's held-back `IntLiteral` arithmetic enabled now that coercion exists. Walk's half (Q-walk) waits for the switch-over to give walk the checker's static types (PLAN phase 4), and rows 79, 395, 443, 454's walk half, 486 and 511 wait with it.
- P-77 **Scalar ranges are over `ZZ32` only, the JVM's largest array size, as the compiler library declares them.** A range over another integer type is a static error, and a wider counter is a `ZZ32` loop that widens its index. A range of rank 2 or 3 is a tuple of `ZZ32` ranges, and the public range traits stay generic in their index type. Built.
- P-78 **`SUM` and `PROD` without the `Number` catch-all: one generic reduction each over the library's algebra, taking its identity from the static argument.** A clause form whose element type nothing at the call fixes writes its static argument; `SUM e` and `DOT` keep their text. `BIG MAXN`, `BIG MINN` and `BIG MINMAXN` are gone, and `MAX` and `MIN` get no identity on the integers or the floats (F-60). - P-79 **Every team demo is kept running as the tree changes.** A demo that a change breaks is rewritten in the same batch where the way is known, as climb batch 20's rung I wrote a float base in three demos, `10.0^(-4)` in `BiCGSTAB` and `BiCGSTAB2` and `10.0^(-6)` in `npbft`; one that fails for want of a feature runs again once the feature is built. - P-80 **The sign-refined number types are a superseded design: a program tests such a subset at run time.** The number chapters test a value's sign by comparison, and a float's finiteness by `check` or `check*` on `RR64`. `advanced-lib/numbers-advanced.tex` stays word for word, marked superseded in the S1 form (P-96), so that the original design stays on record. Built. Their return with covariance is P-62's.
- P-153 **The integer power splits on the base: an integer base gives an integer or raises an error, and a float or rational base gives the fraction.** Each integer type's `^` returns its own type at every exponent. At a negative exponent, the bases 1 and -1 give their exact power, a base of 0 raises `DivisionByZero`, and any other base raises `IntegerOverflow`. A program that wants a fraction writes a float or rational base, as in `2.0^(-1)`. Why: the team's later code gives an integer power the type of its integer base at a signed exponent (P-26, the team's later work outweighs the specification's early text). Overloads choose by type, and no type tells a negative exponent from a non-negative one, since a signed integer or a numeral can be either. So the split is on the base, and the sign of the exponent is tested at run time, as the library tests a value's sign everywhere (P-80, run-time sign tests in place of sign-refined types). Built in the interpreter's library and under walk, at an exponent of any integer type (F-263 states it as built). Still to build: the same rule on the compiled path, whose own powers give 0 at a negative exponent and a raw Java exception at a base of 0 (gap-ledger row 441), and overflow silently or with a raw Java exception (row 523); PLAN, phase 4, the natives, binds the library's `^` to compiled helpers.

- P-85 **The array design's three questions are open, with no default, and return after the switch-over with array decisions A, B and D (PLAN item 13).** The three: a store per element type chosen by the factory, the size also kept as a field of the store, and a factory for a size known only at run time that returns the unsized `Array`. A is how `double[]` goes under a float vector, B where unboxed arithmetic happens, D sizes in the model's own types (P-87). The whole preparation for the array work is done before the switch-over. ### The suites and the gate

- P-102 **Test first, the test kept.** Every edit of source code in the original tree starts from a failing test added to the test suite: the worker writes the test first, verifies that it actually fails, makes the fix, proves it passes, and the test stays in the test suite from then on; the full suite stays green. The test needs no commit of its own: the test and the fix may land in one commit. How the test is written is in the `fortress-repo` skill's tests part.
- P-103 **The suite's verdict is the check.** A test passes or fails, as the team designed the suite, and a value that matters is asserted in the test with the mechanisms the suite already has (an `assert` in an interpreter test, `run_out_equals` in a compiled one). What a test prints beyond its checks does not matter. So no expected-output files are added; none of it is offered to him again.
- P-124 **The specification's examples join the gate at zero red.** `ant testSpecData` runs them under walk as a gate step, and every example must pass. A failing example is not respelled for walk, and no list of known red examples is kept: the implementation is fixed instead. Built.
- P-125 **The suites run Fortress in parallel, pinned at four threads in `build.xml`.** Parallelism is native to Fortress, so a one-thread suite has a blind spot, and sparing a four-CPU machine is no reason for one. A test that fails or varies under parallelism is written wrong, such as a write that needs `atomic`, or it exposes a defect: either is fixed, never hidden by a pin. The pin makes every run the same, whatever the calling shell sets. Built.
- P-150 **No resident compiler is built.** A background JVM that serves Fortress commands, as Scala 2's `fsc` did, would save too little of the workers' time to be worth building (F-234), so the speed work goes to the checker itself (P-148). It is not tried again unless something significant changes.
