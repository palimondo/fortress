## Revival change

**The change.**

- The team's source: the specification's coercion chapter chooses a declaration applicable without coercion before any that a coercion reaches ("we first determine whether there exists a declaration that is applicable without coercion. If so, the most specific declaration is selected", `Specification/basic/conversions-coercions.tex:526-528`), and the revival's own text read a numeral so until this change: a numeral was applicable without coercion to a parameter of its default type and to one that fixes no type, and "its conversion into any other type is a coercion" (`Specification/basic/conversions-coercions.tex:111-114` at db352c1776). The interpreter's library declares `opr =(a:Any, b:Any)` and `opr =/=(a:Any, b:Any)` (`Library/FortressLibrary.fss:96-98`), which a numeral fits at its default.
- What the tree does now: at a call, a numeral goes to the most specific declaration that takes it, by its own coercion if need be. Where one declaration fits the numeral at its default and another is reached only by the numeral's own coercion, every other argument fitting as it is, the second runs when its declared parameter types lie strictly below the first's by subtyping. So `u = 0` and `0 = u` are `true` and `u =/= 0` is `false` for a zero `u` of `NN32`, `NN64` or `RR32`, on both paths; `h = 0.5` is `true` for `h: QQ = 1/2`; `k(5)` runs `k(x: NN32)` beside `k(x: Any)`; `case u of 0 => ...` matches a zero `NN32`; a program's own number type with a numeral coercion and its own `=` compares with a numeral by that `=`. Where the two declarations are not ordered by subtyping, the one that the numeral's default fits runs: `f(1.5)` beside `f(x: RR32)` and `f(x: RR64)` runs the `RR64` declaration. Of two declarations that a call reaches only by coercion and that are not ordered, the one that the numeral's default fits runs, also where they differ at another argument: `mul(1.0, f)` for `f: RR32` runs `mul(a: RR64, b: RR64)` beside a program's `mul(a: Q, b: Q)`, and `1.0 s` for `s: ZZ32` is `RR64`'s juxtaposition. A value's coercion still never changes which declaration runs. `Equality[\T\]` declares `opr =/=(self, other:T)` as `NOT (self = other)`, so `=/=` reaches a type's own `=` for every type that extends `Equality`. A value whose static type is `Any` or `Number` fixes no type for a numeral beside it, which takes its default: the compiled checker answers so, and walk, which has no static types, reads the value's run-time type, so for `a: Any` holding a zero `NN32` walk answers `a = 0` `true`. Tests: `compiler_tests/NumeralMostSpecificCompiled`, `compiler_tests/NumeralTieDefaultCompiled`, `tests/NumeralMostSpecificWalk`, `tests/NumeralEqualsNumberWalk`, `tests/NotEqualNumeral`; the expected failure `tests/XXXNumeralBesideAnyWalk` for walk's departure.
- The reason, as evidence: with no `=` between a numeral type and a number type, `u = 0` met the library's `=` over `(Any, Any)`, which the numeral's default `ZZ32` fits, and `SEQV` of an `NN32` and a `ZZ32` is `false`: walk printed 'FAIL: u = 0 for an NN32 zero' on the code before the change. On the compiled path `k(5)` beside `k(x: Any)` and `k(x: NN32)` died with 'NoSuchMethodError ... \=k{...}(fortress.AnyType$Any)', and the checker refused `mul(1.0, f)`: 'Ambiguous coercion in call to function mul'. The Working Draft says that `e =/= e'` is `NOT (e = e')` (`Specification/basic/operators/opr-overview.tex:272`).
