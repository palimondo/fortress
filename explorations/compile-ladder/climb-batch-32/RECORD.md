### Rung N, `rung-numeral-most-specific`: a numeral at a call goes to the most specific declaration

**The change.**

- The team's source: the specification's coercion chapter chooses a declaration applicable without coercion before any that a coercion reaches ("we first determine whether there exists a declaration that is applicable without coercion. If so, the most specific declaration is selected", `Specification/basic/conversions-coercions.tex:526-528`), and the revival's own text read a numeral so until this change: a numeral was applicable without coercion to a parameter of its default type and to one that fixes no type, and "its conversion into any other type is a coercion" (`Specification/basic/conversions-coercions.tex:111-114` at db352c1776). The interpreter's library declares `opr =(a:Any, b:Any)` and `opr =/=(a:Any, b:Any)` (`Library/FortressLibrary.fss:96-98`), which a numeral fits at its default.
- What the tree does now: at a call, a numeral goes to the most specific declaration that takes it, by its own coercion if need be. Where one declaration fits the numeral at its default and another is reached only by the numeral's own coercion, every other argument fitting as it is, the second runs when its declared parameter types lie strictly below the first's by subtyping. So `u = 0` and `0 = u` are `true` and `u =/= 0` is `false` for a zero `u` of `NN32`, `NN64` or `RR32`, on both paths; `h = 0.5` is `true` for `h: QQ = 1/2`; `k(5)` runs `k(x: NN32)` beside `k(x: Any)`; `case u of 0 => ...` matches a zero `NN32`; a program's own number type with a numeral coercion and its own `=` compares with a numeral by that `=`. Of two declarations that a call reaches only by coercion and that are not ordered, the one that the numeral's default fits runs, also where they differ at another argument: `mul(1.0, f)` for `f: RR32` runs `mul(a: RR64, b: RR64)` beside a program's `mul(a: Q, b: Q)`, and `1.0 s` for `s: ZZ32` is `RR64`'s juxtaposition. A value's coercion still never changes which declaration runs. `Equality[\T\]` declares `opr =/=(self, other:T)` as `NOT (self = other)`, so `=/=` reaches a type's own `=` for every type that extends `Equality`. A value whose static type is `Any` or `Number` fixes no type for a numeral beside it, which takes its default: the compiled checker answers so, and walk, which has no static types, reads the value's run-time type, so for `a: Any` holding a zero `NN32` walk answers `a = 0` `true`. - The reason, as evidence: with no `=` between a numeral type and a number type, `u = 0` met the library's `=` over `(Any, Any)`, which the numeral's default `ZZ32` fits, and `SEQV` of an `NN32` and a `ZZ32` is `false`: walk printed 'FAIL: u = 0 for an NN32 zero' on the code before the change. ### Rung F, `rung-generic-function-value`: a generic function passed as a value under walk

**The change.** The team's walk gave a function with static parameters no type as a value: `Fcn.type()` returned null for it, and the team's comment there says "FGenericFunction never calls setFtype and this returns null in that case. This leads to extensive bugs particularly when a generic function is overloaded along with non-generic siblings, or when a generic function is passed as an argument to an overloaded function without providing an explicit type instantiation" (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/Fcn.java:58-66` at `db352c1776`). So `app(half, v)`, for `half[\nat n\](x: Vector[\RR64,n\]): Vector[\RR64,n\]` and `app(f: Vector[\RR64,3\] -> Vector[\RR64,3\], v: Vector[\RR64,3\])`, stopped with 'Unification error: ... got arg half[\nat n\](...) ... of type null', and only `app(half[\3\], v)` ran. The tree now runs `app(half, v)`: the parameter receives `half` at 3, the instance that a direct call with a `Vector[\RR64,3\]` runs. A parameter of a function or a constructor, a local variable declared with an arrow type and a variable of arrow type at an assignment receive so. A generic callee's static parameters are fixed by its other arguments first, so `rows(half, m)` runs for `rows[\nat r, nat c\](f: Vector[\RR64,c\] -> Vector[\RR64,c\], m: Matrix[\RR64,r,c\])`. Where the receiving type leaves a static parameter of the function open, and at `Any`, a type parameter or an untyped variable, the value stays generic, and each application infers its static arguments from its arguments' run-time types. An overloaded name with a generic declaration stays the whole overloaded function at an arrow-typed place. Two cases still depart: an immutable top-level variable of arrow type keeps the generic value, so a call at another size runs; and a generic function passed at `f: T -> T` where a value fixes the callee's `T` by its run-time type is refused; write the static argument there, `appT(half[\3\], v)`. Tests: `ProjectFortress/tests/GenericFunctionAsValueWalk.fss`, `GenericFunctionRowLiftWalk.fss`, `GenericFunctionAssignedWalk.fss`; the two departures, `XXXGenericFunctionTopLevelVariableWalk.fss` and `XXXGenericFunctionAtTypeParameterWalk.fss`. The reason: the specification makes a function a value and says of a reference to a polymorphic function that "most identifier references do not include them.; the static arguments are statically inferred from the context of the function call" (`Specification/basic/expressions/var-ref.tex:35-40`); walk has no static types, so the context it can read is the type of the place that receives the value, and the call.

**Provenance.** The item: ledger row 156, and the model's four vector functions passed to the row lift (`explorations/reviews/c4-fortress-way-2026-11-15.md`, section 1.2). The default followed: fork F1 of `explorations/coordinator/CLIMB-BATCH-32.md`, "Forks the batch takes", within P-48 and P-12; P-87 keeps the model's lines. The batch: climb batch 32, rung F.

### Rung B, `rung-toplevel-array-literal`: an array literal at the top level under walk

**The change.** The team's walk bound a top-level variable declared with an array type to the literal's paste, a tuple, and stopped: `shp: ZZ32[3] = [27 16 27]` gave 'Type mismatch binding (27,16,27): (ZZ32,ZZ32,ZZ32) (type (ZZ32,ZZ32,ZZ32)) to shp (type Array1[\ZZ32,0,3\])'; only a declaration in a block built the array (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/LHSEvaluator.java:170-207`, the block's binding; `ProjectFortress/src/com/sun/fortress/interpreter/evaluator/BuildEnvironments.java:788-803`, the top-level check, which built nothing). The tree now builds a top-level literal with a declared array type into the library array of that type, for an immutable and a `var` variable, with numerals, names, expressions, strings or pasted arrays as elements, and a field of an object declared so (`ProjectFortress/tests/ObjectFieldArrayLiteral.fss`); a reader above the declaration sees the array; a literal of another size than its declared type, or with an element that is not of the element type, is refused at load. Test: `ProjectFortress/tests/TopLevelArrayLiteral.fss`, with `TopLevelArrayLiteralSize` and `TopLevelArrayLiteralElement` for the refusals. The reason: the specification gives an array expression one type wherever it stands, `Arrayk[\T, 0, n0, ...\]` (`Specification/basic/expressions/aggregate.tex`, "Array Expressions"), and a top-level declaration `id : Type = expr` the same meaning as a local one (`Specification/basic/variables.tex`, "Top-Level Variable Declarations"). Still so: a top-level literal without a declared type is bound as its paste and fails at its first use; write the type. A literal in a block of another size than its declared type is not refused; a `var` bound to a literal in a block is immutable; a literal assigned to a variable is not built.

**Provenance.** Ledger row 142; the batch's fork B1, "A typed array literal at the top level is the array that the same literal is in a function body", built within P-87 (no model line changes) and P-173 (a numeral element converts at the element type); climb batch 32, rung B.

### Rung D, `rung-tuple-binding`: a top-level tuple binding on the compiled path

**The change.** The team's code generator refuses a top-level declaration of several names: `forVarDeclPrePass` throws 'VarDecl … tupled lhs not handled.' where the left side has more than one name (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:6475-6477` at `db352c1776`), and the team's checker, in its case for a tuple expression of as many elements, rebuilds the right side without a type, so that each name has none (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Decls.scala:270-272` at `db352c1776`). The tree now compiles the form: each name is a top-level variable of its declared type or its element's type, a numeral element at its default, and the right side is evaluated once, when the first of its names is read (`ProjectFortress/compiler_tests/TopLevelTupleBindingCompiled.test`). A use of a name at another type is refused (`ProjectFortress/compiler_tests/XXXTopLevelTupleBindingType.test`, whose prefix is the harness's mark of a compile that must fail). A name's declared type is checked against its element also where other names of the binding declare none and the right side is a call (`ProjectFortress/compiler_tests/TopLevelTupleBindingMixedTypes.test`, `XXXTopLevelTupleBindingMixedRefused.test`): the team's checker leaves such a name unchecked, as it still does in a local tuple binding (`ProjectFortress/compiler_tests/XXXLocalTupleBindingMixedTypes.test`). The reason: the specification gives the form for every top-level declaration, "All forms can be used with tuple notation to declare multiple variables together" (`Specification/basic/variables.tex:99`), and a variable's value "is computed to be the value of the initializer expression" (`:63`); walk's own desugaring states the same design, "Introduce a temporary, then initialize elements piece-by-piece" (`ProjectFortress/src/com/sun/fortress/interpreter/rewrite/DesugarerVisitor.java:858-859`). Walk departs from it: its right side runs once for each name and once more (`ProjectFortress/tests/XXXTopLevelTupleBindingOnceWalk.fss`).

**Provenance.** The item: rows 988 and 474 of the gap ledger, and the model's hyperparameter lines, which P-9 keeps as tuple bindings. The default it follows: fork D1 of CLIMB-BATCH-32.md, "Each name of a tuple binding is a top-level variable of its element's type; the right side is evaluated once", and fork D2, the code generator's half for a top-level binding only; P-173 for a numeral element's default. The batch: climb batch 32, rung D.
