## 2. Where the fix belongs, and what it is not

The fix belongs in `ProjectFortress/src/com/sun/fortress/runtimeSystem/Transaction.java`: the defect is the eager argument of a disabled debug call, the file already carries the flag and the method, and the idiom is the sibling file's. It does not belong in `VarCodeGen`'s emitted sequences, which the skeptic traced by hand and which are right; nor in the payload type, which is right.

It is not a repair of the underlying cycle. `FValue.toString` → `Object.asString` → `jAsString` → `stringOps.asString` → `a.toString()` is a pre-existing defect of the compiled world's runtime, reachable by any stringification of an object without its own `asString`. The specification's prose chapters are silent on what such an object's `asString` is: `grep -rn asString Specification/basic Specification/basic-lib` finds nothing. Choosing a rendering is a language decision — the candidates are the team's own commented-out line at `stringOps.java:39` (the class name), a default `asString` in `CompilerBuiltin.fss:338` that does not go through `jAsString`, or a `FValue.toString` that does not call `asString` — and it is not this rung's. It becomes a verified ledger row with the candidates named, and it reaches Pavol as a decision under a silent specification that this batch did not take.

Four decisions I take here, each with the alternative it displaces.

**All fourteen sites, not nine.** The nine are the crash; the five others build a string of an int on every abort, begin, validate and failed commit. One rule for the file — every `debug(` call in `Transaction.java` is guarded — is verified with one `grep` and leaves no later reader to work out which sites are safe. Rejected: the nine alone, the narrowest diff.

**The same guard on `BaseTask.java`'s eight remaining eager sites** (`:183, :186, :193, :195, :207, :234, :242, :258`). None can crash, per the check above, but `getCurrentTransaction` at `:234` builds `"getCurrentTransaction: ftr = " + ftr` — a `Thread.toString` through `StringBuilder`, the mechanism row 302 measured at about 34 % of a 156× gap — and the rung's `pushValue`/`assignValue` now call it on every transactional read and write of a top-level variable, as `LocalMutableVar` always has. Rung 0 left `:234` for a rung that would touch it; this is that rung, and the batch is gated once after the merge, so the extension costs no second gate. Rejected: leave `BaseTask.java` untouched and append the cost to row 302. This is a decision and it goes to Pavol.

**`MutableFValue.toString` stays as it is.** Rendering the payload is what a debug rendering is for; once every site is guarded it is reached only with `debug` set, and the ledger row for the cycle records that turning `debug` on with a variable of a user type that has no `asString` recurses. Rejected: an identity rendering, which would make the debug output useless for the one thing it exists to show.

**The case is gated, not only probed.** A new `compiler_tests` program with a top-level mutable variable and a local mutable variable of a user-defined object type, each written inside `atomic` and read after. It fails on the landed tree before the guard (`StackOverflowError`, no `PASS`) and passes after; its top-level half also passes on `49ee5e91`, which is the point — the recorded failure for this test is the landed tree, the state it guards against, and its local half fails on `49ee5e91` too (`SK20LocalTrait`). Rejected: leave `SK25` as a probe, which no gate runs.
