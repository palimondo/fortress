## Revival change

**The change.**
- The team's sources: the specification's export rule asks a satisfying trait or object declaration for a satisfying declaration only "for each field declaration and non-abstract method declaration in the exported declaration" (`Specification-1.0-frozen/basic/components/source-code.tex:380-385`), so it asks no declaration of an abstract method; the interpreter's library, written for walk, left 12 such methods out of its component's traits (`Library/FortressLibrary.fss` at `c3c22817c`: `String`'s `depth`, `isBalanced`, `verify`, `rangeContains`, `splitWithOffsets`, `split`, `balanced`; `Range`'s `isEmpty`; `ReadableArray`'s `opr[_:TrivialOpenRange]`; `ActualReduction`'s `empty` and `join`; `AnyMaybe`'s `holds`); walk compares no component with its apis (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/BuildApiEnvironment.java:48-136`) and runs such a component. The compiler's library and the team's compiled check did the other way: the prelude restates each abstract api method bodyless (`Library/CompilerLibrary.fsi:110-120`, `Library/CompilerLibrary.fss:301-312`), and the team's `equalListMembers` compared every api member (`edb516dba`, 2009; `5a68404fd:ProjectFortress/src/com/sun/fortress/scala_src/typechecker/ExportChecker.scala:767`, 2012).
- What the tree does now: a component's trait or object declares each method its api writes `abstract`, at the api's header, with a body or without one; the compiled export check refuses one that leaves it out ('missing members of the trait/object in the component', `ProjectFortress/compiler_tests/XXXExportAbstractMemberAbsent`) or declares it at another header ('different method f', `XXXExportAbstractMemberOtherHeader`), and takes a bodyless declaration (`ExportAbstractMemberBodyless`, whose client's call runs the object's body) or one with a body (`ExportAbstractMemberDefined`). The library writes the 12 bodyless, with no `abstract` (`Library/FortressLibrary.fss:1614`, `:2177`, `:3250-3251`, `:4013`, `:4354`, `:4356`, `:4360`, `:4395-4398`). The specification says so (`Specification/basic/components/source-code.tex:381-399`). Walk still runs a component that leaves one out.
- The reason: a compiled call through a trait is an `invokeinterface` on the component's trait interface, which declares only what the component's trait declares, so the call dies where the component leaves the method out, also where every object defines it: on the old code, `compile WalkAbsentApi.fss` rc 0 and `run WalkAbsent` 'java.lang.NoSuchMethodError: 'com.sun.fortress.compiler.runtimeValues.FZZ32 WalkAbsentApi$T.f()''; on the new, the compile is refused (`compile-ladder/rung-abstract-declared/REPORT.md`, section 7).
- The skill's sentences this makes false: `references/library.md:44`, "It requires no component member for an api member written `abstract`." (the rest of the item, declare each such member at the api's header, now also what the check asks); `references/compiler.md:74`, the second trap of the compiled path, "The export check passes the exporting component." (the check now refuses such a component).
