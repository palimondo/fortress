- P-7 **The goal is to finish what the designers intended, measured by one program, microGPT, compiled to JVM bytecode and running fast.** What the designers intended is judged by the specification in `Specification/`: the team's Working Draft of February 2011, as the revival revises it, with the Types chapter of the team's 2012 restart cited beside it (P-25). The revival revises the specification to reconcile contradictions: where the team's later work, in the compiler or in the papers on types, contradicts the original text, the text is updated to follow that work (P-26: the type group's later word wins). The language is not redesigned. The specification is a living document that states each change that the revival makes (P-95 says how a change is recorded). A pure-Java microGPT is the baseline that compiled microGPT is measured against: the optimal result, the one to aim at.
- P-27 **Whoever extends the library follows the library's own practice.** What microGPT invented goes into the standard library, in the library's own style. Whoever extends the library first studies how it does the same kind of thing, and follows that pattern; exclusion, for one, is all over it. He had to find the diagonal's override himself (P-88) because that study was skipped. No fix is designed from the specification alone or from a workaround on the user's side. This rule governs how the library is extended. It does not choose between two of the team's designs of the language, such as the self type as the interpreter's library and the compiler's prelude write it: the team's later word, dated against the texts, decides between them (P-26).
- P-146 **In a self-typed trait, the compiled checker types `self` in the method bodies as also being the implementing type.** A self-typed trait is a trait `C[\X\]` whose parameter `X` extends `C[\X\]`, such as `Integral[\I extends Integral[\I\]\]`. In its method bodies, `self` has the type `C[\X\] & X`. The method signatures keep the plain trait type, because the proofs of the POPL 2019 paper on multiple dispatch (Park, Hong, Steele and Ryu) assume that no declared type holds a type parameter inside an intersection. Only the overloading check's exclusion test reads `self` in a signature as `C[\X\] & X` (P-157). The checker refuses a type that extends such a trait at another type, since an extender must be a subtype of the static argument that it gives: `object Bad extends Integral[\ZZ32\]` is refused, because `Bad` is not a `ZZ32`. Scala has the same rule for self types. The library's text gains no self type and no `comprises` clause, and walk is unchanged. The rule accepts every self-typed method body of the library except `Integral`'s `numerator`, which each integer type declares instead. Why: the team's later texts point, if weakly, toward the rule, and peer languages share it. The compiler's prelude writes the self type as a `comprises T` clause instead, and that form does not bind the library: Naden's write-up on the Return Type Rule (P-26 names it), later than the team's last edits of that clause, puts the self type in bounds only, the form `X extends C[\X\]` that the library writes. F-225 states the rule as built and holds the dates.
- P-153 **The integer power splits on the base: an integer base gives an integer or raises an error, and a float or rational base gives the fraction.** Each integer type's `^` returns its own type at every exponent. At a negative exponent, the bases 1 and -1 give their exact power, a base of 0 raises `DivisionByZero`, and any other base raises `IntegerOverflow`. A program that wants a fraction writes a float or rational base, as in `2.0^(-1)`. Why: the Working Draft's power, which gives a rational at a signed exponent, was never built on either path. The only power with an integer result type that the team built is the compiler's prelude's, which gives `ZZ32`, `NN32` and `NN64` each a power of its own type at every exponent. Overloads choose by type, and no type tells a negative exponent from a non-negative one, since a signed integer or a numeral can be either. So the split is on the base, and the sign of the exponent is tested at run time, as the library tests a value's sign everywhere (P-80, run-time sign tests in place of sign-refined types). Row 441: the same rule on the compiled path, whose own powers give 0 at a negative exponent and a raw Java exception at a base of 0, and overflow silently or with a raw Java exception (row 523).
- P-154 **A list is ordered only where its element type is totally ordered.** The library's `List` extends its lexicographic order only where its element type extends `StandardTotalOrder` (conditional extension, P-151). Floats and `QQ` are only partially ordered, since NaN, and `QQ`'s 0/0, compare with nothing. So on the compiled checker a list of floats or of `QQ` has no order: no `<`, `CMP` or the other comparisons, though its `=` stays. A pair of floats stays ordered: the curator accepted that mismatch as a cost of the list rule. The tuples' own rule is not decided here. No lexicographic trait over partially ordered elements is added now: the team never wrote one, and the case touches neither the distance to the switch-over nor microGPT. Why: the two lexicographic traits of an unfinished library draft of the team's (`Library/incomplete/advanced/Fortress.PartialTotalOrders.fss:117-140`) both bound the element by a total order, and conditional extension is a `where` form that the team wrote (P-151). The draft is not shown to be later than the specification's sentence that lets a list's order be partial where its elements' order is, so it does not count as the team's later word (P-26). Row 774: walk's half, since walk still gives every list an order.
- P-12 **After the switch-over, walk runs the compiled type checker on its programs, and then uses the static coercions that the checker inserts.** The curator wants the checker usable on the programs that walk runs. Today `fortress typecheck` checks a program only against the compiler's prelude, so it is no check of walk's programs (F-9 holds this fact). Walk is not changed for this before the switch-over. After it, walk runs the checker on its programs and so gains their static types. Walk then uses the static coercions that the checker inserts, in place of its choice on the run-time value (P-59, walk's choice of coercions until the switch-over). The step has three parts, and its size is unmeasured. First, walk must run with the Scala checker on; today it runs with it off. Second, walk must evaluate the `CoercionInvocation` nodes that the checker inserts, for which it has no case today (F-9 holds both facts). Third, the components that walk's programs import must be cleared of the checker's errors, each before this step or before the first program that needs it (F-290 counts them).
- P-17 **Unboxed doubles and arrays of unboxed doubles are required: without them the revival misses its point.** Why: a language meant for high performance cannot box its numbers. The specification states the same intent: its chapter on objects lets an implementation freely copy value objects, among them floating-point numbers, and its chapter on memory sequences makes a `LinearSequence` of a value type a sequence of "unboxed" values. Today the code generator boxes every number: an `RR64` value is an object of the class `FRR64`. In Java models of microGPT's three array kernels, the dot product, the matrix product and the row lift, boxing is the main cost (F-11 holds the measurement). How arrays store doubles, as `double[]`, is P-84's decision.
