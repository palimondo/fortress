## 1. The refusal: strided slices of a string

The skeptic is right.

- The rung replaced `r1.lower`, `r1.upper` with `r1.left.get`, `r1.right.get + 1` in `FlatString.uncheckedSubstring` (`Library/FlatString.fss:64`), and `range.lower`, `range.size`, `seq(range)` with `range.left.get`, `range.extent.get`, `seq(range.left.get # range.extent.get)` in SubString (`Library/String.fss:344`, `:376`, `:383`, `:400`, `:407`, `:429`, `:455`, `:461`, `:472`, `:476`, `:479`, `:491`). - String's indexing passes the strided range on unchanged: `opr[r0]` narrows and calls `uncheckedSubstring` (`Library/FortressLibrary.fss:4170-4173`). Only EmptyString overrides it (`Library/String.fss:300`). So `"abcdef"[0:4:2]` answers `"abcde"`, and `cs[18:24:2]` builds a SubString over a strided range (`Library/String.fss:153`) whose size, flat form and written form disagree. The skeptic's runs are quoted in `SKEPTIC.md` section 1.
- The specification settles the answer. `Specification/basic/expressions/ranges.tex`, section "Ranges" (`:68-73`), makes `a:b:c` the set `{a, a+c, ..., a + floor((b-a)/c) c}`. The ranges are there for indexing (`:37-40`), and implicit strided ranges are given meaning as subscripts (`:115-127`). The library's `Indexed` contract makes indexing by a range the elements at the narrowed range's indices (`Library/FortressLibrary.fsi:1286-1296`), and String is `ZeroIndexed[\Char\]` (`:2398`). So `"abcdef"[0:4:2]` is `"ace"`. This is rule 4's second outcome against the head's walk: the defect is the rung's own, and a loud failure has become a quiet wrong value.
- The library's own way is the precedent the rung itself cited and cut short. `List`'s `opr[n:Range[\ZZ32\]]` narrows, tests `r.stride = 1` before reading `r.left.get` and `|r|`, and otherwise selects element by element (`Library/List.fss:145-151`, the test at `:147`). The arrays read `r'.left.get` and pass `r'.stride` on (`Library/FortressLibrary.fss:2291-2296`, stride at `:2295`; `:2514-2520`, extent at `:2516`, stride at `:2518`). REPORT.md section 4's sentence "so the values are the same" holds for compact ranges only.

**Where the fix goes (a decision, reported).** String's `opr[r0]` (`Library/FortressLibrary.fss:4170-4173`, the strings section, rung S's) takes List's device: `if r1.stride = 1 then self.uncheckedSubstring(r1) else BIG || [i <- r1] self.get(i) end`. `BIG ||` over characters is how the library already builds a string (`reverse`, `Library/FortressLibrary.fss:4283`, which the after list shows typed), and `get` skips the bounds check that `narrowToRange` has just made. The alternatives:

- A stride guard in each `uncheckedSubstring` (`Library/FlatString.fss:55`, `Library/String.fss:141`, `:475`). That is three edits to the team's representation methods for a path no caller takes: `uncheckedSubstring` is called only at `Library/FortressLibrary.fss:4172` and inside `String.fss` and `FlatString.fss`, each time with a range built by `#`, `∩`, `≫` or `≪` from compact ranges. Its api comment puts narrowing and bounds checking in `opr[ ]` and calls it a "friends" interface (`Library/FortressLibrary.fsi:2423-2427`). A SubString's range is compact and nonempty by the library's construction, as its `isEmpty` getter already assumes (`Library/String.fss:346`).
- Keeping the strided case loud, with an XXX test asserting `"ace"`. No library type refuses strided indexing, and `List` and the arrays answer it, so this would leave String short of what `Indexed` promises.

Either answer is a walk value change from the base, which raised (`Cannot find definition for method upper given receiver StridedFullParScalarRange`, `Library/FlatString.fss:64`).
