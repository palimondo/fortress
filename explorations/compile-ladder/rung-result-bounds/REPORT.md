## 2. Where the fix belongs

The decision places the fix in the library. What each path does with the three parameters, read and then measured:

- **The checker.** Under walk's setting and under `any`, the three parameters are bounded by `Any`. Inference then produces the constraint `T <: Any`, which reduces to `True`, and the solver returns the empty substitution for it (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/Formula.scala:493`), so `T` stays open and the call is refused "without context". With a bound other than `Any` the constraint does not reduce to `True`; the solver binds each variable to the join of its lower bounds and one with none to `BOTTOM` (`Formula.scala:524-527`; `ProjectFortress/src/com/sun/fortress/scala_src/useful/STypesUtil.scala:1937-1940`, `killIvars`). This is what the compile path's own setting does to every unbounded parameter (row 412), and why N1 and N2 do not appear under it (FACTS.md, "Static arguments are inferred from the arguments alone, on both paths, and never through a coercion"). The checker's own fix, keeping the expected type at a call written `f(x)` (row 455), binds `Bottom` the same way and is batch N's, not this rung's (the same POSITIONS entry).
- **Walk, for the natives.** Walk never calls `builtinPrimitive`. It matches a native's body by its text, a tight juxtaposition of the name `builtinPrimitive` with a string literal (`ProjectFortress/src/com/sun/fortress/interpreter/glue/NativeApp.java:163-190`), and substitutes the named glue class. The declaration of `builtinPrimitive`, bound included, is never read there.
- **Walk, for `fail` and the comprehension.** Walk installs a written bound as an upper bound before it unifies the arguments (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/EvaluatorBase.java:94-110`, `meetPut` at `:105`) and binds a parameter nothing constrains to `BottomType` (`:243-246`). A result-only parameter meets no argument, so the bound meets no value's type. Measured (`explorations/compile-ladder/rung-result-bounds/probes/walkbound/WalkBound.walk.txt`): a written bound `Object` on a result-only parameter changes nothing under walk, whether the static argument is written at a tuple or an arrow or left unwritten. The same bound on a parameter an argument fixes refuses a tuple, `()` or an arrow argument with an `InterpreterBug`, "Meet((Int,Int), Object) not a singleton" (row 471). None of the three parameters is of that kind.
- **Row 421** is the library's own slip: the two default bodies return one `T` (`Library/FortressLibrary.fss:260-261`) and the declarations said `(T,T)`. Walk does not check a declared return type, so only the declarations were wrong.

So the fix belongs where the decision puts it, in the ten declaration lines. The map's row for type parameters (`explorations/coordinator/map/spec-to-implementation.md:232`) names `STypesUtil.scala` and `FTypeGeneric.java` as the two paths' sites; the reading above opened the checker's and walk's inference, and neither is edited.

## 4. What the specification settles

- **The bound.** The specification's current text makes `Object` the implicit bound (`Specification/basic/trait-parameters.tex:49-50`), which Pavol's answer to Q1 replaces by `Any` and rung S of batch 7b will revise. Its next sentence lists tuple types among what a type parameter is instantiated with (`:53-54`), and `Any`'s immediate subtypes are the tuple types, the arrow types, `()` and `Object` (`Specification/basic/types-vals-vars.tex:135-136`). So a written `Object` excludes a tuple, an arrow and `()` as the parameter's instance.
- **What that costs each of the three.** `builtinPrimitive`'s instance is its native's declared return type, which the checker now solves as `Bottom` whatever it is (run BP added no error, and neither did this rung). `fail`'s body is a `throw`, of type `BottomType`, a subtype of every type (`types-vals-vars.tex:508-513`), so `Bottom` is the precise instance and a written tuple is never needed. The comprehension's `T` is the element type of the list it builds, and a list's elements may be tuples, `()` or functions; the specification's own set comprehension is declared with an unbounded `T` (`Specification/basic/expressions/comprehensions.tex:57-60`). Here the bound restricts what the specification allows (section 12).
- **A written static argument.** Rule T-Invk requires `T <: [T/X]N` for the static arguments of an invocation (`Specification/appendices/calculi/basic/static.tex:190-201`, the premise at `:195`). The prose chapter on a call's static arguments says they may be written and are otherwise "statically inferred from the context of the function call", and nothing on bounds (`Specification/basic/expressions/var-ref.tex:35-40`); the calculus is the specification's statement of the check.
- **Row 421.** `MAX` returns whichever argument is larger and `MIN` whichever is smaller; equal arguments give that value (`Specification/basic-lib/basic-integers.tex:599-602`, stated for `ZZ` and meant, by the library's own comment, for every `StandardMinMax`, `Library/FortressLibrary.fsi:198-203`). One argument, not a pair: the specification settles the row, as the row says.
- **`fail`.** The specification's `fail` is a test helper, `test fail(message: String): ()` (`Specification/basic-lib/tests.tex:46-51`; `Specification/basic/tests.tex:171-172`). The library's `fail[\T\](s:String):T` is not that declaration and was not before; the bound neither brings it closer nor takes it further.
