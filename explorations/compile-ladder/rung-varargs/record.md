## Revival change

**The change.** The team's code generator refused every function and method with a varargs parameter and every call of one: `NamingCzar` threw 'Can't compile VarArgs yet' for a domain with a varargs part (`ProjectFortress/src/com/sun/fortress/compiler/NamingCzar.java:1307`, `:1317`, `:1457`, `:1568` before this change), and `OverloadSet.getSignature` left "some fiddliness with varargs that has to be sorted out" (`OverloadSet.java:615`). The tree now compiles one against the interpreter's library: the arguments that no plain parameter takes are one `ImmutableArray[\T, ZZ32\]`, which `__immutableFactory1` makes and the caller fills in order, at the call or, where another declaration of the name takes as many arguments, in the dispatch method's branch for the varargs declaration (`one_library_tests/OneLibraryVarargsCount.test`, `OneLibraryVarargsOverloaded.test`). Against the compiler's own library the declaration stays refused, the message naming the missing type (`compiler_tests/XXXVarargsMethodCodeGeneration.test`). The reason: the specification binds the parameter to those arguments in order (`Specification/basic/functions.tex`, "Function Applications"), its revision gives the type (`functions.tex`, the `revival-varargs` box), the checker binds the parameter at that type (`Types.java:143-146`), and walk builds the same value (`interpreter/evaluator/values/NonPrimitive.java:224-251`); a dispatch method reads a varargs declaration by the expansion rule (`Specification/basic/overloading.tex`, "Applicability for Functionals with Varargs and Keyword Parameters").
