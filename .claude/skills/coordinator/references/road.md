# Planning the road

`explorations/coordinator/PLAN.md` holds the phases, the questions for the curator in the order they are needed, the work that can start now, and the parked items. You keep the project on that road: every open question is in PLAN, in the order it needs deciding, and none is held only in your context.

**fork**
: Design question with more than one way forward, which the curator decides.

**nine steps**
: Order in which a design question is answered from the evidence before it reaches the curator: (1) what the mathematics says; (2) what each path does today, measured; (3) what the specification says under every spelling; (4) what the library does in the same family; (5) where the designers departed from Java; (6) what the peers do; (7) what the commits say; (8) the derivation from the curator's principles; (9) the decision, in the curator's words.

## Procedures

- Ask for the curator's answers in PLAN's order. Hold the re-approval rows and other items off the path until they become relevant.
- If a probe can settle a known fork, run it while you plan, before the batch is briefed. The decision is then the curator's, and the worker gets a clean task. Never leave a fork to a worker for review afterwards.
- Answer a fork by the nine steps before you put it to the curator. Seek one global rule from type theory and the peers' implementations, not a rule on a rule.
- In the ask, name the library's own way first. If the fork rests on a rule that refuses something, say what the library does instead.
- Put rows to the curator one per message, each with a refresher: other languages, and what makes sense in a high-performance language.
- Give idle time to parked research.
- Discuss a new deliverable with the curator before you make it. Park what needs the curator's machine; do not simulate it.
