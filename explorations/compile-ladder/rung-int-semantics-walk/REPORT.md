## 4. What changed, and why each shape

### 4.1 The catchable throw, measured first

No interpreter native raised a Fortress exception before this rung (`grep -rn "FortressError\|getRootValue" ProjectFortress/src/com/sun/fortress/interpreter/glue` finds only `Reflect.java:65-72`, which looks up constructors), and the brief asked for the route to be measured before the check could stay in Java. The path: a native method is applied by `MethodClosure.applyMethod` (`interpreter/evaluator/values/MethodClosure.java:85-86`) with no `catch`, so a `FortressError` thrown there reaches `Evaluator.forTry` (`interpreter/evaluator/Evaluator.java:1323-1324`) unchanged, which hands the wrapped object to `handleException` to be matched by type. `Int.overflow()` (`glue/prim/Int.java:256-259`) builds it as `Evaluator.java:224-226` builds the try-atomic failure: a root value of the library, from `Driver.getFortressLibrary()` (whose own comment, `interpreter/Driver.java:61`, reads "Native code sometimes needs access to the library component wrapper"), wrapped with the one-argument `FortressError(FObject)` (`exceptions/FortressError.java:31-34`), which had no caller until now, since a native has no location or environment to give. **Measured: it arrives catchable.** Every `overflows(...)` assertion of the test passes, and its helper's only clause is `IntegerOverflow => true` (`IntSemanticsRungI.fss:6-12`), so the fallback of a Fortress-body `throw IntegerOverflow` was not needed. The interpreter's general mapping of other Java exceptions (`FunctionClosure.java:188-196` wraps any other `RuntimeException` of a native function in a `ProgramError`) is untouched, so the stop the brief names does not arise.

**Decision: the name is a `WellKnownNames` constant** (`compiler/WellKnownNames.java:86`, `integerOverflowException = "IntegerOverflow"`), beside the six exception names already there (`:80-85`), as `StringPrim.java:130-133` looks up `WellKnownNames.varargsFactoryName`. The alternative, a string literal in `Int.java`, would have kept the edit inside the manifest's file list; it was rejected because the interpreter's shape for "a library name the Java side looks up" is the constant at every site (five in `Evaluator.java`, one in `StringPrim.java`). The cost is one more 2012-tree file, on the `historical:` line.

### 4.2 GCD and LCM

`Int.gcd`'s zero case returned its other argument unnormalized (base `Int.java:253`); it now returns the magnitude (`Int.java:292`), and the function's existing convention that `Long.MIN_VALUE` stands for `2^63` (it negates and then shifts with `>>>`) is kept. `Int$Gcd` throws when the magnitude exceeds `Integer.MAX_VALUE` (`Int.java:134-140`), `Long$Gcd` when it is negative, i.e. `2^63` (`Long.java:148-154`). `LCM` on both widths goes through one new helper, `Int.lcm` (`Int.java:274-284`), which follows the compiled body (`CompilerBuiltin.fss:616-619`, `if (self = 0) OR (other = 0) then 0 else (|self| DIV (self GCD other)) DOT |other|`): zero first, then `|u / g| * |v|` by `Math.multiplyExact` (Java 8, and the JVM's own spelling of the check, as the batch record notes at `CLIMB-BATCH-3.5.md:35`), with the two operands whose magnitude has no `long` tested before `Math.abs`. `Int$Lcm` then range-checks to `int` (`Int.java:142-148`).

**Decision: `MIN GCD MIN` and `MIN LCM MIN` throw too.** The brief's list stops at `MIN GCD 0`, `0 GCD MIN`, `MIN LCM ±1` and `5 LCM MIN`; `MIN GCD MIN` (`2^31`, resp. `2^63`) and `MIN LCM MIN` are the same unrepresentable results reached with both operands at the minimum, measured wrapping on the base tree (`probes/IntSemProbe-before.txt:86`, `:89`, `:106`, `:109`), and the rule cannot be applied to half of them. `MIN LCM 0` is `0` (spec `:529`) and not a throw, although `MIN GCD 0` throws: the zero test comes before the divisor is computed, as in the compiled body.

**The specification's passage, read whole.** `basic-integers.tex:524-525` and `:528-529` say, besides "The result is always nonnegative", that "If either argment is 0" (for `LCM`, 1) "the result equals the other argument", which read alone gives `0 GCD -4 = -4` and `1 LCM -5 = -5`, against the first sentence. The chapter's source reconciles them: its declarations in Fortress text, kept as LaTeX comments above the rendered ones, are `opr GCD(self, other: ZZ): NN` and `opr LCM(self, other: ZZ): NN` (`:518-519`), a return type of ℕ, under which "the other argument" can only mean its magnitude. The rung follows the nonnegative reading, which is also Pavol's decision for row 334 (`CLIMB-BATCH-3.5.md:19`); the test asserts it at `IntSemanticsRungI.fss:105`, `:107`, `:124`, `:126` and `:146`.

**The unbounded `ZZ`'s `LCM` (second repair round, the skeptic's finding 2).** `BigNum$Lcm` (`BigNum.java:176-192`), bound as `ZZ`'s `LCM` at `Library/FortressLibrary.fss:871-872`, computed `u.divide(g).multiply(v)` with `g = u.gcd(v)` on the signed operands, so the result carried a sign and `0 LCM 0` divided by `g = 0`: `1 LCM -5` was `-5`, `-4 LCM 6` was `-12`, and `0 LCM 0` ended the run with `ArithmeticException: BigInteger divide by zero` (`probes/skeptic/SkBigLcm.walk.txt:1-4`, `:8-9`). The specification declares `GCD` and `LCM` on ℤ itself (`basic-integers.tex:520-521`), so the clause covers it. It now returns zero when either argument is zero and otherwise takes both magnitudes (`BigNum.java:178-180`) before the existing `gcd`, smaller-first swap and divide-multiply, which are unchanged; the shape is the compiled body's (`CompilerBuiltin.fss:616-619`), as `Int.lcm`'s is. The swap compared signed values before, and is meaningful only on the magnitudes it now gets. `BigInteger` has no overflow to raise, so nothing here touches how Java exceptions are mapped. `BigNum$Gcd` (`BigNum.java:170-174`) is `u.gcd(v)`, which the JVM defines nonnegative, and the skeptic's capture agrees (`probes/skeptic/SkBigLcm.walk.txt:6`). Home 1: `IntSemanticsRungI.fss:146-148` (`1 LCM -5 = 5`, `-4 LCM 6 = 12`, `0 LCM 0 = 0`), red before (`test-before-biglcm.txt`) and green after (`test-after.txt`); the skeptic's own probe now gives every wanted answer (`probes/SkBigLcm-after.txt`, no `DIFF`, `END`, exit 0). **Decision (the judge's, `JUDGE.md`, second ruling, section 2): repaired here**, rather than given an `XXX` file with row 334 left open for ℤ; the fix is four lines in a file the rung edits, and neither of the rung's stops applies.

`Int.rc` is untouched, as the brief requires (row 347 stays open). Its callers after this rung are `Int$Choose` (`Int.java:152`) and `Int$Pow` (`Int.java:225`); see section 9 on the brief's "two exponentiation callers".

### 4.3 The fixed widths, and how the count is read

Each of the four shift pairs gains one line before the existing one; `Int$LShift` (`Int.java:180-185`), for example, is `if (v < 0) return (v > -32) ? (u >> (int) -v) : (u >> 31);` followed by the original `((v & ~31) == 0) ? (u << (int) v) : 0`. The comparison with `-32` (`-64`) precedes the negation, so `Long.MIN_VALUE` is never negated. `NN32` and `NN64` shift right logically and saturate to `0` both ways (`NN32.java:183-195`, `UnsignedLong.java:184-196`).

**The `NN64` question, established.** `UnsignedLong$LShift` took its count through `UU2U`, whose `applyMethod` reads `y.getNN64()` (base `UnsignedLong.java:88-94`). Through that `long`, a negative count and a large unsigned one cannot be told apart: `FInt.getNN64` and `FLong.getNN64` return the signed value unchanged (`evaluator/values/FInt.java:36-39`, `FLong.java:37-40`), so a `ZZ32` count of `-1` and an `NN64` count of `2^64-1` both arrive as `-1L`, and `Long.MIN_VALUE` as a `ZZ64` count and `2^63` as an `NN64` count both arrive as `Long.MIN_VALUE`. **They can be told apart one step earlier, by the class of the count's value**, which is `FNN64` for an `NN64`. The same ambiguity sat in `Long$…` (`y.getLong()` of an `FNN64` is its raw bits) and in `BigNum`'s `ZL2Z`; it was harmless while every negative count saturated, and this rung's negative-count rule would have made it wrong (`-3 LSHIFT` an `NN64` count of `2^63` would have become a right shift, `-1` instead of `0`). So the count is read once, by `Int.shiftCount(FValue)` (`Int.java:261-272`): an `FNN64` of `2^63` or more as `Long.MAX_VALUE` (a count beyond every width), an `FBigNum` exactly when it fits a `long` and clamped to `Long.MIN_VALUE`/`Long.MAX_VALUE` when it does not (exact for every width, and for `ZZ`, whose values the JVM limits to `2^31-1` bits), anything else by `getLong()`. The guards are asserted at `IntSemanticsRungI.fss:73-76`.

Precedent for the shape: each natives file declares small abstract classes named for their Java types, with a shift-only one where the count's reading differs: `ZL2Z` in `Int.java:90-96` and `BigNum.java:102-108`, `NL2N` in `NN32.java:95-101`, each extended by the two shifts alone (`grep -n "extends ZL2Z\|extends NL2N"` finds only the shifts, plus the dormant `ZZ32.java`). Their `applyMethod` now calls `shiftCount`. `Long.java` and `UnsignedLong.java` had only the shared `LL2L`/`UU2U`, so each gains a shift-only twin, `LC2L` (`Long.java:104-110`) and `UC2U` (`UnsignedLong.java:96-102`), "C" for the count; the alternative, extending `NativeMeth1` directly as the `Pow` classes do (`Int.java:218-228`), was rejected to keep the four pairs one shape.

### 4.4 The unbounded ZZ

`BigNum$LShift` and `$RShift` (`BigNum.java:228-238`) call one helper, `shiftLeft(BigInteger, long)` (`BigNum.java:240-254`); `RShift` negates the count, mapping `Long.MIN_VALUE` to `Long.MAX_VALUE` first (both are beyond any `BigInteger`'s width, so the answer is the same). A negative count of magnitude up to `Integer.MAX_VALUE` is a `BigInteger.shiftRight`, a floor, as the spec's `shift` requires; beyond it the answer is `0` or `-1` by sign; zero shifted is zero; a positive count beyond `Integer.MAX_VALUE` on a nonzero value raises `IntegerOverflow` (`:246`); and a count inside the `int` range whose result `BigInteger` cannot hold is refused before the shift, by `if (u.abs().bitLength() + v > Integer.MAX_VALUE) throw Int.overflow();` (`:247`). The check is exact: `BigInteger` holds a magnitude of at most `Integer.MAX_VALUE` bits (measured with a throwaway Java probe on JDK 25 in the first round: `3 << 2147483645` succeeds with bit length `2147483647`, `3 << 2147483646` throws), and `u.abs().bitLength()` is the magnitude's bit length (for a negative power of two `u.bitLength()` alone is one less, so the `abs()` matters). `probes/PrecheckBoundary.java` measures it at the boundary for the receivers `±1`, `±3`, `±4` and `±5`, powers of two of both signs included: the check refuses exactly where `BigInteger.shiftLeft` throws, 24 cases, `mismatches 0` (`probes/PrecheckBoundary.txt:25`). Two things keep their places. The bound at `:246` stays first: `Int.shiftCount` (`Int.java:261-272`) clamps an `NN64` count of `2^63` or more and a `ZZ` count beyond a `long` to `Long.MAX_VALUE`, and without `:246` ahead of it the `long` sum `bitLength + v` would overflow, the check would pass, and `(int) v` would be `-1`, a silent right shift; `IntSemanticsRungI.fss:95` is the assertion that guards that order. And the `try`/`catch` of the JVM's `ArithmeticException` stays at `:248-253` as a backstop, because the check's exactness rests on a JDK-internal constant (`BigInteger`'s `MAX_MAG_LENGTH`).

**Why a check before the shift, measured.** The first two rounds translated the JVM's `ArithmeticException` after the call and did not check first. `BigInteger.shiftLeft` allocates the shifted magnitude before its range check throws, about 268 MB for `3 << 2147483647`. `bin/fortress` gives the JVM `-Xmx256m` when `JAVA_FLAGS` is unset (`bin/fortress:28-29`); the testSystem harness gives it 768 MB (root `build.xml:131`, `junitMem`, the `systemShard` macro's `maxmemory` at `:1181`), and the shared prefix's `JAVA_FLAGS` 4 GB. So at the launcher's own heap `:93` of the gated test ended the run with an uncatchable `java.lang.OutOfMemoryError` (`probes/skeptic/test-default-heap.txt`, the skeptic's red, reproduced in `probes/test-default-heap-before.txt`), while every run of the first two rounds, at 4 GB or 768 MB, passed. The earlier decision, "translating the JVM's own check rather than predicting it keeps the limit the JVM's", was taken without measuring at the launcher's heap, and it was wrong. The base tree fails the same way (its `u.shiftLeft((int) v)`, base `BigNum.java:224`, is the same call), so this was not a regression, but the claim of a catchable `IntegerOverflow` was the rung's. With the check, the test prints `PASS` under `bin/fortress` with `JAVA_FLAGS` unset (`test-after.txt`), and the skeptic's `SkBigAlloc.fss` prints `THROWS IntegerOverflow` at `-Xmx256m` (`probes/SkBigAlloc-after.txt`) where it ran out of memory (`probes/skeptic/SkBigAlloc.txt:1-4`). The check is the skeptic's (`probes/skeptic/fix-trial-patch.txt`), placed as the judge ruled (`JUDGE.md`, second ruling, section 1).

**What the check does not do.** A left shift whose result is representable but larger than the heap still ends the run with `OutOfMemoryError`, as any allocation beyond the heap does: `ZZ 3 LSHIFT 2147483645`, a 2^31-bit result of about 256 MB, returns at 4 GB and exhausts the 256 MB default (`probes/BigShiftHeap.txt`, from `probes/BigShiftHeap.fss`). That is the JVM's memory limit, not an integer overflow; the result fits the type, and the specification's rule (`opr-overview.tex:154-155`) does not reach it. It is not asserted.

**Decision: `IntegerOverflow`, catchable.** The brief left the exception to the rung. The alternatives were the raw `ArithmeticException` (uncatchable under `walk`, row 336's shape, and what the base tree already did for counts inside the `int` range), a `ProgramError` through `error(...)` (uncatchable, row 347's shape), or a new exception type. The spec's rule is that an integer result that does not fit throws `IntegerOverflow` (`opr-overview.tex:154-155`); `ZZ` has no width of its own but the JVM gives it one, and Pavol's principle is not to fight the JVM where it precludes an implementation; `IntegerOverflow` is the one exception the library has for "an integer result that does not fit". The limit is still the JVM's: the check states the boundary the JVM enforces, measured above, and the backstop translates the JVM's own exception should that boundary ever move.

## 5. The `shift` declaration: the collision, and the renames the specification requires

The brief (`CLIMB-BATCH-3.5.md:45`): "The name is new at top level; the library's other shift is the array-origin dotted method (…), and a collision with it is a stop." A parameter's own reach is its functional declaration (`:459-461`), so the reaches overlap. For the importing components (`RangeInternals`, `List`, a user's program), "the reach of any top-level declaration (including any imported declaration) is the component containing (or importing) that declaration" (`:454-456`), which is the reading the implementation, shared by both paths, enforces.
