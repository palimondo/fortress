\section{Changes Made by the 2026 Revival to the Working Draft}
\seclabel{revival-changes}
\sloppy

This section lists the changes made to this working draft by the 2026
revival of the Fortress project (\url{https://github.com/palimondo/fortress}).
The revival works to finish what the designers intended, judged by this
working draft, and changes the text only where a decision it has taken for
the implementation would otherwise leave the text and the implementation in
open disagreement.
Each changed passage carries a box headed
``Revised by the 2026 revival'' that points to its entry here.

Each entry gives the affected sections, the change, its rationale, its
effect, the original text, and what reversing to the alternative not taken
would require.
The original text is that of the \emph{Working Draft of February 2011},
the unrevised copy of this document kept in the revival's repository under
the directory \nolinkurl{Specification-1.0-frozen/}, cited by path and line
there.
The directory's name is misleading: its sources are the working draft of
2~February 2011, and only the file \nolinkurl{fortress.1.0.pdf} in it is the
Fortress~1.0 release.
The full reasoning behind every entry, with each original passage and each
new one, is in the revival's decision records,
\nolinkurl{explorations/compile-ladder/rung-spec-route-a/decision-record.md}
and, for the number chapters,
\nolinkurl{explorations/compile-ladder/rung-spec-numbers/decision-record.md},
in the same repository.

Each change below follows a decision of the revival.
The first of those decisions, taken on
24~September 2026 and called \emph{route~A}, is that the compiled type checker keeps
the type group's rule that no type is a subtype of two different
instantiations of one parameterized trait, a rule this working draft never
stated, and that the library's numeric types are reorganized so that they
satisfy it.
An entry whose change does not follow from route~A says so, and names the
decision it follows or gives its reason.
The revision of the number chapters (\secref{revival-numbers} to
\secref{revival-reductions}) also carries out three decisions of
26~September 2026 that follow from route~A: on the refined number types, on
conversions between number types, and on sums and products.
The alternative not taken, \emph{route~C}, is described once, in
\secref{revival-routec}.

\subsection{Instantiation exclusion}
\seclabel{revival-rule}

\begin{description}
\item[Affected sections] \secref{trait-types}; \secref{trait-decls}.
\item[Change] A property of the exclusion relation is added:
two instantiations of the same parameterized trait exclude each other
unless every static argument other than an operator argument is the same.
The rule it imposes on declarations is added beside the example of
\TYP{InclusiveMolecule}: a trait or object may not extend two such
instantiations, directly or through its supertraits.
\item[Rationale] Without the rule a value may belong to two instantiations
of one parameterized trait, and code specialised for one of them can be
chosen for a caller that was promised the other; with the rule relaxed, the
compiled implementation accepts such a program and fails at run time.
The type group adopted the rule as \emph{multiple instantiation exclusion}
(Allen, Hilburn, Kilpatrick, Luchangco, Ryu, Chase, and Steele, ``Type
Checking Modular Multiple Dispatch with Parametric Polymorphism and
Multiple Inheritance'', OOPSLA 2011), and the compiled type checker has
enforced it since 2010.
The team's later, unfinished Types chapter (Luchangco, 2012) states it in
the two parts used here, under the name \emph{instantiation exclusion}.
The type group's paper of 2019 states it as its rule [Anc-Same-Trait], which
it credits to Steele and Chase in 2012: a class that extends two instances of
a trait extends an instance below both, which for an invariant static
parameter is the same instance (Park, Hong, Steele and Ryu, ``Polymorphic
Symmetric Multiple Dispatch with Variance'', POPL 2019, Figure~4).
Operator arguments do not count: an operator argument only names the
operator a subtrait inherits (\secref{opr-ident}), neither implementation
distinguishes instantiations by it at run time, and the algebra of the
library chapters depends on types that are several instantiations of one
trait differing only in operator arguments.
\KWD{nat}, \KWD{int} and \KWD{bool} arguments count: they are values at
run time (\secref{natparams}, \secref{boolparams}).
\item[Effect] Programs in which a type is a subtype of two instantiations
of one parameterized trait that differ in any other static argument are no
longer valid. The compiled type checker refuses them where the arguments
that differ are types, or numerals given as \KWD{nat} or \KWD{int}
arguments (row~402 of the revival's gap ledger). It does not yet refuse
them where those arguments are \KWD{bool} arguments, though it accepts boolean parameters written out (row~406),
or where one of them is a static parameter of the trait or object that extends both (row~414).
The interpreter does not check the rule.
The number chapters are revised to the reorganized numeric types
(\secref{revival-numbers}).
\item[Original text] The Working Draft of February 2011 states no such
property; its relations are ``the smallest ones that satisfy all the
properties given in those sections (and this one)''
(\nolinkurl{Specification-1.0-frozen/basic/types-vals-vars.tex}, lines
185--189), and the properties it gives for trait types are these (lines
212--216):
\begin{quote}
A trait declaration may also include an \KWD{excludes} clause,
in which case the defined trait type
excludes every type that appears in that clause.
Every trait type also excludes every arrow type and every tuple type,
and the special types \TYP{()} and \TYP{BottomType}.
\end{quote}
Its rule on declarations is only that of exclusive traits,
``no trait can extend them both''
(\nolinkurl{Specification-1.0-frozen/basic/traits.tex}, lines 218--222).
\item[Route C] Replaces this rule by the rule of \secref{revival-routec}.
\end{description}

\subsection{Where-clause variables in extends clauses}
\seclabel{revival-where}

\begin{description}
\item[Affected sections] \secref{where-clauses}; \secref{trait-decls}.
\item[Change] One sentence is added: a \KWD{where}-clause variable may not
appear as a static argument in an \KWD{extends} clause.
The three declarations that followed it are kept, marked
``Not allowed'', each with the way to write it
(\secref{revival-covariance}, \secref{revival-every},
\secref{revival-empty}).
A box after Victor Luchangco's two draft notes in \secref{trait-decls},
which say that a trait can explicitly extend itself through hidden type
variables and that ``we could just rule this a special case'', answers
them.
\item[Rationale] Such a variable makes the declared type a subtype of one
instantiation for each type the variable may stand for, and instantiation
exclusion forbids any two of them.
\item[Effect] None of the three declarations ran before the revision:
both implementations stop at name resolution, because a
\KWD{where}-clause variable is not in scope in an \KWD{extends} clause.
The revision makes that the rule.
The calculus of \appref{where-calculus} still admits such
declarations (\secref{revival-calculi}).
\item[Original text] No such sentence; the draft notes are unchanged.
\item[Route C] The same under route~C, which places no type below
infinitely many instantiations of one trait.
\end{description}

\subsection{The covariance example}
\seclabel{revival-covariance}

\begin{description}
\item[Affected section] \secref{where-clauses}.
\item[Change] The declaration is kept, marked ``Not allowed''; the claims
that trait declarations may extend other instantiations of themselves and
that the declaration expresses covariance are withdrawn; static
parameters are stated to be invariant, and a widening function with
bounded static parameters is given as the way to convert one
instantiation to another.
\item[Rationale] \EXP{C\llbracket{}S\rrbracket} would be a subtype of
\EXP{C\llbracket{}T\rrbracket} for every supertype \VAR{T} of \VAR{S}.
The widening function is how the library writes covariance, in the
conversions and the \OPR{APPCOV} operator of its covariant collections,
and it runs on both implementations.
\item[Effect] Covariance is written as an explicit conversion, with the
static arguments given at the call. The box at the example adds that the
type group's later design declares variance with a \KWD{covariant}
modifier, implemented on neither implementation; the decision record and
row~404 of the revival's gap ledger say what is known of it.
\item[Original text] \nolinkurl{Specification-1.0-frozen/basic/trait-parameters.tex},
lines 339--351; the declaration is the one kept above, marked
``Not allowed'', and the text around it read:
\begin{quote}
Trait declarations are allowed to extend other instantiations of
themselves. For example, we can write:
[the declaration]
In this declaration, for every subtype \VAR{S} of \VAR{T}, \EXP{C\llbracket{}S\rrbracket}
is a subtype of \EXP{C\llbracket{}T\rrbracket}. Effectively, we have expressed
  the fact that the static parameter \VAR{S} of \VAR{C} is covariant.
\end{quote}
\item[Route C] The same under route~C.
\end{description}

\subsection{The empty optional value}

\begin{description}

\item[Change] \TYP{Nothing} becomes

\begin{description}

\item[Change] \TYP{Object} extends \TYP{Any} alone and \TYP{Tuple} likewise,

\TYP{Any}; they are no longer restated at \TYP{Object} through the

\subsection{The calculi}
\seclabel{revival-calculi}

\begin{description}
\item[Affected sections] In \appref{calculi}: \basiccore\
(Section~\ref{basic-calculus}), \wherecore\ (\appref{where-calculus}),
\overloadingcore\ (\appref{overloading-calculus}) and \acffdcore\
(Section~\ref{acffd-calculus}).
\item[Change] One box at the opening of each calculus, saying that the
calculus predates instantiation exclusion and naming the shape it admits

\nolinkurl{Specification-1.0-frozen/appendices/calculi/where/static.tex},

\nolinkurl{Specification-1.0-frozen/appendices/calculi/overloading/static.tex},

\nolinkurl{Specification-1.0-frozen/appendices/calculi/acffd/static.tex},

\subsection{The number types}
\seclabel{revival-numbers}

\begin{description}
\item[Affected sections] \secref{basic-rationals}; \secref{basic-integers}.
\item[Change] The eighteen rational types and the twelve integer types of the
original, with \EXP{\mathbb{N}} and \EXP{\mathbb{N}^*}, each a subtype of others,
are replaced by seven number types \library\ declare: \EXP{\mathbb{Z}},
\EXP{\mathbb{Z}64}, \EXP{\mathbb{Z}32}, \EXP{\mathbb{N}64}, \EXP{\mathbb{N}32},
\EXP{\mathbb{Q}} and \EXP{\mathbb{R}64}, siblings under \TYP{Number}, with the
coercions the library declares: \EXP{\mathbb{Z}64} from \EXP{\mathbb{Z}32} and
\EXP{\mathbb{N}32}; \EXP{\mathbb{N}64} from \EXP{\mathbb{N}32}; \EXP{\mathbb{Z}}
from the four fixed-size types; \EXP{\mathbb{Q}} from the five integer types;
\EXP{\mathbb{R}64} from \EXP{\mathbb{Z}32} and from integer numerals.
Every other conversion between them is explicit, the one into \EXP{\mathbb{R}64} written \EXP{\VAR{asFloat}(x)} with the method the library declares on \TYP{Number}.
\EXP{\mathbb{Q}} includes \EXP{+\infty}, \EXP{-\infty} and \EXP{0/0}; the integer
types hold no infinite value.
A subset such as the positive values is tested at run time, and the two checks
the library declares, \VAR{check} and \EXP{\VAR{check}^*} on \EXP{\mathbb{R}64},
returning \EXP{\TYP{Maybe}\llbracket\mathbb{R}64\rrbracket}, are stated.
The sentences that the type system tracks the refined types through arithmetic
are removed, and so are the sentences that \EXP{\mathbb{Q}} is a field and totally
ordered and that \EXP{\mathbb{Z}^*} is not a ring; \EXP{\mathbb{Q}}, which holds
\EXP{0/0}, is stated to be neither totally ordered nor a field.
\item[Rationale] Route~A makes the library's numeric types siblings under
\TYP{Number}, each with its own algebra, a wider type converting a narrower one
by coercion, and \EXP{\mathbb{Z}} inside \EXP{\mathbb{Q}} by coercion.
The revival decided on 26~September 2026 that the refined types become the
library's own run-time checks, which return a \TYP{Maybe}, and that their
original design is kept as a superseded design (\secref{revival-superseded});
and that a conversion between number types is a coercion where it is exact and
stays explicit where it can lose precision, the coercion into
\EXP{\mathbb{R}64} being declared from \EXP{\mathbb{Z}32} and the numerals only.
\Library\ never declared the refined types, and the trait that defines them is
refused by instantiation exclusion (\secref{revival-rule}).
\EXP{\mathbb{Q}} holds the values that \EXP{\mathbb{Q}^*} and \EXP{\mathbb{Q}^{\#}}
added, as the library's rational type does, and as \chapref{operators} already
says: ``For rational results, division by zero produces \EXP{1/0}.''
The type that holds \EXP{0/0} is ``neither totally ordered nor a field'' in the
original's own words.
The team's later Types chapter (Luchangco, 2012) keeps the statement that the
numeric types are mutually exclusive (\secref{types-libraries}).
\item[Effect] A program names \EXP{\mathbb{Q}} or \EXP{\mathbb{Z}} where it named a
refined type, and tests a sign or finiteness at run time.
A generic call over two different integer types writes its static
argument until the rule that infers the narrowest type both coerce into is
written into \chapref{type-inference} together with its implementation.
The conversion from \EXP{\mathbb{N}32} into \EXP{\mathbb{R}64}, though exact,
stays explicit, since the decision names only \EXP{\mathbb{Z}32} and the
numerals.
The library's \EXP{\mathbb{R}32}, which this change left below
\EXP{\mathbb{R}64}, is made a sibling of the other number types by
\secref{revival-rr32}, and \EXP{\mathbb{R}64} coerces from it.
\item[Original text] \nolinkurl{Specification-1.0-frozen/basic-lib/numbers.tex},
lines 19--105:
\begin{quote}
The trait \EXP{\mathbb{Q}} (\STR{QQ}) encompasses all finite rational numbers,
the results of dividing any integer by any nonzero integer.
The trait \EXP{\mathbb{Q}^*} (\STR{QQ{\char'137}star}) is \EXP{\mathbb{Q}} with
two extra elements, \EXP{+\infty} and \EXP{-\infty}.
The trait \EXP{\mathbb{Q}^{\#}} (\STR{QQ{\char'137}splat}) is \EXP{\mathbb{Q}^*} with
one additional element, the indefinite rational (written \EXP{0/0}), which is used as the result
of dividing zero by zero or of adding \EXP{-\infty} to \EXP{+\infty}.

Often it is desirable to indicate that a variable ranges over only a subset of
the rationals, such as only positive values or only nonnegative values or only
nonzero values.
Unfortunately, traditional notations such as \EXP{\mathbb{Q}^+} are not used consistently
in the literature; one author may use \EXP{\mathbb{Q}^+} to mean the set of strictly positive rationals
and another may use it to mean the set of nonnegative rationals.
Fortress therefore uses a notation that is novel but unambiguous:

chapter states the rule the checker was built to, and the effect below lists
where the checker departs from it.
The bound in place of the union is the rule by which the dispatcher of the type
group's paper of 2019 instantiates a type parameter that the arguments do not
fix, the intersection of its upper bounds, never \TYP{BottomType}; the team
had assumed the union of the lower bounds, of which the authors write ``we were
unable to complete the proofs of correctness'' (Park, Hong, Steele and Ryu,
``Polymorphic Symmetric Multiple Dispatch with Variance'', POPL 2019,
Section~5.4).
The paper gives no algorithm for static inference and asks of it only that it
never instantiate at \TYP{BottomType}; its one example of a static call is
typed at the union of its arguments' types.
The revival decided on 29~September 2026 to take the paper's rule for static
inference as well, which the paper allows and does not require.
The same rule gives a type parameter that neither an argument nor the expected
type fixes the intersection of its upper bounds: the paper's solving step
``never instantiates method type parameters with Bottom'' (Section~5.2), which
answers the question the Working Draft's own note asks, whether type inference
may infer \TYP{BottomType} for a static parameter.
The reasoning for that item, and for the order in which the compiled type
checker tries a call, is in
\nolinkurl{explorations/compile-ladder/rung-instance-bound/decision-record.md}
in the revival's repository.
The revival's decision of 29~September 2026 provided that the interpreter
follow the same rule where it instantiates a declaration, from the run-time
types of the arguments; it has no static return type to add to the bound.
It departs from the rule for the type parameters that the two boxes name,
four kinds by decision and the others as defects.
Until 9~October 2026, by decision, a type parameter whose bound mentions the
type parameter itself kept \TYP{BottomType}: it has no bound to take before its
own instance is known, the paper's calculus admits no type parameter of a
method in an upper bound (p.~11:11), and the revival had not decided that case.
The revival decided on 8~October 2026 that the interpreter leaves such a type
parameter open where nothing at a call fixes it: it does not instantiate it,
and it admits every value where it checks a value against that type.
An open type parameter is no instance: the rule that inference never
instantiates a static parameter at \TYP{BottomType} keeps a call from an
instance that admits no value, and an open parameter refuses none.
The reasoning is in \nolinkurl{explorations/reviews/p1-judgement.md} in the
revival's repository.
By decision, a big operator's static parameter whose bound does not mention it,
that a reduction or a comprehension does not write, keeps \TYP{BottomType}: it
is the element type of the reduction, which this chapter does not yet
describe, and from \TYP{BottomType} the interpreter's
library builds a comprehension's collection at the type of its elements, where
from the bound it would build it at the bound.
By decision, a type parameter that only the bound of a type parameter that the
arguments fix mentions takes the arguments' type: the interpreter has no
expected type to fix it, and the library's operator that appends two covariant
collections builds its result at such a type parameter, which at its bound
would be \TYP{Any}.
By decision, a lone type parameter whose bound mentions a static parameter,
itself or another, keeps the narrowest named common supertype of the arguments
rather than its bound: the interpreter cannot evaluate such a bound before the
instances are known, and keeping the candidates it had leaves unchanged the
case of a type parameter whose bound mentions itself and that the arguments
fix, which the revival has not yet decided.
As defects, each gated by an expected failure of the revival's tests, the
interpreter erases to \TYP{BottomType} a type parameter declared with several
bounds that it cannot meet, having no intersection type, and a type parameter
that only the result of a function expression without a declared return type
fixes, since it gives that result the type \TYP{BottomType}.
Until 3~October 2026 it also erased a type parameter that an argument bounds
only from above, taking the lower end of the interval that the arguments give
the type parameter; it now takes the upper end, the intersection of the upper
bounds that the rule gives, except, as defects gated by expected failures, for
a type parameter whose bound mentions a static parameter, which it cannot
evaluate before the instances are known, and one declared with several bounds
that it cannot meet.
The reasoning is in
\nolinkurl{explorations/compile-ladder/rung-walk-instance/decision-record.md}
in the revival's repository.
The order, a declaration chosen and then instantiated, is that of

declare, as the type group's paper of 2011 reads a declaration with static

\subsection{Overloading with static parameters}
\seclabel{revival-overloading}

\begin{description}

\item[Change] The sentence of \secref{overloading-terms} that declarations of
one name may not differ in their static parameters, and its echo in
\secref{principles-overloading}, are replaced: declarations of one name may have
different static parameters, or some of them static parameters and others none,

checker: the Return Type Rule checked over every instance, and the positional
restriction.

changes which declaration runs when one is applicable without it, declarations
being chosen on the parameter types they declare and the declaration chosen

declarations with different static parameters since May 2007, the compiled type

\subsection{The proof of overloading resolution}
\seclabel{revival-proof}

\begin{description}
\item[Affected section] \secref{proof-overloading-resolution}.
\item[Change] The proof states its scope and its assumptions: declarations
whose parameter and return types have no static parameters, calls to which
declarations are applicable without coercion, the overloading rules, bodies
that exist and are well typed, a sound and transitive subtype relation, and
every value of a trait with a \KWD{comprises} clause a value of one of its
listed types, which the compiled type checker does not yet enforce across

It states the Meet Rule as it uses it: declarations below both parameter types
that together hold every value of both, of which a declaration on the
intersection is the case of one.
Lemma~\ref{lem:le} proves only that the dynamic call has at most one most

Theorem~\ref{thm:overloading-subtyping} proves only that the dynamic call has

that the proof keeps its lemmas of existence and gives up the uniqueness of the
most specific declaration for the static call for its uniqueness for the
dynamic call, with its scope and its assumption on \KWD{comprises} clauses
marked.
Covering gives a declaration that holds the value of the argument, not one
whose parameter type is a supertype of the static type of the argument, so the
static call may have more than one most specific declaration.
The type group's paper of 2019 keeps a unique most specific declaration for
every call as a theorem (Park, Hong, Steele and Ryu, POPL 2019, Theorem~4.1);
a call whose argument's static type stands between two traits with
\KWD{comprises} clauses is outside that paper, which has no closed types, and
the revival gives up the unique most specific declaration for the static call

The full reasoning is in
\nolinkurl{explorations/reviews/comprises-type-level-proof-addendum.md} and
\nolinkurl{explorations/compile-ladder/rung-spec-overloading/decision-record.md}
in the revival's repository.
\item[Effect] The appendix proves that no call is undefined or ambiguous at run
time within its scope and on its assumptions; it does not prove the soundness of
declarations with static parameters, of inference or of coercion.
Where a type declared in a later component escapes the check of a
\KWD{comprises} clause (row~487 of the revival's gap ledger), the uniqueness of
the most specific declaration for the dynamic call is not guaranteed.
\item[Original text] \nolinkurl{Specification-1.0-frozen/appendices/overloading-function.tex},
lines 37--48:
\begin{quote}
Below we prove: $|\Sigma| \neq 0$ implies $|\sigma| = 1$, and $|\Sigma| \neq 0$
implies $|\delta| = 1$.
Informally, if any declaration is applicable to a static call then there exists
a single most specific declaration that is applicable to the static call and a
single most specific declaration that is applicable to the corresponding
dynamic call.
\end{quote}
lines 84--135, the lemma and the two theorems this change revises:
\begin{quote}
\emph{Lemma.} $|\sigma| \le 1$.  Also, $|\delta| \le 1$.

\emph{Proof.} We prove this for $\delta$, but the case for $\sigma$ is
identical.
For the purpose of contradiction suppose there are two declarations
$\f(\Ps)$ and $\f(\Qs)$ in $\delta$.  Since both $\f(\Ps)$ and
$\f(\Qs)$ are applicable without coercion to the call $\f(\Xs)$ we
have $\Xs \Ovrsubtype \Ps \inter \Qs$.  Therefore it is not the case
that $\Ps \incompatible \Qs$.  By the overloading rules, $\Ps
\neq \Qs$ and either $\Ps \excludes \Qs$ or there is a declaration
$\f(\Ps \inter \Qs)$ visible at $Z$.  Since it cannot be the case that
$\Ps \excludes \Qs$ there must exist a declaration $\f(\Ps \inter
\Qs)$ visible at $Z$.  Since $\Ps \inter \Qs \Ovrsubtype \Ps$ and $\Ps
\inter \Qs \Ovrsubtype \Qs$ we know $\f(\Ps \inter \Qs)$ is applicable
without coercion to the call $\f(\Xs)$.  Since $\Ps \neq \Qs$ either
$\Ps \inter \Qs \strictsubtype \Ps$ or $\Ps \inter \Qs \strictsubtype
\Qs$.  Either case contradicts our assumption.

\emph{Theorem.} If $|\Sigma| \neq 0$ then $|\sigma| = 1$.  Also, if
$|\Sigma| \neq 0$ then $|\delta| = 1$.

\emph{Proof.} Follows from the three lemmas before it.

\emph{Theorem.} If $\sigma = \set{S}$ and $\delta = \set{D}$ then
$D \Ovrsubtype S$.

\emph{Proof.} If the declaration with parameter type $S$ and the declaration
with parameter type $D$ satisfy the Subtype Rule then the theorem is
proved.  Otherwise, by the definition of $\sigma$ we have $\sigma
\subseteq \Sigma$.  Therefore $S \in \Sigma$.  By the first lemma,
$S \in \Delta$.  Notice that $S,D \in \Delta$ implies
$X \Ovrsubtype S$ and $X \Ovrsubtype D$.  Therefore, $S \not \excludes
D$.  By the More Specific Rule for Functions, there must exist a
declaration with parameter type $S \inter D$.  Because $X
\Ovrsubtype (S \inter D)$, $(S \inter D) \in \Delta$.
Notice $(S \inter D) \Ovrsubtype S$ and $(S \inter D) \Ovrsubtype D$.
By the definition of $\delta$, we have $\lnot \exists D'\in\Delta: D'
\strictsubtype D$.  In particular, $(S \inter D) \not \strictsubtype
D$.  Therefore $(S \inter D) = D$.
\end{quote}
\item[Route C] The same under route~C.
\end{description}

comment withheld, each integer type declaring a coercion from it.
\EXP{\mathbb{Q}} and \EXP{\mathbb{R}64}, which that library does not declare from
a numeral, coerce from it too, since \EXP{\mathbb{Q}} coerces from every integer
type (\secref{basic-rationals}) and \EXP{\mathbb{R}64} from integer numerals
(\secref{revival-int-float}).
\item[Effect] The compiled type checker converts an integer numeral to the
integer type, \EXP{\mathbb{Q}} or \EXP{\mathbb{R}64} that its context expects,
\EXP{\mathbb{N}32} and \EXP{\mathbb{N}64} among them, which refused a numeral
before.
A numeral beside a value of an integer type is converted to that type where no
declaration of the operator is applicable to the two without coercion, and that
type's own declaration of the operator is then the most specific
(\secref{resolving-coercion}); \library\ state on each integer type the
comparisons \EXP{<}, \EXP{\leq}, \EXP{>} and \EXP{\geq}, \OPR{CMP},
\OPR{MAXNUM}, \OPR{MINNUM} and a power with a numeral exponent, which the types
inherited before from a declaration that a converted numeral leaves tied with
those of \EXP{\mathbb{Z}64}, \EXP{\mathbb{Q}} and \EXP{\mathbb{R}64}.
Equality and inequality are not converted so: the declaration of \EXP{=} on
\TYP{Number} is applicable to an integer value and a numeral without coercion,
and so is the top-level declaration of \EXP{\neq}, whose parameters are of type
\TYP{Any}; the compiled type checker selects these and converts neither
operand, and \EXP{=} then compares the two as rationals, through the case for a
numeral that this change adds to \VAR{exactValue}, the function by which
\TYP{Number}'s \EXP{=} takes an exact value.
\EXP{\mathbb{Z}} states in its api, for the same reason, the additive and
multiplicative operators its body declares.
\TYP{IntLiteral} declares its own \VAR{zero}, \VAR{one}, \VAR{even},
\VAR{odd}, \VAR{floor}, \VAR{ceiling}, \VAR{truncate}, \OPR{DIVIDES},
\OPR{TIMES} and a power with a numeral exponent, which a numeral reached
before as a \EXP{\mathbb{Z}32}, since no member of \TYP{Integral} is
applicable to a numeral of that type, even with coercion
(\secref{applicability-with-coercion}).
A numeral given where any integer type is accepted, as the count of a shift,
is converted to the narrowest of \EXP{\mathbb{Z}32}, \EXP{\mathbb{Z}64} and
\EXP{\mathbb{Z}} that holds its value, as \secref{numeral-default} reads a
numeral whose conversions tie.
The interpreter still gives an integer numeral the type \EXP{\mathbb{Z}32},
\EXP{\mathbb{Z}64} or \EXP{\mathbb{Z}} by its value, so a numeral reaches none
of the declarations of \TYP{IntLiteral} there.
Its calls of the comparisons, \OPR{CMP}, \OPR{MAXNUM} and \OPR{MINNUM} on an
integer type reach that type's own declarations, which answer as the
declarations inherited before did, except that \OPR{MAXNUM} and \OPR{MINNUM}
with a converted argument, which stopped at a tie with those of
\EXP{\mathbb{Q}} or answered at \EXP{\mathbb{Q}}, now answer at the integer
type both arguments convert to.
\item[Original text] \nolinkurl{Specification-1.0-frozen/basic/expressions/literals.tex},
lines 146--148, which stand unchanged and are now followed by the new
sentence:
\begin{quote}
\Library\ define coercions
from numerals to integers (for simple numerals)
and rational numbers (for compound numerals).
\end{quote}
The box of \secref{coercion} is the revival's own text of 26~September 2026,
not the Working Draft's; it said, in
\nolinkurl{Specification/basic/conversions-coercions.tex}, lines 84--85,
before this revision:
\begin{quote}
The interpreter gives an integer numeral outside the range of \EXP{\mathbb{Z}32}
a wider integer type, and so does not yet convert it.
\end{quote}
\item[Route C] The same under route~C.
\end{description}

\subsection{The type of a varargs parameter}
\seclabel{revival-varargs}

\begin{description}
\item[Affected sections] \secref{function-decls}.
\item[Change] A box after the sentence of \secref{function-decls} that gives a
varargs parameter the type \EXP{\TYP{HeapSequence}\llbracket{}T\rrbracket}
says that no library declares that type, nor the immutable sequence that the
team's draft note at the start of \secref{function-app} agreed on in its place;
that both implementations give the parameter the array type
\EXP{\TYP{ImmutableArray}\llbracket{}T, \mathbb{Z}32\rrbracket} of \library;
and that the compiled path's own library declares no such type.
The normative text is unchanged.
\item[Rationale] This change does not follow from route~A; it follows the
revival's decision of 23~September 2026 that the implementers' later word
outweighs text that the designers left unfinished.
The text and its draft notes name \TYP{HeapSequence} and
\TYP{ReadOnlyHeapSequence} (``We agreed to implement varargs tuples using
\TYP{ReadOnlyHeapSequence} which is immutable and invariant.
We'll add \TYP{MakeReadOnlyHeapSequence} into the core library.''), and no
library declares either.
The authors of the compiled type checker named a type for the parameter,
\EXP{\TYP{ImmutableArray}\llbracket{}T, \mathbb{Z}32\rrbracket}, with the
comment ``Replace ImmutableArray with ImmutableHeapSequence when
ImmutableHeapSequence is put into the libraries''
(\nolinkurl{ProjectFortress/src/com/sun/fortress/compiler/Types.java}, lines
47--49, in the revival's repository), and the interpreter binds the parameter
to an immutable one-dimensional array of the arguments that the factory
\VAR{\_\_immutableFactory1} of \library\ builds
(\nolinkurl{ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/NonPrimitive.java},
lines 224--251), a value of that type.
The type is immutable, as the draft note asks.
Before this change the compiled type checker typed the parameter in the body
as \VAR{T}, the type of one argument, and read a parameter list with plain
bindings before a varargs binding as if the varargs binding were one more plain
binding, so that a call that passed no argument, or more than one, for the
varargs binding after plain bindings was refused (row~604 of the revival's gap
ledger).
The full reasoning is in
\nolinkurl{explorations/compile-ladder/rung-checker-defects/REPORT.md} in the
revival's repository.
\item[Effect] The compiled type checker applies a declaration with a varargs
parameter to a call as \secref{function-app} and
\secref{applicability-with-special-params} say, whatever the number of
arguments for the varargs binding, none among them, each a subtype of the type
of the binding or convertible to it; and it types the parameter in the body at
\EXP{\TYP{ImmutableArray}\llbracket{}T, \mathbb{Z}32\rrbracket} of \library,
where it typed it as \VAR{T}.
Under the compiled path's own library, which declares no \TYP{ImmutableArray},
it refuses every use of a varargs parameter, in a body, a contract or a
function expression, naming the type.
The code generator does not yet compile a function with a varargs parameter,
so no program with one runs on the compiled path.
The interpreter is unchanged.
\item[Original text] \nolinkurl{Specification-1.0-frozen/basic/functions.tex},
lines 178--180, which stand unchanged and are now followed, after the draft
note that refers to the library section for \TYP{HeapSequence}, by the box:
\begin{quote}
The type of a varargs parameter
is \EXP{\TYP{HeapSequence}\llbracket{}T\rrbracket} where \VAR{T} is
the type mentioned in (or inferred for) that binding.
\end{quote}
\item[Route C] The same under route~C.
\end{description}

\subsection{Passages not yet revised}
\seclabel{revival-notrevised}

No passage that instantiation exclusion or the reorganized numeric types
contradict is known to be unrevised.
The rule by which a generic call over two different integer types
infers the narrowest type that both coerce into is written into
\chapref{type-inference} together with its implementation
(\secref{revival-inference}); the passages that chapter left unrevised, the
sentences of \chapref{multiple-dispatch} by which static parameters were
inferred before the applicability of a declaration was checked and before
declarations were compared, the implicit bound of \secref{type-param}, and the
rule of \chapref{overloaded-declarations} on a naked type parameter of bound
\TYP{Any}, are revised with the overloading chapters (\secref{revival-overloading},
\secref{revival-bound}). The result of an integer raised to a negative power is not yet given (\secref{basic-integers}; \secref{revival-integers}).
The instance of a \KWD{nat} or \KWD{int} parameter of a declaration that a call
reaches only by dispatch, where nothing fixes it at run time, is not described;
the rule of \secref{resolving-overloading} is for type parameters (row~446 of the
revival's gap ledger).
The sentence of \secref{where-clauses} that a \KWD{where}-clause variable may
not appear as a static argument in an \KWD{extends} clause also refuses a
variable that a constraint fixes to one type; whether it is to be narrowed is
not settled.
The Meet Rule for dotted methods (\secref{more-specific-rule}) asks for a
declaration on the intersection of two parameter types; whether declarations
that together cover the intersection satisfy it too is not settled.
The type of a static call whose argument's static type stands between two
traits with \KWD{comprises} clauses, where its most specific declarations, or a
declaration more specific than them that the call may run, have static
parameters, is not given (\secref{revival-meet}).
Whether two parameter types exclude each other when the only static arguments
at which they could meet are ones that a bound rules out is not settled: the
compiled type checker takes them to exclude where the static argument that the
two parameter types force is a named type that fails the bound, and not where
it would reason through the ancestors of the parameter types
(\secref{overloading-static-params}).
Whether a \KWD{nat} parameter, which may appear wherever a variable of type
\EXP{\mathbb{N}32} can (\secref{natparams}), may be a component of a range is
settled (\secref{revival-inference}): it converts to \EXP{\mathbb{Z}32} as an
integer numeral does, so the static ranges of \secref{ranges} and the examples
whose ranges a \KWD{nat} parameter bounds stand as written.
Before the number chapters were revised, this section said:
\begin{quote}
The number chapters, \chapref{lib:numbers-basic} (whose integers are \secref{basic-integers})
and \chapref{lib:numbers-advanced}, are not yet revised.
Their nested tower, in which each integer type is a subtype of the rational
one above it and each carries its algebra at its own type, and the
conditional self-extension of \TYP{RationalQuantity}, are refused by
instantiation exclusion, as the compiled type checker refuses the
library's nested tower today.
They will be revised together with the reorganization of the library's
numeric types that route~A decides, and not before, because a
specification ahead of its library is as much an open discrepancy as one
behind it.
Until then the rule refuses the tower these chapters describe.
\end{quote}

\subsection{Route C, the alternative not taken}
\seclabel{revival-routec}

The team's 2012 patent applications (US~8,843,887 and US~8,898,632;
Chase, Steele, Naden, Hilburn, and Luchangco) relax the rule for a
self-typed parameterized trait: a type may be a subtype of several of its
instantiations when they form a chain.
The revival built that rule whole as an experiment and measured it.
It closes the unsoundness that instantiation exclusion guards against only
together with a rule on return types over every level of a chain and a
change in how a call chooses among generic methods specialised to
different instantiations: 188 lines of code in five files of the compiled
type checker and code generator.
Reversing route~A for route~C would also need a method per level of a
chain in the code generator, work in the interpreter, a way past a stack
overflow of the type checker on the self-typing clauses, and seven library
declarations, besides undoing the reorganization of the library's numeric
types.
Route~C rescues none of the \KWD{where}-clause examples of
\secref{where-clauses} nor the \TYP{Nothing} of \secref{convenience-types},
each of which places one type below infinitely many instantiations, which
no chain contains.
Under route~C the numeric chapters could have kept the nesting of their
widths, and their original text, quoted in \secref{revival-numbers} and the
entries after it and kept in the Working Draft of February 2011, is route~C's
for that nesting; route~C rescues neither the refined number types nor
\TYP{RationalQuantity} (\secref{revival-numbers}).
The record of the experiment is
\nolinkurl{explorations/reviews/mie-probes/route-c-experiment.md} in the
revival's repository.
