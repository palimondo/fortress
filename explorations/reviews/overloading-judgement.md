# The overload sentence, the `fill` pairs and rung N's decision 3: the judgement

## 1. The decisions in plain words

Three questions, one answer each, then how they hang together. Terms: an *overload set* is several declarations with one name; each is an *arm*. *Static parameters* are the `[\T\]` or `[\nat n\]` list on a declaration; an arm with them is *generic*, one without is *plain*. *walk* is the interpreter; *the checker* is the compiled path's static type checker. *The sentence* is the specification's rule that arms of one name may not differ in their static parameters (`Specification/basic/overloading.tex:100-107`, again at `advanced/overloading.tex:95-99`).

**Question 1, the sentence: it goes.** The specification is revised to the model the type group built in 2011 and the checker already runs: each arm's parameter type is read with its static parameters folded in (a plain arm is the degenerate case), arms are compared on those types, and a set is valid by the paper's three rules. The reasons, in order of weight:
- Neither implementation has ever enforced the sentence. walk has accepted differing lists since May 2007 (Chase's "nice" proposal), the library dropped its padding a month later, and the checker was built on the 2011 paper, which was written for exactly this case.
- The sentence is 2009 text. It displaced the 1.0 text of 2008, which itself said its treatment "may be replaced when the static type checker ... [is] implemented"; the 2011 paper superseded it; the team's 2012 restart of the specification dropped it.
- The library's practice is overloading across different lists, made checkable by declared exclusion or avoided by names. Enforcing the sentence would refuse 179 library api pairs at the least, the number tower's own methods among them, and put the 2007 padding back.

What the checker enforces after the revision: the paper's three rules as it does today, with two defects fixed (the return-type rule checked over every instance, not one guessed solution; and a call refused, not silently re-routed, when the arm it should pick has a size the call cannot fix, which is question 3), plus one narrow rule kept from the sentence: two generic arms of which one is more specific than the other must agree on their own static parameters position by position. That last rule is what makes a call with written static arguments safe, and it is Java's rule for overriding a generic method. It closes ledger row 398.

The library's refused set is repaired by the library's own devices, not by a checker extension: plain "exclusion" traits for the three range kinds (the device the library already uses for `Rank1/2/3` and `AnyMaybe`) clear the 12 `CAP` errors that are the sentence's; marker traits and an `excludes` clause, the device of `Vector excludes { AnyMultiplicativeRing }`, clear the array `MIN`/`MAX` arms and `String`'s juxtaposition; `openRangeHelper`'s three thunk arms, which the language itself calls ambiguous, become named helpers chosen by a `typecase` on the thunk, the way `array1` already chooses; and `StandardMinMax`'s declared `(T,T)` return, a slip the body contradicts, becomes `T`. Measured on a private copy of the library (section 9): the devices take the count stage from 125 to 113 and the named families to zero, except `openRangeHelper` and `seq`, left for the rung, and 5 `CAP` errors on same-list pairs that are a checker defect of another class, not the sentence's. `CMP` and `MINMAX` are tower-shaped and go with the flattening.

Of the four defects the clean list found, two must be fixed under every option, because on each one path gives a wrong answer the other does not: walk's choice between a generic and a plain arm depends on the order the arms were written, and the checker accepts the paper's own counterexample and the JVM then refuses the bytecode. The third (code generation for two generic arms on a bare type variable) is needed only if a family is repaired the paper's way, which none of the named ones is; it goes on the code-generation list with an expected-failure test. The fourth is question 3.

**Question 2, `fill`: the diamond by redeclaration, the pair by two names, and it is the function form that gets the new name.** The *diamond* is `fill` inherited by an array object from two unrelated parents with no declaration below both; the library already answers that for `copy`, `map`, `ivmap` and `replica` by redeclaring in the leaf traits, and `fill` follows (18 refusals to 0, no program line touched). The *pair* is `fill(v: E)`, one value everywhere, against `fill(f: I -> E)`, a function called per index; with an unbounded element type `E`, a value can be a function, so the pair is ambiguous and the checker is right to refuse it (77 refusals). Every peer language but X10 spells the two forms differently, and wherever a peer uses the word `fill` it means the value form (Java, Scala, Kotlin, C++, Rust, Julia); where the library itself had to derive a name it put it on the function-taking form (`ivmap` beside `map`, Steele's `fill2` beside `fill`). So `fill(v)` stays and the function form is renamed; the name is Pavol's (candidates: `tabulate`, Scala's word and the mathematical one; `generate`; `fillWith`). Measured: section 9. The alternatives, in one line each: rename the value form instead (the same count, about 20 fewer lines to touch, against every peer and the library's own naming); keep only the function form, the January 2007 shape (a lambda at every value site); bound the element type so that arrays cannot hold tuples or functions (the specification's own resolution, at the cost of `Map`, `Heap`, `Sparse`, a team test, and a rule the later Types chapter reversed); change the overloading rule to decide at the call (out under question 1).

What it changes: about 30 library call sites and the declarations; 11 test lines; the function row of the specification's arrays figure; 12 vocabulary lines in the microGPT programs, none of them a line of either model file (the diff is in section 4.4). Nothing changes what any program computes.

**Question 3, decision 3 stands, and it reaches into overload sets.** Decision 3 is rung N's rule that a size (a `nat` argument) the checker cannot infer at a call is an error at that call, stricter than the rule for types, under which a dead type parameter silently becomes the bottom type. It stands because the two are not alike: a type parameter nobody mentions can never be observed, but a size is a value, so an unbound one can be read in a body and would fail only at run time. Under question 1 a generic arm beside a plain arm stays legal, so row 400's case remains: the checker drops the arm it cannot instantiate and picks the plain one, while run-time dispatch picks the dropped one. The fix is the record's third candidate: when the arm the rules would pick has a size the call cannot fix, the call is refused with the same "could not infer" error, instead of the arm being dropped. Both paths then agree on which arm a call means, and nothing is asked of the run-time size rung's dispatcher. Row 400 closes with an expected-failure test.

**How the three interact.**
- Question 1 rules out the `fill` ways that would decide overloads at the call (the clean list's ways 6 and 7): the type group's rule is that a set is checked once, at its declarations. It also keeps generic-beside-plain sets legal, which is why question 3 has a case to answer.
- Question 3 is question 1's rule applied to sizes: a set is valid, a call resolves to the most specific arm by the declared types, and if that arm needs a size the call does not give, the call is wrong, not the set.
- Question 2 is independent of the sentence (no `fill` pair differs in static parameters) but not of the checker's model: under the paper's rules a type variable and an arrow type do not exclude, so the pair can only be separated by a name or a bound.
- The tower-shaped overloading errors (175 of the 482 the forced run reports) are route A's, not this judgement's; the families judged here are the ones that survive the flattening.

**Where it lands and what it costs, in rungs.**
- Batch 5 or 6, one small checker rung: question 3's call-site refusal (one condition where the checker drops an arm it cannot instantiate, reported through the existing "could not infer" error; small by reading, not built), with two expected-failure tests. It shares no file with batch 5's rungs; whether it rides in batch 5 is a manifest question for the coordinator.
- Batch 6, beside the flattening if the manifest confirms no shared declaration, else phase 3: the `fill` rung (one library rung with its tests, the figure row, and the 12 program lines).
- Phase 3, one batch of four rungs that touch disjoint files, after the flattening has landed so that the families are measured on the flat library first: the specification rung (the sentence and its two echoes, the appendix entry in S1's form); the checker rung (the return-type rule over every instance, the positional rule for generic pairs in the subtype relation); the walk rung (dispatch by declared domains); the library rung (the devices above).
- Nothing here changes a line of either model file. The 12 vocabulary lines are shown as a diff (section 4.4).

**What is open for him**: section 10, seven items, each with a default.

## 2. The words used

- **Domain**: the tuple of an arm's parameter types. **Exclude**: two types exclude when no value can have both. **More specific**: arm A is more specific than arm B when every argument A accepts, B accepts too.
- **The paper**: "Type Checking Modular Multiple Dispatch with Parametric Polymorphism and Multiple Inheritance", OOPSLA 2011, in `Papers/Types/`. Its model: a generic arm is one declaration whose domain is *existentially quantified* over its static parameters, "some `T` within the bound, and an argument of type `T`"; a plain arm is the degenerate case (`Papers/Types/introduction.tick:326-331`). A set is valid under three rules: No Duplicates, Meet, Return Type (`rules.tick:158-180`). The checker implements this (`OverloadingOracle.scala:66-117`; `TypeSchemaAnalyzer.scala:125-251`).
- **The instantiation reading**: the older idea, a generic arm as infinitely many plain arms, one per instantiation. The paper shows it fails: with `quux[\X\](x: X)` beside `quux(x: ZZ)`, an argument of type `NN <: ZZ` picks the generic arm's instance at `NN`, "which nobody wants" (`introduction.tick:171-251`). The sentence's "inferred ... before comparing" (`basic/overloading.tex:173-176`, `:292-295`) is this reading.
- **Instantiation exclusion** (the S2 judgement's name, Luchangco's short form of "multiple instantiation exclusion"): no type is two different instantiations of one generic trait; route A keeps it (POSITIONS 2026-09-24). Rung S states it in `basic/types-vals-vars.tex` and `basic/traits.tex` (S2, POSITIONS 2026-09-26).
- **Lifting**: the checker treats a method of `trait S[\I\]` as if the method itself had `[\I\]` (`STypesUtil.scala:123-127`), so a method of a generic trait beside a top-level arm is a pair with different lists.
- **The forced run**: the clean worker's copy of `StaticChecker.java` that runs the overloading check even where an api already has errors (`StaticChecker.java:268-272` returns before it), which is how the 482 were counted. The count stage of the gate sees 125 because of that early return.
- **Decision 3** (rung N): a size left unknown in a call's static arguments is refused at that call (`compile-ladder/rung-nat-checker/record.md`, "What comes back to Pavol").
- **E2, E3** (the array review, 2026-09-21): E2, an unknown size is an error only when it reaches a type, a name or a value; E3, the 25 api declarations with a dead size lose it, shown to him as a diff (`reviews/array-design-review.md:81`, `:181`; POSITIONS 2026-09-21).

## 3. Question 1: the overload sentence

### 3.1 What the evidence establishes

- The checker does not enforce the sentence. It checks every pair by the paper's rules and refuses only pairs it cannot prove unambiguous: `SCMP`/`PCMP`, overloaded over one, two and three static parameters, draw no error because their domains (a scalar, a pair, a triple) exclude structurally (`RangeInternals.fsi:30-40`; probe `DifferExcl`). What fails is open traits nothing declares exclusive, and one reasoning step (`CAP`, below). Source: `reviews/overload-static-params-ways.md` §§ 2, 5.
- Forced past the api's early return, the overloading check reports 482 errors, of which 175 (132 generic-plus-plain return-type errors and 43 duplicates) have a plain arm on a tower or `Comparison` type that the checker reports as excluding its own supertypes: the nested tower's, which route A flattens. That attribution is by reading; the worker did not re-run on a flat library, and the count of what survives is the first measurement the phase-3 batch takes (§ 3.8). The families that are this judgement's: `CAP` 17, `MIN`/`MAX` 8 plus 2, `openRangeHelper` 3, `seq` 5, juxtaposition 3, `CMP` 2 and `MINMAX` 2 (tower-shaped).
- walk's rule is the instantiation reading with a load-time check: each generic arm is instantiated from the arguments and the first strictly more specific instance is kept (`OverloadedFunction.java:856-895`), after a check that arms with generic parameters have "at least one pair of parameters [with] excluding types" unless a self parameter or an object type settles it (`:416-425`, `:519-527`). So walk accepts `GenPlainSub` and prints `generic` three times where the compiled path prints `circle, generic, circle`, and prints `circle, generic, circle` itself when the plain arm is declared first (capture `GenPlainSub.txt`): declaration order decides. That is defect 1.
- The checker's return-type rule solves the domain match once and checks that one instance (`OverloadingOracle.scala:81-117`), where the paper asks for every instance (`rules.tick:174-180`, the theorem at `overloading-check.tick:166-172`). So the paper's own counterexample, `ident[\T <: Shape\](x: T): T` beside `ident(x: Round): Round`, passes the checker and the JVM verifier refuses the class ("Bad return type", capture `GenPlainRTR.txt`); walk refuses the pair at load. That is defect 2.
- The sentence's dates: 2009 text (Sukyoung Ryu, `0f49d8698`), untouched since (`reviews/mie-probes/spec-sentences-dated.md`); the 1.0 release of March 2008 has instead §15.6.1, bounds as supertypes, "may be replaced when the static type checker and the type inference engine are implemented" (`Specification-1.0-frozen/fortress.1.0.pdf`); walk's relaxation is `3e05c3424` (2007-05-21, Chase, "the 'nice' proposal where functions with different numbers of static parameters can all be overloaded together"); the padding's removal `b176e1440` (2007-06-27, Maessen); the checker's rule `a7f149194` (2009-10, Kilpatrick, uninferable arms not dispatched); the paper 2011; the restart's overloading chapter (`overloading.tick:100-114`) goes from the operator note straight on where the sentence stood, and keeps only "inferred ... before comparing" (`:299-302`).
- The team's own doubt is in the specification: "Relaxing restrictions on static parameters of overloaded functionals", with Jan's `array1` pair and Marc's `conjugate` pair, and "What is the exclusion rule for a pair of overloaded declarations with different static parameters?" (`appendices/future.tex:236-266`).

### 3.2 The options, the library's own way first

1. **The library's practice made the rule.** Overloads across different lists, checkable by declared exclusion or avoided by names; the specification revised to the paper's model; the families repaired by the library's devices (the clean list's options 1 and 3). Commits him to: a specification rung; a checker rung (defect 2, the positional rule of § 3.5); a walk rung (defect 1); a library rung (§ 3.6). Cost: four rungs in one phase-3 batch, disjoint files. Reversal: the sentence's text is preserved in the appendix entry; enforcing it later is option 3's cost.
2. **The same, with the checker taught the missing reasoning step** for `CAP` and the object witness (the clean list's option 4, its way 11): conclude that two domains exclude when the only way they could meet contradicts a bound. Commits him to an extension beyond the paper, a soundness argument to write, and a specification paragraph the paper does not have; saves a handful of plain traits.
3. **Enforce the sentence** (the clean list's option 2). Commits him to both paths refusing every set with differing lists, lifted methods included, so every numeric operator against its algebraic trait; renaming or padding across the library, undoing `b176e1440`; 179 library api pairs refused under the narrow reading and 335 under the wide one, the tower's own method implementations among them (`reviews/mie-probes/scope-call-site-dispatch.md`, FACTS 2026-09-23); the padding clashes with the checker's rule that an arm whose parameters cannot be inferred is never dispatched. Against the library's practice and the type group's later word.
4. **Make walk the standard** (the clean list's option 6): drop the refusals walk does not make. Gives up the static guarantee the JVM verifier already enforces (`GenPlainRTR` is exactly what walk cannot catch and the verifier does). Against microGPT compiled.
5. **A rule that every static parameter must be fixed by the parameter types or a witness** (the clean list's option 5). Taken in its call-site form as question 3; its declaration form would refuse the library's own factories (`array1[\T, nat s0\]()` has both parameters in the return type only) and reopen E2.

### 3.3 The decision and why

Option 1. Derived from the fixed ground:
- *The library's practice is the standard* (POSITIONS 2026-09-19). The practice is overloading across lists since 2007, with 45 numbered declarations where names were easier, plain exclusion traits where a where-clause `excludes` cannot be written, and the `typecase`-on-thrower factory where two bounds would have made two arms. Option 1 is that practice; options 3 and 5 refuse it.
- *The type group's late, implementation-informed positions outweigh early specification text* (POSITIONS 2026-09-23). The sentence is the early text (2009); the paper (2011), the checker (2009-2012), Welterweight (2012) and the restart's Types chapter (2012, universal arrow types and function types holding generic and plain arms together, `types.tick:553-558`, `:794-801`) are the late positions, and they say option 1. The restart dropped the sentence.
- *No open discrepancy between the specification and the implementation* (POSITIONS 2026-09-24). Today the sentence describes neither path. Option 1 makes the text say what the checker does, with the original preserved and the way back priced.
- *microGPT compiled and fast* (2026-09-16). Option 1 costs no run-time mechanism; option 2 costs checker work with no library need once the plain traits exist; option 3 would rewrite the tower's operators on the way to the flattening.

This agrees with the S2 judgement: the rule S states (instantiation exclusion) is what makes the paper's reasoning about `CAP` and the `baz` repair possible at all, and the revised overloading chapter cites it rather than restating it.

### 3.4 What the revised specification says

In S1's form (a labelled callout at each changed passage, an entry in the changes appendix with the original sentences quoted with path and line in the Working Draft of February 2011, one paragraph in the front matter, the reasoning in this note), original-tree edits flagged as such, `Specification-1.0-frozen/` untouched.

- `basic/overloading.tex:100-107`: the sentence replaced by: declarations of one name may have different static parameters, or none. A declaration with static parameters is read as one declaration whose parameter type is quantified over them (the chapter names the Types chapter's universal arrow type for the function's type and the existential reading of its domain); a declaration without is the degenerate case. Applicability and specificity are decided on those quantified types. Then `:173-176` and `:292-295` ("inferred ... before comparing") rewritten to match: inference instantiates the chosen declaration; it does not precede the comparison.
- `advanced/overloading.tex:95-102`: "must have static parameters that are identical ... ignored in the remainder of this chapter" replaced by the three rules over declarations with static parameters as the paper states them: No Duplicates (no two distinct declarations each more specific than the other), Meet (a declaration more specific than both covering their overlap), Return Type (for every argument type both apply to, every applicable instance of the less specific one is matched by an instance of the more specific one with a return type below it); exclusion of two quantified domains through instantiation exclusion and the bounds, as the paper's reduction; and one rule the paper does not state, because its calls infer their instantiation and Fortress also lets a call write its static arguments: when one declaration with static parameters is more specific than another with static parameters, the two must declare the same number and kinds of their own (unlifted) parameters, position by position, with the more specific declaration's return type a subtype of the other's under that identification. The naked-`Any` rule (`:114-127`) stays.
- The examples: the paper's `baz` pair as "Not allowed" (the specification's own form, `basic/traits.tex:286-292`) with its repair beside it; `quux` beside its plain arm as allowed, with which arm a call gets; a permuted override as "Not allowed" under the positional rule.
- `appendices/future.tex:236-266`: a sentence that the relaxation is done, Jan's `array1` pair answered by the library's `typecase` factory (`FortressLibrary.fss:2245-2250`), and the exclusion question answered by the paper's reduction.
- The decision record: the sentence's date and authorship, the 2008 §15.6.1 it displaced and that section's own expectation of replacement, walk since 2007, the paper, the restart; and the way back (option 3) with its price. It also names Naden's 2012 design, run-time instantiation restricted by the return type (`Papers/RuntimeInstantiation/2012-6-15 return type instantiation restrictions.txt`, `RTRinstantionTheory.tex`), as the type group's fuller answer to the case the positional rule closes, implemented on neither path, in the same way S2 records the `covariant` keyword.

### 3.5 What the checker enforces

- The three rules over existential domains, as today.
- Defect 2 fixed: the return-type rule built as the paper's special arrow, `∀[Δ1, Δ2] (S1 ∩ S2) → T2`, with the less specific declaration's parameters kept quantified except where the domain reduction *forces* an equality (instantiation exclusion forcing `T = ZZ32` when `ZZ32` meets `AdditiveGroup[\T\]`), instead of substituting the one solution the solver returns. That refuses `GenPlainRTR` (the constraint `Round <: T` is a bound, not an equality, so `T` stays quantified and `Round <: T` fails for `T = Circle`), keeps `GenPlainSub` and the library's numeric-operator-against-trait shape, and is rung N's `escaped` treatment of sizes (`OverloadingOracle.scala:92-106`) generalised to type parameters. It is measured on the flat library before the rung is briefed, because a stricter return-type rule can refuse pairs the tree accepts today.
- The positional rule of § 3.4 for pairs in the subtype relation with unlifted static parameters on both. By reading, every such pair in the library agrees (the overriding `map[\R\]`, `ivmap[\R\]`, `replica[\U\]`, `subarray[\nat b, nat s, nat o\]` keep their lists; the top-level families with different lists are not in the subtype relation). Measured with the same run.
- Question 3's call-site refusal (§ 5).
- Not the reasoning step of option 2. The library's devices do that work.
- walk keeps its load-time check and gets defect 1's fix: the comparison of a generic arm against another arm on the declared (quantified) domains, not on the instance made from the arguments, in `bestMatchInternal` and its load check.

### 3.6 The library's refused set, repaired

Each family: the library's own device, what it costs, and whether it was measured (section 9).

- **`CAP`** (12 different-list errors, 5 same-list; `RangeInternals.fsi:46`, `:63-64`, `:98-99`, `:136`, `:191`, `:237`): `ScalarRange[\I\]`, `Range2D[\I,J\]` and `Range3D[\I,J,K\]` each get a plain parent trait, and the three plain traits exclude each other, the device of `Rank1/2/3` ("Potemkin exclusion traits. Really we just want to say that `Rank[\n\] excludes Rank[\m\] where { m =/= n }`, but we cannot yet", `FortressLibrary.fsi:1074-1084`) and of `AnyMaybe`. Both paths run the probe shape today (`DifferMIEPotemkin`). Measured on the library (§ 9): the 12 go, the 5 same-list ones stay, and those 5 are the triage's checker-side class (a lifted same-list pair in the subtype relation over the F-bounded `I`, refused where the Subtype Rule accepts it), which the keep-the-rule measurement saw vanish under the flattening anyway.
- **The array `MIN`/`MAX` arms** (8; `FortressLibrary.fsi:2557-2560` against `StandardMin`'s and `StandardMax`'s functional methods, `:185`, `:196`, and `StandardMinMax`'s, `:209-210`): a plain marker trait over each of `StandardMin` and `StandardMax`, and `ReadableArray[\E,I\] excludes` them, the device of `Vector excludes { AnyMultiplicativeRing }` (`:1467`), which exists for the same reason, an array operator against an algebraic trait's method. The design decision it takes: an array is never itself a `StandardMin`; its elementwise `MIN` is the block's operator, not the trait. Measured (§ 9): 8 → 0.
- **`StandardMinMax`'s slip** (2 return-type errors): the api declares `opr MIN(self, other:T): (T,T)` and `MAX` alike (`:209-210`) where the component's bodies return one `T` (`FortressLibrary.fss:260-261`); both files say `T`. Already so in the 2012 tree; a library defect row. Measured (§ 9): 2 → 0.
- **`String`'s juxtaposition** (3; `:2361-2363` against `MultiplicativeRing[\T\]`'s `:271`): `String excludes { AnyMultiplicativeRing }`, the same device; a string is never a ring. Measured (§ 9): 3 → 0.
- **`openRangeHelper`** (3; `RangeInternals.fsi:612-616`): three arms told apart only by the arrow type of a thunk. By the language's own rule the pair is ambiguous, since a function value can carry several arrow types (`types-vals-vars.tex:400-403`; `types.tick:518-519`), and the checker is right. The library's own ways: names (the numbered `open1Range`/`open2Range`/`open3Range` already exist beside them), and one generic entry, `openRange[\I\]()` (its callers: `FortressLibrary.fss:1697` and `tests/RangeTest.fss:81`), whose body chooses by a `typecase` on the thunk's arity, as `array1` chooses by a `typecase` on its thrower (`FortressLibrary.fss:2245-2250`, the specification's own example, `future.tex:241-245`; probe `TypecaseWitness` runs on both paths). The object witness (`N[\n\]`) is the other library device, but the checker separates `Wit[\A\]` from `Wit[\(A,B)\]` only with option 2's step (`NullaryObjWitness` refused). The shape is the rung's; not measured here.
- **`seq`** (5; `FortressLibrary.fsi:1274` `ReadableArray`, `:2044` `FilterGenerator`, `:763` `SequentialGenerator`, all functional methods `seq(self)` on open traits under `Generator`): the refusal is right, since another component could declare a type extending two of them. The library's device is an `excludes` or a meet; which one is a small design decision per pair (an array is never a filter generator; a filter over a sequential generator exists, `SimpleSeqFilterGenerator`, `FortressLibrary.fss:3461`, so that pair may want the meet, a `seq` declared on a type below both). The rung decides with the count in hand; not measured here.
- **`CMP`** (2 generic-plus-plain and the tower-shaped rest) and **`MINMAX`** (2): the `Comparison` hierarchy's double instantiation (`TotalComparison` is a `StandardPartialOrder` at `Comparison` and at itself, `FortressLibrary.fsi:100-121`) is among the 61 errors at 23 declarations route A's flattening takes (FACTS 2026-09-22, "4 comparisons"). Not this judgement's.

### 3.7 The four defects

- **Defect 1, walk's order dependence** (`GenPlainSub`): fixed under every option, since it arises between two arms with identical lists as well (both instantiated at the argument's type, equal domains, the first kept). A walk rung in the phase-3 batch; a new ledger row; gated by an interpreter test that declares the plain arm second and asserts `circle`.
- **Defect 2, the return-type rule** (`GenPlainRTR`): fixed under every option, in the form each gives it (option 1: § 3.5; option 3: parameters identified by position, which is row 398's note). A checker rung in the phase-3 batch; a new ledger row; gated by an expected-failure compile test on the `baz` pair and a passing test on its repair once defect 3 allows it to run.
- **Defect 3, code generation for two generic arms on a bare type variable** (`GenBoundedFix`: duplicate class name; `GenBoundedFixU`: unreadable serialized data): needed only if a library family is repaired the paper's way (the special arm made generic with a tighter bound), which none of § 3.6 is. ### 5.3 The decision and why

Option 1. A size is a value; a type is not.
