## FACTS.md

New entry, section "Landed semantics":

- **Walk runs the generic dotted methods of one name that a trait or an object declares together, each as its instance at symbolic static arguments.** An object takes each generic method of a name, alone or beside others of the name, with one symbolic instantiation for each name and kinds of static parameters, so that an object's redeclaration of a trait's generic method hides it; a call that writes no static argument infers them and dispatches among the instances; a call that writes static arguments instantiates each generic method whose static parameters, by their number and kinds, take them and chooses among those instances by the call's arguments, as a call of a top-level generic function does. Of two such methods of one number of parameters whose static parameters differ only in their bounds, one is dropped (row NEW-L-4), and a call on a receiver assumed at the trait stops (row NEW-L-5). Where a plain method shares the name with a generic one, a call that writes static arguments stops (row 744); of two generic functional methods of one name and one number of parameters, the second is never chosen (row NEW-L-2). Tests: `ProjectFortress/tests/GenericMethodOverloadArity.fss`, `GenericMethodOverloadSetWalk.fss`, `GenericOverloadStaticArgKindsWalk.fss`. Detail: `compile-ladder/rung-walk-load-check-generic-numeral/REPORT.md`, "What changed and why" and "Programs run old against new"; `SKEPTIC.md` beside it.

## Revival change

**The change.**
- The team's walk does not run a set of generic dotted methods of one name that a trait or an object declares together: their members' overloaded function is left unfinished (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/BuildTraitEnvironment.java:126-151`, "This blows up because the type is not instantiated"), the object takes no method of the name, and a call stops, 'Cannot find definition for method tk given receiver Two'; a dotted call that writes static arguments to an overloaded method stops in every case, 'Don't actually resolve overloading of generic methods yet.' (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/DottedMethodApplication.java:130` in `a874948ac`).
- The tree now runs each such call on the declaration that fits it, also where the static arguments are written: `ProjectFortress/tests/GenericMethodOverloadArity.fss`, `GenericMethodOverloadSetWalk.fss`. A call that writes static arguments still stops where a plain method shares the name with a generic one. Of two of one number of parameters and kinds of static parameters that differ only in their bounds, one is dropped (NEW-L-4); a receiver assumed at the trait stops (NEW-L-5).
- The reason: a dotted method declaration with static parameters is applicable to a call if some instance of it is (`Specification/basic/overloading.tex:235-238`), and such a set is a valid overloading by the rules of `Specification/advanced/overloading.tex:543-560`; the compiled path runs every case of `GenericMethodOverloadSetWalk` (`PASS`).

The two other repairs, rows 1058 and 981, change the revival's own load check (`returnRuleAtObjectArguments`, `checkNumeralTypesWritten`), not a source of the team's, and need no entry.
