## F-25 — class loader lock on first load

- **Established:** On the compiled path, `InstantiatingClassloader.loadClass` takes the JDK's per-name class-loading lock (`getClassLoadingLock(name)`) for the whole load, the same way the JDK's own `ClassLoader.loadClass` does. So when several threads first use instantiations of generic code at once, the classes those instantiations need are made and loaded without a race.
- **Conditions:** The compiled path, the first load of an instantiation's class (a class the loader makes from a template), with threads running in parallel. Before the lock, two threads first-loading such classes at once could race and the run died with a `NullPointerException` (ledger row 417, now fixed). It was measured at four threads.
- **Consequence:** A worker can count on concurrent first loads being safe and need not add locking of their own; a change that removes or narrows the lock brings the NPE back. A change near the class loader's first load needs the four-thread atomic runs (`compiler.md` says so too).
- **Evidence:** `compiler_tests/FirstLoadThreadsRungG`, which calls a generic overload at eight instantiations inside a parallel `for`. At four threads it failed 5 of 5 runs without the lock and passed 5 of 5 with it. It is one of the gate's atomic runs (four threads; `gate.md` lists it). Detail: `compile-ladder/rung-generic-runtime/REPORT.md` sections 1 and 12.
- **Could not resolve:**
  - "safe on four threads at once" (title): I could not tell whether "four threads" bounds the claim or only names the measured case. The lock argument holds for any number of threads, but the title reads as if the claim is limited to four. Unclear wording (minor).
  - "at eight instances": I read it as eight different instantiations (so eight first loads); "instances" could also mean eight calls. Unclear wording (minor).

## F-26 — walk's call-time choice when a declaration has static parameters of its own

- **Established:** Under walk, when a call has two applicable declarations and at least one of them is generic in its own right, walk picks the one whose declared domain lies strictly inside the other's. Before, it went by the order of the declarations in the source. A declaration is "generic in its own right" if it is a generic function, a generic constructor, or a functional method with static parameters that sits in a trait or object that itself has none. Its declared domain (walk's "symbolic instance") is its parameter types with each type parameter left standing as a symbol bounded by its bounds. In all other cases, which include functional methods of a generic trait or object, walk compares the domains of the concrete instances the call creates. Generic dotted methods follow F-253 instead. Separately: if the chosen instance accepts an argument only after converting it (a coercion), walk converts it and dispatches again on the converted values, so the most specific declaration for them runs.
- **Conditions:** Walk only (the compiled path has its own dispatch). The second dispatch does not happen for an overloaded method, or when `Coercions.coercionFor` finds no single conversion, as when a tuple is converted element by element. Known limit: two generic overloads whose static parameters have the same names, kinds and bounds share one symbolic instance even if their `where` clauses differ, so the comparison ignores the `where` clauses. No test or library declaration has such a pair (row 478).
- **Consequence:** A worker can rely on walk's overload choice not depending on declaration order for these pairs, and should not reorder declarations to steer it. A worker writing two generic overloads that differ only in their `where` clauses must expect walk to misjudge them (row 478). A coerced argument can end up at a different, more specific declaration than the one first chosen. This builds P-45 (choice by declared parameter types) for walk.
- **Evidence:** Gated by `tests/DispatchDeclaredDomain.fss` and `DispatchConvertedAgain.fss`. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.1, 5.2 and 5.5.
- **Could not resolve:**
  - "where exactly one lies inside the other": I read it as strict containment (one domain is a subset of the other, not both). The entry does not say what the call does when neither domain lies inside the other, or when the two are equal: fall back to the instances, to source order, or fail? (`interpreter.md` says the load check refuses equal declared domains, which may answer part of this, but the entry does not say.) Unclear wording.
  - "a generic dotted method follows F-253": the rule for dotted methods is given only as a bare entry number with no title words, so on its own the entry does not say how dotted methods are chosen. Unclear wording (missing cross-reference text).
  - "It does not for an overloaded method": I could not tell whether "it does not" means walk does not dispatch a second time (but still converts), or does not convert at all. I also could not tell whether "overloaded method" means an overloaded dotted method, or any method including functional ones. In the tuple case, I could not tell whether walk still converts element by element and simply skips the second dispatch. Unclear wording.
  - Whether the second dispatch after a conversion applies to every walk call or only to calls that involve declarations with static parameters (it sits in this entry, but its wording is general). Unclear wording.
  - "each type parameter standing for itself under its bounds": the entry does not say what happens to size, `bool` or `opr` static parameters in the symbolic instance. Unclear wording (minor).

## F-27 — walk's load check: generic beside plain, and covers through `comprises`

- **Established:** At load, walk accepts two kinds of overload pair that its parameter-by-parameter ordering would refuse. (1) A generic declaration beside a plain one, compared on their declared domains. It is accepted if one domain lies inside the other, or else if the overlap is covered as in (2). (2) Two plain declarations whose overlap is covered by other declarations through `comprises` clauses. To test a cover, walk cuts the overlap, position by position, into the pieces that the `comprises` clauses give. Every combination of pieces must fall inside the domain of some declaration that has no static parameters and lies below both declarations of the pair. Several such declarations may share the cover. If the search does not settle, walk refuses. Two generic declarations are also compared on their declared domains by the same rules (F-252).
- **Conditions:** Walk's load check only. Known limit: walk still refuses the POPL 2019 paper's valid example, a set of three generic declarations (row 539). From `interpreter.md`, a search does not settle at a cycle of `comprises` clauses, at a symbolic type, or past step and combination limits.
- **Consequence:** A worker can write such pairs and expect them to load under walk. Each piece of the overlap must be covered by non-generic declarations below both members of the pair, or walk refuses the program. A library edit that adds an overload without such a cover stops every program at load. The paper's three-declaration example cannot yet serve as a walk test that should pass. This builds P-46 and P-60 (several declarations below both may cover a meet).
- **Evidence:** Gated by `tests/ComprisesMeetWalk.fss`, `GenericBesidePlain*.fss` and others. Detail: `compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.3 and 5.4.
- **Could not resolve:**
  - P-45 (in F-26) and P-46 (here) are glossed almost the same way: "the choice among overloads by declared parameter types" and "the choice on declared parameter types". I could not tell how the two positions differ, or whether one of the numbers is a mistake. Unclear wording.
  - "by the same rules (F-252)": a bare entry number. I read "the same rules" as the containment-or-cover test above, but I could not confirm that. Unclear wording (minor).
  - "the POPL 2019 paper": not named, so I could not find which paper in `Papers/` or which example. Unclear wording (minor).
  - "lies below both": I read it as the covering declaration's domain lying below both members' domains, i.e. more specific than both. I could not rule out reading it as the declaration lying below both pieces. Unclear wording (minor).

## F-29 — walk refuses an extender that a closed trait's `comprises` does not allow

Every trait and object of the program is checked as a possible extender. An extender is allowed if it lies below one of the listed types, or if it is a trait that is itself closed, or generic, in the ways the specification permits (`Specification/basic/traits.tex`, "Trait Declarations").

- **Consequence:** A worker's test program whose main component declares a closed trait gets this check. A worker cannot rely on it for library traits. ## F-37 — compiled `typecase` on a sized type tests the class

- **Established:** On the compiled path, a `typecase` clause on a sized type such as `Vec[\ZZ32,3\]` compiles to a single `INSTANCEOF` on the instantiation's class (`Vec⟦FZZ32,3⟧`). This works even when the size is a static parameter of the enclosing generic function, because the class loader fills in the size when it makes the function's instance. So the `typecase` tells `Vec[\ZZ32,3\]` from `Vec[\ZZ32,4\]` and never reads the size's run-time descriptor (P-41).
- **Conditions:** Compiled path. Known limit: a `typecase` that is the entire body of a function, with a clause that needs a coercion, fails in code generation, sized or not (row 340).
- **Consequence:** A worker can rely on compiled `typecase` to tell sizes apart, and needs no run-time size check. A worker should avoid the body-only `typecase` with coercing clauses in compiled tests, or write it as an `XXX` test.
- **Evidence:** Gated by `compiler_tests/NatRtCase` and `NatRtCaseGen`. The bytecode was read in `perf-probes/nat/size-probes.md` section 4.
- **Could not resolve:** Nothing. Clear.

## F-39 — an operator static argument exists only at compile time

- **Established:** A static parameter of kind `opr` (e.g. `object Op[\opr ODOT\]() end`) stands for an operator name that is fixed when the code is instantiated, and nothing reads it as a value at run time. The specification and walk substitute the operator into the declaring trait's or object's methods. The compiled path puts it into the instantiation's class name, and gives the operator no descriptor, unlike a type or a size (P-41). The one library has no live `opr` parameter (the two in `FortressLibrary`, in `embiggen` and `Monoid`, are commented out). Nine test files across `tests/`, `compiler_tests/` and `other_compiler_tests/` declare one.
- **Conditions:** Known defect: compiled, `Op[\+\]()` dies with `NoSuchMethodError` on a descriptor class's `factory()`, while walk prints `Op[\+\]` (row 366, open; expected failure `compiler_tests/XXXOprParamRungS`). A three-line change to `MethodInstantiater` fixes that reproducer. It was measured but not landed.
- **Consequence:** A worker needs no run-time representation of operator arguments. Library work need not handle `opr` parameters today. Whoever fixes row 366 can start from the measured `MethodInstantiater` change, and must promote `XXXOprParamRungS`.
- **Evidence:** `perf-probes/nat/opr-kind-history.md` sections 2 and 3, `perf-probes/nat/size-probes.md` section 5, and the `XXX` test above.
- **Could not resolve:**
  - "dies with `NoSuchMethodError` on its descriptor class's `factory()`" right after "the operator has no descriptor": I could not tell whose descriptor class "its" means. It could be `Op[\+\]`'s (the instantiation's) or the operator's, which the entry just said does not exist. Unclear wording.
  - "known only at compile time, on both paths": walk has no compile step. I read this as "fixed when the code is instantiated and never read as a run-time value", but the wording does not fit walk literally. Unclear wording (minor).
