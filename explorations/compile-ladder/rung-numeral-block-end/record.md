# Rung E, rung-numeral-block-end: the record lines

## Findings

1. **A compiled block that ends in a numeral after a local declaration, or in a tuple with a numeral element, at a declared type, now runs.** Conditions: the place fixes a type (a function's declared return type, a typed binding, a parameter, or the type of an `if`'s other branch). Evidence: before, the checker's join that converts a numeral where it stands had no case for a `LocalVarDecl`, a `LetFn` or a tuple (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/Functionals.scala:1304-1313`, `:1334-1385`), so the whole block was wrapped in the coercion, which the code generator compiled as a call of the generic coercion's closure at its uninstantiated arrow type (`CodeGen.java:7808-7819`, `:4147`): 'NoClassDefFoundError: fortress/CompilerBuiltin$v'. The join now reads both forms (`7fb38bbe30`); `four()` compiles to `iconst_4`, `FZZ32.make`, `areturn`. Tests: `compiler_tests/NumeralEndsBlockAfterDeclarationCompiled`, `BlockEndsInTupleOfNumeralCompiled`, `TupleBindingIfBranchesCompiled`, each failing on the base and passing after (`junit.sh final`: `OK (19 tests)`). What it means: rows 1014, 1030 and 1031 close; the workaround of binding the numeral to a typed variable first is no longer needed at a declared type.
2. **At a place that fixes no type the block after a local declaration keeps its numeral's own type.** `x = do`, `k: ZZ32 = 3`, `4`, `end` makes `x` a `NaturalNumeral[\1,10,4\]`: `println(x)` prints 4 on the base and after, and `y: ZZ32 = x` dies with 'NoClassDefFoundError: fortress/CompilerBuiltin$v' (`compiler_tests/XXXNumeralEndsUntypedBlockCompiled`). What it means: a new row, NEW-E-2.
3. **Under the compiler's prelude `=/=` is refused at `RR32` and at `RR64`, and `=` at `RR32` overflows the stack.** `c =/= 0` for `c: RR32 = 0`, and `r =/= 0` for `r: RR64 = 0`: 'Could not check call to operator NE' (`compiler_tests/XXXNumeralNotEqualsFloatCompiled.test`); `c = 0`: 'java.lang.StackOverflowError' (`compiler_tests/XXXNumeralEqualsRR32Compiled`), since `Equality`'s `=` calls `===` (`Library/CompilerAlgebra.fss:26`) and `===` at `RR32` calls `=` (`Library/CompilerLibrary.fss:67`). 4. **Kin unchanged.** `XXXAtomicExprNumeralArms` and `XXXAtomicExprNumeralBody` (row 1043), and `XXXLabelNumeralValueCompiled` (row 340), fail as before, with the same messages: the join has no case for an atomic expression or a `label`.

## FACTS

**A numeral at the end of a block, or in a tuple, converts where it stands on the compiled path.** At a declared type (a return type, a typed binding, a parameter, an `if`'s other branch) the compiled checker converts a numeral that ends a block after a local declaration, and each numeral element of a tuple, by the type's own coercion of the numeral itself, so the code generator folds it into a constant (`scala_src/typechecker/impls/Functionals.scala`, `numeralResult` and `joinInto`). At a place that fixes no type, a block after a local declaration keeps its numeral's own type (row NEW-E-2). Tests: `compiler_tests/NumeralEndsBlockAfterDeclarationCompiled`, `BlockEndsInTupleOfNumeralCompiled`, `TupleBindingIfBranchesCompiled`; `XXXNumeralEndsUntypedBlockCompiled`. Detail: `explorations/compile-ladder/rung-numeral-block-end/REPORT.md`, "What changed and why".

## Revival change

Revival change: none. The change makes the compiled path do what the team's specification says and walk already does: a block's value is its last expression's (`Specification/basic/expressions/blocks.tex:54-56`), and a tuple's coercion is distributed element by element (`Specification/basic/conversions-coercions.tex:829-830`). That a numeral converts where it stands, by its type's coercion of the numeral itself, is the revival's numeral design, whose departure from the team's sources is recorded with it; this change only carries that design into two more places on the compiled path, with no value that differs from what the team's compiler would have computed for the same block.
