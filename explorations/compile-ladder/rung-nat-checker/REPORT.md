## 1. What changed

The compiled type checker now checks `nat` and `int` static parameters, a size such as the `n` of `Vector[\RR64, n\]`, by the plan's minimal design: a size is a symbol or a literal, two sizes are equal when they are the same symbol or the same literal, an inference variable is bound by equality, and there is no arithmetic. A program with a size inferred from an argument, one with the size written out, and a method called on a sized receiver compile; a mismatch is refused; arithmetic in a size and inference of a `bool`, `dim` or `unit` parameter are refused with an error that names them. The checker-count stage reads 125 with the crash row `none`, the numbers the batch record predicted.

## 2. Where the fix belongs

The map's row for `nat` and `int` parameters puts the wall in the checker: `STypesUtil.scala:550-557`, "interp works / comp absent — the wall is the checker, not codegen" (`explorations/coordinator/map/spec-to-implementation.md:233`; `:355` in the path table). The checker is the TYPECHECK phase, `compiler/StaticChecker.java` calling the Scala checker (`explorations/coordinator/map/modules-and-phases.md:266`, `:353`). Code generation already names a size (`NamingCzar.forIntRef`/`forIntBase`, `explorations/perf-probes/nat/java.md:36-38`) and a sized program then fails at load, which is the run-time rung's (`explorations/coordinator/POSITIONS.md:93`). So the fix is in `scala_src/`, and in the one Java class the checker calls on every method invocation, `FnNameInfo.boundsFor`, reached from `scala_src/typechecker/impls/Functionals.scala:606` and `:730`. Nothing in `compiler/StaticChecker.java`, `runtimeSystem/`, `compiler/runtimeValues/`, `CodeGen.java`, `OverloadSet.java`, `Library/` or `interpreter/` was edited.

## 3. Precedent search

- **Inference variables.** The checker has two, both syntax-tree nodes minted with `new Object()` identity: `_InferenceVarType` (`Fortress.ast:1061`, `NodeFactory.java:1166-1175`) and `_InferenceVarOp` (`Fortress.ast:1593`, `NodeFactory.java:1178-1180`). No inference variable in the tree is a reserved name. The size variable follows them (decision 1).
- **Equality-only constraints.** The operator track is the one whose constraints are equalities (`OPrimitive(pe, ne)`, `Formula.scala:57-61`): its reduce steps `oSimplify`, `oContradiction`, `oTrivial` (`:355-371`), its cliques through `getCliques` and `makeSub` (`:640-642`), its primitive constructors (`:802-806`) and `TypeAnalyzer.pEqv(Op, Op)` (`TypeAnalyzer.scala:342-348`). The size track copies each of these once, with `nEq` in place of `==`. The interpreter's rule is the same three cases (`IntNat.java:126-146`: a literal must be equal, a symbol is bound, anything else fails), which is what the plan ports (`explorations/reviews/nat-checking-plan.md:348-356`).
- **A static argument for a static parameter.** The kind-correct `STypesUtil.staticParamToArg` (`STypesUtil.scala:333-345`) and its list form are called at 17 sites (`grep` of `staticParamsToArgs\|staticParamToArg` over `ProjectFortress/src`, 19 lines less the two definitions). Two sites made a `TypeArg` for every parameter whatever its kind: `AbstractMethodChecker.scala:83` and `FnNameInfo.boundsFor` (`FnNameInfo.java:162-173` before the edit), the Scala and the Java half of one defect (`explorations/perf-probes/nat/REPORT.md:548-580`); both now call the helper. A third helper, `staticParamToArgEnhanced` (`:347-362`), is kind-correct already.
- **The shadow.** `explorations/perf-probes/nat/shadow.patch` built this design in classpath shadows and measured it; `java/java-shadow.patch` the Java site; `size-probes/keep-size-params.patch` the four lines. They are evidence; section 5 lists where the edit differs.

## 4. The specification

- **Sizes are part of the language.** "Static parameters may include one or more `nat` and `int` parameters ... These parameters are instantiated at runtime with numeric values. A `nat` parameter may be used to instantiate other `nat` parameters, or to appear in any context that a variable of type ℕ32 can appear" (`Specification/basic/trait-parameters.tex:68-90`). The chapter opens with the 2012 draft's note "Non-type static parameters and static expressions are not yet supported" (`:15-17`), which records the implementation of its day.
- **Inference is assumed, not specified.** "We assume throughout this chapter that all static variables in functional calls have been instantiated or inferred" (`Specification/basic/overloading.tex:137-138`); the inference chapter is a placeholder, "This chapter will include the Fortress static type inference mechanism" (`Specification/basic/inference.tex:15`). How an unknown size is treated is therefore Pavol's rule of 09-21 (`explorations/coordinator/POSITIONS.md:47`): an error only when it reaches a type, a name or a value.
- **Arithmetic in a size is in the language.** "Static expressions which use a restricted subset of operations can occur as static arguments" (`Specification/basic/expressions/constant.tex:23-24`, under the draft note "Static expressions are not yet supported", `:15`). Refusing it is a limit of the minimal design that the specification does not share; its test is an expected failure (section 6).
- **`bool`, `dim` and `unit` parameters are in the language** (`Specification/basic/trait-parameters.tex:101-120`, `:122-145`). Refusing their inference is a limit; its test is an expected failure.
- **The return-type rule.** "Overloaded declarations must have static parameters that are identical (up to α-equivalence) ... Therefore, static parameters ... are ignored in the remainder of this chapter" (`Specification/advanced/overloading.tex:95-103`), and the Subtype Rule requires the more specific declaration's return type to be a subtype of the other's (`:158-170`); the same sentence in the basic chapter is `Specification/basic/overloading.tex:100-107`, Pavol's open decision (`explorations/coordinator/CLIMB-BATCH-4.md:33`). The designers' checker implements the rule of their paper instead: `arrow(d1)` must be a subtype of `∀[Δ1, Δ2](S1 ∩ S2) → T2` (`Papers/Types/overloading-check.tick:166-172`), each declaration's static parameters its own. Section 5, decision 2, and section 9 say where the two readings part.

## 5. Decisions, and the deviations from the shadow

**Decision 1: the unknown size is a node, `_InferenceVarInt(Object id)`, not a reserved name.** Pavol left this to the rung (`explorations/coordinator/POSITIONS.md:47`). The alternative is the shadow's `IntRef` named `$nat$k` (option B, `explorations/reviews/nat-checking-plan.md:408-428`).
- For the node: it is the codebase's shape for both its inference variables (section 3), and it removes the four costs the shadow names (`explorations/perf-probes/nat/REPORT.md:122-126`, `:649-655`, `:695-700`): the size cliques go through the tree's own `makeSub`, which splits variables from terms by class (`Formula.scala:646`), instead of a hand-written twin; the constraint map is keyed by the node, not by a string; identity is `new Object()`, not a global counter that is not thread-safe; and no program name can collide with it. The node implements `OutAfterTypeChecking`, like `_InferenceVarType`, so one that survives checking trips the tree's own assertion (`compiler/StaticChecker.java:263-265`, `STypesUtil.scala:1955-1965`) instead of reaching code generation as a symbol.

**Decision 3: a size left unknown in a call's static arguments is an error at the call** ("Could not infer static argument nat m without context.", `Functionals.scala:247-249`, `ApplicationError.scala:114`). The shadow built only the type half of Pavol's rule (`explorations/perf-probes/nat/REPORT.md:649-655`). On the compiled path every static argument of a call names the instantiation the code generator emits (`explorations/perf-probes/nat/java.md:42-45`), so a size unsolved there reaches a name. The alternatives were to leave the variable in the static arguments for the run-time rung, where it would reach `NamingCzar` as an unknown node or trip the `OutAfterTypeChecking` assertion as an internal bug, both in files that are not this rung's; or to default it to `0`, decision E1, which Pavol did not take. The consequence goes to Pavol: a compiled call to a function with a dead size is refused (`probes/DeadSize.fss`, `explorations/compile-ladder/rung-nat-checker/probes/typecheck-probes.txt:26-33`), where `walk` binds it to `Bottom` and runs (`explorations/compile-ladder/rung-nat-checker/probes/walk-probes.txt:35-40`). The library's six vector `DOT` declarations with a dead `nat m, nat p` (`explorations/perf-probes/nat/REPORT.md:153-160`) are such functions, so E3, deleting those parameters, is what lets their compiled calls check. The declarations themselves pass, as the rule says.

**Decision 4: `solve` returns a triple**, the size substitution third, and its one test line changes (`FormulaJUTest.scala:177`); `And` and `Conjuncts` take the size map as a defaulted third field. The shadow kept `solve` a pair beside a new `solveN` and added two-argument companions because its classpath shadow had to link against classes compiled for the tree; a real edit has no such constraint.

**Decision 5: the test shapes.** The brief's `.test` files stop at `compile`. Two programs cannot pass `compile`: code generation refuses a sized overload set (`OverloadSet.java:1199`, "Only handling some static args of generic types") and a size in an `extends` clause (`CodeGen.java:5793`, "Only emitting RTTI for types right now"), both the run-time rung's. Each is one `XXX` test driving `compile` with `compile_exception_contains`, the shape of `ProjectFortress/compiler_tests/XXXObjExprRungS.test:1-3`: it is green only if the checker accepts the program (a checker refusal is not that exception) and code generation then refuses it, so it gates this rung's acceptance and the run-time rung's defect at once. A plain `typecheck` test over the same component was tried and dropped: the harness orders `.test` files by a clock-seeded shuffle (`FileTests.java:1116`, `:1135-1137`), and after a `typecheck` of an unchanged component a `compile` writes nothing and exits 0 (measured by hand: `fortress compile compiler_tests/XXXNatDispArmChecker.fss` after its typecheck printed nothing, exit 0), so the pair's verdict would depend on the order.
