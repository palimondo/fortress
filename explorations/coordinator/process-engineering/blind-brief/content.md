# The step: four pieces of work on the Fortress revival

Repository `/home/user/fortress`, branch `main`. This file says what the step must achieve. The binding rules are in `requirements.md`; the machine and its prices are in `machine.md`. Line numbers are those of the tree as it stands before the step (call it the base); edits move them, so name a declaration, not a line, when you talk about it after an edit.

## 0. The step's aim, in three lines

1. The compiled type checker's error list on the one library goes down toward zero: 340 errors in the distance measurement before the step (section 5 says what it measures); the four pieces below reach 148 of them by reading (piece C 13, piece G 57, piece N 60, plus the 18 that N's drop of three written bounds clears), and the rest belong to later work.
2. Walk, the interpreter, refuses at load what the specification refuses and it does not refuse today: a type that provides two overlapping functional methods without their meet, and an overloaded single parameter written bounded by `Any`; and it stops instantiating at `Bottom` a type parameter that an argument bounds only from above.
3. After the step the specification and the one library agree with both execution paths: every language change is in the specification with its reason, the library's declarations say what their bodies and callers say, and the compiled checker's defects found on the library are repaired or traced.

No line of the model program (microGPT's text) changes in this step, no line of a test written by the original Fortress team changes, and nothing is added to the compiler's own small prelude library.

## 1. Terms and facts the pieces rely on

- **Walk** is the interpreter: `./bin/fortress file.fss` (the file name without `.fss` must equal the component name). Its load-time checks run when a component is loaded, before `run()`. **The compiled path** is `fortress compile` then `fortress run`; its static type checker, **the checker**, also runs over the library. Both paths must keep working.
- **The one library** is the interpreter's library, `Library/*.fsi` (the apis) and `Library/*.fss` (the components) together with `ProjectFortress/LibraryBuiltin/` (`FortressBuiltin`, `NativeArray`, `AnyType`, and so on): `FortressLibrary`, `List`, `String`, `FlatString`, `Stream`, `Writer`, `RangeInternals`, `NatReflect`, `TypeProxy`, `FortressBuiltin`, `NativeArray`, `AnyType`. It is to become the library that the compiler checks. The compiler's own smaller prelude (`CompilerLibrary`, `CompilerBuiltin`, `CompilerAlgebra`) is to be deleted later; nothing goes into it now.
- **The ledger** is `explorations/fortress-gap-ledger.md`: a table of every known gap, one row each, the row number in the first column. "Row 544" means that row. A row has a status (for example NEGATIVE-VERIFIED, FIXED), the specification passage that settles it and a note.
- **The specification** is `Specification/` (LaTeX). **Appendix I** is `Specification/appendices/changes.tex`, the revival's list of changes, one subsection per entry. `Specification-1.0-frozen/` is never touched. The **S1 form** (decision "S1 form", section 4) is how every change to the text is written.
- **Test corpora.** `ProjectFortress/tests/` holds the interpreter tests (run under walk by `ant testSystem`); `ProjectFortress/compiler_tests/` and `ProjectFortress/library_tests/` hold the compiled-path tests (run by `ant testFast`, which also runs the unit tests of the compiler). A `.test` file beside a program holds its keys (`compile`, `link`, `run`, `compile_err_contains=...`, `run_out_contains=...`, `load_exception_contains=...`, `tests=` the component name). A test file named `XXX...` is an **expected failure**: the suite is green while the program fails the way its keys say and red once it starts to pass. To **promote** one is to `git mv` its `.fss` and `.test` files to a plain name chosen by topic (not by row), and re-key it where the defect's absence changes the verdict, so that it passes when the defect is gone. A test cites the specification by file and section, never by line.
- **What a test can hold.** In `tests/` a program that walk must refuse at load is held by `load_exception_contains=<text>` (the test passes when the load fails with that text; as an `XXX` file it is the expected failure that walk loads and runs instead). In `compiler_tests/` an `XXX` test can express a compile-time failure only: a defect that compiles but misbehaves at run time needs two `.test` files over one component (a plain-named one driving `link`, an `XXX`-named one driving `run` with a marker the failing run prints); a thrown `CompilerError` is keyed on the `tests=` name with `compile_exception_contains`; and an `XXX` compile test whose program compiles is red ("Saw failure, but did not satisfy compile_err_contains"), so an over-acceptance (a program that compiles and should not) cannot be held by an expected-failure compile test, and its home is the ledger row alone.
- **The interpreter suite is split in four.** `ant testSystem` runs four shards of `tests/`, each file kept by its index in the sorted list modulo 4; a file added moves every later file along the shards, so only the sum of the four shards' test counts is comparable across a change to `tests/`.
- **The distance measurement's class codes** (section 5) name kinds of error. The ones the pieces use: OT other one-off library slips and checker limits; NM names the api does not declare; D1 an abstract method that is a bodyless function under compiled desugaring; MB `Just` and `Nothing` do not join to `Maybe`; BR a big operator's body typed as the element, not the `BigReduction` or `Comprehension` declared; I2 and I3 integers in generic code (I2 the dummy-`ZZ32` device of `#` and `:`; I3 a numeral where a type parameter is expected); GF a generator filter that failed for another reason; G1 generic code with no bound compares its values (the tuples' `<` and `CMP`, `LexicographicOrder`); X1 an export error, component against api.
- **A caution on reading the measurement.** The distance measurement's class table sorts errors by fixed library line ranges, so an edit that inserts lines in a library file misfiles errors by class (ledger row 577). The per-site list of the measurement (each error's location and message) is the reliable reading, with its lines mapped through the edit's diff.

### Piece W. Walk refuses at load what the overloading chapter refuses, and a parameter bounded from above takes its bound

**The problem in plain words.** Walk's load-time checks accept two kinds of overloading set that the specification's overloading chapter forbids and that the compiled checker already refuses, so a program can load and run under walk that the compiled path rejects. And walk instantiates a type parameter that a function-typed argument bounds only from above at `Bottom`, where the specification and the compiled checker take the bound.

Defects it fixes:
- **Row 544.** Walk loads and runs a type that inherits two overlapping functional methods of one name and provides no declaration covering their overlap. The test program: two traits `S` and `T`, each declaring the functional method `tag(self): ZZ32` (bodies 1 and 2), `trait V extends { S, T } end`, `object Vo extends V end`, then `tag(Vo)`; walk prints one of the two answers, the compiled checker refuses per providing type with "Invalid overloading of tag". Walk's cover through declarations below both is, by design, not for functional methods ("whose Meet Rule is another", `overlapCovered`). The one library has no such type today (every type below two `seq` traits declares its own `seq`; the range types and `Just` declare their meets). The compiled checker skips every symbolic operator (row 584), so `String`'s four symbolic families `||`, `|||`, `//` and `///`, each pairing `(a:Any, self)` with `(self, b:Any)` (row 585), have never been checked by this rule on either path.
- **Row 534.** `f[\T extends Any\](x: T): ZZ32 = 1` beside `f(x: ZZ32, y: ZZ32): ZZ32 = 2` loads and runs under walk (`f(3) = 1`), where the compiled checker refuses the set: "A functional which takes a single parameter of a parametric type bound by Any / cannot be overloaded." The restriction is on a bound written `Any` only; a type parameter declared with no `extends` clause (whose bound is `Any` all the same) is not restricted, and the library relies on that (`array1[\T, nat s0\](v: T)` beside `array1[\T, nat s0\]()`).
- **Row 588.** `co[\T\](g: T -> ZZ32): BoxU[\T\]` given `fn (x: ZZ32): ZZ32 => x` is a `BoxU[\BOTTOM\]` under walk and a `BoxU[ZZ32]` on the compiled path. Walk takes the lower end of the interval its arguments give a type parameter, and here there is no lower end; the specification's rule and the paper's give the intersection of the upper bounds, never `Bottom`.
- **The lone-parameter pin (owed, no defect fixed).** For a generic function `[\S, T extends S\](a: T, b: T, s: S)` (named `loneS` and `loneT`; the two report the instances of `S` and of `T`), walk gives `S` and `T` both `Fruit` over the arguments `Apple, Pear, Pear` (`Apple` and `Pear` share `Fruit`) and both `Any` over `Apple, Cherry, Apple` (`Cherry` shares only `Any` with `Apple`). No test pins this and no row names the open question, whether the inference chapter means a call's type parameters to be solved jointly; that question is the project owner's and this piece does not answer it.
- **A stale sentence.** The reductions callout in the specification says both implementations take `BottomType` for a big operator's static parameter that no argument fixes; the compiled checker takes the bound there (ledger row 425's note), so the sentence is false of the checker.

### Piece C. The compiled checker's defects, and its four crashes on the library traced

**The problem in plain words.** The compiled checker wrongly refuses some valid programs (a valid object, a call, a field read), wrongly accepts one construct, prints one misleading message, passes an object expression against a closed trait that the specification forbids, and crashes outright on four declarations of the one library, hiding the errors behind them.

Defects it fixes:
- **Row 563.** The abstract-method check lets an inherited abstract generic method's own static parameter capture the implementing object's parameter of the same name, so a valid object is refused ("has no concrete implementation"). Example: `object P[\R\](x: R) extends Pair[\R\]` implementing `gen[\G\](f: Pair[\R\] -> G): G` for `Gen[\E\].gen[\R\](f: E -> R): R`; walk prints `PASS`. The same capture was fixed in the overloading checker (row 561: static parameters renamed apart before instantiation; `OverloadingChecker.scala:181-202`, called at `:144` and `:173`). Code: `ProjectFortress/src/com/sun/fortress/scala_src/typechecker/AbstractMethodChecker.scala:95-99` (the replacer is applied to the method's own domain).
- **Row 593.** The checker instantiates a lone type parameter at its declared bound when the bound of another type parameter mentions it: `depS[\S extends Number, U extends BoxU[\S\]\](s: S): BoxU[\S\]` called on a `ZZ32` is a `BoxU[Number]`, where `idS[\S extends Number\](s: S): BoxU[\S\]` gives a `BoxU[ZZ32]`. The specification: a type parameter that is the whole type of parameters takes the narrowest candidate its bounds permit. - **Row 604, the checker's varargs, three faces.** (1) A call passing nothing for a varargs parameter after two `Any` parameters is refused: `g(x: Any, y: Any, rest: Any...)` refuses `g("a", "b")`. (2) Calls with five and six varargs arguments are refused (a tail of three is accepted; the library's tails of five and six are not). (3) A varargs parameter is typed in its body as its element, not as a sequence: `k(rest: String...): String = rest` typechecks (an over-acceptance). ### Conversions

Source: `explorations/coordinator/POSITIONS.md`, the entry titled "Conversions never change which declaration runs."

> **Conversions never change which declaration runs.** A conversion is applied to make a call possible and never changes which declaration runs when one already fits; declarations are chosen by the coercion chapter's order, applicability and specificity taken on declared, quantified domains as answer 9 words them (a generic declaration fits when some instance within its bound fits); the chosen declaration is then instantiated by answer 8's promotion, its coercions inserted statically, and the rewritten call dispatches on the converted values; a numeral whose candidate types are incomparable reads as `ZZ32` (`ZZ64` or `ZZ` by magnitude), stated once in the inference chapter. So a generic arm over `T extends Number` beside a plain arm over `Any` runs the generic at `ZZ64` for a mixed-width call, the specialised instance; plain declarations are untouched; the broader rule (his own idea, "if there is a conversion to a specific type, it should be applied. And only if all combinations are exhausted and we haven't reached a specific implementation, then we go to a plain implementation") is not taken. His principle behind it: "we must make it fast, and generic is never fast. So make it fast." — fast code a JVM can specialise. With it, the inference rule: the checker infers a static argument with coercion, answer 8's promotion its number case, and keeps the expected type at a call written `f(x)` with a retry without it, so that a binding's coercion still applies; walk does the same at dispatch, re-instantiating the chosen declaration by the promotion from run-time types; the specification's type-inference chapter states it in the S1 form.

## 5. The two measurements

Both are scripts over the one library. Both need `ant compileAll` first and touch nothing in the tree (their caches and temporary files go to a scratch directory). Both are reported, never red.

- **The checker-count measurement**: `explorations/coordinator/tools/checker-count/run.sh <out-file> [scratch-dir]`. It runs the bytecode compiler's static checker over the interpreter's library, with the interpreter's prelude in scope, and prints a per-api error table, the total, and a line for any crash. The checker stops a unit at its first failing phase (an early return), so this count sees only the errors before that point: it reads 1 now (`FortressLibrary`, two locations, `isLeftZero`, row 582). A change in it is reported.
- **The distance measurement**: `explorations/coordinator/tools/distance/run.sh <out-file> [scratch-dir] [setting]`. It runs the compiled checker over the whole library, the twelve apis and their twelve components, in one JVM, every phase of every unit whatever the earlier phases reported, so that nothing hides behind an early return. The setting defaults to `any` (the compiled path with the implicit bound `Any`, as walk has it). It prints one table: `#total` (340 before the step), `#kind` (exclusion, comprises, overloading, return-type, abstract-method, bound-Object, wellformed, typecheck, export), `#class` (the root-cause classes of section 1), `#unit` (which api or component printed it first), and `#crash` rows (each declaration or check on which the checker itself crashed; a crash hides the errors behind it). The helper `errors.py <tsv-out> <run.out>...` beside it writes the per-site list (kind, family, unit, location, message, one row per distinct error); `compare.sh <last-table> <this-table>` prints the verdict (DISTANCE DOWN, UP or SAME) and every kind, class and crash row that moved.
