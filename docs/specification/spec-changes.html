I.1 Changes Made by the 2026 Revival to the Working Draft

This section lists the changes made to this working draft by the 2026 revival of the Fortress project (https://github.com/palimondo/fortress). The revival works to finish what the designers intended, judged by this working draft, and changes the text only where a decision it has taken for the implementation would otherwise leave the text and the implementation in open disagreement. Each changed passage carries a box headed “Revised by the 2026 revival” that points to its entry here.

Each entry gives the affected sections, the change, its rationale, its effect, the original text, and what reversing to the alternative not taken would require. The original text is that of the Working Draft of February 2011, the unrevised copy of this document kept in the revival’s repository under the directory Specification-1.0-frozen/, cited by path and line there. The directory’s name is misleading: its sources are the working draft of 2 February 2011, and only the file fortress.1.0.pdf in it is the Fortress 1.0 release. The full reasoning behind every entry, with each original passage and each new one, is in the revival’s decision records, explorations/compile-ladder/rung-spec-route-a/decision-record.md and, for the number chapters, explorations/compile-ladder/rung-spec-numbers/decision-record.md, in the same repository.

Each change below follows a decision of the revival. The first of those decisions, taken on 24 September 2026 and called route A, is that the compiled type checker keeps the type group’s rule that no type is a subtype of two different instantiations of one parameterized trait, a rule this working draft never stated, and that the library’s numeric types are reorganized so that they satisfy it. An entry whose change does not follow from route A says so, and names the decision it follows or gives its reason. The revision of the number chapters (Section I.1.11 to Section I.1.17) also carries out three decisions of 26 September 2026 that follow from route A: on the refined number types, on conversions between number types, and on sums and products. The alternative not taken, route C, is described once, in Section I.1.53.

I.1.1 Instantiation exclusion

Affected sections

Section 6.3; Section 10.1.

Change

A property of the exclusion relation is added: two instantiations of the same parameterized trait exclude each other unless every static argument other than an operator argument is the same. The rule it imposes on declarations is added beside the example of InclusiveMolecule: a trait or object may not extend two such instantiations, directly or through its supertraits.

Rationale

Without the rule a value may belong to two instantiations of one parameterized trait, and code specialised for one of them can be chosen for a caller that was promised the other; with the rule relaxed, the compiled implementation accepts such a program and fails at run time. The type group adopted the rule as multiple instantiation exclusion (Allen, Hilburn, Kilpatrick, Luchangco, Ryu, Chase, and Steele, “Type Checking Modular Multiple Dispatch with Parametric Polymorphism and Multiple Inheritance”, OOPSLA 2011), and the compiled type checker has enforced it since 2010. The team’s later, unfinished Types chapter (Luchangco, 2012) states it in the two parts used here, under the name instantiation exclusion. The type group’s paper of 2019 states it as its rule [Anc-Same-Trait], which it credits to Steele and Chase in 2012: a class that extends two instances of a trait extends an instance below both, which for an invariant static parameter is the same instance (Park, Hong, Steele and Ryu, “Polymorphic Symmetric Multiple Dispatch with Variance”, POPL 2019, Figure 4). Operator arguments do not count: an operator argument only names the operator a subtrait inherits (Section 12.5), neither implementation distinguishes instantiations by it at run time, and the algebra of the library chapters depends on types that are several instantiations of one trait differing only in operator arguments. nat, int and bool arguments count: they are values at run time (Section 12.2, Section 12.3).

Effect

Programs in which a type is a subtype of two instantiations of one parameterized trait that differ in any other static argument are no longer valid. The compiled type checker refuses them where the arguments that differ are types, or numerals given as nat or int arguments (row 402 of the revival’s gap ledger). It does not yet refuse them where those arguments are bool arguments, though it accepts boolean parameters written out (row 406), or where one of them is a static parameter of the trait or object that extends both (row 414). The interpreter does not check the rule. The number chapters are revised to the reorganized numeric types (Section I.1.11).

Original text

The Working Draft of February 2011 states no such property; its relations are “the smallest ones that satisfy all the properties given in those sections (and this one)” (Specification-1.0-frozen/basic/types-vals-vars.tex, lines 185–189), and the properties it gives for trait types are these (lines 212–216):

A trait declaration may also include an excludes clause, in which case the defined trait type excludes every type that appears in that clause. Every trait type also excludes every arrow type and every tuple type, and the special types () and BottomType.

Its rule on declarations is only that of exclusive traits, “no trait can extend them both” (Specification-1.0-frozen/basic/traits.tex, lines 218–222).

Route C

Replaces this rule by the rule of Section I.1.53.

I.1.2 Where-clause variables in extends clauses

Affected sections

Section 12.6; Section 10.1.

Change

One sentence is added: a where-clause variable may not appear as a static argument in an extends clause. The three declarations that followed it are kept, marked “Not allowed”, each with the way to write it (Section I.1.4, Section I.1.5, Section I.1.6). A box after Victor Luchangco’s two draft notes in Section 10.1, which say that a trait can explicitly extend itself through hidden type variables and that “we could just rule this a special case”, answers them.

Rationale

Such a variable makes the declared type a subtype of one instantiation for each type the variable may stand for, and instantiation exclusion forbids any two of them.

Effect

None of the three declarations ran before the revision: both implementations stop at name resolution, because a where-clause variable is not in scope in an extends clause. The revision makes that the rule. The calculus of Appendix A.2 still admits such declarations (Section I.1.10).

Original text

No such sentence; the draft notes are unchanged.

Route C

The same under route C, which places no type below infinitely many instantiations of one trait.

I.1.3 Conditional extension

Affected sections

Section 12.6; Section 40.2; the overview of operators in Chapter 16.

Change

A paragraph and an example are added, with a box: where the where clause of an entry of an extends clause introduces no where-clause variable and all its constraints are trait constraints, the declared trait or object extends the entry’s type exactly where the constraints hold, and the constraints hold while the entry itself, the declaration’s value parameters and its members are checked, and not while the rest of the declaration is, which holds at every instance: its static parameters, its own where clause, its throws clause and contract, its excludes and comprises clauses and the other entries of its extends clause; the example is the Fortress standard libraries’s list, totally ordered exactly where its elements are. Callouts at the lexicographic order of Section 40.2 and at the comparison of lists in the overview of operators say that a list is ordered only where its element type is totally ordered, and that the interpreter still orders every list.

Rationale

This change does not follow from route A; the revival decided on 16 October 2026 to build the forms of where clause the team wrote down, among them that a trait that extends another under a where condition is that type only where the condition holds and that its members are checked under the condition, as Haskell checks an instance’s context, Rust a conditional implementation and Swift a conditional conformance. The grammar gives each entry of an extends clause its own optional where clause, and the text orders lists “whose elements support these same comparison operators” (Specification-1.0-frozen/basic/operators/opr-overview.tex, lines 284–285), which no unconditional declaration of the list type can state: the Fortress standard libraries declared their list type as lexicographically ordered at every element type, so the compiled type checker refused the comparison of two elements of an unbounded type in the order’s own body. The team’s internal notes foresaw conditional subtyping and its cost, that “we may also not be able to tell whether a trait has a particular method” (Specification-1.0-frozen/appendices/internal-document.tex, lines 538–543, in its subsection “No Wrapped Fields Whose Types Are Naked Type Variables”). A clause that introduces a where-clause variable, or whose constraints are not all trait constraints, keeps the reading it had: the entry is extended at every instance. the Fortress standard libraries’s list keeps an element-wise = of its own outside the condition, so that a list whose elements are not ordered, a list of pairs among them, is still compared element by element. The alternative not taken is to read the clause as limiting nothing, the extension holding at every instance, under which the clause has no effect and the list’s order needs another construct. The full reasoning is in explorations/compile-ladder/rung-checker-conditional-extension/REPORT.md in the revival’s repository, and for the two callouts in explorations/compile-ladder/rung-slices-list-equality/REPORT.md.

Effect

The compiled type checker reads such a clause as this section says: a value of an instance whose static arguments satisfy the constraints is of the entry’s type, one whose static arguments do not is refused where that type is expected, and the entry, the declaration’s value parameters and its members are checked with the constraints holding, the rest of the declaration without them. Of that rest, the compiled type checker never sees a trait’s or an object’s throws clause or contract: the disambiguator drops both, so neither is checked, and neither path evaluates an object’s contract (row 781). the Fortress standard libraries’s LexicographicOrder bounds its element type by StandardTotalOrder, and its list extends it under the constraint that its element type does, so the compiled type checker orders a list exactly where its elements are totally ordered. It gives no order to a list of partially ordered elements, of RR64, QQ or ranges among them, where Section 40.2 says that a lexicographic order “may be partial or total depending on whether the ordering of the elements is partial or total” (Specification-1.0-frozen/advanced-lib/algebraic-constraints.tex, lines 520–522), and where the operators chapter’s subsection “Comparisons Operators” compares lists “whose elements support these same comparison operators”, as floating-point numbers do: no partial lexicographic order of lists is declared. The compiled type checker still lets a member that it checked with the constraints holding be called where they fail: it accepts a call of such a member on an instance whose static arguments do not satisfy them (row 773 of the revival’s gap ledger). Its other readers of an extends clause, the members a type inherits and its checks of the type hierarchy, read the entry as extended at every instance. An entry under a clause that introduces a where-clause variable or holds a constraint that is not a trait constraint, as the entries of the team’s sketch of conditional subtyping do (Specification-1.0-frozen/appendices/internal-document.tex, lines 483–512, its subsection “Conditional Subtyping”), is read as extended at every instance on both paths. The interpreter reads the extension as holding at every instance, and so does the compiled run time: a type test of an instance whose static arguments fail the constraints answers true on both (row 774, gated for the interpreter by ProjectFortress/tests/XXXConditionalExtensionTypeTestWalk.fss), so the interpreter keeps the order of a list of tuples or of floating-point numbers. The code generator compiles a declaration whose extends clause has such a clause, and one that carries a where clause of its own, for whose constraints, which the type checker checks, it emits nothing; a compiled call of a function or method whose own clause introduces a where-clause variable links and dies when it runs (row 867 of the revival’s gap ledger).

Original text

No such paragraph. The grammar is unchanged: Specification-1.0-frozen/basic/traits.tex, line 83,

TraitTypeWhere ::= TraitType Where?

and the front matter lists “where clauses and conditional extension” among the features not yet supported (Specification-1.0-frozen/fortress/preamble.tex, line 82). The two passages that order lists are unchanged (Specification-1.0-frozen/advanced-lib/algebraic-constraints.tex, lines 519–522, and Specification-1.0-frozen/basic/operators/opr-overview.tex, lines 284–285); each gains its callout.

I.1.4 The covariance example

Affected section

Section 12.6.

Change

The declaration is kept, marked “Not allowed”; the claims that trait declarations may extend other instantiations of themselves and that the declaration expresses covariance are withdrawn; static parameters are stated to be invariant, and a widening function with bounded static parameters is given as the way to convert one instantiation to another.

Rationale

C⟦S⟧ would be a subtype of C⟦T⟧ for every supertype T of S. The widening function is how the library writes covariance, in the conversions and the APPCOV operator of its covariant collections, and it runs on both implementations.

Effect

Covariance is written as an explicit conversion, with the static arguments given at the call. The box at the example adds that the type group’s later design declares variance with a covariant modifier, implemented on neither implementation; the decision record and row 404 of the revival’s gap ledger say what is known of it.

I.1.8 The root’s algebra

Affected sections

Chapter 31.

Change

Object extends Any alone and Tuple likewise, each still excluding the other; the sentences saying that they describe their operators with algebraic constraints are removed. The original declaration of Object is kept, marked “Not allowed”.

Rationale

Every trait but Any, Object and Index extends Object, and every commutative algebraic type T is an EquivalenceRelation⟦T, =⟧; with the original declaration such a type is also an EquivalenceRelation⟦Object, ≣⟧, and the two differ in a type argument. Tuple’s declaration is not refused by the rule, since no tuple type extends a generic trait (a tuple of indices is a subtype of the trait Index, which takes no static parameter, Section I.1.44), but its text follows Object’s. The replacement is the library’s declaration.

Effect

The properties of ≣ are those stated in trait Any; they are no longer restated at Object through the algebra chapter.

I.1.10 The calculi

Affected sections

In Appendix A: Basic Core Fortress (Section A.1), Core Fortress with Where Clauses (Appendix A.2), Core Fortress with Overloading (Appendix A.3) and Acyclic Core Fortress with Field Definitions (Section A.4).

Change

One box at the opening of each calculus, saying that the calculus predates instantiation exclusion and naming the shape it admits that the rule refuses: in Basic Core Fortress, an object that extends two different instantiations of a parameterized trait declaring no method, so that its statement that all of its valid programs are valid Fortress programs no longer holds for every program; in Core Fortress with Where Clauses, a where-clause variable in a supertype, which its subtyping rule turns into one supertype for each witness of the variable; in Core Fortress with Overloading, the same object as in Basic Core Fortress, which its rule for valid method declarations admits because the trait declares no method; in Acyclic Core Fortress with Field Definitions, a trait that extends an instantiation of itself at its parameter’s bound, which conditions (2) and (3) of its rule for an acyclic type hierarchy admit. Rationale

The calculi are the team’s formal record of this working draft as it stood, and the rule changes the language, not that record. New premises in their rules would be new formal work, and would reopen soundness claims that were proved for the rules as they are written. The revival decided on this treatment on 26 September 2026.

Effect

None on the language or on either implementation. The four calculi admit programs, in the shapes named, that are not valid Fortress programs.

I.1.11 The number types

Affected sections

Section 33.1; Section 33.2.

Change

The eighteen rational types and the twelve integer types of the original, with ℕ and ℕ∗, each a subtype of others, are replaced by seven number types the Fortress standard libraries declare: ℤ, ℤ64, ℤ32, ℕ64, ℕ32, ℚ and ℝ64, siblings under Number, with the coercions the library declares: ℤ64 from ℤ32 and ℕ32; ℕ64 from ℕ32; ℤ from the four fixed-size types; ℚ from the five integer types; ℝ64 from ℤ32 and from integer numerals. Every other conversion between them is explicit, the one into ℝ64 written asFloat(x) with the method that each number type declares (Section I.1.29). ℚ includes +∞, −∞ and 0/0; the integer types hold no infinite value. A subset such as the positive values is tested at run time, and the two checks the library declares, check and check∗ on ℝ64, returning Maybe⟦ℝ64⟧, are stated. The sentences that the type system tracks the refined types through arithmetic are removed, and so are the sentences that ℚ is a field and totally ordered and that ℤ∗ is not a ring; ℚ, which holds 0/0, is stated to be neither totally ordered nor a field.

Rationale

Route A makes the library’s numeric types siblings under Number, each with its own algebra, a wider type converting a narrower one by coercion, and ℤ inside ℚ by coercion. The revival decided on 26 September 2026 that the refined types become the library’s own run-time checks, which return a Maybe, and that their original design is kept as a superseded design (Section I.1.14); and that a conversion between number types is a coercion where it is exact and stays explicit where it can lose precision, the coercion into ℝ64 being declared from ℤ32 and the numerals only. The Fortress standard libraries never declared the refined types, and the trait that defines them is refused by instantiation exclusion (Section I.1.1). ℚ holds the values that ℚ∗ and ℚ# added, as the library’s rational type does, and as Chapter 16 already says: “For rational results, division by zero produces 1/0.” The type that holds 0/0 is “neither totally ordered nor a field” in the original’s own words. The team’s later Types chapter (Luchangco, 2012) keeps the statement that the numeric types are mutually exclusive (Section 6.9).

Effect

A program names ℚ or ℤ where it named a refined type, and tests a sign or finiteness at run time. A generic call over two different integer types writes its static argument until the rule that infers the narrowest type both coerce into is written into Chapter 20 together with its implementation. The conversion from ℕ32 into ℝ64, though exact, stays explicit, since the decision names only ℤ32 and the numerals. The library’s ℝ32, which this change left below ℝ64, is made a sibling of the other number types by Section I.1.28, and ℝ64 coerces from it.

Original text

The trait ℚ# (QQ_splat) is ℚ∗ with one additional element, the indefinite rational (written 0/0), which is used as the result of dividing zero by zero or of adding −∞ to +∞.

Often it is desirable to indicate that a variable ranges over only a subset of the rationals, such as only positive values or only nonnegative values or only nonzero values. Unfortunately, traditional notations such as ℚ+ are not used consistently in the literature; one author may use ℚ+ to mean the set of strictly positive rationals and another may use it to mean the set of nonnegative rationals. Fortress therefore uses a notation that is novel but unambiguous:

The Fortress type system tracks these types closely through various arithmetic operations; for example, adding two values of type ℚ> produces a result of type ℚ>, and adding a value of type ℚ∗> and a value of type ℚ≥ produces a value of type ℚ∗≥.

Here we present only the trait ℚ and its methods. I.1.12 The rational trait

Affected section

Section 33.1.

Change

The listing of ℚ extends Number in place of the real numbers, ℚ∗, three instantiations of Field with ℚ≠ as the multiplicative group, TotalOrderOperators and PartialOrderAndLattice, and declares the coercions from the five integer types, with a method entry for them. Ten sentences of the method entries lose the words “For types ℚ∗ and ℚ#,” or “For type ℚ#,”, the next word taking the capital (the sentence on MAXNUM and MINNUM now begins “The operators”); the parenthesis on the reciprocal’s result type and the sentence on TotalComparison are removed.

A signature that named a refined type takes the type the Fortress standard libraries declare for the method where they declare it (division and the absolute value return the rational type, exponentiation by an integer returns it, and the comparison CMP returns Comparison), and ℚ or ℤ where they do not. The library declares check and check∗ on ℝ64, where Section 33.1 states them, and no check by sign. What the entries said of ℚ∗ and ℚ# holds of ℚ, which holds their values.

Effect

Affected sections

Change

A third revision adds a fourth: an argument of a call that the section does not accept with its arguments typed without an expected type, where the argument is itself a call with inferred static arguments, whose expected type is the parameter type at its position of each declaration of the enclosing call in turn, instantiated, where that declaration has static parameters, by the arguments not so typed and the expected type of the enclosing call; and a paragraph after the list says that the enclosing call then invokes, of the declarations that are applicable to it with its arguments so typed and whose return types fit its expected type, the one more specific than every other on the parameter types they declare, and is otherwise typed as before, so that a declaration that the section accepts for the call as its arguments are typed without an expected type is never passed over. Rationale

This change does not follow from route A; it follows the revival’s decision of 8 October 2026 that these four contexts give a call the type that the text already requires of them, a clause of a typecase expression by the rule for the type of the typecase expression. The text gives each context its type. “If there is no else clause in an if expression, then every clause must have type ()” (Section 13.19). “If the last element of the expression block is an expression, the value and type of this expression are the value and type of the expression block as a whole” (Section 13.11), whatever local declarations precede it. The static arguments of an identifier reference “are statically inferred from the context of the function call” (Section 13.2), however the call is written. “The type of a typecase expression is the union of types of all right-hand sides of the typecase clauses” (Section 13.22), which is a subtype of the expected type when the type of each clause is. The second revision follows the revival’s decision of 9 October 2026 that the body of a label expression and the with clause values of its exits take the expected type of the whole label expression, as the clauses of a typecase expression take that of the typecase expression. “The type of a label expression is the union of the type of the last expression of its expression block and the types of the with clause values of any exit expressions within the label expression whose target is the label expression’s name” (Section 13.12), which is a subtype of the expected type when each of those types is. I.1.28 The single-precision floating-point type

Affected sections

Section 33.1; Section I.1.11.

Change

The passage that names the number types names ℝ32 (RR32) beside ℝ64, a sibling of the others under Number, and says that ℝ64 coerces from ℝ32. The effect of Section I.1.11 no longer says that the library’s ℝ32 stays below ℝ64.

Rationale

The Fortress standard libraries declared ℝ32 a value object extending ℝ64, so that a value of ℝ32 was also a value of ℝ64, which Section 6.9 excludes: “These types are mutually exclusive; no value has more than one of them.” The team’s later Types chapter (Luchangco, 2012) keeps that sentence (Documentation/Specification/Prose/Language/types.tick, lines 977–978, in the revival’s repository). Route A makes the number types siblings under Number, each with its own algebra, and the revival decided on 26 September 2026 that a conversion between number types is a coercion where it is exact; every ℝ32 value is exact in ℝ64. The Fortress standard libraries now declare ℝ32 extending Number and the four algebraic traits at its own type, as they declare ℝ64, and ℝ64’s coercion from it (ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi, lines 47–48; Library/FortressLibrary.fsi, lines 291–296). The team’s own compiler library has declared the two types siblings since its change of 31 August 2009, whose message says “RR32 is NOT a subtype of RR64” and “this would be a good time to get coercion working”; it declares the same coercion today (ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi, lines 433–435 and 475). The example of Section 17.8 computes an ℝ32 with an ℝ64 by the declaration on ℝ64 after a coercion from ℝ32, which is what the library now does. The full reasoning is in explorations/compile-ladder/rung-rr32-sibling/decision-record.md in the revival’s repository.

Effect

A value of ℝ32 is not a value of ℝ64. Two ℝ32 values combine by the operators declared on ℝ32, into an ℝ32; an ℝ32 combined with an ℝ64 or a ℤ32 is converted to ℝ64, and the result is an ℝ64; an ℝ32 combined with a numeral by an operator that ℝ32 declares over two of its values, as + or MAX, takes the numeral converted into ℝ32, which declares a coercion from both numeral types, and the result is an ℝ32, on whichever side of the ℝ32 the numeral stands; an ℝ32 is converted where an ℝ64 is expected. A conversion from ℝ64 into ℝ32, which can lose precision, stays explicit.

The team’s later compiler library declares Number with nothing in it (ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss, lines 510–511, in the revival’s repository), and declares its conversion into ℝ64 on each of its number types, not on a shared trait; the Working Draft names no such method. With Number open to a program’s own number types, an abstract asFloat would oblige a program’s complex number to give a float, and an = on Number built on it would call two different complex numbers equal. The Fortress standard libraries now declare asFloat on ℝ64, ℝ32, ℚ, ℤ32, ℤ64, ℕ32, ℕ64 and ℤ (Library/FortressLibrary.fsi; ProjectFortress/LibraryBuiltin/FortressBuiltin.fsi), and the vector norm at each of the eight number types as its element type. The revival decided on 9 November 2026 that the numeral types declare none, since no value of a numeral type exists when a program runs (Section I.1.50). A reversal would declare asFloat on Number again, abstract, with an = built on it, so that every type below Number must give a float, or declare it on a new trait that the number types extend.

Effect

asFloat(x) is unchanged at every number type of the library. Two numbers of different types compare by = where a coercion carries one into the other: for each of the library’s fourteen coercions between number types, the type converted to declares = at the type converted from, and that type declares = at the first, each converting the narrower operand as the coercion does. The library’s eleven coercions from the two numeral types have no such pairs, since no value of a numeral type exists when a program runs (Section I.1.50). Two numbers of different types that no coercion joins, as a ℚ and an ℝ64, compare by the library’s fallback = over Any, which answers a ≣ b; a program that means their values writes the conversion, asFloat(x) = y. Two values of different types are never strictly equivalent (Section 11.4), so that fallback answers false for them, on the interpreter as in the compiled code’s helper. A number type of a program’s own compares by the = it declares, or else by the fallback.

I.1.30 Overloading with static parameters

Affected sections

Section 15.1; Section 15.2; Section 15.3; Section 15.5; Section 24.1; Section 24.5; Section 17.5; and, in a draft build, the proposed features of the appendix “Internal Document”.

Change

The sentence of Section 15.1 that declarations of one name may not differ in their static parameters, and its echo in Section 24.1, are replaced: declarations of one name may have different static parameters, or some of them static parameters and others none, and a declaration with static parameters is read as one declaration whose parameter type ranges over its instances. Such a declaration is applicable to a call when some instance of it within its bounds is, and it is compared with others on the parameter types they declare, taken over all their instances; the static arguments that a call does not write are inferred for the declaration it selects, after the selection (Chapter 20). The three sentences of Chapter 15 that inferred static parameters before applicability was checked and before declarations were compared, and the chapter’s assumption that the static variables of a call have been instantiated or inferred, are rewritten to match. A new section, Section 24.5, states for declarations with static parameters the three rules of the type group’s paper of 2011, the No Duplicates Rule, the Meet Rule and the Return Type Rule, the last checked over every instance of the less specific declaration; how two parameter types with static parameters exclude each other, by existential reduction with instantiation exclusion; and a pair that the Return Type Rule refuses, in the shape of that paper’s own example, beside the pair that repairs it. A box in that section states the restriction that the compiled implementation adds, that of two declarations with as many static parameters of their own, one of which is more specific than the other, the two agree on their static parameters position by position, with an override that reorders them as its example. A later revision states the section’s No Duplicates Rule on the relation without “and not the other way round”, that d1 and d2 are not each applicable to every call to which the other is applicable, with a box, and the box on Jan’s example in the internal document gives that rule as its reason. A further revision has that box say that the factory of the Fortress standard libraries gives a Vector where its type argument is one of the eight number types and a plain array where it is any other type, Number among them: the factory called the vector factory at its own type argument, which has no bound, an instance that the bound of a Vector’s element type refuses (Section 12.1), and it now builds the vector at each number type, so that a Vector of Number, which is not well-formed, is no longer its result. Another revision has the section’s existential reduction read instantiation exclusion where the two parameter types, or their elements at one position, are or extend instances of one parameterized trait, where it read it only where they mention one, with a box, and the internal document’s box on the questions on exclusion says the same. Section 17.5 says in three places that a declaration with static parameters is applicable when some instance of it is, that it is compared on the parameter types it declares, and that the declaration selected is then instantiated, the coercions of its instance inserted statically. In the internal document, the proposed features on relaxing the restrictions on the static parameters of overloaded functionals and on overloading with static parameters are marked done, Jan’s example answered by the Fortress standard libraries’s factory and the questions on exclusion by the existential reduction.

Rationale

This change does not follow from route A; the revival decided on 26 September 2026 that the sentence goes and that this working draft states the model of the type group’s paper of 2011 (Allen, Hilburn, Kilpatrick, Luchangco, Ryu, Chase, and Steele, “Type Checking Modular Multiple Dispatch with Parametric Polymorphism and Multiple Inheritance”, OOPSLA 2011; Papers/Types/rules.tick, lines 132–180, and Papers/Types/setup.tick, lines 393–397, in the revival’s repository), which the compiled type checker applies, with two changes to the checker: the Return Type Rule checked over every instance, and the positional restriction. On 28 September 2026 it decided that a coercion makes a call possible and never changes which declaration runs when one is applicable without it, declarations being chosen on the parameter types they declare and the declaration chosen being then instantiated. Neither implementation enforced the sentence: the interpreter has overloaded declarations with different static parameters since May 2007, the compiled type checker applies the rules of that paper to them, and the Fortress standard libraries overload across different static parameters throughout. The sentence is text of 2009. The Fortress 1.0 release of 2008 compared generic declarations instead by using “their bounds as their supertypes”, in a section whose type relations “may be replaced when the static type checker and the type inference engine are implemented” (Specification-1.0-frozen/fortress.1.0.pdf, Section 15.6.1), and the team’s unfinished restart of this specification in 2012 dropped the sentence (Documentation/Specification/Prose/Language/overloading.tick, lines 100–114, in the revival’s repository). The restart’s Types chapter (Luchangco, 2012) gives function types that hold generic and plain declarations together, as sets of arrow types and universal arrow types, and drops from a quantified type a static parameter that appears in none of its types (Documentation/Specification/Prose/Language/types.tick, lines 553–558, 764–767 and 794–801). The positional restriction is the compiled implementation’s and not the language’s: its code generator hands the static arguments that a call writes, by position, to whichever declaration dispatch reaches (row 398 of the revival’s gap ledger), while the type group’s paper of 2019 instantiates a dispatched declaration by substitution and renames static parameters freely (Park, Hong, Steele and Ryu, “Polymorphic Symmetric Multiple Dispatch with Variance”, POPL 2019, Sections 4 and 5.2). That paper’s soundness proof excludes an upper bound that names a type parameter, its own included, and closed types, so that the Fortress standard libraries’s families over a type parameter bounded by an instance of a trait at itself, such as SUM, BIG MAX and those over Integral, rest on the rules of 2011 as the compiled type checker implements them, and not on the proof of 2019. The full reasoning is in explorations/compile-ladder/rung-spec-overloading/decision-record.md in the revival’s repository. The No Duplicates Rule was first stated on the strict sense of more specific that the section defines, under which no two declarations are each more specific than the other, so that it refused no pair, and two declarations each applicable to every call to which the other is fell to the Meet Rule (row 696 of the revival’s gap ledger). The paper of 2011 defines its relation of specificity without strictness, one declaration being more specific than another when every type to which the first is applicable is one to which the second is, and its No Duplicates Rule “forbids distinct declarations from being equally specific” (Papers/Types/rules.tick, lines 97–108, 158–162 and 184–185); the paper of 2019 states it as “Distinct method declarations must have different applicable sets” (Section 2.2), and its rules [No-Dup-Not-Less] and [No-Dup-Not-Gtr] refuse exactly a pair whose domain types are each a subtype of the other (Section 4.1 and Figure 5). The restatement follows the revival’s decision of 23 September 2026 that the type group’s later word, that paper among it, outweighs the early text; its reasoning is in explorations/compile-ladder/rung-popl-examples/REPORT.md in the revival’s repository. The revision of the existential reduction follows the paper of 2011, whose exclusion of two instances of type constructors reads every pair of their ancestors (Papers/Types/fig-exclusion.tick, lines 136–147, in the revival’s repository), and the revival’s decision of 17 October 2026 that two declarations with static parameters exclude each other as the existential reduction reads their whole parameter types, in both implementations; its reasoning is in explorations/compile-ladder/rung-existential-reduction/REPORT.md in the revival’s repository. The compiled type checker’s test of exclusion reads the static parameters’ bounds by the revival’s decision of 23 October 2026: the existential reduction of the paper of 2011 solves the condition that the meet is not empty together with the bounds of its static parameters (Papers/Types/exc-reduction.tick, lines 40–46 and 68, in the revival’s repository), which the compiled type checker carried but from which its solver took no equality; its reasoning is in explorations/compile-ladder/rung-self-type-exclusion/REPORT.md in the revival’s repository.

I.1.47 A comparison at a NaN or at the rational indefinite

Affected section

The revival takes the Working Draft’s names, its static parameters and the default as its own finishing of the text; no source of the team calls those names either final or temporary. A nat parameter used as a value has one type, ℤ32, as the revival decided on 28 September 2026 for the ranges (Section I.1.26), not ℕ32 as Section 12.2 says; the four numbers of a numeral type, naturals of any size, are read in a coercion’s body as values of type ℤ, the bound of a size to 32 bits being this implementation’s, for the lengths of arrays. A numeral at a type of a program’s own that declares no coercion from the numeral’s type is refused, since coercion does not chain; the alternative not taken converts it into its default first and then by the type’s own coercion from that default. A reversal to the Working Draft’s polymorphic numerals would keep a numeral’s own type wherever nothing fixes a type, as the team’s compiled path’s own library did, so that x = 3 binds a numeral and Cell(3) is a Cell⟦NaturalNumeral⟦1, 10, 3⟧⟧; a reversal to that library’s numeral types would give a numeral a value when the program runs, an IntLiteral or a FloatLiteral, to which a coercion is applied at run time without the four numbers. The full reasoning is in explorations/coordinator/postmortem-2026-11-09-numerals/design-snapshot.md, explorations/compile-ladder/plan-30/probes/draft-numerals.md, explorations/reviews/literal-design-judgement-2026-11-08.md and explorations/compile-ladder/rung-static-numerals-spec/REPORT.md in the revival’s repository.

Effect

Both implementations convert a numeral where its place fixes a type and give it its default elsewhere. So x = 3 binds a ℤ32, and x ≣ z is true for z: ℤ32 = 3 on both, where the compiled path answered false; y: ℝ64 = 0.5 is strictly equivalent to a + a for a: ℝ64 = 0.25, q: ℚ = 0.5 binds 1/2, and 1/2 = 0.5 is true, where the interpreter answered otherwise (rows 943 and 944 of the revival’s gap ledger); a variable of type ℕ32 or ℕ64 takes a numeral, and one of type ℝ32 takes a numeral with one rounding, where the interpreter refused them (row 454); a variable bound from 3000000000 is a ℤ64 and reaches a declaration over ℤ64, where the compiled path stopped at run time (row 946); 7 passed to a parameter of type Object is a ℤ32 there (row 79); a numeral outside its type’s range is a static error, where the compiled path raised an exception at run time (row 325); a numeral at a declared floating-point type is rounded once, where the compiled code rounded it two or three times (row 862); and a nat parameter used as a value is a ℤ32, which a variable of type ℕ32 refuses, where the compiled type checker took it (row 486). round(2.50000000000000001) is 2, its numeral read as an ℝ64. A numeral that took its default prints as a value of its default type, so that “” 2.50 is “2.5”, and the team’s test ProjectFortress/tests/NumberPrintTest.fss, which asserted that a numeral prints as written, is changed. No value of a numeral type exists on either implementation when a program runs. The compiled path, which until it is built on the Fortress standard libraries compiles against a smaller library of its own, declares there the same numeral types, with coercions generic over the four numbers from NaturalNumeral at its five integer types, ℝ64 and ℝ32, and from RadixPointNumeral at ℝ64 and ℝ32; that library has no ℚ. The compiled code converts a numeral as written at a number type by that type’s coercion, whose body the compiler evaluates at the numeral’s four numbers with no knowledge of the type, into the constant that the class file holds; a value of another representation, as one of ℤ, and a value of a type of a program’s own come from one compiled method for each coercion from a numeral type, which takes the four numbers as values of type ℤ and which each place calls once, in the initialization of the class of the component that holds the place, before the program runs, the type’s prefix − on a negated numeral with it; so a coercion that throws an exception stops the program. The compiled program initializes the class of its component, and after it the class of each component whose declarations it uses, directly or through another component, before the program runs, inside a task on a pool of one thread of its own, so that a coercion whose body spawns a task, as an operator applied to two calls may, fills its place; the tasks that a coercion spawns there run one after another. A signed constant at a number type of the Fortress standard libraries is converted from its exact value on both implementations, outside the coercion, so that no coercion from a numeral type receives a sign. The interpreter, which has no static types, applies a coercion from a numeral type at the place’s first evaluation, with the four numbers bound as values of type ℤ, and keeps its result for the place; it refuses a numeral only when the place is evaluated: one outside an integer type’s range, one that rounds to an infinity of ℝ64 or ℝ32, one at a type that declares no coercion from the numeral’s type or whose coercion’s where clause the numeral does not meet, a negated numeral at a type without a prefix −, a folded constant at a type of a program’s own without a coercion from the constant’s default type, and a numeral bound to a variable declared of a numeral type. It refuses when it loads a program a numeral type written as a type that an object or a trait extends, or as a static argument. It converts a numeral at a parameter of the declaration that a call chooses, at a variable or a field of a declared type and at a declared return type, but not one passed through a tuple or a varargs parameter (rows 395 and 511). The compiled type checker does not apply the rule that a numeral type is written only as a parameter type to the libraries’ own files. A numeral type declares no = with a number type, so a numeral compared by = with a number of a type that declares no = with the numeral’s default type meets the top-level = of the Fortress standard libraries, whose parameters are of type Any and which takes the numeral at its default: the interpreter answers u = 0 false, and u ≠ 0 true, for a zero u of ℕ32, ℕ64 or ℝ32, none of which declares = with ℤ32 (rows 966 and 973 of the revival’s gap ledger; the expected failure ProjectFortress/tests/XXXNumeralEqualsNumberWalk.fss asserts true), and whether u = 0 is true is open; the compiled path’s own library declares no = over Any, and declares = and ≠ on each integer type with an operand of that type, into which the numeral is converted, so that there u = 0 is true and u ≠ 0 false for a zero u of ℕ32. The implementations depart from the text in these further ways, each with its row of the revival’s gap ledger: a numeral with a radix point keeps only one of its leading zeros in its digit count, as the parser gives the numeral to both implementations (row 960); the interpreter loads and runs a program that writes a numeral type in a comprises clause (row 981); the compiled path keeps a numeral’s own type, NaturalNumeral⟦n, r, v⟧, at the selector of a typecase (row 963); at a place whose type names a type parameter of its generic declaration, as m(): Gen⟦T⟧ = 3 in object Box⟦T⟧, the compiled code applies the coercion at each evaluation of the place (row 957); where a nat or int parameter of 231 or more, other than one of a numeral type’s four numbers, is used as a value, the compiled path stops with an error that no catch sees, and the interpreter makes it a ℤ64 (row 962); and both leave an expression of numerals alone as written where the form of its result needs a prefix − or a / that its component writes nowhere (row 956). No line of the revival’s model program changes, and by reading none of its numerals changes its value.

I.1.51 A string literal as one object

Affected sections

Section 13.1; Chapter 11; Section 13.27; Section I.1.41.

Change

Section 13.1 says that two string literals of the same text denote one object, so that every evaluation of a string literal with a given text yields the same string; that a string that a program builds as it runs is another object than a literal of the same text, unless the operation that builds it answers an existing string; and that a concatenation of string literals is a string literal. The opening of Chapter 11 says the same of strict equivalence. Each passage gains a box, and so does the paragraph of Section 13.27 on the concatenation of literals, which says that it is built. The effect of Section I.1.41 gains a sentence.

Rationale

This change does not follow from route A; the revival decided on 8 November 2026 that two string literals of one text are one object, on both implementations, and that a concatenation of two string literals is folded into one literal. Strings remain reference objects, whose equality of text is their own = (Section I.1.41). Every source of the team that speaks of literals makes equal literals one value: the Working Draft’s “Literals are values; they do not require evaluation” (Specification-1.0-frozen/basic/expressions/literals.tex, lines 25–26); the team’s restart of 2012, “All literals represent value objects” (Documentation/Specification/Prose/Language/Expressions/literals.tick, line 29); and the team’s compiled test ProjectFortress/compiler_regressions/seqv.fss, line 22, which expects “cat” to be strictly equivalent to “cat”. Java, Kotlin, Scala and Clojure, whose strings are Java strings, give equal literals one object. The concatenation is the Working Draft’s own sentence, which neither of the team’s implementations built. A reversal would have each evaluation of a string literal construct a new string, so that two literals of one text are never strictly equivalent, and would leave a concatenation of literals to be computed when it is evaluated. The full reasoning is in explorations/reviews/literals-2026-11-08.md, sections 6.1 and 6.4, in the revival’s repository.

Effect

On both implementations “ab” ≣ “ab” is true, as is one literal evaluated twice, and so are (“foo”‖“bar”) ≣ “foobar” and (“a”‖‘b’) ≣ “ab”, where the interpreter answered false, and so did the strict equivalence that the compiled code gives the values of the Fortress standard libraries (row 945 of the revival’s gap ledger); the compiled path’s own library answers by text (below). A string built at run time is not strictly equivalent to an equal literal, unless the library’s operation answers the string it was given, as a substring that spans its whole string does on both implementations. The literals of the Fortress standard libraries are strings of this kind too, so that an empty substring, which the Fortress standard libraries answer with their literal “”, is strictly equivalent to “”. The interpreter interns the text of each literal, and compares two flat strings strictly by the identity of the Java strings that they carry; the compiled code loads each literal as the Java Virtual Machine’s interned string, and its strict equivalence compares the Java strings that two of its string values carry by identity. The concatenation is folded in the desugaring that both implementations run before the static check. The compiled path’s own library, until the Fortress standard libraries replace it, answers its own ≣ on two strings by their text (row 908).

I.1.52 Passages not yet revised

No passage that instantiation exclusion or the reorganized numeric types contradict is known to be unrevised. The rule by which a generic call over two different integer types infers the narrowest type that both coerce into is written into Chapter 20 together with its implementation (Section I.1.26); the passages that chapter left unrevised, the sentences of Chapter 15 by which static parameters were inferred before the applicability of a declaration was checked and before declarations were compared, the implicit bound of Section 12.1, and the rule of Chapter 24 on a naked type parameter of bound Any, are revised with the overloading chapters (Section I.1.30, Section I.1.31). The instance of a nat or int parameter of a declaration that a call reaches only by dispatch, where nothing fixes it at run time, is not described; the rule of Section 15.5 is for type parameters (row 446 of the revival’s gap ledger). The sentence of Section 12.6 that a where-clause variable may not appear as a static argument in an extends clause also refuses a variable that a constraint fixes to one type; whether it is to be narrowed is not settled. The Meet Rule for dotted methods (Section 24.4) asks for a declaration on the intersection of two parameter types; whether declarations that together cover the intersection satisfy it too is not settled. The type of a static call whose argument’s static type stands between two traits with comprises clauses, where its most specific declarations, or a declaration more specific than them that the call may run, have static parameters, is not given (Section I.1.35). Whether two parameter types exclude each other when the only static arguments at which they could meet are ones that a bound rules out is not settled: the compiled type checker takes them to exclude where the static argument that the two parameter types force is a named type that fails the bound, and where a static parameter that stands at the top of their meet, read as within its declared bounds, leaves the meet empty, as for row 713’s pair, which the interpreter refuses at load; it reads no bound of a static parameter that stands inside a static argument (Section 24.5). Whether a nat parameter, which may appear wherever a variable of type ℕ32 can (Section 12.2), may be a component of a range is settled (Section I.1.26): it converts to ℤ32 as an integer numeral does, so the static ranges of Section 13.16 and the examples whose ranges a nat parameter bounds stand as written. Before the number chapters were revised, this section said:

The number chapters, Chapter 33 (whose integers are Section 33.2) and Chapter 41, are not yet revised. Their nested tower, in which each integer type is a subtype of the rational one above it and each carries its algebra at its own type, and the conditional self-extension of RationalQuantity, are refused by instantiation exclusion, as the compiled type checker refuses the library’s nested tower today. I.1.53 Route C, the alternative not taken

The team’s 2012 patent applications (US 8,843,887 and US 8,898,632; Chase, Steele, Naden, Hilburn, and Luchangco) relax the rule for a self-typed parameterized trait: a type may be a subtype of several of its instantiations when they form a chain. The revival built that rule whole as an experiment and measured it. It closes the unsoundness that instantiation exclusion guards against only together with a rule on return types over every level of a chain and a change in how a call chooses among generic methods specialised to different instantiations: 188 lines of code in five files of the compiled type checker and code generator. Reversing route A for route C would also need a method per level of a chain in the code generator, work in the interpreter, a way past a stack overflow of the type checker on the self-typing clauses, and seven library declarations, besides undoing the reorganization of the library’s numeric types. Route C rescues none of the where-clause examples of Section 12.6 nor the Nothing of Section 39.2, each of which places one type below infinitely many instantiations, which no chain contains. Under route C the numeric chapters could have kept the nesting of their widths, and their original text, quoted in Section I.1.11 and the entries after it and kept in the Working Draft of February 2011, is route C’s for that nesting; route C rescues neither the refined number types nor RationalQuantity (Section I.1.11). The record of the experiment is explorations/reviews/mie-probes/route-c-experiment.md in the revival’s repository.
