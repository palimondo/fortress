# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- On microGPT-shaped array code boxing is the dominant representational cost, 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` in Java models of the program's three kernels, and nothing microGPT-shaped compiles: the compiler prelude lacks the array types, with `Array`, `Vector` and `Array3` undefined in `FlatArrays.fsi` (row 305, wider than row 72). On the interpreter, the only path that runs the kernels, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch and 0% number representation (JFR on `krows`). The two one-line runtime defects the probe found are fixed (rows 302, 303; the next two entries), and no array type goes into the compiler prelude: the arrays reach the compiled path with the one library (POSITIONS, the library route). A failed compile leaves a 0-byte jar in the bytecode cache (`perf-probes/kernels/REPORT.md`).
- The boxing probe's scalar-loop reading, 156× primitive Java with boxing about 2% of it, is of the tree before rung 0's two fixes (rows 302, 303; `compile-ladder/rung0/REPORT.md`); of the costs it named, `countedseqloop`'s boxed indices and closure call (about 7%) and the representational rest (about 30%) are unaddressed (`perf-probes/boxing/REPORT.md`).
- The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `compile-ladder/rung0/REPORT.md`).
- `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `compile-ladder/rung0/REPORT.md`).
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine: the same unmodified tree measured 13.0566 s and 8.8159 s in another session, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes.
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`), and its descriptor in a stamped class is `RTTIsize.of("<n>")` ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see "The checker and the one library" below): this no longer holds. The checker checks `nat` and `int` static parameters ("The compiled type checker checks `nat` and `int` static parameters" below), and a sized program loads and runs compiled ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half).
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** The Working Draft's `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:49`, kept in `Specification/basic-lib/convenience.tex:61-65` marked "Not allowed") stops on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`; `reviews/spec-refused-examples/probes/SpecNothing.fss` and its captures). Without that clause, `fortress compile` and `fortress walk` give the identical single error, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`; `reviews/spec-refused-examples/probes/SpecNothingNoExcludes.fss`). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause in either implementation. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at codegen — `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4093`) — but nothing reaches it. This is the mechanism behind the library's comment on its parametric `Nothing[\T\]`, "Obviously ought to be a non-parametric singleton when we get where clauses working" (`Library/FortressLibrary.fss:1449-1450`), and it is why both worlds must spell the empty case some other way.
- **An exported function fails exactly as an exported variable does when a component's name differs from the api it exports, and the failure is the repository's, not codegen's** (`compile-ladder/rung-export-var/`). `probes/FnApi.fsi`+`FnLib.fss`+`FnMain.fss` dies with `NoClassDefFoundError: FnApi`, alongside `P8Api$shared` and `P9Api$shared` (`explorations/compile-ladder/rung-export-var/probes/probes-preedit.txt:29,96,163`). Through the real entry points the divergence never reaches codegen at all: `fortress link P8Main` and `walk` on each of the three main components print "Could not find an implementation for API … on path" (`probes/link-and-walk-preedit.txt:4-9,45-60`), so both execution paths assume the api and its implementing component share a name. The assumption is `Linker.whoIsImplementingMyAPI`'s fallback to the api's own name (`ProjectFortress/src/com/sun/fortress/linker/Linker.java:72-76`) when nothing has been registered in its persisted map, and only the user can register one, by hand, through `LinkShell`'s `alink`/`clink` verbs (`linker/LinkShell.java:41-70`; `linker/README:28-40` describes the intended design). `Specification/basic/components/overview.tex:33-35` settles it — a reference to an imported api is "resolved to a component that exports that api" — and the team reserved the codegen half of the repair in three comments in one file (`CodeGen.java:411-441`, `:1856`, `:6599-6606`). Gated as an expected failure by `ProjectFortress/compiler_tests/XXXExportVarRungXLinked.test`.
- **A comment placed after a declaration that ends in an expression or a type becomes part of that declaration's source span and of the unambiguous name the parser derives from it** (`compile-ladder/rung-library-comments/probes/SpanAbsorb.fss` and `SpanAbsorb.txt`; ledger row 359). `createSpan` (`ProjectFortress/src/com/sun/fortress/parser/Fortress.rats:145-157`) trims back over space characters only. A declaration ending in `end` is unaffected. So a comment-only edit to the library is not neutral at the syntax-tree level: the library's comment-only edit widened three spans (the scalar block's first `-` in both files, `SUFFIX_SUM` in the `.fsi`), besides shifting every position below each insertion, and a before-and-after comparison of parse trees or diagnostics must map positions back first (`compile-ladder/rung-library-comments/parse-compare.sh`, `ast-compare.py`, `remap-lines.py`). No answer changed.
- **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees** (`explorations/compile-ladder/rung-int-semantics-walk/REPORT.md`, section 4.1): `throw new FortressError((FObject) Driver.getFortressLibrary().getRootValue(name))` from inside a `builtinPrimitive` method reaches `Evaluator.forTry` unchanged (`MethodClosure.java:85-86` has no `catch`) and matches `catch e IntegerOverflow`; `Int.overflow()` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Int.java:258-261`) is the helper and `WellKnownNames.integerOverflowException` the name. Measured by the 25 `overflows(...)` assertions of `ProjectFortress/tests/IntSemanticsRungI.fss`, whose helper catches nothing but `IntegerOverflow`. The natives that raise it: the shift, `GCD` and `LCM` natives of the integer rules ("The interpreter's integer rules" under Landed semantics), the eighteen fixed-width arithmetic natives, `^` and `CHOOSE` on the four fixed widths, `LCM` on `NN32` and `NN64`, and the narrowing checks `Int.rc` and `NN32.rc` (row 347 closed; "Under `walk`, fixed-width integer arithmetic raises `IntegerOverflow` when the result does not fit" under Landed semantics). The interpreter's mapping of every other Java exception is unchanged (`FunctionClosure.java:188-196`), so row 336's division by zero still ends the run.
- **The compiled run's class loader takes its first load of a name under the JDK's class-loading lock, and a generic arm's first load is safe on four threads** (`compile-ladder/rung-generic-runtime/REPORT.md` sections 1, 11, 12; row 417). `InstantiatingClassloader.loadClass` runs under `getClassLoadingLock(name)`, as the JDK's own `ClassLoader.loadClass` does (`compile-ladder/rung-generic-runtime/probes/jdk-loadclass-javap.txt:2-9`). No loader in the tree registers as parallel-capable, so that lock is the loader's own monitor, the one the JVM already holds when it resolves a class through the loader. The explicit loads, `RTHelpers.loadClosureClass`, `RTHelpers.getRTTIclass` and the union instantiation, are under it too. `history` is still written before `defineClass`, safe under the lock. Measured: `compiler_tests/FirstLoadThreadsRungG` fails 5 of 5 compiled runs at `FORTRESS_THREADS=4` without the lock and passes 5 of 5 with it (`compile-ladder/rung-generic-runtime/probes/threads-before.txt:10-14`, `threads-after.txt:10-14`). The gate's four-thread stage runs it as its fourteenth program. Cost: none measurable; against a loader without the lock, seven interleaved runs each at four threads, the medians differ by -42 to +62 ms on the thirteen `atomic` programs, whose runs take 270 to 1,400 ms (`compile-ladder/rung-generic-runtime/probes/lock-cost.txt`; nproc 4, Intel Xeon @ 2.10GHz, load 4.2 to 5.1, JDK 25).
- **Walk chooses between a generic declaration and another on their declared domains, so the order they are written in no longer decides** (`compile-ladder/rung-walk-dispatch/REPORT.md` section 5.1; POSITIONS, "The static-parameter sentence goes"; row 548). `OverloadedFunction.bestMatchInternal` keeps a candidate by `moreSpecificDeclaration` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/OverloadedFunction.java:1335-1342`). When one of two applicable declarations is a generic function or constructor with static parameters of its own, their declared domains are compared: the symbolic instantiation, each type parameter standing for itself with its bounds as supertypes, and a domain lies inside a generic one when walk's inference finds an instance holding it from values that carry only its types (`instanceHolding`, `:1291-1306`). Otherwise, as for two plain declarations, their instances' domains are compared. A functional method of a generic trait and a generic dotted method keep the instance comparison. `GenPlainSub`, `describe[\T extends Shape\](x: T)` beside `describe(x: Circle)`, prints `circle, generic, circle` in either order (`ProjectFortress/tests/DispatchDeclaredDomain.fss`), as the compiled run does. When the chosen generic declaration's instance, made by walk's inference with coercion and answer 8's promotion ("Under `walk`, a generic call's static arguments are inferred with coercion ..." under Landed semantics), converts an argument, the call converts and dispatches again through the overloaded function (`convertedCall`, `:1222-1239`), so `opz(z, w)` with a `ZZ32` and a `ZZ64` runs `opz(a: ZZ64, b: ZZ64)` (`ProjectFortress/tests/DispatchConvertedAgain.fss`); not for overloaded methods. The shared symbolic instantiation of generic functions and constructors is keyed by each static parameter's kind and bounds as well as its name (`GenericFunctionOrMethod.java:57-68`), so two overloads whose parameters share a name keep their own bounds (row 478, fixed; `ProjectFortress/tests/GenericOverloadBoundsApart.fss`); a `where` clause is not in the key (the team's TODO, `FGenericFunction.java:49-51`).
- **Walk's load check reads a generic declaration beside a plain one on declared domains, and covers an overlap through `comprises` clauses, where its parameter-by-parameter check refuses** (`compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.3 and 5.4; POSITIONS, "Conversions never change which declaration runs" and "The `comprises` passages read at the level of values (PLAN item 26, row 491)"; row 492, fixed). Both run only where the parameter-by-parameter check refuses (`OverloadedFunction.java:494-497`), so they refuse no set that check loads. For one own generic beside a plain declaration (`validOnDeclaredDomains`, `:692-721`): equal declared domains are refused; one inside the other is valid when the inner one's return type is below the outer one's with the generic's type parameters standing for themselves, which is sound for every instance and refuses the Types paper's `baz` pair (`ProjectFortress/tests/XXXGenericBesidePlainReturnRule.fss`); neither inside the other is valid when plain declarations below both cover the overlap, the generic read at its bounds and only when each type parameter is a whole parameter type with at most one bound naming no static parameter. For two plain declarations with an unrelated parameter pair (`overlapCovered`, `:799-808`), the overlap is distributed over the `comprises` clauses, excluding pairs dropped (`overlapPieces`, `:901-945`), and every combination of its parts must lie inside one declaration below both. The search refuses on a cycle, after 10,000 steps or 4,096 combinations, on a symbolic type, or when the clauses do not settle. The helpers are private to the load check; `FType.meet` and subtyping do not use them. Pairs of two generic declarations take the parameter-by-parameter check alone (Q4 = (1)), so row 159's renamed and swapped pairs are refused. Loaded: `O2Z64`, `O2Meet`, the Meet Rule's `comprises` example (`ProjectFortress/tests/ComprisesMeetWalk.fss`), `MeetViaExclusion`, the proof addendum's `CoverageReturnGood` in both orders (`ProjectFortress/tests/ComprisesCoverReturn.fss`), `BetweenTwoClosed` (`f(g) = 3`). Refused: `MeetViaExclusionNoV` (`XXXComprisesMeetUncovered`), `CoverageReturnBad`, on the return-type rule (`XXXComprisesCoverReturnWrong`), a generic declaration with two bounds beside the plain declarations that cover its overlap (`ProjectFortress/tests/XXXGenericBesidePlainTwoBounds.fss`, row 552), and the POPL 2019 paper's `ArrayList`/`List` set of three generic declarations (`ProjectFortress/tests/XXXOverloadExistentialMeetWalk.fss`, row 539). Walk checks no `comprises` clause's closure, so an object that extends two closed traits unlisted loads beside a covered set and runs the first-written of two incomparable declarations (row 551).
- **Walk instantiates a generic declaration declared to return `Any`** (`compile-ladder/rung-walk-dispatch/REPORT.md` section 3; row 157, fixed): `MakeInferenceSpecific.forAnyType` is a no-op like `forTraitType` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/MakeInferenceSpecific.java:72-75`). `peek[\X\](t: Tag[\X\]): Any` alone runs, and beside `peek(a: Any): Any` it is chosen for a `Tag[\Red\]` (`ProjectFortress/tests/GenericReturningAny.fss`); row 496's probe `PlainBesideZZ32` (`compile-ladder/rung-generic-runtime/probes/PlainBesideZZ32.fss`) prints `Marker[ZZ32]` under walk. The visitor has no case for 11 of the AST's 18 concrete type classes, of which only the dimension forms can be written as a return type.
## The checker and the one library

- The one library binds its natives with `builtinPrimitive("…")`: 424 live bindings in nine files (445 written, 20 inside comments, one `RR32` binding fewer since `RR32` became a sibling of `RR64`), 125 of them in `FortressLibrary.fss`, and the rest of the library is plain Fortress. Beside them, walk loads the Java classes of 32 objects of `native component`s by name and binds `true`, `false` and `Any` at start-up. The interpreter's glue classes take the evaluator's boxed values and cannot be reused by the compiled path; the compiler's natives are static Java methods over plain Java values, called through `import java`: 369 public static helpers in 25 classes of `nativeHelpers/`, which the compiler prelude's 366 native bodies call. Matched by owner, name and signature, then by operation: 147 of the bindings are bound on the compiled path already, so only their binding text changes; 61 have a helper that nothing binds yet, 25 of them under a name the compiler prelude binds to another helper, the 12 wrapping operators among them (row 348); 139 need a new static helper, written from 132 glue classes of about 0.7K lines; and 78 need something else, 36 methods of native I/O objects (`Writer`, `BufferedWriter`, `FileReadStream`, `FileWriteStream`, `Reader`) and 42 with no compiled analogue (reflection, `Thread`, the native arrays, the task trace). The prelude and what it imports hold 369 of the bindings. Every program's output needs the I/O objects: `println` writes through `stdOut`, a native `Writer` (`Library/FortressLibrary.fss:4249-4252`, `Library/Writer.fss:20-24`), so the first compiled program on the one library needs `Writer`'s natives. MicroGPT calls `nanoTime`, which needs a new helper (the compiled one returns `RR64`), imports `System`, whose top-level `args` calls `getProgramArgsPrim`, which has no compiled analogue, when the component loads (`Library/System.fss:28`), and its arrays reach `NativeArray`, which has none either. Source: `perf-probes/prelude/natives-shape.md` § 2, its scripts and every binding's class under `perf-probes/prelude/natives-shape/count/` (`classified.tsv`). The nine rungs that move walk onto the helpers are PLAN's phase 4, the natives; which construct is the one binding text is PLAN item 35 (the `import java` entry under The territory map).
- `fortress compile Library/FortressLibrary.fss` as it is: 1,417 errors, all in DISAMBIGUATE, all name collisions because both preludes are in scope; an artifact. With `FortressLibrary` made the prelude (a driver over `Shell`'s public entry points, no tracked file changed), disambiguation passes with zero errors (`perf-probes/prelude/REPORT.md`). The title was the first measurement of the checker against the library (`perf-probes/prelude/REPORT.md`).

Two obstacles the error counts do not show: the compile path's own `extends Object` pre-desugaring (`Shell.java:371-386`) adds 712 of the 960 checker errors in the prelude apis and 618 of 1,204 in the component under its own setting, rejecting every generic instantiated at a tuple type (row 412; the gate's stages run under the bound `Any` instead); and overload dispatch generation did not terminate on the nested library's exclusion graph (1,046 s, stopped by hand). On the flat library the dispatch generator finishes and the checker's figures are the gate's ("The true distance to the switch-over" below).

Theorem 4.1 keeps static uniqueness, a unique most specific declaration for every call (p. 11:15); the exclusion rule is [Anc-Same-Trait], a class that extends two instances of a trait extends an instance below both (p. 11:11), blanket for an invariant parameter; and [D-Method] keeps a covariant parameter out of parameter positions, so no self-typed algebra trait can be covariant (`Equality[\+T\]`; the recheck's § 1.1).
