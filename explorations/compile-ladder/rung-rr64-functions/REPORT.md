## 1. Where this belongs, and why here

The map's row for the numeric tower sends every prelude question to §4.2-4.3 of `explorations/coordinator/map/spec-to-implementation.md` (`spec-to-implementation.md:323`), whose table of the compiler prelude says `RR64` is "present, **flat**: … with `+`, `-`, `/`, `juxtaposition`, `DOT`, `^`, `MIN`, `MAX`, `SQRT` and the comparisons all declared on the trait itself (`CompilerBuiltin.fsi:412-441`)" (`spec-to-implementation.md:411`).

So the declaration site is `trait RR64` in `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi` and its body in `.fss`, and the same map says operator and functional-method declarations inside a compiler-prelude trait are the established shape, not an invention: "**yes** — the compiler prelude declares its own operators this way (`CompilerBuiltin.fsi:412-441`)" (`spec-to-implementation.md:356`).

The native side is equally settled: the compiler world's one Java-interop mechanism is `import java` over `nativeHelpers/`, read by `ForeignJava` with ASM and wrapped by `FortressTransformer` into `nativewrapper_cache` (`explorations/coordinator/map/modules-and-phases.md:441-449`, and the divergence table at `:483`, "Natives | `builtinPrimitive` + `interpreter/glue/` | `import java` + `nativeHelpers/` + `nativeInterface/`"); `spec-to-implementation.md:157` records the same for the feature row "foreign import".

Nothing about this rung touches a phase: the names are missing from the prelude, so every blocked file dies in disambiguation with `Variable <name> is not defined` (`explorations/compile-ladder/after/raw/tests/buffons.fss.compile` and six more), which is a library gap and not a checker or codegen gap. There is no phase already doing this work, which is the trap rung 7 fell into (`compiler/phases/PhaseOrder.java:57,142`); the one phase that could have interfered, `INTEGERLITERALFOLDING`, folds integer literals only and none of the thirteen deals in one.

## 2. Precedent search: has the team solved this here, and in how many ways

Four ways, and they do not agree. This matters, because the answer decides the return types.

**(a) The interpreter's api, on `trait Number`.** `Library/FortressLibrary.fsi:319-332` declares `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2(self, x: Number)`, `log`, `exp`, `floor` and `ceiling` returning `RR64`, the two enclosing operators `opr |\self/|` and `opr |/self\|` returning `ZZ64`, and `truncate` returning `ZZ64`. `round` is **not** in this api at all.

**(b) The interpreter's bodies, twice.** `trait Number` gives all thirteen a default body that forwards to `asFloat(self)` (`Library/FortressLibrary.fss:405-419`), and `value object Float` binds each one to a `builtinPrimitive` (`ProjectFortress/LibraryBuiltin/FortressBuiltin.fss:162-190`), including the `round(self): ZZ64` that the api omits (`:189-190`). The glue is `java.lang.Math`, one method each, in `ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Float.java:318-386`.

**(c) The interpreter's `trait QQ`, which follows the specification where (a) and (b) do not.** `Library/FortressLibrary.fsi:396-401` declares `floor`, `ceiling`, `truncate` and `round` on ℚ returning `ZZ` — the specification's ℤ — and `Library/FortressLibrary.fss:589` gives `round` a hand-written round-half-to-even body. That body is the precedent this rung follows for `round`.

**(d) The team's own draft for the compiler world**, commented out in the file being edited: `ceiling(self):RR64` and `floor(self):RR64` at `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:439-440`, with both natives already bound (`simpleDoubleArith.doubleFloor => jDoubleFloor`, `doubleCeiling => jDoubleCeiling`, `CompilerBuiltin.fss:212-213`) and already used by the enclosing operators of the same trait at `.fss:898-899`. Those two enclosing operators return `RR64` in the compiler world (`CompilerBuiltin.fsi:437-438`), where the interpreter's return `ZZ64`.

The in-file shape copied for the body is `opr SQRT(self): RR64 = jDoubleSQRT(self)` (`CompilerBuiltin.fss:900`, pre-edit), with its native bound in the `import java` block at `.fss:196-214`.

No corpus file competes for any of the thirteen names. `grep -rnE "(sin|cos|tan|asin|acos|atan|atan2|log|exp|floor|ceiling|truncate|round)[[:space:]]*\([[:space:]]*self"` over `ProjectFortress/tests` and every `*_tests/` directory returns nothing, and a declaration-shaped grep over the same eight directories returns only uses. This is the check rung 1 lost a cycle to (`library_tests/MaybeTest9.fss`'s own `trait Equality`); it is clean here. The one place the names are declared again is the target program itself, at the array level and deliberately overloaded with the scalar: `exp[\T extends Number, I\](a: Array[\T,I\]): Array[\RR64,I\] = a.map[\RR64\](exp)` (`explorations/apl/mg/FlatArrays2.fss:44-45`), which is why the scalar must be a functional method nameable as a bare `exp`.

## 3. The specification, read

`Specification/basic-lib/numbers.tex` is chapter 33, "Numbers", and it has exactly one section, "Rational Numbers" (`:12-17`); the ℝ types appear in it only as names inside the subtype lists of the ℚ family (`:37-90`). The four rounding methods are declared at `:457-462` and defined in prose at `:464-477`: `floor` "returns the largest integer that is not greater", `ceiling` "the smallest integer that is not less", `round` "returns the integer that is closest … but if this rational number is exactly halfway between two consecutive integers, then `round` returns whichever of the two integers is **even**", `truncate` "returns the ceiling … if it is negative, and otherwise … the floor", that is toward zero. `:464` and `:467` both say "likewise the enclosing operator", so the specification makes the named method and the bracket the same operation with the same result type.

**A correction to the brief.** CLIMB-BATCH-1.md section F says "the 'Real' numbers section of that chapter is commented out (`numbers.tex:920`)". There is no such section and no such line: the file is 566 lines long and has no second section, commented out or otherwise, and no file under `Specification/basic-lib` or `Specification/advanced-lib` reaches line 920 except `advanced-lib/binary.tex`. The chapter's many `%` lines are the ASCII sources of the typeset displays, as `explorations/coordinator/map/design-intent-sources.md:104` already records for `algebraic-constraints.tex`; they are not disabled text. The conclusion the brief drew from the wrong citation is nevertheless right — the specification has no chapter for the real types — but it is right because the chapter was never written, not because it was switched off.

For `exp`, `log` and the trigonometric functions the prose is silent in the sense that matters (no definition and no declaration), but it is not silent about their existence, and two passages are worth having on the record because they are the closest the prose comes: `Specification/basic/expressions/constant.tex:123-133` lists "`+`, `-`, `×`, `·`, `/`, `!`, `MIN`, `MAX`, `√`, `floor`, `ceiling`, `hyperfloor`, `hyperceiling`, `gcd`, `lcm`, `sin`, `cos`, `tan`, `arcsin`, `arccos`, `arctan`" as the operations that may combine numeric **static** expressions — naming six of the transcendentals in mathematical spelling (`arcsin`, not `asin`), defining none, and not naming `exp`, `log` or `atan2` at all; and `Specification/basic/dimensions.tex:214-215` presumes them as library functions — "Other numerical functions, such as `sin` and `log`, require dimensionless arguments."

Neither passage constrains a return type or an argument type, so for the nine non-rounding methods the precedent of section 2 governs, as the brief says.

**Rule 3 in passing.** Rows 314 and 316 of the gap ledger, and the comment at `ProjectFortress/library_tests/IntLiteralArithRung7.fss:30-31`, cite `Specification/library/apis/FortressLibrary.tex`, `…/CompilerLibrary.tex` and `…/CompilerBuiltin.tex`. That directory does not exist in this repository: the api renderings are `\input` files generated from the `.fsi` sources at spec-build time (`Specification/library/default-libraries.tex:27,39`), and the two `Compiler*` ones are not even among the inputs the spec build names. So an `(api listing)` citation under `Specification/library/apis/` is not merely circular in the sense of `Specification/library/structure.tex:25-31`; it cites a path that is not in the tree and cannot be opened. This rung cites no such path.

## 4. The four deviations, each a decision

**(i) `floor` and `ceiling` return `RR64`, where the specification says ℤ.** Alternatives: `RR64`, which is precedent (d) — the team's commented-out draft in this very file — and also precedent (a), the interpreter's method type; or `ZZ64`, which is the specification's ℤ and the interpreter's *bracket* type. `RR64` was chosen. The reason is not that the specification is silent; it is that the specification requires the method and its enclosing operator to be the same operation with the same result (`numbers.tex:464`, `:467`, "likewise the enclosing operator"), the compiler prelude's two brackets are already declared `RR64` (`CompilerBuiltin.fsi:437-438`), and changing a declared type the prelude already has is one of the two stops CLIMB-BATCH-1.md reserves. Declaring the methods `ZZ64` would have satisfied the specification's magnitude and broken its identity, leaving one trait in which `floor(x)` and `⌊x⌋` have different types. Declaring them `RR64` keeps the trait coherent and leaves a single pre-existing deviation, now written down as a ledger row rather than doubled.

**(ii) `round` and `truncate` return `ZZ64`.** No enclosing operator for either exists in the compiler prelude, so (i)'s constraint does not apply; `ZZ64` is both the precedent (`FortressBuiltin.fss:187-190`) and an integer type, which is what ℤ asks for. The alternative, `RR64` for symmetry with `floor` and `ceiling`, was rejected: it would deviate from the specification and from the precedent at once, for symmetry alone.

**(iii) `round` is built on `Math.rint`, not `Math.round`.** `Math.round` rounds an exact half toward positive infinity, which contradicts `numbers.tex:470-472`; `Math.rint` rounds an exact half to the even integer, which is that sentence. The interpreter's `Float$Round` is `Math.round(x)` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Float.java:382-385`), so this is a deliberate deviation from precedent (b) — taken because precedent (c), the team's own ℚ body at `Library/FortressLibrary.fss:589`, implements the specification's rule in Fortress, and because a gated interpreter test asserts it: `ProjectFortress/tests/RationalTest.fss:428` asserts `round(15/6) = 2`, that is `round(2.5) = 2`. The differential in section 6 shows `walk` answering `3` for the same value at `RR64`. Ledger row (provisional 329) carries the interpreter-side defect.

**(iv) `atan2` takes `x: RR64` where the interpreter takes `x: Number`.** The compiler world's `Number` is an empty marker (`CompilerBuiltin.fsi:96`, `spec-to-implementation.md:410`) and carries no arithmetic, and every binary declaration in the compiler world's `trait RR64` narrows the interpreter's `Number` parameter to `RR64` already (`CompilerBuiltin.fsi:419-435` against `Library/FortressLibrary.fsi:291-316`). So the type follows the file. The parameter **name** `x` is kept from the interpreter rather than renamed to the file's usual `other`, because for `atan2` the name carries meaning: `self` is the *y* coordinate and the argument is the *x* coordinate, which is what `Float.java:334-337` computes (`ATan2 extends RR2R`, `f(y, x) = Math.atan2(y, x)`, with `RR2R.applyMethod(FObject x, FValue y)` at `:86-92` putting `self` first).

**A fifth decision, about the natives' home.** The eleven new static methods went into `ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleDoubleArith.java`, the team's own file, rather than into a new file beside it as rung 7 did with `simpleIntLiteralArith.java`. The criterion is the one that made rung 7 split: its helper dealt in a Fortress type and needed a clause in `NamingCzar.fortressTypeForForeignJavaType` (`ProjectFortress/src/com/sun/fortress/compiler/NamingCzar.java:341-343`). These eleven deal in `double` and `long`, which the generic path maps without a clause (`NamingCzar.java:441-446`, `s(Type.LONG_TYPE, fortLib, "ZZ64")` and `s(Type.DOUBLE_TYPE, fortLib, "RR64")`), and they are the same kind of one-line wrapper over `java.lang.Math` as the file's existing `doublePow`, `doubleSQRT`, `doubleFloor`, `doubleCeiling` and `doubleAbs`. A new file would have split the double primitives across two files with no criterion. Worth noting for the next rung that touches this: `doubleTruncate` and `doubleRound` are the first natives in the tree that take a `double` and return a `long`.

**A sixth decision, about the test's assertions.** The comparing `assert` has no `RR64` form — rung 4 added `ZZ32`, `String` and `Character` only (`Library/CompilerLibrary.fsi:45-49`) — and this rung did not add one. The alternative, adding `assert(x: RR64, y: RR64)` and `assert(x: RR64, y: RR64, failMsg: String)` to `CompilerLibrary`, was rejected for two reasons: rung T of this batch is editing `CompilerLibrary` in the same wave, and batch rule 1 keeps the merge clean by keeping the rungs' declarations disjoint; and floating-point assertions want an epsilon rather than `=`, which a comparing `assert` cannot express. The test therefore uses the Boolean form over `opr =` for the exact cases and over a local `near` for the inexact ones, and `.asZZ32` into rung 4's `ZZ32` form for `round` and `truncate` — the same idiom as `ProjectFortress/library_tests/IntLiteralArithRung7.fss:58-70`.
