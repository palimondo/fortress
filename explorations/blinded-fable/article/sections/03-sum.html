3. Summation, and how a user type joins the ∑ big operator

Everything else in a transformer is sums of products. Python writes sum(wi * xi for wi, xi in zip(wo, x)); the mathematics writes a ∑ with its index below. Fortress has ∑ as a big operator: SUM[i <- g] e (typeset ∑i←g e) desugars into a call of the generator's generate method with a reduction object — an associative join and an identity empty. The library defines that reduction for numbers only (opr SUM[\T extends Number\]()), and the Number trait is sealed (comprises { RR64 }), so a user type such as Value cannot simply become a Number.

{{math:sum}}

What the language does provide is (a) the reduction protocol as ordinary library code, and (b) an except clause on the implicit import of the standard library. Hiding the library's nullary ∑ and defining a CommutativeMonoidReduction over Value makes ∑ available to autograd scalars with exactly the semantics of the mathematics — a monoid with identity 0 — while the library's ∑ over plain numbers is no longer visible in this component (the model never needs it):

import FortressLibrary.{...} except { opr BIG + }
{{fig:gpt_sum}}

Two details are worth knowing. The nullary form opr SUM() is what SUM[gs] body desugars to (the interpreter names the accumulator BIG + internally, hence the except spelling); the prefix form opr SUM(g) serves SUM xs on a whole list. And the identity element is node(0): like Python's built-in sum, which starts from the integer 0 and wraps it in a Value, a summation may add a zero leaf to the graph; it changes nothing numerically and the gradient flows through it correctly. Where the reference sums sequentially (a left fold), a Fortress reduction combines terms in whatever order the generator chooses — the differences this produces are the rounding-level discrepancies reported in section 7, and they are the price of not suppressing the language's parallelism.

A second question the exploration answered: could one ∑ serve scalars and vectors, as it does on paper (yt = ∑s αts vs)? A reduction over an Additive trait with an explicit Zero runs correctly for both in the interpreter, but the static type of such a sum is Additive, not Value or Vec: it works dynamically but a type checker would demand a cast, so it is shown as an alternative in section 9, not used.
