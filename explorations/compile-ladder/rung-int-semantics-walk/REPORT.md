## 4. What changed, and why each shape

### 4.1 The catchable throw, measured first

No interpreter native raised a Fortress exception before this rung (`grep -rn "FortressError\|getRootValue" ProjectFortress/src/com/sun/fortress/interpreter/glue` finds only `Reflect.java:65-72`, which looks up constructors), and the brief asked for the route to be measured before the check could stay in Java. The path: a native method is applied by `MethodClosure.applyMethod` (`interpreter/evaluator/values/MethodClosure.java:85-86`) with no `catch`, so a `FortressError` thrown there reaches `Evaluator.forTry` (`interpreter/evaluator/Evaluator.java:1323-1324`) unchanged, which hands the wrapped object to `handleException` to be matched by type. `Int.overflow()` (`glue/prim/Int.java:256-259`) builds it as `Evaluator.java:224-226` builds the try-atomic failure: a root value of the library, from `Driver.getFortressLibrary()` (whose own comment, `interpreter/Driver.java:61`, reads "Native code sometimes needs access to the library component wrapper"), wrapped with the one-argument `FortressError(FObject)` (`exceptions/FortressError.java:31-34`), which had no caller until now, since a native has no location or environment to give. **Measured: it arrives catchable.** Every `overflows(...)` assertion of the test passes, and its helper's only clause is `IntegerOverflow => true` (`IntSemanticsRungI.fss:6-12`), so the fallback of a Fortress-body `throw IntegerOverflow` was not needed. The interpreter's general mapping of other Java exceptions (`FunctionClosure.java:188-196` wraps any other `RuntimeException` of a native function in a `ProgramError`) is untouched, so the stop the brief names does not arise.

**Decision: the name is a `WellKnownNames` constant** (`compiler/WellKnownNames.java:86`, `integerOverflowException = "IntegerOverflow"`), beside the six exception names already there (`:80-85`), as `StringPrim.java:130-133` looks up `WellKnownNames.varargsFactoryName`. The alternative, a string literal in `Int.java`, would have kept the edit inside the manifest's file list; it was rejected because the interpreter's shape for "a library name the Java side looks up" is the constant at every site (five in `Evaluator.java`, one in `StringPrim.java`). The cost is one more 2012-tree file, on the `historical:` line.

### 4.2 GCD and LCM

`Int.gcd`'s zero case returned its other argument unnormalized (base `Int.java:253`); it now returns the magnitude (`Int.java:292`), and the function's existing convention that `Long.MIN_VALUE` stands for `2^63` (it negates and then shifts with `>>>`) is kept. `Int$Gcd` throws when the magnitude exceeds `Integer.MAX_VALUE` (`Int.java:134-140`), `Long$Gcd` when it is negative, i.e. `2^63` (`Long.java:148-154`). `LCM` on both widths goes through one new helper, `Int.lcm` (`Int.java:274-284`), which follows the compiled body (`CompilerBuiltin.fss:616-619`, `if (self = 0) OR (other = 0) then 0 else (|self| DIV (self GCD other)) DOT |other|`): zero first, then `|u / g| * |v|` by `Math.multiplyExact` (Java 8, and the JVM's own spelling of the check, as the batch record notes at `CLIMB-BATCH-3.5.md:36`), with the two operands whose magnitude has no `long` tested before `Math.abs`. `Int$Lcm` then range-checks to `int` (`Int.java:142-148`).

**Decision: `MIN GCD MIN` and `MIN LCM MIN` throw too.** The brief's list stops at `MIN GCD 0`, `0 GCD MIN`, `MIN LCM ±1` and `5 LCM MIN`; `MIN GCD MIN` (`2^31`, resp. `2^63`) and `MIN LCM MIN` are the same unrepresentable results reached with both operands at the minimum, measured wrapping on the base tree (`probes/IntSemProbe-before.txt:86`, `:89`, `:106`, `:109`), and the rule cannot be applied to half of them. `MIN LCM 0` is `0` (spec `:529`) and not a throw, although `MIN GCD 0` throws: the zero test comes before the divisor is computed, as in the compiled body.

`Int.rc` is untouched, as the brief requires (row 347 stays open). Its callers after this rung are `Int$Choose` (`Int.java:152`) and `Int$Pow` (`Int.java:225`); see section 9 on the brief's "two exponentiation callers".

### 4.3 The fixed widths, and how the count is read

Each of the four shift pairs gains one line before the existing one; `Int$LShift` (`Int.java:180-185`), for example, is `if (v < 0) return (v > -32) ? (u >> (int) -v) : (u >> 31);` followed by the original `((v & ~31) == 0) ? (u << (int) v) : 0`. The comparison with `-32` (`-64`) precedes the negation, so `Long.MIN_VALUE` is never negated. `NN32` and `NN64` shift right logically and saturate to `0` both ways (`NN32.java:183-195`, `UnsignedLong.java:184-196`).

**The `NN64` question, established.** `UnsignedLong$LShift` took its count through `UU2U`, whose `applyMethod` reads `y.getNN64()` (base `UnsignedLong.java:88-94`). Through that `long`, a negative count and a large unsigned one cannot be told apart: `FInt.getNN64` and `FLong.getNN64` return the signed value unchanged (`evaluator/values/FInt.java:36-39`, `FLong.java:37-40`), so a `ZZ32` count of `-1` and an `NN64` count of `2^64-1` both arrive as `-1L`, and `Long.MIN_VALUE` as a `ZZ64` count and `2^63` as an `NN64` count both arrive as `Long.MIN_VALUE`. **They can be told apart one step earlier, by the class of the count's value**, which is `FNN64` for an `NN64`. The same ambiguity sat in `Long$…` (`y.getLong()` of an `FNN64` is its raw bits) and in `BigNum`'s `ZL2Z`; it was harmless while every negative count saturated, and this rung's negative-count rule would have made it wrong (`-3 LSHIFT` an `NN64` count of `2^63` would have become a right shift, `-1` instead of `0`). So the count is read once, by `Int.shiftCount(FValue)` (`Int.java:261-272`): an `FNN64` of `2^63` or more as `Long.MAX_VALUE` (a count beyond every width), an `FBigNum` exactly when it fits a `long` and clamped to `Long.MIN_VALUE`/`Long.MAX_VALUE` when it does not (exact for every width, and for `ZZ`, whose values the JVM limits to `2^31-1` bits), anything else by `getLong()`. The guards are asserted at `IntSemanticsRungI.fss:73-76`.

Precedent for the shape: each natives file declares small abstract classes named for their Java types, with a shift-only one where the count's reading differs: `ZL2Z` in `Int.java:90-96` and `BigNum.java:102-108`, `NL2N` in `NN32.java:95-101`, each extended by the two shifts alone (`grep -n "extends ZL2Z\|extends NL2N"` finds only the shifts, plus the dormant `ZZ32.java`). Their `applyMethod` now calls `shiftCount`. `Long.java` and `UnsignedLong.java` had only the shared `LL2L`/`UU2U`, so each gains a shift-only twin, `LC2L` (`Long.java:104-110`) and `UC2U` (`UnsignedLong.java:96-102`), "C" for the count; the alternative, extending `NativeMeth1` directly as the `Pow` classes do (`Int.java:218-228`), was rejected to keep the four pairs one shape.

### 4.4 The unbounded ZZ

`BigNum$LShift` and `$RShift` (`BigNum.java:225-235`) call one helper, `shiftLeft(BigInteger, long)` (`BigNum.java:237-250`); `RShift` negates the count, mapping `Long.MIN_VALUE` to `Long.MAX_VALUE` first (both are beyond any `BigInteger`'s width, so the answer is the same). A negative count of magnitude up to `Integer.MAX_VALUE` is a `BigInteger.shiftRight`, a floor, as the spec's `shift` requires; beyond it the answer is `0` or `-1` by sign; zero shifted is zero; a positive count beyond `Integer.MAX_VALUE` on a nonzero value raises `IntegerOverflow`, and so does the JVM's own `ArithmeticException("BigInteger would overflow supported range")` for a count inside the `int` range whose result exceeds `BigInteger`'s limit (measured with a throwaway Java probe on JDK 25: `3 << 2147483645` succeeds with bit length `2147483647`, `3 << 2147483646` throws), caught at the call and translated.

**Decision: `IntegerOverflow`, catchable.** The brief left the exception to the rung. The alternatives were the raw `ArithmeticException` (uncatchable under `walk`, row 336's shape, and what the base tree already did for counts inside the `int` range), a `ProgramError` through `error(...)` (uncatchable, row 347's shape), or a new exception type. The spec's rule is that an integer result that does not fit throws `IntegerOverflow` (`opr-overview.tex:154-155`); `ZZ` has no width of its own but the JVM gives it one, and Pavol's principle is not to fight the JVM where it precludes an implementation; `IntegerOverflow` is the one exception the library has for "an integer result that does not fit". Translating the JVM's own check rather than predicting it keeps the limit the JVM's.

### 4.5 ZZ64.narrow

`Long$FromLong` is `(int) x` (`Long.java:248-252`), as `UnsignedLong$FromLong` (`UnsignedLong.java:240-243`) and `BigNum$ToZZ32` (`BigNum.java:282-285`) already were.

## 5. The `shift` declaration: the collision, and the renames the specification requires

The brief (`CLIMB-BATCH-3.5.md:46`): "The name is new at top level; the library's other shift is the array-origin dotted method (…), and a collision with it is a stop." The declaration is written as the brief says: `shift(self, k:AnyIntegral): ZZ` in `trait ZZ` of `Library/FortressLibrary.fsi` (`:544`), and in the component `shift(self, k:AnyIntegral): ZZ = builtinPrimitive("com.sun.fortress.interpreter.glue.prim.BigNum$LShift")` after `RSHIFT` (`Library/FortressLibrary.fss:885-886`). **Alone, it collided, not with the dotted method, but with every declaration of a parameter or local named `shift` in a component that sees the library**, and every `walk` run then failed before the program started. The five layers, measured in the first round with the declaration in place (the line numbers are those of the landed tree, one line below the base tree's in `FortressLibrary.fsi` and two below in `FortressLibrary.fss`, because the declaration and its body precede them):

- `probes/shift-collision-layer1.txt`: 12 × `Variable shift is already declared.`, at `Library/FortressLibrary.fsi:2081-2084` (the `Range` trait's `shiftLeft(shift: I)`, `shiftRight(shift: I)`, `opr <<(self, shift: I)`, `opr >>(self, shift: I)`) and `Library/RangeInternals.fsi:194-195`, `:263-264`, `:323-324`, `:431-432`.
- With those twelve renamed (to `amount`, in a trial only), `probes/shift-collision-layer2.txt`: 6 more, at `Library/FortressLibrary.fss:3670-3673` and `:3688-3689`; then `probes/shift-collision-layer3.txt`: 30 more in `Library/RangeInternals.fss`, from `:454` to `:1357`; then `probes/shift-collision-layer4.txt`: `Library/List.fss:311`, a local `shift = start - firstUsed`; then `probes/shift-collision-layer5.txt`: clean (its two errors are the probe program's own, below).

The rule is the disambiguator's `checkForShadowingVar` (`ProjectFortress/src/com/sun/fortress/scala_src/disambiguator/ExprDisambiguator.scala:745-763`): a variable may not shadow any variable or function in scope, and an imported api's functional methods are in scope in every importer. It is not peculiar to `shift`: `probes/ShadowEven.fss` binds a parameter `even` and a local `numerator`, both functional methods of the library's `ZZ` today, and on the unedited library gets `Variable even is already declared.` and `Variable numerator is already declared.` (`probes/ShadowEven.txt`). The specification makes the collision real at least inside the library's own component: "It is also a static error for multiple declarations with overlapping reaches to declare the same name in the same namespace unless the declarations are overloaded or one declaration shadows the other" (`Specification/basic/declarations.tex:426-432`); a parameter is not among the declarations that may shadow ("No other shadowing is permitted in a Fortress program", `:533`, after the list at `:476-529`); and "The reach of a functional method declaration is the component containing that declaration" (`:435-436`), which takes in `FortressLibrary`'s own `Range` trait. A parameter's own reach is its functional declaration (`:459-461`), so the reaches overlap. For the importing components (`RangeInternals`, `List`, a user's program), "the reach of any top-level declaration (including any imported declaration) is the component containing (or importing) that declaration" (`:454-456`), which is the reading the implementation, shared by both paths, enforces.

**What it cost.** The landed edit is the first round's trial patch unchanged (`probes/route-i-trial-patch.txt`, applied with `git apply` in commit `fafc4eb75`): the declaration and its body (one line in the api, two in the component), and 49 declarations of a parameter or local named `shift` renamed to `amount`: 4 in `Library/FortressLibrary.fsi` (`:2081-2084`), 6 in `Library/FortressLibrary.fss` (`:3670-3673`, `:3688-3689`), 8 in `Library/RangeInternals.fsi` (`:194-195`, `:263-264`, `:323-324`, `:431-432`), 30 in `Library/RangeInternals.fss` and 1 in `Library/List.fss` (`:311`), 71 changed lines over the five files with the uses in their bodies. After it, `grep -rnw shift` over `Library/*.fss`, `Library/*.fsi` and `ProjectFortress/LibraryBuiltin/*.fs[si]` shows only the array-origin dotted declarations (`Library/FortressLibrary.fsi:1294`, `:1317`, `:1337`, `:1417`, `:1447`, and two more the brief's list does not name, `Array2`'s at `:1557` and `Array3`'s at `:1688`, all inside trait declarations) with their component bodies and one call (`FortressLibrary.fss:1757`), the new declaration and body, and six comments in `Library/CompilerLibrary.fss`. The renames change no type and no declaration a gated test names (`shiftLeft`, `shiftRight`, `<<` and `>>` keep their names and types), and the renamed parameters are positional, not the keyword-parameter declarations of `Specification/basic/declarations.tex:243-244`, so no call site names them. Measured on the landed tree: the test prints `PASS` (`test-after.txt`); `tests/subArray.fss`, the corpus's one caller of an array's `.shift(`, and the tests of the renamed `Range` and `ArrayList` code pass under the harness (`probes/harness-shift-landed.txt`, section 8), so the dotted method does not collide, as `declarations.tex:416-425` predicts for a name after a `.`; the checker count stays 103 (`probes/checker-count-after-shift.txt`). It makes `shift` a name no `walk` program may bind, as `even` and `numerator` already are; section 8 measures that cost at zero files.

## 6. Two further defects found, and repaired

### 6.1 A `ZZ` count crashed every fixed-width shift

Every fixed-width shift declares its count `AnyIntegral` or `ZZ64` (`Library/FortressLibrary.fss:637-638` on `Integral`, and the overrides), and `AnyIntegral` comprises `ZZ`, but the natives read the count with `getLong()`, which on an `FBigNum` throws unconditionally (`evaluator/values/FBigNum.java:48-50`, "might not fit in ZZ64"): `widen(3) LSHIFT big(widen(3))` ended the run with `ProgramError: Value 3 might not fit in ZZ64.` (`probes/run-enders-before.txt`, case 7; a `ZZ32` receiver reaches `Long$LShift` by dispatch, case 8). `Int.shiftCount` reads it exactly, and the two now answer `24` and `-1` (`probes/run-enders-after.txt`). **Decision: repaired here**, because the count reader this rung needed anyway is the fix; the alternative was a ledger row. Home 1: `IntSemanticsRungI.fss:81-82`, cited to the declaration `FortressLibrary.fss:637`.

### 6.2 The `ZZ` natives read an `NN64` of `2^63` or more as negative

`BigNum.toB`, the receiver and argument conversion of every `BigNum$…` native, fell through to `BigInteger.valueOf(x.getLong())` for an `FNN64` (base `BigNum.java:41-49`), so `NN64 2^63 + ZZ 0` was `-9223372036854775808` and `NN64 2^63 = ZZ 2^63` was `false` (`probes/IntSemProbe-before.txt:66-68`), where `ZZ` "encompasses all finite integers" (`basic-integers.tex:15-16`). The same misreading made a `ZZ` shift by an `NN64` count of `2^63` a no-op (`:63-64`). `toB` now converts an `FNN64` exactly, in the spelling of the compiled world's `simpleArbitraryPrecisionArith.makeZZfromNN64` (`nativeHelpers/simpleArbitraryPrecisionArith.java:117-119`; `BigNum.java:46-48`). **Decision: repaired here**, because the `shift` declaration's route needs it and it is one branch in a file this rung edits; it changes the answer of any `ZZ` operator reached with an `NN64` operand of `2^63` or more, from wrong to right, and nothing else. Home 1: `IntSemanticsRungI.fss:94-96`.

## 7. The gated test that relied on the old LCM

The regression subset (section 8) turned up one red: `tests/RangePrototype.fss`, `FAIL: a dumpShow[\ZZ32\]: RightScalarRange(2,1)==...-2,-1,0,1,2] =/= a dumpShow[\ZZ32\]: LeftScalarRange(2,-1)==[2,1,0,-1,-2...;` for `(spec, curr) match for OpenScalarRange(1)==...o,o+1... and LeftScalarRange(2,-1)` (`probes/harness-regression-1.txt:6-8`). The test carries its own prototype of range intersection, `INTERSECTOLD` and `INTERSECTNEW` ("This is the current spec for INTERSECTION", `RangePrototype.fss:155`), and compares it with the library's (`:430-434`). Both prototypes compute `resultStride = this.stride LCM other.stride` (`:66`, `:171`), and `intersectUnbounded` takes its direction from the sign of `resultStride DIV other'.stride` (`:24-25`). With the old signed `LCM`, `(u / g) * v`, that quotient was `this.stride / gcd`, sign included; with `LCM` nonnegative it loses the sign whenever a stride is negative. The library does not depend on the sign: `RangeInternals.fss:513-517` flips negative strides before its `LCM`, `:442-445` restores the sign by hand, and its open-range case uses `GCD` (`:326-328`).

**Decision: the two lines now compute the signed stride the prototype means, explicitly**, `resultStride = (this.stride DIV (this.stride GCD other.stride)) DOT other.stride`, which equals the old `(u / g) * v` for the nonzero strides a range has (the `GCD` of two nonzero values is positive, and this rung does not change it there). No assertion changes; the test is green again (`probes/harness-RangePrototype.txt`, `OK (1 test)`). The alternatives were to stop (the brief lists `RangePrototype.fss:66` and `:171` under what must stay green; it does, with this edit), or to keep a signed `LCM` under `walk`, which the specification (`basic-integers.tex:528`) and Pavol's decision both rule out. `RangePrototype.fss` is a 2012-tree file and is on the `historical:` line.
