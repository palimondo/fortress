# Pavol's type decisions, read as one chain: the judgement

## 0. Words

Each term of type theory is defined here once, with a Fortress example where one helps; the verdicts use them without further definition.

- **Type, subtype.** A type is a set of values; `A` is a subtype of `B` when every `A` is a `B`. Under route A, `ZZ32` is not a subtype of `ZZ64` (F-131).
- **Trait, object, extends.** A trait is an interface that may carry method bodies; an object is a leaf type. `trait Vector[\T, nat s0\] extends { AnyVector, Array1[\T,0,s0\], AdditiveGroup[\Vector[\T,s0\]\] }` says every vector is an array and an additive group (`Library/FortressLibrary.fsi:1616-1618`).
- **Static parameter, instantiation, bound, F-bound.** `[\T\]` is a static parameter; `List[\ZZ32\]` an instantiation; `T extends Number` a bound. An F-bound names the parameter itself: `trait Integral[\I extends Integral[\I\]\]` (`FortressLibrary.fsi:447`).
- **Self-typed trait, self type.** A self-typed trait is one whose F-bounded parameter stands for the implementing type (`Integral[\I\]`, implemented by `ZZ32` at `I = ZZ32`). The self type is the further fact that, inside the trait, `self` is also an `I`. Scala declares it (`this: S =>`), Rust builds it in (`Self`), the team's compiled library spelled it `comprises T` (`Library/CompilerAlgebra.fsi:16`, `:24`).
- **Intersection.** `A & B` is the type of values in both. `Integral[\I\] & I` is the type P-146 gives `self` in a body.
- **Exclusion.** Two types exclude when no value has both: `trait Range[\I\] ... excludes { Number, String }` (`FortressLibrary.fsi:2182-2183`). The checker proves two overloads never both apply by exclusion.
- **Instantiation exclusion.** No type extends two different instantiations of one generic trait; so a nested number tower, in which `ZZ32` is `Equality` at five instantiations, is refused (F-44).
- **Domain, declared domain.** A declaration's parameter types; for a generic declaration, every argument type that some instance within its bounds accepts.
- **The three overloading rules** (the 2011 paper, POPL 2019 Fig. 5): No Duplicates (two declarations may not have equivalent domains), Meet (two overlapping domains exclude, or one is a subtype of the other, or a third declaration covers their intersection), Return Type (the more specific declaration's result fits the other's).
- **Existential reduction.** The way to decide whether two generic domains overlap: collect the equalities a shared value would force on their static parameters and solve them (P-152; POPL Fig. 6).
- **Coverage, closed trait.** `trait AnyIntegral comprises { ZZ, ZZ64, ZZ32, NN64, NN32 }` closes the trait: every value of it is of a listed type. A set of types covers a type when every value of the type is in one of them (P-60).
- **Conditional extension.** An `extends` entry that holds only under a `where` condition: `List[\E\] extends LexicographicOrder[\List[\E\],E\] where { E extends StandardTotalOrder[\E\] }` (`Library/List.fsi:67-68`; P-151, P-154).
- **Tuple type.** `(ZZ32, ZZ32)`, the type of a pair; the index type of a matrix. The Working Draft and the 2012 Types chapter both say a tuple type excludes every trait type (`Specification-1.0-frozen/basic/types-vals-vars.tex:214-215`, `:272-273`; `Documentation/Specification/Prose/Language/types.tick:341`, `:424`).
- **Coercion, promotion.** A conversion a type declares (`ZZ64`'s `coerce(z: ZZ32)`), inserted only where no declaration fits as written (P-46); promotion instantiates a generic call at the narrowest type into which all arguments coerce (P-74).
- **Sound; proof scope.** A type system is sound when a program the checker accepts cannot go wrong at run time in the ways its types promise. A paper's proof covers only the calculus it models; outside that scope the paper is silent, not opposed. POPL 2019's calculus is FGFV (`research/extracts/ParkPOPL2019-extract.md` §1).

Verdicts use three words. **Finishes**: the designers' latest word says this, or it completes what they left unfinished in the direction they pointed. **Departs**: against a designers' text, where their later word or the JVM requires it; justified or not. **Bends**: against a designers' text or design where they left a way the revival did not take.

## 1. The verdicts, in order of consequence

### V1. The chain bends in one place that matters: P-146's signature half forces P-157, and P-157 overrules the team's library on a conflict that is the checker's, not the library's.

P-157 gives up `Vector` and `Matrix` as additive groups because "the scalar block that microGPT uses (P-88) and the team's additive-group vectors cannot both pass the overload check while it reads a self-typed trait's `self` in a signature as the plain trait type (P-146)" (POSITIONS P-157). Four facts, each checked at its source, turn this from a library decision into a checker gap:

1. The pair is valid under the designers' own rules. A vector is an `Array[\T,ZZ32\]` (`Array1` extends `StandardMutableArrayType`, which extends `Array[\E,I\]`: `FortressLibrary.fsi:1591-1593`, `:1522-1523`, the same at `a874948ac:1435-1437`, `:1371-1372`) and an `AdditiveGroup[\Vector[\T,s0\]\]`. For a value to lie in both the scalar block's domain `(Array[\T,I\], T)` and `AdditiveGroup`'s `(AdditiveGroup[\V\], V)`, the second argument must be a `T` (a `Number`) and a `V`; its bounds make it an `AdditiveGroup[\T\]` and an `AdditiveGroup[\V\]`, so by instantiation exclusion `V = T`; the first argument is then an `Array` and an `AdditiveGroup[\T\]`, and by P-146's extender rule every `AdditiveGroup[\T\]` value is a `T`, a `Number`, which arrays exclude (`:1594`). The domains exclude. The two steps the checker's exclusion test lacks are exactly these: reading a parameter's bounds, and reading the extender rule's fact. The probe's `VecPairsC` says exactly this: the pair is "valid only by the self-type conformance" and "the overload check reads the plain trait type (P-146)" (`perf-probes/symbolic-operators-2/REPORT.md:166`); its left-hand mirror needs the exclusion test to read bounds, row 786's open gap (`:168`).
2. The team had both. At `a874948ac` the library declares `Vector ... extends { ..., AdditiveGroup[\Vector[\T,s0\]\] }` (`:1459-1460`) beside `opr +(x: Array[\ZZ32,ZZ32\], y: ZZ32)` (`:2537`). The evidence map's "the team never had both" (`evidence.md:217`, `:587`) is true only of the generic block; the team's concrete pair has the shape of `VecPairsC`, which the probe found refused, so by that reading, not measured on the team's library, the checker would refuse the team's own library. The conflict is between the team's library and the checker's exclusion reasoning, not between the revival's extension and the team's design.
3. The team's compiled world would have accepted it. Under the team's idiom `comprises T`, the checker types `self` in the signature as `(T[\U\] & {U})` (`XXX10k.test:13-29`, cited in `reviews/self-typed-bodies-judgement.md:20`), and with `self: AdditiveGroup[\V\] & V` the domains exclude at once. P-146 chose the intersection in bodies only and the plain trait type in signatures (POSITIONS P-146; `Specification/appendices/changes.tex:3949-3953`).
4. The two reasons for the signature half do not carry it. The first, that POPL 2019's proofs "assume that no declared type holds a type parameter inside an intersection", is the paper's Lemma 5.2 on type matching at run-time dispatch (`research/extracts/ParkPOPL2019.txt:1098-1107`); it is a silence about FGFV's syntax (declared types there have no intersections at all), and it bears on the dynamic dispatcher's completeness in phase 5, not on the static exclusion test of the Meet Rule, which is where the vectors' pair fails. The second, the 18 Return Type errors on `CMP` (`changes.tex:3997-4004`), was traced by the judgement's own measurement to a checker mechanic: `providedAndOverridden` pairs an overriding `CMP` with the one it overrides as equals and checks the Return Type Rule in both directions (`self-typed-bodies-judgement.md:197-202`; `STypesUtil.scala:1663-1671`, `OverloadingChecker.scala:672-674`). An override whose return type narrows is not a Return Type error; the errors are an artifact of the override check, not of the intersection.

So P-146's body half and extender rule finish a design the team pointed at (Naden's "only in bounds", `Papers/Types/journal/justificationOfRTR.tex:626-630`; the checker's own 2009 self type), while its signature half departs from the team's compiled idiom on a silence and an artifact, and that departure is the sole reason P-157 overrules the team's library and parks P-28's algebra further off. His yes to P-157 rested on the premise that his own extension was being reverted (`POSITIONS-history.md`, P-157's block; `evidence.md:215`). **P-157 should wait; the way back is a checker change, not a library change** (section 2, item 2; section 4, change 1).
