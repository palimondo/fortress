## Change A: the self type in the exclusion test

Entries: F-225, F-277 (its self-type half), P-146 and P-157 (its self-type half).

- **Default.** The orientation's own sentence "signatures keep `T[\X\]`" (`revival-changes.md:40`). From it a reader concludes that a functional method of a self-typed trait, such as `AdditiveGroup`'s `abstract opr +(self, other: T): T` (`Library/FortressLibrary.fsi:264-269`), has the domain `(AdditiveGroup[\T\], T)` in every overloading rule. If so, it overlaps a declaration over an array and a number, because some array could be an additive group of another type. Java's F-bounded `this` reads the same way.
- **Correction.** The checker's test of whether two declarations exclude each other reads `self` as `T[\X\] & X` (P-157), as P-146's extender rule guarantees: every `self` is an `X`. Specificity, the Meet Rule, the coverage of a meet and the Return Type Rule keep the plain `T[\X\]`. So the library's generic scalar `+`, `-`, `MIN` and `MAX` between an array and a number stand beside the vectors' own `+` and `-`. An object that is an array of itself and an additive group of itself still lies in both domains, and the checker refuses that pair (`XXXExclusionSelfTypeSharedLeft`, `...Right`).
- **Path difference, one clause.** Walk refuses this shape at load in a program's own component (row 804). The full list of such cases is in `interpreter.md`, "What walk checks".
- **Mistakes prevented.**
  - Reshaping the team's library, or adding meets, to satisfy a pair that the checker accepts: taking `Vector` and `Matrix` out of `AdditiveGroup`, or dropping the arrays' scalar `+` and `-`.
  - Expecting the checker to refuse such a pair in new code. This comes up whenever the scalar block is extended by P-88's pattern.
  - Writing a walk test of this shape and expecting it to load.
- **Evidence.**
  - A failure on record. The probe's default was A2, "Vector and Matrix leave AdditiveGroup" (`explorations/perf-probes/symbolic-operators-2/REPORT.md:241`, section 5). Its alternative A3, the scalar `+` and `-` dropped, broke four revival tests and microGPT's `sm` (`:175`). Both bend the library for a gap of the checker. The curator overrode them: P-157's "Why" says that "taking vectors out of `AdditiveGroup` would have bent the team's design for a gap of the checker".
  - The landing's record lists `revival-changes.md:40` as a skill sentence made false (`RECORD.md`, rung X, "Lines on `main`", item 2).
- **For the writer.** Add one clause to the existing rule, naming P-157. Do not add a paragraph. The bound half of P-157 stays out of the orientation (see the F-277 row).

## Change B: `Index`, and a tuple of indices

Entries: F-278 and P-156.

- **Default.** No trait type holds a tuple, and an index type parameter needs no bound. The Working Draft says: "Every trait type also excludes every arrow type and every tuple type" (`Specification-1.0-frozen/basic/types-vals-vars.tex:215-216`) and "A tuple type excludes any non-tuple type other than `Any`" (`:272-273`). Both team implementations agreed, and the team's library declared `trait Indexed[\E, I\]` unbounded. In Java and Scala an unbounded type parameter is the norm. The pretraining quiz shows weak priors on tuples here: its guess "`Any` does not include tuples" was graded wrong (`explorations/reviews/fortress-pretraining-quiz.md:66`; `skills-distillation-audit.md:175`).
- **Correction (P-156).**
  - Every index parameter of the library's generic indexed types is bounded `I extends Index` (`Library/FortressLibrary.fsi:1249`, `:1270`).
  - `ZZ32` extends `Index`, and `Range` excludes it, so a subscript by an index and a subscript by a range never apply to the same value.
  - A tuple type whose element types are all `Index` types is an `Index`, on both paths and in the specification. So `m[i, j]` passes its tuple as before.
  - `Index` extends only `Any`, so such a tuple is still no `Object`, and `()` is no `Index`.
- **Mistakes prevented.**
  - Writing a generic over an indexed type's index parameter without the bound. Walk runs it, but the checker refuses it: "Ill-formed type: Array[\RR64,I\] The static argument I does not satisfy the corresponding bound Index." (`explorations/compile-ladder/rung-index-bound/REPORT.md:156`, section 6). Such code passes every walk test, then fails at the count stage, or for a program at the switch-over.
  - Overloading a function on `Index` beside one on a tuple of `Index` types, and expecting the two to exclude each other.
- **Evidence.**
  - A failure on record. The model program's own array helpers declare the index parameter unbounded: `explorations/run-c4/src/FlatArrays.fsi:15-21`, `explorations/apl/mg/FlatArrays2.fsi:68-73` and `:126`, and `explorations/apl/mg/AplMg.fsi:41`. Walk runs them, and the checker will refuse them once the compiled path reaches them (rung B's `REPORT.md:222`, section 11). No model line was changed.
  - The team's own `UniformDistribution[\T\]` had to take the bound (`Library/Random.fsi:260`; rung B's `REPORT.md`, section 9, decision 11).
  - Tried with the bound and without the tuple rule, the checker refused 73 tuple-index sites, and walk stopped with "** bug! Meet((Int,Int), Index) not a singleton: []" (`RECORD.md`, rung B, "The reason").
- **Departures to name by row.** The checker refuses a tuple expression at a parameter of type `Index` (row 805). Walk loads a function over `Index` beside one over a pair whose elements neither lie below `Index` nor exclude it (row 806).
- **Not for the orientation.**
  - Walk refuses a program's own top-level type named `Index` as ambiguous. That goes to `interpreter.md`, beside the core's reserved names.
  - `BoundedRange`'s `atMost` under `where { I extends Index }`, and `UniformDistribution`'s bound, go to `library.md`.
  - A type that extends only `Index` is an `Object` (F-259): no mistake is on record.
