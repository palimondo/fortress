# The POPL 2019 paper against the judgement: what changes

## In short

- The paper confirms the large calls: the exclusion rule kept, the tower flat, the 2009 overload sentence gone, the three rules, the return-type rule in the form batch 7b's rung C plans, applicability and specificity on declared quantified domains, and the implicit bound `Any`.
- It contradicts one default and one mechanism, both in batches not yet run or cheap to change: item 30's "least instance" is the 2012 rule the paper says the team could not prove and abandoned; the checker's binding of an unconstrained type parameter to `Bottom` (rows 447, 425, 516) is what the paper's model forbids outright. The paper's rule for both is the same sentence: instantiate at the intersection of the upper bounds, the declared bound and the call's static return type, never at the value's type alone and never at `Bottom`.
- It adds four things the record lacked: that rule; the exact form of the overloading rules with "existential reduction"; a restriction that its proof needs (a method type parameter may not appear in another's upper bound), which the library's `SUM`, `BIG MAX` and `Integral` families break; and a phase-5 requirement, that the dispatcher must know the call's static return type at run time.
- Three things should be done differently, all cheap: item 30's sentence in 7b's rung S and one test pair in rung C; the `Bottom` binding replaced by the bound in one checker rung, which replaces the "treat as a throw" fix the judgement recommended for row 447; row 516's union replaced by the bound. Nothing on route A, answer 9, item 26 or the conversion order changes.

## 0. What the record knew, and what the paper says

The record's account (`literature.md` § 1) was right as far as it went: the paper keeps the invariant-instantiation exclusion through its ancestor rule, moves the return-type check to run time, and has no self types and no numeric tower. What it did not have, each checked in the text:

- The instance rule. "The Fortress team had assumed, because it seemed from several working examples to be in accord with intuition, that once the tightest possible upper and lower bounds for a method type parameter have been found, then the union (or pseudo-union) of the lower bounds should be chosen as the type to be used for that type parameter. We considered this and the hybrid technique ... but we were unable to complete the proofs of correctness of both the techniques. Since the minimum requirement for a type to instantiate a method type parameter is that it satisfies all the lower and upper bounds of the type parameter, the dynamic dispatch algorithm presented here always chooses the intersection of the upper bounds." (§ 5.4, p. 11:25, lines 1274-1284.) The rule itself is [Solve-Step] (§ 5.2.3, p. 11:19, lines 965-1016): the substitution for a parameter is the intersection of its computed upper bound and its declared upper bounds, checked against the lower bounds; "Because g' is a ground type, the solving step never instantiates method type parameters with Bottom."
- The static return type at run time. Dispatch "seeks the most specific method declaration with a dispatchable instance that is applicable to the ilk of the arguments and whose return type is a subtype of the annotated static return type" ([R-Method], § 5.2.1, p. 11:17, lines 888-896); "the language semantics needs to make the static types of method invocations available at run time" (§ 2.3, p. 11:7, lines 329-331). The upper bound of a return-only parameter comes from that static return type ([Dispatch], line 875: `g match ρ - bounds`).
- The default bound. "By default, each type parameter has an upper bound Any and a lower bound Bottom" (§ 3.2, p. 11:9, lines 418-419). `Bottom` "is intentionally not expressible in the surface syntax" (line 438).
- The overloading rules in checkable form (§ 4, Figure 5, p. 11:13, lines 630-661): No Duplicates as non-subtyping of domains either way; Meet as exclusion, subtyping or a third declaration whose domain is equivalent to the intersection ([Meet-Third], line 645); Return Type as one universal subtyping check, `arrow(d1) ⊑ ∀[κ,κ']((α ⊓ α') → ρ')` ([Return-Test], lines 656-660). Specificity is subtyping of existentially quantified domains, "a sound approximation of the subset relation of applicable sets, [but] not complete" (§ 4.2, p. 11:13, lines 673-675), narrowed by "existential reduction", which collects the constraints that keep a domain off `Bottom` and solves them (lines 733-743, Figure 6).
- A restriction the proof needs. A method's type parameter bindings are well formed only if "no reference to a method type parameter appears in any of the upper bounds" and every reference falls within a left-to-right scope; "restriction (1) makes dynamic dispatch more efficient and restriction (2) makes it consistent" (§ 3.3, p. 11:11, lines 565-570); the one-pass right-to-left solve depends on it (lines 1010-1016, 1258-1262). Trait type parameters carry no such restriction.
- What the calculus leaves out. "FGFV omits functional methods [Allen et al. 2007] and declarations of closed types [Allen et al. 2011], but these could be added back to FGFV in an obvious way" (§ 1, p. 11:3, lines 142-144); "FGFV does not support features like modularity, nominal exclusion, and closed types in their work, [but] they can be added in an obvious way" (§ 6, p. 11:25, lines 1302-1303). No coercion, no `nat` parameters, no numbers.
- The exclusion rule's form and date. [Anc-Same-Trait] (Figure 4, p. 11:11, lines 530-532): a class extending two instances of a trait must extend an instance below both; "the 'Ancestor Meet Rule' ... was introduced into Fortress in 2012 by Guy Steele and David Chase" (§ 5.4, p. 11:24, lines 1230-1232). For an invariant parameter only the same instance is below both; for a covariant one the lower instance is.
- Variance in full: marks `+ - =` on trait parameters, objects always invariant (§ 3.2, lines 406-409); a covariant parameter only in covariant positions, a contravariant one only in contravariant ones ([D-Method], § 3.3, pp. 11:11-12, lines 571-595); dispatch with variance marks (§ 5.2.2); exponential blowup only where union types meet contravariance, accepted (§ 5.4, lines 1239-1257); the two alternatives the team weighed in 2012, dropping contravariance or dropping union types.
- Cost. "In simple invariant cases, we expect the run-time cost to be relatively low but nonzero"; for variant cases "caching or dynamic recompilation" (§ 5.4, pp. 11:24-25, lines 1263-1273).

## 1. The verdicts the paper bears on

### 1.1 Route A: the exclusion rule kept, the tower flattened (D4)

- The paper confirms the rule and the flattening. [Anc-Same-Trait] is the exclusion in the paper's own terms, and "because the rules guarantee that there always exists a single minimal ancestor when a class extends multiple instances of a trait, no ambiguous method calls are possible due to multiple instances of a trait" (p. 11:11, lines 550-554). There is no tower, no self type and no `comprises T` in it (searched).
- It adds one thing the route-C notes could not know: variance cannot rescue the tower. The self-typed algebra traits put their parameter in a parameter position (`opr =(self, other: T)`), and [D-Method] forbids a covariant parameter there (lines 571-572, 584-592). So `Equality[\+T\]` is ill formed, and the covariant clause of the ancestor rule, the only clause that admits two instances on one chain, is closed to the tower. The patents' forest rule stays what the record called it, a sketch outside the group's proven model.
- Nothing to do differently. One line for batch 7b's rung S: Appendix I's instantiation-exclusion entry cites [Anc-Same-Trait] beside the 2011 paper and the 2012 Types chapter.

### 1.2 Answer 9: the overload sentence goes, the three rules, the return-type rule over every instance (D17)

- The paper confirms the drop and the rules: a generic declaration "is applicable to a type α if there exists an instance D of d that is applicable to α" (§ 2.2, p. 11:5, lines 246-248); "we use the subtype relation of their domain types as in Allen et al. [2011]" (§ 4.1, line 604); the three rules as Figure 5 states them.
- It confirms rung C's planned form of the return-type rule. The record plans "the paper's special arrow, `∀[Δ1, Δ2] (S1 ∩ S2) → T2`, with the less specific declaration's parameters kept quantified except where the domain reduction forces an equality" (`reviews/overloading-judgement.md:93`); that is [Return-Test] with the paper's reduction in a narrower form.
- It adds the general form of that reduction (§ 4.2, lines 733-743, with the `ArrayList`/`List` example at lines 676-683 and 731-732): collect the constraints that keep the intersected domain off `Bottom`, solve them, and compare the reduced domain. The record's reduction forces equalities through instantiation exclusion only; the paper's also carries bounds it cannot solve as constraints. The difference is a family of valid overloads the revival's checker will refuse and the paper's accepts.
- Do differently: nothing in the decision. Rung C's decision record names the paper's reduction as the general form and its own as the special case; rung C's tests add the paper's `ArrayList`/`List` triple as a program, expected to be refused today and gated as an expected failure if it is. Cost: one paragraph and one test in a rung already in batch 7b.

### 1.3 The positional rule (answer 9's revival addition)

- The paper has no such rule. Type parameters are α-renamed ("We assume the conventional α-conversion to rename bound variables", line 669) and a dispatched declaration is instantiated by substitution from the ilks and the static return type ([Dispatch], line 874-879), never handed the call's written static arguments by position. So an override that reorders its parameters is well formed in the paper's model.
- The positional rule exists because the team's code generator passes written static arguments by position to whichever declaration dispatch reaches (row 398). It guards an implementation habit, not a rule of the designers' model. It refuses nothing in the library (`coordinator/CLIMB-BATCH-7.md:234`).
- Do differently: keep the guard, since the code generator still has the habit, but batch 7b's rung S states it in a callout as a restriction of the compiled implementation pending run-time instantiation by substitution, with the paper cited, not as a rule of the language; phase 5 lifts it when the dispatcher instantiates as [Dispatch] does. Cost: wording in an entry rung S already writes.

### 1.4 The conversion-and-overloading decision of 2026-09-28 (D25, decision 1)

- The paper has no coercion, so it is silent on the order "convert only when nothing fits". It confirms the two halves the decision rests on: applicability when some instance fits (line 246-248) and specificity on declared, quantified domains (line 604, Figure 6).
- It adds a caution about what its proof covers. Its well-formedness rule (2), "no reference to a method type parameter appears in any of the upper bounds" (lines 565-570), excludes every F-bounded generic function: the library's `SUM[\T extends AdditiveGroup[\T\]\]` and `PROD` of answer 7, its `BIG MAX[\T extends StandardMax[\T\]\]`, and every function over `T extends Integral[\T\]`. The record's option-2 soundness note already found that the readings part exactly at the F-bounded shapes (`reviews/option-2-soundness.md:14`, `:54`, `:110`). So the paper's Theorem 5.11 does not cover the library's reductions, and the record should not cite it as covering them. Where such a parameter is fixed by an invariant argument type (`Generator[\T\]`), the bound is checked and never solved, which is why both the team's checker and the revival's handle it; the paper's restriction protects its one-pass solve, not those calls.
- Do differently: nothing built. The decision records of rungs S and C say in one sentence that the paper's soundness result excludes F-bounded method type parameters and closed types, and that the library's reductions rest on the 2011 rules as implemented, not on the 2019 proof.

### 1.5 Item 26: `comprises` read at the level of values, with run-time uniqueness (D27)

- The paper omits closed types and nominal exclusion and says both "can be added in an obvious way" (lines 142-144, 1302-1303). So it neither confirms nor contradicts the coverage reading, the Meet Rule's closed-trait case or row 492's repair.
- It adds one fact for the proof appendix. Theorem 4.1 (§ 4.3, p. 11:15, lines 782-789) keeps static uniqueness: No Duplicates makes the more-specific relation antisymmetric, Meet makes every applicable set a meet semilattice, and "there always exists a unique most specific method declaration". The revival's addendum gives static uniqueness up for run-time uniqueness at a call whose argument's static type sits between two closed traits (`reviews/comprises-type-level-proof-addendum.md:8-9`, `:115-116`). In the paper's model the same case would be met by the team's own plan of 2009, identifying the intersection of two closed traits with the union of their common subtypes (`Specification-1.0-frozen/appendices/future.tex:285`), under which [Meet-Third] holds with a single meet and Theorem 4.1 stands. Item 26's judgement did not weigh the paper on this (searched: no citation).
- Do differently: no change to batch 7b; this is the one place the revival's type theory steps outside the designers' last proven model, and it should be said. Rung S's entry for the proof appendix says in one sentence that FGFV keeps static uniqueness as a theorem, that the coverage case is beyond FGFV, and that the revival gives up static uniqueness there on the addendum's premises. Cost: one sentence.

### 1.6 Item 30: a generic declaration beside a plain one at run time (D28)

- The paper contradicts the default and gives the rule. The record chose "the instance the value fixes, the least instance where it fixes none", Welterweight's rule (`Papers/Welterweight/dispatch.tick:189-192`: "l_j is the type inferred for P_j", the lower bound), and recorded Naden's return-type restriction as future work, weighing Naden's 2012 objection that programmers could not follow execution without static types (`literature.md` § 1). The paper, with Steele among its authors, took the other road: static return types are carried to run time ([R-Method], lines 888-896), and the instance is the intersection of the upper bounds, the declared bound and the static return type's constraint, never the lower bound alone (lines 1274-1284). It says in so many words that the lower-bound rule could not be proven.
- Where the two rules agree: a parameter fixed by an invariant position in a parameter type (`grab[\X\](t: Tag[\X\])`), since lower and upper bound coincide, which is the case the judgement's example and rung W's row 157 concern. Where they differ: a parameter that is the whole type of a parameter or occurs only covariantly. `id[\T\](x: T): Box[\T\]` called through `r: Any = id(z)` with a `ZZ32` value gives `Box[\ZZ32\]` under the record's rule and `Box[\Any\]` under the paper's; a later dispatch on the box tells them apart.
- Where they meet answer 8: the revival's static promotion instantiates `op[\T extends Number\](z, w)` at `ZZ64` and annotates the call's result `ZZ64`; the paper's run-time rule then gives `Number ⊓ ZZ64 = ZZ64`, the same instance. So the paper's rule reproduces rung I's static choice at run time from the annotation, which the "least instance" rule does not promise.
- Walk cannot apply the paper's rule: it has no static types, so no static return type to constrain the instance; the value's type is all it has. That is walk's limit, as for coercion (judgement, item 7).
- Do differently, in batch 7b: rung S states the paper's rule as the designers' latest word in the dispatch paragraph (the dispatched declaration's parameters instantiated at the intersection of their upper bounds under the call's static return type, never `Bottom`), and states in a callout that both implementations today take the value's type where nothing fixes the parameter, walk by necessity and the compiled path until phase 5. Rung C adds one expected-failure pair for the case where the two rules differ (the `Box[\Any\]` shape above) beside the two it already adds. Rung W's row-157 fix stays, being walk's best. Phase 5's list gains one line: the dispatcher needs the call's static return type, which the team's code generator does not pass (`ProjectFortress/src/com/sun/fortress/compiler/OverloadSet.java:2048`, "Not sure what to do with return type"). Cost: wording in a rung that already edits the passage, one test pair, one plan line.

### 1.7 The implicit bound `Any` (Q1; the judgement's item 3)

- The paper confirms it: "By default, each type parameter has an upper bound Any and a lower bound Bottom" (lines 418-419). The judgement's item 3 stands with this as its deciding citation; rung S cites it in the callout that revises `trait-parameters.tex:49-50`. Nothing else changes.

### 1.8 Row 447, the written `extends Object` bound, and every `Bottom` binding (D23 decision 2; the judgement's commission error 1 and item 2)

- The paper contradicts the mechanism and gives the fix. Its type system "requires that both static and dynamic type inference algorithms instantiate type parameters with non-Bottom types" (lines 845-847, 884, 1119-1120), the solving step "never instantiates method type parameters with Bottom" (lines 1005-1006), and an otherwise unconstrained parameter takes the intersection of its upper bounds: its declared bound, `Any` by default, and the static return type's constraint.
- Under that rule the crashes of row 447 do not arise. `fail[\T\]("...")` in a `ZZ32` value position is instantiated at `ZZ32`; `r: Any = et(z)` instantiates `et` at `Any`, and `BoxT[\Any\]` is a class that exists, where `BoxT[\Bottom\]` carried as `java/lang/Object` was not. The compiled checker's solver does the opposite today: an inference variable left open is bound to `BOTTOM` (`ProjectFortress/src/com/sun/fortress/scala_src/useful/STypesUtil.scala:1954-1955`, `killIvars`; `Formula.scala:524`), which is why rung B's written bound "works" and why the kept expected type of rung I still binds `Bottom` (row 447's later notes). The Working Draft's own note asks "Do we want to forbid such cases where type inference infers BottomTypes for static parameters?" (`Specification/basic/inference.tex:233-234`); the paper is the designers' answer.
- This replaces the judgement's item 2. Treating a `Bottom`-typed call as a `throw` in the code generator was a repair of the symptom; the paper's rule removes the cause and is the designers' own, and it reaches row 425 (a generic big operator's no-argument form bound to `Bottom`), the interpreter's counterpart row 424 (walk erases an unwritten static argument to `Bottom`; it should take the bound), and the inference chapter's callout (`inference.tex:212-215`), which today describes the `Bottom` binding as the checker's behaviour.
- Do differently: one checker rung, in batch 8 or beside rung Q in batch N's second run, that binds an inference variable with no lower bound to the intersection of its upper bounds instead of `BOTTOM`, with row 447's two probes and row 425's `SUM[j <- lo#i] (3 j)` as its tests (row 425 may need the big-operator desugaring's bounds as well; the rung measures it); rung B's written `extends Object` lines become unnecessary and may stay; one walk rung for row 424 later. The inference chapter's callout and its Appendix I entry change in the same batch. Cost: two small rungs; it removes a phase-4 prerequisite the judgement had ranked first among the errors of commission.

### 1.9 Row 516: a lone type parameter with no narrowest candidate (D23 decision 3, batch N's chapter)

- The paper contradicts the chapter's rule. The chapter gives such a parameter "the union of the types of those arguments" (`inference.tex:95-98`); the paper says that is the assumption the team could not prove, and takes the intersection of the upper bounds, the declared bound or `Any`. Both implementations already take the bound where one is written (row 516: `pick[\T extends Number\](w, r)` is a `BoxT[\Number\]` on both paths), and the two expected-failure tests `XXXInferLoneBoundUnion` and `XXXInferLoneUnionWalk` pin the union as the intended behaviour.
- Answer 8's promotion is not touched: it is a coercion the paper does not model, and for number arguments it decides the instance statically before the paper's rule applies (1.6 above).
- Do differently: batch 7b's rung S, whose file list already gains the inference chapter, replaces the union sentence by the bound (the declared bound, `Any` if none, under the static return type), citing the paper; the two expected-failure tests become plain tests of the bound behaviour; the checker's union candidate for an unbounded parameter (`Functionals.scala:334-343`, the `named` list, and the union fallback planned for rows 515 and 518) becomes `Any`. Cost: one sentence, two test flips, a few checker lines in the rung of 1.8. Nothing fast is lost: a body at the union of two unrelated types is a body at `Any` in the generated code.

### 1.10 The `covariant` keyword (row 404; answer 6's road back)

- The paper confirms the direction and is the specification for it: the marks, the position check, the ancestor rule under variance, dispatch with marks, and the cost. It also confirms answer 6's road back: phantom covariant parameters appear in no position, so they pass [D-Method] trivially.
- Nothing to do now; it is off the path. Row 404 and worklist item 12 point to the paper as their design when they are built.

### 1.11 Walk's run-time choice of coercions (the judgement's item 7)

- The paper is silent on coercion. But its whole dynamic semantics needs the static types of invocations at run time (lines 329-331, 820-824), which walk does not have. So walk cannot implement the designers' last model of dispatch either, and the judgement's reading, walk's run-time choice accepted as the interpreter's limit and the compiled path following the text, is strengthened. Nothing changes; the road to a walk that matches is static types under walk, his wish of 2026-09-15.

### 1.12 The omissions the judgement named

## For Pavol

The question in one line: does the full POPL 2019 paper, the type group's last published word, say anything that means we should do something differently?

What changes:

- Three things, all cheap, none built yet. First, the answer you gave on item 30 (2026-09-29, "only option one makes sense") took the 2012 rule, the instance the value fixes. The 2019 paper says the team could not prove that rule and replaced it: the instance is fixed by the declared bound and by the call's static result type, never by the value alone. For microGPT the two agree, because its static types are concrete. The specification should state the 2019 rule; both implementations keep what they do today, in a callout; one test marks the difference. Second, the crash I ranked first among the errors (row 447, the `fail` calls that fail JVM verification) has a designers' fix that is better than the one I recommended: the checker should never bind a type parameter to the empty type `Bottom`; it should bind it to the parameter's bound, or to the expected type. The paper says this outright. One small checker rung, and the same rung fixes rows 425 and 516. Third, the inference chapter batch N wrote says a type parameter with two unrelated arguments takes their union; the paper says that was an unproven guess and takes the bound; the implementations already do the latter; the text and two tests flip.
- Nothing changes in the big decisions. Route A, the flat tower, the overload sentence, the three rules, the conversion order, `comprises` on values and the implicit bound `Any` are all confirmed, the last one in so many words.
- Two things to know, no decision needed: the paper's soundness proof does not cover the library's own reductions (`SUM`, `BIG MAX`, the `Integral` family), because it forbids a bound that names the parameter itself; and the item 26 you approved is the one place our type theory goes past the designers' last proven model, since the paper keeps a unique static winner as a theorem where we keep it only at run time. Both go into the decision records as sentences.
- One thing for phase 5's list: the compiled dispatcher will need the call's static result type at run time, which the team's code generator never passed.
