## FACTS entry

**The compiled transaction: what a read records, who validates, and which block an abort restarts.** A compiled `atomic` block's transaction records no read of its own write; it records a read of an ancestor's write with that write, a read of the committed value with that value, and a read of an empty array element with a mark. Validation, at a read once the global lock has moved and at a commit that did not get the lock at its snapshot, covers the transaction and every ancestor. An abort names the transaction whose read failed; `abort()` names none. The block's generated handler takes every exception (`BaseTask.leaveTransaction`): it ends the block's transaction, starts the block again for an abort of that transaction (or any abort at the outermost block), and throws everything else on, an exception after the nested transaction's reads went to its parent. A nested commit hands its parent its reads and its writes, also where it wrote nothing. The exception-table entry of a block or a `try` follows its body's code, so a nested one is taken first. Source: `ProjectFortress/src/com/sun/fortress/runtimeSystem/Transaction.java:228-367`, `runtimeSystem/BaseTask.java:273-294`, `compiler/codegen/CodeGen.java:1782-1814`, `:2116-2120`. Tests: `compiler_tests/AtomicOwnWriteNestedCompiled`, `AtomicNestedSameBodyCompiled`, `NestedAtomicAbortCompiled`, `AtomicNestedViewCompiled`, `AtomicSharedReadsCompiled`, `AtomicThrowRevertsCompiled`, `AtomicNestedReadsKeptCompiled`, `NestedTryInnerCatch`; `ArrayStoreJUTest`. ## Revival change

### The change

- The team's code generator wrote the exception-table entry of an `atomic` block and of a `try` before it visited the body (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:1793` and `:2112` at 9d0147ff9e), so in one body the outer block's handler, or the outer `try`'s `catch` clause, took an exception first. The tree now writes the entry after the body's code (`CodeGen.java:1801`, `:2120`): the innermost `atomic` block is the one that `abort()` starts again, and the inner `try`'s `catch` clause is matched first. Tests: `compiler_tests/NestedAtomicAbortCompiled`, `AtomicNestedSameBodyCompiled`, `NestedTryInnerCatch`. Reason: `Specification/advanced/parallelism-locality/transactions.tex`, "Abortable Atomicity" ("abandons execution of the innermost `atomic` expression"); `Specification/basic/expressions/try.tex`, "Try Expressions"; a parallel `for` of `atomic do atomic do d := d + 1 end end` over 1#400 left `d` at 395.
- The team's handler of a compiled `atomic` block took only `TransactionAbortException` (`CodeGen.java:1790` at 9d0147ff9e), so a Fortress exception left the block with its transaction open and its writes visible. The tree's handler takes every exception and ends the transaction, so the block's writes are discarded and a later block is a transaction of its own (`CodeGen.java:1801-1811`; `runtimeSystem/BaseTask.java:273-294`). Test: `compiler_tests/AtomicThrowRevertsCompiled`. Reason: `Specification/basic/expressions/atomic.tex`, "Atomic Expressions": "Any variable reverts to the value it held before evaluation of the `atomic` expression began"; walk gives 100 where the compiled path gave 7.
- The team's compiled transaction recorded a read of its own write as a read of the committed state, validated a nested transaction's own reads only, and let the threads of one block iterate and write its read set at once (`ProjectFortress/src/com/sun/fortress/runtimeSystem/Transaction.java:220-224`, `:257-278`, `:243` at 9d0147ff9e). The tree records nothing for an own write, validates a nested transaction with its ancestors, restarts the block whose read failed, and guards the shared sets (`Transaction.java:228-284`). Tests: `compiler_tests/AtomicOwnWriteNestedCompiled`, `AtomicNestedViewCompiled`, `AtomicSharedReadsCompiled`. Reason: measured failures: a block that read its own write around a nested block never ended (exit 124 under `timeout 60`); a nested block saw `x` and `y` differ where other blocks change both together; `ConcurrentModificationException` from a `for` inside a block.
- A program that depended on any of the old behaviours changes: a `catch` clause of an outer `try` that used to take an exception which the inner `try` also takes no longer runs; a variable written in an `atomic` block before a `throw` keeps its old value.
