## Revival change

**The change.**
- The team's compiled path folds integer numerals before the checker, and walk folds nothing (`ProjectFortress/src/com/sun/fortress/compiler/phases/PhaseOrder.java:125-147` at b430f9f428: the fold is in `compilerPhaseOrder` only). The team's fold folds integers only, takes `BOXPLUS`, `DOTPLUS`, `BOXMINUS` and `DOTMINUS` as `+` and `-`, folds `AND`, `OR`, `XOR` and prefix `NOT` bitwise, folds `n DIV 0` into `Infinity`, and throws at a `CHOOSE` outside `0..n` (`compiler/desugarer/IntegerLiteralFoldingVisitor.java:38-109`, `:152-157` at b430f9f428). The tree now folds an expression of numerals alone, integer and radix-point, exactly on both paths, into a numeral as written or an operation on numerals, leaves the operators whose meaning needs a width and a division by zero, and gives `CHOOSE` outside `0..n` the value 0 (tests `ProjectFortress/tests/NumeralFoldWalk.fss`, `ProjectFortress/compiler_tests/LiteralFoldCompiled.test`, `NumeralFoldJUTest`). So under walk `2147483647 + 1` is 2147483648 and `0.1 + 0.2` is `0.3`. The reason: the Working Draft's static expressions of literals and operators denote exact values, and a static rational expression in a floating-point computation incurs at most one rounding (`Specification-1.0-frozen/basic/expressions/literals.tex:163-173`; `constant.tex`, "Static Expressions"); measured: the team's fold stops the compile at `3 CHOOSE 5` ("Integer Literal folding: Need to do something for factorial of negative values") and makes `a: ZZ32 = 2147483647 BOXPLUS 1` die with "Not in range for ZZ32: 2147483648".
- The team's code generator makes a radix-point numeral's double as `intPart.doubleValue() + numerator.doubleValue() / Math.pow(base, power)` (`compiler/codegen/CodeGen.java:2035-2045` at b430f9f428), two or three roundings: `x: RR64 = 0.9999999999999999` was 1.0. The tree rounds the exact value once, and a numeral at a typed place of `ZZ32`, `ZZ64`, `NN32`, `NN64`, `ZZ`, `RR64` or `RR32` is that type's constant (tests `FloatNumeralOneRounding`, `LiteralFoldCompiled`). The reason: the Draft's one rounding (above).
- The team's compiled program calls its own coercion from a numeral at each evaluation of the numeral's site, so one site gave distinct reference objects (a probe on the base: `start`, `coerce  3`, `coerce  3`, `coerce  4`, `a SEQV b  false`). The tree calls it once per site, when the component's class is initialized, and every evaluation reads the one result; a coercion that raises stops the program before `run()` (tests `NumeralCoercionOnceCompiled`, `NumeralCoercionRaisesCompiled`). The reason: a numeral is one constant of the program text, and each construction of a reference object is a new object (`Specification/basic/objects.tex:51-53`), so a call at each evaluation made one written numeral many objects.
