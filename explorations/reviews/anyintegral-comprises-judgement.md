# `AnyIntegral`'s `comprises` clause: the judgement

The error. `trait AnyIntegral extends { Number } comprises { ZZ, ZZ64, ZZ32, NN64, NN32 } end`, with `trait Integral[\I extends Integral[\I\]\] extends { StandardTotalOrder[\I\], MultiplicativeRing[\I\], AnyIntegral }` (`Library/FortressLibrary.fsi:433-436`), is refused by the compiled checker: "Invalid comprises clause: FortressLibrary.AnyIntegral has a comprises clause but its immediate subtype Integral is not eligible to extend it". It is the `FortressLibrary` api's last early error. The api's check stops on it before its overloading and return-type checks run (`ProjectFortress/src/com/sun/fortress/compiler/StaticChecker.java:269-272`), so the count stage reads 22 and never sees the api's 66 (`reviews/anyintegral-comprises-ways.md` section 2, the "ways note" below). The ways note lists twelve ways with their measurements. This note weighs them and recommends one.

## 1. The type question, in plain words

Terms first.

- A `comprises` clause closes a trait. `trait T comprises { A, B }` says `A` and `B` are the only types directly under `T`.
- `Integral[\I\]` is a generic trait, and its parameter is bounded by the trait itself ("F-bounded"): each integer type implements `Integral` at itself, `trait ZZ32 extends { AnyIntegral, Integral[\ZZ32\] }` (`.fsi:510`). It sits between the closed `AnyIntegral` and the five listed types, and it is not listed.
- Two readings of a clause. The type-level reading: the clause says which types may extend `T`. The value-level reading ("coverage"): the clause says where `T`'s values come from. A trait has no values of its own; only objects do.

The question: does a closed trait that lists concrete types admit a generic, F-bounded subtrait? Each source, at its line:

1. The rendered specification: no. A listed reference "is a declared trait identifier" (`Specification/basic/traits.tex:161-165`), and the `Molecule` example forbids an unlisted trait to extend a closed one (`:262-279`). Victor Luchangco's draft note beside the first sentence asks whether the term includes "instantiations of parametric traits" (`:166-170`); the text never answers.
2. The draft note: no. "The traits listed in its comprises clause are exactly the traits that immediately extend T and they must explicitly extend T" (`traits.tex:234-246`). It is a `\note`, which a release build drops (`Specification/fortress/fortress.tex:35-36`). It restates Sukyoung Ryu's checker rule of 2009-04-17 and is in the draft by 2009-11-06 (ways note section 1); the Working Draft of February 2011 has it at `Specification-1.0-frozen/basic/traits.tex:231-234`.
3. The Types paper (OOPSLA 2011): no at the type level. "Any strict subtype of `C[\T\]` must also be a subtype of `[T/X]K_i` for some `K_i`" (`Papers/Types/exc-spec.tick:18-23`), and each listed `K_i` must be below `C[\T\]` (`:47-51`). `Integral[\ZZ32\]` is a strict subtype of `AnyIntegral` and above `ZZ32`, below none of the five, unless it is identified with `ZZ32`.
4. Karl Naden's journal text (2012; last touched 2012-08-31, `8015b17f4`): the identification is the self-type idiom. "The self-type idiom is realized with the comprises clause which contains the instantiation of the self type ... the type `Ring[\X\]` is identified as `X`" (`Papers/Types/journal/justificationOfRTR.tex:580-582`). With `Integral[\I\] ... comprises I`, `Integral[\ZZ32\]` is `ZZ32`, and the five-type list holds at the type level for the five.
5. The later Types chapter (Luchangco, 2012-05-31, `275b90773`; `coordinator/spec-lineage.md:151-152`): yes, as coverage. A clause "specifies a set of types and generic types determined by the generic type of the declaration. An instantiation of the generic type defined by such a declaration is covered by the union of the types in this set and the corresponding instantiations of the generic types in this set" (`Documentation/Specification/Prose/Language/types.tick:384-389`). `G` determines `G'` "if every parameter of `G'` is a parameter of `G`" (`:271-277`). So `AnyIntegral` may list the five and may not list `Integral`, which it does not determine. The chapter states no rule about extenders.
6. Welterweight (2012; in the tree by the import of 2012-07-19, `5a68404fd`): yes, at the value level. "The comprises clause, if present, indicates that no value can belong to the trait unless it also belongs to one of the comprised types" (`Papers/Welterweight/grammar.tick:21-22`). Its rule D-Trait asks each listed type to be well formed and a subtype of the trait at the trait's own parameters, and asks nothing of the traits that extend it (`Papers/Welterweight/fig-wellformeddecls.tick:38-62`). Its grammar lets a clause hold constructed types only, never a bare type parameter (`fig-grammar.tick:6-8`, `:33-37`).
7. The compiled checker's rule (Ryu, 2009): no, unless the subtrait has a clause of its own. A trait extending a closed one must be below a listed type, or have a clause whose entries are each eligible (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/TypeHierarchyChecker.scala:203-208`, `:254-266`); a type variable in that clause is filtered out (`:262`), so `comprises I` makes any generic subtrait eligible. The rule's own statement is the team's test `ProjectFortress/compiler_tests/Compiled10.i.fss` ("(3) Eligibility to extend").

Which is the designers' latest word. The decision of 2026-09-23 weighs the type group's later, implementation-informed word above the specification's earlier text; the decision of 2026-09-26 names the later Types chapter as the designers' later word wherever it covers a topic (POSITIONS 2026-09-23, 2026-09-26, the lineage note). The chapter covers this one (`types.tick:384-389`), and Welterweight, the group's 2012 calculus, reads the clause the same way. Naden's sentence of the same year is the type-level reading, in a paper about the return type rule; his idiom and the coverage reading agree on every value and differ only on whether a valueless trait may sit between. So the answer: yes. A closed trait that lists concrete types admits a generic subtrait, on the condition that every value below the generic subtrait belongs to a listed type. `AnyIntegral`'s clause meets it: only the five extend an instantiation of `Integral` anywhere in the tree (ways note section 1, the grep). The checker's rule is the group's earlier reading. It is the rule that made Ryu delete the team's own clause in 2009 ("Fixed comprises clauses in libraries", `3d2849cef`) and leave the comment that records what was meant, "not yet: comprises Integral[\I\] where [\I\]" (`.fsi:434`; Jan-Willem Maessen's message of 2008-07-02, "we can't write a comprises clause that mentions Integral[\I\]", `82c85b03a`, ways note section 4). The five-type list is that closure written the only way the later chapter allows.

One fact every reading shares. A program's own `trait MyIntegral extends Integral[\MyIntegral\] end` with an object makes the list false. Measured: the checker accepts that program with 0 errors on the tree, under `comprises I`, and under both accommodations; only the 2008 clause on `Integral[\I\]` refuses it (ways note section 1, `anyintegral-comprises-ways/captures/probes/user-integral.txt`). The checker checks immediate subtypes only, so the hole is at every closed level of the tower, not at this clause. Under Welterweight values come from objects (its rule D-Object, `fig-wellformeddecls.tick:66-`), so the sound check is at an object declaration: an object below a closed trait must be below a listed type. That is a ledger row, not this decision.

## 3. The recommendation

Way 11, the narrow accommodation, with its specification change. The clause and walk stay as they are.

Why, in order of weight:

1. The clause is what the team meant. Their comment on the line closes `AnyIntegral` to `Integral`'s instantiations (`.fsi:434`), the five are those instantiations, and the later Types chapter allows `AnyIntegral` to list only the five (section 1, item 5).
2. Under the designers' latest word the clause is right and the checker's rule is the earlier reading (section 1). The custodians' job (protocol principle 1) is then to bring the checker to the group's 2012 semantics, not the library to the checker's 2009 rule, which is what Ryu did in 2009 under time pressure and marked "not yet".
3. It changes nothing under walk, where the tree passes both microGPT checks today, and no line of the model or the library moves.
4. It stays inside route A: no self type enters the library (POSITIONS 2026-09-24, route A).
5. It has an approval on record, parked (POSITIONS 2026-09-21; `PLAN.md` item 21).
6. Its cost is the smallest that clears the error on both paths: 14 lines in one checker file, no team test changes, one S1 entry.

The alternative, if he prefers the team's code to the team's prose: way 3, `Integral[\I\] comprises I`. It leaves the checker as the team wrote it, at the price of an interpreter edit whose tests are unmeasured, a specification callout that legalises a form the group's 2012 calculus dropped, and the first self type in the library under route A. If the S1 class's `Integral` share is later found to clear under it (section 4), that is a reason to revisit in batch 8, not a reason against way 11 now: the two are compatible, since under `comprises I` the accommodation's disjunct is simply never reached.

**Question.** How do we resolve the checker's refusal of `AnyIntegral`'s `comprises` clause, the last early error in the `FortressLibrary` api?

**Context.**

- Refresher. `trait T comprises { A, B }` closes `T`: `A` and `B` are the only types directly under it. The design has it so two traits can be told apart without a `where` clause: closed families that share no member exclude each other, which lets an operator be overloaded on both.
- The shape. `AnyIntegral` is the marker "some integer type" and lists the five integer types. `Integral[\I\]`, the generic interface each integer type implements at itself, sits between them, unlisted. The checker wants every direct child listed; `Integral` cannot be, being generic, and the team's `where` spelling (their "not yet" comment on the line) is unimplemented.
- What the designers said. The 2008 text and the checker's 2009 rule: a child must be listed. The group's 2012 texts (Luchangco's Types chapter, Welterweight): a clause says where a trait's values come from, and a trait in between adds none. Under your decisions of 09-23 and 09-26 the 2012 texts weigh more, and by them the clause is right as written.
- The library's own way, an open marker with `excludes`, is blocked: a number cannot exclude the algebra traits, so walk refuses the generic scalar block.
- Walk passes today: both microGPT checks 40 of 40 with the clause as it stands.

**Options.**

1. Teach the checker the 2012 reading: a generic child of a closed trait is accepted when every type the checker sees under it is listed. 14 Scala lines, gated tests, no team test changes, one S1 specification callout. Walk untouched. The count stage rises 22 to 87 as the api's 66 overloading errors become visible. Approved and parked by you on 09-21.
2. The compiler library's idiom, `Integral[\I\] comprises I`. Passes the checker as is; walk overflows (row 407), so a 6-line interpreter edit, its interpreter tests not yet run; a specification callout legalising a type variable in a clause, which the 2012 calculus dropped; the library's first self type under route A.
3. Take `Integral` out from under `AnyIntegral`, its exclusions restated by hand. Two or three library lines per file; both microGPT checks pass; interpreter tests not run. `Integral` stops being a `Number`, against the team's comment.
4. Leave it. The api's 66 stay off the count stage; it must be resolved before the switch-over anyway.

**A yes to 1** commits you to one small batch of two rungs between 7R and N (checker, specification), a checker rule of ours, reversible by deleting 14 lines, and a ledger row for a hole every option but the 2008 clause shares: a program's own integer type in another file is not caught.

**A no** leaves 7b's overload rung without the count stage's measure of the api and defers the same choice to the switch-over.

**Recommendation.** Option 1: the checker learns the 2012 reading; the clause and walk stay as they are.
