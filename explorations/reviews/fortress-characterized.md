# Fortress, characterized from the evidence

This is a reading of the 286 rows of `explorations/fortress-gap-ledger.md` and of the reports around them, arranged by language area for a reader who knows Scala, Swift, Kotlin and Rust well and Fortress not at all.
The question it answers is Pavol's: where does Fortress stand next to those languages, where is the impedance mismatch when a concept from them is expressed in it, and what does that imply for the order of the next work.
The rule throughout: a claim about Fortress here is a claim the tree has evidence for, cited by row number or `file:line`; general knowledge about Fortress is not used.
Where the evidence is thin the sentence says so.

Sections: (1) what Fortress is, in one page; (2) area by area, a table and a paragraph each; (3) the impedance mismatches, named; (4) the ledger's rows classified, with the revival worklist checked against the 113 rows added since it was derived; (5) options for the next work, with the evidence for each.

## 1. What Fortress is, in one page

**Two executions of one language.** The tree carries two nearly disjoint ways of running a Fortress program, sharing a parser and a phase list and differing at the end (`explorations/repo-internals.md:95-129`).
The interpreter (`fortress file.fss`, "walk") is a tree-walking evaluator over the 4,518-line `Library/FortressLibrary.fss`; it is the mature path, and every microGPT port and the whole APL ladder ran on it.
The bytecode compiler (`fortress compile` + `fortress run`) is the team's unfinished 2010-2012 push: it lowers every type to a JVM reference type, emits one generated dispatch method per overloaded name, and stamps generic instantiations out at class-load time by rewriting template bytecode (`repo-internals.md:129`).
The static type checker, a Scala rewrite started in 2009 (`repo-internals.md:54`), runs only on the compile path: `walk` never turns it on and there is no switch to make it (`repo-internals.md:127`).
So the interpreter accepts spec-illegal programs, and the ledger records what that buys and costs: `object Value extends Number` against `Number comprises { RR64 }` is accepted and then the whole linear-algebra library works for the user type (rows 22, 52), a `fill` lambda's declared return type is not enforced (row 153), `comprises` is never checked (row 22).

**What the compiled path is worth and what it lacks.** Measured on the corpus's own shapes, compiled code runs 6.8× faster on a scalar `RR64` loop and 8.9× on object-allocating autodiff-style code, and starts in 0.67 s against the interpreter's 5.1 s (`explorations/compiled-path-gaps.md:45, 100-101`).
What blocks it is not code generation but its prelude: `Library/CompilerLibrary.fss` is 592 lines against the interpreter's 4,518 (`compiled-path-gaps.md:58`), with no `List`, no generic `array`, no `exp`/`log`, no `SUM`, two monomorphic reductions and an empty `trait Matrix` (rows 71-74; `Library/CompilerLibrary.fsi:126-159, 213-216, 230`).
Twelve rows (70-82) bound the path: what works (implicit tuple parallelism, `atomic`, generic objects and functions, `while`, `try`), the six library holes, two dispatch gaps against `comprises` unions (77, 78), a `typecase` that silently answers wrong (79), a stubbed `IntLiteral` comparison family (80), one true codegen `sayWhat` at `label` (81), and `spawn` without a usable handle (82).

**"Implicit parallelism" in practice.** A `for` loop is parallel unless every generator is wrapped in `seq` (`Specification/basic/expressions/for.tex:28-32`), and so are the elements of a tuple and the operands of an operator (`basic/expressions/tuple-expr.tex:23-24`; row 265).
On this tree that means: `for c <- s` over a string at one thread prints the string backwards (row 111); a bare `acc := acc + c` in a parallel loop silently loses updates at four threads and `atomic do … end` is correct (row 59); reductions and `__generate` are safe (row 60); a loop whose iterations write disjoint blocks through views is safe and 2.4× faster at four threads (row 155); and a mutable frame stack shared by the elements of one tuple crashes at pool size four (row 265).
The runtime is a work-stealing pool on the JDK's ForkJoin (`CLAUDE.md`, toolchain paragraph); `FORTRESS_THREADS` sets the pool size, and every ledger probe ran at one thread unless stated (`fortress-gap-ledger.md:29`).

**The syntax-extension mechanism.** A user `grammar` declared in an api adds new expression forms to the language; a Rats! parser is generated for it at run time, which costs about 40 s on a cold cache and needs a JDK with `javac` (row 266).
A rule is a sequence of terminals and typed gaps with a template `<[ … ]>` that is parsed as Fortress; free names in a template resolve at the use site (row 270), binders written in a template are gensymmed (row 204), and a grammar may live only in an api, never in a component (row 269).
The specification's own chapter on this is a one-line stub deferring to the FOOL 2009 paper "Growing a Syntax" (`Specification/advanced/domain-specific-languages.tex:15-16`; `research/README.md:60`), and the spec's one normative form, `syntax … = Expr`, is not implemented (row 267).
The APL side quest climbed six chapters of Kruger's "Learning APL" inside `apl⦇ … ⦈` on this mechanism and then ran the flat-style microGPT through it at C4's own cost (`explorations/apl/README.md:11-21`; rows 281, 282; `explorations/apl/mg/REPORT.md:186-192`); section 2.8 says what the mechanism carried and where it gave.

**The surface a reader sees first.** Multiplication is juxtaposition (`2 x`, `M v`), defined in the library from `TIMES` (`Library/FortressLibrary.fsi:264-271`), and the library therefore declares no `opr ×` in any arity (row 249).
Operators are Unicode characters from a generated table (`≡ ≢ × ÷ ∘ ⊂ ⊃ ⊖` are operators, `⍳ ⍴ ⌽` are not; rows 185, 216, 278) or all-uppercase ASCII words (`SUM`, `DOT`, `MAX`), and any word of two or more capitals is an operator, not a name (row 7).
The ASCII source renders to mathematics through Fortify: `SUM[m <- g] body` becomes `∑` and `DOT` becomes `·` (row 65), which is why the Unicode `∑` need not lex as an accumulator (row 5).
Whitespace carries fixity: `w |hs|` works and `w|hs|` does not (rows 87, 88), a two-line `a ||` / `b` does not parse (row 9), `/|` is one token (row 86).
Precedence is deliberately not transitive: `-` and `AND`, or `MOD` and `+`, have incomparable precedence and demand parentheses (row 89; `basic/operators/precedence.tex:162-169`).

The numeric tower is the first mismatch a Swift or Rust programmer meets: in Fortress `ZZ32 <: ZZ64 <: ZZ <: QQ <: RR64` is subtyping, not conversion, so `1.0 c` on a `ZZ64` is a juxtaposition that happens to widen (row 146) and an integer passes wherever a `RR64` is expected — while the reverse direction has no working path at all (rows 188, 283).
The tower is sealed by `comprises { RR64 }`, so a user number type is illegal by the spec and accepted by the interpreter (row 22); the legal route through `AdditiveGroup`/`MultiplicativeRing` reaches `+ - scale pmul .t()` and stops at `DOT` and every top-level operator, all of which carry `[\T extends Number\]` (row 53).
The design's numeric ambition — `ℂ`, intervals, dimensions, coercions — is the largest never-built area after the algebraic library; what shipped is a working IEEE `RR64`, a rational `QQ` that appears unbidden (row 174), and 32/64-bit integers whose literal typing has traps (rows 146, 79, 80).
The seed for `ℂ` (`explorations/complex_ring.fss`) already runs on the two shipped traits, and the `settable` value-object idiom the spec gives for `Complex` works (row 116); what would be new is a place in the tower, which `Number comprises { RR64 }` currently forbids (row 53's suggested `comprises { RR64, ... }` at `FortressLibrary.fsi:276`).

What a reader from nalgebra or Breeze expects — an algebra inherited from traits — is present exactly once: `+`, `-`, unary `-` and `zero` at rank 1 and 2, from `AdditiveGroup` (row 36; `vocabulary/REPORT.md:9`).
Everything else is a top-level declaration because no trait supplies it, which is why C4's array vocabulary has 40 declarations and why 30 of them are forced in count even though 19 of those are habits in shape (`vocabulary/REPORT.md:13, 25`).
The sized types are the surprising part: a `nat` is a static parameter, yet the interpreter reads it off a runtime-built array and dispatches on it (row 214), so rank overloading is real and a six-line view object with `reflect`ed sizes is a full `Matrix` (row 150); what the `nat` never does on the walk path is get checked statically, because the checker is off (`repo-internals.md:127`), and what it does at run time is fail as an uncatchable overload error (row 254).
The shipped `SUM` cannot reduce anything but a `Number` (row 44), a matrix generates all its cells so `SUM` over it is `+/,m` and not `+/m` (row 221), and the empty sum is the integer `0` (row 45).
Two of the four rows every port paid for are here: the missing matrix operators (row 35) and the `Number`-sealed `SUM` (row 44; `explorations/gap-cross-run.md:329-356`).

### 2.3 Generics, traits and overloading

| concept the reader brings | Fortress by design | what the implementation does | rows |
|---|---|---|---|
| static overload resolution on the declared types of arguments (Scala, Swift, Kotlin), or none (Rust); single dispatch on the receiver; Julia-style multiple dispatch known from elsewhere | symmetric multiple dispatch on the run-time types of all arguments (`basic/overloading.tex`, chapters 15 and 24); the Meet Rule: two overloads whose parameter types are unrelated need an `excludes` or a declaration at the meet (`advanced/overloading.tex:224-262`) | the interpreter dispatches on run-time types including inferred `nat`s (rows 214, 218, 225, 248, 259); a more specific user overload wins over the library's (218) and an equally specific one with a different result type wins too (237); the Meet Rule is enforced only on a cold cache, so a rejection appears once per source version (rows 97, 98); the meet declaration the spec asks for cannot be written (`BottomType is undefined`, row 97); the compiled path cannot dispatch a method declared only in subtypes or an overload set over a `comprises` union (77, 78) | 77, 78, 97, 98, 214, 218, 225, 237 |
| variance annotations (`+T`, `out T`), declaration-site or use-site | declaration-site covariance by a `where` clause: `trait C[\S\] extends C[\T\] where { S extends T }` (`basic/trait-parameters.tex:339-346`) | rejected (`T is undefined`); `Library/CovariantCollection.fss` is the hand-rolled workaround; `List` is invariant and an aggregate's element type is its elements' runtime class, so ascriptions are mandatory (row 20) and two `nat` instantiations never join (row 96); `BIG UNION` needs explicit static arguments (row 135) | 17, 20, 96, 135 |

| type aliases, sealed hierarchies, implicit conversions | `type` aliases (`basic/types-vals-vars.tex:597-623`); `comprises` seals a trait to exactly its listed subtypes (`basic/traits.tex:231-235`); coercions (chapter 17) | aliases are unimplemented (`Not yet implemented: TypeAlias`, row 18); `comprises` is never checked on the walk path (row 22); coercions parse and are ignored (row 19) | 18, 19, 22 |
| a generic function is a value; `Any` is a harmless top type | arrow types are subtypes of `Any` so a function is a value (`types-vals-vars.tex:136`); `Any` is the top (`:121-122`) | a `nat`-generic function passed as an argument fails three ways, one a Java NPE (row 156); `Any` as a parameter or result of a `nat`-generic function is an `InterpreterBug`, and an overloaded function whose result is `Any` never dispatches at all (rows 157, 240); `Object` is the type the ports use instead | 156, 157, 240 |
| overloads that differ in a function-typed parameter | most-specific by the whole parameter tuple (`basic/overloading.tex:170-175`) | resolved correctly for a typed lambda or a named function (row 171), silently the first declared for an untyped lambda (row 164); two generic `opr` declarations of one operator in one component need an excluding pair (row 159), a user generic beside a library generic is not checked and dispatches by specificity (`vocabulary/REPORT.md:84`, candidate row 288) | 159, 164, 171 |
| n-ary operator overloads; operators as values | multifix operators (`basic/operators/chained-multifix.tex`) | never looked for, reassociated to binary (row 29); an operator is not a value, `applyIt(opr ×, …)` is a parse error and `(×)` an `InterpreterBug` (row 165) | 29, 165 |

Fortress's dispatch is Julia's, not Scala's: which body runs is decided at the call from every argument's run-time type, and the interpreter extends that to sizes (row 214) and, through `Rank1 excludes Rank2` (`fsi:1072-1078`), to rank (rows 225, 248).
The price is the Meet Rule, a declaration-time check Scala and Swift do not have: two overloads over `Array[\RR64,ZZ32\]` and `Array[\RR64,(ZZ32,ZZ32)\]` are rejected as unrelated (row 97), and the check is cache-dependent so a program can run for its author and fail on a clean checkout (row 98).
What Scala and Kotlin programmers reach for first — variance annotations, aliases, inferred generic arguments, implicit conversions — is designed and not implemented (rows 17, 18, 19, 21), and the hand-rolled substitutes (`CovariantCollection`, explicit `[\T\]` ascriptions, `konst`-style shims) are what every port ended up writing.
The trait system's promise, "declare the algebra and inherit the implementation", is kept by exactly two traits (row 36); the library that would have carried the rest was never built (row 37), and the shipped tower's self-typing by `Number` rather than by each type makes the spec's bound shape unusable on `RR64` (`vocabulary/REPORT.md:83`).

### 2.4 Functions and lambdas

| concept the reader brings | Fortress by design | what the implementation does | rows |
|---|---|---|---|
| placeholder lambdas (`_ + 1`), operator sections, `+` as a function value, `::plus`, eta-expansion | none: no production makes an operator a primary expression (`grep OpRef` in the grammar finds nothing, row 165); `fn x => e` with optional types (`basic/expressions/function.tex:28-31`) | an operator is not a value and a generic function is not a value (rows 165, 156); a plain function and a lambda are; the eta-expansion `fn (w, r) => w r` is the workaround (row 165); a library functional method is a value `map` takes (`vocabulary/REPORT.md:88`, candidate row 292) | 156, 165 |

| hygienic macros (Rust `macro_rules!`, Scala macros) | templates in a user grammar; "any bindings introduced by a macro are fresh" (the FOOL 2009 paper, via row 204) | hygiene is implemented: a binder written literally in a template is gensymmed, a gap-bound binder is not, so a name can only meet its reference if both come from outside the template (rows 204, 201, 285); a template cannot expand to a binding or assignment with a gap on the left (rows 186, 196), only to one with a literal name (row 205) | 186, 196, 201, 204, 205, 285 |

The point-free habits of a Scala or Swift programmer have no counterpart: there is no placeholder, no section, no operator value, and no way to pass a `nat`-generic function (rows 165, 156), so a lift takes a lambda written out, which is what C3's attention lines carried and C2 avoided by lifting the operators instead (`explorations/reviews/run-c2-vs-run-c3.md:65-73`).
The shadowing rule is stricter than any of the four languages: one namespace for locals, top-level functions, inherited method names, static parameters and imports (rows 92, 147, 167, 168, 262), which cost Run C3 three compile rounds on the name `rows` (row 168) and is the reason the APL ladder's dfns became zero-parameter lambdas over a frame stack (row 245).
Contracts are the pleasant surprise: they run, they are catchable, and they cross a macro expansion (rows 118, 220, 231), which the spec's own chapter note still calls "not yet supported" (row 118).

### 2.5 Collections and strings

## 3. The impedance mismatches, named

**Concepts the reader brings that have no counterpart here.**

1. Point-free code. No placeholder, no operator section, no operator value, no generic function value (rows 165, 156); every lift takes an explicit lambda, and an untyped one can pick the wrong overload silently (row 164).
2. Implicit conversion by declaration. Coercions parse and do nothing (row 19); what stands in is the tower's subtyping, in one direction only (rows 146, 188, 283).
3. Type aliases and variance annotations. Designed, unimplemented (rows 17, 18); the substitutes are a carrier object and explicit static arguments everywhere (rows 20, 21, 135).
4. Shadowing. None at all, across five kinds of name (rows 92, 147, 167, 168, 262); the reader's `step` loop variable beside a `step` function is an error.
5. Pattern matching. `typecase` exists and is wrong on the compiled path (row 79); tuple patterns bind but do not appear in parameters or on the left of `:=` (rows 143, 251); no match on constructors, and no `Option`-style chaining beyond `if i <- …` (row 138).
6. Exponent literals, `\u` escapes, a `split`, a float parser (rows 14, 200, 141, 140).
7. Sequential iteration by default. Every generator is parallel and unordered until wrapped in `seq` (rows 111, 136).
8. A single standard library and a type checker one can run on one's program (rows 69, 71; `repo-internals.md:127`).
9. Errors at the use site of a macro (rows 213, 229, 243).

**Concepts Fortress has that those languages lack.**

1. Juxtaposition as an operator. `M v`, `2 x`, `"[" x "]"` are all applications of `opr juxtaposition`, dispatched on both operands (rows 33, 99, 132; `fsi:264-271`); the traps are its reassociation rules — `f()[i]` and `f()^T` are static errors (rows 4, 144, 158), a prefix operator cannot be the second operand (row 85), `b.f(3)` is a method call (row 91), and a macro bracket cannot be a juxtaposed operand (row 239).
2. Mathematical Unicode operators with declarable fixities. Prefix, infix, postfix, bracketing and big operators over a generated table (rows 216, 233, 279, 280), operator words for the rest (row 7), and a typesetter that renders the ASCII (rows 64, 65); the table is fixed at build time, so APL's own glyphs are reachable only inside a sub-grammar (rows 276, 278).
3. Sized types read at run time. `nat` parameters inferred from runtime-built arrays and used for dispatch (rows 214, 225, 248), views with `reflect`ed sizes (row 150); no language of the four does this, and Rust's const generics are the nearest and are static.
4. Symmetric multiple dispatch with a Meet Rule (rows 214, 218, 237, 97); Julia has the dispatch, none of the four has either.
5. Big operators and the generator protocol as one mechanism for iteration, reduction and parallelism (rows 41, 43, 46, 47, 103, 137, 221), extensible by replacement rather than addition for `Σ` (rows 39-41).
6. Contracts on headers, enforced (rows 118, 220, 231).
7. Value traits, `settable`, `comprises`, `excludes` as first-class hierarchy tools (rows 115, 116, 33, 99), though the object half of valueness is unenforced (row 112).
8. Parallel by default with `atomic` (rows 59, 70).
9. A syntax-extension mechanism that runs (row 266) and carried an APL (rows 281, 282), with the limits of section 2.8.
10. Non-transitive precedence and whitespace-sensitive fixity as deliberate design (rows 89, 87, 88, 9).

The shape of the mismatch is one sentence: the reader's languages spend their design on static guarantees for ordinary code, and Fortress spent its design on the notation — juxtaposition, Unicode, sized types, dispatch, big operators — and on parallelism; in this tree the notation mostly runs and the static guarantees mostly do not, because the checker is off on the path that works.
