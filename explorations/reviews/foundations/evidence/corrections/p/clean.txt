- P-37 **One library, the interpreter's, is the library that the compiler checks.** The interpreter's prelude, `FortressLibrary` and `FortressBuiltin`, becomes the compiled path's prelude in place of the compiler's own, and the compiled path reads the interpreter's library with it. Why: the switch-over exists to avoid the need to port the interpreter's library into the compiler's library; the revival develops the type checker further, so that it accepts the fuller library that the interpreter uses. That the compiled path can run the twelve components that the checker passes, and not only check them, is not yet shown: in one measurement at the switch-over's setting, the code generator refused at least 52 of their declarations, and no class emitted from the library was run (F-34). The curator sees the compiler's prelude, its own library files `CompilerLibrary`, `CompilerBuiltin` and `CompilerAlgebra`, as a bootstrap to remove. So no declaration is added to the compiler's prelude, and at the switch-over its three files are deleted and their tests kept (P-38 says which tests are respelled). A fourth compiler-only file, `CompilerSystem`, the compiled path's `System`, is outside the prelude and outside this decision: 27 compiled tests import it, and no decision says whether it goes at the switch-over. The decision settles which files survive, not the designs inside them: the one library may take a design of the prelude's, as it took the prelude's flat shape of the number types. This decision does not stop work on the code generator, which is compiler work under either library. The decision is not put to him again. How the checker comes to accept the library, its first step and the order of the work, was left to a plan for him, which he approved (P-33).
- P-26 **Where the type group's later positions conflict with the specification's early text, the later positions win.** The early text was a wish. The type group, the part of the team that built the type checker and the compiler, then worked to make the language run, with performance as the goal and specialization a must, and learned what is feasible. Specialization, in the type group's design, is a special version of a generic function for one instantiation, such as `tail(x: List[ZZ])` beside `tail[X](x: List[X])`, which dispatch chooses at run time. Where the two conflict, the specification is revised to follow their later word (P-95 records each change with its reason). Their later word includes the exclusion rule, specialization kept, the number types of the compiler's prelude made siblings in 2009 and 2010 (P-43: the library's numbers are flat in the same way), Karl Naden's 2012 write-up "The Return Type Rule and Generics" (`Papers/Types/journal/justificationOfRTR.tex`) and the type group's POPL 2019 paper (F-166). The implementers' later word also outweighs unfinished text. The revival does not second-guess them: it knows less than they did.
- P-43 **The exclusion rule stays, and the number tower is flat (route A).** The compiled checker keeps the multiple instantiation exclusion rule: no type extends two instantiations of one generic trait. So the library's numbers are flat, as the team (Chase, Ryu, Maessen and Allen) flattened the compiler prelude in 2009 and 2010. The fixed widths, `ZZ`, `QQ` and `RR64` are siblings under `Number`, each with its own algebra, and `Number` has no catch-all operators. Why: the type group states the exclusion rule in four texts: the 2011 paper (`Papers/Types/exclusion.tick`), the 2012 Types chapter (`Documentation/Specification/Prose/Language/types.tick`), Naden's 2012 write-up (`Papers/Types/journal/justificationOfRTR.tex`) and the POPL 2019 paper. Under the rule a nested tower whose every level carries the self-typed algebra traits at its own type is impossible: if `ZZ32` extended `ZZ64`, `ZZ32` would be an instance of each such trait at two type arguments. The Working Draft's types chapter also says that the number types "are mutually exclusive; no value has more than one of them" (`Specification-1.0-frozen/basic/types-vals-vars.tex`), and the 2012 Types chapter keeps the sentence. The flattened prelude is the team's last record of the Fortress way, and its route leads to the POPL 2019 paper, which keeps the rule. The curator cares that specialised code runs fast, not how a specialisation is chosen. F-46 prices a return to route C.
- P-158 **A member that an api writes `abstract` is declared in the component that exports the api.** The component's trait or object declares each such member at the api's header, with a body or without one. The compiled export check refuses a component that leaves one out, and the checker then checks that each object defines it. Why: the compiler's prelude, the team's later work, restates each such member in the component without a body, and from March 2009 the team's export check refused a component trait that left out a member of its api's trait (`edb516dba`, Sukyoung Ryu); by P-26, on the team's later word, that way wins over the interpreter's library, written earlier for walk, which leaves some out. The specification's export rule does not ask for this declaration: it asks the component to declare each field and each non-abstract method of the api's trait or object, and allows a concrete declaration of an abstract one (`Specification/basic/components/source-code.tex`, "Export Statements"). Without the declaration, a compiled client's call of the member dies with `NoSuchMethodError` (row 816).
