# The dispatcher taking the call site's static arguments: sized in a shadow

**The answer.** The generic dispatcher is already loaded under the call site's static arguments; only its arms ignore them. Making each generic arm use the dispatcher's own static parameters is one file, one edited function and three new helpers: 43 code lines in `OverloadSet.java`, plus 1 for the switch and 3 for the variant that leaves generic arms out of a dispatcher that has no static parameters. `MieDispatchSub` then prints `Marker[Blue]`. The compiler prelude is byte-identical. The 43 compiler tests that declare generic overloads all print the same. Of the 34 that link, 31 have byte-identical classes and 3 differ only inside a generic dispatcher. Top-level functions only: generic dotted methods fail the same way and are not covered (`ScopeMethod`).

## 1. How the compiled path handles generics today

- A **static argument** is the type that fills a generic's static parameter at one use. In `grab[\Blue\](b)` it is `Blue`. Usually nobody writes it: the checker infers it from the declared types at the call, so `b: Tag[\Blue\]` gives `X = Blue` (`scala_src/useful/STypesUtil.scala:912-930`).
- An **instantiation** is the generic with its static parameters replaced by static arguments: `grab[\Blue\]` is an instantiation of `grab[\X\]`.
- The compiler writes one *template* class per generic function, with `X` left in the names of the types it mentions (`Marker⟦X⟧`). The class loader stamps an instantiation from it when a class named with real arguments is first needed. For `grab⟦Blue⟧` it copies the template and rewrites every `X` in it to `Blue` (`runtimeSystem/Instantiater.java`, `MethodInstantiater.java`). The part of the name after `✚`, the template's arrow type, is never rewritten (`InstantiationMap.java:354`).
- A call that needs no choice at run time is compiled as a call to that named class. The checker's static arguments go straight into the name (`compiler/codegen/CodeGen.java:3670-3735`), so `grab(z)` with `z: Tag[\ZZ32\]` calls `grab⟦ZZ32⟧`.
- **Dispatch** is choosing at run time which declaration of an overloaded name runs, by the argument's actual type. A **dispatcher** is the method the compiler generates for that. It tests the argument against each declaration, most specific first, and calls the first that applies (`compiler/OverloadSet.java:1303-1760`). One is generated for a declaration when some more specific declaration of the same name may apply at run time. If the least specific declaration is generic, the dispatcher is itself a template, named and loaded like any generic function: `grab⟦Blue⟧` at the call site (`OverloadSet.java:2005-2062`).
- **RTTI** (run-time type information) is the object every compiled value carries that describes its type. That includes the argument of each generic supertype, one per generic name: `Mixed`'s RTTI says `Sub` of `Red` and `Tag` of `Blue`.
- How a generic arm finds its static arguments today: it asks the value for its RTTI (`getRTTI`), asks that for the argument at the arm's generic (`Sub__1()`, giving `Red`), and passes the answer to `RTHelpers.loadClosureClass`. That call spells the instance's name from the RTTI's own Java class (`runtimeSystem/RTHelpers.java:160-178`, `runtimeValues/RTTI.java:53-58`), and the loader stamps it (`OverloadSet.java:1410-1728`). Inside a dispatcher template the arms do this too: they ignore the template's `X`, which the loader has already set to the call site's argument (`javap-excerpts.txt:60-80`).
- The authors weighed the question in a comment: "Some overloads have static args, but even if they are supplied, runtime inference is still necessary (so I think) -- drc 2010-02-24 / Not quite so -- if each static parameter is mentioned in any invariant occurrence, then the supplied type is exact" (`OverloadSet.java:1981-1990`).

## 2. The design

**What the specification says.** Declarations of one name share their static parameters (`Specification/basic/overloading.tex:100-105`), so "static parameters do not enter into the determination of which declarations are applicable" (`:106-107`). The chapter assumes "that all static variables in functional calls have been instantiated or inferred" (`:136-138`), and they are "statically inferred from the context of the function call" (`expressions/var-ref.tex:37-40`). One set of static arguments, fixed at the call, therefore applies to every declaration. A declaration applies at run time if the value's type is a subtype of its parameter type at those arguments. For `MieDispatchSub`, `grab(b)` with `b: Tag[\Blue\]` fixes `X = Blue`. `Mixed` is not a `Sub[\Blue\]`, so the `Tag` declaration runs and the answer is `Marker[Blue]`.

**`MieDispatchAny`'s `grab(a)`, `a: Any`.** The specification refuses the program: `grab[\X\](t: Tag[\X\])` beside `grab(a: Any)` is an error "for one declaration to have static parameters and another to not have them" (`overloading.tex:103-105`). The question of which declaration runs therefore does not arise. If the sentence is not enforced, both readings give the same answer. The call was resolved to `grab(Any)`, which has no static parameters, so the call site supplies none. With no arguments to instantiate it, the generic declaration is not applicable. The code should refuse the pair at compile time (§5). Failing that, it should leave the generic arm out of such a dispatcher, which is the `skip` variant below. Either way `grab(a)` returns the `Any` declaration's `Red`.

**The three candidates.**
- **(a) The dispatcher gains the static arguments as parameters**, and every call site the checker resolved with static arguments pushes their RTTIs. This changes the signature of every dispatcher whose least specific declaration is generic, and the descriptor at every call site that reaches one. The template would then carry `X` twice, in its name and in its parameters. The arms would still be stamped through `loadClosureClass` from RTTI names, which keeps the `ZZ32` naming defect (§4). For `grab(Any)` it passes nothing, because that call site has nothing to pass. Not built.
- **(b) The call site loads an instantiated dispatcher named with the static arguments.** It already does, for every dispatcher that is a template (§1). The change is inside the template: each generic arm whose static parameters match the dispatcher's, up to renaming, is renamed into the dispatcher's parameters. It is then tested with a plain `instanceof Sub⟦X⟧` and called as `grab⟦X⟧` by name, and the loader turns both into `Blue`. Nothing is read from the value, and no signature, call site or template kind changes. This is the specification's model, one instantiation of the name fixed at the call, and it is the smallest of the three. Built.
- **(c) The arms keep reading from the value and skip on mismatch.** The template would need `X`'s RTTI in its body. A generic object's RTTI class reads its parameters' RTTIs from fields (`CodeGen.java:5686-5690`), but a function template has no such field, so this needs a new way to name it. Each arm would then compare the RTTI read from the value with it. Equality is wrong where `X` occurs only covariantly, because the value's argument can be a subtype of the call site's. The correct test is "read ⊑ call site" followed by instantiating at the call site's argument, and that is (b) with the reading left in. It keeps `loadClosureClass` and both defects of §4. Not built.

## 3. The size, measured

**The shadow** (`scope/scope-shadow.patch`, first file): `OverloadSet.java` only. In `generateCall` (`:1303`), a generic arm of a template dispatcher gets a `StaticTypeReplacer` from its static parameters to the dispatcher's (`atTemplateParams`). Its parameter and return types are built at those parameters, so they contain no variable of the arm's and take the existing no-inference path. The call goes to the arm's instance named with the dispatcher's parameters (`invokeArmAtTemplateParams`: the same stem the value-reading path passes to `loadClosureClass`, with the arm's name moved away from the dispatcher's as that path does, `:1650-1654`). Code lines: 2 imports, `templateStaticParams` 3, `atTemplateParams` 13, `invokeArmAtTemplateParams` 15, five edited lines in the type-structure loop, and 5 replacing 2 at the call: 43. Add 1 line for the `-Dprobe.scope` switch and 3 for `skip`. `MieDispatchSub`'s template, stock and shadow, is in `scope/javap-template.txt`. Stock reads `Sub__1()` and calls `loadClosureClass` (`:17`, `:28`). The last four programs mix a generic and a non-generic declaration of one name, which the specification refuses (§2, §5). `skip` is what the code should do for them if they are not refused.

**What else it changes.**
- The compiler prelude compiled under `callsite` is byte-identical to stock, all five jars (`scope/prelude-compare.txt`).
- The compiler tests that declare a generic overload, or match `overload` or `Generic` in the name, are 43 files (`scope/compiler-tests.txt`). Every run output is identical between stock and `callsite`.
- 34 of them link and run. Their classes are byte-identical in 31. In the other 3, `Compiled12.invariantInference`, `invariantInference2` and `Compiled180`, only the generic dispatcher templates differ. `Compiled180`'s last arm, for example, stops re-reading `T` from the value.
- The other 9 fail identically under both: 8 before a jar is written, `Compiled240` in code generation.
- Under `skip`, 42 outputs are identical. `Compiled12.invariantInference` changes: its twelve calls pass `Any`-typed arguments to `f(x: Any, z: Any, y: Any)` beside six generics, and all twelve now print `Any`. Its `.test` expects the run-time answers, so that gated test would go red. The sentence refuses the same file at compile time (§5).

**The remainder**, not built, by site:
- Generic dotted methods. Their dispatcher template comes from `OverloadSet.java:2296-2340` (`generateGenericFunctionClass` with `generateBody(mv, 1)`), with the trait's parameters ahead of the method's (`:2315-2316`). The arms are invoked at `:2240-2265` and the tables named at `:2386-2410`. `ScopeMethod` fails identically, stock and shadow.
- Functional methods in a top-level set. Their static parameters are the trait's plus their own (`:1881-1890`); the shadow guards them out.
- Non-type static parameters. An `opr` parameter has its own naming (`Naming.oprArgAnnotatedRTTI`), and a `nat` parameter needs the size work's run-time kind (FACTS, design A). The shadow guards them out with `KindType`.
- An arm whose static-parameter count differs from its dispatcher's stays on the value path. `Compiled12.invariantInference`'s `[\X1, X extends X1\]` beside `[\X\]` is one; the sentence refuses it.
- A non-generic dispatcher with generic arms stays on the value path unless `skip` is used. The sentence makes it impossible.
- Once the sentence holds and methods are converted, the value-inference block (`OverloadSet.java:1410-1728`) and `RTHelpers.loadClosureClass` (`:160-213`) are dead code.
