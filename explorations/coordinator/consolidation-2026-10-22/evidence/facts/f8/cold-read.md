## F-231 "The generated AST walker is split into eight methods ..."

- **Established:** The checker's syntax-tree walker, `Walker.walk`, is generated by `ScalaAstGenerator` into `FortressAst.scala`. As one method it was 31,704 bytes of bytecode, over HotSpot's 8,000-byte limit, so HotSpot never compiled it to machine code and it ran in the bytecode interpreter. Every substitution and normalization of the checker goes through it, so it dominated the checker's time. It is now cut into eight consecutive methods that give the same output.
- **Conditions:** The times were taken on climb batch 15b's code on an idle machine: count stage 911 s to about 340 s, distance stage 2,375 s to 931 s. That count-stage run also had the row-680 repair applied (the count stage checks a block's local functions; F-233). After the split, about 95 % of what was left was the solver reducing formulas it had already reduced; the solver's memos now answer those (F-235). These are historical times; F-240 has the current ones.
- **Consequence:** Do not let a `Walker` method grow back over 8,000 bytes. For current timings use F-240, not these. (The skill adds the how: `MethodSizeJUTest`, `WALKER_CASES_PER_METHOD`.)
- **Evidence:** Gated by `WalkerJUTest`. Detail: `perf-probes/checker-speed-2/REPORT.md` sections 2 and 6.

## F-232 "The syntax tree's hashes do not depend on the JVM's identity hashes, except ..."

- **Established:** Each generated node class's `hashCode` starts from the hash of its class name. That code is emitted by makeAST's post-processing of ASTGen's output and by the in-repo generators (`build.xml:679-697`). Fields whose type contains an `Option` are hashed through `NodeHash.of`, because the PLT library's `Option` classes hash by identity. So hash maps and hash sets of ordinary nodes iterate in the same order on every run, whatever identity hashes other code asked for before. The order in which `StaticChecker.checkApis` takes the apis is fixed the same way. There are three exceptions: inference variables (their id is a bare `Object`), walk's `_WrappedFValue` (it hashes its wrapped value), and any node that holds one of these.
- **Conditions:** The inference-variable exception does not reach any count-stage output. The `_WrappedFValue` exception is walk's (row 430). `DeclaredFunction` objects still hash by identity. Since row 737's repair, no choice of `ApiTypeExtractor` depends on their order (F-254).
- **Consequence:** You can rely on a stable iteration order over node collections, as the skill's compiler.md does when it compares `run.txt` files. If an output's order changes, the change itself caused it. A new node field holding an `Option` presumably has to be hashed by `NodeHash.of`, but the entry implies this and does not say it.
- **Evidence:** Gated by `NodeHashJUTest`; row 737's repair by `OmittedReturnTypeFromApi`. Sources: `NodeHash.java`, `NodeFactory.java:1166-1184`, `_WrappedFValue.java:170-177`, `build.xml:679-697`. Detail: `compile-ladder/rung-ast-hashes/REPORT.md` sections 4.2 to 4.4.

  - "makeAST", "PLT `Option`" (concepts I lack): the skill mentions ASTGen but not makeAST or the PLT library. I inferred them to be a build step and a Java utility library.

## F-237 "The well-formedness walk reports an ill-formed type that it meets outside the expression it is in at that expression ..."

- **Established:** A call's type carries the source spans of the callee's declared type. Suppose a call's static argument breaks a bound in the callee's result type, so the type is ill-formed only because of that call. The checker's well-formedness walk then reports the error at the innermost expression where it met the type, which is the call, not at the callee's declaration. Each call that produced the type reports once. Expressions that the call's value flows into share the same type node and add nothing. A second call whose static argument prints the same still gets its own error. A type that is ill-formed as written gets its error at its declaration, once. A local variable's right-hand side is walked before the lines that use the variable, so the error lands at the call, not at a later use.
- **Conditions:** One exception: two nested calls of the same callee whose static arguments print the same, `next[\T\](next[\T\](x))`, report only the inner call (row 776). In the library, by reading, the change adds or drops no error, and the distance has no well-formedness errors (F-53).
- **Consequence:** Expect a bound violation from instantiation at the call site, once per call. Do not expect it at uses of the result, or at the callee's declaration. Expect the nested-call case to show one error.
- **Evidence:** `TypeWellFormedChecker.scala`: `check`, `error`, `outside`, `within` and the `SLocalVarDecl` case. Gated by six `compiler_tests/XXX...` tests (compile-refusal tests, as the skill's `XXX` compile tests are). Detail: `rung-checker-abstract-callsite/REPORT.md` sections 1 and 6, its `SKEPTIC.md` 5.1 and 5.2, and its `JUDGE.md`.
- **Could not resolve:**
  - Title, "that it meets outside the expression it is in" (unclear wording): "it" can be the walk or the type. Only the second sentence shows that the type's *span* lies outside the expression. The title could say so directly.
  - Row 776's exception (two readings): it could be intended behaviour or a known defect (a ledger row normally records a gap). It is also unclear whether `XXXStaticArgBoundNestedCall` pins today's one error or the correct answer.
  - "no error is added or dropped" (unclear wording): relative to what? Probably the behaviour before this reporting change, but the entry does not name the baseline. "by reading" presumably means it was checked by reading the library, not by a run.
