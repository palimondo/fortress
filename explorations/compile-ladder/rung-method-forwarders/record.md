## Revival change

**The change.** The team's code generator (`compiler/codegen/CodeGen.java`, `dumpMethodChaining`, with `STypesUtil.removeIdenticallyCoveredMethods`, `scala_src/useful/STypesUtil.scala:1574`) wrote a forwarder for each inherited declaration with a body that no declaration of a subtype covered, comparing the two domains as schemas over each trait's own static parameters; it skipped every declaration without a body, an imported api's among them. So a compiled generic trait that declared again a method which it inherited through a trait that was not its first could not load, and a compiled object could not call a method whose body an imported api's trait gave it, unless that trait was first in its extends clause. The tree now writes one method for each such group, which runs the declaration of the lowest type that declares it, as walk does, and forwards to the api trait's body: `compiler_tests/TraitOwnMethodBesideInheritedCompiled`, `compiler_tests/ApiTraitMethodNotFirstCompiled`. The reason: the traits chapter, section "Method Declarations" (`Specification/basic/traits.tex:584-590`), by which a trait does not inherit a declaration whose parameter types are those of one that it declares; the measured failures 'ClassFormatError: Duplicate method name "mx?0"' and 'AbstractMethodError ... does not define or inherit an implementation'; and the compiled checker's reading of an api's method without `abstract` as one with a body (`scala_src/typechecker/AbstractMethodChecker.scala:274`). A programmer no longer needs to put an api's trait first in an extends clause, or to keep a generic trait from declaring again what it inherits. Two limits stay: an object's own overloads of a functional method with self not first beside an inherited one still die at dispatch, and a body of a self-typed trait that returns `self` still fails verification at an object instance.
