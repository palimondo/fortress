> Extended by rung T of climb batch 1 (2026-09-19). The mechanism, read in the tree rather than inferred: the class the importing component looks for is named after the **api**, not after the component that declares the variable. `NamingCzar.jvmClassForToplevelDecl(IdOrOp x, String api)` (`ProjectFortress/src/com/sun/fortress/compiler/NamingCzar.java:1653-1656`) first replaces its `api` argument with `repairedApiName(x, api)` (`:1673-1679`), which, whenever the identifier carries an api name of its own, substitutes that api's package-and-class name for the one the caller passed; it then builds the inner-class name from it. So the name it produces is an existing class exactly when the api and the declaring component share a name — which is every prelude pair's case (`CompilerLibrary.fsi` and `CompilerLibrary.fss`, and so on) and is not the shape the row probed. The row's `NoClassDefFoundError` is therefore the failure when the two names *differ*: the emitted class is the component's and the name asked for is the api's, and nobody emits it. When the two names are the same, that class does exist and the run dies one step later, on the field: `NoSuchFieldError: Class fortress.CompilerLibrary$__globalTimeInformation does not have member field 'com.sun.fortress.compiler.runtimeValues.FRR64 ONLY'`. Measured by exporting `Library/CompilerLibrary`'s own stored time — `var __globalTimeInformation: RR64` in the api and `var __globalTimeInformation: RR64 = 0.0` in the component, the only spelling the checker accepts on both sides — and reading it from a second component (`compile-ladder/rung-timing/probes/ReadStoredTime.fss`, capture `probes/export-variable-3.txt`; `probes/export-variable.txt` and `-2.txt` are the two spellings the checker refuses first, "due to different mutabilities" and "due to different modifiers", which is `Specification/basic/components/source-code.tex:340-342` enforced). The mechanism is derived from two code sites, both read in the tree: `CodeGen.generateVarDeclInnerClass:5872-5906` gives a **mutable** top-level variable's singleton field the descriptor `NamingCzar.descFortressMutableFValueInternal` — R1's cell — and an immutable one the declared type's descriptor (`:5878-5881`); `CodeGen.forVarRef`'s fresh-import path `:5953-5971` always builds a plain `VarCodeGen.StaticBinding` with `tyDesc = NamingCzar.jvmTypeDesc(ty, thisApi())` (`:5966-5970`) and never consults the imported declaration's mutability, unlike `addTopLevelVarBinding:5934-5951`, whose branch at `:5945-5950` does. So the fix has two parts, not one: the class name, and the descriptor, which needs the fresh-import path to know the imported declaration's mutability and to emit a `MutableStaticBinding` when it is mutable. A repair that fixes only the class name would move the failure from one exception to the other. This matters for the batch that takes row 320: both target programs export a top-level variable from their api (`explorations/apl/mg/MicroGptApl.fsi:18`, `explorations/run-c4/src/MicroGptFlat.fsi:16`).

## The decisions to report to Pavol

Two, both taken because the specification is silent and both written up in REPORT.md under "The decisions".

**The rendering of the elapsed time.** `printTime` prints real milliseconds, `Operation took 341.574931ms`, where the interpreter prints whole ones, `Operation took 18ms`. The alternatives were: round as the interpreter does and print `3.0ms`, which throws the fraction away and still does not match; reach a true integer; or reach one by string surgery on `Double.toString`'s output. The fraction is not noise — two of the four intervals this rung's own test measures are reported as `0ms` by the interpreter and as `0.001982ms` and `0.087981ms` by the compiled path.

**What the chosen rendering does at its extremes, measured rather than feared.** `Double.toString` switches to scientific notation at `>= 1.0e7` and at any non-zero value `< 1.0e-3` (measured on this container's JDK 25, `compile-ladder/rung-timing/probes/skeptic/double-boundary.txt`). So `printTime` prints `1.0174680816587E7ms` for any interval at or above 2.78 hours — measured, not projected: that is the actual line a probe produced when `printTime` was called with no preceding `recordTime` (`probes/skeptic/compiled.txt`) — and `9.99E-4ms` for any non-zero interval below 1000 ns; the shortest interval actually measured is 1338 ns, which prints `0.001338ms`, and the rung's own test's shortest was 1982 ns. Scientific notation is therefore a property of the rendering that was chosen, not only a cost of the string-surgery alternative that was rejected, and this is where it is recorded as such.

**What changing the rendering would now cost, corrected.** At the batch base there was no `RR64`-to-integer conversion on the compile path at all, which is why the report first priced this as a `.java` slot. That is no longer the price: rung F of this same batch was chartered to add `round` and `truncate` to `trait RR64` (`CLIMB-BATCH-1.md`, section F), its cited precedent returns `ZZ64` (`Library/FortressLibrary.fsi:332`, `ProjectFortress/LibraryBuiltin/FortressBuiltin.fss:188-191`), and it landed them with `ZZ64` returns (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:462-463`, bodies `.fss:972-973`). With rung F merged, changing `printTime` to print a whole number of milliseconds is a one-line library edit — `round(e / 1000000.0)` in `Library/CompilerLibrary.fss` — and not a `.java` slot in a later batch. Pavol should not be asked to weigh a cost this batch has already paid.

**The revival's own rendering precedent, which the report did not search for.** Eight sites in the two target programs already render an elapsed `nanoTime` by integer division rather than as a real: six as whole milliseconds — `explorations/apl/mg/MicroGptApl.fss:124`, `MicroGptAplCheck.fss:61`, `:67`, `explorations/run-c4/src/MicroGptFlat.fss:95`, `MicroGptFlatCheck.fss:59`, `:65` — and two as whole seconds, `MicroGptAplCheck.fss:97` and `MicroGptFlatCheck.fss:95`. That is the house convention and it agrees with the interpreter. The consequence the coordinator needs: those eight sites as written will not compile on the compiled path whatever `printTime` does, because the compiler prelude's `trait RR64` has no `DIV` at all (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fsi:425-465`) and the compiler world's `nanoTime` returns `RR64`.

**The stored time is not exported.** It stays out of `CompilerLibrary.fsi`, as the interpreter keeps its own out of `FortressLibrary.fsi`. Exporting it is spellable and does not work; that is the row 320 addition above.
