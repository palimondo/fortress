# The dispatcher taking the call site's static arguments: sized in a shadow

**The answer.** The generic dispatcher is already loaded under the call site's static arguments; only its arms ignore them. Making each generic arm use the dispatcher's own static parameters is one file, one edited function and three new helpers: 43 code lines in `OverloadSet.java`, plus 1 for the switch and 3 for the variant that leaves generic arms out of a dispatcher that has no static parameters. `MieDispatchSub` then prints `Marker[Blue]`. The compiler prelude is byte-identical. The 43 compiler tests that declare generic overloads all print the same. Of the 34 that link, 31 have byte-identical classes and 3 differ only inside a generic dispatcher. Top-level functions only: generic dotted methods fail the same way and are not covered (`ScopeMethod`). Enforced, the specification's overload sentence refuses 179 declaration pairs in the library's apis under the narrower reading, 11 of them already errors today, and 6 gated compiler tests; a text scan finds 6 gated interpreter tests (§5).

## 1. How the compiled path handles generics today

- A **static argument** is the type that fills a generic's static parameter at one use. In `grab[\Blue\](b)` it is `Blue`. Usually nobody writes it: the checker infers it from the declared types at the call, so `b: Tag[\Blue\]` gives `X = Blue` (`scala_src/useful/STypesUtil.scala:912-930`).
- An **instantiation** is the generic with its static parameters replaced by static arguments: `grab[\Blue\]` is an instantiation of `grab[\X\]`.
- The compiler writes one *template* class per generic function, with `X` left in the names of the types it mentions (`Marker⟦X⟧`). The class loader stamps an instantiation from it when a class named with real arguments is first needed. For `grab⟦Blue⟧` it copies the template and rewrites every `X` in it to `Blue` (`runtimeSystem/Instantiater.java`, `MethodInstantiater.java`). The part of the name after `✚`, the template's arrow type, is never rewritten (`InstantiationMap.java:354`).
- A call that needs no choice at run time is compiled as a call to that named class. The checker's static arguments go straight into the name (`compiler/codegen/CodeGen.java:3670-3735`), so `grab(z)` with `z: Tag[\ZZ32\]` calls `grab⟦ZZ32⟧`.
- **Dispatch** is choosing at run time which declaration of an overloaded name runs, by the argument's actual type. A **dispatcher** is the method the compiler generates for that. It tests the argument against each declaration, most specific first, and calls the first that applies (`compiler/OverloadSet.java:1303-1760`). One is generated for a declaration when some more specific declaration of the same name may apply at run time. If the least specific declaration is generic, the dispatcher is itself a template, named and loaded like any generic function: `grab⟦Blue⟧` at the call site (`OverloadSet.java:2005-2062`).
- **RTTI** (run-time type information) is the object every compiled value carries that describes its type. That includes the argument of each generic supertype, one per generic name: `Mixed`'s RTTI says `Sub` of `Red` and `Tag` of `Blue`.
- How a generic arm finds its static arguments today: it asks the value for its RTTI (`getRTTI`), asks that for the argument at the arm's generic (`Sub__1()`, giving `Red`), and passes the answer to `RTHelpers.loadClosureClass`. That call spells the instance's name from the RTTI's own Java class (`runtimeSystem/RTHelpers.java:160-178`, `runtimeValues/RTTI.java:53-58`), and the loader stamps it (`OverloadSet.java:1410-1728`). Inside a dispatcher template the arms do this too: they ignore the template's `X`, which the loader has already set to the call site's argument (`javap-excerpts.txt:60-80`).
- The authors weighed the question in a comment: "Some overloads have static args, but even if they are supplied, runtime inference is still necessary (so I think) -- drc 2010-02-24 / Not quite so -- if each static parameter is mentioned in any invariant occurrence, then the supplied type is exact" (`OverloadSet.java:1981-1990`).

## 2. The design

**What the specification says.** Declarations of one name share their static parameters (`Specification/basic/overloading.tex:100-105`), so "static parameters do not enter into the determination of which declarations are applicable" (`:106-107`). The chapter assumes "that all static variables in functional calls have been instantiated or inferred" (`:136-138`), and they are "statically inferred from the context of the function call" (`expressions/var-ref.tex:37-40`). One set of static arguments, fixed at the call, therefore applies to every declaration. A declaration applies at run time if the value's type is a subtype of its parameter type at those arguments. For `MieDispatchSub`, `grab(b)` with `b: Tag[\Blue\]` fixes `X = Blue`. `Mixed` is not a `Sub[\Blue\]`, so the `Tag` declaration runs and the answer is `Marker[Blue]`.

**`MieDispatchAny`'s `grab(a)`, `a: Any`.** The specification refuses the program: `grab[\X\](t: Tag[\X\])` beside `grab(a: Any)` is an error "for one declaration to have static parameters and another to not have them" (`overloading.tex:103-105`). The question of which declaration runs therefore does not arise. If the sentence is not enforced, both readings give the same answer. The call was resolved to `grab(Any)`, which has no static parameters, so the call site supplies none. With no arguments to instantiate it, the generic declaration is not applicable. The code should refuse the pair at compile time (§5). Failing that, it should leave the generic arm out of such a dispatcher, which is the `skip` variant below. Either way `grab(a)` returns the `Any` declaration's `Red`.

**The three candidates.**
- **(a) The dispatcher gains the static arguments as parameters**, and every call site the checker resolved with static arguments pushes their RTTIs. This changes the signature of every dispatcher whose least specific declaration is generic, and the descriptor at every call site that reaches one. The template would then carry `X` twice, in its name and in its parameters. The arms would still be stamped through `loadClosureClass` from RTTI names, which keeps the `ZZ32` naming defect (§4). For `grab(Any)` it passes nothing, because that call site has nothing to pass. Not built.
- **(b) The call site loads an instantiated dispatcher named with the static arguments.** It already does, for every dispatcher that is a template (§1). The change is inside the template: each generic arm whose static parameters match the dispatcher's, up to renaming, is renamed into the dispatcher's parameters. It is then tested with a plain `instanceof Sub⟦X⟧` and called as `grab⟦X⟧` by name, and the loader turns both into `Blue`. Nothing is read from the value, and no signature, call site or template kind changes. This is the specification's model, one instantiation of the name fixed at the call, and it is the smallest of the three. Built.
- **(c) The arms keep reading from the value and skip on mismatch.** The template would need `X`'s RTTI in its body. A generic object's RTTI class reads its parameters' RTTIs from fields (`CodeGen.java:5686-5690`), but a function template has no such field, so this needs a new way to name it. Each arm would then compare the RTTI read from the value with it. Equality is wrong where `X` occurs only covariantly, because the value's argument can be a subtype of the call site's. The correct test is "read ⊑ call site" followed by instantiating at the call site's argument, and that is (b) with the reading left in. It changes every generic arm of every template dispatcher, keeps `loadClosureClass`, and keeps both defects of §4. Not built.

## 4. The two side defects

**A generic reached through a less specific declaration throws when its return type mentions the parameter.** The value-reading arm ends with a cast to the arm's declared return type, spelled with the arm's own parameter names (`OverloadSet.java:1720-1727`). In a dispatcher that is not a template, nothing rewrites `X`, so the cast is to the template class `Marker⟦X⟧` itself. `MieDispatchAny`'s `grab(a1)` throws this way under stock and `callsite` alike (`dispatch-probes.compiled.txt:31-32`, `:75-76`). The same cast also goes wrong inside a template whenever the arm names its parameters differently from the dispatcher: the loader rewrites only the dispatcher's names. Stock `ScopeArms` casts to an unrewritten `Marker⟦Y⟧` (`ScopeArms.compiled.txt:5-6`). Stock `ScopeAlpha2` gets its `Marker⟦B,A⟧` rewritten with the dispatcher's map to `Marker⟦Blue,Red⟧` (`ScopeAlpha2.compiled.txt:5`). No multiple instantiation is involved in either. **The change fixes it inside templates**: a renamed arm takes the no-inference path, whose call returns the right type without that cast, and both probes pass. It leaves the defect in non-template dispatchers (`MieDispatchAny` under `callsite`) and in dotted methods. `skip` removes that path, and the sentence makes it unreachable for top-level functions, because a set that mixes generic and non-generic declarations is refused.

**A `ZZ32` instantiation made at run time is spelled differently from the static one.** `loadClosureClass` spells each argument with `RTTI.className()`, the RTTI's own Java class: `fortress.CompilerBuiltin$ZZ32` becomes `fortress|CompilerBuiltin%ZZ32` (`RTHelpers.java:174-175`, `RTTI.java:53-58`). Static code spells `ZZ32` as `com|sun|fortress|compiler|runtimeValues|FZZ32` (`javap-excerpts.txt:6`). The dispatcher's value path is its only caller (`OverloadSet.java:1696`). `ScopeZZ32Sub` reaches it through a template with no multiple instantiation. Stock throws: `IntSub` is not a `Sub⟦fortress|CompilerBuiltin%ZZ32⟧` (`ScopeZZ32Sub.compiled.txt:5`). Under `callsite` the arm is named `grab⟦X⟧` inside the template, the loader writes the call site's own spelling, and it prints `SubM[ZZ32]` (`:10`). **The change avoids the defect on the template path and does not remove it.** `MieDispatchZZ32` and `MieDispatch`'s `grab(a)` still throw under `callsite` (`dispatch-probes.compiled.txt:81-82`, `:58-59`), and `skip` removes that path. The two spellings remain: the generated RTTI factories also build class names from `RTTI.className()` (`RTHelpers.getRTTIclass`, `:18-54`, called from `InstantiatingClassloader.java:2810`), untouched and unmeasured here.

## 5. What the specification's overload sentence refuses, measured

**The check.** It is in `checkOverloading`'s pair loop (`OverloadingChecker.scala:383`, before the existing rules; `scope-shadow.patch`, second file, 19 code lines). Two declarations of one name are refused when their static parameters differ in number, in kind, or in bounds after positional renaming. "Static parameters" has two readings for a functional method. Under `own` it is only the method's own list. Under `lifted` the trait's parameters come first, which is how the checker already builds its arrows for a top-level set (`STypesUtil.scala:123-127`). Like every rule of this checker, the check never sees a symbolic operator (`OverloadingChecker.scala:546-550`), and in a component it sees only declarations with a body (`:117-121`). ## 6. Not settled

- **The specification is not uniform on when static arguments are fixed.** `overloading.tex:136-138` fixes them before applicability. `:173-175`, read alone, says of any "call f(C)", dynamic calls included (`:135-136`): "If the parameter type P includes static parameters, they are inferred as described in \chapref{type-inference} before checking the applicability of the declaration to the call". That is the interpreter's model. The chapter it cites is empty: "This chapter will include the Fortress static type inference mechanism." (`inference.tex:15`).
- **Which static parameters a functional method has.** The specification does not say. `lifted` refuses implementations of a generic trait's functional methods, and `own` does not; this note recommends neither.
- **Whether the sentence covers operators and different arities.** It says "multiple declarations with the same functional name" (`:100-101`), and operators overload by name like functions ("Operator declarations with the same name but different fixity are not a valid overloading", `:87-88`). Taken literally it refuses scalar `juxtaposition` beside matrix `juxtaposition` unless the scalar side is padded, and `genericMethod4`'s one- and two-argument `g`.
- **The interpreter, measured in passing** (`walk.txt`). Its overload check depends on names: `ScopeArms` (`Y`) and `ScopeAlpha2` are refused at load, while `ScopeArmsX` (both `X`) and `MieDispatchSub` load. On `ScopeArmsX` it answers `TagM[Blue]` for `grab(r)` with `r: Sub[\Red\]`, a value outside the call's static type `Marker[\Red\]`; the compiled path gives `SubM[Red]`. `MieDispatchSub`'s `grab(r)` gives `Marker[Blue]` there.
- **Not built:** generic dotted methods, functional methods, `opr` and `nat` parameters (§3). Their size is unmeasured.
- **Not run:** the gate. The shadow's effect on `ant testFast` is not known beyond the 43 programs of §3.
- **The text scan is not the checker** for `tests/`, `library_tests/` and the library components. In a component it also counts abstract declarations, which the checker leaves out.
