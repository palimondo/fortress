# Facts on record

## Execution model

- F-7 Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:97-129`).
- F-8 The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- F-9 `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (`ProjectFortress/src/com/sun/fortress/Shell.java:453-458` calls `useCompilerLibraries()`; row 69). The checker on interpreter programs comes after the switch-over (P-12, "The type checker on interpreter programs.").
- F-10 The code generator lowers every type to a JVM reference type: `RR64` to the run-time class `FRR64`, so a compiled loop over `RR64` holds no `dadd` or `dmul` (`repo-internals.md:129`; the bytecode quoted in `perf-probes/boxing/REPORT.md` section 4). An array is a library object read and written through `get` and `put` (`Library/FortressLibrary.fsi:1417`, `:1468`), not a `double[]`.
- F-11 On microGPT-shaped array code boxing is the dominant representational cost: in Java models of the program's three kernels, boxed elements cost 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` (`perf-probes/kernels/REPORT.md` sections 2 and 4). No microGPT-shaped kernel compiles: the compiler prelude has no array type, and `Array`, `Vector` and `Array3` are undefined in `FlatArrays.fsi` (row 305). No array type goes into the compiler prelude; the arrays reach the compiled path with the one library (P-37, "One library, the interpreter's, is the library the compiler checks."). A failed compile leaves a 0-byte jar in the bytecode cache (row 304).
- F-12 With rows 302 and 303 fixed (the next two entries), the compiled scalar `RR64` loop `bench1t` runs in 0.74 s, against 13.06 s on the tree before them, a pair timed in one session (`compile-ladder/rung0/REPORT.md`, "The four timings"). Two costs that the boxing probe named in that loop are unaddressed (`perf-probes/boxing/REPORT.md` section 5). One is the `for` lowered to the compiler prelude's `countedseqloop`, a recursive binary subdivision over boxed indices with a closure call per element (`Library/CompilerLibrary.fss:373-381`). The other is the representational rest, which unboxed doubles would attack: the transacted volatile cell, four allocations per iteration, the interface hop to the native wrapper and the `checkcast`s.
- F-13 The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `compile-ladder/rung0/REPORT.md`).
- F-14 `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `compile-ladder/rung0/REPORT.md`).
- F-15 The benchmark numbers on record, `bench1t` 9.3441 s and `bench1h` 6.0732 s (`perf-probes/boxing/REPORT.md`, `perf-probes/kernels/REPORT.md`), are one session's: the same unmodified tree timed 13.0566 s and 8.8159 s in another (`compile-ladder/rung0/REPORT.md`, "The four timings"). Absolute seconds are not comparable across sessions; only a before-and-after pair taken in one session measures a difference.
- F-16 `ant compileAll` leaves the bytecode cache holding no library jars when it changes the implementation, and only then: it deletes the caches whole when the sources or the build differ from what the last successful build left (F-100, "**`ant compileAll` deletes the caches folder, the linker's untracked `global.map` with it, when the implementation changed, and keeps it otherwise**"), and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`. The library-order recompile of `repo-internals.md:172-185` restores the jars in about two minutes. Nothing else clears `bytecode_cache/`: with the caches kept through a rebuilt compiler, the five library jars survive and a compiled program runs (`coordinator/process-engineering/build-efficiency.md` section 2).
- F-17 The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- F-18 Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`), and its descriptor in a stamped class is `RTTIsize.of("<n>")` (F-129, "A size is carried at run time as a descriptor from `RTTIsize.of`").
- F-19 Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`Specification/basic/expressions/tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool. No program under `explorations/` writes `spawn` or `also`.
- F-20 Sizes, the `nat` and `int` static parameters, are instantiated at run time with numeric values (`Specification/basic/trait-parameters.tex:97`). The compiled checker checks them (F-67, "The compiled type checker checks `nat` and `int` static parameters"), and a sized program loads and runs compiled (F-129, "A size is carried at run time as a descriptor from `RTTIsize.of`"). Sizes check shapes when a value is made or passed; no optimization is built on them. Under walk, a `nat` parameter does not unify with a run-time-built array, while a literal size does (row 23). Walk matches sizes at dispatch, and a mismatch reads "Failed to find any matching overload", a `ProgramError` that no `catch` takes (row 254). Row 83, a `nat`-generic function that mis-unifies on its second instantiation through an api, is contested and has no reproducer.
- F-21 **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** The Working Draft's `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:49`) stops on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`; `reviews/spec-refused-examples.md`, E4). Without that clause, `fortress compile` and `fortress walk` give the same single error, `T is undefined`, at the `T` inside the extends clause (`compile-ladder/rung-maybe/REPORT.md`, "Why the specification cannot simply be transcribed"). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause, in either implementation; row 17 holds the same defect for a trait's extends clause. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at code generation, since `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4107`), but nothing reaches it. The specification keeps the declaration marked "Not allowed" and gives instantiation exclusion and the missing `excludes` clause as the reasons (`Specification/basic-lib/convenience.tex:58-73`); the parametric spelling stands (P-90, "`Maybe`'s empty case").
- F-22 **An exported function fails exactly as an exported variable does when a component's name differs from the api it exports, and the failure is the repository's, not codegen's** (`compile-ladder/rung-export-var/REPORT.md`; row 320). Both paths assume an api and its implementing component share a name: `fortress link` and `walk` print "Could not find an implementation for API … on path", and the compiled run dies with `NoClassDefFoundError`. The assumption is `Linker.whoIsImplementingMyAPI`'s fallback to the api's own name (`linker/Linker.java:72-76`); only `LinkShell`'s `alink`/`clink` register another. The specification resolves an imported api to a component that exports it (`Specification/basic/components/overview.tex:33-35`), and the team reserved the codegen half in `CodeGen.java:417-450`, `:1859`, `:6660-6666`. Gated as an expected failure by `compiler_tests/XXXExportVarRungXLinked.test`. The workaround is to name the api after its component (row 320).
- F-23 **A comment placed after a declaration that ends in an expression or a type becomes part of that declaration's source span and of the unambiguous name the parser derives from it** (`compile-ladder/rung-library-comments/REPORT.md` section 6, D1; ledger row 359). `createSpan` (`parser/Fortress.rats:145-157`) trims back over space characters only; a declaration ending in `end` is unaffected. So a comment-only library edit is not neutral at the syntax-tree level, and a before-and-after comparison of parse trees or diagnostics maps positions back first. The report's scripts for that, `parse-compare.sh` and `remap-lines.py`, print with `git show ab067d9b6^:explorations/compile-ladder/rung-library-comments/<name>`.
- F-24 **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees** (`compile-ladder/rung-int-semantics-walk/REPORT.md`, section 4.1): `throw new FortressError((FObject) Driver.getFortressLibrary().getRootValue(name))` from a `builtinPrimitive` method reaches `Evaluator.forTry` unchanged; the helper is `Int.overflow()` (`interpreter/glue/prim/Int.java:258-261`). Gated by the `overflows(...)` assertions of `tests/IntSemanticsRungI.fss`. The natives that raise `IntegerOverflow` so are those of F-125, "The interpreter's integer rules" and F-132, "Under `walk`, fixed-width integer arithmetic raises `IntegerOverflow` when the result does not fit", with the narrowing checks `Int.rc` and `NN32.rc` (row 347, fixed). Every other Java exception of a native is wrapped in a `ProgramError` (`FunctionClosure.java:191-196`), which no `catch` takes, so row 336's division by zero ends the run.
- F-25 **The compiled run's class loader takes its first load of a name under the JDK's class-loading lock, and a generic arm's first load is safe on four threads** (`compile-ladder/rung-generic-runtime/REPORT.md` sections 1, 11, 12; row 417, fixed). `InstantiatingClassloader.loadClass` runs under `getClassLoadingLock(name)` (`runtimeSystem/InstantiatingClassloader.java:180`), as the JDK's `ClassLoader.loadClass` does; no loader in the tree registers as parallel-capable, so the lock is the loader's own monitor, and the explicit loads (`RTHelpers.loadClosureClass`, `RTHelpers.getRTTIclass`, the union instantiation) are under it too. Gated by `compiler_tests/FirstLoadThreadsRungG`, which the gate's four-thread atomic runs also run (`coordinator/climb-batch-workflow.js:1304`).
- F-26 **Walk chooses between a generic declaration and another on their declared domains, so the order they are written in no longer decides** (`compile-ladder/rung-walk-dispatch/REPORT.md` section 5.1; P-45, "Overloads may differ in ..."; row 548, fixed). `OverloadedFunction.bestMatchInternal` keeps a candidate by `moreSpecificDeclaration` (`interpreter/evaluator/values/OverloadedFunction.java:1570-1575`, `:1710-1717`): beside a generic function or constructor the declared domains are compared through the symbolic instantiation (`instanceHolding`, `:1666-1681`), otherwise the instances' domains; a generic trait's functional method and a generic dotted method keep the instance comparison. A chosen generic instance that converts an argument dispatches again (`convertedCall`, `:1597-1614`), not for overloaded methods. The symbolic instantiation is keyed by each static parameter's kind and bounds (`GenericFunctionOrMethod.java:57-68`; row 478, fixed), not by a `where` clause (`FGenericFunction.java:49-51`). Gated by `tests/DispatchDeclaredDomain.fss`, `DispatchConvertedAgain.fss` and `GenericOverloadBoundsApart.fss`.
- F-27 **Walk's load check reads a generic declaration beside a plain one on declared domains, and covers an overlap through `comprises` clauses, where its parameter-by-parameter check refuses** (`compile-ladder/rung-walk-dispatch/REPORT.md` sections 5.3 and 5.4; P-46, "A conversion makes a call possible, and never changes which declaration runs when one already fits." and P-60, "The specification reads a `comprises` clause at the level of values (PLAN item 26, row 491)."; row 492, fixed). Both run only where the parameter-by-parameter check refuses (`OverloadedFunction.java:507-510`). For one own generic beside a plain declaration, `validOnDeclaredDomains` (`:730-759`) compares declared domains under the return-type rule and accepts an overlap that plain declarations below both cover, reading each parameter of the generic as the types whose intersection holds its values: a type parameter as its bounds that name no static parameter, a type that mentions a static parameter as `Any`, any other type as itself (`genericOverlapCovered`, `:773-815`; row 552, fixed). For two plain declarations with an unrelated parameter pair, `overlapCovered` (`:851-862`) cuts the overlap by the `comprises` clauses (`overlapPieces`, `:1023-1067`). Both need every part of the overlap inside one declaration below both, and refuse what the search cannot settle (`overlapCoveredBy`, `:880-940`; `intersectionPieces`, `:963-1013`). Two generic declarations keep the parameter-by-parameter check alone, so walk refuses such a pair unless some parameter pair excludes (row 159; the report's section 11, decision 1). Gated by `tests/ComprisesMeetWalk.fss`, `ComprisesCoverReturn.fss`, `GenericBesidePlainTwoBounds.fss` and `GenericBesidePlainOverlapShapes.fss` (row 552); by the refusals `XXXGenericBesidePlainReturnRule.fss`, `XXXComprisesMeetUncoveredWalk.fss` and `XXXComprisesCoverReturnWrong.fss`, programs walk must refuse at load; and by `XXXOverloadExistentialMeetWalk.fss`, the expected failure of row 539, a valid set that walk refuses. Walk checks the closure of the main component's `comprises` clauses (row 551), not yet the library's (rows 595, 596), another component's (row 551) or an object expression's (row 597; F-29, "Walk checks at load the `comprises` clauses of the program's main component ...").
- F-28 **Walk instantiates a generic declaration declared to return `Any`** (`compile-ladder/rung-walk-dispatch/REPORT.md` section 3; row 157, fixed): `MakeInferenceSpecific.forAnyType` is a no-op like `forTraitType` (`interpreter/evaluator/MakeInferenceSpecific.java:72-75`). Gated by `tests/GenericReturningAny.fss`; row 496's probe `PlainBesideZZ32` prints `Marker[ZZ32]` under walk. - F-29 **Walk checks at load the `comprises` clauses of the program's main component, and its harness names an expected refusal at load** (`compile-ladder/rung-walk-load-check/REPORT.md`; row 552 fixed, row 551 for the main component's clauses). `BuildEnvironments.checkComprisesClauses` (`interpreter/evaluator/BuildEnvironments.java:1153`), called from `Driver.evalComponent` once every component's types are built (`interpreter/Driver.java:227`), reads the declarations as written and asks every extender of a closed trait of the main component for the traits chapter's three eligible forms, reading a generic child's extenders across the whole program; the library's clauses (rows 595, 596), another component's (row 551), an object expression (row 597) and the clause's other half, that a listed type extends each instantiation (row 598), are not read. ## The checker and the one library

- F-32 **The one library binds its natives by 424 `builtinPrimitive` calls, and the compiled path cannot reuse walk's glue classes behind them.** The glue classes take walk's boxed values. Against the compiler's static helpers, 147 bindings change only their text (P-58). 61 have a helper that nothing binds, 25 of them under a name that the compiler prelude gives another helper (row 348). 138 need a new helper, and 78 need more. Every program's output needs `Writer`'s natives. MicroGPT also needs `nanoTime`, whose compiled helper returns `RR64`, `getProgramArgsPrim`, which `System` calls as it loads, and `NativeArray`; the last two have no compiled analogue. They are PLAN's phase 4. Detail: `perf-probes/prelude/natives-shape.md` section 2.
- F-34 **Between the interpreter's library and bytecode stands the checker, not disambiguation, desugaring or code generation.** Compiled as it is, the library gives 1,417 disambiguation errors, all collisions between the two preludes, an artifact. With `FortressLibrary` the prelude, disambiguation, desugaring and the overload rewriting report none. Code generation, measured once, refuses 4 declarations that the checker passes: two `AsIfExpr`, one `LetFn` and one call on an intersection-typed receiver. The rest fall where the checker fails, or on synthesized overloads. The dispatch generator refuses 12 of 198 overload sets, each a functional method and a top-level function with one signature. Detail: `perf-probes/prelude/switch-over-distance-flat.md` sections 3 and 4.
- F-35 **The `FortressLibrary` api has 25 declarations with a dead size, a size parameter that occurs in no parameter type, return type or body.** They check clean (P-40). Where the component omits the dead size, the export checker reports the api's declaration missing. Six vector `DOT` and juxtaposition operators have this shape, `[\T, nat n, nat m, nat p\]` in the api and `[\T, nat n\]` in the component, and give one of the distance's export errors (F-53). P-40 lets the dead sizes go only by a diff shown to the curator with the switch-over's design. Detail: `perf-probes/nat/REPORT.md` sections 2 and 7.
- F-36 **The code generator's `FnNameInfo.boundsFor` gives a size parameter a size argument, and every other kind a type argument.** A `bool`, `dim`, `unit` or `opr` parameter still gets a type argument, a latent defect; the checker refuses the first three by name (F-67). A size symbol stays in the mangled name and needs no descriptor. Only a literal size reaches the class loader, which takes its descriptor from `RTTIsize.of` (F-129). Detail: `perf-probes/nat/java.md` sections 1 to 3.
- F-37 **The one library's own sizes are the literals 0 to 3, and a compiled `typecase` on a size tests the value's own class.** A `typecase` tells `Vec[\ZZ32,3\]` from `Vec[\ZZ32,4\]` compiled by one `INSTANCEOF`, also when the size is a static parameter. A `typecase` that is a whole function body, with clauses that need a coercion, fails in code generation, size or not (row 340). Gated by `compiler_tests/NatRtCase` and `NatRtCaseGen`. Detail: `reviews/size-runtime-design-brief.md` section 5; `perf-probes/nat/size-probes.md` section 4.
- F-38 **The compiled dispatcher chooses an overload arm generic in a size by the value's size, and the arm reads its size.** Called with an argument typed `Any`, the dispatcher reads the size off the value's descriptor. The checker's return-type rule compares the arms' own sizes (row 410). The dispatcher skips the bound `Object` that the compile path gives a size parameter (row 412). Gated by `compiler_tests/NatRtDisp`, `NatRtDispSize` and `NatRtDispTrait`. Detail: `perf-probes/nat/size-probes.md` section 2.
- F-39 **An operator static argument is a compile-time name on both paths and by the specification, and no code reads it at run time.** The specification and walk substitute its name into the trait's methods; the compiled path carries it in the class name, with no descriptor. Only two tests declare an `opr` static parameter. Compiled, `Op[\+\]()` dies with `NoSuchMethodError` on its descriptor's `factory()` (row 366). A three-line fix in `MethodInstantiater` works on its reproducer, and the row waits (P-123). Detail: `perf-probes/nat/opr-kind-history.md` sections 2 and 3.
- F-40 **A size costs a few kilobytes at load and nothing on the hot path, and only the overload dispatcher reads a size off a value.** No optimisation uses a size. A sized loop is no faster, since boxing and a transaction check per local variable cost about 31 ns per element. A call dispatched on a size costs about 4 to 20 ns more than a resolved one. The checker checks a shape once per call site; at run time, once per arm tried and per type test. Detail: `perf-probes/nat/size-cost.md`, "The answers".
- F-41 **The compiled dispatcher tests `DOT`'s shared size for equality in both directions before it chooses the shared-size arm.** It is the team's check for a type variable in two invariant positions. A mismatch goes to the catch-all on both paths, and the checker gives a static mismatch the catch-all's signature without an error. By reading, the matrix product's shared inner size takes the same check. A size made by `array[E](n)` gets one descriptor per number from `RTTIsize.of`. Gated by `compiler_tests/NatRtDot`. Detail: `perf-probes/nat/size-rung-probes.md` sections 2 and 3.
- F-42 **A unit's earlier error hides its overloading and return-type checks, and the checker refuses a local function's parameter left untyped.** `StaticChecker` runs the overloading rules only on a unit with no earlier error, so clearing an early error can raise a count (F-53). The checker refuses an untyped local function parameter, "Missing parameter type for i", as at top level (rows 620, 621). The specification leaves the inference there undescribed (Appendix I), so write the type. Detail: `perf-probes/nat/zero.md` section 1.
- F-43 **The overloading checker's memo hides errors by build order, so every count runs with it off.** The switch is `fortress.analyzer.overload.cache=false`, which the gate's stages set. The checker renames an inherited method's own static parameters apart from its trait's before it compares them, so `Generator.generate[\R\]`, inherited by `PossibleReductionPair[\R\]`, keeps its own `R` (row 561). Gated by `compiler_tests/InheritedMethodStaticParamSameName`. Detail: `perf-probes/nat/triage.md` sections 1 and 3.
- F-44 **The compiled checker enforces the designers' "multiple instantiation exclusion" and relies on it, and the one library meets it.** The return-type rule relies on it, so relaxed alone it admits programs that die with `IncompatibleClassChangeError`. Walk lacks it (row 416). P-43 keeps it. The library meets it through `TotalComparison`'s supertypes (row 461), `AnyMaybe` extending `AnyUniqueItem` alone, and `andCondCombine` choosing `andRelCond`, so a program's own `ANDCOND` of two relational predicates is not relational under walk (row 458). Detail: `reviews/multiple-instantiation-exclusion.md` sections 1, 2 and 5.
- F-45 **Without the exclusion rule, every dispatcher must call its generic arms at its own static arguments, and no published work resolves double membership under run-time dispatch.** These prices decided P-43. F-136 builds that call for template dispatchers; generic dotted methods, other dispatchers, and `opr` and `nat` arguments lack it (rows 495, 496). The 2012 patents' forest rule lets a self-typed generic stand at several instantiations along a chain, but alone it leaves the specialisation hole open; F-46 closes it. Detail: `reviews/mie-probes/scope-call-site-dispatch.md` section 3; `literature.md` beside it.
- F-46 **Route C, the patents' forest rule with a return-type rule over every level of a chain, closes the specialisation hole, but a return to it needs work beyond the checker.** Built as a shadow, it refuses 25 pairs of the nested tower's declarations. Completing the tower needs `comprises T` on the eight self-typed traits, which overflows the checker. Leaving P-43 for it needs the tower un-flattened, the call-site fix in every dispatcher, a method per level in the code generator, walk's work and a way past the overflow. Detail: `reviews/mie-probes/route-c-experiment.md` sections 2 to 4.
- F-47 **The exclusion rule refuses some of the specification's own examples, and a parametric object with a factory, or a widening function, runs in their place on both paths.** F-167 lists them. The where-clause examples stop earlier on both paths, at `T is undefined`. A marker object with a coercion in the generic trait also runs compiled, and walk applies such a coercion (row 389). The 2012 `covariant` keyword passes the checker and dies at run time (row 404), and a generic coercion is refused as a cyclic hierarchy. Route C (F-46) would rescue none of these examples. Detail: `reviews/spec-refused-examples.md`, "What was found".
- F-48 **The compiled checker's exclusion rule compares type arguments and literal sizes only, and its abstract-method check does not substitute an operator argument.** Two booleans, or a static parameter against another argument, count as no exclusion (rows 406, 414). Compiled, a subtrait that inherits an abstract method named by an operator static argument is refused even at one instantiation; the specification and walk substitute the name. The code generator throws on `Any` as a static argument in an `extends` clause. Gated by `compiler_tests/XXXNatExcludeChecker`. Detail: `reviews/spec-refused-examples-judgement.md` sections 4, 6 and 9.
- F-49 **Walk chooses between a value form and a function form of one name by the argument's run-time type, so with the element type `Any` a function passed as the value goes to the function form.** The one library has no such pair (F-158). The checker refuses such a pair under the bound `Any`: a functional whose one parameter has a parametric type bounded by `Any` cannot be overloaded. Declared where the array diamond meets, the pair clears the diamond's refusals; declared in the leaves alone, as `copy` is, it does not. Detail: `reviews/fill-overloads-ways.md` section 2.
- F-50 **The compiled checker lets overloads differ in static parameters, as the specification's 2011 model does, and refuses only the pairs it cannot prove unambiguous.** It builds P-45. It cannot prove a pair over open traits that nothing declares exclusive, nor one whose domains exclude only through the exclusion rule and a bound. It never checks a pair of symbolic operators (row 584). Two generic arms on a bare type variable fail compiled (row 537). Walk runs an arm whose size the call leaves unfixed, unbound, where the checker refuses the call or drops the arm (row 400). Detail: `reviews/overload-static-params-ways.md` sections 2 and 3.
- F-51 **A generic call converts a narrower argument for a parameter typed by a type variable that another argument fixes, on both paths.** For `scale[\T\](b: Box[\T\], x: T)` and `b: Box[\RR64\]`, `scale(b, 3)` takes `T = RR64` and converts the `3` (row 388, fixed). So under walk the library's vector and matrix operators take a `ZZ32` scalar with `RR64` elements. F-73 and F-137 give each path's rule. Gated by `tests/InferCoercionRungK` and `compiler_tests/InferCoercionShapes`. Detail: `reviews/numeric-hierarchy-integration-review/row388-container-probe.md`.
- F-52 **An empty reduction's identity comes from its static argument, a mixed-width call takes the narrowest type its arguments convert into, and neither path can build `RationalQuantity`.** A form with no argument cannot be overloaded by its result type alone (F-59), and F-55 holds the mixed widths. A manual compaction between turns leaves a running Workflow alive: its agents keep writing through the compaction and go on to their results. The transcripts record the interrupt, not the control that sent it; in one case the curator's own words confirm the client's stop control. Not tested: an automatic compaction mid-turn, and an interrupt during the Stop hook while a run is alive. The rule: send messages at any time; compact between turns; do not stop a turn while the session is working, including the seconds after a reply while the transcript backup runs; after an accidental stop, say so and resume the run with `resumeFromRunId`, which keeps every agent that had finished (the next entry; P-127, "Check-ins and stops"). An `Agent`-tool worker killed by an interrupt cannot be resumed: a `SendMessage` to it is refused ("was stopped by the user and won't be resumed ... only launch a new agent if the user explicitly asks"), so it is relaunched only at the curator's explicit ask, and the new worker is told its predecessor's leftovers (session `fe616d40`, six workers stopped by one interrupt). A Fable worker told to read its predecessor's transcript was ended by the API's safety filter as it printed the transcript's tail (`reasoning_extraction`, the false positive of the `agent()` entry below), so a Fable worker is given the leftovers in the tree and no transcript.
- F-201 **A restart of the session's own process kills its background runs, and `resumeFromRunId` then recovers every agent that had finished** (session `fe616d40`; the environment manager's log `/tmp/env-manager.log`). A restart of the session's process (`environment-manager task-run … --session-mode resume`), whether the platform's cap (F-202, "The platform stops the session's process ...") or a VM restart (the VM entry above), stops every Workflow run and every `Agent`-tool worker alive at that moment. The conversation, the session ID, worktrees, untracked files, transcripts and each run's journal survive, and so do shell scripts the workers had started in the background. So the run is resumed, not relaunched: the same script and arguments as at its launch, with `resumeFromRunId`. A finished agent's result is kept, an unfinished one runs from its start, and its worktree's leftovers are its starting point; a relaunch from the base restarts at the first stage instead. An `Agent`-tool worker continues from its transcript on a `SendMessage`. The resume reuses the longest unchanged prefix of the run's `agent()` calls in call order, so it needs the launch's arguments byte for byte and the same order of calls: a base given as a short hash where the launch gave the full hash misses the cache from the first call, and when cached stages resolve at once, a pipeline may call its next stage in another order than the live run did and miss from there. A run whose script has changed since launch is resumed from a copy of the script as launched (`git show <base>:<path>`). Where the call order would differ, the copy forces the live run's order, prompts unchanged, by wrapping `agent()` so that the finished calls are issued in the journal's order of their `started` lines. A copy that changes only what follows the cached prefix (a gate skipped, a commit's prompt extended) runs the changed call live and nothing before it. A stage stopped mid-work can leave its work in the tree. A commit stage killed before it had committed leaves its edits in the main tree, uncommitted, and a resume whose commit prompt names them (a changed prompt, so a new key) checks and keeps them and lands the batch. A gather killed mid-work leaves partial staged state, which is stashed and moved aside before the resume; the gather then runs again live from its start under its key, and the journal holds two `gather` lines under one `launched` line (`compile-ladder/climb-batch-6.5b/RECORD.md`, "A relaunched gather"). The run's journal is `journal.jsonl` in `~/.claude/projects/<project>/<session>/subagents/workflows/<run>/`: one `launched` line, then a `started` line per agent call (`key`, `agentId`, `label`, `phase`) and a `result` line with the same key and the agent's structured result, none for an agent that returned nothing. A resumed run appends to the same journal, and an agent run live again under a key the journal holds gets a second `started` line (`coordinator/tools/journal-text.py` reads it). A new session cannot resume another session's run (`remote-container.md` § The 2026-09-18 restart, and § Recovering a session whose container died, step 5).
