# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The compiled path measured 6.8× on a scalar `RR64` loop, 8.9× on object-allocating code, 8× on startup, numerics identical (`compiled-path-gaps.md:45, 100-101`); what blocks it is its 592-line prelude (no `List`, no generic `array`, no `exp`/`log`, no `SUM`, an empty `Matrix`), not code generation (rows 71-82).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- **On microGPT-shaped code, boxing is the dominant representational cost, and nothing microGPT-shaped runs on the compiled path today** (measured 2026-09-15, `perf-probes/kernels/REPORT.md`, which corrects the boxing probe's scalar-loop conclusion below as Pavol suspected): the three kernels the program is made of (a 4192-element dot product, a 16×16 matrix product, the row lift with `rmsn`) all fail to compile with `Array is undefined`, `Vector is undefined`, `Array3 is undefined` in `FlatArrays.fsi` (77 errors): the compiler prelude lacks the array TYPES, not only the constructor (wider than ledger row 72; ledger row 305). In Java models of those kernels, boxing as the runtime boxes costs 6.3× (dot), 6.5× (matrix), 2.6× (row lift) over `double[]`, because array element results escape and cannot be scalar-replaced; the generic array object adds only 1.6-9% on top. On the interpreter, the only path that runs them, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch, 0% number representation (JFR on `krows`). A fairly written scalar loop (literals hoisted, no `:=`) compiles to 9.7× primitive Java; JFR on the real compiled run puts 88.9% of the mutable-variable loop under `BaseTask.inATransaction()`'s eagerly built debug string (`BaseTask.java:248`, `Thread.toString()` through `StringBuilder`). Order that follows: (1) an `RR64` array type in the compiler library (G2) so the kernels exist on that path; (2) the two one-line defects, the debug string and `FFloatLiteral`'s String round-trip; (3) unboxing and `double[]`, where the remaining ~6× on array code lives, designed into (1) rather than retrofitted. Also: a local function does not compile (`Can't compile LetFn`, `CodeGen.java:1552`, ledger row 304); a failed compile leaves a 0-byte jar in the bytecode cache.
- Rung 0's two fixes took the eager debug string (row 302) and `FFloatLiteral`'s String round trip (row 303) out of the scalar loop, so the boxing probe's own reading of the unrepaired tree — 156× primitive Java, of which boxing was about 2 %, with `countedseqloop`'s boxed indices and closure call (about 7 %) and the representational rest (about 30 %) still unaddressed — is history (`FACTS-history.md` § Execution model; `perf-probes/boxing/REPORT.md`).
- **The two one-line runtime defects are fixed** (2026-09-17, rung 0 of the plan, `compile-ladder/rung0/REPORT.md`, `before.out`/`after.out`): guarding `BaseTask.inATransaction()`'s debug message with the `debug` flag it already had (`BaseTask.java:248`, ledger row 302) takes the compiled `bench1h`, the loop whose literals are hoisted so the transaction check is the only defect left in it, from **8.8159 s to 0.7287 s** (loop-only medians of 3, JDK 25, 20 M iterations, same freshly rebuilt library jars on both sides).
- **Caching the `double` in `FFloatLiteral`** instead of keeping the literal as a `String` and re-parsing it in `asRR64()` (ledger row 303) takes the compiled `bench1t`, which builds both float literals inside the loop, from **13.0566 s to 0.7384 s**; the literals' own share, the `bench1t` minus `bench1h` difference, falls from 4.2407 s to 0.0097 s, so the per-iteration decimal round trip is gone (2026-09-17, `compile-ladder/rung0/`). The gate after both edits: `ant testFast` 1,377 tests, `ant testSystem` 382 tests, zero failures and zero errors.
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine; the 2026-09-17 before-run of the same unmodified tree measured 13.0566 s and 8.8159 s, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes (observed 2026-09-17).
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); whether `nat` parameters are baked into stamped classes is unprobed.
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see the prelude section). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half).

## What the conformance review of the eight rungs established (2026-09-17, `reviews/rung-conformance-1-4.md` and `-5-8.md`, verified in this session)

- The review's first finding, a top-level mutable variable compiled outside the transaction, has been repaired: what the compiled path does now is the repair-batch entry in the ladder section below, the finding as it stood is in `FACTS-history.md` § What the conformance review of the eight rungs established, and the gate rule it exposed is the thread-count entry in that same section (`compile-ladder/repair-r1-atomic-static/REPORT.md`).
- **The team already folds `IntLiteral` arithmetic at compile time and warned against doing it at run time.** `IntegerLiteralFoldingVisitor.java` folds the operators in `BigInteger` and `phases/PhaseOrder.java:57,142` wires `INTEGERLITERALFOLDING` before `TYPECHECK`; three lines below the comparison block rung 6 cited by line number, `FortressBuiltin.fss` carries the team's comment, verbatim: "Do not enable these until coercion is implemented; doing so will cause all our arithmetic to occur on IntLiterals". Rung 7's run-time bodies are nonetheless genuinely needed, because folding is syntactic and cannot see a literal bound to a variable, which is the case its three files hit; what it landed without was the knowledge that the phase exists, so the throwing bodies read as unfinished work rather than as the bodies of a case the team meant to be folded away, and the two mechanisms now disagree on the same values: `println (4294967295 + 1)` folds to the correct `4294967296` while the same arithmetic through two variables gives `0`.
- **Citing `Specification/library/apis/*.tex` as an independent standard is circular.** `Specification/library/structure.tex:25-31` says in the team's own words that Part Library "is largely automatically generated from the API code for the libraries themselves" and that the libraries are "presently in a state of flux", so `library/apis/CompilerBuiltin.tex` is a rendering of `CompilerBuiltin.fsi` and cannot justify an edit to that same file. Two rung reports cited it as the published api or the spec's shape. The prose chapters of `Specification/basic/` and `basic-lib/` are the standard; the api renderings are not. Sharper still (2026-09-19, batch 1's record worker): the rendered `library/apis/*.tex` files are not in the tree at all, they are generated at spec-build time from the `.fsi` sources (`Specification/library/default-libraries.tex:27,39`), so the `(api listing)` citations of ledger rows 314 and 316 and of `library_tests/IntLiteralArithRung7.fss:30-31` name paths that cannot be opened; the `(api listing)` convention should cite the `.fsi` line instead.
- **The specification makes an integer literal arbitrary precision** (`basic/expressions/literals.tex:83-85`, a digits-only numeral having the value of the numeral interpreted in radix ten, with nothing bounding it), and gives wrapping its own operator spellings (`basic-lib/basic-integers.tex:369-370, 400-401`), so the literal wrap of ledger row 317 is a violation predating the ladder rather than an unaddressed case.

- **Checked integer arithmetic keeps integer loops scalar on the JVM** (2026-09-17, from the rung 6 skeptic's overflow finding; recorded at length in `performance-roadmap.md` under "Corrections recorded on the way"): `+` on `ZZ32` binds to `jIntOverflowingAdd` (`LibraryBuiltin/CompilerBuiltin.fss:625`), whose helper (`nativeHelpers/simpleIntArith.java`) tests the sign bits and throws `IntegerOverflow`, which the spec mandates (`Specification/basic-lib/basic-integers.tex:114-117`; `⊞`/BOXPLUS is the wrapping operator, `CompilerBuiltin.fss:626`); HotSpot's SuperWord vectorizes only counted loops with no control flow in the body, so a branch per operation, however cheap scalar, forecloses SIMD. The consequence for the roadmap: step A5's "SIMD comes free from HotSpot" holds for floating-point loops, which is where microGPT's hot arithmetic is (`RR64`, no trapping), and not for the integer indices, counters and reductions around them, nor for A2's address arithmetic. Four remedies exist, cheapest first, and the roadmap lists them; none is worth doing before the loops are measured.

## What an autonomous climb costs in wall clock (measured 2026-09-17, `explorations/coordinator/iteration-cost.md`)

- **The eight-rung climb took 8h37m and every minute of it was serial**: 36 agents, no two ever overlapping, the sum of agent walls plus the 35 inter-agent gaps equalling the span exactly. Of the 508.3 agent-minutes, 57.8% was inside tool calls and 42.2% was model thinking, so no build optimization can buy back more than 57% of anything. Whole rungs in parallel worktrees buy nothing for the same reason: cores, not disk, are the constraint (a worktree costs 293 MB). What overlaps is a model-bound stage against a tool-bound one — `plan` is 68% model time and `implement` 76% tool.
- **The three-component bytecode-cache rebuild is 4.7× the five-component one** where the edit is downstream of `AnyType` and `CompilerBuiltin`: 24.6-30.4 s against 110-162 s, found by the rung 8 agents in the climb's last hour after 20 of 22 rebuilds had used the long form.

## The interpreter's library fed to the compiler (measured 2026-09-16, `perf-probes/prelude/REPORT.md`)

- Only 211 of `FortressLibrary.fss`'s 4,518 lines (4.7%) are the 108 `builtinPrimitive` native bindings; the rest is plain Fortress. Whole interpreter library: 427 bindings across nine files. The interpreter's glue classes take the evaluator's boxed values and cannot be reused by the compiled path; the compiler's natives are static Java methods, and `nativeHelpers/` already ships 355 of them, covering about 79 of the 108 by another name.
- `fortress compile Library/FortressLibrary.fss` as it is: 1,417 errors, all in DISAMBIGUATE, all name collisions because both preludes are in scope; an artifact. With `FortressLibrary` made the prelude (a driver over `Shell`'s public entry points, no tracked file changed): disambiguation passes with zero errors; the type checker then reports 92 errors in the library's own apis (36 `X excludes Y but it extends Y`, 26 `types exclude each other`, 26 `Integral[\I\]` bound failures, in the comparison and numeric tower) and then **crashes: `Not yet implemented`** in `STypesUtil.makeInferenceArg` (STypesUtil.scala:546-559) for `nat`, `int`, `bool`, `dim` and `unit` static parameters. Desugar and codegen are never reached.
- **The Scala type checker does not implement `nat` static parameters at all**: a six-line program with a `nat` parameter fails on the compile path (`Not yet implemented` inferred, `ClassCastException` explicit) and runs on the interpreter. The interpreter's library has 81 such declarations, C4's vocabulary 30; `CompilerLibrary` has one, the empty `Matrix`. So the sized-array vocabulary cannot pass the compile path's checker today, and the static dimension checking the `nat` design promises is not implemented anywhere.
- **Between the interpreter's library and bytecode stands the checker, not desugaring or code generation** (2026-09-20, `perf-probes/prelude/desugar-codegen.md`, the library pushed through DESUGAR and CODEGEN with the checker's failures caught per top-level declaration, validated on `CompilerLibrary.fss` where the method reproduces the ordinary compile exactly): of `FortressLibrary.fss`'s 446 top-level declarations the checker passes 237 clean, reports errors on 97 and crashes on 112 (81 `makeInferenceArg` nyi, 29 `TraitType→IntExpr`, the `nat` gap); DESUGAR and OVERLOADREWRITE then report zero diagnostics on all of it; CODEGEN emits 275 and refuses 313, of which only **5 are on declarations the checker checked clean** (four a numeric static argument, one a method call on an intersection-typed receiver); the rest are missing annotations on unchecked declarations (227), the two missing visitors `Juxt` (53) and `Label` (1), `nat` static arguments (14), malformed overload sets (7); `canCompile` refused nothing and no native binding was missing. Two obstacles the earlier counts did not show: the compile path's own `extends Object` pre-desugaring (`Shell.java:371-386`) adds 712 of the 960 checker errors in the prelude apis and 618 of 1,204 in the component, rejecting every generic instantiated at a tuple type, more than the 93 tower errors; and overload dispatch generation does not terminate on this library's exclusion graph (1,046 s, stopped by hand), so it was switched off for the measurement.
- Plain-Fortress library code without `nat`s passes the checker: `FlatArrays.fsi` type-checks with zero errors of its own against the interpreter prelude; its only failures are the prelude's and the `nat` crash. A minimal `Array`/`Vector` shim for the compiler's world is not possible; FlatArrays uses the array protocol (`fill`, `map`, `ivmap`, `t()`, `get`/`put`/`init0`/`replica`), which is `NativeArray.fss` plus about 1,000 lines of the library.
- Therefore "use FortressLibrary for the compiler too" is, in order: implement `nat`/`int`/`bool` static parameters in the checker; fix or relax the 92 tower errors; port the native bindings (the smallest part). Supersedes the coordinator's guess of 2026-09-15 that the library would "fail the checker in places nobody has counted": counted now, and the wall is the checker, not the library.

## A user grammar on the compile path (measured 2026-09-16, `perf-probes/grammar-compile/REPORT.md`)

- As shipped, a grammar-importing program stops at DISAMBIGUATE on the compile path with 1,342 errors, none in the program: every grammar api imports `FortressSyntax`, which imports `FortressAst`, which imports the interpreter's `FortressLibrary`, so the two preludes collide. The GRAMMAR phase is in the compiler's phase order and `GraphRepository.syntaxExpand` serves both worlds; what is missing is a compiler-world spelling of `FortressAst`/`FortressSyntax`.
- With two probe-only shims shadowing `FortressLibrary` and `List` on the source path, the collision is gone, Rats! runs under `fortress compile`, and a user grammar compiles to bytecode and runs (`twicep⦇ 21 ⦈` prints 42).
- Behind that wall the type checker does not know templates: there is no `TemplateGap`/`_SyntaxTransformation` case anywhere under `scala_src/typechecker/`. Consequences: an expansion in argument position must be parenthesized by the template text itself (`Argument to function must be parenthesized`); a template naming a function declared in the using component (ledger row 270, the mechanism the focused base's named functions rest on) crashes the post-typecheck assertion (`ClassCastException: BoxedUnit cannot be cast to AbstractNode`); a typed lambda written in a template (row 285) fails with `Unbound type: ZZ32`, the type never disambiguated. So rows 270, 282 and 285, the APL ladder's whole division of labour, are interpreter-only facts, and the APL microGPT cannot go through the compiler until the checker learns templates. Ledger rows 288-291 (merged 2026-09-16).

## The territory map (2026-09-16, `explorations/coordinator/map/`)

- Four survey reports and a synthesis (`map/README.md`, parts 5-7: the gaps on the path in dependency order, the loop, touch-this-affects-that). Read the map before ordering any edit under the sealed tree; this section keeps only what other sections do not have.
- The editable surface is about 148,000 hand-written Java lines and 19,700 Scala lines; 533,353 Java lines are generated and checked in (`map/modules-and-phases.md` A.1). The AST is the only IR from parse to bytecode (B.1).
- The two paths share phases 1-4 exactly; the interpreter's TYPECHECK phase is present but inert (`Shell.java:1275`); `fortress run` never enters `Shell.java`, it is a second JVM with `bytecode_cache` first on the classpath (`bin/fortress:15-18`, `bin/run:41`). Which desugarings run is a `Shell` flag, not the path: coercion, chained comparison and compound assignment are gated on `use_scala`, which `walk` turns off (B.5; `spec-to-implementation.md` §2).
- A user grammar is expanded before phase 1 runs on the component (`GraphRepository.java:511`); the GRAMMAR phase processes apis only (B.3).
- The api cache key hashes the source directory path, not content (`NamingCzar.java:244-254`); staleness is by file date alone (B.10).
- Tasks and transactions are implemented twice, `interpreter/evaluator/` and `runtimeSystem/`, independently (B.11). Row 302's fix is in the compiled world's copy only.
- `import java` also works on the interpreter path through `ForeignComponentWrapper` + `ClosureMaker`; no test uses it (B.12).
- Codegen refuses any declaration carrying a where clause or a contract (`CodeGen.java:2937, :2941, :4076, :4078, :4983, :4985`); not in the ledger (flagged, Pavol's call). `atomic <expr>` has no visitor, `atomic do … end` compiles; `spawn`, `label`/`exit`, object expressions, array literals and comprehensions, local function declarations have no visitor (`spec-to-implementation.md` §3).
- The checker (`IndexBuilder.scala:187-189`) refuses `type` aliases, `test` and `property` on both paths. Coercion is the one mechanism the compiler path has and the interpreter does not (no `Coercion`/`coerce` under `interpreter/`; row 19).
- **A generic object referenced without its static arguments is a static error on the compiled path, and the checker never consults the expected type for it** (2026-09-19, `explorations/compiler-probes/maybe-inference/inference.md`): `b: Box[\ZZ32\] = Box` fails with `Ill-formed type: Box`; a bare `Empty` as a call argument or a field default fails with `T is not in the kind env`, an internal `bug()` from `TypeAnalyzer.scala:766` reported at the declaration's span; the same forms with the static argument written compile and run on both paths. The decision is in the checker's `SVarRef` case, `typechecker/impls/Misc.scala:624-641`, whose `:639-640` keeps the uninstantiated type under the team's own `TODO: handle missing static args`; static-argument inference exists only for arrows (`STypesUtil.scala:912-930`, called from application and coercion), and a parametric empty case reached by `coerce` still fails bare. Under `walk` the same forms are `InterpreterBug: Couldn't figure out Empty[\T\](uninstantiated) <: Opt[\ZZ32\]`. Consequence for row 331: a parametric `Nothing[\T\]` would serve the corpus's `Nothing[\ZZ32\]` and never the specification's bare `= Nothing`; the non-parametric object plus `coerce` that the prelude uses is the only shape that compiles, so `Maybe` stays as landed. Incidental: `typecase` over a user-declared generic object crashes code generation (`Error trying to close method scope`, `CodeGen.java:2802`), row 340. Corrected the same day by the minimal reproducer (`compiler-probes/maybe-inference/probes/TcPlain.fss`): neither the generic object nor `typecase` alone is the trigger; a `typecase` used directly as a function or method body whose value needs an implicit coercion (`IntLiteral` to a declared `ZZ32`) makes ASM's stack-map frame computation fail (`ArrayIndexOutOfBoundsException` under `MethodWriter.visitMaxs`, relabelled by the `catch (Throwable)` at `CodeGen.java:2801-2802`); wrapped in `do … end` the same body compiles, and every gated use of the shape returns `()` so never reaches the coercion.

## The library's arrays and algebra

- `Vector[\T extends Number, nat s0\]` and `Matrix[\T extends Number, nat s0, nat s1\]` are the only sized array traits; `Array3[\T, nat b0, nat s0, …\]` carries no algebraic trait (row 292; `FortressLibrary.fsi:1460, 1578, 1652`).
- `Vector` and `Matrix` inherit `+`, `-`, unary `-` and `zero` from `AdditiveGroup`, nothing else; `×` reaches no array by design because juxtaposition is the inner product and the array traits exclude `AnyMultiplicativeRing` (rows 64, 109, 293); a carrier that extends the ring is accepted unchecked, changes juxtaposition to elementwise and breaks `+` (vocabulary review v02, v02b).
- The library's products are declared with shared `nat`s (`Matrix[\T,n,m\]` × `Matrix[\T,m,p\]`, `FortressLibrary.fsi:1508-1516`); C4's own products were not, which is habit; the focused base's `FlatArrays2` states them (twelve declarations including the per-rank elementwise `×` and `/`, 25 of 29 nats agreeing; 39 declarations), and a wrong-shape call is refused at dispatch, uncatchable for an overloaded name (row 83), as a unification error naming the nat for an unoverloaded one (`apl/mg/checks/mismatch_probe.out`).
- Two declarations of one name differing only in the element type, or a rank-specialised declaration beside an index-generic one, are refused at load ("at least one pair of parameters must have excluding types"; `apl/mg/checks/model_run.out.0`, `elemwise_nat_probe.out.0`); two apis' overloads of one name are checked as one family, so two vocabularies cannot stand in one component (`diag_fwd_two_vocabularies_rejected.out.0`).
- The shipped `RR64` does not satisfy the specification's algebraic bound `T extends AdditiveGroup[\T\]` (vocabulary review, probe `v04b_groupbound.out.0`); `T extends Number` is the bound that works for every element type and rank (row 295).
- No trait for scalar extension ships; no reshape, plane, gather, outer product or ravel exists in the library (vocabulary review, section A).
- An array is a trait with `get`/`put`; a view is an object implementing it over other storage, the language's own idiom; the library's row slice `m[i,:]` costs 5× a six-line user view; a diagonal as a `Matrix` view costs 13-54× the operator (vocabulary review v20, v07).
- The element type is `Number` only for `Vector`/`Matrix` (row 24); irrelevant to numeric microGPT, decisive for Run B's autodiff value and for APL characters.

## The syntax-extension mechanism (the APL ladder's findings, ledger 179-287; narrative in `apl/lessons.md`)

- A binder written literally in a template is renamed by hygiene; a free name written by another template is not; they never meet (row 204); an `Id` gap in a binder position is not renamed (row 201). Consequence: a sub-language cannot type or even name `⍵` inside a user-written body; named functions and lambdas one rule writes whole are the two shapes that work (rows 285, 96 of `apl/gaps.md`).
- The interpreter refuses every nested re-declaration of a name (rung 4 probes u01-u03); with hygiene this is why rung 4 built a frame stack, which is unsafe under implicit parallelism (row 265) and was replaced by the focused base (`apl/mg/`).
- APL names are closed sets, one grammar line per name (row 194, 202); a word of two or more capitals is an operator, not a name (row 7/193).
- A host `Expr` gap swallows a following terminal that is a host operator (`⋄`, `∘`) (row 284); a template that writes the host caret drops its right operand silently (row 286); nine `apl⦇ ⦈` uses in one expression do not parse (row 261); parser generation costs about 15-40 s per grammar-importing run.
- Direct rules cost 3.8× less than general forms with per-element frame pushes (row 256); with per-row or per-plane cells the general route was 1.12× C4 at pool 1 and 1.49× at pool 4; the focused base is level with C4 at both.
