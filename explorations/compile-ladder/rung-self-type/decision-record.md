The decision this rung carries out is P-146, "The checker reads `self` in a self-typed trait's method bodies as the implementing type (way 6)", from the judgement's recommendation (`explorations/reviews/self-typed-bodies-judgement.md`, section 4), with the default the coordinator took under it after the batch record's review and listed for review (`explorations/coordinator/CLIMB-BATCH-14.md:86`): a trait's type parameter bounded by a self-typed trait that the trait extends at that parameter counts as the trait's self parameter too, never an object's. The form follows P-95 and P-96.

## 1. A word, before the passages

The specification already says "self parameter" for the parameter named `self` of a method (`Specification/basic/overloading.tex:167-182`, `Specification/basic/traits.tex:577`, `:591`, `:631`, `:644`, `Specification/preliminaries/overview.tex:1140-1146`). The checker's code and the record call the trait's static parameter that `self` is read as "the self parameter" (`SelfParamDisambiguator.selfParam`; the judgement, way 6). So the text calls the static parameter a **self-type parameter**, and keeps "self parameter" for `self`. The checker's message keeps the record's wording, "whose self parameter is A" (the batch record, section S, "Rule (b), not yet built"), which reads as the instantiation's argument for the trait's static self parameter.

## 2. The passages

### 2.1 The type of `self` (`Specification/basic/expressions/var-ref.tex`, section "Identifier References")

- Original: `Specification-1.0-frozen/basic/expressions/var-ref.tex:53-54` and `:64-69`, the same text as the base's `var-ref.tex:53-54`, `:64-69`, unchanged by this rung: "The type of `self` is the type of the trait or object being declared by the innermost enclosing trait or object declaration or object expression." and the self-type idiom, "If the innermost enclosing such construct is a trait declaration (for a trait called, say, `T`), and that trait declaration has a `comprises` clause, and `U_1`, `U_2`, ..., `U_n` are the traits mentioned in the `comprises` clause, then the type of `self` is instead `T ∩ (U_1 ∪ U_2 ∪ ... ∪ U_n)`."
- New text, `var-ref.tex:70-79`, after the idiom's sentence: "If that trait declaration has no `comprises` clause and has a self-type parameter `X` (§ trait-decls), a static parameter bounded by the trait itself at its own static parameters, as in `trait T[\X extends T[\X\]\]`, or by a trait with a self-type parameter that `T` extends at `X`, then the type of `self` in the bodies of its methods is instead `T ∩ X`; the `self` parameter keeps the type `T` in the signature of each method declaration, which overloading and the choice of a declaration at a call read." The callout follows at `:80-90`.
- Reason. Rule (a) of way 6 (the judgement, section 3, "Way 6"): a bound constrains the argument, not `self`; a body that treats `self` as the parameter is sound only under a further fact, which Scala gets from a declared self type checked at each extender. The checker's own self type under a `comprises` clause (`SelfParamDisambiguator.scala:56-75`, `TypeAnalyzer.removeSelf`), which the team pinned in `XXX10k.test`, is read from the bound that the library already writes. Naden asked for exactly this, "a separate construct which cannot be used as a first class type, but instead only in bounds" (`Papers/Types/journal/justificationOfRTR.tex:626-630`).
- The confinement's reason, the signatures kept at the trait's type. The POPL 2019 paper (Park, Hong, Steele and Ryu) has no self types, so it neither supports nor contradicts rules (a) and (b); but its matching of types is complete only for types that hold no type parameter inside a union or intersection, an assumption it shows every declared type meets (pp. 11:21-22, `research/extracts/ParkPOPL2019-extract.md:258-264`), and its Return Type Rule compares declared domains (p. 11:13). The unconfined rule put `C[\X\] & X` into the functional methods' signatures and the distance stage then reported 18 Return Type Rule errors between `StandardPartialOrder`'s and `StandardTotalOrder`'s `CMP`, whose domains became equivalent, and 3 call sites typed `Comparison` (the judgement, "Rule (a) alone, as section 6 asks"; `explorations/reviews/array-judgements-popl-check.md`, section 5). Keeping the self parameter at the plain trait type in `FunctionalMethod`'s signature keeps every declared type within the paper's assumption; a later widening of the self type into signatures leaves the paper's ground.

### 2.2 Self-type parameters and their extenders (`Specification/basic/traits.tex`, section "Trait Declarations")

- Original: none; the paragraph is new, at `traits.tex:285-326`, after the `comprises` passage and its note on `...` (`:235-283`) and before the `Catalyst` example.
- New text: a trait with no `comprises` clause may have a self-type parameter, a static parameter `X` whose bounds include the trait at its own static parameters, or an instantiation of a trait with a self-type parameter that the trait also lists in its `extends` clause, with `X` as the static argument for that self-type parameter; `self` then has the type `T ∩ X` in its methods' bodies; a trait or object declaration, or an object expression, that extends an instantiation of `T` must be a subtype of the static argument for the self-type parameter, a trait with its own self-type parameter `Y` standing as the intersection of its type and `Y`; an object declaration has none. The example, `trait Shape[\S extends Shape[\S\]\] end`, `object Point extends Shape[\Point\] end`, and `object Mark extends Shape[\Point\] end` marked "Not allowed" in the chapter's form (as at `traits.tex:355-359` and `:372-376`). The callout follows at `:317-326`.
- Reason. Rule (b) of way 6: Scala's conformance rule, "The self type of a class or object must conform to the self types of all classes which are inherited by the template" (*Scala Language Specification 2.13*, section 5.1, as `explorations/reviews/self-typed-bodies-ways.md:304` cites it). Checking direct extensions at every declaration suffices, by induction up the hierarchy: a value of `C[\A\]` comes from an object whose every supertrait was checked (the judgement, way 6, (b)). The widened reading (the coordinator's default) keeps the team's 2009 mixins `ContainmentBySubset[\T extends Containment[\T\]\] extends Containment[\T\]` and `ContainmentByComparison` (`Library/Containment.fsi:22-30`, `.fss:42`, `:57`) valid as written, rule (b) then checking their extenders, `Relation` among them (`Library/Relation.fsi:17`, `.fss:23`). An object has no self-type parameter, so `object M[\T extends Shape[\T\]\] extends Shape[\T\]` is refused: the object is where rule (b) closes the check that a trait passes down.

### 2.3 The type of a functional method's `self` parameter (`Specification/basic/traits.tex`, section "Method Declarations")

- Original: `Specification-1.0-frozen/basic/traits.tex:486`, unchanged at `traits.tex:598`: "This parameter is not given a type and implicitly has the type of the enclosing trait or object."
- New text: a callout at `traits.tex:599-603`: under a self-type parameter the sentence still holds of the declaration's signature, and in the body `self` has the type `T ∩ X`. The sentence stays true under the confinement, so it is not revised; the callout says so. `Specification/basic/overloading.tex:180-182`, "Note that the static type of the self parameter is the trait or object trait type in which the declaration occurs", stays true for the same reason and gets no callout.

## 4. What it bends

The record's reading of route A, "no self type enters the library" (`explorations/coordinator/CLIMB-BATCH-8.md:113`), is set aside by P-146 itself: the library's text gains no self type and no clause, but the checker gives `self` a self type in every trait with a self-type parameter, the library's among them. Route A (P-43) and the `comprises` decision (P-44) stand: under a `comprises` clause the self type is the clause's, and rule (a) is never reached there.
