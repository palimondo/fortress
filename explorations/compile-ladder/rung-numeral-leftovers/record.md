## Revival change

**The change.**

1. The team's compiled run time loads a program's component class on the JVM's main thread, before any task exists, and leaves the class of each imported component to the JVM, which initializes it at its first use, on whichever worker runs that use (`ProjectFortress/src/com/sun/fortress/runtimeSystem/MainWrapper.java:64` in the team's file: `Class.forName(whatToRun, true, icl)`, under the comment "so that there is a task pool before any user code is run"). The tree now initializes the program's component class, and after it the class of each component whose declarations the program's classes name, at any depth, before `run` starts, inside a root task on a pool of one thread of its own; the program's arguments are set before that. So every numeral's place of a compiled program is filled before the program's first statement, inside a task, and a task that its coercion forks runs in place; a top-level variable's initializer runs at the variable's first use, as before. Tests: `compiler_tests/NumeralCoercionSpawnCompiled`, `compiler_tests/NumeralCoercionSpawnImported`. The reason: a class initializer that forks a task failed with 'Thread cannot be cast to FortressTaskRunner' on the main thread, and on a worker of the program's pool of four threads it hung, a second worker 'waiting on the Class initialization monitor' while the initializer joined the task that the worker had taken.
2. The compiler's prelude declared, at `RR64` and `RR32`, a coercion from a numeral with a radix point only, so `x: RR64 = 3` was refused: 'Right-hand side has type NaturalNumeral[\1,10,3\], but declared type is RR64.' (`ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss`, the two traits). The tree's prelude declares the coercion from `NaturalNumeral` at both, as the one library does (`Library/FortressLibrary.fss:389`), and the compiled program holds the rounded constant. Test: `compiler_tests/NumeralNaturalAtFloatCompiled`. A `ZZ32` value at `RR64` is still refused there: write `i.asRR64`.
3. Walk ran three things that the rules of the numerals refuse or decide otherwise: a numeral that rounds to an infinity at a typed place of `RR64` or `RR32` became `Infinity`; a float numeral to the left of an `RR32` operand ran `RR64`'s operator; a numeral type written as an extended type or as a static argument loaded and ran. Walk now refuses the first when the place runs ('Type mismatch binding'), runs `RR32`'s operator on either side, and refuses the third at load with the checker's message, 'NaturalNumeral cannot be written in a program except as a parameter's type.' Tests: `tests/NumeralRoundsToInfinityWalk`, `tests/NumeralFoldedRoundsToInfinityWalk`, `tests/NumeralPointRoundsToInfinityWalk`, `tests/NumeralPointRoundsToInfinityAtParameterWalk`, `tests/NumeralLeftOfRR32Walk`, `tests/NumeralTypeWrittenWalk`, `tests/NumeralTypeExtendedWalk`, `tests/NumeralTypeStaticArgumentWalk`. The reason: `Specification/basic/expressions/literals.tex`, "Literals" (a numeral that rounds to an infinity is a static error; a numeral type is written only as a parameter type), and `Specification/basic/conversions-coercions.tex`, "Coercion Resolution" (the more specific declaration applicable with coercion). Where nothing fixes a type, a numeral with a radix point that rounds to an infinity is still `Infinity` on both paths.
