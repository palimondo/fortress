## 2. The shadow

`P1/make-shadow.py` edits copies of `OverloadingOracle.scala` and `OverloadingChecker.scala`. `P1/build.sh` compiles them with the build's own scalac entry point, and the classes go first on the classpath. The edit of record is `P1/shadow.patch`: 123 lines added, 4 removed.

For every pair the checker accepts, in both orders, `returnTypeCheck` computes three return-type verdicts:
- `stock`, today's rule (`OverloadingOracle.scala:81-117`), which substitutes the one solution `subEDsolution` returns;
- `paper`, the paper's theorem as written, `arrow(d1) <: ∀[Δ1, Δ2] (S1 ∩ S2) → T2` (`Papers/Types/overloading-check.tick:166-172`). Its code is the team's own implementation, commented out at `OverloadingOracle.scala:120-145`, restored under a new name.
- `forced`, the judgement's construction (`reviews/overloading-judgement.md` section 3.5). A parameter of the less specific declaration is replaced by its solution only where the solver's constraint implies the parameter equals it (`Formula.implies`); otherwise it stays quantified. An unsolved size stays quantified, as the stock rule keeps it.

It also checks answer 9's positional rule for every pair in the more-specific relation where both declarations have static parameters of their own:
- The two must declare the same number and kinds.
- The more specific one's return type must be a subtype of the other's under the identification by position.
- In the second build, with `-Dprobe.positional.domain`, its domain must also be a subtype of the other's under the identification.

The shadow prints a line for each pair where the three return-type verdicts differ (`@@P1 RTR`) and for each pair the positional rule applies to (`@@P1 POS`, with `agree`, `shape`, `return` or `domain`). Switches choose which verdicts report errors: `-Dprobe.rtr=stock|paper|forced` and `-Dprobe.positional=true`. With neither switch it reports today's errors.

The second build went to its own class directory (`P1_CLASSES`), so the runs already under way kept the first build. The domain condition is the only change between the two builds.

- **Why the widened `cond` parameter is refused.**
  - For the special arrow, `(PossibleReductionPair[\R\] -> G) ∩ (SomeReductionPair[\R\] -> G')` bounds `G'` only from below, by `G`. So the rule finds an instance where `G` is not below `G'`.
  - `Just`'s, `Nothing`'s and `NotUnique`'s `cond[\R\](t: T -> R, ...)` against `Condition[\T\]`'s pass: their parameter domains are equal, the meet of the two arrows is then one arrow, and the rule accepts the pair.
  - By the paper's semantics the refusal is sound but conservative: its witness is a function value that has both arrow types at once.
- **Two repairs for `cond`, measured.**
