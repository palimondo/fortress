- F-173 **The specification's type-inference chapter states the rule that the compiled checker builds: the declaration is chosen first, then its static arguments are inferred.** It states P-46, P-48 and P-49. A type parameter that a parameter's declared type mentions inside another type, as `List[\T\]` mentions `T`, is fixed by the argument at that position. One that is the whole declared type of one or more parameters, as `T` is of `x: T`, and that nothing else fixes, takes the narrowest type, within its bounds, that every one of those arguments has or converts into: `ZZ64` for a `ZZ32` and an `NN32`. Where there is none, and no numeral settles the tie, it takes its bound, narrowed by what the call's expected type requires of the return type (P-48). So does a type parameter that neither an argument nor the expected type fixes. Inference never gives a type parameter `BottomType`. The compiled path departs from the chapter in these ways, among others. It bounds a type parameter written without an `extends` clause by `Object`, not `Any`, as the chapter's callouts say (row 412, P-42). Its prelude lacks the coercion of `NN32` into `ZZ64`, so a `ZZ32` and an `NN32` instantiate a type parameter at `ZZ`, not `ZZ64`; no callout names this (row 442, `compiler_tests/XXXInferPromoteNN32`). The callouts at `Specification/basic/inference.tex:236-298` and `:364-425` also give walk's departures, such as the return type `BottomType` that walk gives a function expression that declares none (row 587). Plain tests gate the rule for a type parameter that is a parameter's whole type, at its bound where no argument type is narrowest, on both paths: `compiler_tests/InferLone*` and `tests/InferLone*Walk.fss`. Detail: `compile-ladder/rung-instance-bound/REPORT.md` (the bound rule); `Specification/basic/inference.tex:47-124` (the chapter's rule).
- F-174 **The specification states the type group's 2011 overloading model: declarations of one name may differ in their static parameters, and a declaration with static parameters is read as one declaration over all its instances within its bounds.** It states P-45 and P-42. The section "Declarations with Static Parameters" states the OOPSLA 2011 paper's three rules: No Duplicates, Return Type and Meet. It gives one more restriction as the compiled path's, not the language's. Where one generic declaration is more specific than another with as many static parameters, the two must declare them of the same kinds, position by position. Also, the more specific one's return type must be a subtype of the other's when their static parameters are matched by position, so the checker refuses an override whose return type reorders its static parameters (row 398, fixed). The section "Principles of Overloading" forbids overloading a functional whose single parameter's type is a type parameter with the bound `Any` written, as `T extends Any`. A type parameter with no `extends` clause, whose bound is also `Any`, is exempt. Both paths refuse such an overload: the checker in `OverloadingChecker.checkBoundAny`, and walk since row 534's fix. Neither path runs every set that the rules allow. Appendix I's entry "Overloading with static parameters" names the sets that each path fails. In row 542, the checker refuses a generic declaration beside a plain one over an object type, as `ident[\T\](x: T): T` beside `ident(x: Circle): Circle`. In row 537, the code generator fails on two generic declarations whose bounds differ. In row 539, walk refuses at load the 2019 paper's valid set over an array list and a list. In rows 779 and 780, walk fails on two generic functional methods one of whose declared domains lies inside the other's: in a trait or object without static parameters it refuses them at load, and in a trait with static parameters it loads them, but a call to which both apply fails. Detail: `Specification/advanced/overloading.tex:134-150` and `:531-674`; `compile-ladder/rung-spec-overloading/decision-record.md` sections 3 and 4.

- F-176 **The specification allows arithmetic in a size, and two size arguments are identical when they are written alike once each operation whose operands are numerals is replaced by its value.** It states P-55. By the grammar, a size is a numeral, a name, a sum, a difference, a product, a power to a numeral or a name, or a bracketed size. So `2 3` and `6` are identical, but `s0 s1` and `s1 s0` are not. Two types are identical when they have the same name and identical static arguments, sizes compared this way. Two sizes are known to differ when they are two different numerals. A static parameter, or a size in which one occurs, is not known to differ from a numeral, since an instance may make them equal. F-146 gives the compiled checker, and F-222 walk's arithmetic. When walk infers a size parameter from a call's argument type, it matches a numeral and binds a name, and solves no size written as an operation: read in `IntNat.unifyStaticArg` (`interpreter/evaluator/types/IntNat.java:126-147`), and observed in row 767. Source: `Specification/basic/types-vals-vars.tex:49-62`; `Specification/appendices/grammars/concrete-syntax.tex:533-547` (`IntExpr`).
