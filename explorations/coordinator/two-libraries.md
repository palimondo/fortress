# Two libraries

Terms used below. **Prelude**: the set of apis the compiler implicitly imports into every component, so a program can name `ZZ32` without importing anything. **World**: a prelude plus the switches that go with it; `fortress <file>.fss` runs the interpreter's world, `fortress compile` the compiler's. **Rung**: one declaration added to a prelude with a failing test, gated on `ant testFast` and `ant testSystem`.

## 1. When the split was made, and in whose words

The compiler's prelude was born on **2008-12-19** in commit `c8d301411` by **Jan-Willem Maessen** (`jmaessen`), whose whole message is: *"[libraries, interpreter] Preliminary version of stripped-down minimalist fortress library for first crack at compilation, plus interpreter support to let it all run through gracefully."* It created `Library/CompilerLibrary.fss` (27 lines: two `print` bindings and an empty `trait String`), `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss` (49 lines), and the world switch itself, then in `interpreter/glue/WellKnownNames.java`.

The switch was documented as provisional in the same commit, in a comment that is still in the tree at `compiler/WellKnownNames.java:109-111`: *"Re-points fortressLibrary etc. to special compiler (rather than interpreter) versions of the code. **Hopefully temporary hack as we work on importing java objects cleanly.**"* Note the stated reason: importing Java objects. Not the type checker — the first `CompilerBuiltin` still bound its natives with `builtinPrimitive` and the interpreter's glue package; `import java` arrived three months later (`b2880c05c` 2009-03-03, *"We now import java.lang.Math, but we don't use it yet"*; `2f8744701` 2009-03-09).

Three further facts from the history. A **third** prelude existed for a month — `352c78880` (EricAllen, 2009-02-06) *"Added TypeCheckerLibrary and TypeCheckerBuiltin; threaded through front-end"*, removed by `904bd2684` (sukyoungryu, 2009-03-09) *"[type checker] Eliminated type checker libraries"*; its residue is `Types.useTypeCheckerLibraries()` (`compiler/Types.java:90-92`), which now just calls `useCompilerLibraries()`. The split's maintenance cost shows up early: `ce1366c17` (2010-02-25) *"Fixed a bug in Shell: use the interpreter library instead of the compiler library when running tests with the interpreter. (Found by Chulwoo Lee)"*. And the team had a word for what it was putting in the compiler's library: *"Tested by adding **bogus** Array traits in the CompilerLibrary. Tests should be added when generic traits can be compiled"* (`ccccbe26f`, 2009-10-04), *"It should use a parameterized Generator type but it is not yet supported. Instead, we use GeneratorZZ32 for now. Added **bogus** IN and = operators"* (`525264af1`, 2009-10-02), and, a month before the wind-down, David Chase's *"Added missing CMP method to **bogo-trait** ZZ32"* (`b16964470`, 2012-06-27). `compiler/Types.java:73-76` names the pair the way they thought of it: *"the compiler libraries"* against *"the full libraries"*.

**The specification knows one library, not two.** `Specification/library/structure.tex:13-22`: the automatically imported libraries are *"chiefly `FortressLibrary` and `FortressBuiltin`"*; `library/default-libraries.tex:15-24`: *"Two sets of libraries are imported into every Fortress program by default"* — `FortressLibrary` and the builtins. `CompilerLibrary` appears in no `.tex` in the tree, and Sun's own `README.txt:432-437` says the same. The split is an implementation fact the published design never acknowledged.

**What no source says.** No commit message, no README, no text under `Papers/`, no spec `\note{}` states an intention to compile the full library one day, or any plan for ending the split. The record runs the other way: the compiler prelude was still being grown declaration by declaration in the project's last month. The wind-down note names the wall the project stopped at, and it is the same one — *"the mismatch between the (rather ambitious) Fortress type system and a virtual machine not designed to support it"* — while listing *"symmetric multiple inheritance with type exclusion"* among the eight things they were pleased with (`research/extracts/fortress-websites-wayback.md:110-123`). Exclusion is what two thirds of §3's errors are about.

## 2. What the two libraries share, and where they differ

**Sizes.** Compiler world: `CompilerLibrary.fss/.fsi` 718 + 358 lines, `CompilerBuiltin.fss/.fsi` 1,636 + 786 — 3,498 in all. Interpreter world: `FortressLibrary` 4,507 + 2,550, `FortressBuiltin` 701 + 218 — 7,976. `AnyType.fss` (17 lines) is shared. Since ladder rung 1 (`1bd8d3ad1`) the compiler prelude is four apis, not three: `compilerAlgebra()` is no longer commented out at `WellKnownNames.java:124`, which supersedes `map/dormant-code.md` §1.4. `Library/GeneratorLibrary` (469 + 314) remains unwired.

**Written twice.** Counting top-level declarations in the four api files by kind and name: 183 in the compiler world, 276 in the interpreter's, **75 in both** — 21 traits (`ZZ32`, `ZZ64`, `NN64`, `RR64`, `ZZ`, `Number`, `String`, `Generator`, `Maybe`, `Range`, `Matrix`, `Comparison`, `TotalComparison`, `Reduction`, `Condition`, the exception roots), 27 objects, 9 operator names and 18 functions. The operator figure is by name and so under-reports: `opr` declaration lines alone number 346 in the compiler world's apis against 496 in the interpreter's. 108 declarations exist only in the compiler world, 63 of them the `characterXxx` category constants and the fixed-size integer bounds. **201 exist only in the interpreter's**: the array and range vocabulary (`Array`, `Array1..3`, `ImmutableArray`, `Vector`, `Indexed`, `Rank`, the `Range` family), the reductions and generators (`SumReduction`, `BigReduction`, `MonoidReduction`, `Comprehension`, `BigOperator`), the algebra above `Number` (`QQ`, `Integral`, `AnyIntegral`, `StandardTotalOrder`, `AdditiveGroup`, `MultiplicativeRing`, `LexicographicOrder`), `Thread`, and the factory and reflection functions (`array`, `matrix`, `vector`, `immutableArray`, `region`).

**The two native binding mechanisms.** The interpreter writes `builtinPrimitive("com.sun.fortress.interpreter.glue.prim.Int$Less")` as the body; the evaluator pattern-matches that literal call and substitutes the named Java class for the body (`glue/NativeApp.java:157-215`, reached only from `interpreter/evaluator/values/FunctionClosure.java:47-57`), and the class takes the evaluator's boxed `FValue`/`FObject` and returns `FBool.make(…)`. 339 such bindings in the two interpreter prelude files (108 in `FortressLibrary.fss`, 231 in `FortressBuiltin.fss`), 427 across the whole interpreter library. The compiler writes `import java com.sun.fortress.nativeHelpers.{simpleIntArith.intLT => jIntLT}` and then an ordinary call `jIntLT(self, other)`: 330 such aliases in 20 `import java` blocks, over 370 public static methods in 25 classes under `nativeHelpers/`.

**Could one text carry both?** Not in the `builtinPrimitive` direction: the name is declared only at `FortressBuiltin.fsi:30`, nothing under `compiler/` or `codegen/` refers to it, and a component that gives it a body compiles and then calls that body, the class-name string being inert data (`perf-probes/prelude/REPORT.md` §3, `07-builtinprimitive-probe.out`). The other direction is **not obviously blocked, and this is new here**: `ForeignJava`, which reads a Java class with ASM and synthesizes an api for it, lives in the shared `repository/` package and is wired into the *interpreter* as well as the compiler — `interpreter/Driver.java:441`, `interpreter/env/ForeignComponentWrapper.java:59`, `interpreter/env/ClosureMaker.java:64`. None of the 381 `.fss` files in `ProjectFortress/tests/`, the interpreter's own corpus, contains an `import java` line. So the mechanism is wired on both sides and exercised on one; whether an `import java` binding runs under the interpreter is one small probe that nobody has run.

**A difference that is not in the library files.** `Shell.useCompilerLibraries()` (`Shell.java:371-386`) flips three desugaring settings besides the prelude names, and one of them changes the language the text is written in: `setExtendsObjectPreDesugaring(true)` makes `PreDisambiguationDesugaringVisitor.forStaticParam` (`:134-148`) rewrite an unbounded static parameter's extends clause in the compiler world and leave it alone in the interpreter's. `Types.useCompilerLibraries()` (`compiler/Types.java:72-83`) additionally re-points `String`, `JavaString`, `Exception` and `CheckedException` from the library api to the builtin one. A shared text has to be correct under both settings, or the settings have to be reconciled first.

## 3. The errors, classified

Re-measured for this brief rather than taken from the record: the probe's own driver (`perf-probes/prelude/WorldFlip.java` with its instrumented `StaticChecker` copy) re-run on the tree at `29a827877` under a private cache (`-Dfortress.caches`, honoured through `ProjectProperties.java:261-269,283`); `default_repository/` was not touched. Result: **93 errors at 96 locations across 48 declaration sites**, not the 92 on record. The extra one is the revival's own: commit `02d09a39f` (2026-09-19) gave `AnyIntegral` a `comprises { ZZ }` clause, and the checker now applies the comprises rule to `Integral[\I\] extends { …, AnyIntegral }` at `FortressLibrary.fsi:411`. Everything else is the same set shifted by three lines. The crash that follows is unchanged (`Not yet implemented`, `STypesUtil.scala:557`).

| family | errors | sites | verdict |
|---|---|---|---|
| A `Type X excludes Y but it extends Y` | 36 | — | see below |
| B `Types A and B exclude each other. C must not extend them` | 26 | 27 (A and B together) | see below |
| C `Ill-formed type` + `static argument I does not satisfy the bound Integral[\I\]` | 26 | 15 | library defect |
| D `multiple declarations of split / splitWithOffsets with the same parameter type: ()` | 2 | 2 (+2 secondary) | library defect |
| E `Invalid comprises clause: … should not be extended` | 2 | 2 | library against a rule the spec states only in a note |
| F return type not a subtype of the overridden one | 1 | 1 (+1 secondary) | library defect |

**A and B are one phenomenon under two message templates, and they are not one verdict.** The checker builds its exclusion relation from four clauses (`scala_src/types/TypeAnalyzer.scala:423-457`): an explicit `excludes` clause (`checkEC`), a `comprises` clause (`checkCC`), object-ness (`checkO`), and **two distinct instantiations of the same generic ancestor** (`checkP`). Only the first is in the specification, which derives exclusion from `excludes` clauses and symmetry alone (`Specification/basic/traits.tex:218-228`). Of the 27 sites: **one** is a defect on anybody's reading — `FortressLibrary.fsi:2526` extends and excludes `Condition[\()\]` in the same declaration, which the spec's own *"neither can extend the other"* forbids; **two declarations across five lines** (`SumReduction` :1816-1818, `ProdReduction` :1827-1831) inherit one generic trait at two instantiations, with the library's own comment calling it *"Hack to permit any Number to work non-parametrically"*, a shape the spec neither permits nor forbids and about which it carries an open editorial question (*"Does it include instantiations of parametric traits?"*, `traits.tex:167-171`); the remaining **21** are the comparison, numeric and `Maybe` towers, where the checker enforces consequences of `comprises` that the spec states nowhere. Which of the four clauses fires at which site was not traced: the clauses were read, the per-site attribution was not.

**C is the clean case and it is a library defect.** `RangeInternals.fsi` declares four traits requiring `[\I extends Integral[\I\]\]` (`:44, :121, :235, :304`) and then instantiates them from declarations whose own parameter is unbounded (`object RightScalarRange[\I\]` at `:309`, `emptyScalarRange[\I\]()` at `:578`) or bounded only by the non-parametric `AnyIntegral` (`sized1Range[\I extends AnyIntegral\]` at `:580`, and nine more). The interpreter checks no static-parameter bound, so nothing ever reported them. D is the same kind of thing: `trait String` declares `splitWithOffsets()` and `split()` twice, once `abstract` at `:2311-2312` and once concrete at `:2327-2328`. F is a real covariance violation across two files: `List[\E\].zip` returns `Generator[\(E,F)\]` (`List.fsi:99`) where the `ZeroIndexed[\E\].zip` it overrides returns `ZeroIndexed[\(E,F)\]` (`FortressLibrary.fsi:1187`).

**The checker gap is not in this list.** It is the crash that follows it: `nat`, `int`, `bool`, `dim` and `unit` static parameters are unimplemented in the checker (`STypesUtil.scala:546-559`), and the interpreter's library carries 81 declarations that use them. That is a separate, already-planned step (`reviews/nat-checking-plan.md`, PLAN step 4) and it blocks routes (b) and (c) equally.

## 4. The three routes, costed

Units. A **rung** is one declaration plus its failing test under the full gate; the eight-rung climb of 2026-09-17 took 8h37m, median 54 minutes a rung (`iteration-cost.md` §A). A **gated batch** is up to four rungs under one gate, measured saving 58.2 minutes over eight (`batched-climb-plan.md` §9). A **worker session** is one delegated report with its probe, of which this is one.

**(a) Keep growing the compiler world's prelude — the standard library written twice.** Costed by what it has already done: eight rungs moved the compile-path pass count from 59 to 81 of 410 corpus files, +22 (`compile-ladder/CLIMB.md:44-50`), and thirteen revival commits grew the four compiler-prelude files by 298 lines. The next fourteen fork-free rungs are forecast to move 38 files, mostly by one phase and not to a pass (`next-climb.md` §0). *Blocks:* nothing; it is the only route that can proceed today without a decision. *Forecloses:* nothing technically, but 104 of the 303 non-passing `tests/` files sit behind the array representation, `nat` parameters or the generator tower, and none of those is reachable by a rung — so the route runs out before the target program, and every declaration it writes is the copy the other two routes would delete.

**(b) One library, the interpreter's, made to pass the checker.** Three pieces in this order (`perf-probes/prelude/REPORT.md` §5). First `nat` kinds in the checker: PLAN step 4, five Scala/Java files plus an optional AST node, with a shadow-prototype recipe and a five-clause gate already written (`reviews/nat-checking-plan.md` §e, §f) — larger than a batch, smaller than a climb. Second the 93 errors at 48 sites: C, D and F (18 sites) are ordinary library edits, a batch or two; A, B and E (27 sites, the two E sites being among them) are not edits but a language-design conversation about `comprises` and exclusion, to be settled against the spec first — one worker session to state the question with the spec text and the four checker clauses beside it, then edits. Third the natives: about 79 of the 108 `builtinPrimitive` bindings in `FortressLibrary.fss` already have a `nativeHelpers/` counterpart under another name, about 29 do not, and the interpreter's remaining 319 bindings live in files the compiler world does not load. *Blocks:* every compiler-prelude rung written in the meantime becomes work to discard. *Forecloses:* the compiler world's own spellings where they differ — `NothingObject[\T\]`/`Nothing` against `Nothing[\T\]`, `Character` against `Char`, `Option`/`Some`/`NoneObject` against `Maybe`/`Just` (`array-design-review.md` §3c). *Does not settle:* whether the code generator can compile it. No run has ever reached DESUGAR or CODEGEN with this library.

**(c) One text, two native bindings.** The layer written once in `Library/`, with the native binding the only per-world file (`array-design-review.md` §3, decision C3, which records it as unprobed). *What is now known that was not:* the compiler's binding mechanism is wired on the interpreter's side too (§2), and no interpreter test exercises it, so the first experiment is one probe — a two-declaration component bound with `import java`, run under `fortress <file>.fss` — at roughly half a worker session. *What it still costs if that probe is green:* the same 93 errors and the same `nat` gap as (b), because a shared text meets the same checker; plus the three desugaring settings (`Shell.java:371-386`) reconciled and the four well-known types that the two worlds place in different apis (`Types.java:72-83`). *Forecloses:* the compiler world as a place to try a declaration the interpreter must not see — every rung of the last climb relied on exactly that (`next-climb/worlds.md`: an edit confined to `CompilerLibrary`/`CompilerBuiltin` cannot affect the 382 interpreter tests, with two named exceptions).

**Where the team's breadcrumbs point, and where they stop.** They point at the split being provisional, in their own words: *"hopefully temporary hack"* in a comment written the day it was made and still in the tree (`WellKnownNames.java:109-111`), *"stripped-down minimalist … for first crack at compilation"* in the birth commit (`c8d301411`), *"bogus"* in 2009 and *"bogo-trait"* in 2012 for what went into it, and a specification that recognizes one default library and never names the compiler's. They do **not** point at any of the three routes. Nothing on record says how the split was meant to end, or that it was meant to end at all; the last month of the project was spent adding to the compiler prelude. "Temporary" is evidence about intent, not about method: it is equally consistent with (b) and with (c), and it is not evidence against (a), which is what the team in fact did for three and a half years. The one thing the evidence does settle is negative and useful: the obstacle is not bytecode generation. 95.3% of `FortressLibrary.fss` is plain Fortress, and none of it has ever reached the desugarer or the code generator, because the checker stops it first.
