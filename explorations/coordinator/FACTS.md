# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:97-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (`ProjectFortress/src/com/sun/fortress/Shell.java:453-458` calls `useCompilerLibraries()`; row 69). The checker on interpreter programs comes after the switch-over (POSITIONS, "The type checker on interpreter programs.").
- The code generator lowers every type to a JVM reference type: `RR64` to the run-time class `FRR64`, so a compiled loop over `RR64` holds no `dadd` or `dmul` (`repo-internals.md:129`; the bytecode quoted in `perf-probes/boxing/REPORT.md` section 4). An array is a library object read and written through `get` and `put` (`Library/FortressLibrary.fsi:1417`, `:1468`), not a `double[]`.
- On microGPT-shaped array code boxing is the dominant representational cost: in Java models of the program's three kernels, boxed elements cost 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` (`perf-probes/kernels/REPORT.md` sections 2 and 4). No microGPT-shaped kernel compiles: the compiler prelude has no array type, and `Array`, `Vector` and `Array3` are undefined in `FlatArrays.fsi` (row 305). No array type goes into the compiler prelude; the arrays reach the compiled path with the one library (POSITIONS, "The library route."). A failed compile leaves a 0-byte jar in the bytecode cache (row 304).
- With rows 302 and 303 fixed (the next two entries), the compiled scalar `RR64` loop `bench1t` runs in 0.74 s, against 13.06 s on the tree before them, a pair timed in one session (`compile-ladder/rung0/REPORT.md`, "The four timings"). Two costs that the boxing probe named in that loop are unaddressed (`perf-probes/boxing/REPORT.md` section 5). One is the `for` lowered to the compiler prelude's `countedseqloop`, a recursive binary subdivision over boxed indices with a closure call per element (`Library/CompilerLibrary.fss:373-381`). The other is the representational rest, which unboxed doubles would attack: the transacted volatile cell, four allocations per iteration, the interface hop to the native wrapper and the `checkcast`s.
- The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `compile-ladder/rung0/REPORT.md`).
- `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `compile-ladder/rung0/REPORT.md`).
- The benchmark numbers on record, `bench1t` 9.3441 s and `bench1h` 6.0732 s (`perf-probes/boxing/REPORT.md`, `perf-probes/kernels/REPORT.md`), are one session's: the same unmodified tree timed 13.0566 s and 8.8159 s in another (`compile-ladder/rung0/REPORT.md`, "The four timings"). Absolute seconds are not comparable across sessions; only a before-and-after pair taken in one session measures a difference.
- `ant compileAll` leaves the bytecode cache holding no library jars when it changes the implementation, and only then: it deletes the caches whole when the sources or the build differ from what the last successful build left ("**`ant compileAll` deletes the caches folder, the linker's untracked `global.map` with it, when the implementation changed, and keeps it otherwise**" under The harness and the gate), and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`. The library-order recompile of `repo-internals.md:172-185` restores the jars in about two minutes. Nothing else clears `bytecode_cache/`: with the caches kept through a rebuilt compiler, the five library jars survive and a compiled program runs (`coordinator/process-engineering/build-efficiency.md` section 2).
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`), and its descriptor in a stamped class is `RTTIsize.of("<n>")` ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`Specification/basic/expressions/tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool. No program under `explorations/` writes `spawn` or `also`.
- Sizes, the `nat` and `int` static parameters, are instantiated at run time with numeric values (`Specification/basic/trait-parameters.tex:97`). The compiled checker checks them ("The compiled type checker checks `nat` and `int` static parameters" under The checker and the one library), and a sized program loads and runs compiled ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics). Sizes check shapes when a value is made or passed; no optimization is built on them. Under walk, a `nat` parameter does not unify with a run-time-built array, while a literal size does (row 23). Walk matches sizes at dispatch, and a mismatch reads "Failed to find any matching overload", a `ProgramError` that no `catch` takes (row 254). Row 83, a `nat`-generic function that mis-unifies on its second instantiation through an api, is contested and has no reproducer.
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** The Working Draft's `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:49`) stops on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`; `reviews/spec-refused-examples.md`, E4). Without that clause, `fortress compile` and `fortress walk` give the same single error, `T is undefined`, at the `T` inside the extends clause (`compile-ladder/rung-maybe/REPORT.md`, "Why the specification cannot simply be transcribed"). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause, in either implementation; row 17 holds the same defect for a trait's extends clause. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at code generation, since `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4107`), but nothing reaches it. The specification keeps the declaration marked "Not allowed" and gives instantiation exclusion and the missing `excludes` clause as the reasons (`Specification/basic-lib/convenience.tex:58-73`); the parametric spelling stands (POSITIONS, "`Maybe`'s empty case").

The report's scripts for that, `parse-compare.sh` and `remap-lines.py`, print with `git show ab067d9b6^:explorations/compile-ladder/rung-library-comments/<name>`.
- **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees** (`compile-ladder/rung-int-semantics-walk/REPORT.md`, section 4.1): `throw new FortressError((FObject) Driver.getFortressLibrary().getRootValue(name))` from a `builtinPrimitive` method reaches `Evaluator.forTry` unchanged; the helper is `Int.overflow()` (`interpreter/glue/prim/Int.java:258-261`). Every other Java exception of a native is wrapped in a `ProgramError` (`FunctionClosure.java:191-196`), which no `catch` takes, so row 336's division by zero ends the run.

## The checker and the one library

- The one library binds its natives with `builtinPrimitive("…")`: 424 live bindings in nine files, 125 of them in `FortressLibrary.fss`, and the rest of the library is plain Fortress. The five `IntLiteral` conversion bindings of `FortressBuiltin.fss:487-495` are not in the count. Walk also loads the Java classes of 32 objects of `native component`s by name, and binds `true`, `false` and `Any` at start-up. The interpreter's glue classes take the evaluator's boxed values, so the compiled path cannot reuse them. The compiler's natives are static Java methods over plain Java values, called through `import java`: 369 public static helpers in 25 classes of `nativeHelpers/`. Matched against these helpers, 147 bindings are bound on the compiled path already, and only their binding text changes. 61 have a helper that nothing binds yet; 25 of them carry a name that the compiler prelude binds to another helper, the 12 wrapping operators among them (row 348). 138 need a new static helper. 78 need something else: 36 are methods of native I/O objects (`Writer`, `BufferedWriter`, `FileReadStream`, `FileWriteStream`, `Reader`), and 42 have no compiled analogue (reflection, `Thread`, the native arrays, the task trace). Every program's output needs `Writer`'s natives, because `println` writes through `stdOut`, a native `Writer` (`Library/FortressLibrary.fss:4357-4358`, `Library/Writer.fss:20-24`). MicroGPT needs three more: `nanoTime` needs a new helper, since the compiled one returns `RR64`; importing `System` calls `getProgramArgsPrim`, which has no compiled analogue, when the component loads (`Library/System.fss:28`); and its arrays reach `NativeArray`, which has none either. Source: `perf-probes/prelude/natives-shape.md` § 2. The rungs that move walk onto the helpers are PLAN's phase 4, the natives; the binding text is POSITIONS, "The natives' one binding text is `builtinPrimitive` naming a static helper (item 35)."
- `fortress compile Library/FortressLibrary.fss` as it is: it reports 1,417 errors, all in DISAMBIGUATE, because both preludes are in scope and every error is a name collision between them, an artifact. With `FortressLibrary` made the prelude, by a driver over `Shell`'s public entry points, disambiguation reports no error (`perf-probes/prelude/REPORT.md`). What the checker then reports on the library is measured at every landing by the gate's checker-count and distance stages ("The true distance to the switch-over" below). The checker checks `nat` and `int` static parameters and refuses a `bool`, `dim` or `unit` one by name, with no crash ("The compiled type checker checks `nat` and `int` static parameters" below), and a sized program loads and runs compiled ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- **Between the interpreter's library and bytecode stands the checker, not desugaring or code generation** (`perf-probes/prelude/desugar-codegen.md`; on the flat library, `perf-probes/prelude/switch-over-distance-flat.md` sections 3 and 4). With the checker's failures caught per top-level declaration, DESUGAR and OVERLOADREWRITE report no diagnostic on the library. Code generation on `FortressLibrary.fss`, measured once on the flat library, emits 326 declarations and refuses 225. Four of the refusals are on declarations that the checker passed: two `AsIfExpr`, one `LetFn` and one method call on an intersection-typed receiver. The other 221 fall on declarations that the checker reported errors on or crashed on, and on overload declarations that the overload rewriting synthesizes. The dispatch generator finishes and refuses 12 of 198 overload sets, each "a functional method and top level function with same signature". The compile path's own setting gives every static parameter with an empty `extends` clause the bound `Object` before disambiguation (`Shell.java:371-386`; `compiler/desugarer/PreDisambiguationDesugaringVisitor.java:77-86`, `:135-148`; row 412), which refuses every generic instantiated at a tuple type. The gate's stages run under the bound `Any` instead (POSITIONS, "The implicit bound of an unbounded type parameter is `Any`").
- **The `FortressLibrary` api has 25 declarations with a dead size, a size parameter that occurs in no parameter type, return type or body** (`perf-probes/nat/REPORT.md` section 2, which lists them by line, and section 7). Under the size rule as built, a size that reaches no type, name or value is no error (POSITIONS, "Sizes"), so the declarations themselves check clean. Where the component declares the same function without the dead size, the export checker reports the api's declaration as missing, because `equalListStaticParams` compares two static-parameter lists by length, name and kind (`ExportChecker.scala:613-627`). - **The code generator's `FnNameInfo.boundsFor` gives a size parameter a size argument, and gives every other kind a type argument** (`perf-probes/nat/java.md`). `FnNameInfo.boundsFor` (`compiler/codegen/FnNameInfo.java:168-183`) maps a `nat` or `int` parameter to itself as an `IntArg`, the identity that `STypesUtil.staticParamToArg` gives (`STypesUtil.scala:340`), so a method call on a sized receiver does not crash with `cannot be cast to IntExpr`. For `bool`, `dim`, `unit` and `opr` parameters it still returns a type argument, a latent defect. The mangled name of a sized receiver keeps the size as its own symbol (`NamingCzar.forIntRef` and `forIntBase`, `compiler/NamingCzar.java:1889-1897`). A size symbol needs no descriptor, since the template holds `Box⟦k⟧$RTTIc`. Only literal sizes reach the loader, through `MethodInstantiater.rttiReference` (`runtimeSystem/MethodInstantiater.java:95-148`) and `CodeGen.generateTypeReference` (`compiler/codegen/CodeGen.java:5703-5838`), and their descriptors come from `RTTIsize.of` ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- **The one library's own sizes are the literals 0 to 3, and a type test on a size reads the value's own class** (`reviews/size-runtime-design-brief.md` sections 5 and 2; `perf-probes/nat/size-probes.md` section 4). The library's source uses four size literals, 0, 1, 2 and 3, in 85 places, 78 of them 0. With clause bodies that need no coercion, a `typecase` tells `Vec[\ZZ32,3\]` from `Vec[\ZZ32,4\]` compiled, also when the size is a static parameter of the enclosing function, because the test is an `INSTANCEOF` on the value's own class. Gated by `compiler_tests/NatRtCase` and `NatRtCaseGen`. A `typecase` that is a whole function body, with clauses that need a coercion, fails in code generation with or without a size (row 340).
- **The compiled dispatcher chooses an overload arm generic in a size correctly, and the arm reads its size** (`perf-probes/nat/size-probes.md`; rows 410 and 411, fixed). With row 214's three arms and a catch-all, called with an argument typed `Any`, the dispatcher reads the size off the value's descriptor and chooses the arm, and the arm reads its size. The checker keeps a `nat` parameter in a generic arrow, so the return-type rule compares the arms' own sizes (`keep-size-params`, `scala_src/types/TypeSchemaAnalyzer.scala`; row 410). The dispatcher skips the bound `Object` that the compile path gives a size parameter (row 412, open). Gated by `compiler_tests/NatRtDisp`, `NatRtDispSize` and `NatRtDispTrait`.
- **An operator static argument is a compile-time name on both paths and by the specification, and sizes were never carved out with it** (`perf-probes/nat/opr-kind-history.md`). The specification makes an operator parameter a name substituted into the declaring trait's method names, the declarations of the actual operator "irrelevant" (`Specification/basic/trait-parameters.tex:224-226`, `:252-254`), and a `nat` or `int` parameter a value "instantiated at runtime with numeric values" (`:97`). Walk substitutes the name: an operator argument is a memoized, name-only `FTypeOpr` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/types/FTypeOpr.java:44-46`), taken out of an instantiation's identifying arguments and written into the body by `OprInstantiaterVisitor` (`FTypeGeneric.java:156-180`). Sizes take the descriptor-bearing treatment of a type argument (`InstantiatingClassloader.java:1600-1622`), which is design B (POSITIONS, "The run-time size design is B"). Neither library declares an `opr` static parameter; `ProjectFortress/tests/conditionalExtension.fss` and `compiler_tests/XXXOprParamRungS.fss` are its only uses. - **What a size costs at run time, measured: a few kilobytes at load, nothing on the hot path, and only the overload dispatcher ever reads a size off a value** (`perf-probes/nat/size-cost.md`; `reviews/size-runtime-design-brief.md`, "Run-time cost, measured"). Sizes add a few kilobytes to the 8.6 MB of classes that a run loads, and start-up does not change beyond noise. The stamped method of a sized object holds its size as a constant (`ldc 8`; `size-cost.md`, "The answers"). A loop bounded by that constant is no faster than one that reads the storage's length: the cost is boxing and a transaction check per local variable, about 31 ns per element, and nothing ties the size to the storage's length. The dispatcher tests a literal-size arm by one `instanceof` on the stamped class; for an arm generic in a size it reads the size's descriptor and looks the arm up in a table on every call. A dispatched call costs about 4 to 20 ns more than a resolved one. The checker checks a shape once per call site at compile time (`DOT`'s shared inner size, `Library/FortressLibrary.fsi:1764-1765`). At run time a shape is checked once per arm tried at a dispatched call and once per type test, and never at load, in a resolved call or per element, where only the JVM's own bounds check runs (`compiler/runtimeValues/FZZ32Vector.java:64`). No optimisation uses a size. A `ZZ32Vector` passed to a generic object's constructor fails at load with no size involved (row 408, expected failure `compiler_tests/XXXVecCtorLoad`).
- **`DOT`'s shared size is tested by the dispatcher in both directions, and a size made at run time gets its descriptor from `RTTIsize.of` directly** (`perf-probes/nat/size-rung-probes.md`). Under `walk` the same forms are `InterpreterBug: Couldn't figure out Empty[\T\](uninstantiated) <: Opt[\ZZ32\]`. So a parametric `Nothing[\T\]` serves `Nothing[\ZZ32\]` and never the bare `= Nothing`, which compiles only with the compiled prelude's non-parametric `Nothing` and its `coerce` (row 331; POSITIONS, "`Maybe`'s empty case"). So a file he is to read is given as a published page or as its GitHub URL on `main`, `https://github.com/palimondo/fortress/blob/main/<path>`; a path is named only as a reference, never as the way to read the file.

## The ledger

- **The ledger's rows stand in fifteen topic sections, each in the row template, and `ledger.py` is the only way to write them** (`explorations/fortress-gap-ledger.md`, "The row template"; POSITIONS, "The gap ledger's form."). Rows are never renumbered, and reports cite them by number; a row is at most 1,200 characters, its status one of seven words, its class `kind (area)`. Every earlier text of a changed row, and the ledger's text before the topic sections (the counts by kind, the revival worklist, the old section headings and which rows stood under each), is in `explorations/fortress-gap-ledger-history.md`. `explorations/coordinator/tools/ledger.py` reads (`show`, `find`, `section`, `heads`), writes (`add --section`, `note`, `close`, `duplicate`), counts (`count`) and checks (`check`, `--base` against a commit), with its tests in `tools/test_ledger.py`; `facts-extract.sh`'s ledger queries read through its parser. A row at its length limit takes no further note, and the tool has no command to edit a claim; `close` takes a corrected claim with `--claim`. Its heading reader does not expand the specification's `\Trait{X}` macro, so a row naming a library trait's section cites `Specification-1.0-frozen/` by line instead (row 457). `apl/lessons.md` is a view derived from the ledger.
