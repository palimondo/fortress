## Where the fix belongs

The map's rows are `explorations/coordinator/map/spec-to-implementation.md:223` (object declarations, `CodeGen.forObjectDecl`) and `:225` (value objects: "the `value` modifier has no representation meaning in codegen"), and the native mechanism is `explorations/coordinator/map/modules-and-phases.md:449` (B.12: `import java` + `nativeHelpers/` + `nativeInterface/`). The defect is where they meet: the compiled prelude's default is a native whose body bounces back into `asString`. Candidate homes:

- The code generator could emit an `asString` per object class. It knows a Fortress name statically but not a generic instance's arguments, which exist only when the class loader stamps the instance (`runtimeSystem/RTHelpers.java:18-50`); it would be a change to every generated class for what one native can read at run time.
- `FValue.toString` given a life of its own is the judgement's alternative C, refused by the batch record for the interop rule (`explorations/reviews/default-rendering-judgement.md`, section 3).
- Changing `stringOps.asString`'s body in place, with no Fortress edit, is smaller, but that helper is bound for `Any`-typed values, and on a builtin such as `ZZ32` it would answer `ZZ32` where the value's own `asString` answers `1`. A native named for what it does is the honest shape.
- `RTTI.className()` (`compiler/runtimeValues/RTTI.java:53-58`) through `getRTTI()`: `FValue.getRTTI()` is `null` unless generated code overrides it (`FValue.java:17-19`), and the class name carries the same information without it.

So one native behind the prelude default, as the batch record prescribes. On the library route (POSITIONS 2026-09-21, the compiler prelude frozen) the edit is a body and an import line, sanctioned by Pavol's decision of 2026-09-22 (POSITIONS, row 321: "one native behind the compiled `Object.asString`"). At the switch-over the interpreter's `Object.asString` is `builtinPrimitive("…ObjectPrims$ToString")` (`FortressBuiltin.fss:40-41`), which the compiled path cannot call; `stringOps.typeName` is the compiled counterpart that declaration will need.

## Precedent search

- **Rendering a type name: one way, the interpreter's.** `FObject.toString` is `type().toString()` (`interpreter/evaluator/values/FObject.java:33-39`); a generic instance appends `Useful.listInOxfords` of its arguments (`interpreter/evaluator/types/FTraitOrObject.java:184-191`, `useful/Useful.java:233-235`, separator `","` at `:79-80`); a tuple type is `Useful.listInParens` (`FTypeTuple.java:61-63`) and an arrow `domain + "->" + range` (`FTypeArrow.java:107-109`). The compiled path had none; the native reproduces this one, and the differentials below show it byte for byte.
- **Decoding a stamped class name: two ways, both followed.** `RTTI.className()` (`RTTI.java:53-58`: canonical name, `demangleFortressIdentifier`, `dotToSep`) and the class loader's decode of a generic class name (`runtimeSystem/InstantiatingClassloader.java:246-251`: `dotToSep`, `demangleFortressIdentifier`, the stem before `⟦`, `RTHelpers.extractStringParameters`) followed by a dispatch on the *full* stem against `Naming.ARROW_TAG`, `ABSTRACT_ARROW`, `WRAPPED_ARROW`, `Naming.TUPLE_TAG`, `CONCRETE_TUPLE`, `ANY_TUPLE`, `ANY_CONCRETE_TUPLE`, `Naming.UNION` (`:252-269`). - **A run-time class back to a Fortress name: none in the tree.** `Naming.specialFortressTypes` (`runtimeSystem/Naming.java:277`, filled at `:287-305`) maps the other way, is package-private, and lacks `NN32`, `NN64`, `String` and `IntLiteral`. ## The specification

`Specification/basic-lib/objects.tex` (read `:1-200`) declares `toString(): String` on trait `Any` (`:30`, rendered `:47`), says every object implements `Any`'s methods (`:19-22`), and gives `toString`'s general contract (`:117-122`): "returns a string that 'textually represents' this object. The idea is to provide a concise but informative representation that will be useful to a person reading it." Its property `x === y → x.toString() = y.toString()` is at `:34` (rendered `:51`). The implementation spells the method `getter asString()`; the team's 2008 api rendering of this chapter, `Library/incomplete/basic/Fortress.Core.fsi:12-29`, carries the same property under that name (`:24`). So the prose is not silent on the question as ledger row 321 records it ("`grep -rn asString …` finds nothing": the chapter's word is `toString`). It requires every object to have a working rendering, which the stack overflow violated, and gives a contract the bare type name meets: concise, and equal for identical objects because it depends only on the class. It does not fix the spelling; that is Pavol's decision of 2026-09-22, which the native implements. The note at `Specification/basic/expressions/typecase.tex:135-147` uses `x.toString()` as the rendering of an arbitrary `Object`, the same assumption.

Tuple *values* have their own rule (`objects.tex:161-185`: `(a, b)` with `", "`); it governs values, not the spelling of a tuple *type* argument, which follows walk's type rendering `(ZZ32,String)`.

## Decisions

- **The worktree did not exist, and I created it.** At launch `/home/user/fortress-rendering` and `wip/rung-default-rendering` were absent (only P's and L's worktrees existed). I created them with the coordinator's recipe (`explorations/coordinator/remote-container.md:96-110`: `git worktree add -b`, `cp -a ProjectFortress/build`, `mkdir tmp`, `git push -u origin`) from the batch base `d610695c0`, not from `main`'s head, which had moved one handover commit past it. The alternative was to stop and report without doing the rung. Nothing was inherited.
- **`stringOps.asString` and its import stay.** After the edit nothing in the tree calls `jAsString` (the one other mention is the comment at `compiler_tests/AtomicTopLevelObjectVar.fss:10-14`) and no Java or Scala code calls `stringOps.asString`, so the rung has shown it dead, which the batch record made the condition for removing it. It is kept anyway: it is no longer a trap (`a.toString()` now ends in `jTypeName` for an object with no `asString`), removal would enlarge a diff in a frozen file that the switch-over deletes, and no test needs it gone. The alternative is a two-line removal, one in each file. The comment at `AtomicTopLevelObjectVar.fss:10-14` now describes the default this rung replaced; it is another rung's file and was left alone.
