# How arrays should be built in the compiled world

## 0. The words used below

Boxing: a number wrapped in a heap object so that it can be treated like any other object. On the compile path every `RR64` is an `FRR64`, a Java object with one `double` field (`compiler/runtimeValues/FRR64.java:14-19`); adding two of them allocates a third. "Unboxed" means the bare JVM `double`, which lives in a register or in a `double[]` and costs nothing to make.

Stamping: the compiler writes a generic declaration (`Box[\T\]`) once as a template class; when a program first uses `Box[\RR64\]`, the class loader reads the template and rewrites it with the argument's name filled in (`runtimeSystem/InstantiatingClassloader.java:178`, the general case at `:210-290`; `Instantiater.java:48` substitutes the names). One stamped class per distinct argument list.

`nat` parameter: a static parameter that is a natural number rather than a type, written `Vector[\T, nat s0\]`; it puts a size into the type so that `Matrix[\T,n,m\]` times `Matrix[\T,m,p\]` can be declared with the shared `m`. Inference: working out a static argument the program did not write, from the types of the call's arguments.

Descriptor: the JVM's spelling of a type in bytecode. `D` is a bare double, `[D` an array of doubles, `Lcom/sun/…/FRR64;` a reference to the boxed class. Whether a field is boxed or not is exactly which of these its descriptor is.

View: an object that implements the array protocol (`get`/`put`) over some other array's storage without copying, such as a row of a matrix or a transposed matrix.

Rank: the number of indices an array takes; a vector has rank 1, a matrix rank 2, `Array3` rank 3. Shadow: compiled copies of a few source files placed first on the class path, so an edit can be tried and gated without changing a tracked file (`perf-probes/template-check/run-all.sh`).

Project units: a rung is one worker session plus one skeptic under the batch script (`coordinator/climb-batch-workflow.js`); batch 1 was four rungs, fifteen agents, 3 h 11 min, with the full gate run once at 830 s (FACTS, ladder section). A rung that touches a `.java` or `.scala` file forces the full gate pair, and a batch holds at most one such rung; a library-only rung may drop `ant testSystem` (`next-climb.md` §5). The regression net is the ladder's 85 passing files (`compile-ladder/baseline-2026-09-19/pass-list.txt`).

## 1. What an array is in the interpreter today

An array is a trait, not a primitive. `Array[\E,I\]` (`Library/FortressLibrary.fsi:1322`) is generic in the element type `E` and the index type `I` (`ZZ32` for rank 1, `(ZZ32,ZZ32)` for rank 2) and carries no size in its type. Its protocol is `get(i)` and `put(i, v)`; subscripting is sugar for them (`opr[i:I]:=(v:E) = put(offset(i),v)`, `FortressLibrary.fss:1886-1889`). `ReadableArray` (`.fsi:1247`) is the read half; `Indexed` (`.fsi:1111`) makes every array a generator, so `for x <- a` and `BIG +` work over it.

Sizes enter one layer up. `Array1[\T, nat b0, nat s0\]` (`.fsi:1435`), `Array2` (`.fss:2289`) and `Array3[\T, nat b0, nat s0, nat b1, nat s1, nat b2, nat s2\]` (`.fsi:1652`) put the lower bound and size of each dimension into the type. `Vector[\T extends Number, nat s0\]` (`.fsi:1460`) is an `Array1` that is also an additive group (`+`, `-`, unary `-`, `zero`, plus `scale`, `pmul`, `dot`); `Matrix[\T extends Number, nat s0, nat s1\]` (`.fsi:1578`) is an `Array2` with `mul[\nat s2\]`, `rmul`, `lmul`, `t()`. Both exclude the multiplicative ring because juxtaposition is the inner product (FACTS, the library's arrays and algebra).

Storage is one object per rank-1 array, holding boxed values. `PrimitiveArray[\T, nat s0\]` (`LibraryBuiltin/NativeArray.fss:15-27`) binds `get`, `put` and `init0` to Java glue; the glue allocates an `AtomicArray` of the evaluator's boxed `FValue`s (`interpreter/glue/prim/PrimitiveArray.java:35, 44-56`; `evaluator/transactions/AtomicArray.java:23`). A rank-2 array is a rank-1 array with the index folded as `i s1 + j`, row by row (`__DefaultArray2`, `FortressLibrary.fss:2415-2421`); rank 3 the same. So the interpreter's arrays are already flat, row-major storage under a trait; what they are not is unboxed. One exception exists and nothing uses it: `PrimImmutableRR64Array[\nat s0\]` over a Java `double[]` (`NativeArray.fss:41-51`; `glue/prim/PrimImmutableRR64Array.java:40`), referenced by no library file.

The everyday operations are Fortress loops over `get`/`put`. `fill(f)` is `for i <- zeroIndices() do init0(i, f(toIndex(i))) end` (`.fss:1974-1976`); `map(f)` and `ivmap(f)` (map with the index) make a `replica` of the same shape and `fill` it (`.fss:2135-2138`); `t()` returns a transposed view, not a copy (`.fss:2395` for `Array2`, `:2559` for `Matrix`). The whole protocol runs from `trait Indexed` at `.fss:1636` to the end of `SubArray3` at `:2808`, about 1,170 lines, plus the 54 lines of `NativeArray.fss` and the integer-only scalar extension at `.fss:4477-4517`.

A run-time size becomes a type by reflection. `array[\E\](x: ZZ32)` (`.fss:1922`) calls `reflect(x)`, which returns a value of type `N[\n\]` with the number baked into the nat (`LibraryBuiltin/NatReflect.fsi`), and `__arr1[\E, nat n\](…, x: N[\n\])` (`.fss:1930`) then builds an `Array1[\E,0,n\]`. The interpreter can do this because a nat is a type in its own lattice, made at run time (`interpreter/evaluator/types/IntNat.java`).

A nat is checked at run time, at dispatch, and only then. When a call meets a nat parameter, a literal must be equal and a symbol is bound (`IntNat.unifyStaticArg`, `IntNat.java:127-147`); a mismatch is "Failed to find any matching overload", uncatchable (FACTS, execution model, last bullet). Nothing is optimised on a nat anywhere.

## 2. What the compiled world has

The compiler's own library is small: `CompilerBuiltin.fsi` 778 lines with a 1,627-line body, `CompilerLibrary.fsi` 356 with 718. It has no `Array`, `Array1`, `Vector` or `Matrix` with a body. The one `nat` declaration in it is `trait Matrix[\T, nat s0, nat s1\] extends Object end` (`Library/CompilerLibrary.fsi:279`), empty.

It has exactly one numeric array, and it is the shape the 2012 team chose for this world. `trait ZZ32Vector` (`LibraryBuiltin/CompilerBuiltin.fsi:555-572`) has no static parameters at all: `shape`, `nrows`, `ncols`, `copy`, `opr[i]`, `opr[i,j]`, their `:=` forms, `|self|`, `fill`, `fill2`. Its body (`CompilerBuiltin.fss:1101-1136`) forwards every member to Java helpers imported at `.fss:299-305`. The Java class `FZZ32Vector` holds an unboxed `int[]` and four shape integers (`compiler/runtimeValues/FZZ32Vector.java:18-19`); a 2-D index is folded to `(i-lower_x)*dim_y + (j-lower_y)` (`:65`); the whole class is 83 lines and its helper `nativeHelpers/simpleIntVector.java` 40. `NamingCzar` lists it as a special type whose implementation class is hand-written (`compiler/NamingCzar.java:553`, in the table declared at `:508-514`; also `:337-338` and `:461`). Above it, `CompilerLibrary.fss:484-535` declares `PREFIX_SUM`, `+`, `-`, `MIN`, `MAX` with a scalar, each a Fortress `for` loop over subscripts, and factories at `:587-593`. `StringVector` is the same design over `String[]` (`FStringVector.java:16`). Three live tests: `other_compiler_tests/VectorTest.fss`, `VectorTest2.fss`, `VectorTest3.fss`.

An element read on that unboxed vector still boxes. Verified in bytecode (§9, probe 2): `v[0]` compiles to a virtual call `FZZ32Vector."[]"(FZZ32) → FZZ32`, which calls `getValue`, which calls the generated native wrapper, which unwraps the index with `FZZ32.getValue()`, calls `simpleIntVector.getIndexedValue(FZZ32Vector, int) → int`, and re-wraps the result with `FZZ32.make(int)`; the caller then `checkcast`s. Four calls and one allocation per element. The storage is unboxed; the traffic is not.

The code generator lowers every type to a reference. `RR64` is `FRR64` (`NamingCzar.java:441-446` maps the bare JVM `double` to `RR64` only at the foreign-Java boundary); `x y` on two `RR64` is an interface call on `FRR64`, no `dmul` (`perf-probes/boxing/javap/CompilerBuiltin.juxtaposition_RR64.javap.txt:3559-3565`). The subscript node has no code-generation case of its own: `CodeGen.forSubscriptExpr` throws if reached (`codegen/CodeGen.java:4931`), so every `a[i]` is desugared into a method call on the array's trait before code generation.

Stamping renames; it cannot change a representation. Verified (§9, probe 1): the template for `object Box[\T\](x: T)` has the field `x` with descriptor `LT;`; the stamped `Box⟦FRR64⟧` has `Lcom/sun/fortress/compiler/runtimeValues/FRR64;`. The substitution replaces one class name with another inside a reference descriptor. `[D` is not a class name, so no instantiation of a generic template can produce a `double[]` field, and the stamped interface's `get` returns the boxed class. The place the team left for anything cleverer is `if (false) { // Here will go all the magic expando-stuff. }` at `InstantiatingClassloader.java:168-172`.

The checker does not implement `nat` parameters, and the code generator carries them in names only; §6 has the full account. In one line each, verified (§9, probes 3-6): a nat passed explicitly to a function that uses it in no type compiles and runs; a nat that must be inferred from an argument is `Not yet implemented`; a nat-parameterised object instantiated with a literal crashes the checker with `ClassCastException: VarType cannot be cast to IntExpr`; a nat used as a value inside a function compiles to a reference to a class that does not exist and dies at run time. So sized array types cannot be declared on this path until the second fork lands, and unsized ones can be declared today.

The generic generator protocol exists here: `Generator[\E1\]` (`CompilerBuiltin.fsi:614`) and `Reduction[\R\]` (`:638`). What is missing for arrays is `Indexed` and everything below it.

## 3. What microGPT needs from arrays

The vocabulary is `explorations/run-c4/src/FlatArrays.fsi`, inventoried in `reviews/c4-flatarrays-review.md` §1 at the committed version `a92569f83`: 38 declarations, of which 5 are aliases of library calls, 26 are new operations over the library's own array types, and 9 are new structures. (The working copy is under uncommitted repair after that review; Pavol's position of 2026-09-19 is that the model's operators stay operators and the vocabulary is repaired around the notation, `POSITIONS.md:38`, so the 26 stay operators and the compile path's overloading check must let them stand beside the prelude's `+`, `MAX` and juxtaposition, which is unmeasured.)

The 26 operations, by what they do to the data. Elementwise maps, 14: `+` and `-` with a scalar in both orders (4), the elementwise product `×`, `/` array by array and array by scalar (2), `MAX` with a scalar (2), `>` giving 0/1, `SQRT`, `exp`, `log`, and the broadcast add of a matrix to every plane of a rank-3 array (review rows 5-17 and 30). Contractions, meaning sums of products such as a matrix product, 2: the row scaling `diag(v) m` (row 20) and the plane-wise batched product of two rank-3 arrays (row 29); the 16×16 matrix product itself and `DOT` are the shipped library's own (`FortressLibrary.fss:2621-2629`) and are what the kernels time. Structural, 10: the row lift `rows(f, m)` in four shapes (31-34), `gather`, `onehot`, `pick`, `flat` (35-38) and the two transposes `^T` (39-40). The 9 structures are views: `Diag`, the transposed rank-3 array, the matrix over a slice of the flat parameter vector (`PView`), the row and plane-row views, and `heads`/`unheads`/`plane`, each a six-line object whose `get`/`put` index another array (review §1, last paragraph).

Element types needed: `RR64` for every weight and activation, `ZZ32` for keys and the integer corpus, `Char`/`String` for the corpus text in `FlatData`. Sizes: the hyperparameters are literals bound to names (`MicroGptFlat.fss:17`: 16, 16, 4, 4, 27, 26); the flat parameter vector's 4192 is computed; every constructor takes a run-time size and returns the unsized `Array[\RR64,ZZ32\]` or `Array[\RR64,(ZZ32,ZZ32)\]` (`FlatArrays.fss:14-17` at `a92569f83`); nat-typed values enter through views built with `reflect` (`PView[\nat s, nat r, nat c\]`, `viewN(…, reflect(nr), reflect(nc))`, `:54-62`) and through the model's `Matrix`/`Array3` declarations: 20 of the api's declarations carry a nat, 25 in the focused base's `FlatArrays2.fsi`.

The measured cost of boxing on these shapes (`perf-probes/kernels/REPORT.md` §2; Java models of the runtime's own box, `Box[]` storage, against `double[]`): the 4192-element dot product 6.26× slower boxed, the 16×16 matrix product 6.53×, the row lift with `rmsn` 2.59×. The generic array object on top (an `Object[]` behind an interface with a `checkcast` per read) adds 9 %, 1.6 % and 4.8 %. The cost is the element boxes, not the container's genericity. None of the three kernels compiles today: 77 errors, `Array`, `Vector`, `Array3` undefined, all raised inside `FlatArrays.fsi`. All eighteen components of the two microGPT programs stop at disambiguation on `Array` (8), `Char` (5), `ImmutableArray` (3), `Vector` (2) (`compile-ladder/baseline-2026-09-19/microgpt-phase.md`); on the ladder, 42 files stop first on an array name (`ImmutableArray` 26, `Array1` 6, `Array` 6, `Array2` 2, the factory `array` 2; counted from `baseline-2026-09-19/ladder.tsv`).

## 4. The options as they stood before the rulings

Option (a), the interpreter's protocol ported boxed, is closed by Pavol's first ruling (§6) and is kept here only so the record shows what was rejected: about 1,200 lines of trait layer moved into `CompilerLibrary` over an `Object[]` native class; the fastest route to "the kernels compile"; the 6.3-6.5× kept; unboxing afterwards a second storage class under the same traits, "the same library written twice" (`map/README.md:127`).

### (b) `double[]`-backed arrays with unboxed elements designed in

What is built: `FRR64Vector.java` beside `FZZ32Vector.java`, the same 83 lines with `double[] val` and the four shape integers; `simpleDoubleVector.java` beside `simpleIntVector.java`; a trait in `CompilerBuiltin.fsi` with the nine members of `ZZ32Vector`; one line in `NamingCzar`'s special table and one in its foreign-route chain; a factory. That is the team's own five wiring sites. `ZZ32Vector` already covers the integer keys; `StringVector` the corpus.

Its own class, not a stamped instance: §2 verified that stamping substitutes class names into reference descriptors, so no instantiation of a generic template can hold a `double[]`; the `RR64` store is a hand-written class, as `FZZ32Vector` is, and anything reached through a generic trait's `get` is boxed at that boundary.

What the code generator must learn, if the loops are to run unboxed in generated code: an element read must become `getfield val:[D`, `iload i`, `daload` instead of the four-call chain of §2, and a bare `double` must have somewhere to go, which means a local variable slot of descriptor `D` and `dadd`/`dmul` for `RR64` arithmetic whenever the checker's static type is `RR64`, boxing only where a value meets a `T` or an `Any`. That is unboxing by static type (`performance-roadmap.md` A1) in `CodeGen.java` (6,750 lines) and `VarCodeGen`; every rung of it is a `.java` rung under the full gate with the 85 files as the net. Without it, an unboxed store with boxed traffic is what `ZZ32Vector` is today; whether that alone is faster than boxed storage is not measured, and the Java model that would answer it is one more class in `perf-probes/kernels/java/`.

A second route to unboxed loops needs no code-generator change: write the loops of the vocabulary's operations as Java natives over `double[]` (the dot product, the matrix product, the elementwise maps, `SQRT`/`exp`/`log` over an array), so a box is paid once per whole-array operation instead of once per element. This is the shape of an APL implementation, each primitive a native loop, and microGPT in the C4 form is whole-array vocabulary; the residue is the user lambdas passed to `fill`, `map` and `rows`, which box per element. Not the team's precedent: their `ZZ32Vector` operators are Fortress loops over boxed subscripts (`CompilerLibrary.fss:484-535`).

As first written, (b) carried sizes as run-time fields only and no nat in the type; Pavol's second ruling (§6) removes that half, so what survives of (b) is the store class and the two routes to unboxed loops, under the library's sized traits of §6.

### (c) The library's generic traits over per-element-type native stores

What is built: the interpreter's trait layer, `Indexed`, `ReadableArray`, `Array[\E,I\]`, `Array1[\T, nat b0, nat s0\]`, `Vector`, `Matrix`, `Array3`, with `fill`, `map`, `ivmap`, `t()` and the views written in Fortress as they are in `FortressLibrary.fss`; beneath them, in the place of `PrimitiveArray[\T, nat s0\]` (`__DefaultVector`'s `mem` field, `.fss:2204-2205`), one hand-written native store per element type: the `double[]` class of (b) for `RR64`, `FZZ32Vector` for `ZZ32`, a boxed `Object[]` store for every other `T`. The checker sees the library's own types; the model's `Array[\RR64,ZZ32\]`, `Vector[\RR64,s\]`, `Matrix[\RR64,r,c\]` resolve as written.

What selects the store. Not the checker: it has no notion of representation. The factory does, from the run-time type tag: a generic instantiation carries its arguments as run-time type descriptors (probe 1's `Box$RTTIc` holds a field `T` of type `RTTI`), so a native helper behind `array1[\T, nat s0\]()` can return the `double[]` store when `T`'s tag is `FRR64` and the boxed store otherwise, which is `performance-roadmap.md` A2's "class tag". Alternatively the vocabulary's `vec`/`mat` make the `RR64` store directly, which is what `FlatArrays.fss:14-17` already does through `array[\RR64\](n)`.

How a hand-written class sits under a stamped generic trait: `FZZ32Vector extends fortress.CompilerBuiltin.ZZ32Vector.DefaultTraitMethods implements ZZ32Vector` (`FZZ32Vector.java:16-17`), a non-generic Fortress trait whose generated abstract class the Java extends. So the store's trait must be non-generic (`RR64Store`), declared in Fortress as extending the generic `Array[\RR64,ZZ32\]`, and the generated abstract class then carries the stamped supertype. Unprobed: that a non-generic trait extending an instantiated generic supertype with a hand-written implementation class compiles and links; it is the first thing the array rung of §8 finds out.

Can Fortress's overloading express the specialisation? Not as two top-level declarations of one operator: `opr +[\I\](a: Array[\RR64,I\], s: RR64)` beside `opr +(a: RR64Store, s: RR64)` is one declaration with a static parameter and one without, forbidden by `Specification/basic/overloading.tex:100-105` and refused by the interpreter's check (the review's probe A). It is expressible as one declaration over the trait whose work is done by the object's own methods (`get`, `put`, `dot`, the product), which is the interpreter's own idiom for views (`TransposedMatrix`, `FortressLibrary.fss:2571-2588`) and ordinary virtual dispatch. Through the trait every `get` still boxes at the boundary; unboxed loops exist only inside the store's native methods (the second route of (b)) or after the code generator learns to unbox (the first route of (b)).

Cost: one `.java` rung (store class, factory helper, the non-generic store trait, full gate), one library rung (the trait layer in Fortress, `testFast` alone), then the native operations as in (b); all of it after or beside the nat rung of §6, because `Array1` and `Vector` cannot be declared before it. What it forecloses: nothing named; `ImmutableArray` (26 ladder files, through `List.fsi`) needs the immutable variant in every option.

## 5. What the specification and the team's own drafts say

The specification's array is a family of sized types over a generic one, and it keeps both factories. The type of a k-dimensional array expression is `Array k[T, 0, n0, …, 0, n_{k-1}]`, abbreviated `T[n0, …]`, with a footnote that "As of March 2008, the Fortress library provides Array k types for 1 ≤ k ≤ 3" (`Specification/basic/expressions/aggregate.tex:130-136`); a two-dimensional array of numbers "is a matrix", a one-dimensional one "is a vector", with the editors' margin notes reading "can be coerced to a matrix" (`:152-170`). The factory table gives `array[E](size)` for "the specified runtime-determined size" and `array1[E,n]()` for "statically determined size n" side by side (`advanced/parallelism-locality/arrays-distributed.tex:42-48`).

On storage: "As in Fortran, Fortress arrays are complex data structures; simple linear storage is encapsulated by the HeapSequence type, which is used in the implementation of arrays" (`arrays-distributed.tex:18-22`), with the note that distributions and `HeapSequence` "are not yet supported" (`:15-16`). Nothing in the prose says boxed or unboxed; the intent is an array as a structure over a linear store, which (c) is.

On sizes in types: "types can be parametric with respect to other types and values (most notably natural numbers)" (`preliminaries/intro/nutshell.tex:85-86`); the nat chapter is quoted in §6.

On the intended aggregate: "Guy's proposal for making tensors the principal user-level indexed aggregate type in Fortress (06/27/07)" and his email "Arrays, matrices, and tensors (short)" of 12/15/06 (`appendices/future.tex:63-65`); the FAQ's answer to variable-sized arrays with static bounds checking is a link to a wiki page that no longer exists (`appendices/FAQ.tex:55-57`); the emails themselves are not in the repository (`map/design-intent-sources.md:111, 128`).

On the compiled encoding: the JVM paper says "mentions of static parameters are replaced with their upper bounds in domain and range" (`Papers/Implementation/MethodMapping.tex:134`), which is why stamping is a renaming, and that the template's side file "contains info about the static parameters, including their names, whether they are types, oprs, or nats" (`:142`), which the tree does (§6). The team's own unboxing note is `compiler/optimization/Unbox.java:18-30`: four cases, "primitive. ZZ{8,16,32,64}, RR{32,64}, Boolean", singleton objects, unboxed fields, "comprises unboxed"; a taxonomy referenced by nothing.

The drafts say nothing about arrays. `Library/incomplete/` (24 files) contains no mention of an array. `Library/GeneratorLibrary.fss` and `.fsi` (783 lines, imported by nothing) are the generator and reduction protocol, `Container`, `DefaultGeneratorImplementation`, without `Indexed` or any array. `Fortress.Operators.fsi.INCOMPLETE` is the algebra above `Number` and names no aggregate. What the team shipped in this world is `ZZ32Vector`, and it is the only precedent with code behind it.

## 6. The nat plan: what the second fork must deliver for the first

Pavol's rulings of 2026-09-19, in his words. On boxing: "we must go to double array for performance. There is again no question about this. If this should have been high performance language, it cannot be boxed." On sizes: "I don't know [that] we can sidestep the nat issue. That is a central design point that they are using." So the sized types are built as the team designed them, `Vector[\T, nat s0\]` and `Matrix[\T, nat s0, nat s1\]`, the checker is taught nat parameters, and the two forks are taken together. On method: "study the existing parts of the Fortress library meticulously, and use those patterns for extending the standard library in the native way"; microGPT's operations go into the standard library in its spirit, not into a user file.

### 6a. What the checker and the code generator lack today

Inference. `STypesUtil.makeInferenceArg` answers `NI.nyi()` for `KindInt`, `KindBool`, `KindDim`, `KindUnit` and `KindNat` (`scala_src/useful/STypesUtil.scala:546-559`), so any call whose nat must be worked out from an argument, `same(x, y)` with `same[\nat n\](a: Vec[\n\], b: Vec[\n\])`, dies with `Not yet implemented` (probe 5). Every product in the library is such a call (`opr DOT[\T, nat n, nat m, nat p\]`).

Equality. `pEqv(IntArg, IntArg)` is `pTrue()` under the team's comment "Not handling all static args properly yet" (`scala_src/types/TypeAnalyzer.scala:327-337`): today any two nat arguments are equal, `Vector[\T,3\]` is `Vector[\T,4\]`. Exclusion has the matching hole, "Todo: Handle int, nat, bool args" (`:447-451`). Export checking compares an api's and a component's declarations with `equalIntExprs`, which is `= false` with the comment "Not implemented!" (`scala_src/typechecker/ExportChecker.scala:640-648`), so every exported signature mentioning `Vector[\T,n\]` fails the export check once the crashes are gone.

Objects. `object Vec[\nat n\](v: ZZ32Vector)` instantiated as `Vec[\4\](…)`, with no `extends` and no use of `n`, crashes with `ClassCastException: VarType cannot be cast to IntExpr` (probe 4), in the method gathering that composes one static-argument replacer with another (`STypesUtil.scala:1536-1548`, `compiler/typechecker/StaticTypeReplacer.java:95-99, 102, 121-128, 221-223`): somewhere the nat `n` is held as a type argument `TypeArg(VarType n)` and a later `IntArg(IntRef n)` receives a `VarType` where an integer expression is required. The disambiguator does rewrite a known nat's argument from `TypeArg` to `IntArg` (`compiler/disambiguator/TypeDisambiguator.java:402-433`, with its comment "TODO: shouldn't there be a NatArg class?"; `:663-697`, "All Args are parsed as TypeArgs"); which path escapes it was not found by reading, here or in `reviews/nat-checking-plan.md` §c.

Code generation. A nat in value position, `foo[\nat n\](): ZZ32 = n.asZZ32 + 1`, compiles, and the call sites are stamped as `foo⟦5⟧` and `foo⟦4192⟧` (probe 6), because the name mangler carries a nat literal or symbol into the instantiation name (`NamingCzar.java:1891-1911`, the kind tag `intnat`, `runtimeSystem/Naming.java:213`) and the template's side file records the kind (`function 1 6 intnat 1 n`). But the template body reads `n` as `getstatic NatVal$n.ONLY`, a top-level variable class that does not exist, and the run dies with `NoClassDefFoundError: NatVal$n`. The loader treats only the operator kind specially (`Naming.java:98`) and substitutes names; nothing turns a nat in a name back into a value. An `IntArg` in an `extends` clause throws `CompilerError("Only emitting RTTI for types right now")` (`codegen/CodeGen.java:5783-5792`), which every `object … extends Vector[\RR64,s\]` will hit. `compiler_tests/Compiled1.av.fss` declares the value use and never calls it, which is why the gate is green over it.

What already works: an explicit nat argument to a function that uses it in no type (probe 3; `compiler_tests/Compiled1.p.fss`, `Compiled6.af.fss`); a nat in value position types as an integer literal (`typechecker/staticenv/KindEnv.scala:64-70`, the spec's "any context a variable of type N32 can appear"); the instantiation walker already substitutes `IntRef` (`STypesUtil.scala:627-679`, per the plan).

### 6b. What the team wrote, and what the interpreter does

The chapter opens "Non-type static parameters and static expressions are not yet supported. The examples in this chapter are not tested nor run by the interpreter." (`Specification/basic/trait-parameters.tex:15-17`). The semantics: "These parameters are instantiated at runtime with numeric values. A nat parameter may be used to instantiate other nat parameters, or to appear in any context that a variable of type N32 can appear, except that it cannot be assigned to." (`:82-86`). The one example is `makeVector`, "a nat parameter s0, which appears in both the parameter type and return type" (`:94-97`). Static expressions in types (`n+1`) are "not yet supported" (`basic/expressions/constant.tex:15`) and only "a restricted subset of operations" may occur as static arguments (`:17-25`), never listed.

The internal meeting record (`Specification-1.0-frozen/appendices/internal-document.tex:160-217`) decided: overloading `T[\n+1\]` against `T[\0\]` is "Not allowed" (`:167-182`); `T[\1\]` against `T[\0\]` is "Allowed" because "nat parameters are all instantiated" (`:183-198`); `ZZ32` against `T[\0\]` is "Allowed" "if our implementation strategy for nat parameters is 'don't instantiate'" (`:199-208`), the one recorded implementation stance; mutually recursive nat-arithmetic extends clauses are out by acyclicity (`:210-217`). The JVM paper planned to carry nats through templates by name (`MethodMapping.tex:142`), which is what the mangler and the side file do.

The interpreter has the whole run-time half. A nat is a type interned per value (`IntNat.java`); a static argument is evaluated, `+`, `-` and juxtaposition included (`interpreter/evaluator/EvalType.java:431-464`); at a call, `unifyStaticArg` requires a literal to be equal, binds a symbol, and errors on anything else (`IntNat.java:127-147`); an unbound parameter becomes `BottomType` (`EvaluatorBase.java:238-240`); the unification runs at every call (`EvaluatorBase.java:88-176`). So the checker's job is the interpreter's `unifyStaticArg` moved to compile time: symbols and literals, equality, no arithmetic, which is also the letter of the meeting record.

### 6d. The compiled representation of a nat-sized `double[]` array

Where the nat lives, two places, both needed: in the stamped class's name, `Vector⟦FRR64,16⟧` and `Vector⟦FRR64,4192⟧` being different classes, which the loader already produces from the mangled name (probe 6) and which is what makes the nat a fact for the checker and for dispatch; and as a run-time field of the native store (`dim_x` in the `FZZ32Vector` shape), because nothing today turns the name back into a value, the store's `get`, `put` and `|self|` need the number, and the `double[]` carries its own length. One class per distinct size is the price; microGPT's sizes are six literals and a computed 4192.

What the loader must do with a nat argument beyond what it does: supply a value for a nat in value position inside a template. Either the instantiater rewrites the `getstatic <Component>$n.ONLY` reference into a constant when it stamps `⟦…,5,…⟧` (an instruction-level substitution in `Instantiater`, the job the expando stub at `InstantiatingClassloader.java:168-172` was left for), or the code generator emits a read from the run-time type descriptor, which today refuses `IntArg` (`CodeGen.java:5783`). Under the two-place representation the library's value uses of a nat are few (`i s1 + j` in `__DefaultArray2`, the `N[\s0\]` witness in `subarray`) and the store's field can serve the first; the second is explicit-only. So the value mechanism is a `.java` rung of its own, needed for the full port and not for the first kernels. Default: the field first, the name-to-constant substitution when the port reaches `subarray`.

Run-time sizes: `array[\RR64\](n)` with `n` computed cannot name its class at compile time. Either a native helper builds the stamped name from the integer and asks the loader for `Array1⟦FRR64,0,4192⟧` by that string, which is a string from a number and unprobed, or the run-time-sized factory returns the unsized `Array[\RR64,ZZ32\]` as it already does in the model (`FlatArrays.fss:14-17`) and only literal and symbol sizes get sized classes. Default: the second; it is what the model writes today, and the `reflect` group of §6c is then the one library pattern the compiled world does not reproduce until the first is probed.

### 6e. The checker edit and the shadow route, assessed

The plan (`reviews/nat-checking-plan.md` §c-§f): a third track beside types and operators in the constraint solver, `Formula.scala` (711 lines) taking most of the diff, `TypeAnalyzer.pEqv` and its cast guard, `STypesUtil.makeInferenceArg`, `ExportChecker.equalIntExprs`, `TypeWellFormedChecker` rejecting arithmetic in a static argument; about 24 functions in five Scala files, 200-300 lines; no Java; the five nat compiler tests stay green; no catalogued test flips. The shadow route (`next-climb.md:102-104`; the recipe of `perf-probes/template-check/run-all.sh`): copies of the five files compiled with `scala.tools.nsc.Main` into `shadow-classes`, placed first on the class path; the gate can be run with the shadow overlaid on `ProjectFortress/build`, as the template fix was (its 31 lines went green that way, `33-testfast.out`, `34-testsystem.out`). Assessment: the tree is unsealed and the batch script already runs `.scala` rungs under the full gate with the test written first, so the shadow is not a gate substitute; it is worth one worker session for the two unknowns and nothing more. ## 7. The decision tree, with two questions closed

Question 1, boxed or `double[]`: closed by Pavol, `double[]`. Consequence: the `RR64` store is a hand-written class on the `FZZ32Vector` pattern, never a stamped generic (§2), and the boxed `Object[]` store exists only for element types that have no native store.

Question 4, where sizes live: closed by Pavol, in the type as the team designed. Consequences: the checker rung of §6e precedes the first sized declaration; the export checker and the object crash are on the path, not optional; every distinct size is a stamped class; the run-time-sized factory returns the unsized `Array` until the string-from-number route is probed (§6d, default).

Question 2, open: what implements the library's sized traits under `double[]`?
Branch "native stores per element type under the library's generic objects": `__DefaultVector[\T, nat s0\]` keeps its shape and its `mem` field is the `RR64` store for `RR64`, `FZZ32Vector` for `ZZ32`, the boxed store otherwise, chosen by the factory from the run-time type tag; the interpreter's own layering with `PrimitiveArray` replaced; one unprobed link, the non-generic store trait under the generic `Array` (§4c).
Branch "the loader picks a `double[]` template per instantiation": the expando route; `PrimitiveArray⟦FRR64,4192⟧` would load a different class than `PrimitiveArray⟦FZZ32,4192⟧`; nothing of it exists, and the instantiater's only tool is name substitution.
Default: the first; it needs one probe and no loader change, and it is the library's own structure.

Question 3, open: where do the loops run unboxed?
Branch "inside native whole-array operations": Java helpers over `double[]` for the contractions and elementwise maps; a box per operation; no code-generator change; the user lambdas of `fill`, `map`, `rows` still box per element.
Branch "in generated code": the code generator learns `D` locals, `daload`/`dastore`, `dadd`/`dmul` for statically `RR64` code; every rung `.java` under the full gate; unlocks unboxed loops written in Fortress.
Default: natives first, with the kernel measurement in the first array rung; generated-code unboxing as PLAN's step 4, once the measured residue says what it is worth.

Question 5, open, from the third ruling: the library's unused nats (`.fsi:1496-1523`). Branch "default an unconstrained nat to `0`" keeps the library's text; branch "refuse and delete the dead parameters" edits six library declarations. Default: the first, the plan's own recommendation, and the only reason the checker rung would otherwise touch `Library/`.

Where microGPT's 26 operations go is not a question after the third ruling: into `CompilerLibrary` in the library's own style, whose precedent for scalar extension is the `ZZ32` block at `FortressLibrary.fss:4477-4517` (`opr +(x: Array[\ZZ32,ZZ32\], y: ZZ32)` beside `AdditiveGroup.+`, the same overloading shape the review found illegal by the letter and the interpreter accepts), for maps `map(f)` over `replica`, for structure the view objects, and for products the shared-nat operators of §6c.
