# Change 37 and the POPL 2019 paper

Citations: a TeX file of the paper is cited by its name and line, all in `Papers/Variance/`. "p. 11:N" is a page of the published paper; "TR p. 1:N" is a page of the technical report. "The extract" is `research/extracts/ParkPOPL2019-extract.md`.

## In short

- By the paper's rules, `trait Wide` with its own `+`, beside the library's `+` between an array and a number, is not a valid set of overloads. It breaks the Meet Rule. So walk's refusal is the paper's answer. The checker's acceptance across the import (row 918) is not.
- In the paper's calculus, no trait has a `comprises` clause and none has an `excludes` clause. Two different traits never exclude each other. Only an object, or two instances of one generic trait, can exclude. So in the paper every trait is open, as `Number` is open now (P-160).
- Variance plays no part in this case. It decides only whether two instances of one generic trait exclude, and no such pair meets here. The revival's generics are invariant anyway.
- The fix of change 37, `excludes { Number }`, is the team's own tool. The team's 2011 paper names it among Fortress's three ways to declare exclusion. The 2019 paper leaves it out for brevity, calls adding it "obvious", and does not reject it.
- The paper's own calculus has one other fix that fits: declare `Wide` as an object. An object is a leaf, so it excludes `Number` and every array with no clause. The cost: no other type can extend `Wide`. A probe shows that walk loads and runs this form (section 10).
- No decision of the curator's on record changes (section 9).

## 1. The case, in code

The test, `ProjectFortress/tests/NumberOpenTraitPlusBesideArrayWalk.fss:6-12`:

```
trait Wide excludes { String }
  getter big(): ZZ32
  opr +(self, other: Wide): Wide = WideOf(self.big + other.big)
end
object WideOf(b: ZZ32) extends Wide
  getter big(): ZZ32 = b
end
```

The library's two `+` between an array and a number, `Library/FortressLibrary.fss:5061-5062` (bodies left out here):

```
opr +[\T extends { Number, AdditiveGroup[\T\] }, I extends Index\](x: Array[\T,I\], y: T): Array[\T,I\]
opr +[\T extends { Number, AdditiveGroup[\T\] }, I extends Index\](y: T, x: Array[\T,I\]): Array[\T,I\]
```

What the library's types declare:

- `trait Number extends { AnyAdditiveGroup, AnyMultiplicativeRing }`, with no `comprises` and no `excludes` clause (`Library/FortressLibrary.fsi:288`; P-160, F-324).
- `Array` extends `ReadableArray` (`.fsi:1571`), which extends `HasRank` and `Indexed` (`.fsi:1496-1497`); `Indexed` extends `Generator` (`.fsi:1359`). `HasRank excludes { Number, AnyMaybe }` (`.fsi:1300`), and `Generator` `excludes { Number }` (`.fsi:806-807`). So no array is a number, and the library's two `+` stand beside each other.
- `HasRank`'s `comprises` clause is "not yet" (`.fsi:1301`), so arrays are open too.

A program could add these two types. No test declares them; they show what the rules must allow for.

```
object B extends { Wide, Number, AdditiveGroup[\B\] } ... end
object A extends { Wide, Array[\B, ZZ32\] } ... end
```

Nothing in the library or in `Wide` forbids them. Take `a: A` and `b: B`:

- `a + b` fits `Wide`'s `+`, because `a` and `b` are both `Wide`s.
- `a + b` fits the library's first `+` at `T = B` and `I = ZZ32`, because `a` is an `Array[\B, ZZ32\]` and `b` is a `B`.
- Neither `+` is more specific than the other. A pair of `Wide`s need not hold an array, and an array of numbers need not be a `Wide`.
- No third `+` takes exactly the calls that fit both.
- So the call `a + b` has no single winner. `b + a` meets the library's second `+` in the same way.

What the two paths do, from the brief and the record:

- Walk refuses the program at load: "fails the Meet Rule: neither is found to be more specific than the other or to exclude it" (`ProjectFortress/tests/NumberOpenTraitPlusBesideArrayWalk.test:1`).
- The compiled checker, over the one library, accepts it. It refuses the same pair when both `+` are declared in one component: "Invalid overloading of PLUS in component OpenPlusControl" (row 918; `explorations/compile-ladder/rung-number-open/REPORT.md:59`).
- With `excludes { Number }` added, walk loads the trait (`ProjectFortress/tests/CoercionOverloadRungC.fss:6`; `REPORT.md:104`).

## 2. The words used below

- **Domain**: the tuple of a declaration's parameter types. `Wide`'s `+` has the domain `(Wide, Wide)`; `self` counts at its own place. The library's first `+` has the domain "`(Array[\T,I\], T)` for some `T` and `I` within their bounds". The paper writes such a domain as an existential type, `∃⟦T, I⟧ (Array⟦T,I⟧, T)` (rules.tex:265-273, p. 11:12).
- **Applicable**: a declaration is applicable to a call if some instance of it takes the call's argument types (motiv.tex:126-129, p. 11:5).
- **More specific**: one declaration is more specific than another if its domain lies inside the other's (rules.tex:104-107, p. 11:12).
- **Meet** of two declarations: the argument types that both take. As a type, it is the intersection of the two domains (rules.tex:300-307, p. 11:13; Figure 6, rules.tex:176-182). Here it is "(a `Wide` that is also an `Array[\T,I\]`, a `Wide` that is also a `T`)", which the paper writes `(Wide ⊓ Array⟦T,I⟧, Wide ⊓ T)`.
- **Exclude**: two types exclude each other if no value has both. `Bottom` is the type with no values, so two types exclude if their intersection is `Bottom`.
- **Leaf**: a type that nothing extends. In Fortress and in the paper, an object.
- **Closed trait**: a trait with a `comprises` clause. **Nominal exclusion**: an `excludes` clause.
- **FGFV**: the paper's calculus, "Featherweight Generic Fortress with Variance": traits, objects, dotted methods and generic types with variance (intro.tex:199-204, p. 11:3).
- **Variance**: a mark on a trait's type parameter. With a covariant (`+`) parameter, `List⟦ZZ32⟧` is a `List⟦Number⟧`, because `ZZ32` is a `Number`. With an invariant (`=`) parameter, the two are unrelated. Revived Fortress has only invariant parameters (the `fortress-repo` skill, "Fortress as a language"; row 404 for the `covariant` keyword).

## 3. The paper's overload rules, with Fortress pairs

FGFV checks three rules on every pair of declarations of one name (Figure 5, rules.tex:6-100, p. 11:13; the informal statements at motiv.tex:226-244, p. 11:6).

- **No Duplicates.** Two declarations must not have the same domain. Refused: `f(x: ZZ32)` beside `f(y: ZZ32)`. A pair passes if one domain is not inside the other ([No-Dup-Not-Less], [No-Dup-Not-Gtr]).
- **Meet.** If some calls fit both declarations, some declaration must take exactly those calls. A pair passes in one of these ways:
  - [Meet-Excl]: the domains exclude. `g(x: Wide)` beside `g(x: Number)` passes when `trait Wide excludes { Number }`.
  - [Meet-Less] or [Meet-Gtr]: one domain lies inside the other. `h(x: Number)` beside `h(x: ZZ32)` passes.
  - [Meet-Third]: a third declaration's domain is equivalent to the meet.
  - The paper's own failing case is this one in small: `m2(x: A)` beside `m2(x: B)`, where a type `C` extends both `A` and `B`. "It is ambiguous which declaration to invoke due to multiple inheritance" (motiv.tex:12-35, p. 11:4). Its repair is a third `m2(x: C)` (motiv.tex:71-90), under the section's assumption that `C` is the only type below both.
- **Return Type.** If one declaration is more specific than the other, its return type must fit the other's ([Return-Not-Less], [Return-Test]).

Where and why the rules are checked:

- [D-Trait] and [D-Object] check every pair of the methods visible in each trait and object, declared or inherited (lang.tex:166-201, 279-290, 418-422; Figure 3, p. 11:10, and p. 11:11).
- [T-Program] checks all the declarations of a program in one environment (lang.tex:154-160, Figure 3, p. 11:10). A program is "a sequence of class declarations and a top-level expression", with no components (lang.tex:106-107, p. 11:8).
- The reason is Theorem 4.1: "For any method invocation, there always exists a unique most specific method declaration in its set of applicable method declarations" (rules.tex:509-521, p. 11:15). Its proof needs every pair to pass the Meet Rule: "Since d1, d2 ∈ {d}, they must satisfy the Meet Rule" (appendix.tex:1406-1447, TR Appendix D, p. 1:53).
- Variance does not change the rules: "the overloading rules for FGF remain the same because covariant or contravariant types affect only the well-formedness of method declarations rather than the validity of overloading" (rules.tex:107-111, p. 11:12).

## 4. How the paper decides that two types exclude

The published paper leaves the type relations to its report: "The entire type relations are formally defined in the companion report" (p. 11:15; in the report's TeX, "in Appendix A", rules.tex:447-450). The report gives them in Figures 18 and 19 (appendix.tex:116-209, TR pp. 1:34-35). The extract, written from the published paper, does not hold them. By the four ways that the question names:

- **An `excludes` clause: not in FGFV.** "While FGFV does not support features like modularity, nominal exclusion, and closed types in their work, they can be added in an obvious way" (related.tex:16-17, p. 11:25).
- **A `comprises` clause: not in FGFV.** "For conciseness, FGFV omits functional methods [Allen et al. 2007] and declarations of closed types [Allen et al. 2011], but these could be added back to FGFV in an obvious way" (intro.tex:203-204, p. 11:3).
- **An object as a leaf: yes.** Objects "are like Java final classes that cannot be extended" (lang.tex:109-110, p. 11:8). The rules:
  - two different objects always exclude ([Exc-Object-Different], appendix.tex:169-171);
  - an object excludes a trait that it does not extend ([Exc-Object-Trait], appendix.tex:189-191);
  - two instances of one generic object exclude unless their arguments are equal ([Exc-Object-Same], appendix.tex:163-165).
- **Two instances of one generic trait: yes.** Two traits exclude only if neither is below the other and some pair of their ancestors cannot be extended together ([Exc-Trait], appendix.tex:179-185). Two different traits can always be extended together (appendix.tex:197-199). Two instances of one trait cannot, by the variance of each parameter (appendix.tex:203-206):
  - invariant: when the two arguments differ;
  - covariant: when the two arguments exclude;
  - contravariant: never.
  This is the ancestor rule [Anc-Same-Trait] at work (lang.tex:388-397, Figure 4, p. 11:11).
- **Three more rules that this case uses:**
  - a type parameter excludes a type if one of its upper bounds does ([Exc-Param], appendix.tex:124-128);
  - two tuples exclude if they differ in size, or if one position excludes ([Exc-Tuple], [Exc-Tuple-Size], appendix.tex:153-159);
  - an intersection of two types that exclude is `Bottom` ([Sub-LIntersection], appendix.tex:99-102, TR p. 1:33).

So in FGFV two different traits never exclude each other, unless they extend two instances of one generic trait. The record already read the paper so: "two unrelated traits never do, since nothing forbids a class extending both" (`explorations/reviews/array-judgements-popl-check.md:129`).

Two of these rules are the readings that the checker and walk already build. [Exc-Param] is P-157's reading of a static parameter's bounds in the exclusion test, which P-157 calls "the POPL 2019 paper's own reduction". [Exc-Tuple], with existential reduction (rules.tex:337-356, pp. 11:13-14), is P-152's reading of exclusion over the whole tuple of parameter types.

## 5. The pair by the paper's rules

`Wide`'s `+` beside the library's first `+`. The second `+` is the mirror case.

1. No Duplicates passes. `(Wide, Wide)` is not inside the library's domain, since a `Wide` need not be an array ([No-Dup-Not-Less]).
2. Return Type passes, because neither domain lies inside the other ([Return-Not-Less]).
3. Meet:
   - [Meet-Less] and [Meet-Gtr] fail, as step 2 says.
   - [Meet-Third] fails: no third `+` has the meet as its domain.
   - [Meet-Excl] asks whether the meet, (a `Wide` that is also an `Array[\T,I\]`, a `Wide` that is also a `T`), is `Bottom`. By [Exc-Tuple] it is if one position excludes.
   - Position 1, `Wide` against `Array[\T,I\]`: two different traits. `Wide` extends only `Object`, so they share no generic trait at two instances. They do not exclude.
   - Position 2, `Wide` against `T`: by [Exc-Param], against `T`'s bounds. `Wide` against `Number`: two different traits, no generic ancestor; no exclusion. `Wide` against `AdditiveGroup[\T\]`: `Wide` extends no instance of `AdditiveGroup`; no exclusion.
   - So the meet is not `Bottom`, and [Meet-Excl] fails. The pair breaks the Meet Rule. The types `A` and `B` of section 1 are a call for which Theorem 4.1 would have no answer.
4. The "obvious" additions do not change this. No `comprises` clause bears on `Wide`, `Number` or arrays: `Number` has none since P-160, and `HasRank`'s is "not yet". No `excludes` clause relates `Wide` to `Number` or to arrays: `Wide` excludes only `String`.

Two limits of this reading:

- FGFV has only dotted methods: no top-level functions and no functional methods (intro.tex:203-204). This note reads a functional method as a declaration with `self`'s type at `self`'s place, and a top-level operator as a method without a receiver. The record reads the paper so (the extract, lines 413-414).
- The library's `+` is itself outside FGFV as written. Its `T` names itself in its bound, `AdditiveGroup[\T\]`, and the paper's restriction (2) says that "no reference to a method type parameter appears in any of the upper bounds" (lang.tex:437-442, p. 11:11; F-271; `explorations/reviews/array-judgements-popl-check.md:34`). The verdict does not rest on that bound: `AdditiveGroup[\T\]` excludes nothing here, and `Number` alone decides position 2.

## 6. Walk against the checker (row 918)

- The paper has no components. It checks all the declarations of a program together ([T-Program], lang.tex:154-160), and it names "modularity" among what it leaves out (related.tex:16-17). So no pair is exempt because one of its declarations comes from the library.
- The rules apply wherever both declarations are visible ([D-Trait] and [D-Object], lang.tex:418-422). Here that is the program's component, which declares `Wide`'s `+` and imports the library's.
- So walk's refusal is the paper's answer. The checker's acceptance across the import is the gap that row 918 records, and its refusal inside one component is the paper's answer too.
- The specification gives the same reason for the rules: they eliminate "some possibility of ambiguous calls at run time, whether or not these calls actually appear in the program" (`Specification/basic/overloading.tex:33-35`). No program needs to declare `A` and `B` for the pair to be refused.
- The paper does not say how a checker that works one component at a time should share this check between a library and a program. CF, the team's 2007 calculus with components, top-level functions and functional methods (motiv.tex:39-44; "Modular Multiple Dispatch with Multiple Inheritance", SAC 2007), may; it is not in the tree and was not read.

## 7. Variance

- Variance plays no part. The paper says that it affects "only the well-formedness of method declarations rather than the validity of overloading" (rules.tex:107-111, p. 11:12).
- Variance enters the exclusion test in one place: two instances of one generic trait (appendix.tex:203-206). The paper's own example: `sort(x: List⟦A⟧)` beside `sort(x: List⟦B⟧)`, where `C` is below both `A` and `B`. With a covariant `List`, both take a `List⟦C⟧`, so the pair needs a third `sort` (motiv.tex:287-310, p. 11:6). With an invariant `List`, the two domains exclude.
- In this pair, no generic trait meets another instance of itself. `Wide` and `Number` are not generic, and `Array[\T,I\]` and `AdditiveGroup[\T\]` meet only `Wide`. So the verdict is the same under every variance.
- The revival's generics are invariant, so the question would not arise in Fortress code today.

## 8. The fix

- **`excludes { Number }` is the team's way.** It is nominal exclusion, which FGFV leaves out and calls an obvious addition (related.tex:16-17). The team's 2011 paper names it: "Fortress provides three mechanisms to explicitly declare exclusion: an `object` declaration, a `comprises` clause and an `excludes` clause" (`Papers/Types/exclusion.tick:58-59`). It treats exclusion as the trivial case of the Meet Rule (`Papers/Types/exclusion.tick:40-56`). With the clause, position 2 of the meet is `Bottom` by [Exc-Param]: `T`'s bound `Number` excludes `Wide`. So [Meet-Excl] holds.
- **Excluding arrays** (`excludes { HasRank }`, the trait that every array of the library extends) makes position 1 `Bottom` instead. The rung chose `Number` for `CoercionOverloadRungC` and named `HasRank` as the way not taken (`REPORT.md:146`).
- **The paper's own way: make `Wide` an object.** An object excludes every trait that it does not extend ([Exc-Object-Trait]), so `Wide` would exclude `Number` and `Array[\T,I\]` with no clause. This is the only exclusion inside FGFV that fits a type that is neither a number nor an array. The cost: no other type can extend `Wide`, so `WideOf` and any other `Wide` go. Walk loads and runs this form (section 10).
- **Two more ways in the rules, which do not fit:**
  - Make `Wide` extend an instance of a generic trait that every number or every array extends at another instance. [Exc-Trait] would then exclude them, but such a parent is odd for a trait that is neither.
  - [Meet-Third]: a third `+` whose domain is the meet. FGFV's intersection types are internal only (lang.tex:247-253, p. 11:9), and Fortress writes none. A static parameter with two bounds, as `A extends { Array[\T,I\], Wide }`, names one, but its bound names other type parameters of the same method, which restriction (2) forbids. The program would also have to say what `+` does on a value that is both.

## 9. Bearing on the decisions on record

- **P-160, `Number` opened: stands.** In FGFV every trait is open. Change 37 is the cost that any open trait has, and the paper gives no reason to close `Number`. Change 37 is about a trait that is not a number. A program's own number type, such as `CC64`, is the case that P-160 opened `Number` for, and its `+` from `AdditiveGroup` stands beside the library's through P-157 and F-318.
- **P-157 and P-152: confirmed.** [Exc-Param] is P-157's bound reading; [Exc-Tuple] with existential reduction is P-152's.
- **Row 918: stands.** The paper makes walk's refusal the right answer, and the checker's acceptance across the import the gap.
- **Change 37's text: correct by the paper.** It gives two fixes, both nominal exclusion. The third, an object, is the one inside the paper's own calculus. Whether the paragraph names it is the coordinator's choice.
