# The hard set: the 109 bindings that cannot name their helper as a bare string

## 1. For the curator

- **The problem, measured.** Moved onto their existing helpers as bare strings, the sample's four bindings over `NN32`, `NN64` and `Char` give the distance 4 on the base code, one error each, such as 'Could not check call to function builtinPrimitive_simpleUnsignedIntArith_unsignedIntOverflowingAdd - (ZZ32, ZZ32)->ZZ32 is not applicable to an argument of type (NN32, NN32).' Walk loads the same four strings with no change and the sample's walk test passes (section 5, runs B1 and B2). So for the 82 bindings over `Char` (40), `NN32` (22) and `NN64` (20) only the compiled checker's reading of a Java `int` or `long` stands in the way, never walk.
- **The team's own device.** The six special names are transfer functions, not a naming scheme for operations: Guy Steele's commit of 2011-06-24 (`c2c769094`) adds "two trivial transfer functions, one to convert from ZZ32 to Character and one to convert from Character to ZZ32", names them so "that no one would stumble across them by accident", and writes every `Character` operation as a composition, `toLowerCase(self): Character = jMakeCharacter(jCharToLowerCase(jCodePoint(self)))`, hoping "that optimizations downstream will open-code the transfer methods". Jean-Baptiste Tristan copied the device for `NN32` and `NN64` (`25f7cf913`, 2011-11-23; `b22c4ac56`, 2012-01-03). At the team's last commit the prelude calls the six transfers 295 times on 154 lines (section 3).
- **What each way does on the sample** (section 5): way 1, helpers with special names, needs a new name rule in the checker and a new helper per binding, and its name rule cannot express a binding whose `int` positions hold two types (`javaDigit(self, radix:ZZ32)`): distance 1. Way 2 read in the foreign-type table (2a) is order-dependent and rewrites a wrapper class that other compiled code shares: distance 1 in the one library, 0 when one unrelated binding is put back on its glue class, and in the compiler's world its checker and its wrapper generator read one helper differently in one JVM. Way 2 read at the rewrite (2b), where the compiled path's rewrite composes the call with the team's six transfers wherever the declared type and the helper's Java type differ: distance 0, walk's suite 695 tests and no failure, the compiled sample links and runs. Way 3, a second declaration that converts, written in the library: distance 0, walk's suite 695 and no failure, the compiled form runs on the unchanged code; it is the only way that admits the binding over `AnyIntegral`.
- **The three principles.** For the 82 they agree on way 2b by this probe's reading: the team's later word is the composition through the six transfers (2b and 3), and the library as the team wrote it is one bare body at the declared types, which walk carries by the declaration (1, 2a and 2b). They split on way 1 (the library admits it; the team's practice and Steele's words go against many special names) and on way 3 (the team's practice; the library's form and P-58's "keeps that form" go against it). The peers, which weigh only where the team is silent, corroborate 2b: foreign-function interfaces take the declaration's types and generate the conversion (section 6). For the rest of the 109 no bare-string way admits them, and the principles do not settle how they convert (section 4.4).
- **Recommendation, the probe's:** take way 2 at the rewrite (2b) for the 82, as a rung H of climb batch 24 that changes `compiler/BuiltinPrimitiveRewriter.java` only and moves 80 of the 82 (NN32's `asFloat` waits for fork 12, its `CHOOSE` for rung K), and leave the rest of the 109 to a decision on P-58's form for converting declarations (section 8, Q2).

## 3. The team's text on the special names, and their history

- **`c2c769094`, Guy Steele, 2011-06-24**, "Made all the changes necessary for the Fortress character type to be called "Character"": foreign imports "simply assumed that for every primitive Java type there is a single corresponding Fortress type", but "the Java int type must be used to represent the Fortress character type"; "all we need is two trivial transfer functions"; "The answer is, a magic hack. The method NamingCzar.fortressTypeForForeignJavaType now takes three arguments: the Java type descriptor (as before), the method name, and whether an argument or result type is being processed"; "Yes, they're ugly, but I wanted to make sure that no one would stumble across them by accident. They are used in just two places"; "Then all the Fortress code for trait Character uses these two methods to perform the necessary type conversions ... and we hope that optimizations downstream will open-code the transfer methods." The commit is one whose parent link the conversion cut, so it shows the whole tree (`references/records.md`, "The repository's history"); its message is the team's.
- **The comment at the reading**, from the same commit and unchanged since: "The following version is needed to hack the methods "jMakeCharacter" and "jCodePoint". If other methods also need to be hacked, then this mechanism should be generalized." (`ProjectFortress/src/com/sun/fortress/compiler/NamingCzar.java:366-367`). The helpers say "There is deep magic associated with making the compiler believe that the argument type of this method is really the Fortress Character type" (`nativeHelpers/simpleChar.java:52-63`).
- **`NN32` and `NN64`**: the earliest commit that holds `makeNN32FromZZ32WithSpecialCompilerHackForNN32ResultType` is `25f7cf913`, Jean-Baptiste Tristan, 2011-11-23, "Implementation of NN32", a cut commit; `b22c4ac56`, Tristan, 2012-01-03, "Adds data types ZZ and NN64", is a true diff: two more names in `NamingCzar` and every `NN64` operation of the prelude written through them, as `opr +(self, other:NN64): NN64 = jMakeNN64FromZZ64(junsignedLongOverflowingAdd(jMakeZZ64FromNN64(self),jMakeZZ64FromNN64(other)))` (`git log -S` on the names; `git show b22c4ac56`). Nobody generalised the mechanism: the team added names by copying, two per type, and composed.
- **Their use at the team's last commit** `a874948ac`: in `ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss`, `jMakeNN32FromZZ32` 34 calls, `jMakeZZ32FromNN32` 80, `jMakeNN64FromZZ64` 34, `jMakeZZ64FromNN64` 76, `jCodePoint` 65, `jMakeCharacter` 6: 295 calls on 154 lines (`git show a874948ac:ProjectFortress/LibraryBuiltin/CompilerBuiltin.fss | grep -o 'jCodePoint(' | wc -l`, and so on); today the same, as `CompilerBuiltin.fss:768`, `:834`, `:1069`, `:1112`.
- **The one library holds the same six transfers as public declarations**: `ZZ32`'s `unsigned` and `NN32`'s `signed`, `ZZ64`'s `unsigned` and `NN64`'s `signed`, `Char`'s `codePoint` and the function `char` (`FortressLibrary.fss:809`, `:902`, `:985`, `:4540`; `FortressBuiltin.fss:469`, `:616`), whose glue classes are identities on the carrier (`glue/prim/NN32.java:239-243`, `UnsignedLong.java:239-243`, `Long.java:244-248`, `Char.java:165-169`); its api documents the pair: "It is always the case that %c = char(c.codePoint())% for %c : Char%." (`FortressBuiltin.fsi:230-232`). Each of the six fits its special-name helper as a bare string (`movable-base.tsv`); climb batch 23 moved `ZZ32`'s `unsigned`, and climb batch 24's rung S moves four more (`CLIMB-BATCH-24.md`, "S. The small rest").
- **The specification** lists a foreign function interface as future work (`Specification/appendices/future.tex:706-710`); the design-intent map has no row for natives (`map/design-intent-sources.md:95-114`); none of the team's later works that `references/exploring.md` names speaks to natives.

## 4. The ways

### 4.1 Way 1: helpers with the special names

- **What the six names can do as they stand.** The reading matches a whole name and one side: `charCodePointWithSpecialCompilerHackForCharacterArgumentType` makes every `int` parameter a `Character`, `...ResultType` the result (`NamingCzar.java:373-384`, `:494-503`). No helper of a binary operation over `NN32`, which needs both, can carry one of the six names, so under P-58's bare form the six move only the six transfers themselves, none of the 82.
- **So the way needs a rule.** The probe's patch (`hard-set-way1-names.patch`) generalises the match to a suffix: a helper whose name ends in `WithSpecialCompilerHackFor` and `<T>ArgumentType`, `<T>ResultType`, `<T>ArgumentAndResultType` or `<T>ArgumentTypeAnd<U>ResultType`, `T` and `U` each `NN32`, `NN64` or `Character`, reads each parameter of `T`'s carrier as `T` and its result as `U`; the six names are cases of it (`NamingCzar.java`, +36 −18, both worlds' readings). Then one delegating helper per binding's helper, as `unsignedIntOverflowingAddWithSpecialCompilerHackForNN32ArgumentAndResultType(int a, int b)` (+12 in three classes), and the strings.
- **Cost.** For the 82: the rule (about 40 lines of Java); 76 new helpers, one-line delegates, since renaming the 76 breaks the prelude's `import java` until the switch-over; 82 strings. A binding whose `int` positions hold two declared types needs a name that encodes positions, or another way: `javaDigit`, measured, and among the rest `FlatString`'s `get` and `javaIndexOf` fit the rule as it is. Walk: no change. For the rest of the 109: nothing (no carrier for `AnyIntegral`, `Number` or `Any`).
- **Residue at the switch-over (P-37).** The rule stays in the checker as the compiled path's reading of every helper over these types: a helper's Fortress type comes from a substring of its Java name. When the prelude goes, the 76 helpers that only its `import java` named are dead beside their 76 delegates, a second rename to make or a duplicate to keep. `NamingCzarJUTest` asserts the six names' reading (`compiler/NamingCzarJUTest.java:53`); the rule keeps it.
- **Measured** (section 5, runs 1a to 1d): the distance 1, at `javaDigit` alone, 'Could not check call to function builtinPrimitive_simpleChar_charJavaDigitWithSpecialCompilerHackForCharacterArgumentType - (Char, Char)->ZZ32 is not applicable to an argument of type (Char, ZZ32).'; the other three bindings 0; walk's sample OK; walk's suite 695 tests, no failure; the compiled sample in the compiler's world links and runs, PASS.

## 6. The three principles

- **The team's later word** (P-26: "The implementers' later word also outweighs unfinished text"). It says nothing on where the composition is written, by hand or by the compiler. The interpreter's bindings over these types cannot be dated: `git blame` stops at the cut commit `5a68404fd` (2012-07-19).
- **The library as the team wrote it.** The one library binds each of the 82 in one bare body at its declared types, which walk's glue carries in `int` and `long`; it holds the six transfers as public methods. It points to 1, 2a and 2b, which keep the 82 bodies as written, and away from 3, which rewrites them; P-58 takes this form ("it keeps that form").
- **What peer languages do where the team is silent.** Foreign-function declarations that name a primitive by a string and give their types in the declaration take those types as the claim and generate the conversion: OCaml's `external f : int -> int = "c_f"`, Haskell's `foreign import ccall "f" f :: Word32 -> Word32` (Haskell 2010 Report, chapter 8, marshallable foreign types), Rust's `extern "C"`, C#'s `DllImport`; that is way 2, with the conversion generated as in 2b. JVM languages that put unsigned types over signed carriers write the conversions in library source and let the compiler erase them, as Kotlin's `UInt` value class over `Int`; that is way 3. Languages that read a callee's richer types read them from metadata, Kotlin's `@Metadata` and Scala's signatures, or from the callee's own declaration, Swift's import of C's `unsigned int`; none types a callee by a substring of its name. The team is not silent here, so the peers corroborate and do not decide.
- **Where they point.** For the 82 the first two meet only at 2b; the peers' FFI practice is 2b's. For the rest of the 109 the team's prelude declared the shifts over `ZZ32` and `ZZ64` only, the library over `AnyIntegral` with the conversion inside its glue; no principle says where the conversion of an `AnyIntegral` goes once the glue goes, and the peers split (FFI marshalling, or library source).
