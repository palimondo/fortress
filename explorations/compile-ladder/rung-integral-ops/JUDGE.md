## 1. The refusal ground, ruled

The skeptic is right that `0 REM -1`, `0 MOD -1`, `0 GCD -1` and the same three at the type minimum throw `IntegerOverflow` on the compiled path, on `ZZ32` and `ZZ64`. The evidence is captured and I read it rather than the summary: `probes/skeptic/SkepZeroNegOne.compiled` (`0 REM -1 = THROWS`, `0 MOD -1 = THROWS`, `0 GCD -1 = THROWS`) against `SkepZeroNegOne.walk` (`0`, `0`, `-1`); `SkepBoundary.compiled` (`MIN REM -1`, `MIN MOD -1`, `MIN GCD -1` all `THROWS`) against `SkepBoundary.walk` (`0`, `0`, `1`); `SkepZZ64Neg.compiled` (the five `ZZ64` lines all `THROWS`) against `SkepZZ64Neg.walk` (`0`, `0`, `-1`, `0`, `0`); and `SkepRaise.compiled`, whose stack runs `intOverflowingDiv(simpleIntArith.java:80)` → `DIV(CompilerBuiltin.fss:666)` → `REM(:667)` → `MOD(:669)`.

The cause is exactly as the skeptic states. `ProjectFortress/src/com/sun/fortress/nativeHelpers/simpleIntArith.java:80` reads `if (b==(-1) && a==(-a)) throw ... IntegerOverflow`, and `simpleLongArith.java:89` is the same line for `long`; `a==(-a)` is true for `a==0` as well as for the minimum. The rung's `REM` at `CompilerBuiltin.fss:584` and `:667` is `self - other (self DIV other)`, so every `REM`, and through it every `MOD` (`:585-591`, `:668-674`) and `GCD` (`:592-601`, `:675-684`), reaches that guard whenever the divisor is `-1`.

The worker's stated justification for the inherited throw is wrong, and the skeptic's reading of it is right. `REPORT.md:55` says `REM` and `MOD` inherit `DIV`'s two failure modes, "which is the specification's requirement for the first (`basic-integers.tex:459`) and the trait's own overflowing-family convention for the second." `Specification/basic-lib/basic-integers.tex:459` says "For all these operators, if `other` is zero then an `IntegerDivisionByZero` is thrown" and nothing else; it requires the first inheritance and says nothing about the second. An overflowing convention is about a result that does not fit, and `0` fits. The worker measured `MIN DIV -1` (`probes/DivOverflow.fss`) and never a `-1` divisor under its own operators.

## 2. Where the fix belongs, which is the required question

The repair goes into the two `REM` bodies, not into the native, and not because the `.java` slot is taken. `x REM -1` is `0` for every `x` by the specification's own identity `m REM n = m - n(m ÷ n)` (`basic-integers.tex:484`), and `MIN ÷ -1` is `2^31` on `ZZ32`, which no `ZZ32` holds — the gated corpus pins that this division throws, at `ProjectFortress/library_tests/Integer3.fss:127` and `Integer4.fss:127` (`assert(shouldOverflow(fn () => minValue DIV minusOne))`). So a `REM` written over an overflow-checked `DIV` needs the `-1` case whatever the native's guard says: with the native repaired to test against the minimum, `0 REM -1` would compute but `MIN REM -1` would still throw through a `DIV` that is right to throw. The guard is therefore not a workaround for the `a==(-a)` defect; it is the only correct spelling of `REM` over this `DIV`. This is the same reasoning the worker applied to `LCM` at `REPORT.md:109` — `|MIN|` throwing there is right because no representable answer exists — and it cuts the other way here because a representable answer does exist.

One guard, in `REM`, is sufficient: `MOD` evaluates `REM` once and returns `0` when the remainder is `0` (`CompilerBuiltin.fss:586-587`, `:669-670`), and `GCD`'s loop calls `REM` with `b = -1`, gets `0`, and ends with `a = -1`, normalized to `1` at `:600`/`:683`. The skeptic verified all six cases and the `±8/±3` table and `8 REM 0 = THROWS` on the guarded shape (`probes/skeptic/SkepZZ64Neg.fss:24-44`, `SkepZZ64Neg.compiled` lines 6-18). The alternatives, for the record: a guard in `MOD` and `GCD` as well (three sites for one fact); a native `rem` (a `.java` file, and `simpleIntArith.java` has no remainder primitive to bind); repairing `intOverflowingDiv` alone (insufficient for `MIN REM -1`, as above, and `.java`).

What remains in the native is a separate defect with a separate scope. `0 DIV -1` throws (`SkepZeroNegOne.compiled` line 1) where the specification gives `0`, and so do `|0|` and `-0` (`probes/AbsZero.compiled`), because six methods use `a==(-a)` as an overflow test: `simpleIntArith.java:80`, `:85`, `:90` and `simpleLongArith.java:89`, `:94`, `:99`. That is row 329, and the skeptic's correction 2 is right that the row must name all six. One thing the row must add that the skeptic did not say: the fix is a test against `Integer.MIN_VALUE` / `Long.MIN_VALUE` and not the removal of the guard, because `Integer3.fss:96`, `:127` and `Integer4.fss:127` pin `|minValue|`, `-minValue` and `minValue DIV minusOne` as overflowing.

## 3. What the specification settles, and how

For `REM` and `MOD`: `basic-integers.tex:438-442` declare them with `throws IntegerDivisionByZero` and no other exception; `:459` conditions the throw on a zero divisor only; `:465-468` give a value for every sign combination; `:484` defines `REM` by an identity that yields `0` for any `m` at `n = -1`. For `GCD`: `:523-524`, the result is nonnegative and `0 GCD n` is `n`, so `0 GCD -1` under the nonnegativity reading the worker adopted (`REPORT.md:111`) is `1`. For division by zero generally: `Specification/basic/operators/opr-overview.tex:165`, "For integer results, division by zero throws a `DivisionByZero`." Every one of these is a prose-chapter citation and none is an api rendering.

On overflow the specification is thinner than the skeptic's citation makes it. `basic-integers.tex:401` ("operations on type ZZ never need to wrap or saturate") is about unbounded ℤ, the type that chapter describes, and does not by itself govern `ZZ32`; the fixed-size types appear in prose only as "fixed-size representations for integers" (`Specification/basic/types-vals-vars.tex:512-513`) and in `opr-overview.tex:172-176`, whose statement that the wrapping and saturating forms "do not overflow" implies that the ordinary forms can. So the standard for `ZZ32` is: the ℤ semantics, plus an overflow throw when the true result is unrepresentable. `0` is representable; the throw at `(0, -1)` is the guard's defect and not a semantics. The skeptic's conclusion stands without `:401`; the ruling records the narrower ground.
