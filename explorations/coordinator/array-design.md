# How arrays should be built in the compiled world

## 0. The words used below

Boxing: a number wrapped in a heap object so that it can be treated like any other object. On the compile path every `RR64` is an `FRR64`, a Java object with one `double` field (`compiler/runtimeValues/FRR64.java:14-19`); adding two of them allocates a third. "Unboxed" means the bare JVM `double`, which lives in a register or in a `double[]` and costs nothing to make.

Stamping: the compiler writes a generic declaration (`Box[\T\]`) once as a template class; when a program first uses `Box[\RR64\]`, the class loader reads the template and rewrites it with the argument's name filled in (`runtimeSystem/InstantiatingClassloader.java:178`, the general case at `:210-290`; `Instantiater.java:48` substitutes the names). One stamped class per distinct argument list.

`nat` parameter: a static parameter that is a natural number rather than a type, written `Vector[\T, nat s0\]`; it puts a size into the type so that `Matrix[\T,n,m\]` times `Matrix[\T,m,p\]` can be declared with the shared `m`.

Descriptor: the JVM's spelling of a type in bytecode. `D` is a bare double, `[D` an array of doubles, `Lcom/sun/…/FRR64;` a reference to the boxed class. Whether a field is boxed or not is exactly which of these its descriptor is.

View: an object that implements the array protocol (`get`/`put`) over some other array's storage without copying, such as a row of a matrix or a transposed matrix.

Rank: the number of indices an array takes; a vector has rank 1, a matrix rank 2, `Array3` rank 3.

Project units: a rung is one worker session plus one skeptic under the batch script (`coordinator/climb-batch-workflow.js`); batch 1 was four rungs, fifteen agents, 3 h 11 min, with the full gate run once at 830 s (FACTS, ladder section). A rung that touches a `.java` or `.scala` file forces the full gate pair; a library-only rung may drop `ant testSystem` (`next-climb.md` §5). The regression net is the ladder's 85 passing files (`compile-ladder/baseline-2026-09-19/pass-list.txt`).

## 1. What an array is in the interpreter today

An array is a trait, not a primitive. `Array[\E,I\]` (`Library/FortressLibrary.fsi:1322`) is generic in the element type `E` and the index type `I` (`ZZ32` for rank 1, `(ZZ32,ZZ32)` for rank 2) and carries no size in its type. Its protocol is `get(i)` and `put(i, v)`; subscripting is sugar for them (`opr[i:I]:=(v:E) = put(offset(i),v)`, `FortressLibrary.fss:1886-1889`). `ReadableArray` (`.fsi:1247`) is the read half; `Indexed` (`.fsi:1111`) makes every array a generator, so `for x <- a` and `BIG +` work over it.

Sizes enter one layer up. `Array1[\T, nat b0, nat s0\]` (`.fsi:1435`), `Array2` (`.fss:2289`) and `Array3[\T, nat b0, nat s0, nat b1, nat s1, nat b2, nat s2\]` (`.fsi:1652`) put the lower bound and size of each dimension into the type. `Vector[\T extends Number, nat s0\]` (`.fsi:1460`) is an `Array1` that is also an additive group (`+`, `-`, unary `-`, `zero`, plus `scale`, `pmul`, `dot`); `Matrix[\T extends Number, nat s0, nat s1\]` (`.fsi:1578`) is an `Array2` with `mul[\nat s2\]`, `rmul`, `lmul`, `t()`. Both exclude the multiplicative ring because juxtaposition is the inner product (FACTS, the library's arrays and algebra).

Storage is one object per rank-1 array, holding boxed values. `PrimitiveArray[\T, nat s0\]` (`LibraryBuiltin/NativeArray.fss:15-27`) binds `get`, `put` and `init0` to Java glue; the glue allocates an `AtomicArray` of the evaluator's boxed `FValue`s (`interpreter/glue/prim/PrimitiveArray.java:35, 44-56`; `evaluator/transactions/AtomicArray.java:23`). A rank-2 array is a rank-1 array with the index folded as `i s1 + j`, row by row (`__DefaultArray2`, `FortressLibrary.fss:2415-2421`); rank 3 the same. So the interpreter's arrays are already flat, row-major storage under a trait; what they are not is unboxed. One exception exists and nothing uses it: `PrimImmutableRR64Array[\nat s0\]` over a Java `double[]` (`NativeArray.fss:41-51`; `glue/prim/PrimImmutableRR64Array.java:40`), referenced by no library file.

The everyday operations are Fortress loops over `get`/`put`. `fill(f)` is `for i <- zeroIndices() do init0(i, f(toIndex(i))) end` (`.fss:1974-1976`); `map(f)` and `ivmap(f)` (map with the index) make a `replica` of the same shape and `fill` it (`.fss:2135-2138`); `t()` returns a transposed view, not a copy (`.fss:2395` for `Array2`, `:2559` for `Matrix`). The whole protocol runs from `trait Indexed` at `.fss:1636` to the end of `SubArray3` at `:2808`, about 1,170 lines, plus the 54 lines of `NativeArray.fss` and the integer-only scalar extension at `.fss:4477-4517`.

A run-time size becomes a type by reflection. `array[\E\](x: ZZ32)` (`.fss:1922`) calls `reflect(x)`, which returns a value of type `N[\n\]` with the number baked into the nat (`LibraryBuiltin/NatReflect.fsi`), and `__arr1[\E, nat n\](…, x: N[\n\])` (`.fss:1930`) then builds an `Array1[\E,0,n\]`. The interpreter can do this because a nat is a type in its own lattice, made at run time (`interpreter/evaluator/types/IntNat.java`).

A nat is checked at run time, at dispatch, and only then. When a call meets a nat parameter, a literal must be equal and a symbol is bound (`IntNat.unifyStaticArg`, `IntNat.java:127-147`); a mismatch is "Failed to find any matching overload", uncatchable (FACTS, execution model, last bullet). Nothing is optimised on a nat anywhere.

## 2. What the compiled world has

The compiler's own library is small: `CompilerBuiltin.fsi` 778 lines with a 1,627-line body, `CompilerLibrary.fsi` 356 with 718. It has no `Array`, `Array1`, `Vector` or `Matrix` with a body. The one `nat` declaration in it is `trait Matrix[\T, nat s0, nat s1\] extends Object end` (`Library/CompilerLibrary.fsi:279`), empty.

It has exactly one numeric array, and it is the shape the 2012 team chose for this world. `trait ZZ32Vector` (`LibraryBuiltin/CompilerBuiltin.fsi:555-572`) has no static parameters at all: `shape`, `nrows`, `ncols`, `copy`, `opr[i]`, `opr[i,j]`, their `:=` forms, `|self|`, `fill`, `fill2`. Its body (`CompilerBuiltin.fss:1101-1136`) forwards every member to Java helpers imported at `.fss:299-305`. The Java class `FZZ32Vector` holds an unboxed `int[]` and four shape integers (`compiler/runtimeValues/FZZ32Vector.java:18-19`); a 2-D index is folded to `(i-lower_x)*dim_y + (j-lower_y)` (`:65`); the whole class is 83 lines and its helper `nativeHelpers/simpleIntVector.java` 40. `NamingCzar` lists it as a special type whose implementation class is hand-written (`compiler/NamingCzar.java:553`, in the table declared at `:508-514`; also `:337-338` and `:461`). Above it, `CompilerLibrary.fss:484-535` declares `PREFIX_SUM`, `+`, `-`, `MIN`, `MAX` with a scalar, each a Fortress `for` loop over subscripts, and factories at `:587-593`. `StringVector` is the same design over `String[]` (`FStringVector.java:16`). Three live tests: `other_compiler_tests/VectorTest.fss`, `VectorTest2.fss`, `VectorTest3.fss`.

An element read on that unboxed vector still boxes. Verified in bytecode (§8, probe 2): `v[0]` compiles to a virtual call `FZZ32Vector."[]"(FZZ32) → FZZ32`, which calls `getValue`, which calls the generated native wrapper, which unwraps the index with `FZZ32.getValue()`, calls `simpleIntVector.getIndexedValue(FZZ32Vector, int) → int`, and re-wraps the result with `FZZ32.make(int)`; the caller then `checkcast`s. Four calls and one allocation per element. The storage is unboxed; the traffic is not.

The code generator lowers every type to a reference. `RR64` is `FRR64` (`NamingCzar.java:441-446` maps the bare JVM `double` to `RR64` only at the foreign-Java boundary); `x y` on two `RR64` is an interface call on `FRR64`, no `dmul` (`perf-probes/boxing/javap/CompilerBuiltin.juxtaposition_RR64.javap.txt:3559-3565`). The subscript node has no code-generation case of its own: `CodeGen.forSubscriptExpr` throws if reached (`codegen/CodeGen.java:4931`), so every `a[i]` is desugared into a method call on the array's trait before code generation.

Stamping renames; it cannot change a representation. Verified (§8, probe 1): the template for `object Box[\T\](x: T)` has the field `x` with descriptor `LT;`; the stamped `Box⟦FRR64⟧` has `Lcom/sun/fortress/compiler/runtimeValues/FRR64;`. The substitution replaces one class name with another inside a reference descriptor. `[D` is not a class name, so no instantiation of a generic template can produce a `double[]` field, and the stamped interface's `get` returns the boxed class. The place the team left for anything cleverer is `if (false) { // Here will go all the magic expando-stuff. }` at `InstantiatingClassloader.java:168-172`.

The checker does not implement `nat` parameters. `STypesUtil.makeInferenceArg` answers `NI.nyi()` for every non-type kind (`scala_src/useful/STypesUtil.scala:546-559`; FACTS, the interpreter's library fed to the compiler). Verified (§8, probe 3): a nat used in a type position (`object Buf[\nat n\](…) extends Sized[\n\]`) crashes with `ClassCastException: VarType cannot be cast to IntExpr`; a nat passed explicitly to a function that uses it in no type (`f[\3\](1)`) compiles and runs. So sized array types cannot be declared on this path until the second reserved fork lands, and unsized ones can be declared today.

The generic generator protocol exists here: `Generator[\E1\]` (`CompilerBuiltin.fsi:614`) and `Reduction[\R\]` (`:638`). What is missing for arrays is `Indexed` and everything below it.

## 3. What microGPT needs from arrays

The vocabulary is `explorations/run-c4/src/FlatArrays.fsi`, inventoried in `reviews/c4-flatarrays-review.md` §1 at the committed version `a92569f83`: 38 declarations, of which 5 are aliases of library calls, 26 are new operations over the library's own array types, and 9 are new structures. (The working copy is under uncommitted repair after that review; Pavol's position of 2026-09-19 is that the model's operators stay operators and the vocabulary is repaired around the notation, `POSITIONS.md:38`, so the 26 stay operators and the compile path's overloading check must let them stand beside the prelude's `+`, `MAX` and juxtaposition, which is unmeasured.)

The 26 operations, by what they do to the data. Elementwise maps, 14: `+` and `-` with a scalar in both orders (4), the elementwise product `×`, `/` array by array and array by scalar (2), `MAX` with a scalar (2), `>` giving 0/1, `SQRT`, `exp`, `log`, and the broadcast add of a matrix to every plane of a rank-3 array (review rows 5-17 and 30). Contractions, meaning sums of products such as a matrix product, 2: the row scaling `diag(v) m` (row 20) and the plane-wise batched product of two rank-3 arrays (row 29); the 16×16 matrix product itself and `DOT` are the shipped library's own (`FortressLibrary.fss:2621-2629`) and are what the kernels time. Structural, 10: the row lift `rows(f, m)` in four shapes (31-34), `gather`, `onehot`, `pick`, `flat` (35-38) and the two transposes `^T` (39-40). The 9 structures are views: `Diag`, the transposed rank-3 array, the matrix over a slice of the flat parameter vector (`PView`), the row and plane-row views, and `heads`/`unheads`/`plane`, each a six-line object whose `get`/`put` index another array (review §1, last paragraph).

Element types needed: `RR64` for every weight and activation, `ZZ32` for keys and the integer corpus, `Char`/`String` for the corpus text in `FlatData`. Sizes: the hyperparameters are literals bound to names (`MicroGptFlat.fss:17`: 16, 16, 4, 4, 27, 26); the flat parameter vector's 4192 is computed; every constructor takes a run-time size and returns the unsized `Array[\RR64,ZZ32\]` or `Array[\RR64,(ZZ32,ZZ32)\]` (`FlatArrays.fss:14-17` at `a92569f83`); nat-typed values enter only through views built with `reflect` (`PView[\nat s, nat r, nat c\]`, `viewN(…, reflect(nr), reflect(nc))`, `:54-62`) and through the model's `Matrix`/`Array3` declarations.

The measured cost of boxing on these shapes (`perf-probes/kernels/REPORT.md` §2; Java models of the runtime's own box, `Box[]` storage, against `double[]`): the 4192-element dot product 6.26× slower boxed, the 16×16 matrix product 6.53×, the row lift with `rmsn` 2.59×. The generic array object on top (an `Object[]` behind an interface with a `checkcast` per read) adds 9 %, 1.6 % and 4.8 %. The cost is the element boxes, not the container's genericity. None of the three kernels compiles today: 77 errors, `Array`, `Vector`, `Array3` undefined, all raised inside `FlatArrays.fsi`. All eighteen components of the two microGPT programs stop at disambiguation on `Array` (8), `Char` (5), `ImmutableArray` (3), `Vector` (2) (`compile-ladder/baseline-2026-09-19/microgpt-phase.md`); on the ladder, 42 files stop first on an array name (`ImmutableArray` 26, `Array1` 6, `Array` 6, `Array2` 2, the factory `array` 2; counted from `baseline-2026-09-19/ladder.tsv`).

## 4. The options

### (a) Port the interpreter's array library as it is, boxed

What is built: the trait layer of §1 moved into `CompilerLibrary` (`Indexed`, `ReadableArray`, `Array`, `Array1/2/3`, `Vector`, `Matrix`, `StandardMutableArrayType`, the factories, about 1,200 lines edited for this world: `builtinPrimitive` bindings become `import java`, and the algebra it extends must exist above `Number`), plus one boxed native class, an `Object[]` on the `FStringVector` pattern, with its helper and one `NamingCzar` line.

What compiles first: `array[\RR64\](n)`, `get`/`put`, `fill`. What it does to generics: one stamped class per element type, the elements boxed in all of them. What it does to `nat` sizes: the sized layer (`Array1`, `Vector`, `Matrix`, `Array3`) cannot be declared until the checker's nat fork lands (§2), and the `reflect` trick has no counterpart here: the checker cannot type a static argument that exists only at run time, so `array[\E\](n)` must return the unsized `Array[\E,ZZ32\]` from a native directly, and sized types are made only from literals and symbols. The code generator learns nothing.

Cost: one `.java` rung (the native class, full gate) for the unsized layer; the sized layer waits on the nat fork and is then two or three library-only rungs. Fastest route to "the kernels compile". What it forecloses: the 6.3-6.5× is kept, and unboxing afterwards means a second storage class and a second set of natives under the same traits, which the map called "the same library written twice" (`map/README.md:127`).

### (b) `double[]`-backed arrays with unboxed elements designed in

What is built: `FRR64Vector.java` beside `FZZ32Vector.java`, the same 83 lines with `double[] val` and the four shape integers; `simpleDoubleVector.java` beside `simpleIntVector.java`; `trait RR64Vector` in `CompilerBuiltin.fsi` with the nine members of `ZZ32Vector`; one line in `NamingCzar`'s special table and one in its foreign-route chain; a factory. That is the team's own five wiring sites. `ZZ32Vector` already covers the integer keys; `StringVector` the corpus.

Its own type, not a stamped instance: §2 verified that stamping substitutes class names into reference descriptors, so `Array[\RR64,…\]` as an instantiation of a generic template cannot hold a `double[]`; the `RR64` array is a hand-written class, as `FZZ32Vector` is, and anything reached through a generic trait's `get` is boxed at that boundary.

What the code generator must learn, if the loops are to run unboxed in generated code: an element read must become `getfield val:[D`, `iload i`, `daload` instead of the four-call chain of §2, and a bare `double` must have somewhere to go, which means a local variable slot of descriptor `D` and `dadd`/`dmul` for `RR64` arithmetic whenever the checker's static type is `RR64`, boxing only where a value meets a `T` or an `Any`. That is unboxing by static type (`performance-roadmap.md` A1) in `CodeGen.java` (6,750 lines) and `VarCodeGen`; every rung of it is a `.java` rung under the full gate with the 85 files as the net. Without it, an unboxed store with boxed traffic is what `ZZ32Vector` is today; whether that alone is faster than boxed storage is not measured, and the Java model that would answer it is one more class in `perf-probes/kernels/java/`.

A second route to unboxed loops needs no code-generator change: write the loops of the vocabulary's operations as Java natives over `double[]` (the dot product, the matrix product, the elementwise maps, `SQRT`/`exp`/`log` over an array), so a box is paid once per whole-array operation instead of once per element. This is the shape of an APL implementation, each primitive a native loop, and microGPT in the C4 form is whole-array vocabulary; the residue is the user lambdas passed to `fill`, `map` and `rows`, which box per element. Not the team's precedent: their `ZZ32Vector` operators are Fortress loops over boxed subscripts (`CompilerLibrary.fss:484-535`).

How sizes are carried: run-time fields (`dim_x`, `dim_y`), as `FZZ32Vector` does; no nat in the type, so no nat fork is needed and shape agreement is checked inside the operation or not at all. What it forecloses: nothing named, but it provides nothing for element types beyond `RR64`, `ZZ32`, `String`; an array of autodiff nodes or of characters still needs a boxed generic array. What it moves: no ladder file (they stop on `Array`, `ImmutableArray`, `Array1`) and no microGPT component (they name `Array`, `Vector`, `Matrix`, `Array3`), unless the type takes one of those names, which then collides with the sized declarations the model writes.

Cost: one `.java` rung for the type with the kernel measurement inside it (kdot and kmat over `RR64Vector` against `KDotPrim` and `KMatPrim`), then one rung per handful of native operations; the code-generator route is a separate ladder of `.java` rungs whose size no one has measured.

### (c) A generic reference-typed `Array[\T,I\]` for everything, plus a specialised `RR64` array

What is built: the unsized trait `Array[\E,I\]` with the interpreter's protocol (`get`, `put`, `fill`, `map`, `ivmap`, `t()`, `Indexed`), a boxed default object over `Object[]` for any `E`, and `object RR64Array1(…) extends Array[\RR64,ZZ32\]` (and a rank-2 twin) backed by the `double[]` class of (b). The checker sees one generic type; the model's `Array[\RR64,ZZ32\]` and `Array[\RR64,(ZZ32,ZZ32)\]` resolve as written.

What selects the specialised class. Not the checker: it has no notion of representation. Either the factory does, from the run-time type tag: on this path a generic instantiation carries its arguments as run-time type descriptors (probe 1's `Box$RTTIc` holds a field `T` of type `RTTI`), so a native `array[\E\](n)` can return `FRR64Array` when `E`'s tag is `FRR64` and the boxed object otherwise, which is `performance-roadmap.md` A2's "class tag"; or the vocabulary skips the generic factory and declares `vec`/`mat` over `RR64` directly, which is what `FlatArrays.fss:14-17` already does.

Can Fortress's overloading express the specialisation? Not as two top-level declarations of one operator: `opr +[\I\](a: Array[\RR64,I\], s: RR64)` beside `opr +(a: RR64Array1, s: RR64)` is one declaration with a static parameter and one without, forbidden by `Specification/basic/overloading.tex:100-105` and refused by the interpreter's check (the review's probe A). It is expressible as one declaration over the trait whose work is done by the object's own methods (`get`, `put`, `dot`, the product), which is the interpreter's own idiom for views (`TransposedMatrix`, `FortressLibrary.fss:2571-2588`) and ordinary virtual dispatch. Through the trait every `get` still boxes at the boundary; unboxed loops exist only inside the specialised object's native methods (the second route of (b)) or after the code generator learns to unbox (the first route of (b)).

How sizes are carried: none in the unsized layer; `Vector[\T, nat s\]` and `Matrix[\T, nat r, nat c\]` come as traits over `Array` when the nat fork lands, with the nat a fact for the checker and the size a run-time field underneath, which is the specification's "instantiated at runtime" (§5) and the `ZZ32Vector` precedent at once. What it needs from the nat fork: a nat in a type position must not crash; symbols and literals unified by equality; a nat inferred from an argument's declared type (`transpose[\nat r, nat c\](m: Matrix[\RR64,r,c\])`). What it does not need: nat arithmetic, `where` constraints, static expressions, and nothing about `reflect`.

Cost: one `.java` rung (native class, factory, trait, full gate), one library rung (`fill`, `map`, `ivmap`, `t()` in Fortress over `get`/`put`, `testFast` alone), then the native operations as in (b). What it forecloses: nothing named; `ImmutableArray` (26 ladder files, through `List.fsi`) needs the immutable variant in every option. What it moves: the ladder's 6 `Array` and 2 `array` files past disambiguation; all 8 microGPT components stopped on `Array` reach the checker and then stop on `Vector`, `Matrix`, `Array3` and the nats until the nat fork lands.

## 5. What the specification and the team's own drafts say

The specification's array is a family of sized types over a generic one, and it keeps both factories. The type of a k-dimensional array expression is `Array k[T, 0, n0, …, 0, n_{k-1}]`, abbreviated `T[n0, …]`, with a footnote that "As of March 2008, the Fortress library provides Array k types for 1 ≤ k ≤ 3" (`Specification/basic/expressions/aggregate.tex:130-136`); a two-dimensional array of numbers "is a matrix", a one-dimensional one "is a vector", with the editors' margin notes reading "can be coerced to a matrix" (`:152-170`). The factory table gives `array[E](size)` for "the specified runtime-determined size" and `array1[E,n]()` for "statically determined size n" side by side (`advanced/parallelism-locality/arrays-distributed.tex:42-48`).

On storage: "As in Fortran, Fortress arrays are complex data structures; simple linear storage is encapsulated by the HeapSequence type, which is used in the implementation of arrays" (`arrays-distributed.tex:18-22`), with the note that distributions and `HeapSequence` "are not yet supported" (`:15-16`). Nothing in the prose says boxed or unboxed; the intent is an array as a structure over a linear store, which both (b) and (c) are.

On sizes in types: "types can be parametric with respect to other types and values (most notably natural numbers)" (`preliminaries/intro/nutshell.tex:85-86`); a nat parameter's semantics is "These parameters are instantiated at runtime with numeric values" (`basic/trait-parameters.tex:82`), and the chapter opens with "Non-type static parameters and static expressions are not yet supported" (`:15-17`). The internal meeting record's one implementation stance is "don't instantiate" (`reviews/nat-checking-plan.md`, §a).

On the intended aggregate: "Guy's proposal for making tensors the principal user-level indexed aggregate type in Fortress (06/27/07)" and his email "Arrays, matrices, and tensors (short)" of 12/15/06 (`appendices/future.tex:63-65`); the FAQ's answer to variable-sized arrays with static bounds checking is a link to a wiki page that no longer exists (`appendices/FAQ.tex:55-57`); the emails themselves are not in the repository (`map/design-intent-sources.md:111, 128`).

On the compiled encoding: the JVM paper says "mentions of static parameters are replaced with their upper bounds in domain and range" (`Papers/Implementation/MethodMapping.tex:134`), which is why stamping is a renaming, and that the template's side file "contains info about the static parameters, including their names, whether they are types, oprs, or nats" (`:142`), so nats were meant to travel through the template machinery by name. The team's own unboxing note is `compiler/optimization/Unbox.java:18-30`: four cases, "primitive. ZZ{8,16,32,64}, RR{32,64}, Boolean", singleton objects, unboxed fields, "comprises unboxed"; a taxonomy referenced by nothing.

The drafts say nothing about arrays. `Library/incomplete/` (24 files) contains no mention of an array. `Library/GeneratorLibrary.fss` and `.fsi` (783 lines, imported by nothing) are the generator and reduction protocol, `Container`, `DefaultGeneratorImplementation`, without `Indexed` or any array. `Fortress.Operators.fsi.INCOMPLETE` is the algebra above `Number` and names no aggregate. What the team shipped in this world is `ZZ32Vector`, and it is the only precedent with code behind it.

## 6. The decision tree

Question 1. Is the storage of an `RR64` array a bare `double[]` (unboxed) or an array of boxed objects?
Branch "boxed": option (a); the kernels compile soonest; the 6.3-6.5× stays; making it fast later means a second storage class and second natives under the same traits.
Branch "unboxed": options (b) and (c); the `RR64` array is a hand-written class on the `ZZ32Vector` pattern, never a stamped generic; boxed traffic at the trait boundary until either natives or the code generator remove it.
Default: unboxed. This is the order on record ("unboxing designed into the first", `POSITIONS.md:14`) and the probe shows a stamped generic cannot get there later by itself.

Question 2. Is the unboxed class hidden behind the generic `Array[\T,I\]` that the model names, or is it its own type?
Branch "own type", option (b): no `Array`/`Vector`/`Matrix` names in the compiler world; nothing in microGPT or on the ladder moves; the model is respelled to the new names, against the position that the model's text is the notation.
Branch "behind the generic", option (c): the model's `Array[\RR64,ZZ32\]` resolves as written; the boxed default object serves every other element type and the ladder's files; the specialised object is chosen by the factory.
Default: behind the generic, with the vocabulary's own `vec`/`mat` constructors making the `RR64` object directly; the type-tag factory is a later convenience.

Question 3. Where do the loops run unboxed?
Branch "inside native whole-array operations": Java helpers over `double[]` for the contractions and elementwise maps; a box per operation; no code-generator change; user lambdas still box per element.
Branch "in generated code": the code generator learns `D` locals, `daload`/`dastore`, `dadd`/`dmul` for statically `RR64` code; every rung `.java` under the full gate; unlocks unboxed loops written in Fortress.
Default: natives first, with the kernel measurement in the first rung; generated-code unboxing as PLAN's step 4, once the measured residue says what it is worth.

Question 4. Where do sizes live?
Branch "in the type now": every sized declaration waits on the nat fork; run-time sizes need a compile-world `reflect` that does not exist.
Branch "run-time fields only": the `ZZ32Vector` shape; the spec's sizes-in-types intent is dropped, and the model's 20 nat-carrying declarations are respelled.
Branch "layered": the storage carries sizes as fields; `Vector[\T, nat s\]` and `Matrix` are declared over `Array` when the nat fork lands and check shapes without changing storage.
Default: layered. It is the specification's own two factories (§5), the interpreter's own layering (§1), and it means this fork needs nothing from the nat fork to start and the nat fork changes no storage class when it lands.
