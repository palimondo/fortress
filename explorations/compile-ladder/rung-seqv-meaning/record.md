## Revival change

**The change.** The team's walk answered `SEQV` across number types (`FInt.seqv` took an `FLong`, `FFloat` or `FFloatLiteral` and compared values: `interpreter/evaluator/values/FInt.java:53-61` at `ed8652dc0`), compared two flat strings by their text (`FString.java:35-38`), and called two value objects equivalent when their body declared no field (`FTypeObject.java:55-64`); the team's compiled helper compared every value by reference (`nativeHelpers/equality.java:14-19`, "Eventually need to deal with tuples, value types, etc."); the Working Draft named arbitrary-precision numbers among the reference objects and named no kind for strings (`Specification-1.0-frozen/basic/objects.tex:39-54`). The tree now answers by the specification's rule on both paths: different types never equivalent, a value object field by field, floats by bit pattern, reference objects and strings only by identity; `Ratio`, `IntLiteral` and `FloatLiteral` are value objects; the list names rationals and every integer among the value objects and strings among the reference objects. Shown by `tests/StrictEquivalenceRuleWalk.fss`, `tests/ValueObjectCC64Walk.fss` and `compiler_tests/StrictEquivalenceRuleCompiled.fss`. Reason: "If the arguments have different dynamic types ... the result is always false. If both arguments are value objects with the same type, then the result is true if and only if corresponding fields of the objects are themselves equivalent ...; two binary words are strictly equivalent if and only if they contain the same bit pattern" (`Specification/basic/objects.tex:433-454`); and the library declares `value object BigNum` and every string object without `value`. Consequences a program meets: two strings of one text built apart are not `SEQV`, so a value without its own `=` that holds a string (a tuple of four or more, a value object) is not `=` to an equal one built apart; a float numeral bound to `RR64` under walk is not `SEQV` a computed `RR64`.
