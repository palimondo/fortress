A call of a function, a method or an operator whose declaration has static parameters, or of the constructor of an object that has static parameters, need not write its static arguments, and most calls do not (Section 13.2, Section 13.4). The static arguments of a call that does not write them are inferred statically. This chapter describes that inference for type parameters (Section 12.1) and for nat and int parameters (Section 12.2); the inference of the static arguments of other kinds of static parameter, and the inference over a whole program of the types that declarations elide (Section 22.6), are not yet described.

The Working Draft had no counterpart to the rule for a numeral whose conversions tie (Section 20.2). A type parameter declared without an extends clause is bounded by Any (Section 12.1), on the compiled path as in the interpreter. The team’s later Types chapter gives the coercion relation and the valid instantiations of a quantified type, and says nothing of inference.

20.1 The Static Arguments of a Call

The static arguments of a call that does not write them are found in two steps: the declaration that the call invokes is chosen first, and it is instantiated second.

Choice. The declaration is chosen as Section 17.5 describes. A declaration with static parameters is applicable to a call, without or with coercion, if some instance of it whose static arguments satisfy their bounds is applicable to the call. Declarations are compared on the parameter types they declare, a declaration with static parameters on its parameter types taken over every instance that its bounds allow, and not on an instance inferred for the call. So a coercion is applied only to make a call possible: it never changes which declaration is chosen when one is applicable to the call without it.

Instantiation. The static arguments of the chosen declaration are then inferred, and with them the instance of the declaration that the call invokes:

  • A type parameter, or a nat or int parameter, that the declared type of a parameter mentions other than as the whole type, as b: List⟦T⟧ mentions T, is fixed by the argument at that position, whose type must be a subtype of the parameter type of the instance.

  • Where the call has an expected type (below), a type parameter that the declared return type mentions other than as the whole type is fixed by the expected type as well.

  • A type parameter that is the whole declared type of one or more parameters, as T is of x: T, and that is not fixed as above, takes, among the types of the arguments at those positions and the types to which they can be coerced, the narrowest under ⊴ (Section 17.5) that every one of those arguments is substitutable for (Section 17.4) and that the bounds of the type parameter permit. For number arguments this is the narrowest type into which every one of them converts: ℤ64 for a ℤ32 and a ℤ64, and also for a ℤ32 and an ℕ32, though neither of them is a ℤ64 (Section 33.2). Where there is no such narrowest type, and the rule for numerals (Section 20.2) does not settle the tie, the type parameter takes the intersection of its upper bounds: its declared bound, Any if it has none (Section 12.1), and what the expected type (below), where the call has one, requires of the declared return type, provided the types of those arguments are subtypes of it; none of those arguments is converted.

    Revised by the 2026 revival see Section I.1.26

    The revival’s text of 28 September 2026 gave such a type parameter the union of the types of those arguments; on 29 September 2026 the revival took the rule by which the dispatcher of the type group’s paper of 2019 instantiates a type parameter, which gives the bound.

  • A type parameter that neither an argument nor the expected type fixes as above, such as a type parameter that only the return type mentions, as its whole type, likewise takes the intersection of its upper bounds: its declared bound, Any if it has none (Section 12.1), and what the expected type (below), where the call has one, requires of the declared return type. Inference never instantiates a static parameter at BottomType, which programmers must not write (Section 6.8). So, for the declaration stop⟦T⟧(s: String): T, the variable declaration x: ℤ32 = stop(“no”) instantiates stop at ℤ32, and the same call with no expected type instantiates it at Any.

    Revised by the 2026 revival see Section I.1.26

    The revival’s text of 28 September 2026 did not describe such a type parameter and left open whether inference may give it BottomType, which the team’s draft note at the end of this chapter asks. The revival decided on 29 September 2026 that the rule by which the dispatcher of the type group’s paper of 2019 instantiates a type parameter that the arguments do not fix, the intersection of its upper bounds, which never instantiates a type parameter at BottomType, is the rule of static inference as well.

  • Every argument is then admitted against the corresponding parameter type of the instance by substitutability: an argument whose type is a subtype of it is passed as it is, and any other argument is coerced to it (Section 17.1), as an argument is coerced to the declared type of a parameter of a declaration without static parameters.

The coercions that the instance needs are inserted into the call statically, as is any coercion that Section 17.5 chooses.

The expected type. A call has an expected type in these contexts: as the right-hand side of a variable or field declaration that declares its type, that type; as the right-hand side of an assignment to a variable whose type is declared, that type; as the body of a functional that declares its return type, that type; as the last expression of a block that has an expected type, whether or not local declarations precede it in the block, the block’s expected type; as a branch of an if expression with an else clause that has an expected type, the expected type of the if expression; as a clause of an if expression without an else clause, (), the type that every such clause must have (Section 13.19); as a clause of a typecase expression that has an expected type, its else clause among them, the expected type of the typecase expression, of which the union of the types of its clauses, the type of the typecase expression (Section 13.22), is then a subtype where the type of each clause is; as the body of a label expression that has an expected type, or as the with clause expression of an exit expression whose target is that label expression, the expected type of the label expression, of which the union of the type of its body and the types of those with clause values, the type of the label expression (Section 13.12), is then a subtype where each of those types is; and as an argument of a call that this section does not accept with its arguments typed without an expected type, where the argument is itself a call with inferred static arguments, the parameter type at the argument’s position of each declaration of the enclosing call in turn, instantiated, where that declaration has static parameters, by the arguments that are not so typed and by the expected type of the enclosing call alone, as described below. The expected type is used whether the call is written by tight juxtaposition, as f(x) (Section 16.8), or by loose juxtaposition, as f x, or as a method invocation or an operator application.

Revised by the 2026 revival see Section I.1.27

The revival’s text of 29 September 2026 gave the last expression of a block an expected type only where no local declaration precedes it, and gave none to a clause of an if expression without an else clause, to a clause of a typecase expression or to a call written by loose juxtaposition; the revival decided on 8 October 2026 that each has the type that the text already requires of it. Its text of 8 October 2026 gave none to the body of a label expression or to the with clause expression of an exit expression; the revival decided on 9 October 2026 that they have the expected type of the label expression, as a clause of a typecase expression has that of the typecase expression. Its text of 9 October 2026 gave none to an argument of another call; the revival decided on 9 October 2026 that an argument that is itself a call with inferred static arguments has the parameter type of each declaration of the enclosing call in turn where the enclosing call is not accepted without it, since the static arguments of a call “are statically inferred from the context of the function call” (Section 13.2).

The return type of the instance that the steps above find must be a subtype of the expected type. If they find no such instance, the static arguments are inferred again without the expected type, and the call is accepted only if the return type of the instance then found is a subtype of the expected type or can be coerced to it; in the second case the result of the call is coerced to the expected type (Section 17.1). So, for the declarations wrap⟦T⟧(x: T): List⟦T⟧ and id⟦T⟧(x: T): T, the variable declaration a: List⟦ℤ64⟧ = wrap(3) instantiates wrap at ℤ64, which the expected type fixes, and coerces the numeral, while b: ℤ64 = id(3) instantiates id at ℤ32, the numeral’s default (Section 20.2), and coerces the result.

Before 8 November 2026 the sentence above said that this call instantiates id at the numeral’s own type; a type parameter that only numerals fix now takes their default.

The arguments of a call are typed first without an expected type. Where this section then accepts no instance of the call, each argument that is itself a call with inferred static arguments is typed again, once for each declaration of the enclosing call, with the parameter type at its position as its expected type, as the list of contexts above says. Of the declarations that are applicable to the enclosing call with its arguments so typed, each declaration with its own, and whose instances have return types that are subtypes of the expected type of the enclosing call, where it has one, or can be coerced to it, the enclosing call invokes the one that is more specific than every other on the parameter types they declare; where there is no such declaration, the call is typed with its arguments typed without an expected type, and is accepted or refused as above. So where this section accepts an instance of a call with its arguments typed without an expected type, no argument is typed again, and the declaration it invokes is never passed over for one that only an argument typed again makes applicable; a declaration that is applicable to those arguments but whose return type neither is a subtype of the expected type nor can be coerced to it is not accepted, and another may then be chosen. For example, for the declarations mk⟦T⟧(): Box⟦T⟧, takes(b: Box⟦ℤ64⟧), over(b: Box⟦ℤ64⟧) and over(x: Any), the call takes(mk()) instantiates mk at ℤ64, which the parameter type of takes fixes, while the call over(mk()) invokes the second declaration of over, which is applicable to mk() typed without an expected type, the instance of mk at the bound of its type parameter.

The revival’s text of 9 October 2026 had no such paragraph; the revival added it with the argument of a call to the list of contexts above, following its decision of 9 October 2026.

Dispatch. The call, with the coercions of its instance inserted, dispatches at run time as Section 15.5 describes, by subtyping and without further coercion, to the most specific declaration applicable to the converted values.

For example, of the declarations op⟦T extends Number⟧(a: T, b: T) and op(a: Any, b: Any), the call op(z, w), where z has type ℤ32 and w has type ℤ64, chooses the first, which is applicable without coercion, since its instance at Number is, and is more specific than the second; the first is instantiated at ℤ64, z is coerced, and the converted call runs that instance.

Revised by the 2026 revival see Section I.1.26

The interpreter has no static types and applies the same rule at dispatch, from the run-time types of the arguments: it infers the static arguments of a declaration with static parameters with coercion, and instantiates the declaration that its dispatch chooses by the rule for a type parameter that is a parameter’s whole type. So where the declared type of a variable is wider than the type of its value, or an argument’s static type is Any, it may run a declaration at a narrower instance than the compiled path, which instantiates it at the static types. Where neither an argument’s type nor a type into which the arguments convert is the narrowest, it gives a type parameter that is the whole type of parameters its declared bound, Any if it has none, as this chapter does: for a ℤ64 and an ℝ64, Number where that is the bound and Any where the type parameter is declared without an extends clause. It does the same where the arguments that fix a type parameter inside other types, as the results of two function arguments do, have several minimal common supertypes. Neither holds of a type parameter whose bound mentions a static parameter, itself or another, or that is declared with several bounds that the interpreter cannot meet, as it cannot meet two bounds neither of which is a subtype of the other: such a type parameter it binds, as before, to the narrowest named common supertype of the arguments’ run-time types that the bounds permit, where there is one, and where there is none a call that fixes a type parameter of the second kind fails (row 591 of the revival’s gap ledger). When its dispatch chooses among declarations, it passes over a declaration with static parameters whose arguments have several minimal common supertypes in favour of any other declaration applicable to the call without coercion (row 589 of the revival’s gap ledger). It fixes a type parameter by the expected type only at a reduction or a comprehension that writes no static argument and whose value is that of a local variable declared with a type or of a top-level or local function declared with a return type, as the box after the list in Section 20.2 says; elsewhere it does not yet fix a type parameter by the expected type. A type parameter that an argument bounds only from above, as a function argument bounds the type parameter of its parameter type, it instantiates at the intersection of the upper bounds that its declared bound and the arguments place on it: at ℤ32 for a function of a ℤ32 where the type parameter is declared without an extends clause, and at Number for a function of an Any where it is bounded by Number; such a type parameter whose bound mentions a static parameter, or that is declared with several bounds that it cannot meet, it still instantiates at BottomType; and where the arguments place on such a type parameter two upper bounds that it cannot meet, as a function over one trait and a function over another do when neither trait extends the other, the call fails with an error of unification (row 616 of the revival’s gap ledger). It infers the static arguments of a generic dotted method that a call does not write as it infers a generic function’s, whether the method is alone under its name or among the overloads of its receiver. It compares declarations with static parameters on the parameter types they declare, but for two kinds: a functional method of a generic trait or object it compares on the instance that a call makes, and a generic dotted method on the parameter types it declares only where exactly one of the two declarations’ declared parameter types lies inside the other’s, and otherwise on that instance. It stops at load on an object or trait that declares a generic dotted method beside a plain one of the same name (row 760 of the revival’s gap ledger), and it stops on an object that extends a generic trait whose dotted method has a static parameter of its own bounded by the trait’s, at load or at a generic object’s first instance (row 762). It reads the bounds of a generic method that a trait declares, and the types into which the arguments convert, where the trait declares the method, as it reads those of a method that an object declares. It dispatches a converted call again, except a call of an overloaded method.

20.2 A Numeral Whose Conversions Tie

A numeral has a numeral type of its own, whose static arguments are the numeral’s four numbers, and from which the Fortress standard libraries define coercions to the number types, generic over those numbers; where nothing at its place fixes a type it is converted into its default (Section 13.1): a ℤ32, or a ℤ64 or a ℤ when its value does not fit in the narrower type, and an ℝ64 for a numeral with a radix point. Nothing fixes a type at a variable declared without a type; at a parameter of type Any, Object or Number, or of a type parameter declared without a bound; at the receiver of a dotted method call whose method the default type declares; and at a static argument that only numerals fix. A type parameter that several numerals fix, and no other argument and no expected type, is instantiated at the narrowest default that holds every one of their values, an ℝ64 where any of them has a radix point, each numeral being converted into it exactly: so for pick⟦T⟧(a: T, b: T): T, the call pick(3, 3000000000) is instantiated at ℤ64, and the list ⟨3000000000, 0.5⟩ is a List⟦ℝ64⟧. The branches of an if or case expression whose value is bound to a variable declared without a type are read in the same way: numerals there take the narrowest default that holds them all. Where the types to which a numeral can be converted are incomparable under ⊴, as ℤ32 and ℕ32 are, each taking a numeral and neither converting into the other, the numeral is read as its default: a numeral without a radix point as a ℤ32, or as a ℤ64 or a ℤ when its value does not fit in the narrower type, and a numeral with a radix point, whose conversions into ℚ, ℝ32 and ℝ64 tie, as an ℝ64. This holds in either step: in the choice among declarations that are applicable to the call only with coercion and that the numeral would otherwise leave tied, and in the instantiation of a type parameter that only numerals fix. So of the declarations g(x: ℕ32) and g(x: ℤ32), the call g(0) invokes the second; a type parameter that only numerals fix, whose bounds ℤ32 and ℕ32 satisfy and the numeral’s own type does not, is instantiated at ℤ32 when ℤ32 holds the numerals’ values; and round(2.50000000000000001), whose numeral the declarations of round on ℚ, ℝ32 and ℝ64 would leave tied, rounds the ℝ64 nearest to that numeral, and is 2.

Revised by the 2026 revival see Section I.1.50

The revival’s text of 28 September 2026 read a numeral at its default only where its conversions tie, and only a numeral without a radix point. The revival decided on 8 November 2026 that a numeral takes its default at every place that fixes no type, that a type parameter that several numerals fix takes the narrowest default that holds them all, and that a numeral with a radix point whose conversions tie is read as an ℝ64; and on 9 November 2026 that a numeral’s own type has its four numbers as static arguments, and that the coercions of the Fortress standard libraries from it are generic over them (Section 13.1).

The rule settles only a tie that a numeral makes. Where an argument that is not a numeral leaves the declarations applicable to a call only with coercion tied, no declaration is the most specific, and the call is a static error.

This chapter does not yet describe:

  • the static arguments of a bool, dim, unit or operator parameter (Section 12.3, Section 12.4, Section 12.5);

  • a nat or int parameter that neither an argument nor the expected type fixes;

  • the element type of a reduction that only its generator clauses determine (Section 13.17): the rule above gives a static parameter of the big operator that nothing at the call fixes its bounds, not the type of the elements;

  • whether an argument whose declared parameter type mentions a static parameter inside another type may be converted where only a conversion of its elements would satisfy the bounds of the parameter; under the rule above such an argument fixes the parameter by subtyping and is not converted;

  • an expected type in any context other than those listed above, such as the body of a for loop;

  • the static arguments of an object with static parameters that is named without a call, which a program writes (Section 12.6);

  • the inference over a whole program of the types that declarations elide (Section 22.6).

Revised by the 2026 revival see Section I.1.26

The compiled type checker instantiates a type parameter that neither an argument nor the expected type fixes at the intersection of its upper bounds, as Section 20.1 says; on the compiled path, as in the interpreter, a type parameter declared without an extends clause is bounded by Any, so that a call that fixes such a parameter by the expected type alone may fix it at a type that Object excludes, such as (). A reduction’s big operator is an argument of the call that the reduction’s desugaring makes, so it has an expected type only as such an argument has one: the compiled type checker instantiates a generic big operator whose static argument the reduction does not write at its bound, and at the reduction’s expected type only where the reduction’s type at that bound does not fit it, and it refuses the reduction where the big operator has no instance at its bound, as one whose bound mentions its own static parameter has none (row 425 of the revival’s gap ledger). The interpreter instantiates a type parameter of a function that nothing at a call fixes at its bound, Any if it has none, and one whose bound mentions other static parameters at that bound with their instances, with two exceptions: a type parameter that only the bound of a type parameter that the arguments fix mentions, as A extends T mentions T, it instantiates at the arguments’ type, not at its bound, since it has no expected type to fix it (row 592 of the revival’s gap ledger); and a type parameter declared with several bounds that it cannot meet, as two bounds neither of which is a subtype of the other, it erases to BottomType (row 591). A type parameter whose bound mentions the type parameter itself, as the big operators ∑ and ∏ declare theirs, and that nothing at a call fixes, it leaves open: it does not instantiate it, and it admits every value where it checks a value against that type, as an argument, a variable declared with that type, a typecase clause or a type assertion. The big operator that a reduction or a comprehension invokes without its static arguments it instantiates as the desugaring by the type N of the expression would (Section 13.17), with run-time types in place of the static type that it does not have: by the declared type of the local variable, or the declared return type of the top-level or local function, whose value the reduction or the comprehension is, also as the last expression of a block, where that type fixes the big operator’s result type; otherwise by the join of the run-time types of the elements that its generator clauses give, which it collects before it reduces them; and where there is no element, at the bound of each static parameter, or open where the bound mentions the parameter itself. So an empty sum that is the value of a function declared ℝ64 is the ℝ64 zero, and the library’s set reductions ⋃ and ⋂ run on sets of their elements’ type; but an empty reduction that no declared type directs takes the identity of ℤ32 whatever the type of the expression, and an empty comprehension that no declared type directs is built at the bound, a list comprehension as a List⟦Any⟧ (row 716 of the revival’s gap ledger); a comprehension that no declared type reaches, such as the value of a top-level variable, a field, a method or a function expression, the right-hand side of an assignment, the body of another reduction or an argument of a call, is built at the run-time types of its elements, which the declared type of an enclosing expression may not admit (rows 20, 510 and 717). A big operator whose declared result is none of the library’s BigReduction, Comprehension and BigOperator it instantiates through the one of those three that its declared result extends, with that trait’s static arguments. It gives a function expression that declares no return type the return type BottomType, so that a type parameter that only its result fixes is instantiated there (row 587); and it instantiates a static parameter of a generic method that only the expected type would fix, as one of a generic function, at its bound (row 510), a method that a trait declares among them. The third item of the team’s draft note below asks whether inference may give a static parameter BottomType; the rule of Section 20.1, taken from the type group’s paper of 2019, answers that it may not. Neither implementation infers a bool parameter yet: the compiled type checker refuses by name to infer a bool, dim or unit parameter, and the interpreter does not unify a bool one (row 307 of the revival’s gap ledger) and stops at load on an object or trait whose method has a parameter type with a bool static argument (row 761). The example of Section 12.3, a coercion whose bool parameter only its parameter type mentions, can be applied only if its argument fixes that parameter.
