## The writers' points

### `.claude/skills/fortress-repo/SKILL.md`

- In "When to explore", the sentence "The curator settles the question after research." says more than `exploring.md`, "The choices that are yours", which lets the agent make a choice that changes one area only, no line of the model and no decision, and can be undone. So a gap that meets those four conditions is the agent's choice in one file and the curator's in the other. I left the sentence unchanged. Options: (a) keep it as it is; (b) narrow it to "The curator settles a conflict, and new evidence against a decision of the curator, after research."; (c) cut it and leave the rule to `exploring.md`, which an agent loads when it switches. Option (a) keeps the current behaviour.

### `.claude/skills/fortress-repo/references/records.md`

- The outline asks for the step `ledger.py check --rows FILE` before `ledger.py add`. That step does not work with the tool as it is. `check --rows` refuses a row with `?` in its number cell, and `add` requires exactly that `?`. `add` already runs the same template check before it writes. So the part says: write the row with `?`, run `add`, and `add` prints each broken rule and writes nothing. Alternatives: (a) keep the part as written, which is the current behaviour; (b) change `check --rows` to accept a `?` number cell, then put the step back. The outline also asks exploring.md's step 7 to check a report row with `check --rows`. Such a row fails the same way unless it carries a real row number.

### `.claude/skills/fortress-repo/references/specification.md`

- The rule "quote each sentence of the specification that your change makes false" moves from specification.md to records.md's list of what every report holds. Its meaning stays the same: it already said "your change", and the script's REPORT.md paragraph asks it of every change. But in practice it now reaches workers who change code and never load specification.md. That is the case it exists for: batch 9's blocking finding was a change to walk that made an Appendix I effect false. Alternatives: (a) move it, as proposed; (b) keep it in specification.md, where only a worker in the specification area reads it. Option (b) keeps the current behaviour.

### `.claude/skills/fortress-repo/references/gate.md`

- Step 3 runs the library order only after a build that started the caches again. The implementation's stamp covers `ProjectFortress/build/`, `third_party/`, `bin/` and `default_repository/configuration` (`build.xml`, `implementationFingerprint`), not `Library/` or `LibraryBuiltin/`. Compiling a program never recompiles a library component already in the cache (`build-and-caches.md`; `build-efficiency.md` 8.1). So suppose a gated tree changes one of the five compiled-library components and no Java. Then the caches are kept, and the atomic runs and the ladder copies run on the old library jars. A changed library body gives no warning; a changed api gives a false red (`NoSuchMethodError`). The suites are not affected, because they compile the library in private caches. Alternatives: (a) keep step 3 as it is; (b) also run the library order when `git diff` since the gated commit touches `LibraryBuiltin/AnyType.*`, `LibraryBuiltin/CompilerBuiltin.*` or `Library/Compiler*`; (c) run it in every gate, as the workflow script still does, at about 100 to 110 s of about 25 minutes. Option (a) keeps the current behaviour. The writer would choose (c), as the simplest rule with no hole.

### `.claude/skills/fortress-repo/references/exploring.md`

- `ledger.py check --rows` counts the `?` in the number cell as a broken rule (ledger.py:525-526), but `add` requires that `?` (:757-758). So step 7 now adds a rule: correct the row until the check names no other rule. Alternatives: (a) keep this sentence; (b) change the tool so that `check --rows` accepts `?`, and drop the sentence. The outline also puts `check --rows FILE` before `add` in records.md. That step is redundant: `add` already runs the same lint (`template_row`, :584-590, called at :766) and prints each broken rule. It would also fail every time on the `?` that `add` needs. The check is needed only where no `add` follows, which is exploring.md's step 7.

### `.claude/skills/fortress-repo/references/toolchain.md`

- A possible new rule. The preparser (`parser/preparser/`) and the import collector (`parser/import_collector/`) are two more Rats! parsers, each with its own `Compilation` and `Symbol` modules. The import collector's two are near copies of the main grammar's (`Compilation.rats` has 413 lines against 417; `Symbol.rats` differs in about 118 diff lines). The preparser's two are smaller variants. The part's copy rule names only the template parser. Alternatives: (a) keep the rule as it is until a worker meets such a change; (b) extend it: "If you change `Compilation.rats` or `Symbol.rats`, check the modules of the same name in `preparser/` and `import_collector/` too." Option (a) keeps the current behaviour. Not checked: whether a change to the main modules ever needs a matching change in those two parsers.

### `.claude/skills/fortress-repo/references/tests-running.md`

- The rule "Run one suite at a time in a tree" names only the two suites. The line "For a shared phase ... or the parser, run both" asks for `ant testQuick` and `ant testSystem`, and an agent may run the two at once. The two targets clash in three ways. `testSystem` and `testFast` delete all of `ProjectFortress/test-caches` when they start (`build.xml:1186`, `:1429`), which includes the folders of testQuick's tracks. Every test target deletes `ProjectFortress/test-tmp` when it ends (for example `:1125`, `:1436`), and the other target's JVMs use that folder as their temporary directory. Both targets run `ant compileAll` in one tree at the same time. Alternatives: (a) widen the rule to "Run one `ant` test target at a time in a tree, because each deletes the `test-caches` or `test-tmp` that another uses"; (b) leave the rule as it is, and write "run both, one after the other" in the shared-phase line; (c) leave both lines as they are. Option (c) keeps the current behaviour.
- The whole-suite rule is unclear for an edit of a parser grammar (`parser/*.rats`). The condition at its top names "the Java or Scala of the checker, of walk or of a phase that both paths share", which a `.rats` edit is not. Read that way, the edit falls under "every other change", so the agent runs only its own tests. The line below it says "For a shared phase ... or the parser, run both". Alternatives: (a) add "or a parser grammar" to the condition, so that a grammar edit runs testQuick and testSystem; (b) read "the parser" as its Java only, and write that a grammar edit runs only your own tests; (c) leave the text as it is. Option (c) keeps the current text, and most readers would then follow the parser line and run both.
