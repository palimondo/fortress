In one paragraph: a numeral has a type at compile time only, the Draft's `NaturalNumeral` and `RadixPointNumeral` below `Numeral`, with the four numbers (digit count `n`, digits after the point `m`, radix `r`, the digits as one integer `v`) as static parameters, so `3.125` has the type `RadixPointNumeral[\4, 3, 10, 3125\]`. Where a type is fixed, the compiler converts at compile time from the exact value: exactly into the integer types and `QQ`, with one rounding into `RR64` and `RR32`, a refusal at compile time when the value does not fit. A number type, the library's own as much as a program's, takes a numeral by declaring a coercion generic over the four numbers, whose body is a call of the type's constructor on values computed from `n, m, r, v`; the compiler instantiates it for the numeral and emits the constructor call with the constants, once per place, into a `static final` field that the class's initializer fills; for a built-in type that call folds to a JVM constant. Where nothing fixes a type, the machine default (`ZZ32`, `ZZ64` or `ZZ` by size; `RR64`), then the same conversion. An expression of numerals alone folds exactly first; a numeral has no sign, so `-3` at a program's type is the type's own `-` applied to the coercion's result, both once at load. No numeral object exists at run time: no getters, no `asFloat`, no `asString`, no `=` pairs on a numeral type. Walk does the same thing at the first evaluation of each place, fixing the coercion's static arguments from the numeral's four numbers. `nat` is unbounded in the type system; the 32-bit `nat` is this implementation's array-size choice.
