> A call of a function, a method or an operator whose declaration has static parameters, or of the constructor of an object
> that has static parameters, need not write its static arguments, and most calls do not (Section 13.2, Section 13.4).
> The static arguments of a call that does not write them are inferred statically. This chapter describes that inference
> for type parameters (Section 12.1) and for nat and int parameters (Section 12.2); the inference of the static arguments of other kinds of static parameter, and the inference over a whole program of the types that declarations elide
> (Section 22.6), are not yet described.
> R EVISED BY THE 2026 REVIVAL
> SEE Section I.1.25
> The Working Draft of February 2011 left this chapter a heading and two draft notes, the second of which is kept at its end,
> although Chapter 15, Section 13.2 and Section 13.4 cite it. The rule this chapter states is the one the revival decided on 26,
> 27 and 28 September 2026 and built into the compiled type checker with this text; the Working Draft had no counterpart to
> the rule for a numeral whose conversions tie (Section 20.2). It assumes that a type parameter declared without an extends
> clause is bounded by Any , as the Fortress standard libraries and the interpreter take it, where Section 12.1 says Object, as
> the compiled path still takes it for a program’s own declarations (row 412 of the revival’s gap ledger). Chapter 15 still says
> that static parameters are inferred before the applicability of a declaration is checked and before declarations are compared
> (Section 15.2, Section 15.3, Section 15.5), where this chapter chooses a declaration first. Those sentences, the implicit bound
> of Section 12.1, and the rule of Chapter 24 that a functional whose single parameter has as its type a naked type parameter of
> bound Any cannot be overloaded, which under that bound would forbid overloading any functional whose single parameter’s
> type is a type parameter declared without an extends clause, are to be revised together, in the revision of the overloading
> chapters that the revival decided on 26 September 2026. The team’s later Types chapter gives the coercion relation and the
> valid instantiations of a quantified type, and says nothing of inference.
> 20.1
> The Static Arguments of a Call
> The static arguments of a call that does not write them are found in two steps: the declaration that the call invokes is
> chosen first, and it is instantiated second.
> Choice. The declaration is chosen as Section 17.5 describes. A declaration with static parameters is applicable to
> a call, without or with coercion, if some instance of it whose static arguments satisfy their bounds is applicable to
> the call. Declarations are compared on the parameter types they declare, a declaration with static parameters on its
> parameter types taken over every instance that its bounds allow, and not on an instance inferred for the call. So a
> coercion is applied only to make a call possible: it never changes which declaration is chosen when one is applicable
> to the call without it.
> Instantiation. The static arguments of the chosen declaration are then inferred, and with them the instance of the
> declaration that the call invokes:
> • A type parameter, or a nat or int parameter, that the declared type of a parameter mentions other than as the
> whole type, as b: ListJT K mentions T , is fixed by the argument at that position, whose type must be a subtype
> of the parameter type of the instance.
> • Where the call has an expected type (below), a type parameter that the declared return type mentions other than
> as the whole type is fixed by the expected type as well.
> • A type parameter that is the whole declared type of one or more parameters, as T is of x: T , and that is not fixed
> as above, takes, among the types of the arguments at those positions and the types to which they can be coerced,
> the narrowest under ⊴ (Section 17.5) that every one of those arguments is substitutable for (Section 17.4) and
> that the bounds of the type parameter permit. For number arguments this is the narrowest type into which every
> one of them converts: Z64 for a Z32 and a Z64 , and also for a Z32 and an N32 , though neither of them is
> a Z64 (Section 33.2). Where there is no such narrowest type, and the rule for numerals (Section 20.2) does not
> settle the tie, the type parameter takes the union of the types of those arguments (Section 6.10), if its bounds
> permit that, and none of those arguments is converted.
> • Every argument is then admitted against the corresponding parameter type of the instance by substitutability: an
> argument whose type is a subtype of it is passed as it is, and any other argument is coerced to it (Section 17.1),
> as an argument is coerced to the declared type of a parameter of a declaration without static parameters.
> The coercions that the instance needs are inserted into the call statically, as is any coercion that Section 17.5 chooses.
> The expected type. A call has an expected type in these contexts: as the right-hand side of a variable or field declaration
> that declares its type, that type; as the right-hand side of an assignment to a variable whose type is declared, that type;
> as the body of a functional that declares its return type, that type; as the last expression of a block that has an expected
> type, where no local declaration precedes it in the block, the block’s expected type; and as a branch of an if expression
> with an else clause that has an expected type, the expected type of the if expression. The expected type is used
> whether the call is written by tight juxtaposition, as f (x) (Section 16.8), or as a method invocation or an operator
> application. The return type of the instance that the steps above find must be a subtype of the expected type. If they
> find no such instance, the static arguments are inferred again without the expected type, and the call is accepted only
> if the return type of the instance then found is a subtype of the expected type or can be coerced to it; in the second case
> the result of the call is coerced to the expected type (Section 17.1). So, for the declarations wrapJT K(x: T ): ListJT K
> and id JT K(x: T ): T , the variable declaration a: ListJZ64K = wrap(3) instantiates wrap at Z64 , which the expected
> type fixes, and coerces the numeral, while b: Z64 = id (3) instantiates id at the numeral’s own type (Section 13.1)
> and coerces the result.
> Dispatch. The call, with the coercions of its instance inserted, dispatches at run time as Section 15.5 describes, by
> subtyping and without further coercion, to the most specific declaration applicable to the converted values.
> For example, of the declarations opJT extends NumberK(a: T, b: T ) and op(a: Any, b: Any) , the call op(z, w) ,
> where z has type Z32 and w has type Z64 , chooses the first, which is applicable without coercion, since its instance
> at Number is, and is more specific than the second; the first is instantiated at Z64 , z is coerced, and the converted
> call runs that instance.

> The interpreter has no static types and applies the same rule at dispatch, from the run-time types of the arguments: it infers the
> static arguments of a declaration with static parameters with coercion, and instantiates the declaration that its dispatch chooses
> by the rule for a type parameter that is a parameter’s whole type. So where the declared type of a variable is wider than the
> type of its value, or an argument’s static type is Any , it may run a declaration at a narrower instance than the compiled path,
> which instantiates it at the static types. It does not yet fix a type parameter by the expected type, compare declarations with
> static parameters on the parameter types they declare, nor dispatch a converted call again.
> 20.2
> A Numeral Whose Conversions Tie
> A numeral has a type of its own, from which the Fortress standard libraries define coercions to the number types
> (Section 13.1). Where the types to which a numeral can be converted are incomparable under ⊴, as Z32 and N32
> are, each taking a numeral and neither converting into the other, the numeral is read as a Z32 , or as a Z64 or a Z
> when its value does not fit in the narrower type. This holds in either step: in the choice among declarations that are
> applicable to the call only with coercion and that the numeral would otherwise leave tied, and in the instantiation of
> a type parameter that only numerals fix. So of the declarations g(x: N32) and g(x: Z32) , the call g(0) invokes the
> second; and a type parameter that only numerals fix, whose bounds Z32 and N32 satisfy and the numeral’s own type
> does not, is instantiated at Z32 when Z32 holds the numerals’ values.
> The rule settles only a tie that a numeral makes. Where an argument that is not a numeral leaves the declarations
> applicable to a call only with coercion tied, no declaration is the most specific, and the call is a static error.
> This chapter does not yet describe:
> • the static arguments of a bool , dim , unit or operator parameter (Section 12.3, Section 12.4, Section 12.5);
> • a static parameter that neither an argument nor the expected type fixes, such as a type parameter that only
> the return type mentions, as its whole type, or the element type of a reduction that only its generator clauses
> determine (Section 13.17); whether inference may give such a parameter BottomType, which programmers
> must not write (Section 6.8), is left open;
> • whether an argument whose declared parameter type mentions a static parameter inside another type may be
> converted where only a conversion of its elements would satisfy the bounds of the parameter; under the rule
> above such an argument fixes the parameter by subtyping and is not converted;
> • an expected type in any context other than those listed above, such as an argument of another call, an expression
> that a local declaration precedes in a block, an if expression without an else clause, a typecase expression,
> the body of a for loop, or a call written by loose juxtaposition, as f x ;
> • the static arguments of an object with static parameters that is named without a call, which a program writes
> (Section 12.6);
> • the inference over a whole program of the types that declarations elide (Section 22.6).
> R EVISED BY THE 2026 REVIVAL
> SEE Section I.1.25
> For a type parameter that only the return type mentions, the compiled type checker binds the parameter to BottomType,
> except that it refuses a call that has no expected type when the parameter is declared extends Any ; the interpreter erases
> such a parameter to BottomType (rows 424, 425 and 447 of the revival’s gap ledger). Whether inference may do so is the
> team’s question, kept in the draft note below. Neither implementation infers a bool parameter yet: the compiled type checker

> the revival’s gap ledger). The example of Section 12.3, a coercion whose bool parameter only its parameter type mentions,
> can be applied only if its argument fixes that parameter.

> The inference of a call’s static arguments
> Affected sections Chapter 20; Section 13.16; Section 33.2; Section I.1.18; Section I.1.26.
> Change Chapter 20, which held a heading and two draft notes, states how the static arguments of a call that does not
> write them are inferred, for type parameters and for nat and int parameters. The declaration is chosen first,
> as Section 17.5 chooses it, a declaration with static parameters being applicable to a call if some instance of it
> within its bounds is, and compared on the parameter types it declares. Its static arguments are then inferred: a
> type, nat or int parameter that a parameter type mentions inside another type is fixed by the argument, and
> a type parameter that the return type mentions inside another type by the expected type; a type parameter that
> is the whole type of parameters takes the narrowest type that their arguments are substitutable for, which for
> number arguments is the narrowest type into which every one of them converts, and otherwise the union of their
> types; every argument is admitted by substitutability, the coercions the instance needs are inserted statically,
> and the converted call dispatches by subtyping. A call written by tight juxtaposition, as a method invocation or
> as an operator application, has an expected type in the contexts the chapter lists, a variable or field declaration
> and an assignment to a variable among them, and is inferred again without it when its result then converts.
> A numeral whose conversions tie is read as a Z32 , or as a Z64 or a Z by its value; any other tie among
> declarations applicable only with coercion is a static error. The chapter lists what it does not yet describe, the
> static arguments of a bool , dim , unit or operator parameter among them, keeps the second of the two draft
> notes, and has three boxes: on the Working Draft, the bound it assumes and the passages it leaves to the revision
> of the overloading chapters; on the interpreter; and on a type parameter that only the return type mentions and on
> the bool parameters that neither implementation infers. The ranges section says that a nat or int parameter
> used as a component converts to Z32 as an integer numeral does, with a box. The box in Section 33.2 says
> that a generic call over two different integer types infers the narrowest type that both coerce into by the rule of
> Chapter 20. Section I.1.26 says that the rule is written and names the passages the chapter leaves unrevised, and

> Rationale This change does not follow from route A. The revival decided on 26 September 2026 that a generic
> call over two different integer types infers the narrowest type that both coerce into, by a rule written into this
> chapter; on 27 September 2026 that the compiled type checker infers static arguments with coercion and keeps

> changes which declaration runs when one is applicable without it, the declaration chosen being then instantiated
> by that rule, that a numeral whose conversions tie is read as a Z32 , and that a nat parameter used as a value
> converts to Z32 as a numeral does. Chapter 15, Section 13.2 and Section 13.4 said that static arguments are
> inferred as Chapter 20 describes, and it described nothing; once the compiled type checker infers them by a rule
> the text does not state, the text and the implementation disagree, so the chapter states the rule that the checker
> builds, and no more. The order, a declaration chosen and then instantiated, is that of Section 17.5, read on
> the parameter types that declarations declare, as the type group’s paper of 2011 reads a declaration with static
> parameters: it “is applicable to a type if and only if at least one of its instances is” (Papers/Types/setup.
