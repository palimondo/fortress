# Facts on record

## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- On microGPT-shaped array code boxing is the dominant representational cost, 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` in Java models of the program's three kernels, and nothing microGPT-shaped compiles: the compiler prelude lacks the array types, with `Array`, `Vector` and `Array3` undefined in `FlatArrays.fsi` (row 305, wider than row 72). On the interpreter, the only path that runs the kernels, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch and 0% number representation (JFR on `krows`). The order that followed: an `RR64` array type in the compiler library (G2); the two one-line runtime defects (rows 302, 303, since fixed by rung 0); unboxing and `double[]`, designed into the first. A failed compile leaves a 0-byte jar in the bytecode cache (`258105b3e`; `perf-probes/kernels/REPORT.md`) (full entry in FACTS-history.md).
- The boxing probe's scalar-loop reading, 156× primitive Java with boxing about 2% of it, is of the tree before rung 0's two fixes (rows 302, 303; `53362cb88`); of the costs it named, `countedseqloop`'s boxed indices and closure call (about 7%) and the representational rest (about 30%) are unaddressed (`perf-probes/boxing/REPORT.md`) (full entry in FACTS-history.md).
- The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `53362cb88`; `compile-ladder/rung0/REPORT.md`) (full entry in FACTS-history.md).
- `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `53362cb88`; `compile-ladder/rung0/REPORT.md`) (full entry in FACTS-history.md).
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine; the 2026-09-17 before-run of the same unmodified tree measured 13.0566 s and 8.8159 s, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes (observed 2026-09-17).
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); whether `nat` parameters are baked into stamped classes is unprobed. Superseded 2026-09-24: a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`). A size's descriptor in a stamped class is `RTTIsize.of("<n>")` since climb batch 5 rung Z (`e893a3e00`).
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see "The checker and the one library" below). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half). Its first sentence is superseded 2026-09-26 by climb batch 4 rung N (`3f297441c`): the compiled checker checks `nat` and `int` static parameters ("The checker and the one library" below); a sized program still fails at load until the run-time rung. Its last clause, that a sized program still fails at load, is superseded by climb batch 5 rung Z (`e893a3e00`; "A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics).
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification/basic-lib/convenience.tex:49`) gives the identical single error from `fortress compile` and from `fortress walk`, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause in either implementation. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at codegen — `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4088`) — but nothing reaches it. This is the mechanism behind `FortressLibrary.fss:1340-1341`'s "when we get where clauses working", and it is why both worlds must spell the empty case some other way. Corrected 2026-09-26 (`reviews/spec-refused-examples/probes/SpecNothing.fss`, `SpecNothingNoExcludes.fss` and their captures): the probe of this entry (`WhereClauseNothing.fss:12`) left out the declaration's `excludes Just[\T\]`; written as the specification writes it, the declaration stops earlier on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`); `T is undefined` is what it gives once that clause is removed.
- **An exported function fails exactly as an exported variable does when a component's name differs from the api it exports, and the failure is the repository's, not codegen's** (2026-09-20, rung X). `probes/FnApi.fsi`+`FnLib.fss`+`FnMain.fss` dies with `NoClassDefFoundError: FnApi`, alongside `P8Api$shared` and `P9Api$shared` (`explorations/compile-ladder/rung-export-var/probes/probes-preedit.txt:29,96,163`). Through the real entry points the divergence never reaches codegen at all: `fortress link P8Main` and `walk` on each of the three main components print "Could not find an implementation for API … on path" (`probes/link-and-walk-preedit.txt:4-9,45-60`), so both execution paths assume the api and its implementing component share a name. The assumption is `Linker.whoIsImplementingMyAPI`'s fallback to the api's own name (`ProjectFortress/src/com/sun/fortress/linker/Linker.java:72-76`) when nothing has been registered in its persisted map, and only the user can register one, by hand, through `LinkShell`'s `alink`/`clink` verbs (`linker/LinkShell.java:41-70`; `linker/README:28-40` describes the intended design). `Specification/basic/components/overview.tex:33-35` settles it — a reference to an imported api is "resolved to a component that exports that api" — and the team reserved the codegen half of the repair in three comments in one file (`CodeGen.java:411-441`, `:1856`, `:6599-6606`). Gated as an expected failure by `ProjectFortress/compiler_tests/XXXExportVarRungXLinked.test`.
- **A comment placed after a declaration that ends in an expression or a type becomes part of that declaration's source span and of the unambiguous name the parser derives from it** (2026-09-22, rung C, `compile-ladder/rung-library-comments/probes/SpanAbsorb.fss` and `SpanAbsorb.txt`; ledger row 359). `createSpan` (`ProjectFortress/src/com/sun/fortress/parser/Fortress.rats:145-157`) trims back over space characters only. A declaration ending in `end` is unaffected. So a comment-only edit to the library is not neutral at the syntax-tree level: rung C's widened three spans (the scalar block's first `-` in both files, `SUFFIX_SUM` in the `.fsi`), besides shifting every position below each insertion, and a before-and-after comparison of parse trees or diagnostics must map positions back first (`compile-ladder/rung-library-comments/parse-compare.sh`, `ast-compare.py`, `remap-lines.py`). No answer changed.
- **Under `walk`, a native can raise a Fortress exception that a Fortress `catch` sees** (rung I, `explorations/compile-ladder/rung-int-semantics-walk/REPORT.md`, section 4.1): `throw new FortressError((FObject) Driver.getFortressLibrary().getRootValue(name))` from inside a `builtinPrimitive` method reaches `Evaluator.forTry` unchanged (`MethodClosure.java:85-86` has no `catch`) and matches `catch e IntegerOverflow`; `Int.overflow()` (`ProjectFortress/src/com/sun/fortress/interpreter/glue/prim/Int.java:256-259`) is the helper and `WellKnownNames.integerOverflowException` the name. Measured by the 25 `overflows(...)` assertions of `ProjectFortress/tests/IntSemanticsRungI.fss`, whose helper catches nothing but `IntegerOverflow`. Before this rung no native raised one; the interpreter's mapping of every other Java exception is unchanged (`FunctionClosure.java:188-196`), so row 336's division by zero and row 347's `Int.rc` still end the run.

## The library's arrays and algebra

- **Route A's generic container obligations still need body-level checks** (source review, 2026-09-26, `reviews/numeric-hierarchy-integration-review.md`, baseline `c5eada1b2`; nothing run). `Vector` and `Matrix` promise scalar results of `T`, while today's `Number` arithmetic returns `RR64` and `SUM` returns `Number`; flattening removes those catch-alls but does not by itself supply evidence for a body bounded only by `T extends Number`. This is partly pre-existing, not a newly measured regression. The flat sketch's `Integral[I]` does not extend `MultiplicativeRing[I]`, so a blanket ring bound would exclude integer containers. Row 388 has a concrete integration consequence to test: fixed-receiver `m.scale(i)` versus generic operator `m i` after flattening, because only the latter infers the operator's element type and sizes. Their divergence is a source prediction, not a matrix probe result. Empty reductions need their advertised result type as well as identity value. The note proposes bounded checks for the existing rungs; it takes no new design decision.

- `Vector[\T extends Number, nat s0\]` and `Matrix[\T extends Number, nat s0, nat s1\]` are the only sized array traits; `Array3[\T, nat b0, nat s0, …\]` carries no algebraic trait (row 292; `FortressLibrary.fsi:1465, 1583, 1657` since the library commits of climb batches 3 and 3.5).
- `Vector` and `Matrix` inherit `+`, `-`, unary `-` and `zero` from `AdditiveGroup`, nothing else; `×` reaches no array by design because juxtaposition is the inner product and the array traits exclude `AnyMultiplicativeRing` (rows 64, 109, 293); a carrier that extends the ring is accepted unchecked, changes juxtaposition to elementwise and breaks `+` (vocabulary review v02, v02b).
- The library's products are declared with shared `nat`s (`Matrix[\T,n,m\]` × `Matrix[\T,m,p\]`, `FortressLibrary.fsi:1508-1516`); C4's own products were not, which is habit; the focused base's `FlatArrays2` states them (twelve declarations including the per-rank elementwise `×` and `/`, 25 of 29 nats agreeing; 39 declarations), and a wrong-shape call is refused at dispatch, uncatchable for an overloaded name (row 83), as a unification error naming the nat for an unoverloaded one (`apl/mg/checks/mismatch_probe.out`).
- Two declarations of one name differing only in the element type, or a rank-specialised declaration beside an index-generic one, are refused at load ("at least one pair of parameters must have excluding types"; `apl/mg/checks/model_run.out.0`, `elemwise_nat_probe.out.0`); two apis' overloads of one name are checked as one family, so two vocabularies cannot stand in one component (`diag_fwd_two_vocabularies_rejected.out.0`).
- The shipped `RR64` does not satisfy the specification's algebraic bound `T extends AdditiveGroup[\T\]` (vocabulary review, probe `v04b_groupbound.out.0`); `T extends Number` is the bound that works for every element type and rank (row 295).
- The library's scalar-extension block for `+ - MIN MAX` over arrays is generic since `02d09a39f` (`Library/FortressLibrary.fss:4511-4521`, `.fsi:2550-2560`); no reshape, plane, gather, outer product or ravel exists in the library (vocabulary review, section A).
- An array is a trait with `get`/`put`; a view is an object implementing it over other storage, the language's own idiom; the library's row slice `m[i,:]` costs 5× a six-line user view; a diagonal as a `Matrix` view costs 13-54× the operator (vocabulary review v20, v07); a subtype of `Matrix` that overrides `mul` gets its specialised product through the library's own operators, which forward to `mul` (`Library/FortressLibrary.fss:2627-2633`), at the operator's cost and with no api line, since the interpreter dispatches the method on the receiver's run-time type (2026-09-25, `run-c4/probes/vocabulary/diag-override.md`; ledger row 299).
- The element type is `Number` only for `Vector`/`Matrix` (row 24); irrelevant to numeric microGPT, decisive for Run B's autodiff value and for APL characters.
