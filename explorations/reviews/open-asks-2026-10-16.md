### Ask 1. A `where` clause on an `extends` entry: does it hold for what the trait inherits?

**The question.** When a trait extends another trait under a `where` clause, are the declarations it inherits checked under that clause?

**The context.**

- **Primer.** A static parameter is a type parameter, written `[\T\]`. A `where` clause puts a condition on one. Fortress lets each entry of an `extends` clause carry its own `where` clause. The trait then extends the other trait only where the condition holds. This is called conditional extension.
  ```
  trait A[\T\]
    f(x: T): String = "A"
  end
  trait G[\T\] extends A[\T\]
      where { T extends ZZ32 }
    override f(x: ZZ32): String
      = "G"
  end
  ```
  Under the condition, `G[\T\]` is an `A[\T\]` only when `T` extends `ZZ32`. So `G`'s `f(x: ZZ32)` replaces the `f(x: T)` it inherits. Without the condition, `G[\String\]` would be an `A[\String\]`, its inherited `f` would take a `String`, and the `override` would replace nothing, which is a static error.
- **The designers' text points to the condition.** The grammar gives each `extends` entry its own optional `where` clause. The front matter lists "where clauses and conditional extension" among the features not yet supported. The traits chapter gives the grammar and nothing more. The text also orders a list only when its elements are ordered, which is conditional extension's main use.
- **The designers' later word says nothing against it.** The team's farewell post of July 2012 names conditional inheritance through `where` clauses among three things the team wished it had explored further. The type group's later calculi, Welterweight (2012) and the POPL 2019 paper, have no `where` clauses at all.
- **The library as the team wrote it** has no `extends` entry with a `where` clause. The team's one test of the form only parses it.
- **What the paths do today.** Walk treats the extension as holding for every `T`. Since climb batch 13 it checks the `override` against `A`'s declarations under the clause, so the example loads and prints `G`. An `override` that the clause cannot make valid is still refused at load. The compiled checker skips `where` clauses on `extends` entries, and the code generator refuses every declaration that carries a `where` clause.
- **On record.** No decision of yours settles it.

**The options.**

- **1a. The clause limits what is inherited.** Walk keeps its check, as built. The traits chapter states this meaning in a callout, the boxed note that marks a revised passage, with its entry in Appendix I, the appendix that gives each revision its reason. No code changes. The test that pins the behaviour stays.
- **1b. The clause limits nothing.** The extension holds for every `T`, and the example's `override` is a static error. Walk's check goes back to refusing it. Its test becomes an expected failure. The traits chapter says that the clause does not limit what is inherited.

**How they weigh.**

- 1a follows the grammar's intent. The build of `where` clauses needs it anyway, since a list ordered by its elements is this form. It gives up nothing that a program on record uses. Until that build, only walk's `override` check follows the clause, and walk's subtyping stays unconditional.
- 1b matches walk's subtyping today and needs no callout about a meaning that is half built. It gives up the clause's meaning: the clause becomes text with no effect, and walk refuses a program that it loads now.

**Recommendation.** 1a, the clause limits what is inherited, as built. Default: 1a.

### Ask 2. May a `where` clause name a new type variable in an `extends` clause when a constraint fixes it?

**The question.** The revival's specification bars every new type variable of a `where` clause from an `extends` clause. Should it bar only the ones that no constraint fixes to one type?

**The context.**

- **Primer.** A `where` clause can introduce a static variable that is not a static parameter: a `where`-clause variable. The specification's own example, now marked "Not allowed":
  ```
  (* Not allowed *)
  object Empty extends List[\T\]
      where { T extends Object }
  ```
  `T` is free, so `Empty` would be a `List[\T\]` for every `T` at once. Instantiation exclusion, the rule that no type extends two instantiations of one generic trait, forbids that. The revival's sentence goes further. It also bars a variable that a constraint fixes:
  ```
  trait Foo[\S\] extends Bar[\T\]
      where { S extends Baz[\T\] }
  ```
  By the same rule, each `S` extends at most one instantiation of `Baz`, so each `Foo[\S\]` extends exactly one `Bar`. The rule allows this. The sentence refuses it.
- **The designers' text.** The Working Draft of February 2011 offered three such declarations as legal, among them `Empty` and a trait that makes its own parameter covariant by extending itself at every supertype, and it gave a core calculus with `where` clauses. It did not separate free variables from fixed ones.
- **The designers' later word points to the sentence.** Instantiation exclusion, as the team's 2012 Types chapter states it, refuses the free variables. The later calculi, Welterweight (2012) and the POPL 2019 paper, have no `where`-clause variables at all: every static variable is a declared static parameter. They would write the fixed case with `T` as a parameter, `trait Foo[\T, S extends Baz[\T\]\] extends Bar[\T\]`. By your rule, the type group's later word outweighs the early text.
- **The library as the team wrote it** uses no `where`-clause variable in an `extends` clause. Where the team wanted a covariant collection, it wrote a widening function instead. Its empty values are parametric, `Nothing[\T\]`. The team's comments that wish for the form, a bare `Nothing`, and a `__Proxy[\T\]` that extends the proxy of every supertype of `T`, want free variables, which instantiation exclusion refuses under either option.
- **What the paths do today.** Neither path lets a `where`-clause variable stand in an `extends` clause: both report "T is undefined". Nothing on microGPT's path has a `where` clause.
- **Who wrote it.** Batch 5 wrote the sentence. Its conformance review found it broader than the rule, and no one decided the breadth.
- **On record.** No decision of yours settles the sentence. Your decision on `Maybe`'s empty value puts the bare `Nothing` behind `where` clauses. Neither option here reopens it, since its variable is free.

**The options.**

- **2a. Keep the sentence, and record its breadth as chosen.** One sentence in its callout and in Appendix I: the ban is broader than instantiation exclusion on purpose, since the later calculi declare every static variable as a parameter, and a fixed variable is written as one. No code changes.
- **2b. Narrow the sentence to the rule.** A `where`-clause variable may stand in an `extends` clause when the declaration's constraints fix it to one type for each instance. A callout says that neither path runs it yet, and a ledger row holds the gap until a checker and walk rung builds it.

**How they weigh.**

- 2a matches both paths and the later calculi, and costs one sentence. It gives up a convenience: a fixed variable is inferred from `S` instead of written as a parameter. No code on record uses that.
- 2b matches the rule exactly and keeps more of the Working Draft. It gives up agreement between the text and both paths: the text then promises a form that neither path runs, a gap the specification's revision is meant to close, and a later rung must build it.

**Recommendation.** 2a, keep the sentence and record its breadth as chosen. Default: 2a.

### Ask 3. The bound on the element type of `Vector` and `Matrix`

**The question.** Do `Vector` and `Matrix` keep the bound `T extends { Number, MultiplicativeRing[\T\] }` on their element type, as landed?

**The context.**

- **Primer.** A bound is the rule on a type parameter: `T extends Number` admits only number types. The bodies of `Vector` and `Matrix` add, subtract and multiply their elements:
  ```
  trait Vector[\T extends
      { Number,
        MultiplicativeRing[\T\] },
      nat s0\]
    opr -(self): Vector[\T,s0\] =
      map[\T\](fn (e: T): T => - e)
  end
  ```
  The checker accepts `- e` only if the bound promises a minus on `T`. On the flat number tower, each number type carries its arithmetic at its own type through the algebra traits: `MultiplicativeRing[\T\]` gives `+`, `-`, times, `zero` and `one`. `Number` is the closed trait above all number types, the one that lists every type below it. It declares no arithmetic.
- **The designers' text.** The specification says that all elements of vectors and matrices must be numbers. The team's library bounded the element by `Number`, and the team's `Number` then carried plus, minus and times on any two numbers, with `RR64` results.
- **The designers' later word.** The team's compiler library flattened the number tower in 2009 and 2010, giving each type its arithmetic at its own type. Your route A follows it, so `Number` lost its arithmetic. The POPL 2019 paper admits a trait parameter's bound that names the parameter, such as `MultiplicativeRing[\T\]`. On a function such a bound is outside its theorem, where the library's `SUM` and `PROD` already stand.
- **Which way they point.** Together: on the flat tower, "a number that is a ring at its own type" says what the team's bound said on theirs. That is the two-trait bound.
- **The library as the team wrote it** has `Number` alone, which on the flat tower gives no arithmetic. The two-trait form is the revival's, as in its fused reduction pairs. The grammar allows it.
- **What landed.** Climb batch 13b, at your word on 2026-10-10, with the checker's speed fix: 24 sites gone and 4 new, the distance 105 to 85. Every integer type is a ring at its own type, so no integer array is excluded. The type group's 2019 paper, checked against this bound at your request, finds that it stands.
- **On record.** Your answer is recorded as pending. The bound keeps the reason of your position that a generic array body is checked against what each operation needs, with no blanket ring bound that would exclude integer arrays, but not its letter. Arithmetic on `Number` itself is not offered: it would reverse route A.

**The options.**

- **3a. Keep the two-trait bound, as landed.** Nothing to build. Probe P5 then finds the ways for the 14 bodies of these traits under it.
- **3b. `MultiplicativeRing[\T\]` alone.** About 60 library lines drop `Number` from the bound. Measured on 2026-09-29, this cleared that day's 36 arithmetic sites and brought 8 new errors, because `Number`'s closed list is what lets the operators between an array and a number stand as a valid overload set. The specification's "must be numbers" then has no type that states it.
- **3c. A bound on each operation instead of on the traits.** It keeps the letter of that position. It needs a `where` clause on each method, which neither path builds yet (probe P4), and it moves the products out of the traits, which loses the diagonal's own product, as you decided it. Until then the family's bound goes back to `Number` alone, and the arithmetic sites it cleared come back.

**How they weigh.**

- 3a says on the flat tower what the designers said, measured, at no further cost. It gives up the letter of your position, not its reason.
- 3b gains a shorter bound and gives up the closed list that the array-and-number operators need: 8 errors, measured.
- 3c gains your position's letter, and gives up the cleared sites until `where` clauses are built, then the diagonal's override.

**Recommendation.** 3a, the two-trait bound, as landed. Default: 3a.

### Ask 4. A size known only at run time

**The question.** May the checker treat a size known only at run time as fixed for the one call that receives it, as built?

**The context.**

- **Primer.** A size is a number inside a type, such as the `16` of `Vector[\RR64, 16\]`. Some sizes are known only when the program runs, such as a file's length. The library turns such a number into a size with `reflect`. A simplified form of its factory:
  ```
  __arr1[\E, nat n\](x: N[\n\])
    : Array1[\E,0,n\]
  array[\E\](x: ZZ32) =
    __arr1(reflect(x))
  ```
  `reflect(x)` answers a `NatParam`, and `__arr1` wants an `N[\n\]`. The team's clause says that every `NatParam` is some `N[\n\]`:
  ```
  trait NatParam
    comprises { N[\n\] }
      where [\nat n\]
  ```
  So the checker binds `n` to that value's own size, for that call. This is called opening the size.
- **The designers' text.** The Working Draft gives sizes as `nat` static parameters, and lets a `where` clause introduce a new static variable, a size among them. It does not say how a number known only at run time becomes a size.
- **The designers' later word points the same way.** The type group's 2011 paper reads a generic declaration's domain as "there is some `n`", and lets a type below it be passed. The POPL 2019 paper's run-time rule gives a parameter at such a position the value's own argument, which is the opened size.
- **The library as the team wrote it.** Maessen wrote `reflect` in 2007, with this clause as a comment and the note "we ought to build it in and document it in the spec". The library calls `reflect` in its own run-time factories and subarrays, ten calls that walk runs.
- **What landed.** Climb batch 13 built the opening on the standing go, uncommenting the team's clause: the ten calls check. The 2019 paper, checked against this way at your request, finds that it stands.
- **What it interprets anew.** Your position on sizes says that a size left unknown after inference is an error only where it reaches a type, a name or a value. The opening treats a size taken from the argument as bound for the call, not as unknown. If you meant that any size the call's text does not fix is refused, the opening needs your word.
- **What hangs on it.** With the opening, two declarations `f(x: NatParamT)` and `f[\nat n\](x: Nt[\n\])`, over copies of `NatParam` and `N`, apply to the same calls, so the checker refuses the pair as duplicates. Walk accepts it at load. A second check, against the 2019 paper's full text, finds the refusal correct under the opening, so the contested ledger row on the pair is no gap of the checker's.
- **On record.** Your answer is recorded as pending.

**The options.**

- **4a. Keep the opening, as built.** Nothing to build. The contested row on the pair is retired as no gap. Walk's looser check at load gets a walk row of its own only if you ask for one.
- **4b. Sizes known only at run time stay unsized.** The checker's opening rule goes: three checker files, about ten lines of walk, two sentences of the specification and their Appendix I entry, and the team's clause back to a comment. The ten library calls are refused again, and the model's bridge lines from run-time to static sizes have no way to check. The pair becomes valid on the checker.

**How they weigh.**

- 4a follows the team's own clause and note, and both later papers. It costs nothing more, and it gives up only the strictest sense of your position on sizes.
- 4b keeps that strictest sense. It gives up the library's run-time factories, which walk runs today, and the model's way to turn its run-time sizes into static ones.
- Two other ways are not alternatives now. A built-in `reflect` adds only speed, measurable after the switch-over. Fixing every size at compile time changes the model's api, which is a question of the model's sized types, after the switch-over.

**Recommendation.** 4a, the opening, as built. Default: 4a.
