# Facts on record

## Execution model

- F-9 **By default `fortress typecheck` checks a program against the compiler's prelude, not walk's library, and walk cannot run the compiled checker on its own programs.** The first is the `fortress-repo` skill's `interpreter.md`, "What walk checks" (row 69). The second bears on P-12's step after the switch-over: walk runs with type checking and the Scala checker off, the Java checker is gone, and walk has no case for the checker's `CoercionInvocation` nodes. Read in the code (row 833).
- F-11 **The code generator boxes every number, and boxing is the main representational cost of microGPT-shaped array code.** In Java models of microGPT's three kernels, boxed elements cost 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]`. In a hot loop, HotSpot keeps one box per assignment to a mutable variable per iteration (F-301). Against the compiler's prelude, which has no array type (row 305), no such kernel compiles. P-17, unboxed doubles, rests on this. Detail: `perf-probes/kernels/REPORT.md` sections 2 and 4.
- F-12 **Against the compiler's prelude, the compiled scalar loop `bench1t` ran in 0.74 s in one measurement; it pays for its generator, for boxing and for a transaction check at each use of its accumulator.** `bench1t` runs `acc := acc 0.9999999 + 0.0000001` 20 million times in a `seq` loop. The loop is the prelude's `countedseqloop`, a recursive split over boxed indices with a closure call per element; each value is boxed (F-11); each use of `acc` calls `BaseTask.inATransaction` (row 641). No share of the time is measured. Source: `compile-ladder/rung0/REPORT.md`, "The four timings".
- F-18 **On the compiled path, the class loader makes a generic instance's class by rewriting the template's bytecode, and the rewriting only renames types, so it gives no instance a `double[]` field.** A field of type `T` becomes `LFRR64;` in `Box⟦FRR64⟧`, never `[D`, so every number stays boxed (F-11). The team left only a plan, `compiler/optimization/Unbox.java`, and an empty "expando" stub in the loader. A loader that stamps a `double[]` field, way A4 of array decision A (P-85), does not exist and is unmeasured (P-84). Read in the code. Detail: `perf-probes/nat/java.md` section 1.
- F-19 **Each path runs a tuple's elements, an operator's operands and a call's arguments as tasks only where it judges them worth it, and splits a parallel `for` over a range into `do … also do` blocks.** Walk judges by `TupleTask.worthSpawning` and makes each block a task. The code generator judges by `ParallelismAnalyzer` (row 987, contested), runs the first block in place and forks the others by `BaseTask.forkIfProfitable`; the prelude's `parloop` splits down to `FORTRESS_LOOP_CHUNK` elements (1). By grep, no program under `explorations/` writes `spawn` or `also do`. Read in the code.
- F-20 **Sizes, the `nat` and `int` static parameters, are values at run time: they check shapes, and no optimization uses them.** The compiled checker checks them (F-67), and a sized program runs compiled (F-129). A size mismatch at a call is a `ProgramError` that no `catch` takes (row 254). Evidence: the rows; `compiler/optimization/` holds only the plan `Unbox.java`.

- F-171 **The specification reads a `comprises` clause as the restart's Types chapter does: every value of the trait is a value of a listed type.** So a trait or object that extends the closed trait must be below a listed type, with two exceptions. - F-172 **The specification's integer chapter states the library's integer rules.** The getters `asZZ32`, `asZZ64`, `asNN32`, `asNN64` and `asZZ` keep the value or throw `IntegerOverflow`. `narrow`, `widen`, `signed`, `unsigned` and `big` keep the bits and throw nothing: `narrow` converts a `ZZ64` to `ZZ32`, and an `NN64` to `NN32`, by keeping the low 32 bits, so a value that does not fit wraps. `ZZ` has neither `narrow` nor `widen`. `LSHIFT` and `RSHIFT` work on the five integer types.
