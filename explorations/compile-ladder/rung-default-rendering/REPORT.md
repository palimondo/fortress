## The repair round

**The finding.** The skeptic measured that the rung's first native changed two renderings that already worked: on the rung tree `x: RR32 = 1.5; println(x)` printed `RR32` and `[RR32]` where the base tree and walk print `1.5` and `[1.5]`, and a `StringVector` holding `a`, `b` printed `StringVector` where the base default printed `[a b ]` (`probes/skeptic/differentials.txt:207-208`, `:214-217`; walk `:222-223`). The cause: `FRR32` and `FStringVector` are the only 2 of the 17 value classes in `compiler/runtimeValues/` whose Fortress trait declares no `asString` (`trait RR32`, `CompilerBuiltin.fss:988-990`; `trait StringVector`, `:1150-1155`) and whose Java class declares none either (`FRR32.java`; `FStringVector.java:34` spells it `asSring`). I re-tabulated all 17 (a Java `asString()`, else the line of the trait's `getter asString`): only these two have neither. So the base default `jAsString(self)` (`a.toString()`) reached their own `toString`, and the rung's `jTypeName(self)` did not. `Specification/basic-lib/objects.tex:117-122` (read `:100-140`) settles it against the rung tree: `RR32` does not textually represent `1.5`. It also broke the batch record's interop rule (`explorations/coordinator/CLIMB-BATCH-3.md:134`), and made the first report's sentence "a Java caller's `toString()` of a Fortress object now shows what `println` shows" false for these two classes.

**The decision (the judge's, JUDGE.md section 3), executed.** A value whose class renders itself in Java keeps that rendering; every other value renders as its Fortress type name. It is detected by the declaring class of `toString`, not by a table and not by the package: `defaultAsString` is bound, and `typeName` is kept pure for row 363's future `ilkName`. The judge's three rejected alternatives, and why: a package test (`getClass().getName()` under `…runtimeValues.`) carries a hidden precondition, that every class in that package overrides `toString`; two `getter asString()` declarations on `trait RR32` and `trait StringVector` are the shape the prelude uses for their neighbours (`CompilerBuiltin.fss:930` for `RR64`, `:1112` for `ZZ32Vector`), but `CLIMB-BATCH-3.md:164` forbids a new declaration in `CompilerBuiltin` in this batch and `FStringVector` has no usable `asString` to bind; folding the fallback into `typeName` would leave no pure type-name function for row 363.

**Where the judge's native was wrong against the source.** JUDGE.md section 5 step 1 gives the helper as `hasOwnToString(Class<?> c)`. With it, `ant compileAll` succeeds and the library rebuild fails in `CompilerBuiltin`: `java.lang.Error: No Fortress type (yet) for foreign Java type descriptor 'Ljava/lang/Class;'` from `FortressMethodAdapter.toImplFFFF` (`probes/judge-shape-wrapper-error.txt:6-8`). The native-wrapper generator reads the whole imported class (`compiler/nativeInterface/FortressTransformer.java:53`, `cr.accept(fa, 0)`) and wraps every method except `<init>`, `<clinit>` and those with bytes, shorts or arrays in the descriptor (`FortressMethodAdapter.java:215-225`, `SignatureParser.java:45-74`), private ones included, and throws for a parameter type with no Fortress counterpart (`FortressMethodAdapter.java:250-258`). Every private helper in an imported `nativeHelpers` class already has a mappable signature (`stringOps.fortressTypeName(String)`, `simpleIntLiteralArith.toBigInteger(IntLiteral)` and `fromBigInteger(BigInteger)`, `simpleIntArith.intCautiousNonNegativeMul(int, int)`, `simpleChar.charToHexString(int)`, `DeterministicRandom`'s three); the one with an unmappable type, `systemHelper.setFinalStatic(Field, Object)` (`systemHelper.java:25`), is in a class no Fortress source imports. So `hasOwnToString` takes the value, `fortress.AnyType.Any a`, and reads `a.getClass()` itself (`stringOps.java:79-81`); the logic is the judge's.

## Where the fix belongs

The map's rows are `explorations/coordinator/map/spec-to-implementation.md:223` (object declarations, `CodeGen.forObjectDecl`) and `:225` (value objects: "the `value` modifier has no representation meaning in codegen"), and the native mechanism is `explorations/coordinator/map/modules-and-phases.md:449` (B.12: `import java` + `nativeHelpers/` + `nativeInterface/`). The defect is where they meet: the compiled prelude's default is a native whose body bounced back into `asString`. Candidate homes:

- The code generator could emit an `asString` per object class. It knows a Fortress name statically but not a generic instance's arguments, which exist only when the class loader stamps the instance (`runtimeSystem/RTHelpers.java:18-50`); it would change every generated class for what one native reads at run time.
- `FValue.toString` given a life of its own is the judgement's alternative C, refused by the batch record for the interop rule (`explorations/reviews/default-rendering-judgement.md`, section 3).
- Changing `stringOps.asString`'s body in place, with no Fortress edit, is smaller, but that helper is bound for `Any`-typed values, and on a builtin such as `ZZ32` a type-name body would answer `ZZ32` where the value's own `asString` answers `1`.
- `RTTI.className()` (`compiler/runtimeValues/RTTI.java:53-58`) through `getRTTI()`: `FValue.getRTTI()` is `null` unless generated code overrides it (`FValue.java:17-19`), and the class name carries the same information without it.
- Declarations on the two natively implemented traits that lack an `asString` (`RR32`, `StringVector`): the repair round's alternative, ruled out for this batch by `CLIMB-BATCH-3.md:164`; recorded for the switch-over in the row-321 note.

So one bound native behind the prelude default, as the batch record prescribes. On the library route (POSITIONS 2026-09-21, the compiler prelude frozen) the edit is a body and an import line, sanctioned by Pavol's decision of 2026-09-22 (POSITIONS, row 321: "one native behind the compiled `Object.asString`"). ## The specification

`Specification/basic-lib/objects.tex` (read `:1-200`) declares `toString(): String` on trait `Any` (`:30`, rendered `:47`), says every object implements `Any`'s methods (`:19-22`), and gives `toString`'s general contract (`:117-122`): "returns a string that 'textually represents' this object. The idea is to provide a concise but informative representation that will be useful to a person reading it." Its property `x === y → x.toString() = y.toString()` is at `:34` (rendered `:51`). The implementation spells the method `getter asString()`; the interpreter makes `toString` an alias of it (`FortressBuiltin.fss:51`), and the team's 2008 api rendering of this chapter, `Library/incomplete/basic/Fortress.Core.fsi:12-29`, carries the same property under that name (`:24`). So the prose is not silent on the question as ledger row 321 records it ("`grep -rn asString …` finds nothing": the chapter's word is `toString`). It requires every object to have a working rendering, which the stack overflow violated. The contract cuts both ways: for an object with no rendering at all, the bare type name is concise and equal for identical objects because it depends only on the class; for a value that already had a rendering, `1.5`, the type name does not textually represent it, which is the refusal and the repair. The spelling itself is Pavol's decision of 2026-09-22, which the native implements. The note at `Specification/basic/expressions/typecase.tex:135-147` uses `x.toString()` as the rendering of an arbitrary `Object`, the same assumption.

Tuple *values* have their own rule (`objects.tex:161-185`: `(a, b)` with `", "`); it governs values, not the spelling of a tuple *type* argument, which follows walk's type rendering `(ZZ32,String)`.

- **The builtin-type rule is "drop the `F` in `compiler/runtimeValues/`", not a table**: it holds for all 17 value classes of that package.

- **The red-on-fix demonstrations for `XXXUnionReturnRungS`, `XXXUnionMethodRungS` and `XXXInferredStaticArgRungS`** were not owed (JUDGE.md step 7) and were run anyway, because each uses a check or a harness path the rung's first `XXX` file did not.
