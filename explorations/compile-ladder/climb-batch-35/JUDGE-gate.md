## The likely cause, a hypothesis

FACTS **F-354** ("Two compiles of one source by different builds of the compiler need not give the same bytes ... a result that depends on the order can come and go between builds") and ledger row 996 (the code generator's order follows the JVM's identity hashes; "No site traced") describe this failure's kind. O's new code runs for every trait and object of every compile, in the checker and in the code generator, and hashes tuples that hold objects hashed by identity before it returns empty; that moves the identity hashes of everything made after it on that thread, and so the iteration order of every identity-hashed set later in the compile. FACTS **F-232** names such objects: "`DeclaredFunction`s, entries of the checker's index and not nodes, still hash by identity". If the choice of the overloading at which a call of `denominator(self)` is compiled depends on such an order, where an abstract functional method and its implementation in the one comprised object are both candidates, this batch's build can take the other branch with no line of the batch at fault. This is a hypothesis: nothing was run for it. Steps 1 to 3 test it.

## What the right behaviour is

The call's argument has static type `QQ`. A declaration is applicable to a named functional call by the static types of the call's arguments (`Specification/basic/overloading.tex:36-44`, and its section on applicability; `Specification/basic/functions.tex:224-232`), and `Ratio`'s `denominator(self)` takes a `Ratio`, which `QQ` is not below. So the call is compiled at an arrow whose parameter is `QQ` or above, and the run-time dispatch reaches `Ratio`'s declaration. A call site whose descriptor takes `Ratio` is a defect of the compiler whatever order produced it. The 9 tests are right as written and change no line.
