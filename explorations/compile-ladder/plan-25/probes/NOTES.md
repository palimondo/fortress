## The files

- `count.sh`: F-32's classes counted again on a built tree, made from `plan-24/probes/count.sh`: the natives probe's scripts read from `4a46fb83a`, with `plan-24/probes/remap.py` run on climb batch 24's table of its base, so that each of the 173 bindings that name a helper gets the glue class it named before it moved; then `plan-23/probes/movable.py`, then the column `now`. Writes `classified.tsv`, `movable.tsv`, `moved.tsv` and `helpers-javap.txt`; it reads the tree and builds nothing, so it was run on the base build itself.
- `classified-base.tsv`, `moved-base.tsv`: `count.sh`'s output on the base build. The first equals climb batch 24's `plan-24/probes/classified-base.tsv` binding for binding, line numbers included; the second lists the 173 bindings that name helpers, each with the glue class it named before it moved. Rungs A and U change six `asFloat` headers, from `Float` to `RR64`, so the next planner's `remap.py`, which matches by file, owner and header, must match those six by file and line, which their one-line edits keep.
- `n3.py` and `n3-base.tsv`: N3's 158, the class C bindings of `classified.tsv`, one line a binding with its line, owner, header, glue class, the batch's rung or the home of what it waits on, the helper's Java signature, the types the compiled checker reads it at in walk's world, whether microGPT's lines reach it, and the glue class's computation read from `interpreter/glue/prim/`. - `codegen.sh` and `cgkinds.py`: the code generator over the distance stage's fourteen components, declaration by declaration, on the tree at `$FORTRESS_HOME`: the distance stage's shadows and driver (`tools/distance/`) with `-order full` and the flags of the probe of 2026-10-23 (`perf-probes/codegen-distance/REPORT.md`, section 1), whose own scripts were not kept. `cgkinds.py` counts each refused declaration once, at its first wall, by component and by the code generator's message. About 140 s on the base, 210 s with the helper strings on glue classes.
- `apply25.py`: writes a rung's text, or the planner's sample of one, into a tree at the base, by exact text, each edit matching once: `R`, `U` and `A` the whole texts; `N`, `D` and `P` the samples; `asfloat-control` `Int`'s `asFloat` moved at its header `Float`.

## How to run them again

From a worktree seeded from a base build at the batch's base, set up as the `fortress-repo` skill's `build-and-caches.md` says:

    explorations/compile-ladder/plan-25/probes/count.sh $PWD tmp/count
    python3 -B explorations/compile-ladder/plan-25/probes/n3.py tmp/count/classified.tsv ProjectFortress/src/com/sun/fortress/interpreter/glue/prim > tmp/n3.tsv
    explorations/compile-ladder/plan-25/probes/codegen.sh tmp/cg                     # in the background; prints the table
    python3 -B explorations/compile-ladder/plan-25/probes/apply25.py $PWD R U A      # or: git apply --3way the patches in the gather's order
    ant compileAll        # then the library order, before a compiled test
    explorations/coordinator/tools/distance/run.sh tmp/distance.txt tmp/distance        # in the background
    explorations/coordinator/tools/checker-count/run.sh tmp/count.txt tmp/count-scratch # in the background
    ant testSystem; ant testSpecData                                                   # in the background

The control of the code generator's run puts the 173 helper strings back on their glue classes for one run, from `tmp/count/moved.tsv` (`glue_before`, `helper_now`), the string searched from the header's line through three lines after it, since a header can span two lines. The `asFloat` control is `apply25.py <tree> asfloat-control` with the distance stage after it.

The value probes were scratch programs, not kept, each run on the old code (`tools/old-fortress.sh /home/user/fortress-base25 <tree>/tmp/old-caches P.fss`) and on the text (`bin/fortress P.fss`), their outputs compared with `diff`: `ValR`, R's ten at the bounds and at pairs of signs; `ValU`, `UnsignedLong`'s getters and `NN64`'s prefix `DOTMINUS` at seven values, and `NN32`'s `CHOOSE` at 128 pairs, each overflow caught; `ValA`, the six `asFloat`s at their bounds; `ValN`, `ValD` and `ValQ`, the samples of N, D and P; `ZeroZZ32`, `ZeroZZ64`, `ZeroNN32`, `ZeroNN64` and `ZeroZZ`, `REM` and `MOD` by zero in a `try` catching `DivisionByZero`. Each was a do-block of typed bindings and `println` lines, written by a script: a list literal at a declared `List[\ZZ32\]` is an `ArrayList[\Int\]` under walk and does not bind (row 364's kind), so the lists were left out. The compiled sample, `SampleRUACompiled` and `SampleNDQCompiled`, each with a `.test` of `link`, `run` and `run_out_contains=PASS`, ran through `ONE_JVM=1 explorations/compile-ladder/climb-batch-N/merged-tests/junit.sh samples ProjectFortress/compiler_tests SampleRUACompiled.test SampleNDQCompiled.test` after the library order on the combined tree, and on the old code through `old-fortress.sh <base build> <caches> junit <the two .test files>`; the compiled prelude's `assert` has no form over two `ZZ64` values, so those comparisons are `assert(a = b, message)`.
