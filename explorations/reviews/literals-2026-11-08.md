## 1. What the sources say

### 1.1 The specification (`Specification/`)

- **Integer numerals.** The Working Draft gives a numeral the types `NaturalNumeral[\n,10,v\]`, `Literal[\v\]` and `Numeral[\n,m,r,v\]` (`basic/expressions/literals.tex:83-129`). No library declares these types. The revival's box says that the library gives every numeral without a radix point the type `IntLiteral`, which extends `Number` and which each integer type, `QQ` and `RR64` coerce from (`:149-165`, P-76). `IntLiteral` is in the text only because of that revision.
- **Float (compound) numerals.** "A numeral is simple if it does not contain a '.' character; otherwise ... compound" (`basic/lexical-structure.tex:1146-1147`). The text says these points:
  - Their type is `RadixPointNumeral[\n,m,10,v\]` (`literals.tex:110-129`).
  - They "are actually rational literals; thus 3.125 has the rational value 3125/1000" (`:179-180`).
  - "Numerals are not directly converted to any of the number types because ... we expect them to be polymorphic ... converting it immediately to a floating-point number may lose precision" (`:132-141`).
  - "Library define coercions from numerals to integers (for simple numerals) and rational numbers (for compound numerals)" (`:146-148`).
  - The revised numbers chapter names the coercion into `RR64` "from integer numerals" only (`basic-lib/numbers.tex:43`).

  **So: is `FloatLiteral` part of the specification? No.** The text names it only in Appendix I: in the list of natives (`appendices/changes.tex:4673-4674`) and as a departure of the interpreter (`:4045-4048`). The revision gave no type to compound numerals. That is a gap in the revision.
- **String literals.** Four statements bear on them:
  - "A string literal has type String" (`literals.tex:57`).
  - "Literals are values; they do not require evaluation" (`:25-26`).
  - `String` is among the "simple standard types for literals", and "Values of these types are immutable" (`basic/types-vals-vars.tex:572-581`). Which types "these types" covers is not clear.
  - "The only operation on literals that produces a new literal ... is concatenation ... "foo"||"bar" yields "foobar"" (`basic/expressions/constant.tex:81-85`).
- **Kinds of objects** (`basic/objects.tex`):
  - "numeric literals ... are value objects" (`:41-46`).
  - "Value objects with the same type, environment and fields are indistinguishable" (`:38-39`).
  - "A new object reference is created whenever a reference object is constructed" (`:51-53`).
  - "Reference objects include strings" (`:55-56`). This is the revival's text (P-168), in its box `revival-object-kinds`.
  - Strict equivalence: different dynamic types give `false`; value objects compare field by field and binary words by their bits; references compare by identity (`:435-460`).
- **Static arguments and identity of types.**
  - `id(3)` "instantiates `id` at the numeral's own type" (`basic/inference.tex:183-187`, revival text).
  - A type parameter that only numerals fix, where the conversions tie, becomes `ZZ32` (`:299-317`).
  - Two types are identical only if their names and static arguments are identical (`types-vals-vars.tex:51-52`).
  - A numeral at an `Any` parameter is not coerced: coercion happens only where the parameter type "is exactly the type U" (`basic/conversions-coercions.tex:93-97`).

- **Walk results:**

      S1 two occurrences: SEQV false; = true
      S2 one occurrence evaluated twice: SEQV false
      S3 literal vs computed: SEQV false; = true
      S4 typed binding vs a second literal: SEQV false; with itself true
      S9 VCell of two literals: SEQV false; = false

- **Compiled results:**

      C1 two literal occurrences sEquiv false; === true; = true
      C2 one occurrence twice sEquiv false
      C3 literal vs computed sEquiv false; === true

  The prelude's `===` answers `true` through `=` (row 908) until the switch-over.
- **Run-time type, dispatch and generics, under walk.**

- **Tuples.** Two four-tuples of literals are not `=` (S13: `four-tuple of literals = false`; row 923).

### 2.4 Where the results depart from the specification, and where from what a programmer expects

- **Against the specification:**
  - Walk and the one library keep a float numeral at a typed `RR64` place. By the specification it is coerced, and so is `SEQV` a computed value (§1.1).
  - `q: QQ = 0.5` is refused and `1/2 = 0.5` is `false`.
  - Two `SEQV` values print differently (E1).
  - Under walk, generics are made at `Int` and not at the numeral's type or the trait (row 364).
- **Against what a programmer expects, but not against the specification:**
  - `"ab" SEQV "ab"` is `false` on both paths. The specification does not say whether a literal is one object, and "Literals are values; they do not require evaluation" leans toward one. The restart says that literals have no identity.
  - Compiled, `3 SEQV z` is `false`. That is the specification's design (numerals polymorphic, kept at `Any`), and walk will reach it after P-12.
- **Not specified:** how a numeral prints.

## Summary

Each path turns a literal into a value by its own code. Walk makes a new `FString` for every evaluation of a string literal. It gives an integer numeral the class `Int`, `Long` or `BigNum` by its magnitude. It keeps a float numeral as a `FloatLiteral`, which carries its text. The compiled path wraps each string literal in a new `FJavaString`. It boxes numerals as `FIntLiteral` and `FFloatLiteral`, which the checker types as `IntLiteral` and `FloatLiteral`.

How this meets equivalence:
- **Strings.** `"ab" SEQV "ab"` is `false` on both paths, even for one literal evaluated twice. `=` compares text. Generics are made at `FlatString` under walk and at `String` compiled. An empty string's `SEQV` depends on where it came from.
- **Integers.** Under walk `3 SEQV z` is `true`. Compiled it is `false`, which is the specification's answer.
- **Floats.** Under walk, `y: RR64 = 0.5` stays a `FloatLiteral`, so it is not `SEQV` a computed `0.5`, and neither are value objects that hold it. Compiled, it converts today. After the switch-over it will not, by reading, because the one library declares `FloatLiteral` below `RR64`. Walk prints a numeral's text, so two `SEQV` values print `2.5` and `2.50`. `q: QQ = 0.5` is refused.

**Against the specification:**
- Float numerals are not converted at typed places (`literals.tex:132-148`).
- `QQ` does not coerce from a compound numeral.
- `SEQV` values print differently (`objects.tex:38-39`).
- Walk makes generics at `Int` (row 364).

**`FloatLiteral` is not in the specification.** The revision gave compound numerals no type.

**Against expectation, but not against the specification:**
- Literal strings are not `SEQV`. The text does not say whether a literal is one object, and "Literals are values; they do not require evaluation" leans toward one.
- `3 SEQV z` is `false` compiled.

**New evidence.** The 2012 restart (`literals.tick:14-29`) says: "All literals represent value objects; therefore their values do not have object identity". It also says a numeral with a '.' is a `QQ`. No note of the record cites it.

**Changes 39, 41 and 42** record these representation choices as if the language gave them. In change 39, the literal-string sentence is placed beside the cases it says to assert as correct. Change 41's example rests on the float representation. Change 42 says no row holds the float `false`, while Appendix I calls it a departure. Change 40 records a walk defect, with its row. Changes 43 and 44 are not the pattern.

- **S-b:** intern string literals and keep P-168. Measured on prototypes: walk about 3 lines; compiled about 4 lines (Java `==` on the carried string) or about 15 lines (an intern table). No measured test flips, and the team's `seqv.fss:22` passes again.
