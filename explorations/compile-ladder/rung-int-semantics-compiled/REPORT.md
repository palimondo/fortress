## 4. What changed, and the decisions

**Decision: the shift rule is in four new natives**, not in Fortress bodies over `<<` and `>>`. The rejected alternative was a four-branch body per operator (`if other >= 32 then 0 elif other >= 0 then self << other elif other <= -32 then self >> 31 else self >> (-other) end`), which needs no Java. Natives were chosen because the team's precedent for signed counts is a native (`intShift`), one native call is the machine shift the decision asks for, and a body adds three compiled comparisons and a negation to every shift.

**Decision: the natives are named in the Bit family** (`intBitLeftShift` beside `intBitNot`/`intBitAnd`; the decision calls them "bit operators"). The rejected alternative was `...ByIntSaturating32` after the neighbouring `...ByIntMod32`; in these files "Saturating" means clamping to MAX/MIN (`intSaturatingAdd`), which is a different thing from a shift saturating to `0` or `-1`.

**Decision: `Math.multiplyExact` replaces the guard-and-divide check in `longOverflowingMul` and `longSaturatingMul`.** The rejected alternative, which the batch record also offered (`CLIMB-BATCH-3.5.md:35`), was testing `Long.MIN_VALUE` plus a zero line. The `int` multiplies widen to `long` and have no guard, so they were not touched.

**Decision: the four saturating natives no prelude body calls** (`intSaturatingDiv`/`Abs`, `longSaturatingDiv`/`Abs`) are asserted by importing them into the test (`IntSemanticsRungB.fss:2-5`, `:135-142`), as `library_tests/IntegerChoose1.fss:13` imports a `simpleIntArith` native. **Signed narrow truncates**, because the rider set at launch is "truncates": `ZZ64.narrow` uses `jLongWrappingToInt` and all five of rung W's assertions are reversed. The tail's sentence for "unchanged" is the conditional for the other value and was not applied.
