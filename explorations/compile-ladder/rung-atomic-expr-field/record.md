## For FACTS

**A compiled object's `var` field lives in a cell that the object holds, and an atomic expression is its body in an atomic block.** On the compiled path a `var` value parameter or `var` field of an object is a `MutableFValue` cell in a `public final` JVM field, made by the constructor; each read and write checks `BaseTask.inATransaction()` and goes through the transaction or the cell, by the code of a top-level `var` (`VarCodeGen.MutableFieldVar`, a `MutableStaticBinding`), and a loop body or a function expression in the object's method captures the cell. A field without `var` holds its value and has no check. `atomic e` is compiled by `forAtomicBlock` on the block that holds `e`. What it means: a change of the transaction's variable code reaches fields with no second edit, and a new kind of nested context must capture a var field's cell as it does a top-level `var`'s. Tests: `compiler_tests/AtomicFieldCompiled`, `compiler_tests/VarFieldCapturedCompiled`, `compiler_tests/AtomicExprCompiled`. Detail: `explorations/compile-ladder/rung-atomic-expr-field/REPORT.md`, "What changed and why" and "The bytecode".

## Revival change

### The change

- **An atomic expression compiles.** The team's code generator compiled `atomic do ... end` and had no case for `atomic e` over any other body: its `defaultCase` refused the node, 'Can't compile AtomicExpr' (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:1776` and `forAtomicBlock` at `:1835`, at `c1ce2a35e1`). The tree now compiles `atomic e` as the atomic block that holds `e`, with the value of `e` (`compiler_tests/AtomicExprCompiled`). The reason: the specification gives the atomic expression its body's value and makes all its reads and writes one step (`Specification/basic/expressions/atomic.tex`, section "Atomic Expressions"), walk runs it, and the one library writes it (`Library/OneShotFlag.fss:18`). Where the body's value is a numeral at a place of declared type, write `atomic do ... end`: the checker refuses `atomic if c then 1 else 0 end` there, and `atomic 1` fails the JVM's verification (ledger row NEW-A-1).
- **A compiled object's `var` field is tracked by a transaction, at the cost of a check on every access.** The team's code generator read an object's field with a bare `GETFIELD` and wrote it with a bare `PUTFIELD`, a `var` field as any other (`ProjectFortress/src/com/sun/fortress/compiler/codegen/VarCodeGen.java:174-236` at `c1ce2a35e1`), so an `atomic` block did not track it: 40,000 `atomic do n := n + 1 end` on a field from a parallel loop gave 34,631 to 39,313 at four threads. The tree now keeps a `var` value parameter or `var` field in a cell that the object holds, read and written as a top-level `var` is; each access, outside `atomic` too, first asks whether a transaction is running (`compiler_tests/AtomicFieldCompiled`). A field without `var` is as it was. The reason: mutable fields of reference objects are mutable locations (`Specification/basic/evaluation/memory-ops.tex`, section "Memory and Memory Operations"), an atomic expression's reads and writes are all one step, and walk is exact on the same program.
- **A loop body or a function expression in an object's method works on the object's `var` field, not on a copy.** The team's code generator gave each task and closure a copy of a field's value, made when the task or closure was built, so a write from a loop body in the object's own method was lost, at one thread too, and a function expression read a stale value: `for i <- 1#k do atomic do n := n + 1 end end` in a method left `n` at 0. The tree now gives the task or closure the field's cell (`compiler_tests/VarFieldCapturedCompiled`). The reason: the measured failure, and walk's result on the same program.
- **Do not give a `value` object a `var` field in a compiled program.** The specification forbids it (`Specification/basic/objects.tex`, section "Value Objects") and nothing refuses it; with the field in a cell, two such objects built alike are no longer strictly equivalent, `V(1) === V(1)` is `false`.
