# Pavol's positions, decisions and known ground

## The goal

- P-7 **The goal is to finish what the designers intended, measured by one program, microGPT, compiled to JVM bytecode and running fast.** What the designers intended is judged by the specification in `Specification/`: the team's Working Draft of February 2011, as the revival revises it, with the Types chapter of the team's 2012 restart cited beside it (P-25). The revival revises the specification to reconcile contradictions: where the team's later work, in the compiler or in the papers on types, contradicts the original text, the text is updated to follow that work. The language is not redesigned. The specification is a living document that states each change that the revival makes (P-95 says how a change is recorded). A pure-Java microGPT is the baseline that compiled microGPT is measured against: the optimal result, the one to aim at.
- P-8 **Where the designers' own sources, the specification, the papers, the library and the implementations, give no answer, the curator decides by the goal, a compiled microGPT running fast, not by type-theoretic purity, and he stays true to the spirit of Fortress.** On the way to a compiled microGPT, he accepts the language's unfinished corners as they are, so that the work does not stall in theory. He has not read the specification, the papers on its type system or the library, and he takes the designers to have known more than he does.
- P-9 **The revival searches for the most readable expression of the microGPT algorithm.** C4 is the flat microGPT program (`explorations/run-c4/src/MicroGptFlat.fss`), whose data layout follows Aaron Hsu's flat style of APL (P-29: C4 is not edited for speed before microGPT runs compiled). In C4, the polishing happens in the vocabulary, the array operations that the model's lines call: `FlatArrays.fss` beside C4, and what of it has moved into the standard library (P-27: what a program builds that a more mature library would hold goes into the library). P-87 holds the limit: the model's text is the notation, and a change to a model line is shown to the curator as a diff first. C4 is the target form of the APL microGPT program (`explorations/apl/mg/MicroGptApl.fss`): the APL program is written so that each of its lines expands into the line that C4 writes by hand. C4 writes its hyperparameters as tuple bindings, such as `(nEmbd, blockSize, nHead, headDim, vocabSize, bosId) = (16, 16, 4, 4, 27, 26)`, the form to which the APL sub-language (P-10) expands a strand assignment, APL's binding of several names at once. The one-line form, declarations separated by semicolons such as `nEmbd = 16; blockSize = 16; ...`, is not used: the APL sub-language has no use for it.
- P-10 **The APL side quest is closed: its sub-language covers only what the APL microGPT program needs, and the parts of APL that it left unbuilt, tacit functions, characters and nested arrays, are not pursued.** The side quest built an APL sub-language in `explorations/apl/`: a DSL grammar that expands APL text into Fortress code over Fortress's native arrays, not an interpreter of APL. Its microGPT program, `explorations/apl/mg/MicroGptApl.fss`, stays in the microGPT check under walk (P-30: the check's limit of one minute; what the check runs: the `fortress-repo` skill, `references/interpreter.md`, "The model program").
- P-11 **The 2D notation is a gimmick: no work on it unless the curator asks.** The 2D notation is Fortify's rendering. Fortify (`Fortify/`, run by `bin/fortify` and `bin/fortick`) typesets Fortress source as mathematics in LaTeX, for the specification and the papers. Taken as programming syntax, such a rendering fixes one view of a computation, though the same mathematics can be written in many ways. APL, with one symbol for each transformation of the data, expresses a computation better. The rendering is presentation only, off the revival's path, and no argument in favour of Fortress. The verdict is on that typesetting only: the Unicode operators, such as `∑` and `×`, are the language's own syntax.
- P-12 **After the switch-over, walk runs the compiled type checker on its programs, and then uses the static coercions that the checker inserts.** The curator wants the checker usable on the programs that walk runs. Today `fortress typecheck` checks a program only against the compiler's prelude, so it is no check of walk's programs (F-9 holds this fact). Walk is not changed for this before the switch-over. After it, walk runs the checker on its programs and so gains their static types; F-9 and F-290 say what walk and the library lack for that step. Walk then uses the static coercions that the checker inserts, in place of its choice on the run-time value (P-59, walk's choice of coercions until the switch-over).

## History he knows (do not re-explain)

- P-17 **Unboxed doubles and arrays of unboxed doubles are required: without them the revival misses its point.** Why: a language meant for high performance cannot box its numbers. Today the code generator boxes every number: an `RR64` value is an object of the class `FRR64`. In Java models of microGPT's three array kernels, the dot product, the matrix product and the row lift, boxing is the main cost (F-11 holds the measurement). How arrays store doubles, as `double[]`, is P-84's decision.
- P-19 **The tree is not described as the third-party port's migration grafted onto the team's history.** The port is a third-party port of the tree to Java 9, which commit `8fe1daa8f` copied onto the team's last commit (the `fortress-repo` skill, `references/records.md`, "The repository's history"). By history, `main` descends from that commit. By content, most of the port's files are removed or redone, and only one piece of the port's code still runs: the `FTypeArrayList` fix for the JDK 8 `TreeSet` crash (F-165). Why: the tree is not built on the port, and the record must not lead anyone to think that it is. The files that still describe the tree so wait for the lineage cleanup; `coordinator/lineage.md`, "Files that still repeat it", lists them.

## Decisions on record

### The standard and the sources

- P-25 **`Specification/` stays the standard, and the Types chapter of the team's 2012 restart is cited beside it.** The restart is a new specification that the team began in 2012 and left unfinished (F-166). Where its Types chapter, `Documentation/Specification/Prose/Language/types.tick`, covers a topic, a worker cites it beside `Specification/` as the designers' later word. On the rules that the revival revises, such as the exclusion rule, the chapter is the designers' latest intent, which the goal is to finish, and `Specification/` is revised to follow it. Three of the chapter's passages bear on the specification; P-97 holds how the revision uses the first two. It names the exclusion rule "instantiation exclusion" and gives it in two parts: which instantiations of a generic exclude each other (`types.tick:355-360`), and, in its note, a rule on trait declarations (`:361-376`). The revised `Specification/` takes that form: the first part in its chapter on types, the second in its chapter on traits. It adds a `covariant` modifier for a trait's static parameters, which neither path implements and which is future work, off the path to microGPT (P-62). Third, it says that `Bottom` cannot be written in a program, as `Specification/basic/types-vals-vars.tex` already says of `BottomType`.
- P-26 **Where the type group's later positions conflict with the specification's early text, the later positions win.** The early text was a wish. The type group, the part of the team that built the type checker and the compiler, then worked to make the language run, with performance as the goal and specialization a must, and learned what is feasible. Specialization, in the type group's design, is a special version of a generic function for one instantiation, such as `tail(x: List[ZZ])` beside `tail[X](x: List[X])`, which dispatch chooses at run time. Where the two conflict, the specification is revised to follow their later word (P-95 records each change with its reason). Their later word includes the exclusion rule, specialization kept, the number types of the compiler's prelude made siblings in 2009 and 2010 (P-43: the library's numbers are flat in the same way), Karl Naden's 2012 write-up "The Return Type Rule and Generics" (`Papers/Types/journal/justificationOfRTR.tex`) and the type group's POPL 2019 paper (F-166). The implementers' later word also outweighs unfinished text. The revival does not second-guess them: it knows less than they did.
- P-27 **What a program builds that a more mature library would hold goes into the library, in the library's own way.** A program written on this library has a part that states its algorithm, and it can have a part that builds domain-independent machinery that the library lacks, as both microGPT programs do. A form of that second part goes into the standard library when, on reasonable judgment, it is not an extension of the program's own domain; a form that the library has for one number type, rank or sibling trait and lacks for another is the plainest case. Whoever writes it there first studies how the library does the same kind of thing, and follows that pattern, such as its `excludes` clauses. This rule governs how the library is extended; it does not choose between two of the team's designs of the language (P-26).
- P-28 **Fleshing out the standard library is a very important task.** Its next layer is algebra: traits such as `Ring` and `Field`, which the library does not declare yet, and what machine learning's matrices and tensors need, so that the library's algebraic traits, such as `AdditiveGroup` and `MultiplicativeRing`, reach them too. Why: the curator wants those matrices and tensors to have the mathematical rigour that the library's way of building its types promises. The work edits the standard library itself, in `Library/`, not a separate tree of the revival's own outside it (P-27, how the library is extended). It is parked off the path to microGPT compiled. Two matrix ideas of his wait beside it: square matrices of one size as a multiplicative ring, and diagonal matrices of one size as a ring whose product commutes.
- P-29 **Walk's speed is irrelevant to every judgement of Fortress's performance.** Walk is far slower than Python's interpreter (`explorations/microgpt-port.md`, "Step-0 results", a measurement of 2026-08-23). Fortress's performance is judged on the compiled path, once the compiler runs programs. So no performance decision rests on walk's timings. In particular, until microGPT runs compiled, C4, the flat microGPT program, is not edited for speed. The gate never runs microGPT's two programs, C4 and the APL-style program, because they run too long to be tests. Why: walk is the unoptimised path, as a debug build is in Swift, where performance is not judged either.
- P-30 **The check of microGPT under walk after a batch must take less than a minute.** A batch is a set of tasks, each called a rung, that agents build at once and land together. The minute is the curator's goal, for a check that runs only about two forward-and-backward passes of the model, not a full training, and compares the results with reference values. That is enough to show that the model's mathematics still works, and that the library's changes, such as those to the arrays, did not break it. A slower check is to him a waste of time. The commit stage of each batch, the step that lands its changes, runs the check as `explorations/coordinator/tools/mg-run.sh`, the quick versions of microGPT's two programs at once, outside the gate.
- P-32 **The record's maps are kept current and used, so that nothing that the record holds is worked out again from scratch.** The maps are `FACTS.md`, `INDEX.md` and the territory map, `explorations/coordinator/map/`. The territory map surveys the repository down to where the team wrote the intent of each design. Part of that intent is written only in the papers under `Papers/`, not in the specification. So the map covers the papers too, and shows where to look up a design's intent. `INDEX.md` is read whole at the coordinator's boot, at the start of each session and after each compaction, and each worker's brief carries a mission briefing from the territory map, not the whole map. The territory map's surveys date from 2026-09-16 (its README), so a status or a line number in them can be stale.
- P-33 **The work toward microGPT compiled follows the phases, in the order that the curator approved.** These phases are steps of the work, not the compiler's phases, and they are numbered 3 to 6, after two earlier ones. Phase 3 ends when the compiled checker reports no error on the apis and components of the interpreter's library that the distance to the switch-over counts (F-53 defines the distance, says what it counts and holds its value). The library's other components are not part of phase 3; F-290 counts their errors. Phase 4, the switch-over: first the natives, the library's `builtinPrimitive` bindings made to run on the compiled path, then the compiled path reads the interpreter's library and the compiler's prelude is deleted; phase 5, microGPT compiles: its static types, the array design and the code generator's open gaps; phase 6, microGPT runs fast. Code-generator work goes on beside that order, under either library (P-37). Row 320, an api implemented by a component of another name does not link, is part of the switch-over's design.

### The one library and the compiled checker

- P-37 **One library, the interpreter's, is the library that the compiler checks.** The interpreter's prelude, `FortressLibrary` and `FortressBuiltin`, becomes the compiled path's prelude in place of the compiler's own, and the compiled path reads the interpreter's library with it. Why: the switch-over spares porting the interpreter's library into the compiler's; the revival develops the checker until it accepts that fuller library. The curator sees the compiler's prelude, its own library files `CompilerLibrary`, `CompilerBuiltin` and `CompilerAlgebra`, as a bootstrap to remove. So no declaration is added to the compiler's prelude, and at the switch-over its three files are deleted and their tests kept (P-38 says which tests are respelled; F-293 holds the compiler's fourth file, `CompilerSystem`). The decision settles which files survive, not the designs inside them: the one library may take a design of the prelude's, as it took the prelude's flat shape of the number types. This decision does not stop work on the code generator, which is compiler work under either library.
- P-38 **The compiler prelude's defects are not repaired: they go with it at the switch-over.** Its `Maybe` block and its `REM` guard `if other = -1 then 0` stay as landed until the prelude is deleted, and their tests stay. Then the compiled tests respell its reversed wrapping and saturating operators (row 348), `ZZ64`'s compiled shift closes (row 381), and the specification's `shift` reaches the compiled path (row 383). `XXXShiftDeclRungI` is then promoted, and the switch-over batch finds the compiler tests that bind `shift`, a reserved name from then on.
- P-39 **Every batch's gate measures the checker count, and its total never turns the gate red.** A batch is a set of tasks, each called a rung, that agents build at once and land together. Its gate runs the gate's steps on their merged tree, and then the checker count, as step 8 (`explorations/coordinator/climb-batch-workflow.md`); the gate of `fortress-repo`'s gate part has no such step. The checker count and the distance to the switch-over both count the compiled checker's errors on the interpreter's library. The count stops where the checker crashes or meets an error that it cannot get past; the distance counts every error, over all apis and components (F-53 defines both and holds their values). A rise of the count's total is reported and never fails a batch on its own. The count's stage can still turn the gate red on the faults that F-66 names. One is a checker crash that no rung of the batch listed in advance as expected, in the field `expectedCheckerCrash` of the batch's manifest, the part of the batch's script that declares each rung's task. The gates of batches whose work drives the distance down also measure the distance, in a stage that only reports. Why: the distance's full measurement takes far longer than the count, and a batch pays for it only when the distance is the number that it tries to move.
- P-40 **Sizes are checked, and a size that inference leaves unknown is an error only where it is used.** A size is a `nat` or `int` static parameter, such as the length of an array in its type. The compiled checker checks sizes, and refuses a size beyond `NN32` or `ZZ32` (F-140, the bound on both paths). Wherever the array design, the compiled path's design for arrays (P-85), creates a JVM array, it checks the length there, at run time, and refuses one over 2^31-1. A size that inference leaves unknown is an error only when it reaches a type, a name or a value. So a declaration may declare a size that none of its types uses, and pass. A call that cannot fix a size of the declaration that it would choose is refused, also inside an overload set, instead of passing over that declaration. In the rule that no type extends two different instantiations of one generic trait, two instantiations differ when any static argument but an operator differs, so `Vec[\3\]` and `Vec[\4\]` are two; boolean arguments count too once the checker has boolean parameters. A size used as a number, as in the range `0#n`, converts to `ZZ32` where one is needed, as a numeral does. The 17 vector and matrix operators of the `FortressLibrary` api declare only the sizes that their types use, the change of `explorations/perf-probes/array-sites/e3-rebased.patch`. It finishes the team's own fix of 2008, which removed those sizes from the component only. The JVM length check waits for the array design; under walk such an array dies with a raw Java exception (row 527). The checker still passes over a declaration whose unfixed size occurs in its own parameter type (row 400). The checker compares no boolean arguments (row 406).
- P-41 **On the compiled path, a size static argument travels at run time as a descriptor object, as a type argument does.** A generic type's descriptor has a field for each of its static parameters that is not an operator. The team's code generator already emitted that field for a size, with nothing to put in it, and the size's descriptor fills it. Each size value, such as the 3 of `Vec[\3\]`, has one descriptor, which `RTTIsize.of` takes from a table; no Java class is written for it. This is the team's pattern for instantiating types, applied to numbers. An operator static argument, by contrast, stays a name known only at compile time (F-39, how both paths carry it). The curator sees no need for an operator argument to be carried at run time the way types and sizes are. F-129 holds what runs and its open rows.
- P-42 **A type parameter declared without a bound has the implicit bound `Any`, not `Object`.** `Any` holds tuples, functions and `()`, which `Object` does not. The library instantiates its generic containers at tuple types: its arrays indexed by pairs, such as `(ZZ32,ZZ32)`, are among them. The specification states the bound `Any`, with a callout that records that the Working Draft of February 2011 said `Object`. The compiled path departs from it until the switch-over, which ends the departure: while it uses the compiler's prelude, it bounds such a parameter by `Object`, and so refuses a generic instantiated at a tuple (row 412).
- P-43 **The exclusion rule stays, and the number tower is flat (route A).** The compiled checker keeps the multiple instantiation exclusion rule. So the library's numbers are flat, as the team (Chase, Ryu, Maessen and Allen) flattened the compiler prelude in 2009 and 2010. The fixed widths, `ZZ`, `QQ` and `RR64` are siblings under `Number`, each with its own algebra, and `Number` has no catch-all operators. Why: the flattened prelude is the team's last record of the Fortress way, and its route leads to the POPL 2019 paper, which keeps the rule. He cares that specialised code runs fast, not how a specialisation is chosen. F-46 prices a return to route C.
- P-44 **`AnyIntegral` stays closed by its `comprises` clause, and the compiled checker reads the clause as the team's 2012 texts do.** The library's `AnyIntegral`, whose `comprises` clause lists the five integer types `ZZ32`, `ZZ64`, `ZZ`, `NN32` and `NN64`, stays closed. Beside the clause stays a comment in the team's `NOT YET` form, by which the team's library records a clause that it cannot write yet: here `comprises Integral[\I\] where [\I\]`, whose `where` form is not built. `Integral[\I\]` extends `AnyIntegral` and is not in the list. The checker accepts such a generic trait below a closed trait when every type that the checker knows below it is listed. The clause's text in the library, and walk, stay as they are. Why: the team's 2012 texts, Luchangco's Types chapter and Welterweight, are its later word (P-25), and by them the clause is right as written. The rule leaves a hole that every way of closing `AnyIntegral` shares, except the team's 2008 way, a `comprises` clause on `Integral[\I\]` itself: a program's own subtype of `Integral`, declared in another component, is accepted although no listed type is above it. Row 487 records the hole, and this decision does not close it.
- P-45 **Overloaded declarations may differ in their static parameters.** The specification drops its sentence that forbids this, and keeps it as superseded text. It states instead the overloading model of the type group's 2011 paper (`Papers/Types/`), which the compiled checker already used. The checker keeps the paper's three rules: No Duplicates, Meet and Return Type. It checks the Return Type Rule over every instance of a generic declaration that the argument types allow, not over one guessed instance. One rule of the old sentence survives: if one generic declaration is more specific than another, their static parameters must line up position by position, as Java's rule for overriding a generic method requires. The compiled checker tests it only where the two declarations have as many static parameters of their own (F-75). Walk chooses among overloads by the parameter types that each declaration declares, not by the order in which they are written. At load, walk judges each pair of two generic declarations by the checker's rules on their declared parameter types. It does not refuse a pair only because none of their parameter types exclude, as when one declaration is more specific than the other. Walk and the checker must accept the same pairs. The library repairs, by declarations of its own, the overload sets that the checker refused, and no line of microGPT's two programs changes. Where walk or the checker still judges a pair against these rules: walk compares two functional methods of a generic trait or object on the instance that a call makes (F-26); both paths refuse the paper's own valid example (row 539); walk refuses two generic functional methods of a trait without static parameters whose declared domains lie one inside the other, and fails at a call on such a pair in a generic trait (rows 779 and 780); and walk and the checker disagree on four kinds of pair (rows 759 and 786 to 788).
- P-46 **A conversion only makes a call possible: it never changes which declaration runs when one already fits.** The declaration that runs is chosen on the parameter types that each overload declares: first those that apply, then the most specific of them (P-45). A generic declaration applies if some type within its bounds takes the arguments. Only then is the chosen declaration instantiated by promotion: at the narrowest type into which its arguments coerce (P-74). So beside `op(a: Any, b: Any)`, `op[\T extends Number\](a: T, b: T)` applies to a call with a `ZZ32` and a `ZZ64`, at `T = Number`. It is the more specific, so it runs, at `ZZ64`. Why: the curator wants fast generic code that a JVM can specialise. His own broader rule is not taken: to apply any conversion that reaches a specific declaration, and to fall back to a plain one only when none does. Walk and the compiled checker both infer static arguments with coercion, by the same promotion. The compiled path inserts the conversions statically. P-49 gives the order in which the checker tries a call. Row 537: the compiled dispatch between two generic declarations of one name with different bounds.
- P-47 **Each integer type declares its own `MIN`, `MAX` and `MINMAX`, instead of relying on those that it inherits from the generic order traits.** The integer types are the five that `AnyIntegral` lists: `ZZ32`, `ZZ64`, `ZZ`, `NN32` and `NN64`. Through `Integral`, each inherits the three operators from `StandardTotalOrder` and the `StandardMin`, `StandardMax` and `StandardMinMax` that it extends. `a MINMAX b` is the pair `(a MIN b, a MAX b)`. The `MAX` that a `ZZ64` inherits types `self` as the order trait, so neither it nor `QQ`'s `MAX` is more specific. Under walk, `b MAX 1` for a `ZZ64` `b` would then stop the run with "Ambiguous coercion". With their own declarations, these operators answer at the type that their arguments promote to (P-74), as `b + 1` does. Why: it is the library's own device. `QQ`, `RR64` and the compiler's prelude declare all three, and the specification's `ZZ` declares its own `MIN` and `MAX`.
- P-48 **A type parameter that a call's arguments do not fix takes its bound, never `Bottom`.** The arguments leave a parameter unfixed when it occurs only in the result type; when two arguments meet at it with no narrowest type into which both convert (a `ZZ32` and a `ZZ64` have one, `ZZ64`, by P-74); or when dispatch, at run time, picks a generic declaration and must choose the instance to run. Its instance is then the intersection of its upper bounds (`Any` if it has none). At checking, that is narrowed by what the call's expected type (P-49 defines it) requires of the declared return type; at run time, by the static type that the checker gave the call. It is never `Bottom`, never the union of the arguments' types, and never the value's type alone. The rule sets the instance, not which declaration runs (P-46). Why: the rule is the team's later word, from the POPL 2019 paper on multiple dispatch, and the curator trusts the team's later work above his own understanding. The rule changes nothing in microGPT, whose types are concrete. The library keeps the team's declarations of `fail`, `builtinPrimitive` and `List`'s empty comprehension, whose type parameters have no written bound, without the `extends Object` that a batch had added. Under walk, which has no static types, dispatch takes the value's type. Row 538: a compiled dispatcher that carries the static type that the checker gave the call, so that a generic declaration reached only at run time gets this instance. Rows 587, 591 and 612: three cases in which walk still gives `Bottom`.
- P-49 **The compiled checker tries a call first by subtyping, without the expected type, and coerces its arguments only when that attempt is not kept.** The expected type is the type that the call's context requires. The checker's first attempt checks the call by subtyping alone, without the expected type. It keeps that attempt when its result converts to the expected type, by coercion if need be. If it does not keep that attempt, it tries coercion of the arguments, with the expected type. So a declaration that fits the arguments as they are is not passed over for one that coercion reaches. Why: in the curator's words, coercion should be tried when there are no matches.
- P-50 **The body of a `label` expression, and each value that an `exit` gives it, take the expected type of the whole `label`.** A `label` is a named block that code inside it can leave early with `exit`, giving a value with `with`. The specification types a `label` as the union of its body's last expression and the values that its `exit` expressions give. So when a `label` has an expected type, the compiled checker passes it into the body and into each of those values, as it does into each clause of a `typecase`. The specification's inference chapter lists the body and those values as contexts that carry an expected type. P-51 decides the same question for a call written as another call's argument. F-87 lists the checker's contexts that carry an expected type.
- P-51 **The checker retries a call written as another call's argument against each declaration's parameter type.** Take an outer call `f(g(x))`, whose argument is an inner call `g(x)`. If none of the compiled checker's attempts at the call accepts `f(g(x))` (P-49 gives the order of those attempts), the checker checks `g(x)` again, once for each declaration of `f`, with that declaration's parameter type at `g(x)`'s position as its expected type. The retry covers every inner call with inferred static arguments, not only one whose type parameter occurs in its result type alone. Why: the curator wants the type inference rules unified across contexts, which covers cases that the team did not build. As built, a generic declaration of `f` is first instantiated from the other arguments. The declaration whose retry succeeds is kept, or the most specific of several; otherwise the call goes on as it would without the retry. The measurement behind the decision is in `explorations/reviews/argument-context-probe.md`.
- P-52 **`narrowToRange` on a range of rank 2 or 3 checks containment corner by corner.** `r.narrowToRange(other)` must raise `IndexOutOfBounds` when `other` reaches outside `r` on any axis. Its bounds check compares the two ranges' lower corners, and their upper corners, by `PCMP`, the ranges' own point order, which compares each axis on its own. It does not use the tuples' lexicographic order, which serves sorting. So `((0,0):(9,9)).narrowToRange((2,-1):(5,5))` raises `IndexOutOfBounds`, since -1 lies below 0 on the second axis.
- P-53 **`String`'s `left` and `right` answer `Just(c)`, as their declared result type `Maybe[\Char\]` promises.** For a non-empty string, `left` answers `Just` of its first character, and `right` `Just` of its last; for an empty string both answer `Nothing`. The `left` and `right` of the library's ranges and lists answer `Maybe` values in the same way. So walk prints `Just(a)` for `"abc".left`, not `a`.
- P-54 **`QQ`'s `ceiling` and `truncate` keep `ZZ`, their declared result type, and raise an error at +∞, −∞ and 0/0.** The specification's paragraph on these methods said that they return the argument itself at those three values (`Specification/basic-lib/numbers.tex`, "Rational Numbers"). That paragraph is revised. `floor`, `round` and the brackets ⌊x⌋ and ⌈x⌉ are built on `ceiling` and `truncate`, so they raise too. Why: the declared integer result and other languages win over the paragraph: Python's `math.floor(inf)`, for one, raises. The library raises `DivisionByZero`, as the revised paragraph says. After the switch-over, `QQ` follows the float ruling (P-68, on rounding the float types): `floor` and `ceiling` return `QQ` and pass the infinities through, and the brackets, `round` and `truncate` give `ZZ` (row 795).
- P-55 **A size may hold arithmetic, compared by its written form once its numerals are computed.** The compiled checker accepts a sum, a difference, a product or a power as a size, such as the length in `Vector[\RR64, 16\]`. - P-56 **The open range `(:)` keeps its wildcard type, and its five cutting methods fail.** `(:)` is the range of every index, as in `a[:]`. - P-58 **Every native binding is a `builtinPrimitive` call naming a static helper.** A native binding is a library body that is exactly `builtinPrimitive("…")`, the library's own form, and it keeps that form. - P-59 **Walk chooses a coercion by the run-time value until it runs the checker, after the switch-over.** Walk has no static types. - P-60 **The specification reads a `comprises` clause at the level of values.** `trait S comprises { U, V }` says that every value of `S` is a value of `U` or of `V`. So another trait may stand between `S` and its listed types. The specification defines "covers" once: a type covers another when every value of the second is a value of the first. The Meet Rule gains a case for closed traits. Where the rule asks for a declaration at the meet of two overloads' parameter types, several declarations below both serve, if together they cover the meet. So a call whose argument's static type stands between closed traits and their listed types may have several most specific declarations. The call's type is the intersection of their return types, and the declaration that runs is unique only at run time. The compiled checker uses coverage only in its overloading rules, to accept an overload set and to justify a call's tie among several most specific declarations, and not in its general subtype test. A ground declaration's types hold no type variable, and `G[\ZZ32\]` is ground. The addendum shows it for coverage used only in that way, and leaves any wider use to a review of its own. A call that needs a coercion is outside the proof too (F-76 gives what the compiled checker does there). The typing by the intersection is not extended to it, and the specification states that boundary. Rows 543 and 551: the compiled checker gives no call an intersection type where any declaration of the family has static parameters, and walk checks no `comprises` clause declared outside the main component.
- P-62 **The `covariant` keyword is future work, off the path to microGPT.** The keyword, with `contravariant`, is the team's 2012 declaration-site variance: under `trait C[\covariant S\]`, a `C[\Dog\]` is a `C[\Animal\]`, as with Scala's `+S`. - P-146 **In a self-typed trait, the compiled checker types `self` in the method bodies as also being the implementing type.** A self-typed trait is a trait `C[\X\]` whose parameter `X` extends `C[\X\]`, such as `Integral[\I extends Integral[\I\]\]`. - P-147 **An object defines an inherited abstract method when its bodies of that name at narrower parameter types together cover the abstract method's parameter types.** That is, each value of the abstract method's parameter types is a value of one body's parameter types. Row 665: walk's check of generic objects, which its load check skips.
- P-148 **The checker's speed comes right after its correctness in priority: a rung that changes the compiled checker also makes the change fast.** The rung times the checker before and after its change. - P-149 **An object that inherits an abstract functional method from one trait, and a body for it from a sibling trait, is refused unless it declares the method itself.** In `object O extends { A, B }`, where `A` declares `pick(self)` abstract and `B` gives `pick(self)` a body, `O` must declare its own `pick`. - P-151 **Only the `where`-clause forms that the team wrote down are built: conditional extension, a function's or a method's condition, and `AnyList`'s `comprises` clause.** A `where` clause states conditions on static parameters, and may introduce static variables of its own, as `where [\E\]` does. Row 773: the members scoped to the condition, since a member checked under it stays callable where the condition fails. Row 774: walk's half of conditional extension. - P-152 **Walk and the compiled checker read the exclusion of two generic declarations over their whole parameter types, by existential reduction.** With static parameters, the parameter types of two declarations can exclude each other as a whole, even where no single parameter excludes its counterpart. Row 774: walk's half, since walk still gives every list an order.

### Numbers

- P-66 **The integer principle: Java's and the JVM's defaults stay where they make sense, and are corrected where they fail high performance or mathematical precision.** The team did so with rounding. A hardware behaviour that bytecode can express gets its own explicit spelling, as the specification's wrapping and saturating operators do. Where the JVM prevents a correct implementation, the project gives way for now. The peers to compare are Julia, X10, Swift and Rust.
- P-67 **`round` on an exact half goes to the even integer, on both paths.** Under walk and on the compiled path, `round(2.5)` gives 2: an `RR64` or `RR32` value rounds an exact half to the even integer, as a rational does. This is the specification's rule for rationals, the default rounding of IEEE 754, and the rule of the team's own `round` on rationals.
- P-68 **On the float types, `floor` and `ceiling` return the same float type, while the brackets ⌊x⌋ and ⌈x⌉, `round` and `truncate` return `ZZ`, the unbounded integer.** So `floor(2.5)` is the `RR64` value 2.0, and ⌊2.5⌋ is to be the `ZZ` value 2. Row 330: one library rung after the switch-over, which first counts the interpreter tests whose output changes, then makes the brackets, `round` and `truncate` return `ZZ` in each of the library's declarations of them; today the brackets are `ZZ64` under walk and `RR64` compiled, and `round` and `truncate` are `ZZ64`, `ZZ` or `RR64` by declaration.
- P-69 **`LSHIFT` and `RSHIFT` are bit operators on the fixed-width integer types, and `ZZ`'s `shift` is exact.** On `ZZ32`, `ZZ64`, `NN32` and `NN64`, a shift loses the bits that it shifts out, silently, as in every peer language. A count at or beyond the width gives 0, or -1 for `RSHIFT` of a negative value, and a negative count shifts the other way, as Swift's and Julia's shifts do. The count may have any integer type, and the shift works at the width of the value shifted. On `ZZ`, the unbounded integers ℤ, `shift(x, k)` is ⌊x·2^k⌋ at any count; there the specification defines `x LSHIFT k` as `shift(x, k)` and `x RSHIFT k` as `shift(x, -k)`. On the compiled path, a shift of a fixed-width value works on the JVM's `int` or `long`, never through `ZZ`. Why: a shift through `ZZ` costs speed wherever the JVM cannot remove it. Row 442: the compiled `NN32` and `NN64` shifts, refused today. Row 383: `ZZ`'s `shift`, which the compiler's prelude does not declare. Row 381: a count of another integer type, where the compiled path refuses a `ZZ`, `NN32` or `NN64` count and computes a `ZZ64` count on a `ZZ32` at 64 bits.
- P-70 **`GCD` and `LCM` give nonnegative results, and `LCM` raises `IntegerOverflow` when the multiple does not fit its type.** So `0 GCD -4` is 4 and `1 LCM -5` is 5, and on `ZZ32`, `(2^31 - 1) LCM 2` raises. The rule applies on both paths. Why: the specification says that both results are nonnegative, and its general rule raises `IntegerOverflow` for an integer result that does not fit. The same general rule makes `GCD` raise it where the divisor does not fit, as in the specification's example `-2^31 GCD 0` on `ZZ32`. Row 442: `GCD` and `LCM` on the compiled path's `NN32` and `NN64`.
- P-71 **An overflow guard tests for the type's most negative value, not for `a = -a`, so `|0|`, `-0` and `0 DIV -1` do not overflow.** On a signed fixed-width type, only the most negative value overflows when it is negated, taken in absolute value or divided by -1. The test `a = -a` is true for that value, and also for 0. Walk already gave 0 in the three cases. On the compiled path, the natives of negation, absolute value and division on `ZZ32` and `ZZ64` test for the most negative value. The same faulty test sat in `ZZ64`'s multiplication, through which its `REM`, `MOD`, `GCD` and `LCM` compute, so `0 · 5`, `3 REM 5` and `12 GCD 18` raised; that multiplication now raises only when the exact product does not fit. Why: no reading of the specification makes the three cases overflow.
- P-72 **`narrow` keeps the low 32 bits of a value that the narrower type cannot hold, signed and unsigned, on both paths, and raises no `IntegerOverflow`.** The decision covers `narrow` from a `ZZ64` to a `ZZ32` and from an `NN64` to an `NN32`. A value that the narrower type holds is unchanged; any other becomes the value of the narrower type with the same low 32 bits. Why: the team's specification said nothing on `narrow`, and the team's boundary test `ProjectFortress/tests/UnsignedTest.fss` asserts the low 32 bits for `NN64` values. On the unsigned types, keeping the low bits is a bit operation, like a shift, and the signed `narrow` gets the same answer.
- P-73 **Under walk, fixed-width integer arithmetic raises `IntegerOverflow` when its result does not fit, on the unsigned `NN32` and `NN64` too.** The rule covers every operation whose result can leave its type, `^`, `CHOOSE` and `LCM` included (F-132 holds what is built and its tests). So a subtraction below 0 on `NN32` raises. Code that means to wrap uses the specification's wrapping operators ∔ (`DOTPLUS`), ∸ (`DOTMINUS`) and ⨰ (`DOTTIMES`), fully parenthesised, since the specification states their precedence only among the three. The specification's saturating operators, such as ⊞ (`BOXPLUS`), are not in the interpreter's library; they come in a later step of their own (row 797). Why: this is the specification's rule, and the compiled path already raised the error for addition, subtraction, multiplication, division, negation and absolute value on `ZZ32` and `ZZ64`. The decision is walk's. On the compiled path the rule holds as the specification's (P-25, the standard), and the compiled path departs from it at `^` (rows 523 to 525) and at `CHOOSE` (row 521).
- P-74 **Mixed integer widths convert by declared coercions: each wider integer type declares a `coerce` from each narrower integer type, as the compiler prelude does.** A conversion that is exact is implicit, and a conversion that can lose precision is written out. So `ZZ32` values and integer numerals coerce into `RR64` implicitly, and a `ZZ64` value into `RR64` is written out (P-66, Java's defaults corrected where they lose precision). A call of a generic function with arguments of mixed widths infers, on both paths, the narrowest type into which its arguments coerce. A range is over `ZZ32` only (P-77, the rule on ranges). The specification's `widens` declaration, which would make a narrow computation stored into a wide variable run wide, is deferred. The implicit coercion of `NN32` into `RR64`: P-75 holds it, with its conflict with the overloads of `RR64` and `ZZ64`.
- P-75 **`NN32` coerces into `RR64` implicitly, since every `NN32` value converts to `RR64` exactly.** Why: a conversion that fits is implicit, the rule of P-74 on mixed widths. With the coercion, an operator that both `RR64` and `ZZ64` declare is ambiguous on both paths for a `ZZ32` with an `NN32`, since neither `ZZ64` nor `RR64` coerces into the other. Without it, P-74's rule, the narrowest type into which both arguments coerce, gives `ZZ64`. Row 575: the coercion, which the tree lacks, with this conflict and its measurement. Each way to build it changes a decided behaviour, so the choice of a way is not a worker's (`fortress-repo`'s exploring part).
- P-76 **An integer numeral has a type of its own, `IntLiteral`, which each number type converts from: in the interpreter's library now, and under walk once walk has the checker's static types.** The design is the compiler's prelude's working one, taken in place of the specification's numeral types, which the team left unfinished. Why the split: walk has no static types, so it would give a list of numerals the element type `IntLiteral`, with no declared type to go by. The interpreter's library declares `IntLiteral`, the conversions from it into the five integer types, `QQ` and `RR64`, and `IntLiteral`'s own arithmetic, which the team had left commented out until coercion existed. Walk still gives an integer numeral the type `ZZ32`, or `ZZ64` or `ZZ` when its value does not fit, so no numeral reaches `IntLiteral`'s declarations under walk. Walk gaps: a numeral that walk matches as a `ZZ32` in a `typecase` or an overload (row 79), a numeral at an `NN32` or `NN64` binding (row 454), an integer numeral beyond `ZZ32`'s range at an `RR64` binding (row 443), a `nat` parameter used as a value (row 486), and coercion through tuple and varargs parameters (rows 395 and 511).
- P-77 **Scalar ranges are over `ZZ32` only, as the compiler's prelude declares them (`Library/CompilerLibrary.fsi`).** Why: a JVM array has at most as many elements as the largest `ZZ32`. A range over another integer type is a static error. A loop whose counter needs a wider type runs over a `ZZ32` range and widens each element, as in `j: ZZ64 = i`. A range of rank 2 or 3 is a tuple of `ZZ32` scalar ranges. The public range traits, such as `Range[\I\]`, stay generic in their index type: the ranges of rank 2 and 3 extend them at pairs and triples of `ZZ32`.
- P-78 **`SUM` and `PROD` are one generic reduction each over the library's algebra, in place of the team's catch-all over `Number`, and take their identity from the static argument.** `SUM` is generic over `AdditiveGroup` and `PROD` over `MultiplicativeRing`. A reduction written with generators writes its static argument where nothing at the call fixes the element type. The compiled checker fixes it from neither the generators, the body nor a declared type that receives the value, and refuses every such `SUM` or `PROD` that leaves it out (row 731, a gap of the checker). Row 731's workaround is to write it in every clause form of `SUM` and `PROD`, as in `SUM[\ZZ32\][j <- 0#n] f(j)`. A sum without generators is written as before, with no static argument: `SUM e` over a collection `e`, and the dot product `x DOT y`. `BIG MAXN`, `BIG MINN` and `BIG MINMAXN`, the team's `Number`-typed big operators for the maximum, the minimum and both, each with an identity, are gone; no program called them. `MAX` and `MIN` get no identity on the integers or the floats, so an empty `BIG MAX` or `BIG MIN` raises `EmptyReduction` (F-60: a maximum's identity is its type's least value, which a coercion into a wider type does not carry). Under walk, an empty `SUM` or `PROD` over another algebra, such as a user `AdditiveGroup`, still fails (row 436) until the specification's `HasIdentity` is built.
- P-79 **Every team demo is kept running as the tree changes.** The team demos are the programs in `ProjectFortress/demos/`; no suite or step of the gate runs them. If a change breaks a demo and the way to repair the demo is known, the batch that makes the change also rewrites the demo. A batch is a set of tasks, each called a rung, that agents build at once and land together. For example, the change that made `10^(-4)` an error (P-153, the integer power) also wrote `10.0^(-4)` in `BiCGSTAB.fss` and `BiCGSTAB2.fss`, and `10.0^(-6)` for `10^(-6)` in `npbft.fss`. A demo that fails for want of a feature is made to run again once the feature is built. So the demos known to fail today are to be respelled where the way is known: the five demos that walk refuses at load, since they leave an inherited abstract method without a body (row 670, which names them); `trips.fss`, which walk runs but the compiled checker refuses, since its `generator` object extends `StandardTotalOrder[\trip\]` without being a `trip` (row 710); the timing line of `BiCGSTAB.fss` and `BiCGSTAB2.fss`, which divides a `ZZ64` by a float and so stops walk (row 791); and the reductions that the compiled checker refuses because they leave out the static argument of a big operator whose bound names its own static parameter, such as `SUM`; their repair writes the argument (row 731).
- P-80 **The specification's sign-refined number types are a superseded design: a program tests such a subset of a type at run time.** These types are the specification's subtypes by sign, such as positive ℚ, non-negative ℚ and non-zero ℚ, and the same refinements of the integers. The machine types `NN32` and `NN64` are separate types, not among them. The specification's number chapters now test a value's sign by comparison, and a float with two getters of `RR64`: `check` returns `Just(x)` for a finite `x`, `check_star` returns `Just(x)` for an `x` that is not a NaN, and each returns `Nothing` otherwise. The chapter that held the design, `Specification/advanced-lib/numbers-advanced.tex`, stays word for word, marked superseded by a callout in the form of every specification change (P-96), so that the original design stays on record. Their possible return belongs to P-62: once the `covariant` keyword is built, a worker tries to bring them back as covariant static parameters.
- P-153 **The integer power splits on the base: an integer base gives an integer or raises an error, and a float or rational base gives the fraction.** Each integer type's `^` returns its own type at every exponent. At a negative exponent, the bases 1 and -1 give their exact power, a base of 0 raises `DivisionByZero`, and any other base raises `IntegerOverflow`. A program that wants a fraction writes a float or rational base, as in `2.0^(-1)`. Why: the team's later code gives an integer power the type of its integer base at a signed exponent. Overloads choose by type, and no type tells a negative exponent from a non-negative one, since a signed integer or a numeral can be either. So the split is on the base, and the sign of the exponent is tested at run time, as the library tests a value's sign everywhere (P-80, run-time sign tests in place of sign-refined types). Row 441: the same rule on the compiled path, whose own powers give 0 at a negative exponent and a raw Java exception at a base of 0, and overflow silently or with a raw Java exception (row 523).

### Arrays and the model program

- P-84 **An `RR64` array is stored as a Java `double[]`, unboxed, and arrays keep the team's `nat` sizes in their types.** Why: a high-performance language cannot box its array elements, and the sizes are central to the team's design. So the storage and the sizes are one design: the sizes stay in the array types as `nat` static parameters, as the library's `Vector` and `Matrix` declare them, and the compiled checker checks them. The sizes do not wait while a first version of the store carries them only as run-time fields; that layered plan was rejected. Both halves follow the library's own patterns (P-27, on extending the library in its own way). The compiled checker checks `nat` static parameters (F-67). The class loader, as it makes a generic instance's class, only renames the type parameter, so it gives no instance a `double[]` field; a loader that would, way A4 of array decision A (P-85), is unmeasured (F-18).
- P-85 **The array design's three questions are open, with no default, and return after the switch-over with the array decisions A, B and D.** The array design is the compiled path's design for arrays. The three questions: whether the array factory chooses a store for each element type; whether the store also keeps the size as a field, beside the size in the type; and whether a factory for a size known only at run time returns the unsized `Array[\E,I\]`, whose type holds no size. These questions are apart from decisions A, B and D: decision A is how an `RR64` array made through the library's generic array traits gets the `double[]` store (P-84), B is where unboxed arithmetic happens, and D is the sizes in the model's own types (P-87). The whole preparation for the array work is to be done before the switch-over; only the work itself waits.
- P-87 **The model's text is the notation, and the vocabulary is repaired around it.** The model is microGPT's two programs; the vocabulary is the array operations that they are written in (`FlatArrays.fss` for C4, the flat program, and `FlatArrays2.fss` for the APL-style one). No operator in the model is replaced by a function call to pass an overload check, as a proposed repair once wrote `planeSum(mask, x)` for `mask + x`; the vocabulary changes instead. Any repair that changes a line of the model is shown to the curator as a diff before it is built. Decision D, still open and returning after the switch-over with the other array decisions (P-85), is such a diff: it gives C4's arrays sized types, in its vocabulary's signatures and in the model lines that these force (`explorations/reviews/decision-d-diff.md`; the patch itself is only in git, in the parent of `84aef6a4f`). Nothing of decision D is applied before microGPT compiles, after the switch-over.
- P-88 **The model's vocabulary leaves `+`, `-` and `MAX` between an array and a scalar to the library's scalar-extension block, and its diagonal keeps its own product.** The vocabulary, the array operations that microGPT is written in, declares none of these six operators, an array with a number on either side; the library's scalar-extension block, in `Library/FortressLibrary.fss`, serves them. `Diag`, the vocabulary's diagonal matrix, extends `Matrix` and overrides `mul`, the method that the library's matrix product calls, so `diag(v) m` scales the rows of `m` without forming the matrix. This is what the type system promises: a diagonal is a kind of matrix, with a faster product of its own. Row 299 records what the general product costs on a diagonal: 13 to 54 times as much as scaling the rows. Since the diagonal is read-only, a read-only matrix trait, `ReadableArray2`, which `Array2` would extend as `Array1` extends `ReadableArray1`, is also wanted (row 798): it is a library change, not a definition in the vocabulary.
- P-89 **`fill` takes a value, `tabulate` a function.** On the library's arrays, `fill(v)` fills an array with the value `v`, even when `v` is a function, and `tabulate(f)` fills it with `f` applied to each index. The function form, formerly an overload of `fill`, takes Scala's name `tabulate`. Why: in every peer language that has `fill`, `fill` takes the value.
- P-90 **`Maybe`'s empty case is the team's parametric `Nothing[\T\]`, in the one library and the specification.** The bare `Nothing` is future work: it needs a `where` clause that binds a type variable in an `extends` clause, which neither path implements, and it is not tried before then. Gating row 331 on static-argument inference instead is parked.
- P-91 **What an object with no `asString` prints: its bare Fortress type name, walk's spelling, on both paths.** An object with no `asString` of its own prints its Fortress type name as walk spells it, such as `Box`, or `Box[\ZZ32\]` for an instance of a generic object, with no marker and no hash code. A debug marker, such as the Java class name that the curator first leaned to, belongs in `asDebugString` if one is still wanted, not in the printed form; walk's `asDebugString` prints `a Box: Box`. Row 363: an `asDebugString` that prints as walk's does, where the compiled one prints `Box`. Row 321: printing an object that declares or inherits a zero-argument member named `toString`, which overflows the stack. Once the compiled path reads the one library, every object inherits such a member, the `getter toString` of that library's `trait Object`, so every object with no `asString` meets the overflow.

### The specification's revision

- P-95 **Every change to the specification is recorded with its reason.** When the revival changes the language, it updates `Specification/` with the change, so that the text and the implementation do not disagree. The original text and the reasoning are kept, so that route C stays open. Route C is the design that P-43 set aside: a nested number tower, under the forest rule of the team's 2012 patent applications (F-46 gives what a return to it would need). Every such change takes the revision form (P-96 gives its parts). The unrevised copy, `Specification-1.0-frozen/`, is never touched. Why: an open disagreement between the text and the implementation would confuse a reader.
- P-96 **A change of the specification is shown in layers, as the team showed its own changes in the 1.0 release of 2008 and in the working draft of 2009.** This form is the revision form. A callout that prints in every build marks each changed passage; a `\note` will not do, since a release build hides it. Appendix I's revival section has an entry for each change: its reason, its original text, what a return to route C would mean for it, or that it would be the same under route C (P-95 says what route C is), and the decision that it follows. The front matter has one paragraph on the revision, and a document in the repository holds the full reasoning. Citations call the unrevised copy, `Specification-1.0-frozen/`, the Working Draft of February 2011: the copy is that draft byte for byte, and only its `fortress.1.0.pdf` is the 1.0 release (F-163). The `fortress-repo` skill's `references/specification.md` gives each part in full, including what else an Appendix I entry holds.
- P-97 **The specification's examples that break the exclusion rule take the library's shapes, and each original stays, marked "Not allowed".** The Working Draft offered such examples as legal. Each now shows the shape that the library uses for the same thing, with the original beside it under the specification's own mark, "Not allowed". The specification states the rule, which it calls instantiation exclusion, once, in the two parts of Luchangco's Types chapter of 2012 (`Documentation/Specification/Prose/Language/types.tick`; P-25): `Specification/basic/types-vals-vars.tex` says which instantiations exclude each other, and `basic/traits.tex` says that a declaration may not extend two that do. The covariance example, a trait that extends other instantiations of itself, is rewritten and marked in the same way. Its callout adds one sentence: the type group's later design, in the same Types chapter, declares variance with a `covariant` modifier, which neither walk nor the compiled path implements (row 404 records the gap). The calculi of Appendix A keep their rules as the team wrote them, under a callout that they predate the rule.
- P-98 **`TotalComparison` extends `StandardMinMax[\TotalComparison\]`, so that the library's `BIG MIN` and `BIG MAX` work over total comparisons.** It does so in the library's api and component, `Library/FortressLibrary.fsi` and `.fss`. It keeps the five members that it restates by hand: `MIN`, `MAX`, `MINMAX`, `<=` and `>=`. Without the parent, walk finds no overload of `BIG MIN` or `BIG MAX` that takes total comparisons (row 461). Why: it is the library's own device, which its other ordered types use. The curator took it on the coordinator's recommendation. It stands and blocks no work.

### The suites and the gate

- P-102 **Test first, the test kept.** Every edit of source code in the original tree starts from a failing test. The worker adds the test to the test suite, sees it fail, makes the fix, and sees it pass. The test then stays in the suite for good. An edit of the specification or of documentation is not source code and needs no test. The gate's three test runs, `ant testFast`, `ant testSystem` and `ant testSpecData` (P-124), must pass when the work lands; they need not pass after every edit. The test and the fix may land in one commit. Why: the rule replaces one-off validation scripts, which no later build runs. The `fortress-repo` skill's `references/tests-writing.md` says how to write the test.
- P-103 **The suite's verdict is the check.** A test's result is pass or fail, as the team designed the suites. A value that matters is checked inside the test, with the checks that the harness already has: an `assert` call in an interpreter test, a `run_out_equals` key in a compiled test's `.test` file. What a test prints beyond its checks does not count. So no expected-output files are added. They are not proposed to the curator again, and neither is a comparison of what a test prints beyond its checks with an earlier run's output. Why: when the suite's designers let a test pass without a further check, what it prints need not be checked.
- P-124 **The specification's examples are a step of the gate, and every one must pass.** `ant testSpecData` runs the examples extracted from `Specification/` under walk (F-114 says which 130 it runs), and the gate fails if any of them fails. When an example fails, the implementation is fixed: the example is not respelled to get around a gap in walk, and no list of examples allowed to fail is kept.
- P-125 **The suites run Fortress in parallel, pinned at four threads in `build.xml`.** `build.xml` sets `FORTRESS_THREADS` to 4 for the two suites, `ant testFast` and `ant testSystem`, so that every run of them uses four threads, whatever the calling shell sets. A test that parallelism makes fail, on every run or only on some, is written wrong, for example a write that needs `atomic`, or it shows a defect. Either is fixed, never hidden by running at one thread. Why: Fortress is parallel by default, so a suite at one thread has a blind spot, and sparing the four-CPU machine is no reason for one.
- P-150 **No resident compiler is built.** A background JVM that serves Fortress commands, as Scala 2's `fsc` did, would save too little of the workers' time to be worth building (F-234), so the speed work goes to the checker itself (P-148). It is not tried again unless something significant changes.
