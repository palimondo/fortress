- **A radix numeral is a natural number, not a bit pattern, and the compile path was the only place that pretended otherwise.** `literals.tex:104-108` gives a radix numeral the type `NaturalNumeralWithExplicitRadix[[n,r,v]]` over the value of its digits in radix $r$, so `8000'0000_16` is $2^{31}$ and `A0000000_16` is $2684354560$; the interpreter has always refused such a numeral at a signed type ("RHS expression type Long is not assignable to LHS type ZZ32"), and the compile path accepted it only because the wrap turned it into something else. The first four are repaired value-for-value; the fifth was not only illegal but was exercising `i = -1257966796` instead of the $\sqrt{2^{63}}$ boundary its own comment names.
- Every numeral in the corpora and the libraries whose value has bit length exactly 32 or exactly 64 is enumerated, by value and in every radix, at `compile-ladder/repair-r2-literal-wrap/probes/boundary-numerals.txt`; eighteen of the enumerated lines are on the compile path, twelve of them in range for their annotated type and right until now only by the wrap's accident. - The bytecode optimizer's `RemoveLiteralCoercions` substitution (`FIntLiteral.make(I)` plus `coerce_ZZ32` becomes `FZZ32.make(I)`, `RemoveLiteralCoercions.java:33-53`) elides `asZZ32`'s range check, which is sound exactly when the code generator's int branch is the `ZZ32`-representable range: false under `l <= 32`, true under `l <= 31`.
