## 2. What the revision states, and what it does not

The revised passage (`Specification/basic/traits.tex:235-252`) states, for a trait `T` whose declaration has a `comprises` clause:
- every listed type extends `T`, and every value of type `T` is a value of one of the listed types;
- a listed type may be an instantiation of a parameterized trait, provided every static variable occurring in its static arguments is a static parameter of `T` ("static parameter" before the gather; decision 4);
- a trait or object that explicitly extends `T` is a subtype of a listed type, or a trait with a `comprises` clause of its own each of whose listed types meets the same requirement, or a trait with static parameters that at least one trait or object extends and every trait or object extending it is a subtype of a listed type;
- for a parameterized `T`, the same of each instantiation, the listed types instantiated alike.

It does not state: whether a bare static parameter (a type variable) may be listed, which is not this rung's (the batch record, section 3, X, "The decisions"; row 407 rests its home on `traits.tex:163-170`, which the edit leaves); any rule about declarations in other units, which the checker's limit makes a ledger row (Y's) and the Appendix I entry names as an effect, not a rule; anything about the ellipsis, whose sentence is kept word for word in its note (`:268-274`); anything about the `Molecule` example (`:292-325`), unchanged. So it states no more than the decision and Y's section build (the batch record's stop).

## 3. The passage: the original, the new text, the reason, route C

- Original, `Specification/basic/traits.tex:235-246` at the base (frozen `:230-241`), a `\note`, which a release build renders as nothing (`Specification/fortress/fortress.tex:35-36`): "If a trait declaration of T includes a comprises clause then the traits listed in its comprises clause are exactly the traits that immediately extend T and they must explicitly extend T (i.e., list T in their extends clause). If the comprises clause of a trait T includes "..." (and must therefore be in an API), then in a component exporting the enclosing API, other traits may explicitly extend T, but these traits may not be declared or imported by the API (see § apis)." Appendix I quotes it whole.
- New text, `traits.tex:235-252`, rendered normative text: "If a trait declaration of T includes a comprises clause then every type listed in its comprises clause extends T, and every value of type T is a value of one of the listed types. A listed type may be an instantiation of a parameterized trait, provided that every static variable that occurs in its static arguments is a static parameter of T. A trait or object that explicitly extends T must be a subtype of a listed type, unless it is a trait with a comprises clause of its own each of whose listed types meets this requirement, or a trait with static parameters such that at least one trait or object extends it and every trait or object that extends it is a subtype of a listed type. If T has static parameters, these statements hold of each instantiation of T, with the static parameters of T in the listed types replaced by the corresponding static arguments." The callout follows at `:253-267`; the note, now its second sentence alone, at `:268-274`.
- Reason: the decision. The later Types chapter reads a clause as coverage, "An instantiation of the generic type defined by such a declaration is covered by the union of the types in this set and the corresponding instantiations of the generic type in this set" (`types.tick:387-390`), the set holding "types and generic types determined by the generic type of the declaration" (`:384-386`), where G determines G' "if every parameter of G' is a parameter of G" (`:277-279`). Welterweight: "the comprises clause, if present, indicates that no value can belong to the trait unless it also belongs to one of the comprised types" (`Papers/Welterweight/grammar.tick:21-22`), and its rule D-Trait asks each listed type to be a subtype of the trait at its own parameters (`Papers/Welterweight/fig-wellformeddecls.tick:53`) and nothing of the traits that extend it (`:38-62`). The type group's later word weighs more (POSITIONS 2026-09-23) and the Types chapter is cited beside `Specification/` where it covers a topic (POSITIONS 2026-09-26, the lineage note). The note restated Sukyoung Ryu's checker rule of 2009 and is in the draft by 2009-11-06 (`explorations/reviews/anyintegral-comprises-ways.md` section 1).
- The callout, `revival-comprises`: what the Working Draft said, the reading adopted with its two sources, why a parameterized trait with a static parameter `T` lacks can be listed only at particular arguments and when it may stand unlisted, and that it answers the third question of Victor Luchangco's note at `:166-170`, whether an instantiation may be listed (worded so at the gather, on the skeptic's correction 4).
- The library's case: `trait AnyIntegral extends { Number } comprises { ZZ, ZZ64, ZZ32, NN64, NN32 } end` with `trait Integral[\I extends Integral[\I\]\] extends { StandardTotalOrder[\I\], MultiplicativeRing[\I\], AnyIntegral }` (`Library/FortressLibrary.fsi:433-436`). `Integral` explicitly extends the closed `AnyIntegral`, is unlisted and cannot be listed at its own parameter (`AnyIntegral` has none); it has static parameters; the five integer types extend it, each at itself (`trait ZZ32 extends { AnyIntegral, Integral[\ZZ32\] }`, `.fsi:510`), and each is listed. So the third case holds, and the clause is valid under the new text as written. The team's comment on the line, "not yet: `comprises Integral[\I\] where [\I\]`" (`.fsi:434`), records the closure the five spell out.
- Route C: the same under route C; there the self-typed traits carry `comprises` clauses of their own, and a parameterized trait between a closed trait and its listed types meets the requirement through its own clause (the second case), so the third case is not needed (the judgement, section 3, "Route C"). The entry says "not needed" rather than the judgement's "never reached": in the shadow's order the new disjunct is tested before the own-clause case (`explorations/reviews/anyintegral-comprises-ways/shadow-thc.py:45-49`), so the code reaches it; the text's third case is simply not required.

## 5. Decisions taken inside the rung

1. **Every listed type extends T, and "explicitly" goes.** The note said the listed traits "must explicitly extend T (i.e., list T in their extends clause)". The checker since 2009 requires a listed type to extend the trait at its own parameters, directly or through its supertypes (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/TypeHierarchyChecker.scala:220-240`, with `extendsContains` recursing through supertypes at `:280-303`), and Welterweight's D-Trait asks a subtype (`fig-wellformeddecls.tick:53`). With a subtrait that has its own clause (the second case), a listed type may extend `T` only through that subtrait, which "explicitly" would refuse and the checker accepts. Rejected: keeping "explicitly" (an open discrepancy with the checker's accepted shapes); dropping the requirement (the text would say nothing of a rule the checker enforces and the calculus states). The judgement's section 3 does not list the requirement; it is the note's first sentence's own, relaxed to what the implementation and the 2012 calculus hold. Listed for Pavol.
2. **The third case covers every trait with static parameters**, not only one "with static parameters the closed trait does not have" (the judgement's words, section 3). The decision says "a generic child of a closed trait is eligible when every type the checker knows under it is listed" (POSITIONS 2026-09-28), and Y's code tests `!tt.getArgs.isEmpty` (`shadow-thc.py:47`). Written with the judgement's condition, the text would refuse a parameterized subtrait whose parameters are all `T`'s, unlisted, whose extenders are all below listed types, which Y's checker accepts: an open discrepancy. The judgement's sentence is kept as the callout's motivating case: such a trait "can be listed only at particular static arguments". Listed for Pavol.
3. **The first case is "a subtype of a listed type"**, the checker's rule 2 (`comprisesContains`, a subtype test, `TypeHierarchyChecker.scala:268-278`), of which "is listed in it" (the judgement's words) is a special case. `ExclusiveMolecule` is refused either way.
4. **The instantiation sentence speaks of the static parameters that occur in a listed type's static arguments.** Rejected: "each listed type is a trait type" (a type variable is not a trait type, `Specification/basic/types-vals-vars.tex:199`, so it would settle row 407's question against `comprises T`, more than the decision); "every static parameter that occurs in a listed type is a static parameter of T" (reads as allowing a bare parameter, the batch record's stop). The Types chapter's "types and generic types determined by the generic type of the declaration" (`types.tick:384-386`) is rendered in the specification's terms: an instantiation whose static arguments mention only `T`'s parameters is the chapter's "generic type determined by" `T`, and one that mentions none is one of its "types". *At the gather, on the skeptic's required correction 1:* the sentence speaks of the static variables that occur in a listed type's static arguments, not only the static parameters. A `where`-clause variable is a static variable that is not a static parameter (`Specification/basic/trait-parameters.tex:312-315`), so the proviso as the rung wrote it said nothing of one, and `trait T comprises { Foo[\I\] } where [\I\]`, the shape of the team's own "not yet" spelling for `AnyIntegral` (`Library/FortressLibrary.fsi:434`), met it vacuously. The Types chapter's "determined by" (`types.tick:277-279`, `:384-386`) and the judgement's "generic types each of whose parameters is a parameter of the declaring trait" (`explorations/reviews/anyintegral-comprises-judgement.md:105`) exclude it, and both paths refuse the program, "I is undefined" (`probes/skeptic/SkWhereListed.txt`). The text now reads "provided that every static variable that occurs in its static arguments is a static parameter of T" (`Specification/basic/traits.tex:238-240`), and the entry's Change "contain no static variable other than the static parameters of T" (`Specification/appendices/changes.tex:1256-1258`); each keeps its line count.
