## 1. The edit

`rule.patch`, made by `make-shadow.py` (variant `rule`) and applied to the tree by `git apply` from the repository root (`build.txt` records that it applies). Two files of the compiled checker, `ProjectFortress/src/com/sun/fortress/scala_src/typechecker/impls/`:

- `Operators.scala`: measurement D's four one-token edits, `, expected` at `:85`, `:90`, `:197` and `:345`, so that a call written `f(x)` is checked with the type its context expects.
- `Functionals.scala`: 124 lines added and 5 removed (`git apply --numstat`), 21 of the added lines comments. Three pieces.
  - The attempts, in `checkApplication` (`:449` today). The candidates of a call are tried up to four times, and the first attempt in which one is applicable is kept: by subtyping with the expected type (today's inference, now with the context at `f(x)` too); with coercion and the expected type; and, only when there is an expected type, by subtyping without it and with coercion without it. An attempt without the expected type is kept only when the most specific candidate's result is a subtype of the expected type or converts to it (`coercions.substitutableFor`), which is what the retry is for: a typed binding's coercion of the result still applies. The third attempt is today's check of a call `f(x)`, so a call whose result today's binding accepts is accepted again there at the latest. A refused call reports the first attempt's errors. `checkApplicable` and `checkApplicableWithInference` gain a `coerce` switch, default `false`.
  - The first build kept the retry without the expected type whatever the result; on the compiler tests it changed the message of one expected-failure test that pins the text, `XXX6bu`'s `compile_err_equals` (a method invocation refused today by its context, then by the assignment), so the condition was added and the rule's side of every run was repeated; that first run's capture was replaced by the repeat, and the commit message of `b15201e5b` records it.
  - The coercion attempt, a new method `checkApplicableWithCoercion`. The argument positions are sorted by their declared parameter type: a type parameter alone (`x: T`), a type that mentions a static parameter (`b: Box[\T\]`, `base: M[\r, c\]`), or a type that mentions none (`m: ZZ32`). Only the second kind and the expected type constrain the solver, by subtyping as today (the constraint is built with `inferStaticParamsHelper`, the solver the tree already uses). A type parameter that stands alone at some position and appears in no other parameter type is chosen instead: each of "whatever the rest fixes", its own arguments' types and its declared bound (a trait type other than `Object`) is tried, and among those that succeed the narrowest is kept, narrowest meaning substitutable, a subtype or a coercion, for every other success. Then every argument is admitted against the instantiated parameter type by subtyping or by a coercion, which is built into the call as `checkApplicableWithoutInference` builds it for a non-generic call.
  - The promotion case, at the end of `checkApplicableWithInference`: when today's inference succeeds but binds such a lone parameter to a union (`OR(ZZ32,ZZ64)`), the coercion attempt runs with the union's members as the only choices, and its result replaces the union when one member is the narrowest; otherwise the union stays.
- Not changed: the solver (`Formula.scala`), the coercion oracle, the other places that drop the expected type (measurement D § 1.3: a loose juxtaposition, an argument, a `let` body, an `if` with no `else`, `typecase`, a `for` body), and a result-only parameter, which the kept context still binds to `BottomType` as in measurement D.
- The trace used on the small programs is a separate variant (`rule-instr`, `instr` for the tree), off unless `-Dprobe.showInfer=true`; the trace-free `rule` gives the same errors (`small/RuleL.rule.walk.L0.txt`, `small/DArg.rule.walk.L0.txt` against their `rule-instr` captures).

## 6. What walk would need [read, not built]

- Where walk infers: `EvaluatorBase.inferAndInstantiateGenericFunction` (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/EvaluatorBase.java:50-251`). It installs each type parameter's bound (`:95-114`, `abm.meetPut` at `:105`), then unifies every argument's run-time type with its declared parameter type, in order, bare type parameters included (`:135-189`, `at.unify` at `:171` and `:176`). A bare parameter takes the join of its arguments' types (`FType.unify`, `evaluator/types/FType.java:533-584`, `abm.joinPut` at `:549`; `FType.join`, `:350-380`, a common supertype, `Number` for `RR64` and `ZZ32`). It instantiates at `:248`, an unfixed parameter erased to `Bottom` at `:245`.
- Where walk converts: an instantiated function's arguments are converted at binding already, rung C's `Coercions.coerce` in `NonPrimitive.buildEnvFromParams` (`evaluator/values/NonPrimitive.java:212-257`, `:257`) and `typecheckParams` (`:134-185`, `:172`), reached from `FunctionClosure.applyInnerPossiblyGeneric` (`evaluator/values/FunctionClosure.java:176`, `:198`). So walk has the admission half; what refuses is the inference half: `scale(b, z)` instantiates `T = Number`, and the binding then refuses `Box[\RR64\]` for `Box[\Number\]` (FACTS, "An inferred generic refuses a coercion ...", `numerics-plan-fable/probes/one-shape/walk/ScaleZ.walk.txt`).
- The same rule under walk, three places:
  1. `inferAndInstantiateGenericFunction`, the loop at `:135-189` split in two passes as the compiled edit splits the positions: first unify only the arguments whose declared type is not a type parameter alone (`p.getIdType()` a `VarType` named in `tp_set`); then, for each lone parameter the first pass fixed, skip its arguments, which the binding converts; for a lone parameter nothing fixed, try its arguments' run-time types and its bound, keep the narrowest that each argument matches (`typeMatch`) or converts into (`Coercions.coercionFor(t, a) != null`), and install it with `abm`. The same choice is the promotion case: `same(z, w)` gets `T = ZZ64` and `z` is converted at binding, where today it gets the join and runs unconverted (`one-shape/walk/SameZW.walk.txt`). Walk has no expected type, so the context half has no counterpart; a typed binding already converts after the call (`Coercions.coerceToDeclared`, `Coercions.java:124`).
  2. `OverloadedFunction` (`evaluator/values/OverloadedFunction.java`): `bestMatchInternal` (`:856-895`) keeps a generic overload only when the arguments match its instantiated domain without conversion (`argsMatchTypes` at `:889`), and `bestMatchWithCoercion` (`:821-852`) skips generic overloads (`continue` at `:826`). With place 1, the instantiation can be computed there and the per-argument coercions built against the instantiated domain, as `:829-837` builds them for a non-generic overload. A generic that is not overloaded is applied through `GenericFunctionOrConstructor.applyInnerPossiblyGeneric` (`evaluator/values/GenericFunctionOrConstructor.java:50-57`), whose instantiated closure converts at binding, so place 1 is enough there.
  3. `Coercions.coercionFor` (`evaluator/values/Coercions.java:48-71`, row 389): a generic target's lifted coercion is instantiated from the value alone (`:59`), before the target's static arguments are known; it would be instantiated with the target instance's static arguments first, as the checker does ("the lifted args are given in U", `scala_src/typechecker/CoercionOracle.scala:193-196`).

## 7. What the rule does not reach, and the forks it meets

Each item is measured where it names a capture, read otherwise.

- **Numerals alone at a bound a numeral does not meet, on A0.** `lohi(2, 46)` with `I extends AnyIntegral`, `twice(3, 4)` with `T extends Integral[\T\]`, `(): ZZ64 = inc(5)`, and today's generic ranges `2:46`, `0#3`, `0#vs` are refused stock and under the rule (`small/RuleL.outcomes-any.txt`, `small/DArg.summary-any.txt`), and so are microGPT's four ranges of the shape (section 3) and the library's three (section 4). The lone parameter's choices are its arguments' type, `IntLiteral`, and its bound when that is a plain trait type (`AnyIntegral`, which a numeral does not convert into; an F-bound is skipped), and none succeeds. Today they pass on L0 only because `IntLiteral extends ZZ32` there. The ways the language offers, none decided here:
  1. the ranges batch before batch N (the recorded order): `#` and `:` over `ZZ32` are not generic, so a numeral converts at them as at any call; section 3's A0T2 measures that on microGPT;
  2. the expected type as one more choice when the result is the lone parameter, so that `(): ZZ64 = inc(5)` and `x: ZZ64 = twice(3, 4)` infer `ZZ64` [not built];
  3. a default type for a numeral that nothing else fixes, among its coercion targets that meet the bound, as Java's `int`, Rust's `i32` fallback and Haskell's defaulting do; `ZZ32` and `NN32` both convert from a numeral and neither into the other, so "the narrowest" does not pick one, and the specification writes no default (`literals.tex:83-95`, the unfinished numeral hierarchy), so it would be a decision;
  4. the written static argument, today's device and answer 8's interim rule.
- **A narrowest common type that is neither argument's.** `ZZ32` with `NN32`: `pick(u, z)`, `lohi(z, u)` and `seq(z:u)` keep the union `OR(ZZ32,NN32)`, where answer 8's rule names `ZZ64`, the narrowest type both convert into (`small/RuleL.outcomes-any.txt`, `small/OneShapeW.summary-any.txt`). Finding it needs, for each argument type, the types that declare a coercion from it; the checker's oracle only goes from a target to its sources (`getCoercionsTo`, `scala_src/typechecker/CoercionOracle.scala:85-115`), and the trait table can be iterated (`TraitTable.scala:99-110`) to build the reverse index [read, not built]. Neither the library's distance nor microGPT's own errors move with the promotion (sections 3 and 4), so no error there comes from this shape today.
- **A structured position.** `SUM <|1, 2, 3|>` (row 432): the list's `IntLiteral` fixes `T` through `Generator[\T\]` and fails the bound `AdditiveGroup[\T\]`; the rule chooses only for a lone parameter and converts only at a lone or non-generic parameter, so it stays refused (`small/OneShapeW.summary-any.txt`).
- **A result-only parameter.** As in measurement D, the kept context binds it to `BottomType` (`DCtx`'s eleven, the natives' shape); the rule does not change that, and what code generation makes of it is measurement D's open question.
- **The other drops of the expected type** (measurement D § 1.3: a loose juxtaposition, an argument, a `let` body, an `if` with no `else`, `typecase`, a `for` body): not changed.
- **The order of the attempts** is this probe's choice: the expected type first, so where it and coercion fix a parameter (`a: BoxT[\ZZ64\] = wrapT(3)`) the call converts its argument, and where they do not (`a: ZZ64 = idt(3)`) the binding converts the result as today. The other order, today's inference first and the context only when it fails, was not built.
- **Messages.** A call written `f(x)` that no attempt accepts, and whose result the binding would refuse, now reports the call's refusal instead of the binding's: 3 sites per setting and library in the probes (2.1), none in the compiler tests (section 5).
- **The comparison of a `case` expression** is checked with the expected type `Boolean` and no check after it (`Functionals.scala:856`); since an attempt without the expected type is kept only when the result converts to it, a non-`Boolean` comparison is not newly accepted [read].
- **A numeral at a non-generic overloaded call on A0.** `w: ZZ64 = widen(4)` is refused, "Right-hand side has type NN64", because A0's numeral picks `widen`'s `NN32` arm; stock and rule alike, 27 sites in `OneShapeW` and 1 in `RuleL` on A0 (`small/OneShapeW.instr.any.A0.txt`).
