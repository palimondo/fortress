## 4. What the specification settles (rule 3)

- **Dispatch.** Declarations of one name may not differ in their static parameters "(up to α-equivalence)", so "static parameters do not enter into the determination of which declarations are applicable" (`Specification/basic/overloading.tex:100-107`). Static variables in calls are "instantiated or inferred" (`:136-138`), inferred "from the context of the function call" (`Specification/basic/expressions/var-ref.tex:37-40`), and the call dispatches to the most specific declaration applicable at run time (`overloading.tex:262-276`). The three dispatch programs are α-equivalent pairs (`pair[\B,A\]` is `pair[\A,B\]` renamed). They are legal under this text as it stands and under answer 9's positional rule (POSITIONS.md:108, 2026-09-26, answer 9). The specification's answers are the assertions of the three tests.
- **Row 419.** Static parameters "are in scope of the entire body of the declaration" (`Specification/basic/trait-parameters.tex:19-24`), and each `also` block is "run in a separate implicit thread" (`Specification/basic/expressions/also.tex:17-21`). A task body therefore sees the declaration's static parameters.
- **Row 351, catch site.** "The exception value is bound to the identifier specified in the catch clause" (`Specification/basic/expressions/try.tex:56-60`).
- **Row 351, typecase site.** "The value of the expression is bound to the identifiers" (`typecase.tex:88-91`). A clause matches if the value's type is a subtype of its type (`:94-95`), and the identifier's static type in a clause is the intersection of the two (`:105-109`). The prose is written for the `typecase x = e of` spelling. The per-clause `x: T =>` spelling the parser takes (`ProjectFortress/src/com/sun/fortress/parser/DelimitedExpr.rats:237-252`) is the pattern-matching form the chapter's own note defers to (`typecase.tex:15`). The binding semantics carries over unchanged, and the checker implements it (`Misc.scala:335-340`).
- **Row 426.** `cast` is the `typecase` of `casting.tex:15-34`. A numeral is not converted to a number type (`Specification/basic/expressions/literals.tex:132-141`), so `cast[\ZZ32\](0)` throws on the compiled path, where the numeral is an `IntLiteral`, and that is the specification's answer. Walk returns 0 because its numeral is a `ZZ32` (row 79; the numeral switch is batch N's).
- **The identity functions.** Answer 7 (POSITIONS.md:112, 2026-09-26): "its identity from the static argument through the library's `() -> T` witness `typecase`". Its values stay what they are.

## 12. Decisions, each with the ways not taken

- **The lock's shape.** Candidates:
  - `synchronized (getClassLoadingLock(name))` around the whole of `loadClass`, which is the loader's own monitor. Taken.
  - The same with `registerAsParallelCapable`, one lock per name.
  - A lock only in `loadClosureClass`.
  - A `ConcurrentHashMap` of futures per name.

  The monitor is the lock the JVM already holds when it resolves a class through a loader that is not parallel-capable, and it is what the JDK's own `loadClass` takes. Explicit loads (`loadClosureClass`, `getRTTIclass`, the union instantiation) were the only ones running without it. Taking it adds no lock order the implicit loads do not already have: a generation step that initialises another class under the monitor, as `ProjectFortress/src/com/sun/fortress/runtimeSystem/MethodInstantiater.java:274` can, already does so on every implicit load. Per-name locks would admit two loads each holding one name's lock while generating a class that needs the other's; the JDK leaves them off unless a loader opts in. A lock in `loadClosureClass` alone leaves the other two explicit callers racing. Futures would change the loader's structure for no gain the measurement can see.
- **Where `history` is written.** Left before `defineClass`. Under the lock no other thread can see the name before its class is defined. Moving the write would change what the same thread does if generation re-enters the loader for the name it is generating, which it does not today by reading, and every single-thread run would need re-measuring for no gain. The pre-existing behaviour after a failed load, where the name stays in `history` and a later load of it returns null (`InstantiatingClassloader.java:189-193`), is unchanged; by reading, not measured.
- **Binding a catch name always.** The grammar makes the name mandatory (`try.tex:22`), and the specification binds it (`:56-60`), so every catch clause's code changes: `getValue`, a cast and a store in place of a pop. The prelude has no `catch`, so no library class moves. The other way, binding only a name the body reads, needs a free-variable test at each clause and saves three instructions.
- **Binding a typecase clause's name only when it has one.** Clauses without a name pop as before, which is why only `cast`'s template changed in the prelude.
- **The identity functions' values of type `T`.** Two ways were on file:
  - A typed binding, `v: ZZ32 = 0` then `cast[\T\](v)`, which converts a numeral by coercion on the compiled path and keeps walk's value as it is (FACTS.md, "Under walk, the interpreter converts by coercion at its three kinds of type check", FACTS.md:110). Taken, in the two branches that passed a numeral.
  - A checker refinement that binds `T` inside a witness branch (`explorations/reviews/sum-replacement-judgement.md` section 7, check 3), which is Scala and not this rung's. Not taken.

  `typed` would not do: the compiled path has no `forAsExpr`. The six branches that pass a function's result (`widen`, `unsigned`, `big`, `Ratio`, `narrow`) already have values of their type on both paths and are unchanged.
- **Row 420's fix is row 419's.** No separate edit was made; the row closes with 419, its cause located and gated.
- **Home 3, not home 2, for a dispatcher that is not a template.** The batch record plans home 2 for both remainders "where the rung shows it failing" (`explorations/coordinator/CLIMB-BATCH-6.5.md:188`). For generic dotted methods the rung took it (`XXXDispatchMethodArmRungG`). For a dispatcher that is not a template the alternative was an `XXX` test asserting only that the call does not throw and answers one of the two declarations. It was not taken, because the chapter as committed forbids the pair (`Specification/basic/overloading.tex:102-105`), so no passage says which answer a test should hold, and the grep of section 9 finds none; home 3, the probes and row 496.
- **Two more compiled tests than the brief named.** `WitnessIdentityRungG` is answer 7's identity shape in the compiler's world. It is the judgement's check 3, `zeroOf[\RR64\]()` through a repaired `cast`, now gated. `XXXDispatchMethodArmRungG` is the remainder's home 2.
