# Pavol's positions, decisions and known ground

## The goal

- P-7 **The goal is to finish what the designers intended, measured by one program, microGPT, compiled to JVM bytecode and running fast.** The revival judges what the designers intended by the team's own sources: its Working Draft of February 2011, its texts on types and its code. `Specification/` holds the Working Draft as a living document: the revival revises it and states each change (P-95). The texts on types include the Types chapter of the specification's 2012 restart (P-25). In `Papers/`, they include the OOPSLA 2011 paper, Naden's 2012 write-up and the POPL 2019 paper with its technical report. P-26 says when code counts, and which source wins where two conflict. The revival does not redesign the language. A pure-Java microGPT is the baseline that compiled microGPT is measured against: the optimal result, the one to aim at.
- P-8 **Where the designers' own sources, the specification, the papers, the library and the implementations, give no answer, the curator decides by the goal, a compiled microGPT running fast, not by type-theoretic purity, and he stays true to the spirit of Fortress.** On the way to a compiled microGPT, he accepts the language's unfinished corners as they are, so that the work does not stall in theory. He has not read the specification, the papers on its type system or the library, and he takes the designers to have known more than he does.
- P-9 **The revival searches for the most readable expression of the microGPT algorithm.** C4 is the flat microGPT program (`explorations/run-c4/src/MicroGptFlat.fss`), whose data layout follows Aaron Hsu's flat style of APL (P-29: C4 is not edited for speed before microGPT runs compiled). In C4, the polishing happens in the vocabulary, the array operations that the model's lines call: `FlatArrays.fss` beside C4, and what of it has moved into the standard library (P-27: what a program builds that a more mature library would hold goes into the library). P-87 holds the limit: the model's text is the notation, and a change to a model line is shown to the curator as a diff first. C4 is the target form of the APL microGPT program (`explorations/apl/mg/MicroGptApl.fss`): the APL program is written so that each of its lines expands into the line that C4 writes by hand. C4 writes its hyperparameters as tuple bindings, such as `(nEmbd, blockSize, nHead, headDim, vocabSize, bosId) = (16, 16, 4, 4, 27, 26)`, the form to which the APL sub-language (P-10) expands a strand assignment, APL's binding of several names at once. The one-line form, declarations separated by semicolons such as `nEmbd = 16; blockSize = 16; ...`, is not used: the APL sub-language has no use for it.
- P-10 **The APL side quest is closed: its sub-language covers only what the APL microGPT program needs, and the parts of APL that it left unbuilt, tacit functions, characters and nested arrays, are not pursued.** The side quest built an APL sub-language in `explorations/apl/`: a DSL grammar that expands APL text into Fortress code over Fortress's native arrays, not an interpreter of APL. Its microGPT program, `explorations/apl/mg/MicroGptApl.fss`, stays in the microGPT check under walk (P-30: the check's limit of one minute; what the check runs: the `fortress-repo` skill, `references/interpreter.md`, "The model program").
- P-11 **The 2D notation is a gimmick: no work on it unless the curator asks.** The 2D notation is Fortify's rendering. Fortify (`Fortify/`, run by `bin/fortify` and `bin/fortick`) typesets Fortress source as mathematics in LaTeX, for the specification and the papers. Taken as programming syntax, such a rendering fixes one view of a computation, though the same mathematics can be written in many ways. APL, with one symbol for each transformation of the data, expresses a computation better. The rendering is presentation only, off the revival's path, and no argument in favour of Fortress. The verdict is on that typesetting only: the Unicode operators, such as `∑` and `×`, are the language's own syntax.
- P-12 **After the switch-over, walk runs the compiled type checker on its programs, and then uses the static coercions that the checker inserts.** The curator wants the checker usable on the programs that walk runs. Today `fortress typecheck` checks a program only against the compiler's prelude, so it is no check of walk's programs (F-9 holds this fact). Walk is not changed for this before the switch-over. After it, walk runs the checker on its programs and so gains their static types; F-9 and F-290 say what walk and the library lack for that step. Walk then uses the static coercions that the checker inserts, in place of its choice on the run-time value (P-59, walk's choice of coercions until the switch-over).

## History he knows (do not re-explain)

- P-17 **Unboxed doubles and arrays of unboxed doubles are required: without them the revival misses its point.** Why: a language meant for high performance cannot box its numbers. Today the code generator boxes every number: an `RR64` value is an object of the class `FRR64`. In Java models of microGPT's three array kernels, the dot product, the matrix product and the row lift, boxing is the main cost (F-11 holds the measurement). How arrays store doubles, as `double[]`, is P-84's decision.
- P-19 **The tree is not described as the third-party port's migration grafted onto the team's history.** The port is a third-party port of the tree to Java 9, which commit `8fe1daa8f` copied onto the team's last commit (the `fortress-repo` skill, `references/records.md`, "The repository's history"). By history, `main` descends from that commit. By content, most of the port's files are removed or redone, and only one piece of the port's code still runs: the `FTypeArrayList` fix for the JDK 8 `TreeSet` crash (F-165). Why: the tree is not built on the port, and the record must not lead anyone to think that it is. The files that still describe the tree so wait for the lineage cleanup; `coordinator/lineage.md`, "Files that still repeat it", lists them.

## Decisions on record

### The standard and the sources

- P-25 **`Specification/` stays the standard, and the Types chapter of the team's 2012 restart is cited beside it.** The restart is a new specification that the team began in 2012 and left unfinished (F-166). Where its Types chapter, `Documentation/Specification/Prose/Language/types.tick`, covers a topic, a worker cites it beside `Specification/` as the designers' later word. On the rules that the revival revises, such as the exclusion rule, the chapter is the designers' latest intent, which the goal is to finish, and `Specification/` is revised to follow it. Three of the chapter's passages bear on the specification; P-97 holds how the revision uses the first two. It names the exclusion rule "instantiation exclusion" and gives it in two parts: which instantiations of a generic exclude each other (`types.tick:355-360`), and, in its note, a rule on trait declarations (`:361-376`). The revised `Specification/` takes that form: the first part in its chapter on types, the second in its chapter on traits. It adds a `covariant` modifier for a trait's static parameters, which neither path implements and which is future work, off the path to microGPT (P-62). Third, it says that `Bottom` cannot be written in a program, as `Specification/basic/types-vals-vars.tex` already says of `BottomType`.
- P-26 **The team's later decision wins over its earlier one, in a text or in code, where the team made it the language's rule.** P-7 names the texts, from the Working Draft to the POPL 2019 paper. Code counts as a decision where the team built it alike for all its types, or stated its rule in a commit message, a comment or the checker. Code that its author called a stub, and code that works around a limit of the JVM or of the checker, serve only the implementation. The decision that they depart from stands. "Later" is the date of the team's work on the point at issue. The revival revises `Specification/` to follow a later decision. The one library follows it too, in place of the team's earlier code, such as the interpreter's library. Where two later decisions conflict, the goal decides (P-8). The implementers' later word also outweighs unfinished text. Why: the Working Draft's early text was a wish. The type group, the part of the team that built the type checker and the compiler, then worked to make the language run. So they learned what is feasible. They sought performance, and specialization was a must. Their later decisions include the exclusion rule, specialization and the number types of the compiler's prelude, siblings from 2009 to 2012 (P-43). The revival knows less than they did, so it does not second-guess them.
- P-27 **What a program builds that a more mature library would hold goes into the library, in the library's own way.** A program written on this library has a part that states its algorithm, and it can have a part that builds domain-independent machinery that the library lacks, as both microGPT programs do. A form of that second part goes into the standard library when, on reasonable judgment, it is not an extension of the program's own domain; a form that the library has for one number type, rank or sibling trait and lacks for another is the plainest case. Whoever writes it there first studies how the library does the same kind of thing, and follows that pattern, such as its `excludes` clauses. This rule governs how the library is extended; it does not choose between two of the team's designs of the language (P-26).
- P-28 **Fleshing out the standard library is a very important task.** Its next layer is algebra: traits such as `Ring` and `Field`, which the library does not declare yet, and what machine learning's matrices and tensors need, so that the library's algebraic traits, such as `AdditiveGroup` and `MultiplicativeRing`, reach them too. Why: the curator wants those matrices and tensors to have the mathematical rigour that the library's way of building its types promises. The work edits the standard library itself, in `Library/`, not a separate tree of the revival's own outside it (P-27, how the library is extended). It is parked off the path to microGPT compiled. Two matrix ideas of his wait beside it: square matrices of one size as a multiplicative ring, and diagonal matrices of one size as a ring whose product commutes.
- P-29 **Walk's speed is irrelevant to every judgement of Fortress's performance.** Walk is far slower than Python's interpreter (`explorations/microgpt-port.md`, "Step-0 results", a measurement of 2026-08-23). Fortress's performance is judged on the compiled path, once the compiler runs programs. So no performance decision rests on walk's timings. In particular, until microGPT runs compiled, C4, the flat microGPT program, is not edited for speed. The gate never runs microGPT's two programs, C4 and the APL-style program, because they run too long to be tests. Why: walk is the unoptimised path, as a debug build is in Swift, where performance is not judged either.
- P-30 **The check of microGPT under walk after a batch must take less than a minute.** A batch is a set of tasks, each called a rung, that agents build at once and land together. The minute is the curator's goal, for a check that runs only about two forward-and-backward passes of the model, not a full training, and compares the results with reference values. That is enough to show that the model's mathematics still works, and that the library's changes, such as those to the arrays, did not break it. A slower check is to him a waste of time. The commit stage of each batch, the step that lands its changes, runs the check as `explorations/coordinator/tools/mg-run.sh`, the quick versions of microGPT's two programs at once, outside the gate.
- P-32 **The record's maps are kept current and used, so that nothing that the record holds is worked out again from scratch.** The maps are `FACTS.md`, `INDEX.md` and the territory map, `explorations/coordinator/map/`. The territory map surveys the repository down to where the team wrote the intent of each design. Part of that intent is written only in the papers under `Papers/`, not in the specification. So the map covers the papers too, and shows where to look up a design's intent. `INDEX.md` is read whole at the coordinator's boot, at the start of each session and after each compaction, and each worker's brief carries a mission briefing from the territory map, not the whole map. The territory map's surveys date from 2026-09-16 (its README), so a status or a line number in them can be stale.
- P-33 **The work toward microGPT compiled follows the phases, in the order that the curator approved.** These phases are steps of the work, not the compiler's phases, and they are numbered 3 to 6, after two earlier ones. Phase 3 ends when the compiled checker reports no error on the apis and components of the interpreter's library that the distance to the switch-over counts (F-53 defines the distance, says what it counts and holds its value). The library's other components are not part of phase 3: each is cleared before the first program that needs it, and at the latest before walk runs the checker (P-12), so `System` by the switch-over, since the compiler's tests need it (F-293); F-290 counts their errors. Phase 4, the switch-over: first the natives, the library's `builtinPrimitive` bindings made to run on the compiled path, then the compiled path reads the interpreter's library and the compiler's prelude is deleted; phase 5, microGPT compiles: its static types, the array design and the code generator's open gaps; phase 6, microGPT runs fast. Code-generator work goes on beside that order, under either library (P-37). Row 320, an api implemented by a component of another name does not link, is part of the switch-over's design.
- P-175 **On the compiled path a call's arguments run in parallel where `ParallelismAnalyzer` judges them worth a task, as a tuple's elements do, so a reduction's two halves run in parallel; the one library's parallel range stops its split at a grain size, not at single elements.** The one library's range joins a reduction's halves as the arguments of one call, `red.join(loop'(lo, mid-1), loop'(mid, hi))`, and splits down to single elements (`Library/RangeInternals.fss:1308-1342`); the code generator evaluates a call's arguments in order (F-19, row 951), under the team's comment "Why isn't this parallel???" (`compiler/codegen/CodeGen.java:7068`), so every `SUM`, `DOT` and `BIG MAX` of microGPT would run its bodies one at a time once compiled programs run the one library. The split stops at a chunk that runs efficiently in sequence: in his words, "you need the right forking constants", as Steele's parallel trees end in sequential leaves and Clojure's persistent vectors take their branching factor from B-trees. It needs a group of forked arms to join every arm before it completes abruptly, which the compiled path does not do (`CodeGen.genParallelExprs` joins on the normal path only, row 947; `reviews/parallelism-foundations-2026-11-08.md`, section 7.1). The library binding the halves as a tuple, and reductions left in sequence, are declined. Why: the specification evaluates each argument of a call in an implicit thread of its own (`Specification/basic/evaluation/parallelism.tex:60-64`), walk forks a call's arguments (`interpreter/evaluator/Evaluator.java:342`), and the model's parallelism is its reductions (the review, section 6). Detail: the review, sections 1.8, 6, 7.1 and 8.

### The one library and the compiled checker

- P-37 **One library, the interpreter's, is the library that the compiler checks.** The interpreter's prelude, `FortressLibrary` and `FortressBuiltin`, becomes the compiled path's prelude in place of the compiler's own, and the compiled path reads the interpreter's library with it. Why: the switch-over spares porting the interpreter's library into the compiler's; the revival develops the checker until it accepts that fuller library. The curator sees the compiler's prelude, its own library files `CompilerLibrary`, `CompilerBuiltin` and `CompilerAlgebra`, as a bootstrap to remove. So no declaration is added to the compiler's prelude, and at the switch-over its three files are deleted and their tests kept (P-38 says which tests are respelled; F-293 holds the compiler's fourth file, `CompilerSystem`). The one exception is the numerals: until the switch-over the prelude carries the design of P-174 and P-176, so that both paths treat a numeral alike before it, and that copy goes with the prelude. The decision settles which files survive, not the designs inside them: the one library takes a design of the prelude's where it is the team's later decision, as it took the prelude's flat shape of the number types. This decision does not stop work on the code generator, which is compiler work under either library.
- P-38 **The compiler prelude's own text is not repaired: its defects go with it at the switch-over.** A helper of `nativeHelpers/` that the one library binds is fixed for the one library, and the prelude's value moves with it (F-313). Its `Maybe` block and its `REM` guard `if other = -1 then 0` stay as landed until the prelude is deleted, and their tests stay. Then the compiled tests respell its reversed wrapping and saturating operators (row 348), `ZZ64`'s compiled shift closes (row 381), and the specification's `shift` reaches the compiled path (row 383). `XXXShiftDeclRungI` is then promoted, and the switch-over batch finds the compiler tests that bind `shift`, a reserved name from then on.
- P-39 **Every batch's gate measures the checker count, and its total never turns the gate red.** A batch is a set of tasks, each called a rung, that agents build at once and land together. Its gate runs the gate's steps on their merged tree, and then the checker count, as step 8 (`explorations/coordinator/climb-batch-workflow.md`); the gate of `fortress-repo`'s gate part has no such step. The checker count and the distance to the switch-over both count the compiled checker's errors on the interpreter's library. The count stops where the checker crashes or meets an error that it cannot get past; the distance counts every error, over all apis and components (F-53 defines both and holds their values). A rise of the count's total is reported and never fails a batch on its own. The count's stage can still turn the gate red on the faults that F-66 names. One is a checker crash that no rung of the batch listed in advance as expected, in the field `expectedCheckerCrash` of the batch's manifest, the part of the batch's script that declares each rung's task. Until the switch-over lands, every batch's gate also measures the distance, in a stage that only reports. Why: the count checks only the `FortressLibrary` component (F-53), so a native binding moved onto a helper in another component is checked by the distance alone, and P-58 has each moved binding checked from the step that moves it.
- P-40 **Sizes are checked, and a size that inference leaves unknown is an error only where it is used.** A size is a `nat` or `int` static parameter, such as the length of an array in its type. The compiled checker checks sizes, and refuses a size beyond `NN32` or `ZZ32` (F-140, the bound on both paths). The bound is this implementation's, for the sizes of arrays, vectors and matrices, to match the JVM's `int` indices; a numeral type's four static parameters have none, and read as values are `ZZ` (P-174). Wherever the array design, the compiled path's design for arrays (P-85), creates a JVM array, it checks the length there, at run time, and refuses one over 2^31-1. A size that inference leaves unknown is an error only when it reaches a type, a name or a value. So a declaration may declare a size that none of its types uses, and pass. A call that cannot fix a size of the declaration that it would choose is refused, also inside an overload set, instead of passing over that declaration. In the rule that no type extends two different instantiations of one generic trait, two instantiations differ when any static argument but an operator differs, so `Vec[\3\]` and `Vec[\4\]` are two; boolean arguments count too once the checker has boolean parameters. A size used as a number, as in the range `0#n`, converts to `ZZ32` where one is needed, as a numeral does. The 17 vector and matrix operators of the `FortressLibrary` api declare only the sizes that their types use, the change of `explorations/perf-probes/array-sites/e3-rebased.patch`. It finishes the team's own fix of 2008, which removed those sizes from the component only. The JVM length check waits for the array design; under walk such an array stops at its store's factory with walk's own error, which no catch sees (row 527). The checker still passes over a declaration whose unfixed size occurs in its own parameter type (row 400). The checker compares no boolean arguments (row 406).
- P-41 **On the compiled path, a size static argument travels at run time as a descriptor object, as a type argument does.** A generic type's descriptor has a field for each of its static parameters that is not an operator. The team's code generator already emitted that field for a size, with nothing to put in it, and the size's descriptor fills it. Each size value, such as the 3 of `Vec[\3\]`, has one descriptor, which `RTTIsize.of` takes from a table; no Java class is written for it. This is the team's pattern for instantiating types, applied to numbers. An operator static argument, by contrast, stays a name known only at compile time (F-39, how both paths carry it). The curator sees no need for an operator argument to be carried at run time the way types and sizes are. F-129 holds what runs and its open rows.
- P-42 **A type parameter declared without a bound has the implicit bound `Any`, not `Object`.** `Any` holds tuples, functions and `()`, which `Object` does not. The library instantiates its generic containers at tuple types: its arrays indexed by pairs, such as `(ZZ32,ZZ32)`, are among them. The specification states the bound `Any`, with a callout that records that the Working Draft of February 2011 said `Object`.
- P-43 **The exclusion rule stays, and the number tower is flat (route A).** The compiled checker keeps the multiple instantiation exclusion rule. So the library's numbers are flat, as the team (Chase, Ryu, Maessen and Allen) flattened the compiler prelude in 2009 and 2010. The fixed widths, `ZZ`, `QQ` and `RR64` are siblings under `Number`, each with its own algebra, and `Number` has no catch-all operators. Why: the flattened prelude is the team's last record of the Fortress way, and its route leads to the POPL 2019 paper, which keeps the rule. He cares that specialised code runs fast, not how a specialisation is chosen. F-46 prices a return to route C.
- P-44 **`AnyIntegral` stays closed by its `comprises` clause, and the compiled checker reads the clause as the team's 2012 texts do.** The library's `AnyIntegral`, whose `comprises` clause lists the five integer types `ZZ32`, `ZZ64`, `ZZ`, `NN32` and `NN64`, stays closed. Beside the clause stays a comment in the team's `NOT YET` form, by which the team's library records a clause that it cannot write yet: here `comprises Integral[\I\] where [\I\]`. The `where` form is built (P-151), but neither path takes this clause yet: the front end of both paths refuses it on a trait that declares a coercion (row 831), and walk refuses the library at load with it (row 804). `Integral[\I\]` extends `AnyIntegral` and is not in the list. The checker accepts such a generic trait below a closed trait when every type that the checker knows below it is listed. The clause's text in the library, and walk, stay as they are. Why: the team's 2012 texts, Luchangco's Types chapter and Welterweight, are its later word (P-25), and by them the clause is right as written. The rule leaves a hole that every way of closing `AnyIntegral` shares, except the team's 2008 way, a `comprises` clause on `Integral[\I\]` itself: a program's own subtype of `Integral`, declared in another component, is accepted although no listed type is above it. Row 487 records the hole, and this decision does not close it.
- P-45 **Overloaded declarations may differ in their static parameters.** The specification drops its sentence that forbids this, and keeps it as superseded text. It states instead the overloading model of the type group's 2011 paper (`Papers/Types/`), which the compiled checker already used. The checker keeps the paper's three rules: No Duplicates, Meet and Return Type. It checks the Return Type Rule over every instance of a generic declaration that the argument types allow, not over one guessed instance. One rule of the old sentence survives: if one generic declaration is more specific than another, their static parameters must line up position by position, as Java's rule for overriding a generic method requires. The compiled checker tests it only where the two declarations have as many static parameters of their own (F-75). Walk chooses among overloads by the parameter types that each declaration declares, not by the order in which they are written. At load, walk judges each pair of two generic declarations by the checker's rules on their declared parameter types. It does not refuse a pair only because none of their parameter types exclude, as when one declaration is more specific than the other. Walk and the checker must accept the same pairs. The library repairs, by declarations of its own, the overload sets that the checker refused, and no line of microGPT's two programs changes. Where walk or the checker still judges a pair against these rules: walk compares two functional methods of a generic trait or object on the instance that a call makes (F-26); both paths refuse the paper's own valid example (row 539); walk refuses two generic functional methods of a trait without static parameters whose declared domains lie one inside the other, and fails at a call on such a pair in a generic trait (rows 779 and 780); and walk and the checker disagree on three kinds of pair (rows 786 to 788).
- P-46 **A conversion only makes a call possible: it never changes which declaration runs when one already fits.** The declaration that runs is chosen on the parameter types that each overload declares: first those that apply, then the most specific of them (P-45). A generic declaration applies if some type within its bounds takes the arguments. Only then is the chosen declaration instantiated by promotion: at the narrowest type into which its arguments coerce (P-74). So beside `op(a: Any, b: Any)`, `op[\T extends Number\](a: T, b: T)` applies to a call with a `ZZ32` and a `ZZ64`, at `T = Number`. It is the more specific, so it runs, at `ZZ64`. Why: the curator wants fast generic code that a JVM can specialise. His own broader rule is not taken: to apply any conversion that reaches a specific declaration, and to fall back to a plain one only when none does. Walk and the compiled checker both infer static arguments with coercion, by the same promotion. The compiled path inserts the conversions statically. P-49 gives the order in which the checker tries a call. Row 537: the compiled dispatch between two generic declarations of one name with different bounds.
- P-47 **Each integer type declares its own `MIN`, `MAX` and `MINMAX`, instead of relying on those that it inherits from the generic order traits.** The integer types are the five that `AnyIntegral` lists: `ZZ32`, `ZZ64`, `ZZ`, `NN32` and `NN64`. Through `Integral`, each inherits the three operators from `StandardTotalOrder` and the `StandardMin`, `StandardMax` and `StandardMinMax` that it extends. `a MINMAX b` is the pair `(a MIN b, a MAX b)`. The `MAX` that a `ZZ64` inherits types `self` as the order trait, so neither it nor `QQ`'s `MAX` is more specific. Under walk, `b MAX 1` for a `ZZ64` `b` would then stop the run with "Ambiguous coercion". With their own declarations, these operators answer at the type that their arguments promote to (P-74), as `b + 1` does. Why: it is the library's own device. `QQ`, `RR64` and the compiler's prelude declare all three, and the specification's `ZZ` declares its own `MIN` and `MAX`.
- P-48 **A type parameter that a call's arguments do not fix takes its bound, never `Bottom`.** The arguments leave a parameter unfixed when it occurs only in the result type; when two arguments meet at it with no narrowest type into which both convert (a `ZZ32` and a `ZZ64` have one, `ZZ64`, by P-74); or when dispatch, at run time, picks a generic declaration and must choose the instance to run. Its instance is then the intersection of its upper bounds (`Any` if it has none). At checking, that is narrowed by what the call's expected type (P-49 defines it) requires of the declared return type; at run time, by the static type that the checker gave the call. It is never `Bottom`, never the union of the arguments' types, and never the value's type alone. The rule sets the instance, not which declaration runs (P-46). Why: the rule is the team's later word, from the POPL 2019 paper on multiple dispatch, and the curator trusts the team's later work above his own understanding. The rule changes nothing in microGPT, whose types are concrete. The library keeps the team's declarations of `fail`, `builtinPrimitive` and `List`'s empty comprehension, whose type parameters have no written bound, without the `extends Object` that a batch had added. Under walk, which has no static types, dispatch takes the value's type. Row 538: a compiled dispatcher that carries the static type that the checker gave the call, so that a generic declaration reached only at run time gets this instance. Rows 587, 591 and 612: three cases in which walk still gives `Bottom`.
- P-49 **The compiled checker tries a call first by subtyping, without the expected type, and coerces its arguments only when that attempt is not kept.** The expected type is the type that the call's context requires. The checker's first attempt checks the call by subtyping alone, without the expected type. It keeps that attempt when its result converts to the expected type, by coercion if need be. If it does not keep that attempt, it tries coercion of the arguments, with the expected type. So a declaration that fits the arguments as they are is not passed over for one that coercion reaches. Why: in the curator's words, coercion should be tried when there are no matches.
- P-50 **The body of a `label` expression, and each value that an `exit` gives it, take the expected type of the whole `label`.** A `label` is a named block that code inside it can leave early with `exit`, giving a value with `with`. The specification types a `label` as the union of its body's last expression and the values that its `exit` expressions give. So when a `label` has an expected type, the compiled checker passes it into the body and into each of those values, as it does into each clause of a `typecase`. The specification's inference chapter lists the body and those values as contexts that carry an expected type. P-51 decides the same question for a call written as another call's argument. F-87 lists the checker's contexts that carry an expected type.
- P-51 **The checker retries a call written as another call's argument against each declaration's parameter type.** Take an outer call `f(g(x))`, whose argument is an inner call `g(x)`. ### Numbers

- P-66 **The integer principle: Java's and the JVM's defaults stay where they make sense, and are corrected where they fail high performance or mathematical precision.** The team did so with rounding. A hardware behaviour that bytecode can express gets its own explicit spelling, as the specification's wrapping and saturating operators do. Where the JVM prevents a correct implementation, the project gives way for now. The peers to compare are Julia, X10, Swift and Rust.
- P-67 **`round` on an exact half goes to the even integer, on both paths.** Under walk and on the compiled path, `round(2.5)` gives 2: an `RR64` or `RR32` value rounds an exact half to the even integer, as a rational does. This is the specification's rule for rationals, the default rounding of IEEE 754, and the rule of the team's own `round` on rationals.
- P-68 **On the float types, `floor` and `ceiling` return the same float type, while the brackets ⌊x⌋ and ⌈x⌉, `round` and `truncate` return `ZZ`, the unbounded integer.** So `floor(2.5)` is the `RR64` value 2.0, and ⌊2.5⌋ is to be the `ZZ` value 2. - P-69 **`LSHIFT` and `RSHIFT` are bit operators on the fixed-width integer types, and `ZZ`'s `shift` is exact.** On `ZZ32`, `ZZ64`, `NN32` and `NN64`, a shift loses the bits that it shifts out, silently, as in every peer language. A count at or beyond the width gives 0, or -1 for `RSHIFT` of a negative value, and a negative count shifts the other way, as Swift's and Julia's shifts do. The count may have any integer type, and the shift works at the width of the value shifted. On `ZZ`, the unbounded integers ℤ, `shift(x, k)` is ⌊x·2^k⌋ at any count; there the specification defines `x LSHIFT k` as `shift(x, k)` and `x RSHIFT k` as `shift(x, -k)`. On the compiled path, a shift of a fixed-width value works on the JVM's `int` or `long`, never through `ZZ`. Why: a shift through `ZZ` costs speed wherever the JVM cannot remove it. Row 442: the compiled `NN32` and `NN64` shifts, refused today. Row 383: `ZZ`'s `shift`, which the compiler's prelude does not declare. Row 381: a count of another integer type, where the compiled path refuses a `ZZ`, `NN32` or `NN64` count and computes a `ZZ64` count on a `ZZ32` at 64 bits.
- P-70 **`GCD` and `LCM` give nonnegative results, and `LCM` raises `IntegerOverflow` when the multiple does not fit its type.** So `0 GCD -4` is 4 and `1 LCM -5` is 5, and on `ZZ32`, `(2^31 - 1) LCM 2` raises. Row 442: `GCD` and `LCM` on the compiled path's `NN32` and `NN64`.
- P-71 **An overflow guard tests for the type's most negative value, not for `a = -a`, so `|0|`, `-0` and `0 DIV -1` do not overflow.** On a signed fixed-width type, only the most negative value overflows when it is negated, taken in absolute value or divided by -1. The test `a = -a` is true for that value, and also for 0. Walk already gave 0 in the three cases. On the compiled path, the natives of negation, absolute value and division on `ZZ32` and `ZZ64` test for the most negative value. - P-72 **`narrow` keeps the low 32 bits of a value that the narrower type cannot hold, signed and unsigned, on both paths, and raises no `IntegerOverflow`.** The decision covers `narrow` from a `ZZ64` to a `ZZ32` and from an `NN64` to an `NN32`. Where nothing fixes a type the numeral is an `RR64` (P-173): `Cell(0.5)` is a `Cell[\RR64\]`, and a bare numeral prints as that double, so `"" 2.50` is `"2.5"`, and the team's `tests/NumberPrintTest.fss:16`, which asserts that a numeral prints as written, changes. `RadixPointNumeral` stands beside the number types, as the compiler's prelude declares it (`LibraryBuiltin/CompilerBuiltin.fss:890`), in place of the interpreter library's `value object FloatLiteral extends RR64` (`FortressBuiltin.fsi:44` at `b430f9f42`). Walk converts such a numeral from its exact value where its place fixes a type, at a binding, a parameter, a field and a declared return type, so `y: RR64 = 0.5` is `SEQV` a computed `0.25 + 0.25`. The specification's literals chapter and the coercions of `basic-lib/numbers.tex:43` follow, with an Appendix I entry, in the revision form (P-96). A numeral at `round`, `floor`, `ceiling` or `truncate` converts into `RR64` by P-173's reading of a tie among `QQ`, `RR32` and `RR64`, so one within half an ulp of a tie rounds as its nearest double, not as the rational: `round(2.50000000000000001)` is 2. No line of microGPT changes, and by reading its numerals keep their bits. Why: the Working Draft keeps a numeral unconverted, since "converting it immediately to a floating-point number may lose precision", gives 3.125 "the rational value 3125/1000", has the library coerce a compound numeral to the rationals, and converts a static rational expression into a float with "at most one floating-point rounding error" (`Specification-1.0-frozen/basic/expressions/literals.tex:132-173`); the curator reads it so: nothing is lost in `QQ`, and a float of fixed size takes one rounding.
- P-173 **A numeral converts where it stands: where its place fixes a type, into that type at compile time from its exact value; where nothing fixes one, into the machine default, a `ZZ32`, or a `ZZ64` or `ZZ` when its value does not fit, and with a radix point an `RR64`.** A place fixes a type when its declared type has a coercion from the numeral type, as the eight number types have and a program's own type may (P-174); `Any`, `Object`, `Number`, an unbounded type parameter and no declared type take the default. So `x = 3` is a `ZZ32`, and `x SEQV z` is `true` for `z: ZZ32 = 3`; `bigN = 3000000000` is a `ZZ64` at its binding (row 946). The default applies to a numeral, a literal after the fold, never to an expression of a numeral type, and a `nat` parameter used as a value is a `ZZ32` where it is a size (P-40), and a `ZZ` where it is one of a numeral type's four numbers (P-174). A type parameter that several numerals fix takes the narrowest default that holds every value, an `RR64` where any has a radix point, each numeral converting into it exactly; a float numeral whose conversions into `QQ` and `RR64` tie reads `RR64`. At a typed place the conversion is exact or rounds once (P-76, P-172), and a numeral outside the type's range is refused statically; walk converts from the exact value at the same places, place by place, before it runs the checker (P-12). An expression of numerals alone folds exactly before the checker into a signed constant, which defaults as an integer numeral, as a `QQ` for a quotient, or as an `RR64` with a radix point: so `x = 7/2` is a `QQ`, `1/2 = 0.5` is `true`, and `-2147483648`, prefix minus on a numeral, folded, is a `ZZ32`. `gg(5, w)`, with `gg` declared at `(ZZ32, T)` and at `(Any, Any)`, runs the `ZZ32` declaration (P-49). Why: the design completes the Working Draft's, whose numerals have types of their own so that a library decides by coercions how they meet other types (P-174 gives that ground). It bends P-26 in two places, the numeral types, whose names and static parameters are the Draft's (P-174), and the places that fix no type, where the compiler's prelude, the team's later word, keeps the numeral's own type; the curator takes the bend by his right to finish the specification. He declined exact defaults, `ZZ` and `QQ` (the 2012 restart gives `NN` and `QQ`, `literals.tick:25`), since microGPT's untyped hyperparameters (`MicroGptFlat.fss:18`) would then be rationals and every untyped index would need `asZZ32`. The Draft's text that it contradicts, for Appendix I: numerals "not directly converted" and "polymorphic" (`Specification-1.0-frozen/basic/expressions/literals.tex:132-141`) at places that fix no type, and a `nat` parameter usable wherever an `NN32` variable is (`basic/trait-parameters.tex:84-86`); P-174 names the binary chapter's, which it leaves out. What it keeps and changes in form: the judgement's section 3, but for the numeral types' form, which P-174 holds. Detail: `reviews/literal-design-judgement-2026-11-08.md`, sections 1 to 6 and the 42 test programs of its appendix; the prototype, `compile-ladder/plan-29/probes/literal-default.md`.
- P-174 **A numeral's type exists only at compile time: the Working Draft's `NaturalNumeral` or, with a radix point, `RadixPointNumeral`, below `Numeral`, with its four numbers as static parameters; every number type, the library's too, takes a numeral through a coercion generic over the four numbers.** The four numbers are the digit count `n`, the digits after the radix point `m`, the radix `r` and the digits read as one integer in that radix `v` (`Specification-1.0-frozen/basic/expressions/literals.tex:83-129`), so `3.125` is a `RadixPointNumeral[\4, 3, 10, 3125\]`; the four are naturals of any size, and read as values in a coercion's body they are exact integers, `ZZ`; this implementation's `NN32` bound (P-40) is for sizes. The coercion's body calls the type's constructor on values computed from the four numbers, as in `coerce[\nat n, nat m, nat r, nat v\](x: RadixPointNumeral[\n, m, r, v\]) = Interval(roundDown(v, r, m), roundUp(v, r, m))`, and the compiler instantiates it for the numeral and folds it (P-176). No numeral value exists when a program runs: a numeral type has no getters, no `asFloat`, no `asString` and no `=` with a number type, and is written only as a coercion's or an operator's parameter type. A numeral has no sign: at a program's type `-3` is the type's own prefix `-` applied to the coercion's result for `3`, and a type without `-` refuses it; any other expression of numerals alone folds first (P-173) and reaches such a type only through its coercion from the folded value's type, such as `QQ` for `1/2`, since coercions do not chain. The design leaves out the binary chapter's numeral coercion and `opr ||` (`Specification-1.0-frozen/advanced-lib/binary.tex:1620-1662`). Why: the Draft gives numerals types of their own so that "library designers [can] decide how numerals should interact with other types of objects by defining coercion operations", and has libraries define the coercions into integers and rationals (`literals.tex:132-148`); the curator finishes that design, in place of the implementations' `IntLiteral` (P-76) and `FloatLiteral` (P-172). Rows 960 and 974 hold where the tree departs: the digit count of `00.5`, and walk running a numeral type written as a static argument or as a type that an object or a trait extends.
- P-176 **A numeral at a place denotes one value, the same on both paths and made once: the compiler folds the coercion instantiated for it (P-174), and walk runs that coercion at the place's first evaluation.** Where the result is a JVM `int`, `long`, `float` or `double`, the class file holds it as a constant; otherwise, as at `QQ` or a program's own type, the constructor call on the constants runs once per place, into a `static final` field filled when the class loads, and a program's type's own `-` on the numeral (P-174) runs there too. Walk fixes the coercion's static arguments from the numeral's four numbers and keeps the result for the place; it refuses a numeral only when the place runs, until it runs the checker (P-12). Before the switch-over the compiler's prelude carries this design (P-37), so that both paths give one value at one place. Why: a numeral is a constant of the program, and a JVM class file holds no object, so a field filled once at load is the nearest form of an object constant. Rows 957 and 971 hold where the tree departs: a place whose type names a type parameter, and a coercion that spawns a task.

### Arrays and the model program

- P-84 **On the compiled path, the array of every number type is to be stored unboxed, in a Java array of its primitive type, and every array is to have the most efficient store that its element type allows; arrays keep the team's `nat` sizes in their types.** `RR64` goes in a `double[]`, `ZZ32` in an `int[]`, and so on, for each number type that has a Java primitive type; `RR64`'s `double[]`, the model's, is the first case. Why: a high-performance language cannot box its array elements, and the sizes are central to the team's design. So the storage and the sizes are one design: the sizes stay in the array types as `nat` static parameters, as the library's `Vector` and `Matrix` declare them, and the compiled checker checks them. The sizes do not wait while a first version of the store carries them only as run-time fields; that layered plan was rejected. Both halves follow the library's own patterns (P-27, on extending the library in its own way). The compiled checker checks `nat` static parameters (F-67). The class loader, as it makes a generic instance's class, only renames the type parameter, so it gives no instance a `double[]` field; a loader that would, way A4 of array decision A (P-85), is unmeasured (F-18).
- P-85 **The array design's three questions are open, with no default, and return after the switch-over with the array decisions A, B and D.** The array design is the compiled path's design for arrays. The three questions: how the array factory chooses the store of each element type; whether the store also keeps the size as a field, beside the size in the type; and whether a factory for a size known only at run time returns the unsized `Array[\E,I\]`, whose type holds no size. These questions are apart from decisions A, B and D: decision A is how an array of a number type, made through the library's generic array traits, gets its unboxed store, `RR64`'s `double[]` first (P-84); B is where unboxed arithmetic happens; and D is the sizes in the model's own types (P-87). The whole preparation for the array work is to be done before the switch-over; only the work itself waits.
- P-87 **The model's text is the notation, and the vocabulary is repaired around it.** The model is microGPT's two programs; the vocabulary is the array operations that they are written in (`FlatArrays.fss` for C4, the flat program, and `FlatArrays2.fss` for the APL-style one). No operator in the model is replaced by a function call to pass an overload check, as a proposed repair once wrote `planeSum(mask, x)` for `mask + x`; the vocabulary changes instead. Any repair that changes a line of the model is shown to the curator as a diff before it is built. Decision D, still open and returning after the switch-over with the other array decisions (P-85), is such a diff: it gives C4's arrays sized types, in its vocabulary's signatures and in the model lines that these force (`explorations/reviews/decision-d-diff.md`; the patch itself is only in git, in the parent of `84aef6a4f`). Nothing of decision D is applied before microGPT compiles, after the switch-over.
- P-88 **The model's vocabulary leaves `+`, `-` and `MAX` between an array and a scalar to the library's scalar-extension block, and its diagonal keeps its own product.** The vocabulary, the array operations that microGPT is written in, declares none of these six operators, an array with a number on either side; the library's scalar-extension block, in `Library/FortressLibrary.fss`, serves them. `Diag`, the vocabulary's diagonal matrix, extends `Matrix` and overrides `mul`, the method that the library's matrix product calls, so `diag(v) m` scales the rows of `m` without forming the matrix. This is what the type system promises: a diagonal is a kind of matrix, with a faster product of its own. Row 299 records what the general product costs on a diagonal: 13 to 54 times as much as scaling the rows. Since the diagonal is read-only, a read-only matrix trait, `ReadableArray2`, which `Array2` would extend as `Array1` extends `ReadableArray1`, is also wanted (row 798): it is a library change, not a definition in the vocabulary.
- P-89 **`fill` takes a value, `tabulate` a function.** On the library's arrays, `fill(v)` fills an array with the value `v`, even when `v` is a function, and `tabulate(f)` fills it with `f` applied to each index. The function form, formerly an overload of `fill`, takes Scala's name `tabulate`. Why: in every peer language that has `fill`, `fill` takes the value.
- P-90 **`Maybe`'s empty case is the team's parametric `Nothing[\T\]`, in the one library and the specification.** The bare `Nothing` is future work: it needs a `where` clause that binds a type variable in an `extends` clause, which neither path implements, and it is not tried before then. Gating row 331 on static-argument inference instead is parked.
- P-91 **What an object with no `asString` prints: its bare Fortress type name, walk's spelling, on both paths.** An object with no `asString` of its own prints its Fortress type name as walk spells it, such as `Box`, or `Box[\ZZ32\]` for an instance of a generic object, with no marker and no hash code. A debug marker, such as the Java class name that the curator first leaned to, belongs in `asDebugString` if one is still wanted, not in the printed form; walk's `asDebugString` prints `a Box: Box`. Row 363: an `asDebugString` that prints as walk's does, where the compiled one prints `Box`. Row 321: printing an object that declares or inherits a zero-argument member named `toString`, which overflows the stack. Once the compiled path reads the one library, every object inherits such a member, the `getter toString` of that library's `trait Object`, so every object with no `asString` meets the overflow.

### The specification's revision

- P-95 **Every change to the specification is recorded with its reason.** When the revival changes the language, it updates `Specification/` with the change, so that the text and the implementation do not disagree. The original text and the reasoning are kept, so that route C stays open. Route C is the design that P-43 set aside: a nested number tower, under the forest rule of the team's 2012 patent applications (F-46 gives what a return to it would need). Every such change takes the revision form (P-96 gives its parts). The unrevised copy, `Specification-1.0-frozen/`, is never touched. Why: an open disagreement between the text and the implementation would confuse a reader.
- P-96 **A change of the specification is shown in layers, as the team showed its own changes in the 1.0 release of 2008 and in the working draft of 2009.** This form is the revision form. A callout that prints in every build marks each changed passage; a `\note` will not do, since a release build hides it. Appendix I's revival section has an entry for each change: its reason, its original text, what a return to route C would mean for it, or that it would be the same under route C (P-95 says what route C is), and the decision that it follows. The front matter has one paragraph on the revision, and a document in the repository holds the full reasoning. Citations call the unrevised copy, `Specification-1.0-frozen/`, the Working Draft of February 2011: the copy is that draft byte for byte, and only its `fortress.1.0.pdf` is the 1.0 release (F-163). The `fortress-repo` skill's `references/specification.md` gives each part in full, including what else an Appendix I entry holds.
- P-97 **The specification's examples that break the exclusion rule take the library's shapes, and each original stays, marked "Not allowed".** The Working Draft offered such examples as legal. Each now shows the shape that the library uses for the same thing, with the original beside it under the specification's own mark, "Not allowed". - P-98 **`TotalComparison` extends `StandardMinMax[\TotalComparison\]`, so that the library's `BIG MIN` and `BIG MAX` work over total comparisons.** It does so in the library's api and component, `Library/FortressLibrary.fsi` and `.fss`. ### The suites and the gate

- P-102 **Test first, the test kept.** Every edit of source code in the original tree starts from a failing test. The worker adds the test to the test suite, sees it fail, makes the fix, and sees it pass. The test then stays in the suite for good. An edit of the specification or of documentation is not source code and needs no test. The gate's three test runs, `ant testFast`, `ant testSystem` and `ant testSpecData` (P-124), must pass when the work lands; they need not pass after every edit. The test and the fix may land in one commit. Why: the rule replaces one-off validation scripts, which no later build runs. The `fortress-repo` skill's `references/tests-writing.md` says how to write the test.
- P-103 **The suite's verdict is the check.** A test's result is pass or fail, as the team designed the suites. A value that matters is checked inside the test, with the checks that the harness already has: an `assert` call in an interpreter test, a `run_out_equals` key in a compiled test's `.test` file. What a test prints beyond its checks does not count. So no expected-output files are added. They are not proposed to the curator again, and neither is a comparison of what a test prints beyond its checks with an earlier run's output. Why: when the suite's designers let a test pass without a further check, what it prints need not be checked.
- P-124 **The specification's examples are a step of the gate, and every one must pass.** `ant testSpecData` runs the examples extracted from `Specification/` under walk (F-114 says which 130 it runs), and the gate fails if any of them fails. When an example fails, the implementation is fixed: the example is not respelled to get around a gap in walk, and no list of examples allowed to fail is kept.
- P-125 **The suites run Fortress in parallel, pinned at four threads in `build.xml`.** `build.xml` sets `FORTRESS_THREADS` to 4 for the two suites, `ant testFast` and `ant testSystem`, so that every run of them uses four threads, whatever the calling shell sets. A test that parallelism makes fail, on every run or only on some, is written wrong, for example a write that needs `atomic`, or it shows a defect. Either is fixed, never hidden by running at one thread. Why: Fortress is parallel by default, so a suite at one thread has a blind spot, and sparing the four-CPU machine is no reason for one.
- P-150 **No resident compiler is built.** A background JVM that serves Fortress commands, as Scala 2's `fsc` did, would save too little of the workers' time to be worth building (F-234), so the speed work goes to the checker itself (P-148). It is not tried again unless something significant changes.
