# R1: the record

## FACTS.md

Four lines. The first is the rung; the other three are facts it established on the way and which the next worker should not have to rediscover.

> A mutable variable declared at the top level of a component is stored in a transactional cell on the compiled path: its singleton field is `ACC_FINAL` and holds a `MutableFValue`, reads and writes route through `Transaction.TXRead`/`TXWrite` while a transaction is running, and a nested code-generation context captures the cell rather than a copy of the value (`VarCodeGen.MutableStaticBinding`, `ProjectFortress/src/com/sun/fortress/compiler/codegen/VarCodeGen.java:310-399`; `CodeGen.java:5872-5906`, `:4647-4650`, `:5908-5951`). Rung 3 (`4d419c9e8`) had emitted a bare `GETSTATIC`/`PUTSTATIC` on a non-final field, so such a variable was outside the transaction that `atomic do … end` really does start — against `Specification/basic/expressions/atomic.tex:38-42` — and a write from inside a `for` body or a parallel `do … also` arm was lost outright, at one thread as well as at four. Repaired 2026-09-19 by R1 of the repair batch; gated by `compiler_tests/AtomicTopLevelVar` (concurrent) and `compiler_tests/MutableTopLevelVarInLoop` (deterministic), both of which fail on `49ee5e91`.

> `compiler_tests` runs its programs with more than one worker, so a concurrency defect on the compiled path can be gated: the `fastTrack` macro sets `FORTRESS_CACHES` and no thread count (`build.xml:927-953`), the harness runs each program in a subprocess that inherits that environment (`ProjectFortress/src/com/sun/fortress/tests/unit_tests/FileTests.java:480-486`), and `FortressExecutable.getNumThreads` then falls back to `availableProcessors/2` (`ProjectFortress/src/com/sun/fortress/runtimeSystem/FortressExecutable.java:37-44`). The `FORTRESS_THREADS=1` pin is in the `testSystem` shards alone (`build.xml:1184`), and those run `SystemJUTest`, not `compiler_tests`. The fallback yields one worker where `availableProcessors` is 1 or 3, and on such a machine a concurrency test passes vacuously.

> The compiled world's mutable-variable cell holds `fortress.AnyType.Any`, the language's top type, not `runtimeValues.FValue`: `FValue` is an abstract class (`runtimeValues/FValue.java:13`) and a compiled closure is not one of its subclasses, so a mutable variable of arrow type failed the verifier. The defect was already in the tree for *local* mutable variables, which have always been stored in such a cell (`explorations/compile-ladder/repair-r1-atomic-static/probes/P15LocalArrow.fss`, `P16LocalArrowTask.fss`: `VerifyError` on `49ee5e91`, `f(1) = 3` after R1), and R1 fixed both kinds by widening the payload (`runtimeValues/MutableFValue.java:18-32`, `runtimeSystem/Transaction.java:20,27-28,144,152,226`).

> `run_out_WIcontains` is not implemented by the test harness: `FileTests.generalTestFailed` handles `_contains`, `_does_not_contain`, `_matches`, `_WImatches` and `_WCIequals` only (`FileTests.java:141-180`). The sixteen `.test` files that still use it therefore assert only the default "stdout contains PASS" that applies when no check matched (`FileTests.java:267-272`), so nothing is silently unchecked, but the line does nothing. Eight of the sixteen are the last climb's own new tests, because the rung briefs name `library_tests/Boolean.test` as the format to copy and that file carries the inert line; the next brief should name a file that does not. R1's two tests use `run_out_contains=PASS` and `run_out_does_not_contain=FAIL`, the form fifteen `.test` files already used.
