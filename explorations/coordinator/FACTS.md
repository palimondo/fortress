## Execution model

- Two execution paths share parser and phases and differ at the end: the walk interpreter (`fortress file.fss`) and the bytecode compiler (`fortress compile` + `run`) (`repo-internals.md:95-129`).
- The static type checker (Scala, `scala_src/typechecker/`) runs only on the compile path; `walk` turns it off and there is no switch to make it run in the interpreter (`repo-internals.md:127`); every "type error" seen from the interpreter is a run-time dispatch failure.
- `fortress typecheck` checks against `Library/CompilerLibrary.fsi`, not the interpreter's prelude, so it is not an oracle for interpreter programs (ledger row 69); making the checker usable on interpreter programs means giving it the interpreter's prelude, which is not a ledger row and not on the worklist as a separate item (it falls under worklist item 2, compiler-path library parity).
- The code generator lowers every type to a JVM reference type: `RR64` to the runtime class `FRR64`, no `dadd`/`dmul` anywhere in the generated loop (shown in bytecode, `perf-probes/boxing/javap/`); arrays are library objects over `get`/`put`, not `double[]` (`repo-internals.md:129`).
- On microGPT-shaped array code boxing is the dominant representational cost, 6.3× (dot product), 6.5× (matrix product) and 2.6× (row lift) over `double[]` in Java models of the program's three kernels, and nothing microGPT-shaped compiles: the compiler prelude lacks the array types, with `Array`, `Vector` and `Array3` undefined in `FlatArrays.fsi` (row 305, wider than row 72). On the interpreter, the only path that runs the kernels, 43.5% is the AST walk, 32.3% environment lookup, 5.2% type dispatch and 0% number representation (JFR on `krows`). The two one-line runtime defects it found are fixed (rows 302, 303; rung 0, `53362cb88`), and no array type goes into the compiler prelude: the arrays reach the compiled path with the one library (POSITIONS 2026-09-21, the library route). A failed compile leaves a 0-byte jar in the bytecode cache (`258105b3e`; `perf-probes/kernels/REPORT.md`).
- The boxing probe's scalar-loop reading, 156× primitive Java with boxing about 2% of it, is of the tree before rung 0's two fixes (rows 302, 303; `53362cb88`); of the costs it named, `countedseqloop`'s boxed indices and closure call (about 7%) and the representational rest (about 30%) are unaddressed (`perf-probes/boxing/REPORT.md`).
- The eager debug string of `BaseTask.inATransaction()` is fixed: the message is built only under the `debug` flag (`ProjectFortress/src/com/sun/fortress/runtimeSystem/BaseTask.java:248`; row 302; `53362cb88`; `compile-ladder/rung0/REPORT.md`).
- `FFloatLiteral`'s String round trip is fixed: the literal caches its `double` instead of re-parsing its text in `asRR64()` (`ProjectFortress/src/com/sun/fortress/compiler/runtimeValues/FFloatLiteral.java`; row 303; `53362cb88`; `compile-ladder/rung0/REPORT.md`).
- The benchmark numbers on record from 2026-09-15 (`bench1t` 9.3441 s, `bench1h` 6.0732 s) were taken on a quieter machine; the 2026-09-17 before-run of the same unmodified tree measured 13.0566 s and 8.8159 s, so absolute seconds are not comparable across sessions and only a before/after pair taken in one session is (`compile-ladder/rung0/REPORT.md`).
- `ant compileAll` leaves the bytecode cache holding no library jars: the first `fortress compile` after a rebuild of the compiler clears `default_repository/caches/bytecode_cache/`, and `fortress run` then dies with `NoClassDefFoundError: fortress/CompilerLibrary$GeneratorZZ32`; the library-order recompile of `repo-internals.md:170-179` restores it, about two minutes (observed 2026-09-17).
- The compiled path's bytecode cache can come up empty after a library-order rebuild that reports exit 0; re-running the same commands one at a time produced the jars (`perf-probes/boxing/REPORT.md`).
- Generic instantiations are stamped out at class-load time by ASM rewriting of template bytecode (`InstantiatingClassloader.java`, `repo-internals.md:129`); a size is in the stamped class's name (`pNatMeth$Box⟦3⟧`, `perf-probes/nat/java.md` § 1; `reviews/size-runtime-design-brief.md`), and its descriptor in a stamped class is `RTTIsize.of("<n>")` since climb batch 5 rung Z (`e893a3e00`).
- Implicit parallelism: `for` is parallel unless every generator is `seq`; the elements of a tuple and the operands of an operator are evaluated in parallel implicit threads (`tuple-expr.tex:23-24`, `operator-app.tex:59`; row 265). `FORTRESS_THREADS` sizes the work-stealing pool; there is no explicit threading in any of our programs.
- The compile path's checker cannot check `nat` parameters at all (see "The checker and the one library" below): so it stood until climb batch 4 rung N (`3f297441c`), since which it checks `nat` and `int` static parameters ("The compiled type checker checks `nat` and `int` static parameters" below), and since climb batch 5 rung Z (`e893a3e00`) a sized program loads and runs compiled ("A size is carried at run time as a descriptor from `RTTIsize.of`" under Landed semantics). Sizes in types (`nat` parameters) are "instantiated at runtime" by the specification (`trait-parameters.tex`, natparams); they check shapes when a value is made or passed; no optimization is built on them anywhere. A `nat`-typed parameter does not unify statically with a run-time-built array (row 23); the interpreter matches at dispatch, and a mismatch reads "Failed to find any matching overload", uncatchable (row 83). A literal size does unify (row 23's positive half).
- **The specification's own declaration of `Nothing` compiles on neither path, and the reason is name resolution, not codegen.** The Working Draft's `object Nothing extends Maybe[\T\] excludes Just[\T\] where {T extends Object}` (`Specification-1.0-frozen/basic-lib/convenience.tex:49`, kept since climb batch 5 rung S in `Specification/basic-lib/convenience.tex:61-65` marked "Not allowed") stops on both paths with a syntax error at `excludes`, because the grammar gives an object no `excludes` clause (`Specification/basic/objects.tex:84-86`; `reviews/spec-refused-examples/probes/SpecNothing.fss` and its captures). Without that clause, `fortress compile` and `fortress walk` give the identical single error, both rc=255: `T is undefined`, at the `T` inside the extends clause (`explorations/compile-ladder/rung-maybe/probes/WhereClauseNothing.fss`, `.txt`; `reviews/spec-refused-examples/probes/SpecNothingNoExcludes.fss`). A where clause on an object declaration does not bind a type variable used in that declaration's extends clause in either implementation. `CodeGen.forObjectDeclPrePass` would refuse the declaration a second time at codegen — `header.getWhereClause().isNone()` is one of its `canCompile` conditions (`ProjectFortress/src/com/sun/fortress/compiler/codegen/CodeGen.java:4093`) — but nothing reaches it. This is the mechanism behind the library's comment on its parametric `Nothing[\T\]`, "Obviously ought to be a non-parametric singleton when we get where clauses working" (`Library/FortressLibrary.fss:1442-1443`), and it is why both worlds must spell the empty case some other way.
