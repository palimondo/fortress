## Revival change

### The change

1. **The self type in the overloading check's test of exclusion.**
   - The team's sources: the team's compiled checker read a self type in a signature as the trait met with the types of its `comprises` clause (`removeSelf`, `ProjectFortress/src/com/sun/fortress/scala_src/types/TypeAnalyzer.scala:567-580`; the team's `ProjectFortress/compiler_tests/XXX10k.test`), while the team's library declares its additive group by an F-bound with no `comprises` clause (`trait AdditiveGroup[\T extends AdditiveGroup[\T\]\]`, `Library/FortressLibrary.fsi:264-269`), whose `self` the checker then typed as the plain trait; the Working Draft gave `self` the trait's type (`Specification-1.0-frozen/basic/expressions/var-ref.tex:53-54`). Before this change the checker read the plain trait type in every rule of overloading (`FunctionalMethod.parameters()`, `ProjectFortress/src/com/sun/fortress/compiler/index/FunctionalMethod.java:152-166`).
   - What the tree now does: the test of whether two declarations' parameter types exclude each other reads the `self` of a functional method of a trait whose self type comes from its F-bound as `C[\X\] & X` (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/OverloadingChecker.scala:552-573`, `:614`); specificity, the Meet Rule, the coverage of a meet and the Return Type Rule keep the plain trait type. Tests: `ProjectFortress/compiler_tests/ExclusionSelfTypeScalarRight.test` (accepted), `XXXExclusionSelfTypeSharedLeft.test` and `XXXExclusionSelfTypeSharedRight.test` (refused: an object that is an array of itself and an additive group of itself lies in both domains).
   - The reason: with the overloads of symbolic operators checked, the checker refused the library's pairs between the additive group's `+` and `-` and the operators between an array and a number, "Invalid overloading of + in API FortressLibrary: [\T extends AdditiveGroup[\T\]\](AdditiveGroup[\T\], T)->T @ FortressLibrary.fsi:267:5-37 and [\T extends Number AdditiveGroup[\T\], I\](Array[\T,I\], T)->Array[\T,I\] @ FortressLibrary.fsi:2702:1-89", 8 such errors, though no call fits both; the specification requires every extender of a self-typed trait to be a subtype of its static argument for the self-type parameter (`Specification/basic/traits.tex:285-302`), so every `self` is an `X`.
2. **The static parameters' bounds in the test of exclusion.**
   - The team's sources: the type group's existential reduction solves the condition that the meet is not empty together with the bounds of its static parameters (`Papers/Types/exc-reduction.tick:40-46`, `:68`); the team's `reduceED` conjoined the bounds, "Add bounds (even if we can't use them very well yet)" (`ProjectFortress/src/com/sun/fortress/scala_src/types/TypeSchemaAnalyzer.scala:382-389` before this change), but its unifier takes an equality only from a lower bound equal to an upper bound (`ProjectFortress/src/com/sun/fortress/scala_src/typechecker/Formula.scala:684-698`), so a bound never fixed a static parameter.
   - What the tree now does: the test of exclusion also reads each static parameter at the top of the meet (the meet itself, a tuple's element, a member of an intersection or union) as within its declared bounds, alone and never beside the parameter (`TypeSchemaAnalyzer.scala:448-543`; `ProjectFortress/src/com/sun/fortress/scala_src/overloading/OverloadingOracle.scala:326-327`); no other reduction reads them. Tests: `ProjectFortress/compiler_tests/ExclusionBoundsScalarLeft.test`, `ExclusionSelfTypeBoundsScalarRight.test` and `ExclusionVectorScalarBlock.test` (accepted), `XXXExclusionBoundsMeetAtObject.test` (refused: the two bounds meet at an object) and `XXXExclusionExcludingBoundsBox.test` (refused: `tint` over a box, whose instance at `Bottom` lies in both domains).
   - The reason: the pairs with the number on the left need the equality of the two static parameters that only the bounds give, and the pairs with the number on the right need it beside the self type; measured, the self type alone clears none of the 8 errors, the bounds alone the four with the number on the left, both all 8, and the distance with the overloads of symbolic operators checked falls from 191 to 183.
3. **A pair the checker now accepts and walk refuses.**
   - The team's sources: walk refuses at load `f[\T extends { K, R[\T\] }\](x: T)` beside `f(x: Z)`, where `K comprises { A, B, C }`, `Z excludes { A, B }` and `C extends Z` but not `R`: "fails the Meet Rule: neither is found to be more specific than the other or to exclude it, and no declaration is found that is more specific than both and applies to every call to which both apply" (`ProjectFortress/src/com/sun/fortress/interpreter/evaluator/values/OverloadedFunction.java:835`); the specification reads each static parameter "for any type within its bound" (`Specification/advanced/overloading.tex:582-588`), and its appendix of changes lists the case as not settled (`Specification/appendices/changes.tex:4135-4140`).
   - What the tree now does: the checker accepts the pair, and the compiled program runs `f(A)` as "R" and `f(C)` as "Z" (`ProjectFortress/compiler_tests/OverloadTwoBoundsClosedTraitExclusion.test`); walk still refuses it at load (`ProjectFortress/tests/OverloadTwoBoundsClosedTraitExclusionWalk.test`).
   - The reason: with the bounds read, the meet is `K & R[\T\] & Z`, which the checker's normal form makes empty (the only listed type of `K` that `Z` admits is `C`, which is no `R`), so no value lies in both domains.
