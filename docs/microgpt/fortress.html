9.1 In the model's file

Six places in MicroGptFlat.fss have a form that a gap of today's tree forces. Each has a box at the place that reads the line.

  1. Lines 21 to 24 declare the postfix operator T^T, the transpose, in the model's file. Its place would be FlatArrays.fss, the file of array helpers that the program imports, beside the function transposetranspose. The parser refuses this declaration in an api (the gap ledger's row 133). Part 2, the transpose.

  2. Outside lines 23 and 24, every array type of the model is Array⟦ℝ64,ℤ32⟧Array[\RR64,ZZ32\]Array⟦RR64,ZZ32⟧ or its like, without a size. The library's VectorVector and MatrixMatrix carry their sizes in the type. Under walk, a function with a size parameter cannot be passed as an argument (row 156). The model passes four functions to rowsrows, the function of FlatArrays.fss that applies a function to every row of a matrix. The four are rmsnrmsn, the RMS norm; smsm, the softmax; and their backward forms, rmsn_brmsn_b and sm_bsm_b. Types with sizes for the model are your open decision D.   3. Lines 37 to 41 write the layout table, the names and sizes of the nine weight matrices, as two functions with ifif chains. Walk refuses a typed array literal at the top level (row 142). Part 2, the nine matrices.

  4. Line 43 writes ⟦ℤ32⟧[\ZZ32\]⟦ZZ32⟧, the type of the result, after ∑SUM. Walk finds the type; the compiled path's checker does not (row 731). Part 2, the nine matrices.

  5. Line 70 writes transpose(…)transpose(...) where lines 63 to 68 write T^T. A call cannot be followed by T^T (rows 144 and 158). Part 6, the two tables.

  6. Lines 88 to 90 write the type of each mutable variable. The parser's checks refuse var p = …var p = ... without one (row 177). Part 7, the training loop.

9.2 In FlatArrays.fss and the loader

The model's lines read as they do because FlatArrays.fss supplies what the library does not. By your rulings, the model's text is the notation, FlatArrays.fss is repaired around it, and what a fuller library would hold moves into the library. FlatArrays.fss still builds these itself:

  • The operators on whole arrays: ×× and // between two arrays, // and >> between an array and a number, and √SQRT√, expexp and loglog of an array, in lines 25 to 32 of the file. The library has ++, −-, MINMIN and MAXMAX between an array and a number, and ++ and −- between two vectors or two matrices. It also has the product of two vectors element by element, as a function named pmulpmul and not as an operator.

  • rowsrows, in four forms: for one matrix, for two matrices, and the same two for rank-3 arrays. Each is a forfor loop over the rows that writes through a view of a row. The library has no operation "apply this function to every row".

  • Everything for rank-3 arrays, which are arrays with three indices: the product plane with plane, a matrix plus every plane, the transpose of every plane, and the views headsheads, unheadsunheads and planeplane. The library's algebra stops at matrices.

  • The views take their sizes at run time, through reflectreflect, the library's function that turns an integer into a size that a type can carry. That runs only under walk (row 307). Part 2.

  • transposetranspose is a function, and T^T cannot stand beside it in the api (row 133).

  • flatflat, which copies the nine gradient matrices into one vector, is two nested loops with a running offset.

DiagDiag, the diagonal matrix of Part 6, is different. A diagonal matrix with its own product is what the type system offers, and by your ruling it stays as it is.

In FlatData.fss, the file that reads the parameters and the corpus:

  • parseFloatparseFloat exists because the library's strToFloatstrToFloat gives wrong results (row 140).

  • parseRowparseRow scans a line character by character, because the library's splitsplit does not cut a string at spaces (row 141).

  • readLinesreadLines reads the file twice: once to count the lines, once to fill an array of that size.

9.3 What only walk runs

The whole program runs only under walk today. The project's goal is the same program compiled to bytecode and running fast, and the record tracks what stands between. Three of them touch lines of the model:

  • The nine views of the parameter vector get their sizes from reflectreflect, which does not run compiled (the gap ledger's row 307).

  • The tuple bindings at the top level, lines 17 to 19, stop the compile today (row 988, filed this week). Under walk they bind, and your ruling keeps the form.

  • 1.0 s1.0 s in line 82, the learning rate, is refused by the compiled path's checker when it checks against the interpreter's library: it cannot choose between the product of two floats and the product of two fractions (row 989, filed this week). Walk runs it as a product of floats.

Under walk there is no static type check. A program with a type error runs until the wrong value meets an operation that has no declaration for it. The error message in Part 7, "Failed to find any matching overload", is of this kind: it came at run time, from the product of a float and a fraction.

9.4 What looks odd and is the language

These forms are not gaps. They are how Fortress is designed, or how the revival has settled it.

  • (1.0 s) / nSteps(1.0 s) / nSteps in line 82. Division of two integers gives an exact fraction, so a float must come in first.

  • seq(…)seq(...) around a range, in lines 91 and in the loaders. A loop is parallel unless its ranges say otherwise.

  • Juxtaposition. β1 mbeta1 mβ1 m, x1 wqTx1 wq^T, 4 nEmbd4 nEmbd, r cr c and the arguments of printlnprintln are all the same operator, with a meaning chosen by the types.

  • The bars. |x||x| is the size of an array and the absolute value of a number.

  • DOT, SQRT and SUM in capitals. They are the ASCII names of the signs ·, √ and ∑. The source may hold a sign itself: the model writes ××, and in a run v · vv · v printed 61.0 and √ 4.0√ 4.0 printed 2.0. The sign ∑ is the exception today. The parser takes it as a prefix operator and not as a big operator, so only the name SUM works (the gap ledger's row 5).

  • The tuple bindings of lines 17 to 19, 53, 58, 67 and 68. Your ruling keeps this form for the constants.

  • The hand-written backward pass. It follows from the layout: the program holds plain arrays of floats, with no objects that could record how a number was made. Autograd, the field's name for a program that finds the gradient by itself, needs such objects.
